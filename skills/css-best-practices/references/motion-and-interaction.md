# CSS Motion and Interaction Rules (MDN, WCAG 2.2)

Extracted 2026-11-08 from the mdn/content repository and the WCAG 2.2 Understanding documents. Baseline statuses from the web-features dataset on the same date.

## Transitions and animations

- **Prefer CSS transitions and animations over script loops**: "we should always try to create our animations using CSS transitions/animations where possible. If your animations are really complex, you may have to rely on JavaScript-based animations instead." Why: "as long as the properties we want to animate do not trigger reflow/repaint" the browser "can move those sampling operations out of the main thread." Smell: a `requestAnimationFrame` or `setInterval` loop that writes `el.style.left` or `el.style.opacity` every frame for a fade or slide. Source: https://developer.mozilla.org/en-US/docs/Web/Performance/Guides/CSS_JavaScript_animation_performance#summary
- **Animate `transform` and `opacity`, not geometry**: "Properties that are rendered in their own layer don't even trigger a repaint, because the update is handled in composition." The examples given are `transform` and `opacity`. Why: "Properties that affect an element's geometry or position trigger a" style recalculation, a layout and a repaint, with `left`, `max-width`, `border-width`, `margin-left` and `font-size` as the named examples. Smell: `transition: width 0.3s, height 0.3s` on an accordion, `@keyframes slide { to { left: 100px; } }`, or `margin-left` and `top` in a transition list. Source: https://developer.mozilla.org/en-US/docs/Web/Performance/Guides/Animation_performance_and_frame_rate#css_property_cost
- **Scale a wrapper instead of resizing the box**: "While we could change the `font-size`, changing any properties that impact the box model negatively impacts performance. Instead, we wrap her name in a `<span>` and then scale and assign a color to that separately." Why: a box model change forces layout of the surrounding content on every frame, while `scale` is composited. Smell: `@keyframes pulse { 50% { font-size: 1.2em; padding: 12px; } }` or a hover state that transitions `padding`. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Animations/Using#adding_another_keyframe_animation
- **List transitioned properties explicitly, never `transition: all`**: "Only properties listed here are animated during transitions; changes to all other properties occur instantaneously as usual." Why: with `all`, every later change to the element, including layout-triggering ones such as `width` or `margin`, becomes an animation nobody designed, and the declaration no longer documents what moves. Smell: `transition: all 0.3s ease;` or `transition: 0.2s;` with no property name. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Transitions/Using#defining_transitions
- **Do not transition to or from `auto`**: "The specification recommends not animating from and to `auto`." Why: "Using animations with `auto` may lead to unpredictable results, depending on the browser and its version, and should be avoided." Smell: `.panel { height: 0; transition: height .3s; } .panel.open { height: auto; }`, or `max-height: 9999px` as a workaround. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Transitions/Using#which_css_properties_can_be_transitioned
- **Opt into `interpolate-size: allow-keywords` for height-to-content animations**: "Setting `interpolate-size: allow-keywords` enables interpolation between a `<length-percentage>` value and an intrinsic size value. Note that it does not enable animating between two intrinsic size values. One end of the animation must be a `<length-percentage>`." The page positions it for cases where "animating a non-box-model CSS property, such as `transform`, is not a viable solution." Why: "The behavior opted-into by `interpolate-size` cannot be enabled by default across the web because many sites in the wild use stylesheets that assume intrinsic size values cannot be animated." Smell: JavaScript reading `scrollHeight` to set a pixel `height` before a transition, or `max-height: 1000px` tricks on an accordion. Baseline: Limited. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/interpolate-size#description
- **Treat `will-change` as a last resort and keep it off large subtrees**: "Use the `will-change` property as a last resort to try to deal with existing performance problems. Don't use it to anticipate performance problems." Why: "Excessive use of `will-change` will result in excessive memory use and will cause more complex rendering to occur as the browser attempts to prepare for the possible change. This will lead to worse performance." and "applying a non-`auto` value on a large section, such as the `<body>`, can actually be bad for a page's performance." Smell: `* { will-change: transform; }`, `.card { will-change: transform, opacity; }` on every card in a grid, or `body { will-change: scroll-position; }`. Baseline: Widely (since 2022-07). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/will-change#description
- **Switch `will-change` on and off from script rather than leaving it in the stylesheet**: "it is a good practice to switch `will-change` on and off using script code before and after the change occurs." Why: "adding `will-change` directly to a stylesheet implies that the targeted elements are always a few moments away from changing and the browser will keep the optimizations for a much longer time than it would have otherwise." The page also says to add it before an animation starts and not inside `@keyframes`, because animated properties already behave as if listed. Smell: a permanent `will-change: transform` on an element that animates once on hover, or `will-change` inside a `@keyframes` block. Baseline: Widely (since 2022-07). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/will-change#description
- **Remember `transform` creates a stacking context and a containing block**: "If the property has a value different from `none`, a stacking context will be created. In that case, the element will act as a containing block for any `position: fixed;` or `position: absolute;` elements that it contains." Why: a `position: fixed` modal or header inside the transformed element is fixed to that element rather than the viewport, and its `z-index` can no longer escape the new context. Smell: `transform: translateZ(0)` or `translate3d(0, 0, 0)` "GPU hacks" on a page wrapper that contains fixed-position UI. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/transform

## Entry and exit

- **Transition `display` with `transition-behavior: allow-discrete` instead of a timeout**: "When transitioning these properties `transition-behavior: allow-discrete` needs to be set on the transitions. This effectively enables `display`/`content-visibility` transitions." Why: "When animating `display` from `block` (or another visible `display` value) to `none`, the value will flip to `none` at `100%` of the animation duration so it is visible throughout." Smell: `el.classList.add('fade-out'); setTimeout(() => el.style.display = 'none', 300)`, or `display: none` toggled instantly so the exit transition never shows. Baseline: Newly (since 2024-08). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Transitions/Using#transitioning_display_and_content-visibility
- **Use `@starting-style` for entry transitions, not a forced reflow**: "To enable first-style transitions, `@starting-style` rules are needed. They provide starting styles for elements that do not have a previous state, defining the property values to transition from." Why: "CSS transitions are by default not triggered on an element's initial style update, or when its `display` type changes from `none` to another value." Starting styles apply only on first render or when leaving `display: none`; on exit the element transitions back to its default rule, so exit values belong there. Smell: `requestAnimationFrame(() => el.classList.add('open'))`, `void el.offsetWidth;` or `setTimeout(..., 10)` to make a freshly inserted element animate. Baseline: Newly (since 2024-08). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@starting-style#description
- **Place `@starting-style` after the rule it starts from**: "To ensure that starting styles get applied, include the `@starting-style` at-rule after the "original rule". If you specify the `@starting-style` at-rule before the "original rule", the original styles will override the starting styles." Why: "The `@starting-style` at-rule and the "original rule" have the same specificity." Smell: a standalone `@starting-style { .toast { opacity: 0; } }` block at the top of the file with `.toast { opacity: 1; }` declared later. Baseline: Newly (since 2024-08). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@starting-style#description
- **Transition `display` and `overlay` on top layer elements**: "`display` is added to the list of transitioned elements to ensure the animated element is visible (set to `display: block` or another visible `display` value) throughout both the entry and exit animations. Without this, the exit animation would not be visible; in effect, the popover would just disappear." and "`overlay` is added to the list of transitioned elements to ensure that the removal of the element from the top layer is deferred until the animation ends." Why: "not doing this can result in the element being removed from the overlay too quickly, meaning the animation is not smooth or effective." Smell: `[popover] { transition: opacity .3s; }` or `dialog { transition: opacity .3s, transform .3s; }` with no `display` or `overlay` entries and no `allow-discrete`. Baseline: `transition-behavior` Newly (since 2024-08); `overlay` Limited. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@starting-style#animating_a_popover

## View transitions

- **Use the View Transition API rather than hand-built route transitions**: "The View Transition API provides an easy way of handling the required view changes and transition animations for both the above use cases." Why: hand-rolled SPA transitions must "Stop accidental user interactions with the old content from causing problems" and "Accessibility issues like loss of reading position, focus confusion, and strange live region announcement behavior can also result from having the new and old content both present in the DOM at once." Smell: old and new route containers both mounted with `.leaving` and `.entering` classes, a `transitionend` listener to unmount the old one, and `pointer-events: none` on the stale view. Baseline: Newly (since 2025-10). Source: https://developer.mozilla.org/en-US/docs/Web/API/View_Transition_API#concepts_and_usage
- **Keep every `view-transition-name` unique at the moment of the transition**: "The `view-transition-name` `<custom-ident>` must be unique for each rendered element taking part in the view transition." Why: "If two rendered elements have the same `view-transition-name` at the same time, the `ViewTransition.ready` `Promise` will reject and the transition will be skipped." Smell: `.card { view-transition-name: card; }` applied to a list of cards. Baseline: Newly (since 2025-10). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/view-transition-name#description
- **Use `match-element` instead of generating a name per item**: "you can use the `match-element` value, which causes the browser to give each selected element a unique internal `view-transition-name`". Why: "Giving each one a unique name can be inconvenient, especially as the number of elements gets larger". Note that "it can only be used for same-document view transitions." Smell: `.item-1 { view-transition-name: item-1; }` through `.item-50`, or `style="view-transition-name: item-${id}"` emitted in a template loop. Baseline: Newly (since 2025-10). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/view-transition-name#specifying_view-transition-name_values_automatically
- **Opt both documents in with `@view-transition` for cross-document transitions**: "To enable a basic MPA view transition, you need to specify a `@view-transition` at-rule in the CSS for both the current and destination documents to opt them in". Why: "No JavaScript is required, as the view update is triggered by a cross-document, same-origin navigation rather than a JavaScript-initiated DOM change." Smell: `@view-transition { navigation: auto; }` present only in the landing page stylesheet, or a script-driven fade on `beforeunload`. Baseline: Limited (cross-document view transitions). Source: https://developer.mozilla.org/en-US/docs/Web/API/View_Transition_API/Using#basic_mpa_view_transition

## Scrolling

- **Snap with CSS scroll snap, not scroll listeners**: "The scroll snap feature lets you define the snap positions where a scroll container's scrollport may end or "snap to" after a scrolling operation has completed." Why: the browser snaps as part of the scroll gesture itself, so there is no scroll handler, no debounce and no `scrollTo` fighting the user's finger. Smell: a `scroll` event listener that finds the nearest slide and calls `scrollTo` or `scrollIntoView`, or a carousel library used only for snapping. Baseline: Widely (since 2022-07). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Scroll_snap/Basic_concepts
- **Prefer `proximity`; use `mandatory` only when section size is known**: "the use of `mandatory` should be carefully considered and only used in situations where you know how much content is on the screen or scrollable section at any time." and "Never use `mandatory` if the content inside one of your child elements will overflow the parent container because user will not be able to scroll the overflowing content into view." Why: "users may find themselves in the frustrating position of never being able to scroll and view a certain point in the content." Smell: `html { scroll-snap-type: y mandatory; }` with `section { height: 100vh; }` holding text taller than a phone screen. Baseline: Widely (since 2022-07). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Scroll_snap/Basic_concepts#using_scroll-snap-type
- **Offset fixed headers with `scroll-padding`, not negative margins**: "A common use case for `scroll-padding` is to prevent scrolling content from being hidden by a fixed-position header." Why: "this property applies to all scroll containers, no matter the value of the `scroll-snap-type` property." Smell: `h2[id] { padding-top: 80px; margin-top: -80px; }`, `h2[id]::before { content: ""; display: block; height: 80px; margin-top: -80px; }`, or `window.scrollBy(0, -80)` after `scrollIntoView`. Baseline: Widely (since 2022-07). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/scroll-padding#preventing_content_from_being_hidden_by_a_fixed_header
- **Give individual targets `scroll-margin`**: "The `scroll-margin` property or the longhand scroll margin values can be set on child elements, defining an outset from the defined box." Why: "This allows for different amounts of space for different child elements and can be used in conjunction with `scroll-padding` on the parent." Smell: a single global `scroll-padding-top` inflated so one tall sticky element fits, or per-target offsets computed in JavaScript. Baseline: Widely (since 2022-07). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Scroll_snap/Basic_concepts#using_scroll-margin
- **Set `scroll-behavior: smooth` on the root and expect it to cover programmatic scrolls only**: "Note that any other scrolls, such as those performed by the user, are not affected by this property. When this property is specified on the root element, it applies to the viewport instead. This property specified on the `body` element will not propagate to the viewport." Why: "User agents are allowed to ignore this property." Smell: `body { scroll-behavior: smooth; }`, or a JavaScript easing loop for in-page anchor links. Baseline: Widely (since 2024-09). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/scroll-behavior
- **Stop scroll chaining with `overscroll-behavior`, not body locks**: "You can use `overscroll-behavior` to get rid of unwanted scroll chaining and the browser's "pull to refresh"-type behavior." and "setting a non-default `overscroll-behavior` such as `contain` or `none` on it will prevent scroll chaining to ancestor scroll containers. This can be used to prevent background scrolling while a dialog or overlay is open." Why: "once the dialog box's scroll boundary is reached, the underlying page will then start to scroll". Smell: `body.modal-open { overflow: hidden; position: fixed; }` toggled from JavaScript, or a `touchmove` listener calling `preventDefault()`. Baseline: Limited. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/overscroll-behavior#description
- **Drive scroll-linked effects with scroll-driven animations**: "It allows you to animate property values along a scroll-based timeline rather than the default time-based document timeline. This means that you can animate an element by scrolling the element, its scroll container, or its root element, rather than just by the passing of time." Why: the browser samples the scroll position itself, so there is no `scroll` handler, no layout read per frame and no lag behind the gesture. Smell: `window.addEventListener('scroll', () => bar.style.width = pct + '%')` for reading-progress bars, or `getBoundingClientRect()` in a scroll handler for parallax and reveal-on-scroll classes. Baseline: Newly (since 2026-10). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Scroll-driven_animations
- **Reserve `touch-action: none` for surfaces with their own gestures**: "A declaration of `touch-action: none;` may inhibit operating a browser's zooming capabilities. This will prevent people experiencing low vision conditions from being able to read and understand page content." Why: "The most common usage is to disable all gestures on an element (and its non-scrollable descendants) that provides its own dragging and zooming behavior". Smell: `body { touch-action: none; }` or `* { touch-action: none; }`; a horizontal carousel wants `touch-action: pan-y` and a button `touch-action: manipulation`. Baseline: Widely (since 2022-03). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/touch-action#accessibility

## Reduced motion and input media

- **Provide a `prefers-reduced-motion` path for every large movement**: "The setting is used to convey to the browser on the device that the user prefers an interface that removes, reduces, or replaces motion-based animations." Why: "Such animations can trigger discomfort for those with vestibular motion disorders. Animations such as scaling or panning large objects can be vestibular motion triggers." Smell: a `@keyframes` that scales, slides or parallax-shifts large blocks with no `@media (prefers-reduced-motion: reduce)` block anywhere in the stylesheet. Baseline: Widely (since 2022-07). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/prefers-reduced-motion
- **Reduce motion, do not blanket-disable animation**: "This preference does not mean all animations must be removed, which could be achieved with `* {animation: none !important;}`. Rather, users expect motion animation, including those triggered by user interaction, to be disabled unless the animation is essential to the functionality or the information being conveyed". Why: "The value of `prefers-reduced-motion` is `reduce`, not "none"." Smell: `@media (prefers-reduced-motion: reduce) { *, *::before, *::after { animation: none !important; transition: none !important; } }` as the only reduced-motion handling, which also kills colour fades and focus transitions that carry no motion. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Media_queries/Using_for_accessibility#reduced_motion
- **Put the reduced-motion override after the animation it tones down**: "the CSS within the reduced motion rules, with the same specificity but coming later in the CSS source order, will take precedence. As a result, the animation on the box will tone down to the `dissolve` animation, which is a more muted animation that is not a vestibular motion trigger." Why: a media query adds no specificity, so an override placed before the component rule silently loses. Smell: a `@media (prefers-reduced-motion: reduce)` block in a base file that component stylesheets loaded later overwrite. Baseline: Widely (since 2022-07). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/prefers-reduced-motion#examples
- **Guard hover-only reveals with `@media (hover: hover)` and give them a non-hover path**: "The `hover` CSS media feature can be used to test whether the user's primary input mechanism can hover over elements." Why: `hover: none` means "The primary input mechanism cannot hover at all or cannot conveniently hover (e.g., many mobile devices emulate hovering when the user performs an inconvenient long tap), or there is no primary pointing input mechanism." Smell: `.card .actions { opacity: 0; } .card:hover .actions { opacity: 1; }` with no `:focus-within` and no tap or button alternative, so touch users never see the actions. Baseline: not listed. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/hover

## Focus

- **Never remove the focus outline without a replacement**: "Never just remove the focus outline (visible focus indicator) without replacing it with a focus outline that will pass WCAG 2.1 SC 1.4.11 Non-Text Contrast." Why: keyboard users have no other cue to where they are on the page. Smell: `:focus { outline: none; }`, `button:focus { outline: 0; }`, or `a:focus { outline: none; }` in a reset. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Selectors/:focus#focus_outline_none
- **Style `:focus-visible`, not bare `:focus`**: "using the `:focus-visible` (instead of the `:focus` pseudo-class) allows authors to change the appearance of the focus indicator without changing when the focus indicator appears." Why: "Changing focus style can decrease usability, while removing focus styles makes keyboard navigation inaccessible for sighted users." and "focus styles are always required when users are navigating the page with the keyboard or when focus is managed via scripts". Smell: `button:focus { outline: none; }` added to stop the ring after mouse clicks, `:focus:not(:focus-visible) { outline: 0; }` polyfill hacks, or a `.js-focus-visible` class system. Baseline: Widely (since 2024-09). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Selectors/:focus-visible#focus_vs_focus-visible
- **Draw focus rings with `outline`, which costs no layout**: "Unlike other areas of the box, outlines don't take up space, so they don't affect the layout of the document in any way." Why: "Assigning `outline` a value of `0` or `none` will remove the browser's default focus style. If an element can be interacted with it must have a visible focus indicator. Provide obvious focus styling if the default focus style is removed." Smell: `:focus-visible { border: 2px solid var(--accent); }` on an element whose rest state has no border, so neighbours shift on focus. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/outline#description
- **Shape the ring with `outline-offset` and `border-radius` rather than stacked shadows**: "It is possible to change the style, color, and width using the `outline` property, the distance from the border using the `outline-offset` property, and corner angles using the `border-radius` property." Why: the ring can sit inside, flush with or outside the box and follows rounded corners, so there is no need to fake it; `outline-offset` takes "A negative value places the outline inside the element. A value of `0` places the outline so that there is no space between it and the element." Smell: `:focus-visible { outline: none; box-shadow: 0 0 0 2px #fff, 0 0 0 4px blue; }` written only to get a gap or rounded corners. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/outline#description

## Forms

- **Style `:user-invalid`, not `:invalid`**: "The `:user-invalid` pseudo-class must match an `:invalid`, `:out-of-range`, or blank-but `:required` element between the time the user has attempted to submit the form and before the user has interacted again with the form element." Why: `:invalid` matches from page load, so every empty required field is flagged before the user has typed. Smell: `input:invalid { border-color: red; }`, `input:required:invalid { ... }`, or `.was-validated :invalid` class juggling. Baseline: Widely (since 2026-05). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Selectors/:user-invalid
- **Style `:user-valid` for success states**: "unlike `:valid` it only matches once the user has interacted with it." Why: "if the control was valid when the user started interacting with it, the validity styling is changed only when the user shifts focus to another control. However, if the user is trying to correct a previously-flagged value, the control shows immediately when the value becomes valid." Smell: `input:valid { border-color: green; }` painting every untouched optional field green on load. Baseline: Widely (since 2026-05). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Selectors/:user-valid
- **Do not signal invalid input with colour alone**: "People who have certain types of color blindness will be unable to determine the input's state unless it is accompanied by an additional indicator that does not rely on color to convey meaning. Typically, descriptive text and/or an icon are used." Why: "The color red is commonly used to indicate invalid input." and some users cannot perceive that change. Smell: `:user-invalid { border-color: red; }` as the only change, with no error text, icon or `aria-describedby` message. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Selectors/:invalid#accessibility
- **Auto-size text fields with `field-sizing: content` plus `min-width` and `max-width`**: "Avoid setting a fixed `width` and `height` when using `field-sizing: content` because they will reimpose a fixed size on the control. However, using properties like `min-width` and `max-width` alongside `field-sizing: content` is quite effective". Why: `field-sizing: content` "provides a way to configure text inputs to shrinkwrap their content and grow as more text is entered." and "If no minimum width is set on the control, it will only be as wide as the text cursor." Smell: an `input` listener setting `textarea.style.height = textarea.scrollHeight + 'px'`, or `field-sizing: content; width: 320px;`. Baseline: Newly (since 2026-06). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/field-sizing#field-sizing_interaction_with_other_size_settings

## Dialogs and popovers

- **Use `<dialog>` with `showModal()` instead of a `div` modal and a focus trap**: "While dialogs can be created using other elements, the native `<dialog>` element provides usability and accessibility features that must be replicated if you use other elements for a similar purpose." Why: "When implementing modal dialogs, everything other than the `<dialog>` and its contents should be rendered inert using the `inert` attribute. When using `<dialog>` along with the `HTMLDialogElement.showModal()` method, this behavior is provided by the browser." and "Keyboard users expect the Esc key to close modal dialogs". Smell: `.modal { position: fixed; inset: 0; z-index: 9999; }` on a `<div role="dialog">` with a hand-written Tab-cycling focus trap and a `keydown` Escape handler. Baseline: Widely (since 2024-09). Source: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/dialog#accessibility
- **Open dialogs with `show()` or `showModal()`, not the `open` attribute or `display`**: "It is recommended to use the `.show()` or `.showModal()` method to render dialogs, rather than the `open` attribute. If a `<dialog>` is opened using the `open` attribute, it is non-modal." Why: dialogs "invoked by the `showModal()` method implicitly have `aria-modal="true"`, whereas `<dialog>` elements invoked by the `show()` method or displayed using the `open` attribute or by changing the default `display` of a `<dialog>` are exposed as `[aria-modal="false"]`." Smell: `dialog.is-open { display: block; }`, `dialog { display: block; }` in a stylesheet, or `dialog.setAttribute('open', '')`. Baseline: Widely (since 2024-09). Source: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/dialog#attributes
- **Style the scrim with `::backdrop`, not a sibling overlay**: "The CSS `::backdrop` pseudo-element can be used to style the backdrop of a modal dialog, which is displayed behind the `<dialog>` element when the dialog is displayed using the `HTMLDialogElement.showModal()` method." Why: "This pseudo-element could be used, for example, to blur, darken, or otherwise obfuscate the inert content behind the modal dialog." Smell: `.overlay { position: fixed; inset: 0; background: rgb(0 0 0 / 50%); z-index: 9998; }` rendered as a separate element next to the dialog. Baseline: Widely (since 2024-09). Source: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/dialog#css_styling
- **Animate dialogs through `display`, `overlay` and `@starting-style`**: "When animating using CSS transitions, `transition-behavior: allow-discrete` needs to be set to enable the above behavior. This behavior is available by default when animating with CSS animations; an equivalent step is not required." Why: "`<dialog>`s are set to `display: none;` when hidden and `display: block;` when shown, as well as being removed from / added to the top layer and the accessibility tree. Therefore, for `<dialog>` elements to be animated the `display` property needs to be animatable." Smell: `dialog { transition: opacity .3s; } dialog[open] { opacity: 1; }` where closing is instant, or a `.closing` class plus `setTimeout(() => dialog.close(), 300)`. Baseline: `transition-behavior` and `@starting-style` Newly (since 2024-08); `overlay` Limited. Source: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/dialog#animating_dialogs
- **Build tooltips, menus and toasts on `popover`, not `z-index: 9999`**: "In its simplest form, a popover is created by adding the `popover` attribute to the element that you want to contain your popover content." Why: "When a popover is shown, it has `display: none` removed from it and it is put into the top layer so it will sit on top of all other page content." Smell: `.tooltip { position: absolute; z-index: 9999; }`, `.dropdown-menu { z-index: 10000; }`, and a `document` click listener to close on outside click. Baseline: Newly (since 2025-01). Source: https://developer.mozilla.org/en-US/docs/Web/API/Popover_API/Using#creating_declarative_popovers
- **Popover for non-modal, `<dialog>` for modal**: "Popovers created using the Popover API are always non-modal. If you want to create a modal popover, a `<dialog>` element is the right way to go." Why: "Typical use cases for the popover API include user-interactive elements like action menus, custom "toast" notifications, form element suggestions, content pickers, or teaching UI." Smell: `[popover]` plus `inert` sprayed on siblings to fake modality, or a `<dialog>` opened with `showModal()` for a hover tooltip. Baseline: Newly (since 2025-01). Source: https://developer.mozilla.org/en-US/docs/Web/API/Popover_API#concepts_and_usage
- **Rely on `popover="auto"` light dismiss instead of outside-click handlers**: with auto state "you can hide the popover by clicking outside it." and "The popover can also be closed, using browser-specific mechanisms such as pressing the Esc key." Why: "Usually, only one `auto` popover can be shown at a time", so the browser already manages the stack you would otherwise track by hand. Smell: `document.addEventListener('click', e => { if (!menu.contains(e.target)) close(); })` and a `keydown` Escape handler on an element that already has `popover`. Baseline: Newly (since 2025-01). Source: https://developer.mozilla.org/en-US/docs/Web/API/Popover_API/Using#auto_state_and_light_dismiss
- **Wire popovers with `popovertarget` to get focus order and ARIA for free**: "When the popover is shown, the keyboard focus navigation order is updated so that the popover is next in the sequence" and "an implicit `aria-details` and `aria-expanded` relationship is set up between them." Why: when a popover is opened through the `source` option instead, "only the focus navigation order changes are made, not the implicit ARIA relationship." Smell: a button toggling `aria-expanded` by hand and calling `showPopover()` with no `popovertarget` or `commandfor`. Baseline: Newly (since 2025-01). Source: https://developer.mozilla.org/en-US/docs/Web/API/Popover_API/Using#popover_accessibility_features
- **Match shown popovers with `:popover-open`, not `:open` or a class**: "The `:popover-open` CSS pseudo-class represents a popover element (i.e., one with a `popover` attribute) that is in the showing state. You can use this to apply style to popover elements only when they are shown." Why: popovers have showing and hidden states that are separate from the open and closed states `:open` tracks on `<dialog>` and `<details>`. Smell: `.tooltip.is-visible`, `[popover].open`, or `[popover]:open`. Baseline: Newly (since 2025-01). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Selectors/:popover-open

## Anchor positioning

- **Tether tooltips with CSS anchor positioning instead of JavaScript measurement**: "Historically, associating an element with another element and dynamically changing a positioned element's location and size based on an anchor's position required JavaScript, which added complexity and performance issues. It also wasn't guaranteed to work in all situations." Why: "The features defined in the CSS anchor positioning module enable implementing such use cases performantly and declaratively with CSS (and HTML) instead of JavaScript." Smell: `getBoundingClientRect()` in `scroll` and `resize` handlers to set `top` and `left` on a tooltip, or a positioning library imported only for menus. Baseline: Limited. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Anchor_positioning/Using#fundamental_concepts
- **Scope repeated anchor names with `anchor-scope`**: "if a document contains multiple repeated components, each with a positioned element tethered to an anchor, all the positioned elements will be anchored to the last anchor on the page unless each component uses a different anchor name." Why: "The `anchor-scope` property can fix this problem by limiting the visibility, or "scope", of an `anchor-name` value to a specific subtree." Smell: `.card .trigger { anchor-name: --trigger; }` in a list with no `anchor-scope: --trigger` on `.card`. Baseline: Limited. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Anchor_positioning/Using#anchor_scoping
- **Always give anchored elements `position-try-fallbacks`**: "Anchor-positioned elements should always appear in a convenient place for the user to interact with, if at all possible, regardless of where their anchor is positioned." Why: "If the positioned element's initial position would overflow, the browser will try each fallback position option; the first fallback option that doesn't cause the element to overflow its containing block is applied." Smell: `position-area: top;` on a tooltip with no `position-try-fallbacks`, so it clips at the top of the viewport. Baseline: Limited. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/position-try-fallbacks#description
- **Reset the popover `margin` when positioning with `anchor()`**: "it's advisable to set the popover's `margin` to `0`, or a positive `<length>` if you want to create some space between the positioned element and the anchor, so that your positioning works as expected." Why: "The usual culprit is the default style for `margin` (`auto`)" and "This is not an issue with popovers positioned with `position-area`". Smell: `[popover] { top: anchor(bottom); left: anchor(left); }` with the UA `margin: auto` still in place, leaving the popover centred in the viewport. Baseline: Limited. Source: https://developer.mozilla.org/en-US/docs/Web/API/Popover_API/Using#popover_anchor_positioning

## Hiding and disabling

- **Use `inert` for regions, `disabled` for single controls**: "While `inert` is a global attribute and can be applied to any element, it is generally used for sections of content. To make individual controls "inert", consider using the `disabled` attribute, along with CSS `:disabled` styles, instead." Why: "An inert element, along with its descendants, gets removed from the tab order and accessibility tree." Smell: `inert` on one `<button>`, or `pointer-events: none` plus `tabindex="-1"` on everything behind a custom overlay instead of `inert` on the page wrapper. Baseline: Widely (since 2025-10). Source: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Global_attributes/inert
- **`pointer-events: none` neither disables nor hides**: "Elements with `pointer-events: none` will still receive focus through sequential keyboard navigation using the Tab key." Why: "the value `none` instructs the pointer event to go "through" the element and target whatever is "underneath" that element instead." so keyboard users can still activate the control and whatever lies beneath receives the clicks. Smell: `.btn.disabled { pointer-events: none; opacity: .5; }` on a link or button that should carry `disabled` or sit inside an `inert` region, or `pointer-events: none` on an overlay meant to block interaction. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/pointer-events#description
- **Keep `user-select: none` off readable content**: "The `user-select` CSS property controls whether the user can select text." Why: "`user-select` is not an inherited property, though the initial `auto` value makes it behave like it is inherited most of the time." so a value on a wrapper blocks selection in every descendant. Smell: `body { user-select: none; }` or `* { -webkit-user-select: none; user-select: none; }` added to stop highlight flashes; limit it to drag handles and button labels. Baseline: Limited. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/user-select
- **`visibility: hidden` keeps the box in flow**: "The `visibility` CSS property shows or hides an element without changing the layout of a document." and "To both hide an element and remove it from the document layout, set the `display` property to `none` instead of using `visibility`." Why: the hidden box still reserves its space. Smell: `.banner.dismissed { visibility: hidden; }` leaving an empty strip, or `visibility: hidden` used to remove a list item. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/visibility
- **Hide interactive content with `visibility`, not `opacity: 0`**: for `hidden`, "The element box is invisible (not drawn), but still affects layout as normal. Descendants of the element will be visible if they have `visibility` set to `visible`. The element cannot receive focus". Why: "Using a `visibility` value of `hidden` on an element will remove it from the accessibility tree. This will cause the element and all its descendant elements to no longer be announced by screen reading technology." Smell: `.menu { opacity: 0; } .menu.open { opacity: 1; }` with links that stay tabbable and announced while invisible. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/visibility#accessibility
- **Transition `visibility` together with `opacity` for fades**: "When animated, visibility values are interpolated between visible and not-visible. One of the start or ending values must therefore be `visible` or no interpolation can happen. The value is interpolated as a discrete step, where values of the easing function between `0` and `1` map to `visible`". Why: the element stays visible for the whole fade and flips to hidden only at the end, so it becomes unfocusable exactly when it becomes invisible. Smell: `transition: opacity .3s;` with `visibility: hidden` applied instantly so the element vanishes before the fade, or a `setTimeout` to flip `visibility` after the transition. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/visibility#interpolation

## WCAG criteria decided in CSS

- **Keep a visible focus indicator (2.4.7 Focus Visible, AA)**: "Any keyboard operable user interface has a mode of operation where the keyboard focus indicator is visible." Why: "The purpose of this success criterion is to help a person know which element has the keyboard focus." and "The focus indicator must not be time limited: when the keyboard focus is shown, it must remain visible." Smell: `:focus { outline: none; }` with no replacement, or a focus ring that fades out through an `animation` after a delay. Source: https://www.w3.org/WAI/WCAG22/Understanding/focus-visible.html
- **Make the focus ring at least a 2px perimeter with 3:1 change (2.4.13 Focus Appearance, AAA)**: the indicator area "is at least as large as the area of a 2 CSS pixel thick perimeter of the unfocused component or sub-component, and" "has a contrast ratio of at least 3:1 between the same pixels in the focused and unfocused states." Why: "The purpose of this success criterion is to ensure a keyboard focus indicator is clearly visible and discernible." Smell: `:focus-visible { outline: 1px dotted; }`, a colour-only text change on focus, or `outline-color` one shade away from the background. Source: https://www.w3.org/WAI/WCAG22/Understanding/focus-appearance.html
- **Give component boundaries and focus rings 3:1 contrast (1.4.11 Non-text Contrast, AA)**: "Visual information required to identify user interface components and states, except for inactive components or where the appearance of the component is determined by the user agent and not modified by the author" must have "a contrast ratio of at least 3:1 against adjacent color(s)". Why: "Low contrast controls are more difficult to perceive, and may be completely missed by people with a visual impairment." and "If the focus indicator is styled by the author, it must meet the 3:1 contrast ratio with adjacent colors." Smell: `outline-color: #ccc` on white, or `input { border: 1px solid #e0e0e0; }` as the only thing marking the field's extent. Source: https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html
- **Reflow to 320 CSS pixels without two-dimensional scrolling (1.4.10 Reflow, AA)**: "Content can be presented without loss of information or functionality, and without requiring scrolling in two dimensions for:" "Vertical scrolling content at a width equivalent to 320 CSS pixels;" Why: "When lines of text extend beyond the edge of a viewport, users will be forced to scroll back-and-forth to read line by line. This can cause them to lose their place and can significantly increase both physical and cognitive effort." Smell: `min-width: 1024px` or `width: 1200px` on a layout wrapper, `white-space: nowrap` on running text, or a fixed-pixel sidebar that never collapses. Source: https://www.w3.org/WAI/WCAG22/Understanding/reflow.html
- **Make pointer targets at least 24 by 24 CSS pixels or space them (2.5.8 Target Size (Minimum), AA)**: "The size of the target for pointer inputs is at least 24 by 24 CSS pixels, except when:" the spacing exception applies, where "Undersized targets (those less than 24 by 24 CSS pixels) are positioned so that if a 24 CSS pixel diameter circle is centered on the bounding box of each, the circles do not intersect another target or the circle for another undersized target;" Why: "Users with dexterity limitations and those who have difficulty with fine motor movement find it difficult to accurately activate small targets when there are other targets that are too close." Smell: `.icon-btn { width: 16px; height: 16px; padding: 0; }` in a toolbar, or `gap: 2px` between 20px controls. Source: https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html
- **Let text scale to 200 percent (1.4.4 Resize Text, AA)**: "Except for captions and images of text, text can be resized without assistive technology up to 200 percent" "without loss of content or functionality." Why: "The author's responsibility is to create web content that does not prevent the user agent from scaling the content effectively." Smell: `touch-action: none` on `body`, `height: 40px; overflow: hidden` on a text container with `font-size: 12px`, or `font-size: 11px` with `line-height: 11px` clipping at zoom. Source: https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html
- **Survive user text spacing overrides (1.4.12 Text Spacing, AA)**: no loss of content or functionality when setting "Line height (line spacing) to at least 1.5 times the font size;" "Spacing following paragraphs to at least 2 times the font size;" "Letter spacing (tracking) to at least 0.12 times the font size;" "Word spacing to at least 0.16 times the font size." Why: "The intent of this success criterion (SC) is to ensure that when people override author-specified text spacing to improve their reading experience, content is still readable and operable." Smell: `height: 48px; overflow: hidden;` on a card title, `line-height: 1 !important;` or `letter-spacing` with `!important`, and fixed-height buttons whose labels clip when spacing grows. Source: https://www.w3.org/WAI/WCAG22/Understanding/text-spacing.html
- **Make interaction-triggered motion switchable off (2.3.3 Animation from Interactions, AAA)**: "Motion animation triggered by interaction can be disabled, unless the animation is essential to the functionality or the information being conveyed." Why: "if scrolling a page causes elements to move (other than the essential movement associated with scrolling) it can trigger vestibular disorders." and "Another animation that is often non-essential is parallax scrolling." Smell: `animation-timeline: scroll()` parallax or scroll-driven `translate` with no `@media (prefers-reduced-motion: reduce)` branch, or hover animations that slide large panels. Source: https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html
- **Make hover and focus content dismissible, hoverable and persistent (1.4.13 Content on Hover or Focus, AA)**: "A mechanism is available to dismiss the additional content without moving pointer hover or keyboard focus," "If pointer hover can trigger the additional content, then the pointer can be moved over the additional content without the additional content disappearing;" "The additional content remains visible until the hover or focus trigger is removed, the user dismisses it, or its information is no longer valid." Why: "Examples of such interactions can include custom tooltips, sub-menus and other non-modal popups which display on hover and focus." which "often leads to accessibility issues". Smell: `.tip { display: none; } .trigger:hover + .tip { display: block; }` with a gap between trigger and tip so the pointer cannot reach it, no Esc dismissal, or an `animation` that hides the tip after a fixed delay. Source: https://www.w3.org/WAI/WCAG22/Understanding/content-on-hover-or-focus.html
