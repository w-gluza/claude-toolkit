# CSS Cascade and Selector Rules (MDN)

Extracted 2026-11-08 from the mdn/content repository. Baseline statuses from the web-features dataset on the same date.

## Cascade layers

- **Import third-party CSS into a layer instead of fighting it**: "try not to use `!important` to override external styles. Instead, use `@import` together with the `layer` keyword or `layer()` function to import external stylesheets (from frameworks, widget stylesheets, libraries, etc.) into layers." Why: "The `!important` flag reverses the precedence of cascade layers." and "Importing stylesheets into a layer as the first declaration in your CSS demotes their precedence, and author-defined layers, defined later in your CSS, will have higher precedence." Smell: `@import "bootstrap.min.css";` with no `layer()`, followed by `.btn { padding: 0 !important; }` in the project CSS. Baseline: Widely (since 2024-09). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Cascade/Introduction#importance_and_layers
- **Declare the layer order once, up front**: "This is useful because the initial order in which layers are declared indicates which layer has precedence." Use a statement at-rule such as `@layer reset, base, components, utilities;` at the top of the entry stylesheet. Why: "A rule in `utilities` would be applied _even if it has lower specificity_ than the rule in `theme`. This is because once the layer order has been established, specificity and order of appearance are ignored. This enables using simpler CSS selectors because you do not have to ensure that a selector will have high enough specificity to override competing rules; all you need to ensure is that it appears in a later layer." Smell: `@layer components { ... }` blocks scattered across many files with no single `@layer a, b, c;` statement, so the order depends on which file loads first. Baseline: Widely (since 2024-09). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@layer#description
- **Remember that unlayered styles beat every layer**: "Styles that are not defined in a layer always override styles declared in named and anonymous layers." Why: "In all origin types, normal styles contained in layers have the lowest precedence." Smell: a rule inside `@layer components` being "fixed" by adding an id or a doubled class when the thing overriding it is a stray unlayered rule that should have been moved into a layer. Baseline: Widely (since 2024-09). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@layer#description
- **Use layers, not specificity, to take precedence over vendor CSS**: "Leveraging cascade layers is the standard way of enabling one set of styles to take precedence over another set of styles; cascade layers enable this without using specificity!" Why: "When two selectors from different layers match the same element, origin and importance take precedence; the specificity of the selector in the losing stylesheet is irrelevant." Smell: `body .container .btn.btn-primary { }` written to beat a framework rule, or an `overrides.css` file whose every selector mirrors the vendor selector plus one extra class. Baseline: Widely (since 2024-09). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Cascade/Specificity#precedence_over_third-party_css
- **Keep `@import` at the top of the file**: "An `@import` rule _must_ be defined at the top of the stylesheet, before any other at-rule (except @charset and @layer) and style declarations, or it will be ignored." Why: "As the `@import` at-rule is declared after the styles it is invalid and hence ignored." Smell: `@import "vendor.css" layer(vendor);` appearing after a `* { margin: 0; }` reset or after a `:root { --token: ... }` block. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@import
- **Put important overrides in the first declared layer**: "If you need to override an external stylesheet containing important declarations, create a cascade layer containing the needed overrides, and declare that layer first." Why: "Important declarations found in a layer take precedence over important declarations found outside of a layer. Important declarations found in the first layer (A) take precedence over important declarations found in layer B, which take precedence over important declarations found in layer C, which take precedence over important declarations found outside of a layer." Smell: `!important` overrides sprinkled through unlayered component CSS to beat a vendor `!important`, instead of a short `@layer importantOverrides;` declared before everything else. Baseline: Widely (since 2024-09). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/important#best_practices

## Specificity

- **Keep specificity as low as possible**: "Generally, you want to keep specificity down to a minimum". Why: "Instead of using `!important`, consider using cascade layers and using low weight specificity throughout your CSS so that styles are easily overridden with slightly more specific rules. Using semantic HTML helps provide anchors from which to apply styling." Smell: `#app .page .card .card__title { }` or `html body main section p { }` where a single class would match the same element. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Cascade/Specificity#the_is_not_has_and_css_nesting_exceptions
- **Do not style by id selector; use the attribute form if an id is the only hook**: "Including the `id` of an element as an attribute selector rather than an id selector is a good way to make an element more specific without adding an overabundance of specificity." Why: "The selector with the greater value in the _ID_ column wins no matter what the values are in the other columns." Smell: `#header .nav a { }` (1-1-1) where `[id="header"] .nav a { }` (0-2-1) or a plain class would do. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Cascade/Specificity#reducing_id_specificity
- **Stop qualifying classes with tags and stacking type selectors**: "no matter how many elements and pseudo-elements are included, even if there were 150, TYPE components never have precedence over _CLASS_ components." Why: "The column values are compared starting from left to right when column values are equal." so the extra tag only ties the rule to the markup without winning anything. Smell: `div.card { }`, `ul.nav li a { }`, or `html body main input { }` written to beat `.lead` or `:root input`. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Cascade/Specificity#examples
- **Do not double up selectors to win**: "Use this sparingly, if at all. If using selector duplication, always comment your CSS." Why: duplication such as `.myClass.myClass.myClass span` (0-3-1) is "for increasing specificity when overriding very specific selectors over which you have no control", which a layer solves without touching the selector. Smell: `.btn.btn { }` or `.modal.modal.modal { }` in first-party CSS. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Cascade/Specificity#increasing_specificity_by_duplicating_selector
- **Use `:where()` to scope a selector without adding weight**: "You can also include the `id` or any part of a selector as a parameter in the `:where()` specificity-adjustment pseudo class if you need to make a selector more specific but don't want to add any specificity at all." Why: "The specificity-adjustment pseudo-class `:where()` always has its specificity replaced with zero, `0-0-0`. It enables making CSS selectors very specific in what element is targeted without any increase to specificity." Smell: `#myContent h1 { }` (1-0-1) where `:where(#myContent) h1 { }` (0-0-1) would target the same heading and stay overridable. Baseline: Widely (since 2023-07). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Cascade/Specificity#reducing_id_specificity
- **Ship shared or library CSS at the lowest possible specificity**: "In creating third-party CSS to be used by developers who don't have access to edit your CSS, it's considered a good practice to create CSS with the lowest possible specificity." Why: "Then the developer implementing the widget can easily override the link color using only type selectors." Smell: a design-system package with `#defaultTheme a { color: red; }` instead of `:where(#defaultTheme) a { color: red; }`. Baseline: Widely (since 2023-07). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Cascade/Specificity#the_where_exception

## The important flag

- **Never use `!important` to win a specificity fight**: "Using `!important` to override specificity is considered a **bad practice** and should be avoided for this purpose." Why: "Understanding and effectively using specificity and the cascade can remove any need for the `!important` flag." Smell: `.modal { display: block !important; }` or `.hidden { display: none !important; }` added because another rule happened to be more specific. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Cascade/Specificity#the_!important_exception
- **Never ship `!important` in a library or shared component package**: "But definitely, don't use `!important` when writing plugins or frameworks that other developers will need to incorporate without being able to control." Why: "CSS declarations marked as important override any other declarations within the same cascade layer and origin." so consumers are left with no clean override path. Smell: `!important` inside `packages/ui/` or any CSS that is published for other teams to import. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Cascade/Specificity#the_!important_exception
- **Know that `!important` on a shorthand marks every longhand important**: "Declaring a shorthand property with `!important` sets all of sub-properties as important." Why: "This example shows one of the several reasons avoiding the important flag is generally recommended." Smell: `background: blue !important;` which also pins `background-image`, `background-size`, `background-position` and five other longhands, so a later `background-image: url(...)` silently fails. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/important#impact_on_shorthand_properties
- **Do not expect `!important` on a custom property to flow through `var()`**: "When the `!important` flag is added to a custom property value declaration, it makes the value assignment important. The `!important` flag is then stripped from the custom property value. The `!important` flag is not passed as part of the custom property value to the `var()` function." Why: the flag only decides which `--token` declaration wins, not how the consuming `color: var(--token)` cascades. Smell: `--brand: red !important;` written to force every `color: var(--brand)` to beat local `color` declarations. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/important#impact_on_custom_properties
- **Avoid inline styles; they force `!important` on everyone else**: "The only way to override inline styles is by using `!important`." Why: "Inline styles added to an element (e.g., `style="font-weight: bold;"`) always overwrite any normal styles in author stylesheets, and therefore, can be thought of as having the highest specificity." Smell: `style="display:none"` or `element.style.color = ...` in templates and scripts, paired with `p[style*="purple"] { color: rebeccapurple !important; }` style hacks in CSS. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Cascade/Specificity#inline_styles

## Modern selectors

- **Collapse repeated selector lists with `:is()`**: "The `:is()` pseudo-class can greatly simplify your CSS selectors." Why: a list such as `ol ol ul, ol ul ul, ol menu ul, ...` (18 lines) becomes `:is(ol, ul, menu) :is(ol, ul, menu) :is(ul, menu)`. Smell: a comma-separated selector list where every entry differs only by one slot, such as `section h1, article h1, aside h1, nav h1 { }`. Baseline: Widely (since 2023-07). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Selectors/:is#simplifying_list_selectors
- **Expect `:is()` to take the specificity of its heaviest argument**: "`:is()` counts towards the specificity of the overall selector (it takes the specificity of its most specific argument), whereas `:where()` has a specificity value of 0." Why: "the specificity weight provided by the `:is()`, `:has()` and `:not()` pseudo-classes is the value of the selector parameter, not of the pseudo-class." Smell: `:is(#sidebar, .panel) a { }` which gives 1-0-1 to every matching link, including the ones under `.panel`. Baseline: Widely (since 2023-07). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Selectors/:is#difference_between_is_and_where
- **Use `:where()` for resets and base styles that must stay overridable**: "The difference between `:where()` and `:is()` is that `:where()` always has 0 specificity, whereas `:is()` takes on the specificity of the most specific selector in its arguments." Why: "selectors inside `:where()` have specificity 0, so the orange footer link will be overridden by our type-only compound selector." Smell: `:is(section.is-styling, aside.is-styling) a { color: red; }` in a reset or theme layer, which then cannot be beaten by `footer a { color: blue; }`. Baseline: Widely (since 2023-07). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Selectors/:where
- **Wrap experimental selectors in `:is()` or `:where()` so one bad entry does not kill the list**: "When using `:is()` or `:where()` instead of the whole list of selectors being deemed invalid if one fails to parse, the incorrect or unsupported selector will be ignored and the others used." Why: "In CSS when using a selector list, if any of the selectors are invalid then the whole list is deemed invalid." Smell: `a:focus-visible, a:-webkit-any-link { }` or `:valid, :unsupported { }` as a plain comma list, so the supported half stops working in a browser that rejects the other half. Baseline: Widely (since 2023-07). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Selectors/:is#forgiving_selector_parsing
- **Reach for `:has()` before a JavaScript class toggle on the parent**: "The `:has()` pseudo-class does that by using `parent:has(child)` (for any parent) or `parent:has(> child)` (for direct parent)." Why: "Without the `:has()` pseudo-class, you cannot use CSS selectors to select a preceding sibling of a different type or a parent element." Smell: `form.classList.toggle("has-error", !!form.querySelector(":invalid"))` plus `.form.has-error { }`, where `form:has(:invalid) { }` does the same with no script. Baseline: Widely (since 2026-06). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Selectors/:has#selecting_a_parent_element
- **Anchor `:has()` to a specific container, never to `body`, `:root` or `*`**: "The anchor selector (the `A` in `A:has(B)`) should not be an element that has too many children, like `body`, `:root`, or `*`." Why: "Anchoring `:has()` to very general selectors can degrade performance because any DOM change within the entire subtree of a broadly selected element requires the browser to re-check the `:has()` condition." Smell: `body:has(.sidebar) { }`, `:root:has(.content) { }`, `*:has(.item) { }`. Baseline: Widely (since 2026-06). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Selectors/:has#avoid_broad_anchoring
- **Constrain the inner `:has()` selector with `>` or `+`**: "The inner selector (the `B` in `A:has(B)`) should use combinators like `>` or `+` to limit traversal." Why: "When the selector inside `:has()` is not tightly constrained, the browser might need to traverse the entire subtree of the anchor element on every DOM mutation to check if the condition still holds." Smell: `.ancestor:has(.foo) { }` or `.ancestor:has(.foo > *) { }` where `.ancestor:has(> .foo) { }` would express the intent. Baseline: Widely (since 2026-06). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Selectors/:has#minimize_subtree_traversals
- **Use `:nth-child(An+B of S)` when the count should skip non-matching siblings**: "By passing a selector argument, we can select the **nth** element that matches that selector." Why: "This is different from moving the selector outside of the function" because `li.important:nth-child(-n + 3)` "selects list items if they are among the first three children and match the selector `li.important`", not the first three important items. Smell: `li.noted:nth-child(-n + 3) { }` written to highlight the first three noted items. Baseline: Widely (since 2025-11). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Selectors/:nth-child#the_of_selector_syntax

## Nesting

- **Treat native nesting as `:is()`, not as Sass**: "The specificity of the `&` nesting selector is calculated using the largest specificity in the associated selector list. This is identical to how specificity is calculated when using the `:is()` function." Why: "CSS nesting is different from CSS preprocessors such as Sass in that it is parsed by the browser rather than being pre-compiled by a CSS preprocessor." Smell: `#a, b { & i { color: blue; } }` which gives `b i` a specificity of 1-0-0 plus 0-0-1 and beats `.foo i`. Baseline: Widely (since 2026-06). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Nesting/Nesting_and_specificity
- **Do not concatenate BEM suffixes with `&`**: "This is not possible in CSS nesting: when a combinator is not used, the nested selector is treated as a type selector. Allowing concatenation would break this." Why: the Sass habit `.component { &__child-element { } }` does not compile to `.component__child-element` in the browser; it is an invalid selector. Smell: `.card { &__title { } &--featured { } }` in a `.css` file. Baseline: Widely (since 2026-06). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Nesting/Using#concatenation_is_not_possible
- **Use `&` when you mean a compound selector**: "When using compound selectors in nested CSS you **have** to use the `&` nesting selector. This is because the browser will automatically add whitespace between selectors that do not use the `&` nesting selector." Why: `.a { .b { } }` parses as `.a .b` (a descendant), while `.a { &.b { } }` parses as `.a.b` (the same element). Smell: `.notice { .warning { } }` intended to style `<div class="notice warning">`. Baseline: Widely (since 2026-06). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Nesting/Using#compound_selectors
- **Keep base declarations above nested rules**: "The nested declaration rule is that CSS rules are parsed in the order that they are written in the CSS document." Why: in `.foo { background-color: silver; @media screen { color: tomato; } color: black; }` the trailing `color: black` is evaluated after the media rule and wins on screen. Smell: declarations placed after a nested `@media`, `@container` or `&:hover` block that are meant to be the default. Baseline: Widely (since 2026-06). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Nesting/Using#nested_declarations_rule

## Scoping

- **Use `@scope` instead of over-specific, DOM-shaped selectors**: "The `@scope` CSS at-rule enables you to select elements in specific DOM subtrees, targeting elements precisely without writing overly-specific selectors that are hard to override, and without coupling your selectors too tightly to the DOM structure." Why: "Write something less specific like `.article-body img`. However, that will select all images inside the `section`." so `@scope (.article-body) to (figure) { img { } }` is the precise and still low-specificity option. Smell: `.feature > .article-body > img { }` or `.article-body img:not(figure img) { }`. Baseline: Newly (since 2026-03). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@scope
- **Rely on bare selectors inside `@scope`; add `:scope` only when you mean the root**: "By contrast, using `:scope` explicitly selects the scope root and adds class-level specificity (0-1-0), since `:scope` is a pseudo-class." Why: "Inside an `@scope` rule, both bare selectors and the `&` nesting selector behave as if `:where(:scope)` were prepended to the selector. Because `:where()` has zero specificity, bare selectors and `&` add zero weight." Smell: `@scope (.card) { :scope img { } :scope p { } }` where `img { }` and `p { }` would match the same elements at 0-0-1. Baseline: Newly (since 2026-03). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@scope#specificity_in_scope
- **Let scoping proximity settle nested theme containers**: "when two scopes have conflicting styles, the style that has the smallest number of hops up the DOM tree hierarchy to the scope root is applied." Why: with plain `.light-theme p` and `.dark-theme p` rules "Because the `.dark-theme p` rule appears later in the source order, it is applied, and the paragraph ends up being wrongly colored white." Note that "Scoping proximity overrules source order but is itself overridden by other, higher-priority criteria such as importance, layers, and specificity." Smell: `.light-theme p { }` and `.dark-theme p { }` pairs, or `.dark-theme .light-theme p { }` chains, used for theme wrappers that can nest. Baseline: Newly (since 2026-03). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@scope#how_scope_conflicts_are_resolved
- **Do not expect `@scope` to block inheritance**: "while `@scope` allows you to isolate the application of selectors to specific DOM subtrees, it does not completely isolate the applied styles to within those subtrees. This is most noticeable with inheritance". Why: "properties that are inherited by children (for example `color` or `font-family`) will still be inherited, beyond any set scope limit." Smell: `@scope (.card) to (.card-footer) { :scope { color: white; } }` with the expectation that the footer text stays dark. Baseline: Newly (since 2026-03). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@scope#description

## Custom properties and tokens

- **Replace repeated raw values with named custom properties**: "Custom properties allow a value to be defined in one place, then referenced in multiple other places so that it's easier to work with. Another benefit is readability and semantics. For example, `--main-text-color` is easier to understand than the hexadecimal color `#00ff00`, especially if the color is used in different contexts." Why: "Changing a color that's been duplicated in many places requires a search and replace across all rules and CSS files." Smell: `#1a73e8` or `0.5rem` repeated across a dozen rules where `var(--color-accent)` or `var(--space-2)` belongs. Baseline: Widely (since 2019-10). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Cascading_variables/Using_custom_properties
- **Declare global tokens on `:root`, local ones on the component root**: "By declaring a custom property on the `:root` pseudo-class and using it where needed throughout the document, a CSS author can reduce the need for repetition". Why: "The selector given to the ruleset (`<section>` elements in the example above) defines the scope in which the custom property can be used." and "you maybe have a good reason for limiting the scope of your custom properties." Smell: the same `--gap: 1rem;` declared separately on `.header`, `.main` and `.footer`, or a component-only token such as `--card-padding` declared on `:root`. Baseline: Widely (since 2019-10). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Cascading_variables/Using_custom_properties#using_the_root_pseudo-class
- **Remember that a custom property is read where it is used, not where it is set**: "The value is computed where it is needed, not stored and reused in other places of a stylesheet. For instance, you cannot set a property's value and expect to retrieve the value in a sibling's descendant's rule. The property is only set for the matching selector and its descendants." Why: "A custom property defined using two dashes `--` instead of `@property` always inherits the value of its parent." Smell: `.sidebar { --accent: teal; }` followed by `.main .button { background: var(--accent); }` where `.main` is a sibling of `.sidebar`. Baseline: Widely (since 2019-10). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Cascading_variables/Using_custom_properties#inheritance_of_custom_properties
- **Give optional tokens a `var()` fallback**: "The second argument to the function is an optional fallback value, which is used as the substitution value when the referenced custom property is invalid." Why: "If the fallback value is omitted, and the custom property has the guaranteed-invalid value, the `var()` function resolves to an invalid value." and the property is then "treated as if it has value `unset`". Smell: `.component .header { color: var(--header-color); }` in a component whose consumers may never set `--header-color`. Baseline: Widely (since 2019-10). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Cascading_variables/Using_custom_properties#defining_fallbacks_in_the_var_function
- **Do not treat a `var()` fallback as browser support fallback**: "Fallback values aren't used to fix compatibility issues for when CSS custom properties are not supported, as the fallback value won't help in this case. Fallbacks cover the case where the browser supports CSS custom properties and is able to use a different value if the desired variable isn't defined yet or has an invalid value." Why: custom properties have been Baseline Widely since 2019, so a duplicated literal declaration above every `var()` is dead weight. Smell: `color: #333; color: var(--text, #333);` pairs throughout a stylesheet. Baseline: Widely (since 2019-10). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Cascading_variables/Using_custom_properties#custom_property_fallback_values
- **Expect an invalid `var()` to reset the property, not fall through to the previous rule**: "When the browser encounters an invalid `var()` substitution, then the initial or inherited value of the property is used." Why: "This is because variables can't "fail early" like other syntax errors can, so by the time the user agent realizes a property value is invalid, it has already thrown away the other cascaded values." Smell: `p { color: blue; } p { color: var(--text-color); }` with `--text-color: 16px` somewhere up the tree, expecting blue. Baseline: Widely (since 2019-10). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Cascading_variables/Using_custom_properties#invalid_custom_properties

## Registered properties

- **Register typed tokens with `@property` to get validation and a real default**: "The `@property` CSS at-rule is used to explicitly define CSS custom properties, allowing for property type checking and constraining, setting default values, and defining whether a custom property can inherit values or not." Why: with `syntax: "<color>"` and `initial-value: teal`, "Both `2rem` and `peenk` are invalid color values, so the initial value of `teal` is applied" instead of the whole declaration collapsing to `unset`. Smell: a design-token file of bare `--color-*: #hex;` declarations with no `@property` registration, or `transition: --progress 1s` on an unregistered property. Baseline: Newly (since 2024-07). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@property
- **Always include both `syntax` and `inherits`**: "The `@property` rule must include both the `syntax` and `inherits` descriptors. If either is missing, the entire `@property` rule is invalid and ignored." Why: "Unknown descriptors are invalid and ignored, but do not invalidate the `@property` rule." but a missing required one does. Smell: `@property --x { syntax: "<length>"; initial-value: 0px; }` with no `inherits`. Baseline: Newly (since 2024-07). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@property#description
- **Give every typed registration a computationally independent `initial-value`**: "If the `initial-value` descriptor is required but omitted, the entire `@property` rule is invalid and ignored." and "`3em` is not valid, because the value of an `em` is dependent on the parent's `font-size`." Why: "The `initial-value` descriptor is optional if the value of the `syntax` descriptor is the universal syntax definition (`syntax: "*"`)." but required for any other syntax. Smell: `@property --c { syntax: "<color>"; inherits: false; }` with no `initial-value`, or `initial-value: 1em` or `initial-value: var(--base)`. Baseline: Newly (since 2024-07). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@property#description
- **Set `inherits: false` for component-local tokens**: "Because `inherits: false;` is set in the at-rule, and a value for the `--box-color` property is not declared within the `.child` scope, the initial value of `teal` is used instead of `green` that would have been inherited from the parent". Why: "The `@property` at-rule lets you explicitly state whether the property inherits or not." whereas a plain `--` property always inherits. Smell: `--card-padding` or `--button-bg` set on one component and silently picked up by a nested instance of the same component. Baseline: Newly (since 2024-07). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Cascading_variables/Using_custom_properties#using_property_to_control_inheritance

## Feature queries

- **Do not wrap widely supported features in `@supports`**: "You don't need to use feature queries to start using new CSS features; CSS error handling means the browser simply ignores CSS it does not yet recognize." Why: "feature queries are a useful alternative to fallback declarations, and enable writing code once that can eventually be supported everywhere." so they belong around the enhancement, not around established CSS. Smell: `@supports (display: grid) { .layout { display: grid; } }` or `@supports (display: flex)` in a codebase targeting current browsers. Baseline: Widely (since 2018-03). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Conditional_rules/Using_feature_queries#summary
- **Test the specific value, not just the property**: "The value part of the property-value pair matters more if you are testing for new values of a particular property." Why: "All browsers support `color: red`: this dates back to CSS1. However, there are often additional values added to properties in CSS, like relative colors, which may not be supported." Smell: `@supports (color: red)` or `@supports (width: 1px)` used as a proxy for a newer value such as `color: AccentColor` or `width: stretch`. Baseline: Widely (since 2018-03). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Conditional_rules/Using_feature_queries#syntax
- **Guard mixed selector lists that use a new selector with `@supports selector()`**: "This rule needs to be inside the @supports block, otherwise it will be partially applied in browsers which don't support the `of` argument of :nth-child(…)". Why: a plain selector list fails as a whole when one entry is not understood, so `:is(:nth-child(1n of ul, ol) a, details > summary)` must be gated or it will match only partially. Smell: a selector list combining a Baseline Newly selector with everyday selectors, outside any `@supports selector(...)` block and outside `:is()`/`:where()`. Baseline: not listed. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@supports#testing_for_the_support_of_a_selector
- **Do not use `@supports` to dodge rendering bugs**: "Feature queries check that declarations are considered valid by a browser, but can't be used to check if it supports a feature properly without bugs or spec violations. Feature queries cannot test for _partial implementations_." Why: "If the property/value pairs are understood by a browser it returns a positive response." regardless of how well the feature works. Smell: `@supports (position: sticky)` wrapping a workaround for a specific browser's sticky bug. Baseline: Widely (since 2018-03). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Conditional_rules/Using_feature_queries#limitations_of_feature_queries

## Inheritance and reset keywords

- **Use `inherit` on form controls instead of repeating body values**: "The `inherit` keyword allows authors to explicitly specify inheritance. It works on both inherited and non-inherited properties." Why: the user-agent stylesheet gives controls their own fonts, so an explicit `inherit` is what reconnects them to the document styles. Smell: `button, input, select { font-family: "Inter", sans-serif; font-size: 16px; line-height: 1.5; }` duplicating the `body` rule instead of `font: inherit;`. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Cascade/Inheritance#notes
- **Beware that a shorthand resets every longhand it omits**: "A value which is not specified is set to a default value defined by the shorthand, which may differ from the property's initial value. That means that it **overrides** previously set values." Why: "This will not set the color of the background to `red` but to the default value for `background-color`, which is `transparent`." Smell: `background-color: red; background: url("bg.gif") no-repeat left top;` or `font-weight: 700; font: 1rem/1.5 sans-serif;`. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Cascade/Shorthand_properties#omitting_properties
- **Use the longhand when one part should inherit**: "the only way to make some specific value to be inherited is to use the longhand property with the keyword `inherit`." Why: "The keyword `inherit` can be applied to a property, but only as a whole, not as a keyword for one value or another." Smell: `border: inherit solid 1px;` or `margin: 0 inherit;`. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Cascade/Shorthand_properties#omitting_properties
- **Do not confuse `initial` with the browser default**: "The initial value should not be confused with the value specified by the browser's style sheet." Why: "A property's **initial value** is the default value as listed in its definition table in the specification." so `display: initial` is `inline` for every element, not the block the user-agent gives a `div`. Smell: `display: initial;` or `all: initial;` on a block container to "undo" a style, which also makes it inline and sets its `color` to black. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Cascade/Property_value_processing#initial_value
- **Prefer `revert` to roll back to user-agent styling**: "If the rule belongs to the author origin, the `revert` value rolls back the cascade to the user level, so that the specified values are calculated as if no author-level rules were specified for the element." Why: `all: revert` on the blockquote example leaves it "styled as a _block_ element" with values inherited from `body`, whereas `all: initial` turned it inline. Smell: `all: initial;` or `all: unset;` on a component root when the goal was "look like the browser default". Baseline: Widely (since 2023-01). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/all#values
- **Use `revert-layer` instead of re-typing the lower layer's value**: "`revert-layer` Specifies that all the element's properties should roll back the cascade to a previous cascade layer, if one exists. If no other cascade layer exists, the element's properties will roll back to the matching rule, if one exists, in the current layer or to a previous style origin." Why: it keeps the override layer free of copies of values that live in the base layer, so a change in the base layer is not silently shadowed. Smell: inside `@layer overrides`, `.btn { padding: 0.5rem 1rem; }` that reproduces the `components` layer value just to cancel a utility. Baseline: not listed. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/all#values

## Stacking

- **Stop escalating `z-index`; find the stacking context instead**: "the `z-index` values of its child stacking contexts only have meaning within its parent's stacking context. Stacking contexts are treated atomically as a single unit in the parent stacking context." Why: in MDN's example "an element with a `z-index` of `6` (SECTION #4) is stacked below an element with a `z-index` of `5` (ARTICLE #1)" because the parent's `z-index: 4` caps it. Smell: `z-index: 9999;` or `z-index: 2147483647;` on a dropdown or tooltip that still renders under a sibling. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Positioned_layout/Stacking_context#nested_stacking_contexts
- **Only set `z-index` on positioned elements or flex/grid items**: "The `z-index` of DIV #5 has no effect since it is not a positioned element." Why: "The `z-index` CSS property sets the z-order of a positioned element and its descendants or flex and grid items." Smell: `.badge { z-index: 10; }` with no `position` and no flex or grid parent. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Positioned_layout/Using_z-index#example
- **Know which properties quietly create stacking contexts**: "Element with an `opacity` value less than `1`." and "Element with any of the following properties with a value other than `none`: `transform`, `scale`, `rotate`, `translate`, `filter`, `backdrop-filter`, `perspective`, `clip-path`, `mask` / `mask-image` / `mask-border`" as well as `will-change`, `contain: layout` or `paint`, `position: fixed` or `sticky`, and `container-type: size` or `inline-size`. Why: "Elements that don't create their own stacking contexts are _assimilated_ by the parent stacking context." so adding one of these to a wrapper traps every descendant's `z-index`. Smell: `transform: translateZ(0);` or `will-change: transform;` added as a performance hack on a layout wrapper, or `opacity: 0.99;` on a container holding a popover. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Positioned_layout/Stacking_context#features_creating_stacking_contexts
- **Use `isolation: isolate` when you want a stacking context on purpose**: "`isolate` A new stacking context must be created." Why: "This property is especially helpful when used in conjunction with `mix-blend-mode` and `z-index`." and it says what it means, unlike a side effect of `transform` or a throwaway `z-index`. Smell: `position: relative; z-index: 0;` or `transform: translateZ(0);` on a component root whose only job is to contain its children's `z-index` or `mix-blend-mode`. Baseline: Widely (since 2022-07). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/isolation#values
- **Do not add an integer `z-index` to a wrapper "just in case"**: "This `<integer>` is the stack level of the generated box in the current stacking context. The box also establishes a local stacking context. This means that the z-indexes of descendants are not compared to the z-indexes of elements outside this element." Why: "For a positioned box (that is, one with any `position` other than `static`), the `z-index` property specifies: The stack level of the box in the current stacking context. Whether the box establishes a local stacking context." Smell: `.section { position: relative; z-index: 1; }` on every section, so a modal inside one section can never paint above the next section. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/z-index#values

## Vendor prefixes

- **Delete prefixed duplicates of standard properties**: "If you encounter the above code in a code base, you can safely remove all but the last line. All browsers support transitions without vendor prefixes". Why: "Now, experimental features in browsers are "put behind a flag"." so new prefixes are not being added and old ones are dead weight. Smell: `-webkit-transition`, `-moz-transition`, `-ms-transition` and `-o-transition` stacked above `transition`, or `-webkit-border-radius` above `border-radius`. Source: https://developer.mozilla.org/en-US/docs/Glossary/Vendor_Prefix#css_prefixes
- **Where a prefix is still genuinely needed, test for it with `or`**: "This can be particularly useful if a feature is vendor prefixed, as you can test for the standard property plus any vendor prefixes." Why: `@supports (font-smooth: always) or (-webkit-font-smoothing: antialiased)` applies the block when either spelling is understood, instead of unconditionally emitting both. Smell: `-webkit-font-smoothing: antialiased;` and `-moz-osx-font-smoothing: grayscale;` pasted into a global reset with no feature test and no standard equivalent. Baseline: Widely (since 2018-03). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Conditional_rules/Using_feature_queries#testing_for_at_least_one_of_multiple_features
