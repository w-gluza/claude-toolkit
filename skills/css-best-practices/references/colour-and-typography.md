# CSS Colour and Typography Rules (MDN)

Extracted 2026-11-08 from the mdn/content repository. Baseline statuses from the web-features dataset on the same date.

## Colour spaces

- **Build new palettes in `oklch()` or `oklab()`, not hex, `rgb()` or `hsl()`**: "it is the brightness of a color as perceived by the human eye rather than the lightness as compared to other colors" - the `L` channel in Oklab functions is perceptual, so a scale built by stepping `L` has even visual lightness across every hue, which no hex or `hsl()` scale gives you. Why: "Putting white text on fully saturated blue (`hsl(240deg 100% 50%)`) is legible, but that same text on fully saturated yellow (`hsl(60deg 100% 50%)`) will not only be illegible, but may hurt your user's eyes." Smell: a new token set such as `--blue-500: #3b82f6; --yellow-500: #eab308;` or `hsl(220 90% 50%)` and `hsl(55 90% 50%)` presented as the same step of a scale. Baseline: Widely (since 2025-11). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Colors/Color_values#lch_and_oklch_cielab_and_oklab_color_spaces
- **Do not reuse `hsl()` hue angles in `oklch()`**: "In `hsl()`, the sRGB color `0deg` represents red. However, in the CIELab color space, `0deg` corresponds to magenta, while red is approximately `41deg`." Why: "The angles corresponding to particular hues differ across the sRGB (used by `hsl()` and `hwb()`), CIELAB (used by `lch()`), and Oklab (used by `oklch()`) color spaces." Smell: `oklch(60% 0.2 0)` written as "red", or a hue token copied from an `hsl()` palette into an `oklch()` call. Baseline: Widely (since 2025-11). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/color_value/oklch#hues_in_oklch
- **Know the `oklch()` number ranges: `L` is 0 to 1, `C` 100% is 0.4**: "Usually when percentage values have a numeric equivalent in CSS, `100%` is equal to the number `1`." but "This is not the case for all of the `oklch()` component values. Here, `100%` is equal to `0.4` for the `C` value." Why: "The `l` channel value is resolved to a `<number>` between `0` and `1`, inclusive." so arithmetic that treats lightness as a 0 to 100 scale overshoots. Smell: `oklch(65 0.2 250)` with a bare `65` for lightness, or `oklch(from var(--c) calc(l + 20) c h)` where `l` is a 0 to 1 number. Baseline: Widely (since 2025-11). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/color_value/oklch#values
- **Gate wide-gamut `color(display-p3 ...)` behind `@media (color-gamut: p3)`**: "if you wanted to show the `display-p3 0 0 1` color, which is outside of the sRGB gamut, you could use a `@media` `color-gamut` at-rule to detect if the client's hardware supports colors in this range before trying to use it" - declare the sRGB value first and the P3 value inside the media query. Why: "the `color()` function supports a much wider color gamut" than `rgb()`, `hsl()` and `hwb()`, and only displays that can show those colours should be asked to. Smell: `background: color(display-p3 0 0 1);` with no sRGB declaration before it and no `color-gamut` query. Baseline: Widely (since 2025-11). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Colors/Color_values#the_color_function
- **Use space-separated colour functions with `/` for alpha, not `rgba()` or `hsla()` with commas**: "Some legacy functional notations, such as legacy syntax for `rgb()`, `rgba()`, `hsl()`, and `hsla()`, used commas, but commas are generally only used to separate items in a list." Why: the comma form is the legacy syntax; the `none` keyword and relative colour syntax only work in the modern space-separated form. Smell: `rgba(0, 0, 0, 0.5)` or `hsla(210, 50%, 40%, 0.8)` in new code instead of `rgb(0 0 0 / 50%)`. Baseline: Widely (since 2022-07). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Values_and_units/Numeric_data_types#functional_notation
- **Pick one colour notation per codebase**: "In the real world, you and your team will preferably pick a preferred color notation, with everyone working on a code base using the same color syntax." Why: "This is not recommended for production code. When writing CSS, use the most intuitive value type for you and your team." Smell: `#6e1478`, `hsl(0deg 95% 95%)`, `hwb(270deg 63% 13%)` and `rgb(245 130 130)` all appearing in the same stylesheet. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Colors/Applying_color#css

## Deriving colours

- **Derive tints and shades with `color-mix()` instead of hand-picking a second hex**: "The `color-mix()` function enables mixing one or more `<color>` values of any type, in a specific ratio, in a given colorspace, using either a shorter or longer hue interpolation method." - for example `color-mix(in oklab, var(--brand) 25%, white)`. Why: a mixed colour follows its base token, so changing the brand colour updates every hover, focus and disabled variant with it. Smell: `--brand: #a71e14; --brand-hover: #8e1a11; --brand-light: #f3d9d6;` written by hand next to each other. Baseline: Widely (since 2025-11). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/color_value/color-mix#description
- **Mix in `oklab` (the default) or `oklch`, not `srgb`**: "Only use sRGB if you need to match the behavior of a specific device or software that uses sRGB. The sRGB color space is neither linear-light nor perceptually uniform, and produces poorer results such as overly dark or grayish mixes." Pick `oklch` when the mix must stay vivid: "If avoiding graying out in color mixing is desired, i.e., maximizing chroma throughout the transition, the Oklch (and older LCH) color spaces work well." Why: "When mixing colors without specifying a color space, the `oklab` color space is used." and Oklab is designed to be perceptually uniform. Smell: `color-mix(in srgb, var(--brand), white 20%)` or `color-mix(in hsl, red, blue)` with no device-matching reason. Baseline: Widely (since 2025-11). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/color_value/color-mix#choosing_a_color_space
- **Fade a colour by mixing with `transparent`, not with `opacity`**: "This example demonstrates using the `color-mix()` function to add transparency to a color by mixing any color with `transparent`." Why: "the `color-mix()` function can be used to add transparency to any color, even if the color is already non-opaque (with an alpha channel value < 1)." and it fades only the colour, whereas `opacity` fades the whole element including its text and borders. Smell: `.badge { background: var(--brand); opacity: 0.5; }` or a duplicate token `--brand-50: rgb(37 99 235 / 0.5)` instead of `color-mix(in srgb, var(--brand) 50%, transparent)`. Baseline: Widely (since 2025-11). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/color_value/color-mix#adding_transparency
- **Use relative colour syntax, not `color-mix()`, to make a translucent colour opaque**: "`color-mix()` can't be used to make a semi-transparent color fully opaque. For this, use a relative color with a CSS color function." Why: relative colours "can alter the value of any color channel, including increasing a color's alpha channel to render the color fully opaque." Smell: `color-mix(in srgb, var(--overlay) 100%, black)` expecting a solid result, instead of `rgb(from var(--overlay) r g b / 1)`. Baseline: Newly (since 2024-09). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/color_value/color-mix#adding_transparency
- **Lighten and darken with relative colour syntax on the token**: "The lightened color has 20% added to the lightness channel, and the darkened color has 20% subtracted from it." - `lch(from var(--base-color) calc(l + 20) c h)` and `calc(l - 20)`. Why: the variants are defined relative to one custom property, so a palette updates from a single value instead of being re-picked by hand. Smell: `--primary: #2563eb; --primary-dark: #1d4ed8; --primary-light: #60a5fa;` as three unrelated literals. Baseline: Newly (since 2024-09). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Colors/Using_relative_colors#using_math_functions
- **Add numbers, never percentages, to relative colour channels**: "If we tried to do `calc(l + 20%)`, that would result in an invalid color" Why: "Channel values originally specified as a `<percentage>` resolve to a `<number>` appropriate for the output color function." so a percentage cannot be added to them. Smell: `oklch(from var(--c) calc(l + 10%) c h)` or `hsl(from var(--c) h calc(s - 20%) l)`. Baseline: Newly (since 2024-09). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Colors/Using_relative_colors#channel_values_resolve_to_number_values
- **Feature-test relative colours with a literal colour, not a custom property**: "When testing complex values like these, you should use the simplest possible declaration that still contains the syntactic difference you want to test for." and "To work around this, in each test we have replaced `var(--base-color)` with the `red` keyword." Why: "This is because a custom property value only becomes invalid when assigned to be an invalid value (or part of an invalid value) of a regular CSS property." so a test containing `var()` always passes. Smell: `@supports (color: oklch(from var(--brand) l c h))`. Baseline: Newly (since 2024-09). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Colors/Using_relative_colors#an_aside_on_supports_testing

## Colour schemes and themes

- **Declare `color-scheme: light dark` on `:root` for any themed page**: "To opt the entire page into the user's color scheme preferences, declare `color-scheme` on the `:root` element." Why: "User agents change the following aspects of the UI chrome to match the used color scheme" - the canvas, scrollbars, form controls and spellcheck underlines; without it a dark theme gets light inputs and scrollbars. Smell: `body { background: #111; color: #eee; }` or a `.dark` class theme with no `color-scheme` declaration anywhere. Baseline: Widely (since 2024-08). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/color-scheme#declaring_color_scheme_preferences
- **Pair the CSS with `<meta name="color-scheme">` in the head**: "also include the `<meta name="color-scheme">` HTML `<meta>` tag in the `<head>`, before any CSS style information, to inform user agents about the preferred color scheme, helping prevent unwanted screen flashes during the page load." Why: the browser knows the scheme before the stylesheet arrives, so the first paint is already the right colour. Smell: `color-scheme: light dark` only in CSS, with no meta tag in the document head. Baseline: Widely (since 2024-08). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/color-scheme#declaring_color_scheme_preferences
- **Use `light-dark()` instead of duplicating declarations in a `prefers-color-scheme` block**: "Alternatively, use the `light-dark()` `<color>` function to set the foreground and background colors for the different color schemes using a more compact code structure" - it also accepts two `<image>` values, so icon and gradient swaps need no media query either. Why: the `light-dark()` reference describes it as returning a colour or image "based on the active color scheme, without needing a `prefers-color-scheme` media feature", and both values sit in one declaration instead of two rules that drift apart. Smell: `.card { color: #222; background: #fff; } @media (prefers-color-scheme: dark) { .card { color: #eee; background: #222; } }` repeated per component. Baseline: Newly (since 2024-05). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/color-scheme#styling_based_on_color_schemes
- **`light-dark()` only works once `color-scheme` includes both schemes**: "To enable support for the `light-dark()` color function, the `color-scheme` must have a value of `light dark`, usually set on the `:root` pseudo-class." Why: "The `light-dark()` function returns the first value if the used color scheme is `light` or if no preference is set and the second value if the used color scheme is `dark`." so with no `color-scheme` the dark value is never used. Smell: `color: light-dark(#333, #eee)` in a stylesheet whose `:root` has no `color-scheme`, or has `color-scheme: light`. Baseline: Newly (since 2024-05). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/color_value/light-dark#description
- **Do not force a single scheme on page sections**: "If the user has made a preference, you generally should not override their preferences." Why: `color-scheme: light` or `dark` on an element overrides the user's choice for that region; MDN uses it only "for demonstration purposes". Smell: `.sidebar { color-scheme: dark; }` or `color-scheme: only dark` on a section of a page that otherwise follows the user. Baseline: Widely (since 2024-08). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/color_value/light-dark#setting_colors_based_on_a_color_scheme
- **Write light as the default and override with `prefers-color-scheme: dark`**: "A common usage is to use a light color scheme by default, and then use `prefers-color-scheme: dark` to override the colors to a darker variant." Why: the `light` value "Indicates that user has notified that they prefer an interface that has a light theme, or has not expressed an active preference." so the light branch is also the no-preference branch. Smell: a theme that only switches on a `.dark` class toggled from JavaScript, with no `prefers-color-scheme` query or `light-dark()` so system preference is ignored on first load. Baseline: Widely (since 2022-07). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/prefers-color-scheme#detecting_a_dark_or_light_theme

## Forced colours and contrast

- **Never use colour as the only signal**: "never use color as the only way to convey information." Why: "If, for example, you indicate the success of an operation with a green border around the associated UI element, and failure with a red border, users with red-green color blindness won't be able to use your site properly." Smell: `.is-valid { border-color: green; } .is-invalid { border-color: red; }` with no icon, text or `aria-invalid` to go with it. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Colors/Using_color_wisely#color_and_accessibility
- **Keep foreground and background contrast sufficient**: "ensure you have enough color contrast between your background and foreground content to ensure legibility." Why: "If the contrast is too low, your text will be washed out by the background, leaving it unreadable, but if your contrast is too high, the user may find your site garish and unpleasant to look at." Smell: `color: #999` body text on `#fff`, or placeholder-grey `#aaa` used for helper text and labels. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Colors/Using_color_wisely#color_and_accessibility
- **Use the smallest number of colours**: "Usually, you are better off using the smallest number of colors possible. Using color to highlight important content rather than adding color to everything will have more impact and your content will be more readable." Why: colour spent on everything leaves nothing to highlight the content that matters. Smell: a tokens file with dozens of one-off hexes, or a component introducing its own colour literal rather than reusing a palette token. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Colors/Using_color_wisely#fleshing_out_the_palette
- **Treat `forced-colors: active` as a place for small fixes, not a second theme**: "In general, web authors should **not** be using the `forced-colors` media feature to create a separate design for users with this feature enabled. Instead, its intended usage is to make small tweaks to improve usability or legibility when the default application of forced colors does not work well for a given portion of a page." Why: "The high contrast provided by forced colors mode's reduced palette and text backplates is often essential for some users to be able to read or use a given website" Smell: a large `@media (forced-colors: active) { ... }` block that re-colours the whole UI. Baseline: Widely (since 2025-03). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/forced-colors#accessibility_concerns
- **Give shadow-only affordances a border under forced colours**: "This example is a button that normally gets its contrast via `box-shadow`. Under forced colors mode, box-shadow is forced to none, so the example uses the forced-colors media feature to ensure there is a border of the appropriate color (ButtonText in this case)" Why: in forced colours mode "`box-shadow` is forced to 'none'" and "`text-shadow` is forced to 'none'", so an element outlined only by shadow disappears. Smell: `.button { border: 0; box-shadow: 0 0 0 1px #ccc; }` or a focus ring drawn with `box-shadow` only, with no `@media (forced-colors: active)` fallback to `border` or `outline`. Baseline: Widely (since 2025-03). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/forced-colors#examples
- **Inside a forced-colours block, use system colour keywords, not literals**: "When a system color is specified, it will be used instead of the value that would otherwise have been forced." and "You can also use system colors with any property _other_ than those listed above, to ensure that the rest of the page integrates with the restricted color palette available in forced colors mode." Why: system colours such as `ButtonText`, `CanvasText` and `Highlight` come from the user's chosen palette, so they keep the contrast the user asked for. Smell: `@media (forced-colors: active) { .btn { border-color: #333; } }`. Baseline: Widely (since 2025-03). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/forced-colors#properties_affected_by_forced-color_mode
- **Reach for `forced-color-adjust: none` only to fix legibility, never to keep brand colours**: "This property should only be used to makes changes that will support a user's color and contrast requirements." and "**It should not be used to prevent user choices being respected**." Why: the user turned on forced colours because they need that palette; opting elements out removes the text backplate and the enforced contrast. Smell: `* { forced-color-adjust: none; }` or `.brand-header { forced-color-adjust: none; }` applied to keep a logo background. Baseline: not listed (the Forced colors feature is Widely since 2025-03). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/forced-color-adjust#usage_notes
- **Strengthen subtle indicators under `prefers-contrast: more`**: "When the `prefers-contrast: more` media query matches, the applied outline is given a higher contrast `solid` style instead." Why: `more` "Indicates that user has notified the system that they prefer an interface that has a higher level of contrast." so dashed, thin or low-contrast borders should get a solid, darker alternative. Smell: `outline: 2px dashed #bbb` or `border: 1px solid #e5e5e5` on controls with no `@media (prefers-contrast: more)` branch. Baseline: Widely (since 2024-11). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/prefers-contrast#examples
- **Recolour native controls with `accent-color` before replacing them**: "Browsers that support `accent-color` currently apply it to the following HTML elements:" checkboxes, radios, range inputs and `<progress>`. Why: "Each user agent has an accent color, with variations to ensure legibility and contrast." and `accent-color` keeps the native control, its keyboard behaviour and its forced-colours handling. Smell: `input[type="checkbox"] { appearance: none; width: 1rem; ... }` plus a hand-drawn tick, when the only goal was a brand colour. Baseline: Limited. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/accent-color#description

## Gradients

- **Make hard stripes by giving two adjacent stops the same position**: "To create a hard line between two colors, creating a stripe instead of a gradual transition, adjacent color stops can be set to the same location." Why: one declaration draws the split; no extra element or pseudo-element is needed. Smell: a wrapper with two child `<div>`s, or `::before` and `::after`, used only to paint a two-tone bar that `linear-gradient(to right, cyan 50%, palegoldenrod 50%)` would draw. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Images/Using_gradients#creating_hard_lines
- **Use double-position stops for solid bands**: "To include a solid, non-transitioning color area within a gradient, include two positions for the color stop. Color stops can have two positions, which is equivalent to two consecutive color stops with the same color at different positions." Why: `red 30% 45%` reads as one band instead of two entries that must be kept in sync. Smell: `linear-gradient(lime 20%, red 30%, red 45%, cyan 55%, cyan 70%, yellow 80%)` with every colour repeated. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Images/Using_gradients#creating_color_bands_stripes
- **Use the `repeating-*` gradient functions for patterns**: "The `linear-gradient()`, `radial-gradient()`, and `conic-gradient()` functions don't support automatically repeated color stops. However, the `repeating-linear-gradient()`, `repeating-radial-gradient()`, and `repeating-conic-gradient()` functions are available to offer this functionality." Why: "The size of the gradient line or arc that repeats is the length between the first color stop value and the last color stop length value." so a stripe pattern is two stops, not a hand-unrolled list. Smell: `linear-gradient(90deg, #000 0 5px, #fff 5px 10px, #000 10px 15px, #fff 15px 20px, ...)` or `background-size: 10px 10px` with `background-repeat` to fake repetition. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Images/Using_gradients#using_repeating_gradients
- **Draw pie charts, rings and colour wheels with `conic-gradient()`**: "Example conic gradients include pie charts and color wheels, but they can also be used for creating checker boards and other interesting effects." Why: "With conic gradients, the colors transition as if spun around the center of a circle, starting at the top and going clockwise." so percentage stops map directly onto chart segments. Smell: an inline SVG `<path>` arc or a `<canvas>` for a single static percentage ring. Baseline: Widely (since 2023-05). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Images/Using_gradients#using_conic_gradients

## Type sizing and units

- **Size text in `rem` (or keywords), not `px`**: "Defining font sizes in `px` is _not accessible_, because the user cannot change the font size in some browsers." and "To maximize accessibility, it is generally best to use values that are relative to the user's default font size." Why: "users with limited vision may wish to set the font size much larger than the size chosen by a web designer." Smell: `font-size: 14px`, `html { font-size: 16px; }`, or a `px` type scale in tokens. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/font-size#pixels
- **Prefer `rem` over `em` for font sizes to stop compounding**: "`rem` values were invented in order to sidestep the compounding problem. `rem` values are relative to the root `html` element, not the parent element." Why: "This is because the inner `<span>`'s `font-size` is 1.6em which is relative to its parent's `font-size`, which is in turn relative to its parent's `font-size`. This is often called **compounding**." Smell: `li { font-size: 0.9em; }` or `.card .card { font-size: 1.1em; }` where nesting shrinks or grows text unexpectedly. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/font-size#rems
- **Write `line-height` as a unitless number**: "The used value is this unitless `<number>` multiplied by the element's own font size. The computed value is the same as the specified `<number>`. In most cases, **this is the preferred way** to set `line-height` and avoid unexpected results due to inheritance." Why: lengths and percentages are computed once on the parent and inherited as a fixed value, so children with a different `font-size` get the wrong spacing; "Values given in **em** units may produce unexpected results". Smell: `line-height: 24px`, `line-height: 1.5em`, `line-height: 150%`. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/line-height#values
- **Give body text a `line-height` of at least 1.5**: "Use a minimum value of `1.5` for `line-height` for main paragraph content." Why: "This will help people experiencing low vision conditions, as well as people with cognitive concerns such as Dyslexia. If the page is zoomed to increase the text size, using a unitless value ensures that the line height will scale proportionately." Smell: `body { line-height: 1.2; }` or `p { line-height: normal; }` on long-form text. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/line-height#accessibility

## Line wrapping and breaking

- **Balance headings with `text-wrap: balance`, not manual `<br>`**: "When the styled content will be limited to a short number of lines, such as headings, captions, and blockquotes, `text-wrap: balance` can be added to balance the number of characters on each line, enhancing layout quality and legibility." Why: "As browsers limit the number of lines impacted by this property, this value's impact on performance is negligible." and the balance holds at every viewport width, which a hard break cannot. Smell: `<h1>Welcome to the<br>dashboard</h1>`, `max-width` tuned per heading to force a break, or `p { text-wrap: balance; }` on body copy (it is "only supported for blocks of text spanning a limited number of lines"). Baseline: Newly (since 2024-05). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/text-wrap#description
- **Reserve `text-wrap: pretty` for long body text**: "For longer sections of text, `text-wrap: pretty` can be used. Note that `pretty` has a negative effect on performance, so it should be only used for longer blocks of text when the layout is more important than speed." Why: `pretty` runs "a slower algorithm that favors better layout over speed", intended for body copy where orphans matter. Smell: `* { text-wrap: pretty; }` or `body { text-wrap: pretty; }` applied to every element including UI labels and tables. Baseline: Limited. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/text-wrap#description
- **Break long words with `overflow-wrap`, not `word-break: break-all`**: "In contrast to `word-break`, `overflow-wrap` will only create a break if an entire word cannot be placed on its own line without overflowing." Use the standard name: `word-wrap` is only an alias. Why: the wrapping guide warns that `word-break` "will cause a break-even if placing the word onto a new line would allow it to display without breaking." so ordinary words get chopped mid-syllable. Smell: `word-break: break-all` on prose, comments or table cells; `word-wrap: break-word` instead of `overflow-wrap`. Baseline: Widely (since 2021-04). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/overflow-wrap
- **Use `overflow-wrap: anywhere` when the container's minimum size must shrink**: `anywhere` means "Soft wrap opportunities introduced by the word break are considered when calculating min-content intrinsic sizes." whereas with `break-word` they "are NOT considered when calculating min-content intrinsic sizes." Why: flex and grid items default to `min-width: auto`, so `break-word` still lets a long token push the item wider than its track. Smell: `.cell { overflow-wrap: break-word; }` on a grid or flex child that still overflows, usually patched with `min-width: 0`. Baseline: Widely (since 2021-04). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/overflow-wrap#values
- **Do not hide text overflow to cover a wrapping problem**: "It is generally better to be able to see overflow, even if it is messy. If things were to disappear or be cropped as would happen if `overflow` was set to `hidden` you might not spot it when previewing your site." Why: "In CSS data loss means that some of your content vanishes." and a visible mess is at least noticed and fixed with `overflow-wrap` or `min-content` sizing. Smell: `overflow: hidden` on a text container, or `text-overflow: ellipsis` on body copy, added to make a long word stop poking out. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Text/Wrapping_breaking_text#what_is_overflowing_text
- **`hyphens: auto` needs a `lang` attribute and no `break-all`**: "Hyphenation rules are language-specific. In HTML, the language is determined by the `lang` attribute. Browsers will only hyphenate if this attribute is present and the appropriate hyphenation dictionary is available." Why: "If you apply `word-break: break-all` then no hyphens are shown, even if the word breaks at a hyphenation point." and without a language the browser has no dictionary to consult. Smell: `hyphens: auto` on a document whose `<html>` has no `lang`, or combined with `word-break: break-all`. Baseline: Widely (since 2026-03). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/hyphens#description
- **Mark break opportunities in URLs and identifiers with `<wbr>` or `&shy;`**: "If you know where you want a long string to be allowed to break, you can also use the HTML `<wbr>` element." Why: "This allows you to preserve meaningful segments in the string, such as long URLs." instead of letting the browser break anywhere. Smell: `word-break: break-all` or `overflow-wrap: anywhere` on a column of URLs, paths or hashes where a break after `/` or `-` was wanted. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Text/Wrapping_breaking_text#the_wbr_element
- **Honour source newlines with `white-space: pre-line`, not injected `<br>`**: `pre-line` means "Sequences of white space are collapsed. Lines are broken at newline characters, at `<br>`, and as necessary to fill line boxes." Why: the text keeps wrapping normally while the author's line breaks survive; `pre` would also preserve runs of spaces and stop wrapping. Also "To make words break _within themselves_, use `overflow-wrap`, `word-break`, or `hyphens` instead." of reaching for `white-space`. Smell: `text.replace(/\n/g, "<br>")` into `innerHTML`, or `white-space: pre` on user-entered text that then overflows horizontally. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/white-space#values
- **Trim leading above and below text with `text-box`, not negative margins**: "The `text-box` properties enable trimming off extra spacing from the block-start edge and block-end edge of a text element's block container, which can include the leading at the text's block-start edge and block-end edges, and the spacing defined inside the font" Why: "Different fonts have different base line-heights, meaning that lines of text with the same `font-size` will produce line boxes of differing heights, affecting the appearance of spacing between lines." Smell: `h1 { margin-top: -0.18em; margin-bottom: -0.12em; }` or per-font magic numbers to align cap height with a box edge. Baseline: Limited. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/text-box#description
- **Hang opening quotes with `hanging-punctuation`, not negative `text-indent`**: `first` means "An opening bracket or quote at the start of the first formatted line of an element hangs." and `last` does the same for closing marks at the end. Why: the browser hangs the real glyph for the current font, so the indent is exact rather than guessed. Smell: `blockquote p { text-indent: -0.4em; }` or a positioned `::before` quote mark used only to keep the text edge flush. Baseline: Limited. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/hanging-punctuation#values

## Web fonts

- **Serve WOFF2**: "For web delivery, it's generally best to serve fonts in WOFF2 format, because it compresses fonts more efficiently than older formats like WOFF or OpenType, reducing file size and improving load times." Why: "WOFF2 is also well supported in modern browsers, making it a safe default choice for most websites." Smell: `src: url("font.ttf")` or `url("font.otf")` as the only or first source, or a `.woff` listed before the `.woff2`. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@font-face#description
- **Order `src` as `local()` first, then the most specific `url()`**: "Browsers attempt to load resources in their list declaration order, so usually `local()` should be written before `url()`." and "If more specific fonts with `format()` or `tech()` values are desired, these should be listed _before_ versions that don't have these values, as the less specific variant would otherwise be tried and used first." Why: the first usable source wins, so a download listed before a `local()` wastes bandwidth and a generic entry listed first hides the better one. Smell: `src: url("a.woff2"), local("Font Name");` or `url("a.woff2"), url("a-color.woff2") format("woff2") tech(color-COLRv1)`. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@font-face#description
- **Set `font-display` explicitly in every `@font-face`**: with `auto` "The font display strategy is defined by the user agent." whereas `swap` "Gives the font face an extremely small block period and an infinite swap period." and `optional` "Gives the font face an extremely small block period and no swap period." Why: during the block period "any element attempting to use it must render an _invisible_ fallback font face." so leaving the strategy to the browser risks invisible text while the file downloads. Smell: an `@font-face` block with `font-family` and `src` but no `font-display` line. Baseline: Widely (since 2022-07). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@font-face/font-display#values
- **Match the fallback font's metrics with `size-adjust`**: "The `size-adjust` property can help when overriding the metrics of a fallback font to better match those of a primary web font." - declare a second `@font-face` with `src: local(...)` and `size-adjust`, then list it after the web font in `font-family`. Why: "All metrics associated with this font are scaled by the given percentage. This includes glyph advances, baseline tables, and overrides provided by `@font-face` descriptors." so the swap from fallback to web font reflows less. Smell: `font-family: "Brand Sans", sans-serif;` with `font-display: swap` and no metric-adjusted fallback face, so layout shifts on load. Baseline: not listed. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@font-face/size-adjust#overriding_metrics_of_a_fallback_font
- **Declare one `@font-face` with ranges for a variable font**: "The basic syntax is the same, but the font technology can be specified, and allowable ranges for descriptors like `font-weight` and `font-stretch` can be supplied, rather than named according to the font file being loaded." - for example `font-weight: 125 950; font-stretch: 75% 125%; font-style: oblique 0deg 12deg;`. Why: "Supplying value ranges for `font-weight`, `font-stretch`, and `font-style` will keep the browser from attempting to render an axis outside that range if you are using the appropriate attribute" Smell: several `@font-face` blocks pointing at the same variable file with `font-weight: 400`, `font-weight: 700` and so on, or a variable face declared with a single `font-weight: 400`. Baseline: Widely (since 2021-03). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Fonts/Variable_fonts#using_a_variable_font_font-face_changes
- **Use `font-weight`, `font-stretch` and `font-style` before `font-variation-settings`**: "wherever possible, the appropriate property should be used, with the lower-level syntax of `font-variation-settings` only being used to set values or axes not available otherwise." Why: "the W3C's intent was for this syntax not to be used when other attributes are available." and the high-level properties cascade and interact with `font-synthesis` correctly. Smell: `font-variation-settings: "wght" 600;` where `font-weight: 600` works, or `"wdth" 85` instead of `font-stretch: 85%`, or `"slnt" -14` instead of `font-style: oblique 14deg`. Baseline: Widely (since 2021-03). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Fonts/Variable_fonts#registered_axes_and_existing_css_attributes
- **Drive `font-variation-settings` axes through custom properties**: "If you have set values using `font-variation-settings` and want to change one of those values, you must redeclare all of them (in the same way as when you set OpenType font features using `font-feature-settings`). You can work around this limitation by using CSS Custom Properties (CSS variables) for the individual values, and modifying the value of an individual custom property." Also "The registered axis names must be in lower case, and custom axes must be in upper case." Why: a later `font-variation-settings` declaration replaces the whole list, so a hover rule that sets one axis silently resets the others. Smell: `h2:hover { font-variation-settings: "GRAD" 130; }` after a rule that also set `"wght"` and `"opsz"`, or `"WGHT" 500` with the registered tag in capitals. Baseline: Widely (since 2021-03). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Fonts/Variable_fonts#notes
- **Leave `font-optical-sizing` on `auto` and do not pin `opsz`**: "Optical sizing is enabled by default for fonts that have an optical size variation axis." Why: "When optical sizing is used, small text sizes are often rendered with thicker strokes and larger serifs, whereas larger text is often rendered more delicately with more contrast between thicker and thinner strokes." so the font already tracks `font-size`. Smell: `font-optical-sizing: none;` with no stated reason, or `font-variation-settings: "opsz" 14;` applied to text of many sizes. Baseline: Widely (since 2022-09). Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/font-optical-sizing#description
- **Load real bold and italic faces for static fonts instead of relying on synthesis**: "To most accurately reflect the typeface design and avoid differences between browsers and how they may or may not synthesize the different styles, it's more accurate to load the specific font files where needed when using a non-variable font." Add `font-synthesis: none` when a variable italic axis is present, since it "will prevent browsers from accidentally applying the variation axis and a synthesized italic". Why: "most typefaces have very specific designs for bolder weights and italics that often include completely different characters" so faux bold and oblique misrepresent the design. Smell: a single `@font-face` for a static family while `<strong>` and `<em>` render through browser synthesis, or a variable font with an `ital` axis and no `font-synthesis` setting. Source: https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Fonts/Variable_fonts#a_note_about_font_families_weights_and_variants
