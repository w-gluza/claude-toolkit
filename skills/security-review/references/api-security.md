# Security review rules: API endpoints

Extracted 2026-11-10 from OWASP ASVS 5.0.0, the OWASP Cheat Sheet Series and the OWASP API Security Top 10 2023 (CC BY-SA 4.0), MDN (CC BY-SA 2.5) and the Next.js 16.4.5 documentation (MIT). One rule per bullet, one source link each. Quotations are short excerpts; the rest is original.

## Exposure and authentication

- **Require authentication on every non-public endpoint, including internal, admin, debug, monitoring and webhook routes** (ASVS V13.2.1, V13.4.5, API2:2023): "Non-public REST services must perform access control at each API endpoint." - service-to-service calls authenticate with individual short-lived credentials, not a shared key, and management, documentation and monitoring endpoints stay off the public surface or behind strong authentication. Why: an unauthenticated route is reachable by anyone who guesses or enumerates its path, and internal routes are routinely found. Smell: a new route with no auth guard where its siblings have one, such as `router.get('/internal/users', list)` next to `router.get('/users', requireAuth, list)`, or `/debug`, `/metrics`, `/admin` and `/swagger` routes mounted before the auth middleware. Severity: exploitable. Source: https://cheatsheetseries.owasp.org/cheatsheets/REST_Security_Cheat_Sheet.html#access-control
- **Give old API versions and non-production hosts the same protection as the current production API, or retire them** (API9:2023): "Use external protection measures such as API security specific solutions for all exposed versions of your APIs, not just for the current production version." - a security fix applied to v2 but not to the still-mounted v1, or a staging host on production data without production rate limits, leaves the weak path reachable. Why: attackers go through the oldest reachable version because it has the fewest controls. Smell: `app.use('/v1', legacyRouter)` kept alongside `/v2` while only v2 gains the new limiter or auth check; a `beta.` or `staging.` host wired to the production database. Severity: exploitable. Source: https://owasp.org/API-Security/editions/2023/en/0xa9-improper-inventory-management/#how-to-prevent
- **Verify webhook signatures over the raw body with a constant-time comparison, then reject stale or duplicate deliveries** (Webhook cheat sheet): "Supply the raw request body before your framework parses it." - recompute the HMAC with the publisher's library or a timing-safe compare, return 401 without detail when it fails, and where the protocol signs a timestamp and event ID enforce a freshness window and deduplicate event IDs, because a captured valid delivery can be replayed. Why: without verification anyone can post a fake "payment succeeded" event and trigger fulfilment or account changes. Smell: a webhook handler that acts on `req.body.event` with no signature check, compares with `sig === expected`, signs `JSON.stringify(req.body)` instead of the raw bytes, or has no timestamp or event-ID check. Severity: exploitable. Source: https://cheatsheetseries.owasp.org/cheatsheets/Webhook_Security_Cheat_Sheet.html#signature-verification

## Resource consumption and automation

- **Bound what a single request and a single client can consume: rate limits per client and per operation, page-size caps, batch caps and body-size limits** (ASVS V2.4.1, V4.3.1, API4:2023): "Limit/throttle how many times or how often a single API client/user can execute a single operation (e.g. validate an OTP, or request password recovery without visiting the one-time URL)." - apply stricter limits to costly operations (SMS, email, image processing, paid third-party calls), cap page size and array length server-side, limit GraphQL depth and batch size, and set spending limits on paid integrations. Why: one script can exhaust memory, storage or a per-call budget and take the service down or run up the bill. Smell: `limit = req.query.limit ?? 20` with no maximum; `await Promise.all(req.body.ids.map(load))` on an unbounded array; `json({ limit: '100mb' })`; a new OTP or password-reset endpoint with no limiter; GraphQL server without depth or batch limits. Severity: exploitable. Source: https://owasp.org/API-Security/editions/2023/en/0xa4-unrestricted-resource-consumption/#how-to-prevent
- **Protect sensitive business flows such as sign-up, checkout, booking, voting and referral against automated use** (ASVS V2.4.1, API6:2023): "An API Endpoint is vulnerable if it exposes a sensitive business flow, without appropriately restricting the access to it." - a generic rate limit is not enough; these flows need per-account quotas, human checks or non-human-pattern detection chosen for the business harm (scalping, spam, slot hoarding, referral farming). Why: excessive access to a flow that is correct for one user can empty stock, flood content or inflate credit when a script runs it thousands of times. Smell: a new `POST /checkout`, `/reserve`, `/votes` or `/referral` handler that only has the global per-IP limiter, or none, and no per-user or per-item cap; sign-up that grants credit with no anti-automation step. Severity: exploitable. Source: https://owasp.org/API-Security/editions/2023/en/0xa6-unrestricted-access-to-sensitive-business-flows/#is-the-api-vulnerable

## Consuming other APIs

- **Treat third-party API responses as untrusted: validate and bound what they return, time out the call, do not follow redirects blindly and keep TLS verification on** (ASVS V13.2.6, API10:2023): "Maintain an allowlist of well-known locations integrated APIs may redirect yours to: do not blindly follow redirects." - data from an integrated API goes through the same validation and encoding as user input before it reaches a query or a page, responses have a size cap and a timeout, and certificate checks are never disabled. Why: a compromised or malicious upstream can inject into your database, redirect a request carrying user data to an attacker host, or hang your workers. Smell: `rejectUnauthorized: false`, `verify=False`, `NODE_TLS_REJECT_UNAUTHORIZED=0`; `fetch(url)` with no `AbortSignal.timeout`; a client following redirects on a POST that carries personal data; `` `INSERT ... ${partner.name}` `` built from an upstream response. Severity: exploitable. Source: https://owasp.org/API-Security/editions/2023/en/0xaa-unsafe-consumption-of-apis/#how-to-prevent

## Configuration and HTTP hygiene

- **Ship production without debug modes, stack traces in responses, default credentials, directory listings, TRACE or unused HTTP methods** (ASVS V13.2.3, V13.4.2, V13.4.3, V13.4.4, V4.1.4, API8:2023): "Error messages include stack traces, or expose other sensitive information" - return generic errors to the client, disable debug and introspection features, allowlist the methods and content types each endpoint accepts and answer the rest with 405 or 415. Why: leaked internals and leftover defaults are what an attacker chains with the next weakness, and a default credential is a direct way in. Smell: `DEBUG=true` or `NODE_ENV` unset in a production config; `res.status(500).json({ error: err.stack })`; `admin:admin` in a service config; a static file server with directory index on; `app.all('/account', handler)`; GraphQL introspection left on. Severity: defence in depth. Source: https://owasp.org/API-Security/editions/2023/en/0xa8-security-misconfiguration/#is-the-api-vulnerable
- **Never change state on GET or another safe method** (CSRF cheat sheet): "Do not use GET requests for state changing operations." - deletes, votes, logouts, purchases and settings changes go on POST, PUT, PATCH or DELETE where CSRF tokens, SameSite cookies and Fetch Metadata checks apply. Why: any link, image tag or prefetcher can trigger a GET with the victim's cookies, and SameSite=Lax does not block top-level GET navigations. Smell: `router.get('/account/delete', remove)`, `app.get('/posts/:id/like', like)`, a server component or loader that writes to the database on page load. Severity: exploitable. Source: https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html#introduction
- **Keep tokens, API keys and passwords out of URLs** (API2:2023): "Passwords, security tokens, and API keys should not appear in the URL, as this can be captured in web server logs, which makes them intrinsically valuable." - send credentials in a header or in the body of a POST; a GET carries them in a header. Why: query strings end up in server and proxy logs, browser history, bookmarks and Referer headers, so a secret in a URL is a secret shared with everyone who can read those. Smell: `GET /api/export?apiKey=...`, `?token=` on a reset link that then loads third-party assets, `fetch('/login?password=' + pw)`. Severity: defence in depth. Source: https://cheatsheetseries.owasp.org/cheatsheets/REST_Security_Cheat_Sheet.html#sensitive-information-in-http-requests

## File uploads

- **Accept uploads only by allowlisted extension verified against the file content, cap their size, store them under a generated name outside the web root and never let them execute** (ASVS V5.2.1, V5.2.2, V5.3.1): "Verify that files uploaded or generated by untrusted input and stored in a public folder, are not executed as server-side program code when accessed directly with an HTTP request." - check magic bytes or re-encode images rather than trusting the client's Content-Type, check uncompressed size and file count before unpacking archives, and serve files through a handler that maps an id to a path. Why: an uploaded script served from the web root is remote code execution, and an oversized or zip-bomb upload is storage and memory exhaustion. Smell: `dest: 'public/uploads'`; a check on `file.mimetype` or `path.extname` alone; `fs.writeFile(join(uploadDir, file.originalname))`; no `limits.fileSize`; `unzip` of a user archive without a size or entry cap. Severity: exploitable. Source: https://github.com/OWASP/ASVS/blob/master/5.0/en/0x14-V5-File-Handling.md#v53-file-storage
