# Security review rules: dependencies and supply chain

Extracted 2026-11-10 from OWASP ASVS 5.0.0, the OWASP Cheat Sheet Series and the OWASP API Security Top 10 2023 (CC BY-SA 4.0), MDN (CC BY-SA 2.5) and the Next.js 16.4.5 documentation (MIT). One rule per bullet, one source link each. Quotations are short excerpts; the rest is original.

## Choosing and pinning dependencies

- **Commit the lockfile and install from it with a frozen install in CI**: "they could pull in unintended package versions and render the entire benefit of a lockfile futile" - when `package.json` and the lockfile disagree, a plain install resolves fresh versions from the manifest, so CI and production builds must use `npm ci` or `yarn install --frozen-lockfile`, which abort on any mismatch. Why: a floating range lets a newly published, possibly compromised version reach production without anyone having reviewed it. Smell: `npm install` or `yarn install` in a CI step or `Dockerfile`; a `package.json` dependency change with no `package-lock.json` or `yarn.lock` diff; `package-lock.json` listed in `.gitignore`. Severity: defence in depth. Source: https://cheatsheetseries.owasp.org/cheatsheets/NPM_Security_Cheat_Sheet.html#2-enforce-the-lockfile
- **Check that a new dependency is the intended, maintained package before adding it**: "Be suspicious of packages created very recently with no release history." - confirm the exact name exists and is the one meant rather than a near miss or a name a tool invented, that it has a real repository, contributors and download history, and that it is actively maintained. Why: typosquatted and slopsquatted packages run attacker code at install or import time and read `process.env` for credentials. Smell: a `package.json` addition whose name is one character off a popular package, or a plausible but unverified suggestion such as `node-fetch-promise`; a package with a handful of downloads, no `repository` field or a first release days ago; a dependency given as a git or tarball URL instead of a registry name. Severity: exploitable. Source: https://cheatsheetseries.owasp.org/cheatsheets/NPM_Security_Cheat_Sheet.html#10-understanding-typosquatting-and-slopsquatting-attacks
- **Disable lifecycle scripts by default and allowlist the few packages that need them**: "bad actors may create or alter packages to perform malicious acts by running any arbitrary command when their package is installed" - set `ignore-scripts=true` in `.npmrc`, pass `--ignore-scripts` on CI installs, and allowlist by name the packages that genuinely need a build step. Why: a `postinstall` script anywhere in the tree runs with the developer's or the runner's full privileges before a single line of the package has been imported. Smell: an `.npmrc` without `ignore-scripts=true`; `npm ci` in CI without `--ignore-scripts`; a new dependency whose own `package.json` declares `preinstall`, `postinstall` or `prepare`; the script allowlist widened for a package nobody has read. Severity: defence in depth. Source: https://cheatsheetseries.owasp.org/cheatsheets/NPM_Security_Cheat_Sheet.html#3-minimize-attack-surfaces-by-ignoring-run-scripts
- **Resolve internal packages only from the expected registry** (ASVS V15.2.4): "Verify that third-party components and all of their transitive dependencies are included from the expected repository" - scope internal packages as `@org/name`, bind the scope to the private registry in `.npmrc`, commit that file so CI resolves the same way, and keep the registry setting from being overridden. Why: an attacker who publishes a public package under an internal package's name with a higher version wins resolution and runs code on every install (dependency confusion). Smell: an unscoped internal name such as `"billing-core": "^2.0.0"` in `package.json`; an `.npmrc` with no `@org:registry=` line; a `registry=` or `@scope:registry=` line pointing at an unexpected host; the `.npmrc` missing from the repository. Severity: exploitable. Source: https://github.com/OWASP/ASVS/blob/master/5.0/en/0x24-V15-Secure-Coding-and-Architecture.md#v152-security-architecture-and-dependencies

## Known vulnerabilities and inventory

- **Scan dependencies on every build, keep an SBOM, and remediate findings within the timeframe set for their severity** (ASVS V15.1.2, V15.2.1): "Verify that the application only contains components which have not breached the documented update and remediation time frames." - run a vulnerability scanner in the pipeline, maintain an inventory of third-party components drawn from trusted repositories, and treat each finding as a task with a deadline by severity; when a finding is deliberately accepted, suppress that one CVE, never the package. Why: a public CVE in a reachable dependency comes with a published write-up and often a public exploit, and attackers scan for exactly those versions. Smell: `audit=false` in `.npmrc` or `--audit-level=none`; an ignore list entry naming a whole package instead of a CVE id; a bump in `overrides` or `resolutions` to a release that does not contain the fix; a scanner step deleted or marked `continue-on-error`. Severity: exploitable. Source: https://github.com/OWASP/ASVS/blob/master/5.0/en/0x24-V15-Secure-Coding-and-Architecture.md#v152-security-architecture-and-dependencies

## Publishing to npm

- **Publish through two-factor authentication or trusted publishing, and keep tokens and secrets out of the repository and the tarball**: "Store the token in a CI secret store and never commit it." - prefer OIDC trusted publishing, which needs no long-lived token and attaches provenance; where a token is unavoidable use a granular, short-lived one with the narrowest scope; require 2FA on the account; and declare a `files` allowlist in `package.json` so `.env` and similar files never ship. Why: a leaked publish token or an unprotected account lets an attacker push a malicious version to every downstream consumer. Smell: an `.npmrc` containing `_authToken=` committed; `npm publish` driven by a long-lived `NPM_TOKEN` secret with no OIDC step; a `.gitignore` entry with no matching `.npmignore` or `files` entry (when both ignore files exist only `.npmignore` governs the tarball); a publish step with no `--dry-run` review of the packed file list. Severity: exploitable. Source: https://cheatsheetseries.owasp.org/cheatsheets/NPM_Security_Cheat_Sheet.html#9-minimize-npm-access-token-use

## CI pipeline

- **Keep CI secrets in the platform secret store, scoped to the one job that needs them, and never print them**: "Secrets should never be hardcoded in code repositories or CI/CD configuration files." - secrets live in the CI secret store or a vault, carry the minimum permissions for their single task, are short-lived where the platform supports federation, and never reach the console, logs, command history or built images. Why: a secret in a workflow file, a build log or an image layer is readable by everyone with read access to the repository, and a broad one hands them the whole account. Smell: a token literal in a workflow file or `Dockerfile`; `echo $SECRET` or `set -x` in a step that uses credentials; `permissions: write-all` or no `permissions:` block on a job that only needs `contents: read`; one deploy credential reused across unrelated pipelines; a static cloud access key where OIDC federation is available; `docker run --privileged` in a pipeline step. Severity: exploitable. Source: https://cheatsheetseries.owasp.org/cheatsheets/CI_CD_Security_Cheat_Sheet.html#secrets-management
- **Review every pipeline configuration change before merge, behind a protected branch, and reference third-party pipeline steps immutably**: "If the file is stored alongside the code, it is imperative that the file is reviewed before any merge request is approved." - treat workflow files as privileged code: require a review that cannot be bypassed, protect the branch they run from, avoid auto-merge, require manual approval before production deploys, and pin third-party steps to a full commit hash rather than a moving tag. Why: whoever can change the pipeline runs code with the pipeline's credentials, and a moving tag lets a compromised upstream step do the same without touching your repository. Smell: a workflow edit buried in an unrelated feature PR; branch protection with no required review or with auto-merge enabled; `uses: vendor/action@main` or `@v1` instead of a pinned commit hash; a production deploy job with no approval gate. Severity: defence in depth. Source: https://cheatsheetseries.owasp.org/cheatsheets/CI_CD_Security_Cheat_Sheet.html#pipeline-and-execution-environment

## DNS and hosting configuration

- **Remove or repoint the DNS record before decommissioning the resource it targets**: "The common mistake is doing these steps in reverse: deleting the cloud resource first, which creates an immediate window for takeover that persists until someone notices the dangling record." - when a hosted app, bucket, CDN endpoint or delegated zone goes away, update the `CNAME`, `A`, `NS` or `MX` record first, wait out the TTL, then delete the resource, and keep any domain verification `TXT` record in place. Why: an attacker who claims the orphaned name serves content on your subdomain, receives cookies scoped to the parent domain, passes wildcard CSP, CORS and OAuth redirect checks and can obtain a TLS certificate for it. Smell: an infrastructure change deleting a site, bucket or app while the matching record stays in the DNS config; a wildcard `*.example.com` record; a `.example.com` cookie domain or `*.example.com` in a CSP, CORS or OAuth redirect allowlist, which turns a takeover into session theft. Severity: exploitable. Source: https://cheatsheetseries.owasp.org/cheatsheets/Subdomain_Takeover_Prevention_Cheat_Sheet.html#1-manage-dns-record-lifecycle-during-decommissioning
