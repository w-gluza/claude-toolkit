# Security review rules: authentication and sessions

Extracted 2026-11-10 from OWASP ASVS 5.0.0, the OWASP Cheat Sheet Series and the OWASP API Security Top 10 2023 (CC BY-SA 4.0), MDN (CC BY-SA 2.5) and the Next.js 16.4.5 documentation (MIT). One rule per bullet, one source link each. Quotations are short excerpts; the rest is original.

## Sessions and cookies

- **Generate session tokens server-side from a CSPRNG with at least 128 bits of entropy and issue a fresh one on every login, re-authentication and privilege change** (ASVS V7.2.3, V7.2.4): "generates a new session token on user authentication, including re-authentication, and terminates the current session token" - the token must be unguessable and the pre-login identifier must die at login, so an identifier the attacker planted or predicted never becomes an authenticated session. Why: stops session guessing and session fixation, both of which hand the attacker a logged-in session without a password. Smell: `sessionId = Math.random().toString(36)` or `Date.now()` as the token, or a login handler that writes `session.userId = user.id` into the existing session with no `regenerate()`. Severity: exploitable. Source: https://github.com/OWASP/ASVS/blob/master/5.0/en/0x16-V7-Session-Management.md#v72-fundamental-session-management-security
- **Set the session cookie with Secure, HttpOnly, an explicit SameSite value, no Domain attribute and the __Host- prefix, and deliver it only via Set-Cookie** (ASVS V3.3.1, V3.3.3, V3.3.4): "cookies have the '__Host-' prefix for the cookie name unless they are explicitly designed to be shared with other hosts" - the prefix forces Secure and Path=/ and forbids Domain, so the cookie is bound to the one host that set it; HttpOnly keeps it out of script and SameSite limits cross-site sends. Why: a script-readable, domain-wide or cleartext session cookie turns any XSS, sibling-subdomain compromise or on-path observer into session theft. Smell: `cookies().set('session', token)` with no `httpOnly`, `secure` or `sameSite`, a `Domain=example.com` on the session cookie, a name like `sid` with no `__Host-`, or the token returned in a JSON body for `localStorage`. Severity: defence in depth. Source: https://github.com/OWASP/ASVS/blob/master/5.0/en/0x12-V3-Web-Frontend-Security.md#v33-cookie-setup
- **Enforce idle and absolute session timeouts on the server and make logout invalidate the session in the backend store, not just in the browser** (ASVS V7.3.1, V7.3.2, V7.4.1): "when session termination is triggered (such as logout or expiration), the application disallows any further use of the session" - expiry is tracked against server-held timestamps, and logout, password change and account disablement delete or revoke the record so a copied token stops working. Why: a stolen or leaked token otherwise stays valid for as long as the attacker keeps it warm, including after the victim logs out. Smell: a logout that only runs `cookies().delete('session')` while the store row stays valid, an expiry computed from a client-supplied `issuedAt`, or a sessions table with no `expiresAt`. Severity: defence in depth. Source: https://github.com/OWASP/ASVS/blob/master/5.0/en/0x16-V7-Session-Management.md#v74-session-termination

## Passwords and login

- **Store passwords only with a memory-hard, salted password hashing function from a maintained library and never with a general-purpose hash or home-made scheme** (ASVS V11.4.2): "Use Argon2id with a minimum configuration of 19 MiB of memory, an iteration count of 2, and 1 degree of parallelism." - scrypt is the fallback, bcrypt only for legacy systems with its 72-byte input limit enforced, and the comparison uses the library's verify function so it runs in constant time. Why: a leaked table of fast or unsalted hashes is cracked offline at billions of guesses per second, and a custom scheme usually has a flaw the attacker finds first. Smell: `createHash('sha256').update(password)`, `md5(password + salt)`, bcrypt with `saltRounds: 4`, a hand-rolled salt and loop, or `storedHash === computed` string comparison. Severity: defence in depth. Source: https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html#introduction
- **Return the same response, status code and timing for every failed login, registration and password reset attempt whether or not the account exists** (ASVS V6.3.8): "valid users cannot be deduced from failed authentication challenges, such as by basing on error messages, HTTP response codes, or different response times" - run the hash check even when the user is missing, and reuse one generic message across login, sign-up and forgot-password. Why: an existence oracle lets an attacker build a confirmed user list for credential stuffing, spraying and phishing. Smell: `if (!user) return 'No account with that email'` beside `return 'Wrong password'`, a `404` for unknown users and `401` for bad passwords, or an early `return` before the hash verification when the lookup fails. Severity: exploitable. Source: https://github.com/OWASP/ASVS/blob/master/5.0/en/0x15-V6-Authentication.md#v63-general-authentication-security
- **Throttle failed logins per account and per source, and design any lockout so an attacker cannot use it to lock the real owner out** (ASVS V6.3.1): "care must be taken to prevent it from being used to cause a denial of service by locking out other users' accounts" - the failure counter belongs to the account rather than the IP address, lockout grows exponentially or is temporary, and a password reset or MFA path lets the owner back in while locked. Why: without throttling an attacker brute-forces or stuffs credentials at full speed; with naive lockout the attacker denies service to any user by sending bad passwords in their name. Smell: a login handler with no attempt counter, a limiter keyed only on `req.ip`, or `locked = true` set permanently on the account with the reset flow also refusing locked users. Severity: exploitable. Source: https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html#account-lockout

## Self-contained tokens

- **Verify every self-contained token's signature with a pinned algorithm allowlist and trusted keys, and reject it unless exp, nbf and aud pass** (ASVS V9.1.1, V9.1.2, V9.1.3, V9.2.1, V9.2.3): "The allowlist must include the permitted algorithms, ideally only either symmetric or asymmetric algorithms, and must not include the 'None' algorithm." - the verifier names the algorithm itself rather than reading it from the token header, loads keys from configuration rather than from jku, jwk or x5u headers, and checks validity window and audience before trusting any claim. Why: an unverified or loosely verified token lets the attacker mint their own claims and become any user, or replay a token issued for another service. Smell: `jwt.decode(token)` used as the authentication check, `jwt.verify(token, key)` with no `algorithms` option, `ignoreExpiration: true`, no `audience` or `issuer` option, or a key fetched from `header.jku`. Severity: exploitable. Source: https://github.com/OWASP/ASVS/blob/master/5.0/en/0x18-V9-Self-contained-Tokens.md#v91-token-source-and-integrity
- **Keep secrets and personal data out of signed token payloads; store them server-side behind an opaque reference instead**: "The payload is only base64url encoded, not encrypted, so anyone who obtains the token can read every claim." - a JWS proves integrity, not confidentiality, and the token also lands in logs, browser storage and referrer headers. Why: anyone holding the token, including the user and every intermediary that logs it, reads whatever was put in the claims. Smell: `jwt.sign({ email, phone, passwordHash, ... })`, API keys or internal identifiers of other users in the claims, or the full token written to logs. Severity: exploitable. Source: https://cheatsheetseries.owasp.org/cheatsheets/JSON_Web_Token_Cheat_Sheet.html#signed-jwts-are-not-confidential

## Cross-site request forgery

- **Protect every cookie-authenticated state change with a CSRF token or an Origin check in addition to SameSite, and never change state on GET** (ASVS V3.5.1): "should be treated as a defense-in-depth layer and combined with a CSRF token or a double-submit pattern rather than relied on alone" - SameSite=Lax still sends the cookie on top-level navigations, is scoped to the registrable domain rather than the origin, is not enforced by every browser and does nothing against client-side CSRF. Why: a page the victim visits elsewhere can submit a form or navigation that the browser decorates with the victim's session cookie, performing the action as them. Smell: a `POST` handler or Server Action that mutates state and checks only the session cookie, with no CSRF token and no `Origin` comparison, a state change reachable by `GET`, or `sameSite: 'none'` on the session cookie. Severity: exploitable. Source: https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html#limitations-of-samesite

## Password reset

- **Issue password reset tokens from a CSPRNG, long enough to resist guessing, single-use, short-lived, rate-limited, and change nothing on the account until a valid token is presented** (ASVS V6.4.3): "Do not make a change to the account until a valid token is presented, such as locking out the account." - the token is stored hashed with an expiry, deleted on use, bound to the account, and the reset must not bypass MFA. Why: a short, reusable or never-expiring token is guessed or replayed into an account takeover, and a request-time lockout turns the flow into a denial of service against any email address. Smell: `randomInt(1000000)` or `randomBytes(4)` as the token, no `expiresAt`, the token row kept after a successful reset, `WHERE token = ?` with no used or expired check, or `user.locked = true` set when the reset is merely requested. Severity: exploitable. Source: https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html#introduction

## Next.js

- **Verify the session in the data access layer on every data read and mutation, and treat the proxy cookie check as an optimistic pre-filter only**: "While Proxy can be useful for initial checks, it should not be your only line of defense in protecting your data." - the proxy runs on every route including prefetches and only reads the cookie, so the real check lives in a `verifySession()` called by every Server Component, Server Action and Route Handler that touches data. Why: a route, action or handler outside the matcher, or reached without the proxy, serves or mutates data for an unauthenticated caller. Smell: `verifySession()` appearing only in `proxy.ts`, a Server Action or Route Handler that queries by a `userId` taken from form data or the URL without calling the DAL, or a `matcher` that excludes `/api`. Severity: exploitable. Source: https://nextjs.org/docs/app/guides/authentication#optimistic-checks-with-proxy-optional
