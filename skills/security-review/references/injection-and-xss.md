# Security review rules: injection and cross-site scripting

Extracted 2026-11-10 from OWASP ASVS 5.0.0, the OWASP Cheat Sheet Series and the OWASP API Security Top 10 2023 (CC BY-SA 4.0), MDN (CC BY-SA 2.5) and the Next.js 16.4.5 documentation (MIT). One rule per bullet, one source link each. Quotations are short excerpts; the rest is original.

## Database, command and template injection

- **Bind every value through a parameterised query and allow-list the structural parts, including behind the ORM raw-query escape hatch** (ASVS V1.2.4): "Concatenating untrusted values into the query before preparing it defeats this protection." - the SQL text stays fixed in code and values travel through the driver's placeholders; table names, column names and sort direction cannot be placeholders, so map the user's choice to a small set of application-owned strings and reject anything else. Why: string-built SQL lets an attacker read, change or delete rows the query was never meant to touch. Smell: `` query(`SELECT * FROM users WHERE email = '${email}'`) ``, `orm.raw("... " + value)`, `createQuery("from Inventory where productID='" + id + "'")`, `` `ORDER BY ${req.query.sort}` ``. Severity: exploitable. Source: https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html#parameterized-queries
- **Confirm a NoSQL filter value is the scalar you expect before it goes into the query object**: "Building a query object does not prevent operator injection when an untrusted value is itself an object." - a JSON body can carry an object where a string was expected and the driver reads its keys as query operators; check the type, never pass a client-supplied object or raw query fragment through, and keep `$where`, `$regex` and `$expr` out of client reach. Why: an operator in place of a value turns a login lookup into a match-anything query or runs attacker JavaScript inside the database. Smell: `find({ name: req.body.name })` with no `typeof name === "string"` check, `find(req.body.filter)`, `{ $where: expr }` built from request data. Severity: exploitable. Source: https://cheatsheetseries.owasp.org/cheatsheets/NoSQL_Security_Cheat_Sheet.html#prevent-nosql-injection
- **Call a library function instead of a shell, and when a process is unavoidable pass an argument array to an allow-listed command** (ASVS V1.2.5): "Built-in library functions are a very good alternative to OS Commands, as they cannot be manipulated to perform tasks other than those it is intended to do." - prefer `mkdir()` to `system("mkdir ...")`; otherwise use a process API that separates the command from its arguments, pick the command from a fixed list, hold each argument to an allow-list pattern and end option parsing with `--`. Why: shell metacharacters in one argument chain a second command that runs with the application's privileges. Smell: `exec("convert " + file)`, `` exec(`ping ${host}`) ``, `spawn(cmd, args, { shell: true })`, `os.system(f"... {name}")`, `subprocess.run(..., shell=True)`. Severity: exploitable. Source: https://cheatsheetseries.owasp.org/cheatsheets/OS_Command_Injection_Defense_Cheat_Sheet.html#defense-option-1-avoid-calling-os-commands-directly
- **Render fixed templates and pass untrusted input only as render variables** (ASVS V1.3.7): "Render a fixed template and pass user values as named variables, the same way a parameterized query keeps data out of SQL." - never build template source, a template name or an include path from request data; auto-escaping protects printed values, not template code the engine has already parsed; a feature where users author templates needs the engine's sandbox, a minimal render context and an isolated process. Why: template syntax in user input is evaluated by the engine and in most engines reaches application objects and code execution. Smell: `render_template_string(user_text)`, `from_string(body)`, `template_from_string(...)`, `new Template(input)`, `compile(req.body.template)`, `render(req.query.page + ".html")`. Severity: exploitable. Source: https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Template_Injection_Prevention_Cheat_Sheet.html#pass-untrusted-input-only-as-data
- **Never feed untrusted bytes to a native object deserialiser; use a pure data format and an allow-list of types** (ASVS V1.5.2): "Deserialization mechanisms that are explicitly defined as insecure must not be used with untrusted input." - parse JSON into plain data-transfer objects, restrict which classes a deserialiser may construct, and sign serialised blobs so only the application's own output is ever deserialised. Why: native serialisation formats rebuild arbitrary objects whose constructors or callbacks run attacker-chosen code on the server. Smell: `pickle.loads(request.data)`, `yaml.load(body, Loader=yaml.Loader)`, `unserialize($_COOKIE[...])`, `new ObjectInputStream(request.getInputStream())`, `BinaryFormatter.Deserialize(stream)`. Severity: exploitable. Source: https://github.com/OWASP/ASVS/blob/master/5.0/en/0x10-V1-Encoding-and-Sanitization.md#v15-safe-deserialization
- **Build file paths from internally generated names, and when a user-supplied name is unavoidable resolve it and confirm it stays inside the intended directory** (ASVS V5.3.2): "instead of user-submitted filenames, it uses internally generated or trusted data" - store uploads under a key the server generates, map a download request to a record rather than a path, and let archive extraction ignore the path recorded inside the archive. Why: `..` segments and absolute paths in a filename read or overwrite files outside the upload directory, including source, configuration and secrets. Smell: `fs.readFile(path.join(UPLOADS, req.params.name))` with no check that the resolved path still starts with `UPLOADS`, `res.sendFile(req.query.file)`, `open(os.path.join(base, filename))`, zip entry names used as write paths. Severity: exploitable. Source: https://github.com/OWASP/ASVS/blob/master/5.0/en/0x14-V5-File-Handling.md#v53-file-storage
- **Fetch from the server only hosts on an allow-list, never a complete URL the client supplied** (ASVS V1.3.6): "Do not accept complete URLs from the user because URL are difficult to validate and the parser can be abused depending on the technology used" - accept a host or an identifier, match it against an explicit allow-list, build the request yourself with a fixed scheme, port and path, disable redirect following in the HTTP client, and where arbitrary external hosts are a product requirement reject private, loopback and link-local ranges after DNS resolution and never relay the raw response body to the client. Why: the server becomes a proxy into the internal network, reaching cloud metadata endpoints, admin interfaces and services a firewall was meant to hide. Smell: `fetch(req.body.url)`, `http.get(webhook.url)`, `fetch(imageUrl, { redirect: "follow" })`, `res.send(await upstream.text())` for a user-chosen target, a scheme check that still allows `file:` or `gopher:`. Severity: exploitable. Source: https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html#url

## Cross-site scripting

- **Encode output for the exact context it lands in: HTML body, quoted attribute, JavaScript string or URL component** (ASVS V1.2.1): "There are many different output encoding methods because browsers parse HTML, JS, URLs, and CSS differently." - rely on the framework's automatic escaping for element content, quote every attribute placeholder, use a JavaScript-string encoder for data inside `<script>` and `encodeURIComponent()` for query values, and keep untrusted data out of event handlers, `<style>` blocks and bare tag or attribute names where no encoder can help. Why: an encoder for the wrong context leaves exactly the characters that close the current syntax and start attacker markup or code. Smell: `<div class=${cls}>` unquoted, `onclick="handle('${name}')"`, `"?q=" + term` with no `encodeURIComponent`, HTML-entity encoding applied to data inside a script block, `{{ user.bio }}` placed inside `<style>`. Severity: exploitable. Source: https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html#output-encoding
- **Write untrusted data to the DOM through text sinks, and check the scheme before it becomes a URL** (ASVS V1.2.2): "Try to refactor your code to remove references to unsafe sinks like innerHTML, and instead use textContent or value." - `textContent`, `createTextNode`, `insertAdjacentText`, `value` and `setAttribute` on a fixed non-event, non-URL attribute treat data as text; `innerHTML`, `outerHTML`, `insertAdjacentHTML`, `document.write`, `eval`, `new Function`, `setTimeout` with a string and `javascript:` in `href`, `src` or `location` execute it, so URL-bearing attributes need the scheme held to `http` or `https` first. Why: one markup-interpreting sink fed from a URL parameter or an API response is a complete DOM-based XSS with no server involvement. Smell: `el.innerHTML = data`, `document.write(q)`, `setTimeout(code)`, `eval(json)`, `<a href={user.website}>`, `location.href = params.get("next")`, `el.setAttribute("onclick", ...)`. Severity: exploitable. Source: https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html#safe-sinks
- **Put a maintained HTML sanitiser between user HTML and every framework escape hatch, and in the browser enforce it with Trusted Types**: "In this case it's up to the developer to ensure that the content is safe, by sanitizing it." - `dangerouslySetInnerHTML`, `v-html`, `bypassSecurityTrust*`, `unsafeHTML` and a template's `safe` filter switch encoding off, so the value must come straight from a sanitiser call with nothing modifying it afterwards; a `require-trusted-types-for 'script'` policy makes the browser refuse plain strings at `innerHTML`, `document.write`, `eval` and script `src`, so the sanitiser cannot be skipped by a later change. Why: raw HTML from one user carries script tags and event handlers that run in every other user's session. Smell: `dangerouslySetInnerHTML={{ __html: post.body }}`, `v-html="comment"`, `bypassSecurityTrustHtml(input)`, `{{ text|safe }}`, `createHTML: (s) => s`, a sanitised string passed through `.replace()` on its way to the sink. Severity: exploitable. Source: https://developer.mozilla.org/en-US/docs/Web/Security/Attacks/XSS#sanitization
- **Do not read configuration from `window` or `document` globals on a page that renders user-controlled markup**: "Document properties, including built-in ones, are always overshadowed by DOM Clobbering, even right after they are assigned a value." - declare values with `const` or `let` in module scope, keep them off `window`, and have the sanitiser strip or namespace `id` and `name` attributes so an injected element cannot shadow a lookup. Why: an element whose `id` matches a global name replaces that global with a DOM node, so a script URL or feature flag read from `window` becomes attacker-chosen even when scripts themselves are filtered out. Smell: `script.src = window.ASSET_BASE + "/app.js"`, `const cfg = window.config || {}`, `var flag` at top level, a sanitiser configured to keep `id` and `name` on user HTML. Severity: defence in depth. Source: https://cheatsheetseries.owasp.org/cheatsheets/DOM_Clobbering_Prevention_Cheat_Sheet.html#7-do-not-trust-document-built-in-apis-before-validation
- **Escape `<` as `<` when serialising JSON-LD or any JSON into an inline script in Next.js** (ASVS V1.2.3): "which does not sanitize malicious strings used in XSS injection" - `JSON.stringify` keeps `<` literally, so a `<` inside a product name or description can end the script block early; apply `.replace(/</g, '\\u003c')` to the string handed to `dangerouslySetInnerHTML`, or use a serialiser built for embedding in script. Why: data from the database or a content system becomes script that runs on a page the whole site trusts. Smell: `<script type="application/ld+json" dangerouslySetInnerHTML={{ __html: JSON.stringify(jsonLd) }} />` with no `<` replacement. Severity: exploitable. Source: https://nextjs.org/docs/app/guides/json-ld
