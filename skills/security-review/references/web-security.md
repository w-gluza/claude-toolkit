# Security review rules: browser and HTTP security

Extracted 2026-11-10 from OWASP ASVS 5.0.0, the OWASP Cheat Sheet Series and the OWASP API Security Top 10 2023 (CC BY-SA 4.0), MDN (CC BY-SA 2.5) and the Next.js 16.4.5 documentation (MIT). One rule per bullet, one source link each. Quotations are short excerpts; the rest is original.

## Content Security Policy

- **Ship a strict Content-Security-Policy on every HTML response and never loosen script-src with 'unsafe-inline' or host wildcards** (ASVS V3.4.3): "As a minimum, a global policy must be used which includes the directives object-src 'none' and base-uri 'none' and defines either an allowlist or uses nonces or hashes." - prefer per-response nonces or hashes with 'strict-dynamic'; host allow-lists are routinely bypassed and 'unsafe-inline' switches the script protection off. Why: a strict CSP stops injected markup from running script even when an XSS bug exists. Smell: no `Content-Security-Policy` in the headers config, `script-src 'self' 'unsafe-inline'`, `script-src *` or `https:`, a policy missing `object-src` or `base-uri`, or a regex that stamps `nonce=` onto every `<script` tag in rendered HTML. Severity: defence in depth. Source: https://github.com/OWASP/ASVS/blob/master/5.0/en/0x12-V3-Web-Frontend-Security.md#v34-browser-security-mechanism-headers
- **Generate the CSP nonce per request in the Next.js proxy and render nonced pages dynamically**: "Every time a page is viewed, a fresh nonce should be generated." - the proxy creates a random nonce, puts it in the `Content-Security-Policy` header and an `x-nonce` request header, and Next.js attaches it to its own scripts only when the page renders per request; static and partially prerendered pages never receive it. Why: a reused or guessable nonce lets injected script carry the right nonce and run. Smell: `const nonce` computed at module scope or from a fixed string, a production CSP in `next.config.js` that keeps `'unsafe-inline'`, or a proxy `matcher` that excludes the pages rendering user content. Severity: defence in depth. Source: https://nextjs.org/docs/app/guides/content-security-policy#adding-a-nonce-with-proxy

## Cross-origin requests

- **Set Access-Control-Allow-Origin to a fixed value or an allow-list match, never the reflected Origin** (ASVS V3.4.2): "or if the Origin HTTP request header field value is used, it is validated against an allowlist of trusted origins." - compare the whole origin string against a list; `*` is acceptable only on responses with nothing sensitive, and browsers refuse it with credentials anyway. Why: reflecting the caller's origin on a credentialed response lets any site read the user's authenticated data. Smell: `res.setHeader('Access-Control-Allow-Origin', req.headers.origin)` next to `Access-Control-Allow-Credentials: true`, `cors({ origin: true })`, `origin.endsWith('example.com')` or an unanchored regex. Severity: exploitable. Source: https://github.com/OWASP/ASVS/blob/master/5.0/en/0x12-V3-Web-Frontend-Security.md#v34-browser-security-mechanism-headers
- **Reject cross-site requests to sensitive endpoints using the Sec-Fetch-* headers, and mark authenticated resources with Cross-Origin-Resource-Policy** (ASVS V3.5.8): "strict validation of the Sec-Fetch-* HTTP request header fields to ensure that the request did not originate from an inappropriate cross-origin call" - allow `same-origin` and `none`, allow `cross-site` only for top-level GET navigations, send `Vary` on the headers you read, and set `Cross-Origin-Resource-Policy: same-origin` so browsers drop authenticated images or files embedded by other sites. Why: stops request forgery and cross-site leaks that embed or measure a logged-in user's responses. Smell: `app.get('/admin', ...)` or an export route that never reads `sec-fetch-site`, authenticated file routes with no `Cross-Origin-Resource-Policy`. Severity: defence in depth. Source: https://github.com/OWASP/ASVS/blob/master/5.0/en/0x12-V3-Web-Frontend-Security.md#v35-browser-origin-separation
- **Check event.origin exactly before trusting a postMessage, and name the target origin when sending** (ASVS V3.5.5): "Check the origin properly exactly to match the FQDN(s) you expect." - compare against a full origin string, validate the message shape, treat the payload as data (never `eval` or `innerHTML`) and pass the expected origin rather than `*` to `postMessage`. Why: any page holding a window reference can post to it, so an unchecked listener becomes attacker input to privileged code. Smell: `addEventListener('message', e => ...)` with no `e.origin ===` test, `e.origin.includes('.example.com')` or `endsWith`, `postMessage(payload, '*')`. Severity: exploitable. Source: https://cheatsheetseries.owasp.org/cheatsheets/HTML5_Security_Cheat_Sheet.html#web-messaging

## Framing and window isolation

- **Send frame-ancestors on every response, keep X-Frame-Options only as a legacy fallback, and add Cross-Origin-Opener-Policy to document responses** (ASVS V3.4.6, V3.4.8): "Note that the X-Frame-Options header field, although supported by browsers, is obsolete and may not be relied upon." - `frame-ancestors 'none'` or `'self'` must travel as an HTTP header (it is ignored in `<meta>`), and `Cross-Origin-Opener-Policy: same-origin` severs the window handle other origins get through `window.open`. Why: clickjacking overlays the real page under an attacker's UI, and shared window handles enable tabnabbing and frame counting. Smell: `X-Frame-Options: SAMEORIGIN` with no `frame-ancestors`, `ALLOW-FROM`, `<meta http-equiv="Content-Security-Policy" content="frame-ancestors ...">`, or a headers config whose `source` matches `/` only. Severity: exploitable. Source: https://github.com/OWASP/ASVS/blob/master/5.0/en/0x12-V3-Web-Frontend-Security.md#v34-browser-security-mechanism-headers

## Transport and response headers

- **Send Strict-Transport-Security on every HTTPS response with a max-age of at least one year and includeSubDomains** (ASVS V3.4.1): "A maximum age of at least 1 year must be defined, and for L2 and up, the policy must apply to all subdomains as well." - browsers only honour the header over HTTPS; add `preload` once the whole domain is ready. Why: without HSTS the first plain-HTTP request can be intercepted and downgraded to steal cookies or inject content. Smell: `max-age=300`, `max-age=0` left from a rollback, missing `includeSubDomains`, or the header set in one route handler instead of globally. Severity: defence in depth. Source: https://github.com/OWASP/ASVS/blob/master/5.0/en/0x12-V3-Web-Frontend-Security.md#v34-browser-security-mechanism-headers
- **Send X-Content-Type-Options: nosniff on every response together with an exact Content-Type** (ASVS V3.4.4): "This instructs browsers not to use content sniffing and MIME type guessing for the given response" - the browser then rejects scripts and styles whose declared type does not match and never promotes a text or JSON body to HTML. Why: without it uploaded text or an API response can be rendered as HTML or script inside the site's origin. Smell: a download route returning user files with `Content-Type: text/plain` or no type and no `nosniff`, `helmet({ noSniff: false })`. Severity: defence in depth. Source: https://github.com/OWASP/ASVS/blob/master/5.0/en/0x12-V3-Web-Frontend-Security.md#v34-browser-security-mechanism-headers
- **Set a Referrer-Policy that strips path and query from cross-origin requests** (ASVS V3.4.5): "prevent leakage of technically sensitive data to third-party services via the 'Referer' HTTP request header field" - use `strict-origin-when-cross-origin` or `no-referrer`, and `rel="noreferrer"` on links to untrusted targets. Why: a third-party page, CDN or analytics host otherwise receives the full URL the user came from, including any token or identifier it carried. Smell: `Referrer-Policy: unsafe-url` or `no-referrer-when-downgrade`, or no header at all on an app whose URLs hold `?token=` or reset links. Severity: defence in depth. Source: https://github.com/OWASP/ASVS/blob/master/5.0/en/0x12-V3-Web-Frontend-Security.md#v34-browser-security-mechanism-headers

## Third-party scripts and redirects

- **Load third-party scripts and styles only from static, versioned URLs with Subresource Integrity** (ASVS V3.6.1): "only hosted externally (e.g., on a Content Delivery Network) if the resource is static and versioned and Subresource Integrity (SRI) is used to validate the integrity of the asset" - add `integrity` with `crossorigin="anonymous"`; a hash cannot pin a URL whose content changes, so unversioned URLs must be self-hosted instead. Why: a compromised or hijacked host otherwise runs arbitrary script in every user's session. Smell: `<script src="https://cdn.example/lib.js">` or `<Script src=...>` without `integrity`, a URL ending in `@latest` or carrying no version. Severity: defence in depth. Source: https://github.com/OWASP/ASVS/blob/master/5.0/en/0x12-V3-Web-Frontend-Security.md#v36-external-resource-integrity
- **Redirect only to destinations on an allow-list matched on the parsed URL, never on a raw user-supplied string** (ASVS V3.7.2): "Compare the parsed scheme, canonical host, and effective port against an explicit allowlist; constrain the path when only specific endpoints are permitted." - map a short id to a server-side URL where possible, and for local return URLs use a helper that rejects non-local targets. Why: a link on your own domain that forwards to an attacker's site makes phishing credible and can carry tokens across. Smell: `res.redirect(req.query.returnTo)`, `redirect(searchParams.get('next'))`, a guard that only checks `startsWith('/')` or `includes('example.com')`. Severity: exploitable. Source: https://cheatsheetseries.owasp.org/cheatsheets/Unvalidated_Redirects_and_Forwards_Cheat_Sheet.html#validating-urls
