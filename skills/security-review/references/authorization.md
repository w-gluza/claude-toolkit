# Security review rules: authorisation

Extracted 2026-11-10 from OWASP ASVS 5.0.0, the OWASP Cheat Sheet Series and the OWASP API Security Top 10 2023 (CC BY-SA 4.0), MDN (CC BY-SA 2.5) and the Next.js 16.4.5 documentation (MIT). One rule per bullet, one source link each. Quotations are short excerpts; the rest is original.

## Object level: the right user for this record

- **Check that the caller may act on the specific record every time an id comes from the client** (ASVS V8.2.2, API1:2023): "Every API endpoint that receives an ID of an object, and performs any action on the object, should implement object-level authorization checks." - being allowed to call the endpoint says nothing about this record; compare the record's owner, membership or tenant with the server-side session before reading, changing or deleting it, and do not count a session-id-equals-param-id comparison as the check. Why: horizontal privilege escalation, where one logged-in user reads or edits every other user's data by changing an id. Smell: `const post = await db.post.findUnique({ where: { id: params.id } })` followed by `return post` or `db.post.delete(...)` with no comparison against `session.user.id`; a GraphQL mutation that takes `reportKeys` and deletes without a resolver-level owner check. Severity: exploitable. Source: https://owasp.org/API-Security/editions/2023/en/0xa1-broken-object-level-authorization/#is-the-api-vulnerable
- **Scope the lookup to the caller's own data instead of fetching by id and remembering to check afterwards**: "When looking up objects based on primary keys, use datasets that users have access to." - make the query itself carry the owner or tenant predicate, so a missing check cannot return someone else's row; random or UUID identifiers slow enumeration but are never a substitute for the check. Why: find-then-check is forgotten on the next endpoint and ids leak through logs, referrers and other responses. Smell: `Project.find(params[:id])` where `current_user.projects.find(params[:id])` was available; `where: { id }` on a user-owned table with no `userId` or `tenantId` in the clause; a pull request that swaps integer ids for UUIDs and drops the ownership check "because they cannot be guessed". Severity: exploitable. Source: https://cheatsheetseries.owasp.org/cheatsheets/Insecure_Direct_Object_Reference_Prevention_Cheat_Sheet.html#mitigation
- **Verify tenant membership on the server and put the tenant in every tenant-owned query** (ASVS V8.4.1): "For each tenant-scoped resource, verify that the authenticated principal can act in the resource's tenant." - a tenant id from a header, path or body is a selector, not proof; resolve it against the authenticated user's current membership and enforce it at a boundary every tenant-owned access path goes through. Why: cross-tenant data access, where one customer reads or edits another customer's records by naming their tenant. Smell: `request.headers.get("X-Tenant-ID")` or `body.orgId` fed straight into `WHERE tenant_id = :tid`; a repository method on a tenant-owned table that takes only `resourceId`; a cache key built from `userId` alone in a multi-tenant app. Severity: exploitable. Source: https://cheatsheetseries.owasp.org/cheatsheets/Multi_Tenant_Security_Cheat_Sheet.html#3-preventing-cross-tenant-data-access-idor-prevention

## Function level: the right role for this operation

- **Deny every function by default and grant explicitly, whatever the path or HTTP method** (ASVS V8.2.1, API5:2023): "The enforcement mechanism(s) should deny all access by default, requiring explicit grants to specific roles for access to every function." - a new route must be unreachable until a rule names who may call it; do not infer "admin" from a `/admin` prefix, and do not let a guarded `GET` share a handler with an unguarded `DELETE`. Why: vertical privilege escalation by forced browsing, guessing an administrative URL or switching the method on a known one. Smell: a middleware matcher or `protectedRoutes = ['/dashboard']` that lists what to protect so anything new is open; an export or bulk endpoint under `/api/users/` with no role check because only `/api/admin/*` is guarded; a route file whose `GET` checks `isAdmin` while `DELETE` or `POST` does not. Severity: exploitable. Source: https://owasp.org/API-Security/editions/2023/en/0xa5-broken-function-level-authorization/#how-to-prevent
- **Re-check the caller inside every Server Function, not only in the page that renders the form**: "A page-level authentication check does not extend to the Server Actions defined within it. Always re-verify inside the action" - a `'use server'` function is a public endpoint with its own id; a redirect in the page or layout only decides which UI is rendered, and layouts do not re-render on client navigation. Why: anyone can invoke the action directly with a fabricated form post and skip the page guard. Smell: a `'use server'` body that goes straight to `db.` with no `auth()` or `verifySession()` call; a role check that lives in `layout.tsx` or `proxy.ts` only; a Route Handler that trusts the page it is fetched from. Severity: exploitable. Source: https://nextjs.org/docs/app/guides/data-security#authentication-and-authorization

## Where the decision is made

- **Make the decision on the server from server-verified identity, never from a value the client can edit** (ASVS V8.3.1): "Verify that the application enforces authorization rules at a trusted service layer and doesn't rely on controls that an untrusted consumer could manipulate, such as client-side JavaScript." - hiding a button, disabling a menu item or reading a role from the request is not a control; the role, owner and tenant must come from the session or token the server verified. Why: an attacker edits the request, so any privilege read from it is granted on demand. Smell: `{isAdmin && <DeleteButton />}` with no matching check in the action or route it calls; `const isAdmin = (await searchParams).isAdmin`; `req.body.userId`, `req.headers['x-user-id']` or a hidden `<input name="role">` used as the acting user or role. Severity: exploitable. Source: https://github.com/OWASP/ASVS/blob/master/5.0/en/0x17-V8-Authorization.md#v83-operation-level-authorization
- **Route all reads and mutations through one server-only data access layer that owns the checks**: "This approach centralizes all data access logic, making it easier to enforce consistent data access and reduces the risk of authorization bugs." - one module, marked `server-only`, that verifies the session, authorises the record and returns a minimal DTO; pages, components and actions call it and never the database. Why: scattered inline checks drift, and the one handler that forgets becomes the exploitable path. Smell: `sql` or `db.` calls spread across `page.tsx`, `route.ts` and `actions.ts` with ad hoc `if (user.id !== row.ownerId)` copies; a Client Component that imports a database helper; no `data/` or `lib/dal` module in a project with authenticated data. Severity: defence in depth. Source: https://nextjs.org/docs/app/guides/data-security#data-access-layer

## Property level: the right fields in both directions

- **Allow-list the fields a client may write; never bind the request body onto a model** (ASVS V8.2.3, API3:2023): "Allow changes only to the object's properties that should be updated by the client." - copy named fields from the parsed input into the update and leave the rest; a block-list misses the next sensitive column, and a DTO limits fields but does not replace the object-level check. Why: mass assignment, where a replayed request with an extra property such as a role, owner, price or blocked flag changes it. Smell: `db.user.update({ data: req.body })`, `Object.assign(user, body)`, `...body` spread into `data`, `User.create(params)` or `new User(req.body)` on a model that also carries `role`, `isAdmin`, `ownerId`, `balance` or `approved`. Severity: exploitable. Source: https://owasp.org/API-Security/editions/2023/en/0xa3-broken-object-property-level-authorization/#how-to-prevent
- **Return only the properties this caller is entitled to see, never the whole row** (API3:2023): "Keep returned data structures to the bare minimum, according to the business/functional requirements for the endpoint." - pick fields per endpoint and per viewer; serialising the record, the ORM entity or `SELECT *` sends every column, including ones added later, and in a server-rendered app a row passed as a prop to a Client Component is just as public as a JSON response. Why: excessive data exposure of hashes, contact details, locations or internal flags to any user who can call the endpoint. Smell: `res.json(rows)`, `return user` or `return db.user.update(...)` from a Server Action; `<Profile user={userData} />` where `userData` came from `SELECT * FROM user`; a GraphQL type that exposes `email` or `recentLocation` on an object other users can query. Severity: exploitable. Source: https://owasp.org/API-Security/editions/2023/en/0xa3-broken-object-property-level-authorization/#how-to-prevent

## High-value actions and proof

- **Gate a high-value transaction on server-held, user-confirmed data at the moment it executes**: "There should be a final control gate before transaction execution which verifies whether the transaction was properly authorized by the user." - for transfers, payouts, role changes and destructive bulk actions, the server stores the transaction the user confirmed, ties the confirmation to that stored copy and refuses execution when the data changed, the steps ran out of order or the credential is stale or reused. Why: time-of-check to time-of-use swaps and skipped confirmation steps let a tampered client execute a transaction the user never approved. Smell: an execute step that reads `amount` or `recipient` from the request again instead of from the stored draft; `if (body.confirmed)` as the whole gate; an OTP or step-up result cached in the session and reused across transactions; a flow where step 3 is reachable without step 2 having run. Severity: exploitable. Source: https://cheatsheetseries.owasp.org/cheatsheets/Transaction_Authorization_Cheat_Sheet.html#28-system-should-check-each-transaction-execution-and-make-sure-it-has-been-properly-authorized
- **Add a cross-user and cross-role negative test for every new resource endpoint**: "Authenticate as User A and create Resource X. Capture the resource identifier. Authenticate as User B (same role, different account) and attempt to read, update, and delete Resource X." - the suite must also hit administrative routes as every non-admin role and, in multi-tenant code, read broad listings as the other tenant, asserting 403 or 404 and never a leaked record. Why: authorisation decays with refactors, and only a failing test stops the regression from merging. Smell: tests for a new `/api/invoices/[id]` route that only exercise the owner and an admin fixture; a `describe('authorization')` block missing from a diff that adds a record-level endpoint; a test setup with a single seeded user or tenant. Severity: defence in depth. Source: https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Regression_Testing_Cheat_Sheet.html#horizontal-escalation-idor-validation
