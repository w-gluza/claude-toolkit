# Security review rules: secrets and data exposure

Extracted 2026-11-10 from OWASP ASVS 5.0.0, the OWASP Cheat Sheet Series and the OWASP API Security Top 10 2023 (CC BY-SA 4.0), MDN (CC BY-SA 2.5) and the Next.js 16.4.5 documentation (MIT). One rule per bullet, one source link each. Quotations are short excerpts; the rest is original.

## Secrets in source, bundles and builds

- **Keep keys and secrets out of source control and build artefacts** (Key Management Cheat Sheet): "Cryptographic keys, secrets, and API keys should never be committed to source code repositories or embedded in build artifacts" - a secret belongs in a secret store or key vault, never in a repository, binary, container image or checked-in configuration file. Why: anyone with read access to the repository, registry or package gets the credential, and history keeps it after deletion. Smell: a literal that looks like a credential such as `apiKey: "sk_live_..."`, `password=` in a committed `.env` or `config.json`, a private key block or connection string in a test fixture. Severity: exploitable. Source: https://cheatsheetseries.owasp.org/cheatsheets/Key_Management_Cheat_Sheet.html#storage
- **Never put a secret in a NEXT_PUBLIC_ variable or in a module a Client Component can import** (Next.js): "It will be inlined into any JavaScript sent to the browser." - only variables without the prefix stay on the server, so a secret given the prefix ships in the bundle, and a module that reads `process.env` should sit in the data access layer with `import 'server-only'` so a client import fails the build. Why: every visitor can read the client bundle, so the key is public the moment it is deployed. Smell: `NEXT_PUBLIC_STRIPE_SECRET_KEY`, `NEXT_PUBLIC_DATABASE_URL`, any `NEXT_PUBLIC_` value sent as a bearer token, or `process.env.API_SECRET` read in a file that lacks `import 'server-only'` and is imported from a `'use client'` component. Severity: exploitable. Source: https://nextjs.org/docs/app/guides/environment-variables#bundling-environment-variables-for-the-browser
- **Inject secrets at runtime from a secret store, never bake them into the build or container definition** (Secrets Management Cheat Sheet): "secrets themselves should never be hardcoded using docker ENV or docker ARG commands, as these can easily leak with the container definitions" - let the orchestrator or a secret manager supply the value when the process starts, prefer a fetch from the store over environment variables, give secrets an expiry and rotate them so a stolen one works only briefly. Why: build arguments, image layers and pipeline logs are copied and shared far more widely than production secrets should be. Smell: `ARG API_KEY` or `ENV DB_PASSWORD=...` in a Dockerfile, a secret passed as `--build-arg`, a static key with no rotation path, `console.log(process.env)` at start-up. Severity: exploitable. Source: https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html#51-injection-of-secrets-file-in-memory

## Logging and error handling

- **Log security events, but never credentials, keys or raw tokens** (ASVS V16.2.5): "it may not be allowed to log certain data, such as credentials or payment details. Other data, such as session tokens, may only be logged by being hashed or masked" - record authentication and authorisation outcomes with who, when and what, and apply the data's protection level to decide what is omitted, masked or hashed. Why: logs are copied to many systems with weaker access control, so a logged password or token is a second place to steal it from. Smell: `logger.info(req.headers)`, `console.log(req.body)` on a login route, `log.error(err, { user })` where `user` carries a password hash, `logger.debug("token=" + token)`. Severity: defence in depth. Source: https://github.com/OWASP/ASVS/blob/master/5.0/en/0x25-V16-Security-Logging-and-Error-Handling.md#v162-general-logging
- **Return a generic message on unexpected errors and keep the detail server side** (ASVS V16.5.1): "ensuring no exposure of sensitive internal system data such as stack traces, queries, secret keys, and tokens" - a last-resort handler logs the exception with its context and answers the client with a fixed message and status code. Why: stack traces, SQL text, file paths and library versions tell an attacker where and how to aim the next request. Smell: `res.status(500).json({ error: err.message, stack: err.stack })`, `catch (e) { return { error: String(e) } }`, a database driver's error object serialised straight into the response. Severity: exploitable. Source: https://github.com/OWASP/ASVS/blob/master/5.0/en/0x25-V16-Security-Logging-and-Error-Handling.md#v165-error-handling
- **Fail closed when a security check throws** (ASVS V16.5.3): "preventing fail-open conditions such as processing a transaction despite errors resulting from validation logic" - an exception inside authentication, authorisation, signature verification or validation must end the request as denied, not fall through to the success path. Why: an attacker who can trigger the exception, for example with a malformed token, skips the check entirely. Smell: `catch (e) { authorised = true }`, an empty `catch {}` around `verifyToken(...)` followed by the protected action, `let allowed = true` set before a `try`, a default return of `true` from a permission helper. Severity: exploitable. Source: https://github.com/OWASP/ASVS/blob/master/5.0/en/0x25-V16-Security-Logging-and-Error-Handling.md#v165-error-handling

## Sensitive data in transit, responses and storage

- **Keep secrets and personal data out of URLs and query strings** (ASVS V14.2.1): "the URL and query string do not contain sensitive information, such as an API key or session token" - send such values in the request body or a header field. Why: URLs land in browser history, proxy and server logs, Referer headers and analytics, so the value leaks to places that never see the body. Smell: `?token=`, `?api_key=`, `?password=`, `fetch("/api/reset?email=" + email)`, a GET route that reads credentials from `searchParams`. Severity: exploitable. Source: https://github.com/OWASP/ASVS/blob/master/5.0/en/0x23-V14-Data-Protection.md#v142-general-data-protection
- **Return only the fields the UI needs, never a raw record** (Next.js): "Server Action return values are serialized and sent to the client. Only return what the UI needs, not raw database records." - pick the public fields in the data access layer before returning from an action, an API handler or a Server Component prop, and treat the taint APIs as a backstop rather than the filter. Why: everything returned is readable in the network tab, so internal fields such as password hashes, roles, tokens and other users' data become public. Smell: `return user` or `return db.user.update(...)` from an action, `<Profile user={user} />` with the whole row, `res.json(rows)` after `select *`, a spread `{...record}` into props. Severity: exploitable. Source: https://nextjs.org/docs/app/guides/data-security#controlling-return-values
- **Mark sensitive responses no-store and keep sensitive data out of browser storage** (ASVS V14.3.2, V14.3.3): "data stored in browser storage (such as localStorage, sessionStorage, IndexedDB, or cookies) does not contain sensitive data, with the exception of session tokens" - send `Cache-Control: no-store` on responses that carry personal or account data, and hold nothing sensitive in web storage, which any script on the origin can read. Why: a cached page or stored value survives logout and is read by the next person at the shared machine or by injected script. Smell: `localStorage.setItem('accessToken', ...)`, `sessionStorage.setItem('user', JSON.stringify(user))`, an account endpoint with `Cache-Control: public, max-age=...` or `no-cache` used where `no-store` was meant. Severity: defence in depth. Source: https://github.com/OWASP/ASVS/blob/master/5.0/en/0x23-V14-Data-Protection.md#v143-client-side-data-protection
- **Use TLS with certificate validation for every connection, inbound and outbound** (ASVS V12.3.1): "an encrypted protocol such as TLS is used for all inbound and outbound connections to and from the application" - that includes databases, caches, queues, internal services and third-party APIs, with no fallback to plaintext and no option that skips verifying the server certificate. Why: cleartext or an unverified peer lets anyone on the path read or rewrite credentials and data in flight. Smell: `http://` in a service or webhook URL, `rejectUnauthorized: false`, `NODE_TLS_REJECT_UNAUTHORIZED=0`, `sslmode=disable`, `ssl: false` in a database client, `verify=False`. Severity: exploitable. Source: https://github.com/OWASP/ASVS/blob/master/5.0/en/0x21-V12-Secure-Communication.md#v123-general-service-to-service-communication-security
