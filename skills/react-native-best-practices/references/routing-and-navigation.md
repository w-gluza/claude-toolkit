# React Native code-review rules: routing and navigation

Extracted 2026-11-12 from the Expo SDK 58 documentation (expo/expo, MIT) and the React Native 0.88 documentation (facebook/react-native-website, CC BY 4.0). One rule per bullet, one source link each. Quotations are short excerpts; the rest is original.

## Project structure and entry point

- **Keep only routes and layouts in the app directory**: "If you put a non-route inside the src/app directory, Expo Router will attempt to treat it like a route." - move components, hooks, constants and utilities to sibling directories such as `src/components`. Why: every file under `src/app` gets a URL and becomes a navigation target. Smell: `src/app/components/button.tsx` or `src/app/utils.ts` added in a diff. Source: https://docs.expo.dev/router/basics/core-concepts/#6-non-navigation-components-live-outside-the-srcapp-directory
- **Give every route file a default export**: "Every file inside the src/app directory has a default export that defines a distinct page in your app" - export the screen component as the default from each route file. Why: the router maps the file to a page through that export; only `_layout` files are treated differently. Smell: a route file with only named exports, or a barrel file inside `src/app`. Source: https://docs.expo.dev/router/basics/core-concepts/#1-all-screenspages-are-files-inside-the-srcapp-directory
- **Let the first index file be the initial route**: "you do not define an initial route or first screen in code" - make the start screen an `index.tsx` that matches `/`, inside a route group if it must live deeper in the tree. Why: on launch the router looks for the first `index.tsx` that matches the `/` URL. Smell: a root layout that navigates to a home screen in an effect on mount, or no `index.tsx` anywhere that resolves to `/`. Source: https://docs.expo.dev/router/basics/core-concepts/#3-first-indextsx-is-the-initial-route
- **Put app initialisation in the root layout**: "This file is rendered before any other route in your app" - load fonts, mount providers and control the splash screen in `src/app/_layout.tsx`. Why: it replaces the old `App.tsx` and wraps every route, including deep-linked ones. Smell: a context provider mounted inside one screen or one tab while other routes read the same context. Source: https://docs.expo.dev/router/basics/core-concepts/#4-root-_layouttsx-replaces-appjsxtsx
- **Import the router entry last in a custom entry file**: "Remember to always import it last to ensure all configurations are properly set up before the app renders." - place polyfills, error reporting and `LogBox` set-up above the `expo-router/entry` import. Why: side effects imported after the entry run after the app has started rendering. Smell: `import 'expo-router/entry'` on the first line of `index.js` with initialisation code below it. Source: https://docs.expo.dev/router/installation/#custom-entry-point-to-initialize-and-load
- **Keep a single app directory**: "Only the src/app directory will be used if you have both." - delete the root `app` directory once routes move to `src/app`. Why: routes left in the root directory are silently ignored. Smell: a new screen added under `app/` in a project that already has `src/app/`. Source: https://docs.expo.dev/router/reference/src-directory/#notes
- **Avoid reserved URL paths**: "Metro intercepts the request and your content is never reached." - do not name routes or public folders `assets`, `_expo`, `_flight`, `inspector`, `expo-dev-plugins`, `manifest` or `public`. Why: Metro or the router answers those paths itself, so the screen never loads or is replaced by a dev server response. Smell: `src/app/assets.tsx`, `src/app/manifest.tsx` or `public/assets/logo.png`. Source: https://docs.expo.dev/router/reference/reserved-paths/#assets
- **Keep test files out of the app directory**: "All files inside your app directory must be either routes or layout files." - place tests in `__tests__` or another directory outside the routes tree. Why: a test file under the routes directory is treated as a route. Smell: `src/app/index.test.tsx` or `src/app/__tests__/`. Source: https://docs.expo.dev/router/reference/testing/#configuration
- **Pair every platform-specific route with a base file**: "are supported in the src/app directory only if a non-platform version also exists" - add `about.tsx` next to `about.web.tsx`, or keep platform files outside the routes tree and re-export them. Why: "This ensures that routes are universal across platforms for deep linking." Smell: `src/app/settings.ios.tsx` with no `src/app/settings.tsx`. Source: https://docs.expo.dev/router/advanced/platform-specific-modules/#within-srcapp-directory

## Route notation and shared routes

- **Use route groups to organise without changing the URL**: "These directories are useful for grouping routes together without affecting the URL." - wrap related screens in a `(name)` directory when they share a layout. Why: a plain directory adds a URL segment and changes every deep link below it. Smell: a `main/` directory created only to hold a layout, which moves every screen under `/main/`. Source: https://docs.expo.dev/router/basics/notation/#parentheses
- **Give the not-found route a way home**: "We recommend having a link to / so users can navigate back to the home screen." - render a `Link` to `/` in a custom `+not-found.tsx`. Why: a stale or mistyped deep link otherwise leaves the user on a dead end. Smell: a `+not-found.tsx` that renders only text. Source: https://docs.expo.dev/router/error-handling/#unmatched-routes
- **Do not use shared routes for per-role screens**: "Do not use shared routes to give different user roles a different version of a screen." - declare the screen once and gate it with a protected route. Why: "The URL does not carry the user's role, so a cold link cannot select the correct group". Smell: `(admin)/dashboard.tsx` and `(member)/dashboard.tsx` both resolving to `/dashboard`. Source: https://docs.expo.dev/router/advanced/shared-routes/
- **Name the group when a link must open one copy of a shared route**: "A cold link has no current group, so Expo Router renders the first alphabetical match." - write the href with the group segment, for example `/(search)/profile`. Why: the same URL can show one screen after in-app navigation and another after a reload or deep link. Smell: a push notification or share link to a shared route with no group in the path, where the tab matters. Source: https://docs.expo.dev/router/advanced/shared-routes/
- **Keep each dynamic route unique within JavaScript tabs**: "You cannot have two screens for the same dynamic route." - declare one `Tabs.Screen` per dynamic route and build a custom navigator if several are needed. Why: the navigator cannot tell the two tabs apart. Smell: two `Tabs.Screen` entries named `[user]` with different `href` options. Source: https://docs.expo.dev/router/advanced/tabs/#dynamic-routes

## Layouts and nesting

- **Match screen names to route names**: "Its name prop should match the route name so that Expo Router can map the route to its component automatically." - use the file name without its extension, with brackets and parentheses kept. Why: options given to a name that matches no route are never applied. Smell: `<Stack.Screen name={'details'} />` when the file is `[productId].tsx`, or a name that includes `.tsx`. Source: https://docs.expo.dev/router/basics/navigation-layouts/#stacks
- **Nest navigators only when the UI needs it**: "While it is possible to nest navigators, be sure to only do so when it is truly needed." - add a `_layout.tsx` to a subdirectory only when it needs its own stack or tabs. Why: an extra layout that returns `Stack` creates a second stack, with its own header, inside the first. Smell: a nested `_layout.tsx` returning a bare `<Stack />` followed by `headerShown: false` on the parent to hide a doubled header. Source: https://docs.expo.dev/router/basics/navigation-layouts/#stacks
- **Declare every screen that should appear in tabs or a drawer**: "JavaScript tabs, top tabs, drawer, headless tabs, and native tabs now show only screens declared in the layout." - add a `Tabs.Screen`, `Drawer.Screen` or trigger for each visible route. Why: before SDK 58 undeclared files appeared in the tab bar automatically; now they do not. Smell: a new file added to `(tabs)/` with no matching entry in its `_layout.tsx`. Source: https://docs.expo.dev/router/migrate/sdk-57-to-58/#declare-tabs-and-drawer-screens
- **Push shared detail screens from a stack above the tabs**: "keep the detail route out of the tabs and push it from an outer stack instead" - place the detail route beside `(tabs)` and register both in the root stack. Why: a link to a URL owned by another tab switches tabs, and going back then stays in that tab instead of returning to the origin. Smell: `(tabs)/feed/[postId].tsx` linked from several tabs, with a bug report about the back button landing on the wrong tab. Source: https://docs.expo.dev/router/basics/common-navigation-patterns/#going-back-to-the-tab-you-came-from
- **Navigate to nested screens with a complete href**: "In SDK 58, they are ordinary user parameters. Navigate to a complete href instead" - replace the React Navigation `screen`, `params` and `initial` form with the full path. Why: those keys no longer build nested state and arrive as plain parameters. Smell: `router.push({ pathname: '/settings', params: { screen: 'media' } })`. Source: https://docs.expo.dev/router/migrate/sdk-57-to-58/#navigate-with-complete-hrefs
- **Call useNavigation only inside a navigator**: "useNavigation now throws when it is called outside a navigator." - move the hook into a route or layout rendered within the navigation tree. Why: providers and wrappers above the navigator have no navigation object. Smell: `useNavigation()` in a provider that wraps the root `Stack`. Source: https://docs.expo.dev/router/migrate/sdk-57-to-58/#move-usenavigation-inside-a-navigator
- **Replace the removed redirect and initialParams screen props**: "Layout Screen components no longer accept redirect or initialParams." - render `Redirect` from the route file, use a protected route for access control, and default params where the screen reads them. Why: the props were removed in SDK 58. Smell: a `redirect` prop on `Stack.Screen` or `initialParams={{ tab: 'all' }}` in a layout. Source: https://docs.expo.dev/router/migrate/sdk-57-to-58/#replace-redirect-and-initialparams
- **Read the URL instead of navigation state**: "Navigation state is an implementation detail." - use `usePathname`, `useSegments` and `useGlobalSearchParams` for route information. Why: the state shape changed in SDK 58, with `preloadedRoutes` removed and `type` and `history` made optional. Smell: `useRootNavigationState().routes[0].state?.index` used to work out the current screen. Source: https://docs.expo.dev/router/migrate/sdk-57-to-58/#read-navigation-state

## Navigating between screens

- **Prefer useRouter inside components**: "Prefer the router returned by useRouter() over useNavigation().navigate() or the module-level router for href-based navigation from a component." - call the hook and navigate through its result. Why: the module-level object "throws before the first router render and cannot distinguish between multiple router roots". Smell: `import { router } from 'expo-router'` used inside a component body, or `navigation.navigate('Profile')` with a screen name. Source: https://docs.expo.dev/router/migrate/sdk-57-to-58/#prefer-userouter-in-components
- **Default to navigate and reserve push for deliberate duplicates**: "This will either push a new page onto the stack or unwind to an existing route on the stack." - use `router.navigate` unless a second copy of the route is wanted. Why: `push` always adds an entry, which can stack the same screen repeatedly. Smell: `router.push('/home')` from a deep screen where the user expects to return to the existing home. Source: https://docs.expo.dev/router/basics/navigation/#native-navigation-basics-with-userouter
- **Use replace when the current screen must not stay in history**: "Removes the current route from the history and replace it with the specified URL." - pass `replace` on `Link` or call `router.replace` after sign-in, onboarding or a redirect. Why: with a push, the back gesture returns to the screen that was meant to be gone. Smell: `router.push('/home')` at the end of a sign-in handler. Source: https://docs.expo.dev/versions/v58.0.0/sdk/router/link/#replace
- **Wrap non-text link children with asChild**: "This means non-text children (such as View) may have unexpected layout behavior." - pass `asChild` and a single `Pressable` child when the link holds views or images. Why: by default the children are rendered inside a `Text` element. Smell: a `Link` whose direct child is a `View`, with layout that collapses. Source: https://docs.expo.dev/router/basics/navigation/#links-and-buttons
- **Pass dynamic segments through an href object**: "For dynamic routes, Href's need to be objects and their parameters are strictly typed" - write `{ pathname: '/user/[id]', params: { id } }` instead of building the path by hand. Why: typed routes then check both the route and its parameters at compile time. Smell: a template string href such as `/user/${id}` cast to `Href` or `any` to silence the compiler. Source: https://docs.expo.dev/router/reference/typed-routes/#statically-typed-routes
- **Redirect with the Redirect component**: "A redirect will navigate to the new route without rendering the current page." - return a `Redirect` element from the page or layout when it should never show. Why: navigating from an effect renders the unwanted screen for a frame first. Smell: `useEffect(() => router.replace('/login'), [])` followed by the normal screen JSX. Source: https://docs.expo.dev/router/basics/navigation/#redirects
- **Guard navigation calls in screens that can be prefetched**: "It cannot use the imperative router API." - check `navigation.isFocused()` before calling `setOptions` or dispatching, and attach listeners in an effect that depends on `navigation`. Why: a screen preloaded in a stack also cannot update options or receive navigator events until it is visited. Smell: `router.replace` or `navigation.setOptions` called on mount in a screen that is the target of a `Link` with `prefetch`. Source: https://docs.expo.dev/router/basics/navigation/#prefetching
- **Choose dismiss or back deliberately in nested navigators**: "Dismiss is different from back as it targets the closest stack and not the current navigator." - use `router.back` to leave one screen and `router.dismiss` to close the nearest stack entry. Why: "If you have nested navigators, calling dismiss will take you back multiple screens." Smell: a close button inside tabs nested in a modal stack that calls `dismiss` and closes more than intended. Source: https://docs.expo.dev/router/advanced/stack/#dismiss-action
- **Add withAnchor when linking into another stack**: "By default, the anchor is only considered when deep linking and not during navigation within your app." - pass `withAnchor` on the `Link`, or the same option to the imperative call, when the stack's first screen should sit below the destination. Why: otherwise the destination becomes the only screen in that stack and back skips the stack's index. Smell: a link from one tab to `/feed/123` in another tab with no way back to the feed list. Source: https://docs.expo.dev/router/basics/navigation/#anchor-routes
- **Write external links as fully qualified URLs**: "Using a complete URL ensures that the link is interpreted as a web URL and opened in the user's browser by default." - include the `https` scheme in hrefs that leave the app. Why: a bare path or host is evaluated as an in-app route. Smell: a `Link` to `example.com/help`, or to `/terms` when a website page is meant. Source: https://docs.expo.dev/router/advanced/native-intent/#forcing-web-links
- **Update params in place with setParams**: "Updating a URL parameter will not push anything new to the history stack." - call `router.setParams` for filters, search text and other state held in the URL. Why: pushing the same route with new params adds a history entry for every keystroke. Smell: `router.push` with only the query changed, inside an `onChangeText` handler. Source: https://docs.expo.dev/router/reference/url-parameters/#updating-url-parameters
- **Replace beforeRemove listeners**: "The beforeRemove and __unsafe_action__ events are removed." - block removal with `usePreventRemove` and observe with the `removed` and `removePrevented` events. Why: listeners on the removed events never fire in SDK 58. Smell: `navigation.addListener('beforeRemove', e => e.preventDefault())`. Source: https://docs.expo.dev/router/migrate/sdk-57-to-58/#replace-beforeremove-and-__unsafe_action__
- **Clear the prevention flag before repeating a blocked action**: "Set the value passed to usePreventRemove() to false before calling repeat()." - set the unsaved-changes state to false, then call `repeat` in the confirm handler. Why: "This keeps your state synchronized with removal prevention." Smell: a discard handler that calls `repeat()` or `router.back()` while the boolean is still true. Source: https://docs.expo.dev/router/advanced/prevent-screen-removal/

## URL parameters

- **Read params with useLocalSearchParams in screens**: "opt-towards using useLocalSearchParams because it will only update when the route is focused" - use the local hook for data fetching and rendering in a route. Why: the previous screen keeps its own params, so its data is still there when the user goes back. Smell: `useGlobalSearchParams` in a stack screen that fetches by id. Source: https://docs.expo.dev/versions/v58.0.0/sdk/router/#useglobalsearchparams
- **Limit useGlobalSearchParams to background work**: "It updates on every URL param change and might cause components to update extraneously in the background." - keep the global hook for analytics and similar code that must follow the active URL. Why: it made background screens re-render in the documented example, and "It can cause performance issues if overused." Smell: the global hook in a list screen that stays mounted under detail screens. Source: https://docs.expo.dev/router/reference/url-parameters/#local-versus-global-url-parameters
- **Avoid the reserved parameter names**: "Avoid using the following names for your own parameters to prevent conflicts" - do not name route or search params `screen`, `params`, `initial` or `state`. Why: the names are reserved for internal use by the router and React Navigation. Smell: `params: { state: 'open' }` or a `[screen].tsx` route. Source: https://docs.expo.dev/router/reference/url-parameters/#reserved-parameters
- **Treat catch-all params as arrays**: "When used with the rest syntax (...), route parameters are returned as a string array" - type and handle a `[...rest]` param as `string[]`. Why: string methods on the value fail or give wrong output at runtime. Smell: `const { rest } = useLocalSearchParams(); rest.split('/')`. Source: https://docs.expo.dev/router/reference/url-parameters/#statically-typed-url-parameters
- **Expect a remount when a route param changes**: "Whenever a route parameter is changed, the component will re-mount." - keep state that must survive an id change in the URL or outside the screen. Why: local state and refs reset on the remount. Smell: `router.setParams({ user: next })` on a `[user]` route with form state held in `useState`. Source: https://docs.expo.dev/router/reference/url-parameters/#route-parameters-versus-search-parameters
- **Type query parameters by hand**: "Most query parameters will not be represented in the file system and therefore cannot be typed automatically." - pass a generic to `useLocalSearchParams` for search params. Why: typed routes only know the segments that come from file names. Smell: a search param read from the hook and used as a specific union with no generic and no runtime check. Source: https://docs.expo.dev/router/reference/typed-routes/#query-parameters

## Stack, headers and router settings

- **Set the back destination with unstable_settings.anchor**: "The initialRouteName navigator prop is removed." - export `unstable_settings = { anchor: 'index' }` from the stack's own layout file. Why: `initialRouteName` in the settings object is also deprecated in favour of `anchor`. Smell: an `initialRouteName` prop on `Stack` or `unstable_settings = { initialRouteName: 'index' }`. Source: https://docs.expo.dev/router/migrate/sdk-57-to-58/#move-initialroutename-to-unstable_settings
- **Do not use anchor to pick the launch screen**: "Do not use anchor to choose the app's initial screen." - make the launch screen the `index.tsx` route for `/`. Why: "The launch URL determines that screen." Smell: `anchor: 'home'` added in the root layout so the app opens on `home`. Source: https://docs.expo.dev/router/migrate/sdk-57-to-58/#move-initialroutename-to-unstable_settings
- **Point anchor at a real route file**: "The anchor sets the default screen of the stack and should match a valid filename (without the extension)." - use the route name exactly as it appears on disk. Why: an anchor that matches no file gives deep-linked screens nothing to go back to. Smell: `anchor: 'index.tsx'` or an anchor left behind after the file was renamed. Source: https://docs.expo.dev/router/advanced/router-settings/#anchor
- **Let scroll views inset under the iOS 26 header**: "The header is transparent with Liquid Glass, and screen content goes under the header." - add automatic `contentInsetAdjustmentBehavior` to the screen's root `ScrollView`, `FlatList` or `SectionList`, or set `headerTransparent: false` on screens with no scroll view. Why: in SDK 58 this is the default for `Stack` on iOS 26 and later. Smell: content hidden behind the header on iOS 26 after an SDK 58 upgrade. Source: https://docs.expo.dev/router/migrate/sdk-57-to-58/#review-the-ios-header-appearance
- **Do not use SafeAreaView to clear the stack header**: "Do not use SafeAreaView from react-native-safe-area-context to move content below the header." - rely on scroll view insets or an opaque header. Why: "It applies only the status bar inset." With an opaque header it adds a second top inset. Smell: a stack screen whose root is `SafeAreaView` with the top edge applied. Source: https://docs.expo.dev/router/migrate/sdk-57-to-58/#review-the-ios-header-appearance
- **Make the scroll view the first child for large titles**: "This happens when the scrollable view is not the direct first child of the screen component." - render `ScrollView` or `FlatList` first, or set `collapsable={false}` on a necessary wrapper. Why: the native header finds the scroll view through the first child chain, and otherwise the large title does not collapse. Smell: a large-title screen whose root is a plain `View` wrapping the list. Source: https://docs.expo.dev/router/advanced/stack/#large-title-does-not-collapse-when-scrolling
- **Remove freezeOnBlur**: "The freezeOnBlur option has no effect in SDK 58." - delete the option, and use `activityEnabled` (experimental) if inactive screens must release resources. Why: the option is silently ignored. Smell: `freezeOnBlur: true` in `screenOptions`. Source: https://docs.expo.dev/router/migrate/sdk-57-to-58/#replace-freezeonblur
- **Flag the alpha composition API for screen options**: "Screen composition API is in alpha and available in SDK 55 and later." - prefer the options-based API in code that must stay stable, and isolate composition components where they are used. Why: alpha APIs can change between releases. Smell: `Stack.Title` and similar composition components spread across many screens with no note on their status. Source: https://docs.expo.dev/router/advanced/stack/#set-screen-options-dynamically
- **Match the navigation theme to the app's colour scheme**: "A white flash between screen transitions usually means the navigation stack is using a light background while your app uses a dark theme." - wrap the root layout in the router's `ThemeProvider` with the matching theme. Why: the default theme uses a white background behind screens during transitions. Smell: a dark-themed app whose root layout renders `Stack` with no theme provider. Source: https://docs.expo.dev/router/advanced/stack/#white-background-flashes-when-navigating-between-screens

## Tabs and drawer

- **Import native tabs from the stable entry point**: "In SDK 54 through 57, use expo-router/unstable-native-tabs instead." - on SDK 58 import `NativeTabs` from `expo-router/native-tabs`. Why: the unstable path belongs to earlier SDKs. Smell: `from 'expo-router/unstable-native-tabs'` in a project on SDK 58. Source: https://docs.expo.dev/router/advanced/native-tabs/
- **Add a trigger for every native tab**: "You need to explicitly add them in your layout file using the NativeTabs.Trigger." - declare one `NativeTabs.Trigger` per tab route. Why: unlike a stack, native tabs do not add routes to the bar automatically. Smell: a new tab file with no trigger, and a report that the tab is missing. Source: https://docs.expo.dev/router/advanced/native-tabs/#get-started
- **Keep native tabs to five on Android**: "On Android, there is a limitation of having a maximum of 5 tabs in the tab bar." - cap the trigger count or move extra destinations elsewhere. Why: the limit comes from the platform's Material component. Smell: a sixth `NativeTabs.Trigger` added in a diff. Source: https://docs.expo.dev/router/advanced/native-tabs/#a-limit-of-5-tabs-on-android
- **Do not nest native tabs inside native tabs**: "Native tabs cannot be nested inside other native tabs." - use JavaScript tabs for the inner level. Why: the native tab bar does not support the arrangement. Smell: a `NativeTabs` layout inside a route that is itself a native tab. Source: https://docs.expo.dev/router/advanced/native-tabs/#no-support-for-nested-native-tabs
- **Define native tabs statically**: "Dynamically adding or removing tabs at runtime is not supported." - keep the trigger list constant for the life of the navigator. Why: "If you dynamically add or remove tabs, the content will be remounted and the state will be lost." Smell: a trigger rendered behind a condition such as `isPremium`, driven by state that changes while the tabs are visible. Source: https://docs.expo.dev/router/advanced/native-tabs/#no-support-for-dynamically-adding-or-removing
- **Do not treat a disabled tab as access control**: "disabled only suppresses the native tap interaction." - protect the route with a guard as well when users must not reach it. Why: `router.push` and `Link` still navigate to a disabled tab. Smell: `disabled={!isPaid}` on a trigger as the only gate for a paid screen. Source: https://docs.expo.dev/router/advanced/native-tabs/#disabled-tabs
- **Remember that hidden native tabs are unreachable**: "Marking a tab as hidden means it cannot be navigated to in any way." - do not link to a route whose trigger is hidden; move it outside the tabs if it must stay reachable. Why: navigation to a hidden tab fails. Smell: `hidden` on a trigger together with a `Link` to the same route elsewhere. Source: https://docs.expo.dev/router/advanced/native-tabs/#hiding-a-tab-conditionally
- **Nest a stack in each native tab that needs a header**: "you should nest a native <Stack /> layout inside the native tabs to support both headers and pushing screens" - give the tab a directory with its own `_layout.tsx` returning `Stack`. Why: JavaScript tabs have a mock stack header that native tabs do not provide. Smell: header options set on a native tab trigger, or a tab screen with no header after migrating from JavaScript tabs. Source: https://docs.expo.dev/router/advanced/native-tabs/#use-stacks-inside-tabs
- **Defer expensive work in native tab screens**: "All tab screens in native tabs render eagerly when the navigator mounts." - gate heavy content with `useIsFocused`, or load it on first focus with `useFocusEffect`. Why: the behaviour cannot be changed, so every tab's mount cost is paid at start-up. Smell: data fetching or a large list rendered at the top level of every tab screen. Source: https://docs.expo.dev/router/advanced/native-tabs/#lazy-loading
- **Provide a web layout when using native tabs**: "On web, native tabs fall back to a basic implementation, loosely based on iPad design." - supply `_layout.web.tsx` or a platform-specific tab component built with `expo-router/ui`. Why: the web has no system tab bar. Smell: a universal app that ships `NativeTabs` with no web alternative. Source: https://docs.expo.dev/router/advanced/native-tabs/#custom-web-layout

## Modals and sheets

- **Anchor stacks that present modals**: "Without anchoring, the screen behind the modal will be wiped away, leaving no navigation context." - export `unstable_settings` with an `anchor` from the layout of the stack that owns the modal. Why: a deep link straight to the modal otherwise opens it with nothing underneath. Smell: a `presentation: 'modal'` screen in a stack whose layout has no anchor. Source: https://docs.expo.dev/router/advanced/modals/#handle-deep-linked-modals
- **Provide a dismiss control for modal routes on web**: "On web, the modal is presented as a separate route, and the dismiss behavior has to be provided manually" - render a close link when `router.canGoBack()` is true. Why: the web has no swipe-down gesture or hardware back button to close the modal. Smell: a `modal.tsx` with no visible close control. Source: https://docs.expo.dev/router/advanced/modals/#modal-presentation-and-dismiss-behavior
- **Limit form sheet detents to three for Android**: "Android supports a maximum of 3 detents." - give `sheetAllowedDetents` at most three values, sorted in ascending order. Why: iOS accepts any number, so a longer list behaves differently per platform. Smell: `sheetAllowedDetents: [0.2, 0.4, 0.6, 1]`. Source: https://docs.expo.dev/router/advanced/modals/#configuring-sheet-detents
- **Render titles and actions inside Android form sheets**: "Native stack headers and nested stack navigators are not supported inside form sheet screens" - draw the title and buttons as part of the sheet content. Why: `headerShown`, `title` and header buttons do not render inside the sheet on Android. Smell: a `formSheet` screen that depends on `headerRight` for its save action. Source: https://docs.expo.dev/router/advanced/modals/#android-limitations
- **Replace the removed web modal implementation**: "The experimental web modal implementation is removed." - build modal overlays on web with a custom navigator. Why: SDK 58 no longer ships the experimental implementation. Smell: web modal options carried over from SDK 57 that now have no effect. Source: https://docs.expo.dev/router/migrate/sdk-57-to-58/#replace-web-modals

## Authentication and protected routes

- **Gate private screens with protected routes**: "Another benefit of protected routes is that they are checked even if you deep link into a page directly." - wrap private screens in `Stack.Protected` with a `guard` in the layout. Why: a check that runs only on an entry screen is bypassed by a deep link. Smell: an auth check in `index.tsx` alone, or a per-screen effect that redirects after the private screen has rendered. Source: https://docs.expo.dev/router/basics/common-navigation-patterns/#authenticated-users-only-protected-routes
- **Enforce access on the server as well**: "Protected screens are not a replacement for server-side authentication or access control." - authorise every request for protected data on the back end. Why: "Protected screens are evaluated on the client side only." Smell: an admin screen behind a guard that calls an API with no authorisation check. Source: https://docs.expo.dev/router/advanced/protected/#static-rendering-considerations
- **Declare each screen in one protected group only**: "If a screen's availability depends on logic, wrap it in a conditional group instead of duplicating the screen." - list a screen once and express its conditions through the guard, nesting groups for layered rules. Why: a screen can only exist in one active route group at a time. Smell: the same `Stack.Screen` name inside two `Stack.Protected` blocks. Source: https://docs.expo.dev/router/advanced/protected/#multiple-protected-screens
- **Expect history to clear when a guard turns false**: "all of its history entries will be removed from the navigation history" - design sign-out and permission changes around an automatic redirect to the anchor or first available screen. Why: the user is moved without any navigation call. Smell: a sign-out handler that calls `router.replace('/sign-in')` and also flips the guard, causing a double navigation. Source: https://docs.expo.dev/router/advanced/protected/#overview
- **Hold the splash screen until the session has loaded**: "Authentication loading is asynchronous, so keep the splash screen visible until authentication loads." - render a controller inside the session provider that hides the splash screen once loading ends. Why: evaluating the guard before the session is known shows the sign-in screen to signed-in users for a moment. Smell: a guard that reads `!!session` with no loading state handled. Source: https://docs.expo.dev/router/advanced/authentication/#using-protected-routes
- **Keep the sign-in screen outside the protected group**: "Since this screen is outside the (app) group, the group's layout and authentication check do not run when rendering this screen." - place `sign-in.tsx` beside the `(app)` group, not inside it. Why: a sign-in route inside the protected group cannot be reached by signed-out users. Smell: `(app)/sign-in.tsx` with a redirect loop. Source: https://docs.expo.dev/router/advanced/authentication/#using-protected-routes
- **Store session tokens in secure storage on native**: "persists tokens securely on native with expo-secure-store and in local storage on web" - follow the documented hook and keep tokens out of unencrypted storage on devices. Why: the session provider that drives the guards reads this value on launch. Smell: an auth token written to `AsyncStorage`. Source: https://docs.expo.dev/router/advanced/authentication/#using-protected-routes
- **Preserve screen names in withLayoutContext processing**: "It must preserve every screen name exactly once because guards are associated with the original screen names." - make a `processScreens` function return each screen it received, once, with its name unchanged. Why: a renamed or dropped screen loses its guard. Smell: a `processScreens` callback that filters or renames screens. Source: https://docs.expo.dev/versions/v58.0.0/sdk/router/#withlayoutcontextnav-processscreens

## Deep linking and native intent

- **Define a custom scheme in the app config**: "On mobile, you define a scheme in your app config file, and this becomes the prefix for deep links into your app." - set `scheme` and create a new development build afterwards. Why: without it the app falls back to the Android package and iOS bundle identifier as schemes. Smell: links such as `myapp://profile` in code or tests with no `scheme` in the app config. Source: https://docs.expo.dev/router/basics/navigation/#deep-links
- **Assume every route can be opened from outside the app**: "deep linking is automatically enabled for all of your app's screens" - protect sensitive screens with guards and validate params on each screen that reads them. Why: no opt-in is needed for a URL to reach a route. Smell: a confirmation or internal step screen that trusts params because it is only pushed from one place. Source: https://docs.expo.dev/linking/overview/#use-expo-router-to-handle-deep-linking
- **Do not hand-roll URL handling beside the router**: "If you are using Expo Router, you can ignore this section." - remove manual `Linking.getInitialURL` and `url` listeners that route users, and express rewrites in `+native-intent`. Why: the router already resolves incoming links, so a second handler navigates twice. Smell: `Linking.addEventListener('url', ...)` followed by `router.push` in the root layout. Source: https://docs.expo.dev/linking/into-your-app/#handle-urls
- **Prefer verified web links for links shared outside the app**: "For most apps, you probably want to set up Android App/iOS Universal Links instead of the deep links described in this guide or set up both." - use `https` links backed by App Links and Universal Links. Why: a custom-scheme link does nothing when the app is not installed. Smell: marketing or email links built with the custom scheme only. Source: https://docs.expo.dev/linking/into-your-app/
- **Place +native-intent at the top of the app directory**: "create a special file called +native-intent.tsx at the top level of your project's src/app directory" - keep the file at `src/app/+native-intent.tsx` and export `redirectSystemPath`. Why: the router looks for it only at that level. Smell: `+native-intent.tsx` inside a group or subdirectory. Source: https://docs.expo.dev/router/advanced/native-intent/#rewrite-incoming-native-deep-links
- **Never let redirectSystemPath throw**: "Note that throwing errors within this method may result in app crashes." - wrap the body in `try/catch`, add `.catch()` to promises, and return a fallback route on failure. Why: the function runs for every incoming native link, so one bad URL can crash the app at launch. Smell: `new URL(path)` or an awaited SDK call with no error handling in `+native-intent.tsx`. Source: https://docs.expo.dev/versions/v58.0.0/sdk/router/#nativeintent
- **Parse the incoming path defensively**: "there is no guarantee that this is a path or a valid URL" - parse with a base URL and return the original path when the input is not recognised. Why: apps can be launched with arbitrary strings from third-party services. Smell: `path.split('/')[2]` or `path.startsWith(...)` used as the only validation before returning a route. Source: https://docs.expo.dev/router/advanced/native-intent/#rewrite-incoming-native-deep-links
- **Keep auth decisions out of +native-intent**: "This means you won't have access to additional logic, such as user authentication status or the current route's state." - rewrite the URL there and leave access decisions to protected routes or layouts. Why: the file "is processed outside the context of your app". Smell: a session or store read inside `redirectSystemPath` to choose between private and public routes. Source: https://docs.expo.dev/router/advanced/native-intent/#using-redirectsystempath
- **Avoid legacy_subscribe in new code**: "Using this API is not recommended for new projects or integrations." - use `redirectSystemPath`; treat `legacy_subscribe` as an alpha bridge for providers that only support React Navigation. Why: it is incompatible with server-side routing and static rendering. Smell: a new `legacy_subscribe` export. Source: https://docs.expo.dev/router/advanced/native-intent/#legacy_subscribe
- **Set autoVerify on Android App Link filters**: "Specifying autoVerify is required for Android App Links to work correctly." - add `autoVerify: true` to each `android.intentFilters` entry for your domain. Why: without verification Android shows a chooser dialog instead of opening the app. Smell: an `intentFilters` entry with an `https` data scheme and no `autoVerify`. Source: https://docs.expo.dev/linking/android-app-links/#add-intentfilters-to-the-app-config
- **Omit the protocol from iOS associated domains**: "This is a common mistake that will result in the universal links not working." - write entries as `applinks:` followed by the bare domain. Why: Apple's format takes a host name, not a URL. Smell: `applinks:https://example.com` in `ios.associatedDomains`. Source: https://docs.expo.dev/linking/ios-universal-links/#native-app-configuration
- **Check and catch when opening non-web URLs**: "If you're passing in a non-http(s) URL, it's best to check canOpenURL() first." - call `canOpenURL` first and handle rejection of the `openURL` promise. Why: the promise rejects when no installed application is registered for the URL. Smell: an un-awaited `Linking.openURL('tel:...')` with no catch. Source: https://reactnative.dev/docs/linking#openurl

## Redirects and rewrites

- **Remember that config redirects also run in the app**: "It applies them to the initial URL, to incoming deep links, and to every navigation call" - review `redirects` and `rewrites` in the plugin options as rules that affect Android and iOS navigation too. Why: a rule written for the web server changes where `router.push` and `Link` land on native. Smell: a redirect added for SEO whose source matches a route still used in the app. Source: https://docs.expo.dev/router/reference/redirects/#server-rules-in-the-app
- **Expect rewrites to behave as redirects in the app**: "The app treats a rewrite rule as a redirect rule." - do not depend on the URL staying unchanged on native. Why: there is no HTTP response in the app, so `permanent` and `methods` are ignored as well. Smell: logic that reads `usePathname()` and expects the rewrite source after navigation. Source: https://docs.expo.dev/router/reference/redirects/#server-rules-in-the-app
- **Remove the deprecated server flags from the plugin options**: "In SDK 58, they have no effect and emit a deprecation warning whenever present, including when set to false" - delete `unstable_useServerRendering`, `unstable_useServerDataLoaders` and `unstable_useServerMiddleware` (web only). Why: setting them to false no longer disables the features. Smell: any of the three keys in the `expo-router` plugin configuration. Source: https://docs.expo.dev/router/migrate/sdk-57-to-58/#remove-deprecated-server-flags

## Errors, splash screen and fonts

- **Export an ErrorBoundary from routes that can fail**: "When ErrorBoundary is not present, the error will be thrown to the nearest parent's ErrorBoundary" - export a named `ErrorBoundary` that shows the `error` and offers `retry`. Why: with no boundary on the route, the failure replaces a larger part of the UI. Smell: a data-heavy route with no `ErrorBoundary` export and none in its layouts. Source: https://docs.expo.dev/router/error-handling/#error-handling
- **Keep navigator chrome mounted with a screen error boundary**: "A screen error boundary keeps navigator UI, such as headers and tab bars, mounted when a screen throws." - set `screenErrorBoundary` on the navigator or in `unstable_settings`. Why: users can still go back or switch tabs after a screen crashes. Smell: one screen's render error blanking the whole tab layout. Source: https://docs.expo.dev/router/error-handling/#error-boundaries-for-screens-in-a-layout
- **Do not depend on SuspenseFallback where async routes are on**: "Async routes do not support custom Suspense fallbacks." - set `asyncRoutes: { web: false }` if the web build needs a custom fallback. Why: in SDK 58 async routes are on by default on web and use the default loading fallback. Smell: a `SuspenseFallback` export that never shows on web. Source: https://docs.expo.dev/router/error-handling/#limitations
- **Call preventAutoHideAsync at module scope**: "It is recommended to call this in global scope without awaiting, rather than inside React components or hooks" - place the call above the root layout component. Why: inside a component it may run too late, after the splash screen is already hidden. Smell: `SplashScreen.preventAutoHideAsync()` inside `useEffect` or the layout body. Source: https://docs.expo.dev/versions/v58.0.0/sdk/splash-screen/#splashscreenpreventautohideasync
- **Hide the splash screen only when content is ready**: "Be careful to ensure that your app has content ready to display when you hide the splash screen, or you may see a blank screen briefly." - call `SplashScreen.hide()` in an effect keyed on the ready flag and return `null` from the root layout until then. Why: hiding earlier exposes an empty frame. Smell: `SplashScreen.hide()` called straight after starting an async load. Source: https://docs.expo.dev/versions/v58.0.0/sdk/splash-screen/#splashscreenhide
- **Hide the splash screen on every code path**: "The goal should be to hide the splash screen as soon as possible." - set the ready flag in a `finally` block, as the documented root layout does. Why: a rejected load that never sets the flag leaves the app stuck on the splash screen. Smell: `setIsReady(true)` only on the success path of an awaited call. Source: https://docs.expo.dev/versions/v58.0.0/sdk/splash-screen/#delay-hiding-the-splash-screen
- **Embed fonts at build time where possible**: "Use useFonts only if you can't use the config plugin." - configure fonts through the `expo-font` config plugin and drop the runtime gate from the root layout. Why: embedding at build time is more efficient than loading at runtime. Smell: a root layout that blocks on `useFonts` for fonts bundled with the app. Source: https://docs.expo.dev/versions/v58.0.0/sdk/font/#usage

## Focus, async routes and experimental features

- **Tie screen-scoped work to focus**: "Even when a page isn't visible, if it is still pushed onto the stack, it is still being rendered." - start subscriptions, timers and polling in `useFocusEffect` and stop them in its cleanup. Why: a plain effect keeps running on screens that sit below the current one. Smell: `setInterval` or a socket subscription in `useEffect` on a screen that pushes further screens. Source: https://docs.expo.dev/router/basics/navigation-layouts/#stacks
- **Memoise the useFocusEffect callback**: "The passed callback should be wrapped in React.useCallback to avoid running the effect too often." - wrap the callback in `useCallback` with its dependencies. Why: an inline function is new on every render and re-runs the effect each time. Smell: `useFocusEffect(() => { ... })` with an inline arrow function. Source: https://docs.expo.dev/versions/v58.0.0/sdk/router/#usefocuseffecteffect-do_not_pass_a_second_prop
- **Prefer useFocusEffect to focus listeners**: "Use useNavigation().addListener only when you cannot express the work as an effect tied to screen focus." - reserve `focus` and `blur` listeners for cases an effect cannot cover, and remove both in cleanup. Why: the effect form handles cleanup on blur, dependency change and unmount. Smell: `navigation.addListener('focus', ...)` with no unsubscribe. Source: https://docs.expo.dev/router/reference/focus-handling/#listen-for-focus-and-blur-events
- **Treat native async routes as experimental**: "On native platforms, async routes remain experimental, require explicit opt-in, and are supported only in development." - do not build native loading UX around route-level suspense. Why: production native builds load routes synchronously. Smell: `asyncRoutes` enabled for `ios` or `android` alongside loading states that only make sense with lazy routes. Source: https://docs.expo.dev/router/web/async-routes/
- **Know what activityEnabled leaves running (experimental)**: "The layout component of the nested navigator does not hide, so its effects continue to run." - keep long-lived work out of layouts when using React Activity support, and set `activityEnabled={false}` on screens that must stay active. Why: hidden screens clean up their effects, but layouts do not hide. Smell: polling started in a nested `_layout.tsx` on the assumption that it pauses with its tab. Source: https://docs.expo.dev/router/advanced/react-activity/#nested-navigators
- **Treat typed routes as beta**: "This feature is currently in beta and is not enabled by default." - enable `experiments.typedRoutes` knowingly and keep the generated `expo-env.d.ts` out of version control. Why: the generated file "should not be removed or changed at any time". Smell: `expo-env.d.ts` committed or edited by hand, or the `.expo` types entry removed from `tsconfig.json`. Source: https://docs.expo.dev/router/reference/typed-routes/
- **Keep link previews on push navigation**: "Previews can only be used with the default push navigation mode." - do not combine `Link.Preview` with `replace`; the feature is iOS-only. Why: preview with replace mode is not supported. Smell: `<Link replace>` containing `Link.Preview`. Source: https://docs.expo.dev/router/reference/link-preview/#replace-not-supported

## Testing router code

- **Await renderRouter and the test router helpers**: "renderRouter now returns a promise." - add `await` before `renderRouter` and before `navigate`, `push`, `replace`, `back`, `setParams` and `dismissAll` on `testRouter`. Why: updates must finish before assertions run. Smell: `renderRouter(...)` followed directly by `expect(screen).toHavePathname(...)` with no await. Source: https://docs.expo.dev/router/migrate/sdk-57-to-58/#update-router-tests
- **Upgrade the testing library with SDK 58**: "expo-router/testing-library requires @testing-library/react-native version 14 or newer." - raise the dependency when upgrading the SDK. Source: https://docs.expo.dev/router/reference/testing/#configuration
- **Write mock file-system keys without prefixes or extensions**: "Do not use leading relative (./) or absolute (/) notation when defining these paths and exclude file extension." - use keys such as `index` and `(tabs)/_layout`. ## Android back button

- **Remove BackHandler subscriptions**: "returns an EventSubscription object which should be cleared using the EventSubscription.remove method" - keep the subscription and call `remove()` in the effect cleanup. Why: a listener that outlives its screen keeps intercepting the back button elsewhere. Smell: `BackHandler.addEventListener(...)` in an effect with no cleanup, or a call to a `removeEventListener` method. Source: https://reactnative.dev/docs/backhandler#example
- **Return true only when the back press was handled**: "If one subscription returns true, then subscriptions registered earlier will not be called." - return true after handling the press and false otherwise. Why: when no subscription returns true, the default behaviour runs and exits the app. Smell: a handler that always returns true and blocks stack navigation, or one that handles the press but returns nothing. Source: https://reactnative.dev/docs/backhandler
- **Scope BackHandler logic to Android**: "It is Android-only." - provide a separate route for the same intent on iOS, such as `usePreventRemove`. Why: iOS has no hardware back button, so the handler never runs there. Smell: an unsaved-changes prompt implemented only with `BackHandler`. Source: https://reactnative.dev/docs/backhandler
- **Handle back inside an open Modal with onRequestClose**: "If your app shows an opened Modal, BackHandler will not publish any events" - close the React Native `Modal` through its `onRequestClose` prop. Why: BackHandler listeners are silent while the modal is open. Smell: a `BackHandler` listener added to close a `Modal`. Source: https://reactnative.dev/docs/backhandler
