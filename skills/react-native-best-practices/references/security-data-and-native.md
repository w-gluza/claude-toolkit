# React Native code-review rules: security, data and native APIs

Extracted 2026-11-12 from the React Native 0.88 documentation (facebook/react-native-website, CC BY 4.0) and the Expo SDK 58 documentation (expo/expo, MIT). One rule per bullet, one source link each. Quotations are short excerpts; the rest is original.

## Secrets in the bundle

- **Keep API keys and secrets out of app code**: "Never store sensitive API keys in your app code." - treat every string in the JavaScript bundle, native config and assets as public. Why: "Anything included in your code could be accessed in plain text by anyone inspecting the app bundle." Smell: a literal key, token, signing secret or private endpoint credential in a `.ts` file, `app.json`, `Info.plist` or `strings.xml`. Source: https://reactnative.dev/docs/security#storing-sensitive-info
- **Do not treat build-time env files as secret storage**: "they should not be confused with server-side environment variables, which can often contain secrets and API keys" - dotenv-style tools only move a value from source into the bundle, so use them for endpoints and flags and nothing private. Why: the value is inlined at build time and ships to every device. Smell: `Config.STRIPE_SECRET`, `process.env.API_SECRET` or a service-role key read in client code. Source: https://reactnative.dev/docs/security#storing-sensitive-info
- **Put secret-bearing calls behind a server**: "build an orchestration layer between your app and the resource" - the app calls your endpoint and the endpoint adds the key before forwarding. Why: "Secrets in server side code cannot be accessed by the API consumers the same way secrets in your app code can." Smell: the app calling a third-party API directly with a privileged key in a header. Source: https://reactnative.dev/docs/security#storing-sensitive-info
- **Never put secrets in `EXPO_PUBLIC_` variables**: "Never store sensitive secrets in environment variables that are prefixed with `EXPO_PUBLIC_`." - the prefix means the value is inlined into the client bundle. Why: "they have access to all of the code and embedded environment variables in your app". Smell: `EXPO_PUBLIC_API_SECRET`, `EXPO_PUBLIC_PRIVATE_KEY` or any `EXPO_PUBLIC_` name holding a credential rather than a public identifier. Source: https://docs.expo.dev/guides/environment-variables/#security-considerations
- **Read `EXPO_PUBLIC_` variables with static dot notation**: "Every environment variable must be statically referenced as a property of `process.env` using JavaScript's dot notation for it to be inlined." - write `process.env.EXPO_PUBLIC_API_URL` in full at each use. Why: "Alternative versions of the expression are not supported", so the value is `undefined` at runtime. Smell: `process.env['EXPO_PUBLIC_KEY']`, `const {EXPO_PUBLIC_X} = process.env` or `process.env[name]`. Source: https://docs.expo.dev/guides/environment-variables/#how-to-read-from-environment-variables
- **Do not select an environment through `NODE_ENV`** (Expo SDK 58+): "In SDK 58 and later, each command sets `NODE_ENV` to its mode and replaces any value you set." - only the standard development and production `.env` files load, so swap `.env.local` contents or use the hosted environment tooling instead. Why: a staging file that never loads means a build pointing at the wrong backend. Smell: `NODE_ENV=staging npx expo start`, or a `.env.staging` file the scripts expect to be picked up. Source: https://docs.expo.dev/guides/environment-variables/#using-multiple-env-files-to-define-separate-environments
- **Never pass a client secret to AuthSession from app code**: "Never put any secret keys inside your application code, there is no secure way to do this!" - keep the secret on a server and expose an endpoint that performs the privileged call. Why: for `clientSecret` the reference says "There is no secure way to store this on the client." Smell: `clientSecret:` in a `useAuthRequest`, `exchangeCodeAsync` or `refreshAsync` config inside the app. Source: https://docs.expo.dev/versions/v58.0.0/sdk/auth-session/#security-considerations
- **Exchange the authorisation code on a server when the provider needs a client secret**: "If the provider requires a client secret, exchange the authorization code on a server" - the server holds the secret and talks to the token endpoint; exchange in the app only when the provider accepts PKCE without a secret. Why: "Your client application code is not a secure place to store secrets". Smell: an in-app token request that includes a secret fetched from config or env. Source: https://docs.expo.dev/guides/authentication/#obtaining-access-tokens

## Storing data on the device

- **Choose storage by the sensitivity of the data**: "choose the right type of storage based on its sensitivity" - decide per value whether it belongs in memory, plain storage or the platform secure store. Why: persisted data "can make that data more vulnerable to being accessed by attackers". Smell: one generic `storage.set()` helper used for preferences and credentials alike. Source: https://reactnative.dev/docs/security#storing-sensitive-info
- **Keep tokens and secrets out of Async Storage**: "provides an asynchronous, unencrypted, key-value store" - the documented do-not list for Async Storage is token storage and secrets; use it for non-sensitive data and cached state. Why: the values sit on disk in plain text. Smell: `AsyncStorage.setItem('accessToken', ...)`, a refresh token in a persisted store, or a password in a cached form. Source: https://reactnative.dev/docs/security#async-storage
- **Store credentials in the Keychain or an encrypted Android store**: "This is an ideal place to store certificates, tokens, passwords, and any other sensitive information that doesn’t belong in Async Storage." - use a library that wraps iOS Keychain Services and Android encrypted preferences or Keystore. Why: "React Native does not come bundled with any way of storing sensitive data." Smell: a hand-rolled obfuscation or base64 step before writing a token to plain storage. Source: https://reactnative.dev/docs/security#secure-storage
- **Exclude sensitive slices from persisted state**: "saving sensitive form data in redux state and persisting the whole state tree in Async Storage" is the documented example of accidental exposure - allowlist what a persistence layer writes. Why: "Be mindful of unintentionally storing or exposing sensitive info." Smell: a persist config with no allowlist, or an auth or payment form slice inside the persisted root. Source: https://reactnative.dev/docs/security#secure-storage
- **Scrub tokens and personal data from monitoring payloads**: "sending user tokens and personal info to an application monitoring service" is named as accidental exposure - filter headers, request bodies and user objects before they reach crash or analytics reporting. Why: the data leaves the device and lands in a third-party system. Smell: `captureException(error, {extra: {user, headers}})`, or a logger that serialises a whole request config. Source: https://reactnative.dev/docs/security#secure-storage
- **Do not persist sensitive data that only this session needs**: "Unpersisted data is never written to disk" - hold one-time codes, card details and similar values in memory and drop them when done. Why: "it’s significantly harder to access information that was never requested in the first place". Smell: a one-time passcode, CVV or identity document number written to any storage. Source: https://reactnative.dev/docs/security#storing-sensitive-info
- **Use SecureStore for small secrets, not as a general database** (Expo): "It's intended for small values such as tokens, keys, and other secrets." - keep larger or non-sensitive data in files, SQLite or Async Storage. Why: the secure store is a key-value keychain wrapper with platform size limits. Smell: a serialised user profile, cache or list written through `SecureStore.setItemAsync`. Source: https://docs.expo.dev/develop/user-interface/store-data/#expo-securestore
- **Handle native errors when writing large values to SecureStore**: "Expo does not enforce a limit, so make sure to handle native errors if you plan to store very large strings." - keep values small and catch the rejection. Why: "Historically, some iOS releases refused values above roughly 2048 bytes." Smell: a full JWT bundle, serialised session object or JSON blob stored under one key with no `try/catch`. Source: https://docs.expo.dev/versions/v58.0.0/sdk/securestore/
- **Do not make SecureStore the only copy of irreplaceable data**: "it is important not to rely on it as a single source of truth for irreplaceable, critical data" - keep anything that cannot be re-issued recoverable from the server. Why: entries can be deleted or invalidated by the system. Smell: an encryption key or recovery secret that exists only in the secure store with no recovery path. Source: https://docs.expo.dev/versions/v58.0.0/sdk/securestore/#data-persistence
- **Expect secure-store data to behave differently after reinstall on each platform**: "data stored with `expo-secure-store` will persist across app uninstallations when the app is reinstalled with the same bundle ID" (iOS), while on Android it "will not be preserved upon app uninstallation" - clear stale credentials on first launch and never depend on either behaviour. Why: "you should never rely on this implementation detail". Smell: first-run logic that assumes an empty store, or a feature that assumes the token survives reinstall. Source: https://docs.expo.dev/versions/v58.0.0/sdk/securestore/#data-persistence
- **Handle `null` from SecureStore reads**: "It resolves with `null` if there is no entry for the given key or if the key has been invalidated." - branch on the missing value and send the user back through sign-in. Why: a missing entry is a normal state, not an exception. Smell: `JSON.parse(await SecureStore.getItemAsync(key))` or a non-null assertion on the result. Source: https://docs.expo.dev/versions/v58.0.0/sdk/securestore/#securestoregetitemasynckey-options
- **Treat a failed biometric prompt as an auth outcome**: "treat a rejection as an auth-flow outcome to retry or back out of, not as data corruption" - wrap protected reads and writes in `try/catch` and offer retry or cancel. Why: the user can cancel, be locked out, have no biometrics enrolled, or the prompt can time out. Smell: a `catch` that deletes the stored credential or signs the user out on any error. Source: https://docs.expo.dev/versions/v58.0.0/sdk/securestore/#securestoregetitemasynckey-options
- **Avoid the synchronous SecureStore calls for protected values**: "This function blocks the JavaScript thread, so the application may not be interactive" - use `getItemAsync` and `setItemAsync` when `requireAuthentication` is set. Why: the app freezes until the user finishes the system prompt. Smell: `SecureStore.getItem(key, {requireAuthentication: true})` in render or in a store initialiser. Source: https://docs.expo.dev/versions/v58.0.0/sdk/securestore/#securestoregetitemkey-options
- **Restrict SecureStore keys to the documented characters**: "Keys may contain alphanumeric characters, `.`, `-`, and `_`." - build keys from a fixed prefix and a safe identifier. Why: other characters are rejected by the native layer. Smell: keys containing `:`, `/`, `@`, spaces or a raw email address. Source: https://docs.expo.dev/versions/v58.0.0/sdk/securestore/#securestoresetitemasynckey-value-options
- **Do not use the always-accessible keychain levels** (iOS): "The data in the keychain item can always be accessed regardless of whether the device is locked. This is the least secure option." - `ALWAYS` and `ALWAYS_THIS_DEVICE_ONLY` are deprecated; pick a level tied to device unlock. Why: the deprecation note says "Use an accessibility level that provides some user protection". Smell: `keychainAccessible: SecureStore.ALWAYS` or `ALWAYS_THIS_DEVICE_ONLY`. Source: https://docs.expo.dev/versions/v58.0.0/sdk/securestore/#constants
- **Pass the same `keychainService` when reading as when writing**: "If the item is set with the keychainService option, it will be required to later fetch the value." - centralise the options object used for a given key. Why: a read without it returns `null` and looks like a signed-out user. Smell: `setItemAsync(key, value, {keychainService})` paired with `getItemAsync(key)` or `deleteItemAsync(key)` without options. Source: https://docs.expo.dev/versions/v58.0.0/sdk/securestore/#securestoreoptions
- **Exclude SecureStore entries from a custom Android backup configuration**: "you should exclude the `SecureStore` under the `sharedpref` domain and set the `configureAndroidBackup` to `false`" - only when the app ships its own Auto Backup rules. Why: "it's impossible to decrypt them after restoring the backup". Smell: a custom `fullBackupContent` or data-extraction rules file that does not mention `SecureStore`. Source: https://docs.expo.dev/versions/v58.0.0/sdk/securestore/#android-auto-backup
- **Flag sensitive clipboard content** (Android, Expo): "set `android.isSensitive` in `setStringAsync` and `setImageAsync`" - when copying passwords, one-time codes, tokens, payment details or personal data. Why: it can obfuscate keyboard previews and hide the clipboard overlay. Smell: `Clipboard.setStringAsync(otp)` or a copied recovery phrase with no options argument. Source: https://docs.expo.dev/versions/v58.0.0/sdk/clipboard/#mark-clipboard-content-as-sensitive-android

## Deep links and authentication

- **Never put sensitive data in a deep link**: "Deep links are not secure and you should never send any sensitive information in them." - pass an opaque identifier and fetch the rest over an authenticated request. Why: "sending tokens is a security concern". Smell: `myapp://login?token=...`, a password-reset secret or session id in a custom-scheme URL. Source: https://reactnative.dev/docs/security#authentication-and-deep-linking
- **Treat data arriving by custom scheme as untrusted**: "There is nothing stopping a malicious application from hijacking your deep link by also registering to the same scheme" - validate the path and parameters and never act on a link as proof of identity. Why: "there is no centralized method of registering URL schemes". Smell: a `url` handler that navigates to a privileged screen or performs an action using parameters taken straight from the link. Source: https://reactnative.dev/docs/security#authentication-and-deep-linking
- **Use universal links for links that carry meaning** (iOS): "will allow linking to content within your app securely in iOS" - verified `https` links are bound to your domain; custom schemes are not. Why: with a custom scheme the system picks the handling app and "the user will be blissfully unaware". Smell: a magic-link or payment-return flow that depends on `myapp://` alone. Source: https://reactnative.dev/docs/security#authentication-and-deep-linking
- **Use PKCE for every OAuth redirect flow**: "an additional check must be added in the form of PKCE" - the client sends a `code_challenge` and later proves it holds the `code_verifier`. Why: "even if a malicious application gets access to the verification code, it will be useless on its own". Smell: an authorisation-code flow with no code challenge, or a hand-built authorise URL opened in a browser. Source: https://reactnative.dev/docs/security#oauth2-and-redirects
- **Leave PKCE on and never use the plain challenge method** (Expo AuthSession): "You should never use `Plain` as it's not good enough for secure verification." - `usePKCE` defaults to true and the method defaults to S256; keep both. Why: a plain challenge exposes the verifier to anyone who sees the request. Smell: `usePKCE: false` or `codeChallengeMethod: CodeChallengeMethod.Plain`. Source: https://docs.expo.dev/versions/v58.0.0/sdk/auth-session/#authrequestconfig
- **Do not use the implicit flow for new code**: "due to inherent security risks, including the risk of access token injection" the implicit flow is no longer recommended - use authorisation code with PKCE. Why: the access token arrives in the redirect URL itself. Smell: `responseType: ResponseType.Token`, or `TokenResponse.fromQueryParams` in a new sign-in flow. Source: https://docs.expo.dev/guides/authentication/#implicit-login
- **Rely on the provider's redirect allowlist and keep it narrow**: "Allowlisting redirect URLs is important to prevent malicious actors from pretending to be your application." - register exact redirect URIs for each build type. Why: the redirect carries the code or token back to whichever app owns the URL. Smell: a wildcard redirect registered with the provider, or a redirect URI built from user input. Source: https://docs.expo.dev/versions/v58.0.0/sdk/auth-session/#how-web-browser-based-authentication-flows-work
- **Build redirect URIs with `makeRedirectUri` and an explicit scheme**: "Create redirects with `AuthSession.makeRedirectUri()`" - pass `scheme` rather than leaving it to inference. Why: "we recommend you define the `scheme` property at least". Smell: a hard-coded redirect string per platform, or `makeRedirectUri()` with no arguments in a production build. Source: https://docs.expo.dev/guides/authentication/#rules-for-all-authentication-providers
- **Call `WebBrowser.maybeCompleteAuthSession()` on the redirect route**: "If you forget to add this then the popup window will not close." - call it at module scope of the screen that receives the redirect. Why: on web the auth popup stays open and the flow never resolves. Smell: an AuthSession screen that imports `expo-web-browser` nowhere. Source: https://docs.expo.dev/guides/authentication/#rules-for-all-authentication-providers
- **Verify the session token on the server on every request**: "you verify the signature and check the expiration" - the client only stores and sends the token. Why: a token that is only checked on the device can be forged or replayed. Smell: client code decoding a JWT to decide access, with API routes that never validate it. Source: https://docs.expo.dev/develop/authentication/#managing-sessions-after-oauth
- **Do not treat a biometric prompt as authentication with the backend**: "A biometric prompt alone does not authenticate with your server." - use it to unlock a credential held on the device after a valid session exists. Why: "It acts as a local gate that protects access to content or credentials on the device." Smell: `if (result.success) setIsAuthenticated(true)` with no server-issued session behind it. Source: https://docs.expo.dev/develop/authentication/#biometrics
- **Declare the Face ID usage description when using local authentication** (iOS): "Apple requires apps which use FaceID to provide a description of why they use this API." - set `NSFaceIDUsageDescription` through the config plugin or `Info.plist`. Why: without it "the module will authenticate using device passcode". Smell: `authenticateAsync` in code and no `faceIDPermission` or `NSFaceIDUsageDescription` in config. Source: https://docs.expo.dev/versions/v58.0.0/sdk/local-authentication/#localauthenticationauthenticateasyncoptions
- **Require strong biometrics for sensitive actions** (Android): "Class 2 biometrics are less secure than Class 3." - pass `biometricsSecurityLevel: 'strong'`; the default is `'weak'`. Why: weak includes camera-based face unlock. Smell: a payment or credential reveal gated by `authenticateAsync` without `biometricsSecurityLevel`. Source: https://docs.expo.dev/versions/v58.0.0/sdk/local-authentication/#localauthenticationoptions

## Transport security and networking

- **Call only `https` endpoints**: "SSL encryption protects against the requested data being read in plain text" - every API base URL, image host and socket should use TLS. Why: plain HTTP exposes credentials and payloads in transit. Smell: `http://` in an API constant, a WebView source or an env default. Source: https://reactnative.dev/docs/security#network-security
- **Scope App Transport Security exceptions to named domains** (iOS): "add exceptions only for specific domains using `NSExceptionDomains` rather than disabling ATS globally" - and remove development exceptions from release configuration. Why: "Apple's App Store review requires justification for disabling ATS". Smell: `NSAllowsArbitraryLoads` set to true in `Info.plist` or in `ios.infoPlist`. Source: https://reactnative.dev/docs/network#using-fetch
- **Do not re-enable cleartext traffic on Android**: "On Android, as of API Level 28, clear text traffic is also blocked by default." - keep the default and use a debug-only network security config for local servers. Why: the override applies to every request the app makes. Smell: `android:usesCleartextTraffic` set to true in the main manifest. Source: https://reactnative.dev/docs/network#using-fetch
- **Ship a rotation plan with any pinned certificate**: "any apps with the old certificate embedded in them will cease to work" - pin more than one certificate or key and schedule the app update ahead of server rotation. Why: "Certificates expire every 1-2 years". Smell: a single pinned leaf certificate with no backup pin and no expiry noted. Source: https://reactnative.dev/docs/security#ssl-pinning
- **Catch errors from every `fetch`**: "Don't forget to catch any errors that may be thrown by `fetch`, otherwise they will be dropped silently." - add `try/catch` or `.catch` and surface a state the UI can show. Why: an unhandled rejection leaves a spinner running with nothing logged. Smell: `await fetch(...)` in an effect or handler with no error path, or a `.then` chain with no `.catch`. Source: https://reactnative.dev/docs/network#handling-the-response
- **Do not rely on CORS to protect an API used by the app**: "The security model for XMLHttpRequest is different than on web" - native requests are not restricted by origin, so the server must authenticate and authorise each call. Why: there is no cross-origin check in a native app. Smell: an endpoint described as safe because only the web origin is allowed. Source: https://reactnative.dev/docs/network#using-other-networking-libraries
- **Do not use `redirect: 'manual'` with `fetch`**: "The following options are currently not working with `fetch`" - the list names `redirect:manual`; handle redirects on the server or follow them. Why: the option is ignored, so code that inspects a 3xx response never runs. Smell: `fetch(url, {redirect: 'manual'})` followed by a `response.status === 302` branch. Source: https://reactnative.dev/docs/network#known-issues-with-fetch-and-cookie-based-authentication
- **Do not send repeated headers with the same name** (Android): "Having same name headers on Android will result in only the latest one being present." - combine values into one header. Why: the earlier values are dropped on one platform only. Smell: `headers.append` called twice with the same name, or duplicate cookie headers. Source: https://reactnative.dev/docs/network#known-issues-with-fetch-and-cookie-based-authentication
- **Prefer token headers to cookie sessions**: "Cookie based authentication is currently unstable." - send an explicit authorisation header from secure storage. Why: cookie handling differs between platforms and has open issues. Smell: `credentials: 'include'` as the only session mechanism in a native client. Source: https://reactnative.dev/docs/network#known-issues-with-fetch-and-cookie-based-authentication
- **Guard against redirect loops when a session expires** (iOS): "if a `Set-Cookie` header is present, the cookie is not set properly" on a `302` - detect expiry explicitly and stop retrying. Why: it "might cause a scenario where infinite requests occur if the redirect is the result of an expired session". Smell: an automatic retry on auth failure with no attempt limit. Source: https://reactnative.dev/docs/network#known-issues-with-fetch-and-cookie-based-authentication

## Linking and URL handling

- **Handle links for both a cold start and a running app** (without Expo Router): "There are two ways to handle URLs that open your app." - read `Linking.getInitialURL()` once and subscribe to the `url` event. Why: a link that launches the app fires no event, and a link to a running app is not the initial URL. With Expo Router the router resolves incoming links itself, so add neither. Smell: only `addEventListener('url', ...)` or only `getInitialURL()` in the link setup of an app with no Expo Router. Source: https://reactnative.dev/docs/linking#handling-deep-links
- **Check `canOpenURL()` before opening a non-http URL**: "If you're passing in a non-http(s) URL, it's best to check `canOpenURL()` first." - and include the scheme on web URLs. Why: "This method will fail if the system doesn't know how to open the specified URL." Smell: `Linking.openURL('tel:' + phone)` or a third-party app scheme opened without a check. Source: https://reactnative.dev/docs/linking#openurl
- **Handle the rejection from `openURL()`**: "If the user cancels the open dialog or there are no registered applications for the url, the promise is rejected." - catch it and show a fallback. Why: a missing mail or maps app is a normal condition on real devices. Smell: `Linking.openURL(url)` with no `await` in `try/catch` and no `.catch`. Source: https://reactnative.dev/docs/linking#openurl
- **Declare queried schemes on iOS**: "your app also needs to provide the `LSApplicationQueriesSchemes` key inside `Info.plist` or `canOpenURL()` will always resolve to `false`" - list each scheme the app checks. Why: the check silently reports that nothing can open the link. Smell: a new `canOpenURL('someapp://')` call with no matching `Info.plist` or `ios.infoPlist` change. Source: https://reactnative.dev/docs/linking#canopenurl
- **Declare intent queries on Android 11 and later**: "When targeting Android 11 (SDK 30) you must specify the intents for the schemes you want to handle in `AndroidManifest.xml`." - add a `queries` entry for each scheme. Why: without it the `canOpenURL()` promise rejects. Smell: a new scheme check with no `queries` block in the manifest or config plugin. Source: https://reactnative.dev/docs/linking#canopenurl
- **Use `https` links for anything shared outside the app**: "Instead, you should use standard `https` links" - configure them to open the app on mobile. Why: with a custom scheme "the user might open the email on a desktop, where the link wouldn't work". Smell: `myapp://` URLs in emails, SMS templates or share text. Source: https://reactnative.dev/docs/linking
- **Forward links from the scene delegate when the app uses scenes** (iOS): "you must forward links from `SceneDelegate` instead" - `RCTLinkingManager` ignores the `AppDelegate` methods once a scene manifest is declared. Why: without the connection options being handed over, `getInitialURL()` resolves to `null`. Smell: a scene-based app with link forwarding only in `AppDelegate`. Source: https://reactnative.dev/docs/linking#enabling-deep-links

## App state and permissions

- **Handle the iOS-only `inactive` state**: "This is a state that occurs when transitioning between foreground & background" - it also occurs in the multitasking view, Notification Center and during a call. Why: logic that only compares `active` and `background` misses or double-counts transitions on iOS. Smell: `if (state === 'background')` used to hide sensitive content, with no handling of `inactive`. Source: https://reactnative.dev/docs/appstate#app-states
- **Do not sign out or wipe state on every Android `background`**: "including temporary system activities" - on Android the app reports `background` while another activity such as an autofill credential picker is in front, even one launched by the app. Why: an aggressive lock breaks password autofill and system pickers. Smell: an immediate lock, navigation reset or token clear in the `background` branch with no grace period. Source: https://reactnative.dev/docs/appstate#app-states
- **Allow for a `null` `AppState.currentState` on the legacy architecture** (not Expo SDK 55 or later, where the New Architecture is always on): "`currentState` will be `null` at launch until it is retrieved asynchronously from the native side" - initialise from the first `change` event as well. Why: a ref seeded with `null` makes the first comparison wrong. Smell: `AppState.currentState.match(...)` without optional chaining. Source: https://reactnative.dev/docs/appstate#basic-usage
- **Remove native event subscriptions on cleanup**: "returns an `EventSubscription` object which should be cleared using the `EventSubscription.remove` method" - keep the returned subscription and call `remove()` in the effect cleanup. Why: a leaked listener keeps firing after the screen unmounts. Smell: `BackHandler.addEventListener`, `AppState.addEventListener` or `Linking.addEventListener` with the return value discarded. Source: https://reactnative.dev/docs/backhandler#example
- **Do not expect `BackHandler` events while a `Modal` is open** (Android): "If your app shows an opened `Modal`, `BackHandler` will not publish any events" - handle the back press with the modal's `onRequestClose`. Why: the handler is never called, so the modal cannot be dismissed with the back button. Smell: a `Modal` with a `BackHandler` listener and no `onRequestClose`. Source: https://reactnative.dev/docs/backhandler
- **Request dangerous Android permissions at runtime**: "You should use this module for those permissions." - a manifest entry alone covers only normal permissions. Why: dangerous permissions require a dialog prompt before the API works. Smell: camera, location or contacts code with a manifest entry and no `PermissionsAndroid.request` or library equivalent. Source: https://reactnative.dev/docs/permissionsandroid
- **Handle all three permission results**: "indicating whether the user allowed or denied the request or does not want to be asked again" - branch on `GRANTED`, `DENIED` and `NEVER_ASK_AGAIN`, and offer a route to system settings for the last. Why: after never-ask-again the prompt will not appear and the feature looks broken. Smell: `if (result === GRANTED) {...}` with no else, or the result treated as a boolean. Source: https://reactnative.dev/docs/permissionsandroid#request
- **Configure permissions natively before requesting them in JavaScript** (Expo): "require native build-time configuration before they can be requested using runtime JavaScript code" - add the config plugin options or app config entries in the same change as the request call. Why: "it may result in your app getting rejected or pulled from the stores". Smell: a new `requestPermissionsAsync()` call with no app config change. Source: https://docs.expo.dev/guides/permissions/
- **Write a specific iOS usage message for each permission**: "These default messages will most likely need to be tailored to your specific use case for your app to be accepted by the App Store." - set them in `ios.infoPlist` or the library's plugin options. Why: boilerplate reasons are a store-review risk. Smell: a plugin added with default permission text, or a placeholder usage string. Source: https://docs.expo.dev/guides/permissions/#ios
- **Block Android permissions the app does not use**: "The only way to remove permissions that are added by package-level" manifests is `android.blockedPermissions` with the full permission name. Why: apps using dangerous permissions without valid reasons "may be rejected by Google". Smell: a library added for one feature that brings `RECORD_AUDIO` or location permissions nobody blocked. Source: https://docs.expo.dev/guides/permissions/#android
- **Design for a permission prompt that will not appear twice**: "prohibits an app from asking for the same permission more than once" - after a refusal show an explanation and a link to system settings rather than calling request again. Why: repeated requests return the stored answer without any dialog. Smell: a retry button that only calls `requestPermissionsAsync()` again. Source: https://docs.expo.dev/guides/permissions/#resetting-permissions

## Alerts, sharing and device feedback

- **Give Android alerts at most three buttons**: "On Android at most three buttons can be specified." - use an action sheet or custom modal for more choices. Why: iOS accepts any number, so the fourth option disappears on one platform only. Smell: `Alert.alert` with four or more buttons. Source: https://reactnative.dev/docs/alert#android
- **Do not use `Alert.prompt` in shared code**: "Alert that prompts the user to enter some information is available on iOS only." - build a cross-platform input modal. Why: the call does nothing on Android. Smell: `Alert.prompt(...)` outside an iOS-only file or platform check. Source: https://reactnative.dev/docs/alert
- **Do not infer a completed share from the result on Android**: "returns a Promise which will always be resolved with action being `Share.sharedAction`" - only iOS reports `Share.dismissedAction`. Why: analytics or rewards keyed on a successful share are wrong on Android. Smell: `if (result.action === Share.sharedAction) grantReward()`. Source: https://reactnative.dev/docs/share#share
- **Put the link in `message` for cross-platform sharing**: "At least one of `url` and `message` is required." - the `url` field is iOS only and `title` is Android only. Why: content passed only as `url` is not shared on Android. Smell: `Share.share({url})` with no `message`. Source: https://reactnative.dev/docs/share#share
- **Declare the vibrate permission on Android**: "Android apps should request the `android.permission.VIBRATE` permission" - add it to the manifest or app config. Why: the call has no effect or fails without it. Smell: a first use of `Vibration.vibrate()` with no manifest change. Source: https://reactnative.dev/docs/vibration
- **Do not pass a custom vibration duration and expect it on iOS**: "the vibration duration is fixed at roughly 400 milliseconds" on iOS - a numeric duration is Android only, and pattern entries mean different things on each platform. Why: on iOS the pattern numbers are separation times only. Smell: `Vibration.vibrate(50)` used as a short haptic tick in shared code. Source: https://reactnative.dev/docs/vibration#vibrate
- **Compare `Platform.Version` with the right type per platform**: "`Version` is set to the Android API version not the Android OS version" - on iOS it is "a string with the current version of the operating system". Why: a numeric comparison against the iOS string, or an OS number against the Android API level, gives the wrong branch. Smell: `Platform.Version >= 13` with no `Platform.OS` check. Source: https://reactnative.dev/docs/platform-specific-code

## Removed and deprecated core modules

- **Import AsyncStorage from a community package**: "Removed from React Native" - the core page points to the community packages on React Native Directory. Why: the core export no longer exists. Smell: `import {AsyncStorage} from 'react-native'`. Source: https://reactnative.dev/docs/asyncstorage
- **Import Clipboard from a community or Expo package**: "Removed from React Native" - the same notice applies to the core `Clipboard` module. Why: the core export no longer exists. Smell: `import {Clipboard} from 'react-native'`. Source: https://reactnative.dev/docs/clipboard
- **Replace `ImagePickerIOS` with a maintained picker library**: "Removed from React Native" - choose a package from React Native Directory. Why: the core export no longer exists. Smell: `ImagePickerIOS.openSelectDialog(...)`. Source: https://reactnative.dev/docs/imagepickerios
- **Do not depend on remote JavaScript debugging**: "Remote JavaScript Debugging has been removed as of React Native 0.79." - use React Native DevTools. Why: code paths and docs that assume the JavaScript runs in a desktop browser no longer apply. Smell: setup notes or dev-only branches that reference the remote debugger. Source: https://reactnative.dev/docs/other-debugging-methods#remote-javascript-debugging-removed
- **Replace `react-test-renderer` with React Native Testing Library**: "`react-test-renderer` does not support React 19 and above" - remove the deprecated package. Why: tests built on it fail or warn after the React upgrade. Smell: `import renderer from 'react-test-renderer'` or the package in `devDependencies`. Source: https://docs.expo.dev/develop/unit-testing/#install-react-native-testing-library

## Background work

- **Keep UI out of Headless JS tasks** (Android only): "as long as it doesn't touch UI" - a task may use the network and timers and must return a promise that settles. Why: once the promise resolves React Native goes into paused mode. Smell: navigation, alerts or state setters called from a registered headless task, or a task that never resolves. Source: https://reactnative.dev/docs/headless-js-android#the-js-api
- **Do not start a headless task while the app is in the foreground**: "By default, your app will crash if you try to run a task while the app is in the foreground." - check foreground state in native code or pass the documented fourth argument on purpose. Why: the guard exists to stop heavy task work slowing the UI. Smell: a service started unconditionally from a receiver. Source: https://reactnative.dev/docs/headless-js-android#caveats

## JavaScript environment and libraries

- **Check that an npm package runs in React Native before adopting it**: "the libraries that it lists may not all be compatible with React Native" - packages built for the DOM or Node do not work. Why: the failure appears at runtime, often only in a release build. Smell: a new dependency that imports `fs`, `path`, `crypto` from Node or touches `document` or `window`. Source: https://reactnative.dev/docs/libraries#finding-libraries
- **Install dependencies with `npx expo install`** (Expo): "We recommend always using `npx expo install` instead of `npm install` or `yarn add` directly" - it picks a version compatible with the SDK. Why: it can also "warn you about known incompatibilities". Smell: a version of an Expo or React Native library that does not match the SDK's expected range. Source: https://docs.expo.dev/workflow/using-libraries/#installing-a-third-party-library
- **Use a development build for libraries with native code** (Expo): "It does not include all of the native code required to support every library" is the stated limit of Expo Go - any library with `android` or `ios` directories or a config plugin needs a development build. Why: the module is missing at runtime in Expo Go. Smell: a native library added while the team's test instructions still say to open Expo Go. Source: https://docs.expo.dev/workflow/using-libraries/#determining-third-party-library-compatibility

## TypeScript

- **Use `tsc` for type checking only**: "We recommend that you use the TypeScript compiler only for type checking." - Babel transforms the sources during bundling. Why: Babel strips types without checking them, so a type error does not fail the bundle. Smell: no `tsc --noEmit` step in CI, or `tsc` configured to emit into the bundle path. Source: https://reactnative.dev/docs/typescript#how-typescript-and-react-native-works
- **Leave the `index.js` entry point as JavaScript**: "You should leave the `./index.js` entrypoint file as it is" - convert other files to `.tsx`. Why: renaming it can break bundling of a production build. Smell: a migration change that renames `index.js` to `index.ts`. Source: https://reactnative.dev/docs/typescript#adding-typescript-to-an-existing-project
- **Import only from the `react-native` root** (0.87+): "The API is restricted to `react-native`'s index file." - the Strict TypeScript API is on by default and removes deep imports. Why: it "ensures that internal file path changes in React Native's source code won't be breaking". Smell: `from 'react-native/Libraries/...'`. Source: https://reactnative.dev/docs/strict-typescript-api
- **Type refs with `*Instance` types** (0.87+): "component type names no longer work as ref types" - use `ViewInstance`, `TextInputInstance`, `ScrollViewInstance` and the rest. Why: under the Strict API built-in components are typed as functions. Smell: `useRef<View>(null)`, `useRef<TextInput>(null)` or `Animated.LegacyRef`. Source: https://reactnative.dev/docs/strict-typescript-api
- **Keep `skipLibCheck` enabled**: "otherwise you will see errors in dependencies that you can't fix" - the shared React Native TypeScript config enables it by default. Why: third-party declaration files are checked against the stricter API. Smell: `skipLibCheck` set to false in `tsconfig.json`. Source: https://reactnative.dev/docs/strict-typescript-api

## Calling native modules from JavaScript

- **Give every native module a typed specification**: "define a typed JavaScript specification" - Codegen turns the spec into the native interfaces. Why: the spec "declares the methods and data types that will pass back and forth" between native code and JavaScript. Smell: `NativeModules.Something.method()` called with no spec file and no types. Source: https://reactnative.dev/docs/turbo-native-modules-introduction
- **Null-check modules obtained with `TurboModuleRegistry.get`**: "which will return `null` if the Turbo Native Module is unavailable" - use `getEnforcing` only when the module exists on every platform the code runs on. Why: `getEnforcing` "will throw an exception if the Turbo Native Module is unavailable". Smell: `TurboModuleRegistry.get<Spec>('X')!.method()`, or `getEnforcing` for an Android-only module in shared code. Source: https://reactnative.dev/docs/turbo-native-modules-introduction#3-write-application-code-using-the-turbo-native-module
- **Avoid synchronous native methods**: "calling methods synchronously can have strong performance penalties and introduce threading-related bugs to your native modules" - expose a promise instead. Why: the JavaScript thread blocks for the duration of the native call. Smell: `isBlockingSynchronousMethod = true` or `RCT_EXPORT_BLOCKING_SYNCHRONOUS_METHOD` behind a frequently called function. Source: https://reactnative.dev/docs/legacy/native-modules-android#synchronous-methods
- **Expect a native callback to fire once**: "A native module is supposed to invoke its callback only once." - use an event emitter for repeated updates. Why: "If the callback is never invoked, some memory is leaked." Smell: a progress or stream API modelled as a single callback argument. Source: https://reactnative.dev/docs/legacy/native-modules-ios#callbacks
- **Read native constants through `getConstants()`**: "This will no longer be supported with TurboModules" refers to reading constants directly off the module object - call `getConstants()`. Why: the direct property is undefined on the New Architecture. Smell: `NativeModules.Calendar.DEFAULT_EVENT_NAME`. Source: https://reactnative.dev/docs/legacy/native-modules-android#exporting-constants
- **Make no assumptions about the thread a native method runs on**: "Native modules should not have any assumptions about what thread they are being called on" - dispatch blocking work to a worker and UI work to the main thread inside the module. Why: "the current assignment is subject to change in the future". Smell: a module method that touches views directly or performs disk or network I/O inline. Source: https://reactnative.dev/docs/legacy/native-modules-android#threading

## Debugging hygiene

- **Guard development-only code with `__DEV__`**: "guard development-only blocks of code" - wrap dev menus, mock toggles and verbose logging in `if (__DEV__)`. Why: it "gets completely stripped out with the `if` blocks it guards in the minified build". Smell: a debug screen, test credential shortcut or feature override reachable in a release build. Source: https://reactnative.dev/docs/global-__DEV__
- **Do not commit `LogBox.ignoreAllLogs()`**: "This can be useful in situations such as giving product demos." - that is the documented use; remove it afterwards. Why: every warning and error notification is hidden for the whole team. Smell: `LogBox.ignoreAllLogs()` in the app entry file. Source: https://reactnative.dev/docs/debugging#ignore-all-logs
- **Limit `LogBox.ignoreLogs()` to warnings that cannot be fixed**: "This can be useful for noisy warnings or those that cannot be fixed, e.g. in a third-party dependency." - name the dependency and keep the pattern narrow. Why: a broad pattern hides new warnings from your own code. Smell: an ignore entry for a warning raised by app code, or a pattern as wide as a single common word. Source: https://reactnative.dev/docs/debugging#ignore-specific-logs
- **Do not rely on LogBox to surface production errors**: "are disabled in release (production) builds" - the Dev Menu, LogBox and DevTools are development features; add error boundaries and reporting. Why: a release build shows nothing when an error is only logged. Smell: an error path whose only handling is `console.error`. Source: https://reactnative.dev/docs/debugging
- **Remove stray `console.log` debugging**: "Using `console.log` for debugging isn't considered the best practice" - use breakpoints, and delete temporary logs before merge. Why: leftover logs can print tokens and personal data to device logs. Smell: `console.log(response)`, `console.log(user)` or logged auth headers in a diff. Source: https://docs.expo.dev/debugging/runtime-issues/#development-errors
- **Generate and keep source maps for each release**: "Source maps are required to symbolicate stack traces." - enable them on iOS, where they are off by default, and archive them with the build. Why: "Make sure that the source map you use corresponds to the exact commit of the crashing app." Smell: a release pipeline with no `SOURCEMAP_FILE` output or no upload of maps to the crash service. Source: https://reactnative.dev/docs/debugging-release-builds#enabling-source-maps
- **Add crash and error reporting to production builds** (Expo): "Implementing a crash and bug reporting service in your production app offers several benefits" - initialise it early and scrub sensitive fields. Why: "When a production app crashes, there is very little information available compared to development." Smell: a production app with no reporting initialisation in its entry point. Source: https://docs.expo.dev/debugging/runtime-issues/#using-error-reporting-services

## Testing

- **Do not call real network services from unit tests**: "It could make the tests slow and unstable (because of the network requests involved)" - provide a mock implementation of the service. Why: "The service may return different data every time you run the test". Smell: a test that hits a real URL or needs credentials to pass. Source: https://reactnative.dev/docs/testing-overview#mocking
- **Assert on what the user can see or hear**: "As a rule of thumb, prefer using things users can see or hear" - query by rendered text or accessibility attributes. Why: such tests survive refactoring. Smell: assertions on component internals rather than rendered output. Source: https://reactnative.dev/docs/testing-overview#testing-user-interactions
- **Avoid assertions on props, state and `testID`**: "making assertions on component props or state" and "testID queries" are the two things the guide says to avoid. Why: they "tend to break by refactoring". Smell: `getByTestId` where a text or role query would work, or `expect(instance.state...)`. Source: https://reactnative.dev/docs/testing-overview#testing-user-interactions
- **Keep snapshots small**: "We recommend that you only use small snapshots" - snapshot a focused subtree, not a whole screen. Why: with large snapshots "their added value becomes low". Smell: a snapshot file of several hundred lines for one test. Source: https://reactnative.dev/docs/testing-overview#testing-rendered-output
- **Review every snapshot update as a behaviour change**: "it's tempting to update it using the `--updateSnapshot` jest option without taking proper care to investigate whether the change is expected" - explain the change in the pull request. Why: a snapshot is considered correct at creation even when the output is wrong. Smell: a large snapshot diff alongside an unrelated code change. Source: https://reactnative.dev/docs/testing-overview#testing-rendered-output
- **Do not treat component tests as proof of native behaviour**: "If there is a bug in the iOS or Android code, they will not find it." - cover native-dependent flows on a device or simulator. Why: component tests "are only JavaScript tests running in Node.js environment". Smell: a permissions, deep-link or secure-storage flow covered only by Jest tests with mocked modules. Source: https://reactnative.dev/docs/testing-overview#component-tests
- **Cover the vital flows end to end on a release build**: "Try to cover the vital parts of your app with E2E tests: authentication flow, core functionalities, payments, etc." - run them against the release configuration. Why: "E2E tests give you the highest possible confidence that part of your app is working." Smell: sign-in or payment changes with no end-to-end coverage. Source: https://reactnative.dev/docs/testing-overview#end-to-end-tests
- **Upgrade Jest together with `jest-expo`** (SDK 58+): "In SDK 58 and later, `jest-expo` requires Jest 30." - update `jest` and `@types/jest` in the same change. Why: a mismatched major version fails at startup. Smell: `jest-expo` at the SDK 58 range with `jest` still on 29. Source: https://docs.expo.dev/develop/unit-testing/#migrate-tests-to-sdk-58
