# React Native code-review rules: configuration, builds and release

Extracted 2026-11-12 from the Expo SDK 58 documentation (expo/expo, MIT) and the React Native 0.88 documentation (facebook/react-native-website, CC BY 4.0). One rule per bullet, one source link each. Quotations are short excerpts; the rest is original.

## App config files and dynamic configuration

- **Keep secrets out of the app config**: "You **should not** include any sensitive information in the app config" - API secrets, signing passwords and private tokens do not belong in app.json or app.config.*. Why: most of the config is readable at runtime through `Constants.expoConfig` and is embedded in builds and updates. Smell: a `clientSecret`, private key or service token added under `extra` or any top-level key. Source: https://docs.expo.dev/workflow/configuration/#reading-configuration-values-in-your-app
- **Audit the public config when config fields change**: "You can verify which configuration will be embedded in your builds/updates and available at runtime by running `npx expo config --type public`." - run it when a diff adds config values that came from the environment. Why: it shows exactly what ships to devices. Smell: a new `process.env.SOMETHING` read in app.config.js with no check of what ends up in the public output. Source: https://docs.expo.dev/workflow/configuration/#reading-configuration-values-in-your-app
- **Read config through Constants.expoConfig, not by importing the file**: "this will import the entire file rather than a processed version of it" - app code should not import app.json or app.config.js. Why: the raw file skips resolution and can pull build-only values into the bundle. Smell: `import appJson from '../app.json'` inside a component or service. Source: https://docs.expo.dev/workflow/configuration/#reading-configuration-values-in-your-app
- **Treat everything under extra as public**: "Any extra fields you want to pass to your experience. Values are accessible via `Constants.expoConfig.extra`" - only put values there that could be printed on the screen. Why: the field exists to hand data to the running app, so it travels with every build and update. Smell: `extra.apiSecret` or `extra.stripeSecretKey` populated from a CI variable. Source: https://docs.expo.dev/versions/v58.0.0/config/app/#extra
- **Do not read ios.config or android.config at runtime**: "This property key is not included in the production manifest and will evaluate to `undefined`." - keep build-only keys there and never reference them from app code. Why: the values are stripped from the public config, so runtime reads silently fail. Smell: `Constants.expoConfig.ios.config.googleMapsApiKey` used in a screen. Source: https://docs.expo.dev/versions/v58.0.0/config/app/#config
- **Return a plain object from dynamic config, never a Promise**: "The return value from the dynamic config is used as the final config. It cannot have any promises." - fetch remote values before the CLI runs and pass them in through environment variables. Why: the config is evaluated and serialised synchronously. Smell: `module.exports = async () => {...}` or an awaited fetch in app.config.ts. Source: https://docs.expo.dev/workflow/configuration/#configuration-resolution-rules
- **Spread the incoming config in function-form app.config**: "If the dynamic config returns a function, then the static config is passed to the function with `({ config }) => ({})`." - return `...config` plus overrides when an app.json also exists. Why: the function's return value is the final config, so anything not spread is dropped. Smell: `export default () => ({ name: 'X' })` next to an app.json that defines `ios`, `android` and `plugins`. Source: https://docs.expo.dev/workflow/configuration/#configuration-resolution-rules
- **Keep every setting inside the expo object when one exists**: "this will be used in place of the root object and all other keys will be ignored" - do not mix root-level keys with a top-level `expo` key. Why: sibling keys are discarded without a warning. Smell: `plugins` or `extra` added beside `expo` rather than inside it. Source: https://docs.expo.dev/workflow/configuration/#configuration-resolution-rules
- **Keep one dynamic config file**: "If both exist, then the TypeScript config is used." - delete app.config.js when app.config.ts is introduced. Why: edits to the ignored file have no effect and reviewers cannot tell which one is live. Smell: a change to app.config.js in a repository that also contains app.config.ts. Source: https://docs.expo.dev/workflow/configuration/#configuration-resolution-rules

## App config reference (SDK 58)

- **Do not expect scheme changes to work in Expo Go or over the air**: "This is a build-time configuration, it has no effect in Expo Go." - a new or renamed URL scheme needs a new binary. Why: schemes are written into Info.plist and AndroidManifest.xml at build time. Smell: a `scheme` change shipped together with an OTA update that depends on the new deep link. Source: https://docs.expo.dev/versions/v58.0.0/config/app/#scheme
- **Replace the deprecated androidStatusBar key**: "@deprecated Use the `expo-status-bar` plugin configuration instead" - move status bar settings to the plugin. Why: the key is marked deprecated in the SDK 58 schema. Smell: a new or edited `androidStatusBar` block in app.json. Source: https://docs.expo.dev/versions/v58.0.0/config/app/#androidstatusbar
- **Do not ship updates.useEmbeddedUpdate set to false**: "Whether to load the embedded update. Defaults to true. If set to false, an update will be fetched at launch." - keep the default in release profiles. Why: the reference says of this setting "This should not be used in production." Smell: `useEmbeddedUpdate: false` in a config that is not limited to a debug variant. Source: https://docs.expo.dev/versions/v58.0.0/config/app/#useembeddedupdate
- **Do not ship updates.disableAntiBrickingMeasures**: "which is liable to leave an app in a bricked state if not done carefully" - leave it at false outside test builds. Why: it lets JS override update configuration with no safety net. Smell: `disableAntiBrickingMeasures: true` without a variant guard. Source: https://docs.expo.dev/versions/v58.0.0/config/app/#disableantibrickingmeasures
- **Check ios.infoPlist and ios.entitlements entries by hand**: "No other validation is performed, so use this at your own risk of rejection from the App Store." - compare each key and value with Apple's documentation. Why: the dictionary is copied into the native file unchecked. Smell: a misspelt `NS...UsageDescription` key or an entitlement with no matching capability. Source: https://docs.expo.dev/versions/v58.0.0/config/app/#infoplist
- **Keep android.versionCode a positive integer that only goes up**: "Version number required by Google Play. Increment by one for each release. Must be a positive integer." Why: Google Play uses it to order releases. Smell: a quoted string, a decimal, or a value lower than the previous release. Source: https://docs.expo.dev/versions/v58.0.0/config/app/#versioncode
- **Do not put the marketing version in ios.buildNumber**: "Transporter will pull the value for `Version Number` from `expo.version` and NOT from `expo.ios.buildNumber`" - `version` is the store-facing number, `buildNumber` identifies the build. Why: the two map to different Info.plist keys. Smell: `buildNumber` bumped for a public release while `version` stays the same. Source: https://docs.expo.dev/versions/v58.0.0/config/app/#buildnumber
- **Decide android.allowBackup on purpose for apps with sensitive data**: "If this is set to false, no backup or restore of the application will ever be performed (this is useful if your app deals with sensitive information)." Why: the Android default is true, so app data goes to the user's Google Drive backup. Smell: an app storing tokens or health data with no `allowBackup` decision recorded. Source: https://docs.expo.dev/versions/v58.0.0/config/app/#allowbackup
- **Treat experiments flags as unstable**: "Enable experimental features that may be unstable, unsupported, or removed without deprecation notices." - each flag (experimental) needs an owner and a reason. Why: an SDK upgrade can remove it with no warning. Smell: several `experiments` flags switched on in one commit with no explanation. Source: https://docs.expo.dev/versions/v58.0.0/config/app/#experiments
- **Know which runtimeVersion applies per platform**: "When both a top level runtime and a platform specific runtime are set, the platform specific one takes precedence." Why: a forgotten platform override keeps old builds and new updates on different runtimes. Smell: the top-level `runtimeVersion` changed while `ios.runtimeVersion` still holds an older value. Source: https://docs.expo.dev/eas-update/runtime-versions/#platform-specific-runtime-version

## Continuous Native Generation and prebuild

- **Never hand-edit generated android and ios directories**: "If you modify the generated directories manually then you risk losing your changes the next time you run `npx expo prebuild --clean`." - express the change as app config or a config plugin. Why: the directories are disposable build output in a CNG project. Smell: a diff touching ios/Podfile, Info.plist or AndroidManifest.xml in a repository that gitignores those folders elsewhere. Source: https://docs.expo.dev/workflow/continuous-native-generation/#usage
- **Do not commit native directories in a CNG project**: "Expo Build will not run Prebuild to avoid overwriting any changes you've made to the native directories." - keep android/ and ios/ in .gitignore. Why: once they are uploaded, app config and plugin changes stop reaching the build. Smell: ios/ or android/ newly tracked while the team still edits app.json expecting it to apply. Source: https://docs.expo.dev/workflow/continuous-native-generation/#usage-with-expo-build
- **Regenerate with --clean**: "This is why using the `--clean` option is the safest way to use the prebuild command and is generally recommended in most cases." Why: without it changes are layered on existing files and "some config plugins aren't idempotent". Smell: a script or README step that runs `npx expo prebuild` with no `--clean` after config changes. Source: https://docs.expo.dev/workflow/continuous-native-generation/#clean
- **Do not run prebuild in a project with hand-maintained native code**: "do not use `npx expo prebuild`, as that may overwrite any manual customizations" Why: manual edits are not represented in config and are lost. Smell: a `prebuild` script added to package.json in a project with committed, customised native folders. Source: https://docs.expo.dev/workflow/continuous-native-generation/#optionality
- **Remove the plugins entry when uninstalling a library**: "which will throw an error when the corresponding node module has been uninstalled" Why: the config no longer resolves and every CLI command fails. Smell: a dependency removed from package.json while its name remains in `plugins`. Source: https://docs.expo.dev/workflow/continuous-native-generation/#how-does-prebuild-help-with-orphaned-code
- **Do not expect app config to drive a project that does not use prebuild**: "then changes in the app config will have no effect" - apply icon, splash and permission changes in the native projects. Why: nothing copies the config into hand-maintained native files. Smell: only app.json changed for an icon or splash update in a bare project. Source: https://docs.expo.dev/develop/user-interface/splash-screen-and-app-icon/#not-using-prebuild
- **Run prebuild --clean when switching app variants locally**: "If a native directory is already present, `expo run` skips regenerating it and compiles it as-is." - set the variant variable on both the prebuild and the run command. Why: the old bundle identifier and name stay in the generated project. Smell: a script that changes `APP_VARIANT` and calls `expo run:ios` directly. Source: https://docs.expo.dev/build-reference/variants/#build-and-run-multiple-app-variants-locally

## Config plugins

- **Keep plugins synchronous with serialisable output**: "Plugins should be synchronous and their return value should be serializable" - mods are the only exception. Why: plugins run during config evaluation, which every CLI command performs. Smell: an `async` plugin function, or a plugin that stores a class instance on the config. Source: https://docs.expo.dev/config-plugins/introduction/#characteristics-of-a-config-plugin
- **Change app config outside mods**: "any modifications made to app config in a config plugin should be outside of a mod to ensure that they are executed in non-prebuild configuration scenarios" Why: mods only run during the syncing phase of prebuild. Smell: `config.ios.infoPlist` or `config.extra` assigned inside a `withInfoPlist` callback. Source: https://docs.expo.dev/config-plugins/introduction/#characteristics-of-a-config-plugin
- **Order the plugins array deliberately**: "Each plugin in the chain runs in the order it appears, with the output of one plugin becoming the input for the next." Why: a plugin that depends on another's output must come after it. Smell: an alphabetical re-sort of `plugins` in a formatting commit. Source: https://docs.expo.dev/config-plugins/plugins/#chaining-config-plugins
- **Rebuild after adding or changing a plugin**: "The changes don't take effect until you rebuild the native project, for example, with Xcode." Why: plugins only alter generated native files. Smell: a plugin option changed and then shipped as an OTA update only. Source: https://docs.expo.dev/config-plugins/plugins/#using-a-config-plugin
- **Reach for withDangerousMod last**: "dangerous mods serve as an escape hatch for modifications that cannot be achieved through existing mod plugins" - check for `withAndroidManifest`, `withInfoPlist`, `withPodfile` and friends first. Why: string edits to native files do not compose with other plugins. Smell: `withDangerousMod` reading and regex-replacing AndroidManifest.xml. Source: https://docs.expo.dev/config-plugins/dangerous-mods/
- **Write dangerous mods so a second run changes nothing**: "Unlike standard mods, which can run multiple times safely, dangerous mods are rarely guaranteed to be idempotent." - check whether the edit is already present before inserting. Why: a prebuild without `--clean` applies the mod again. Smell: an unconditional `contents.replace(anchor, anchor + addition)`. Source: https://docs.expo.dev/config-plugins/dangerous-mods/#why-are-they-considered-dangerous
- **Retest dangerous mods on every SDK upgrade**: "Be careful using `withDangerousMod` as it is subject to change in the future." - the docs label the API experimental and prone to breakage. Why: the native template text that a regex anchors on changes between SDKs. Smell: an SDK bump PR with no mention of the project's dangerous mods. Source: https://docs.expo.dev/config-plugins/dangerous-mods/#considerations-when-using-a-dangerous-mod
- **Keep mods fast and offline**: "Avoid performing long-running tasks like making network requests or installing Node modules in mods." Why: mods run on every prebuild, including on build workers. Smell: `fetch`, `execSync('npm install ...')` or a file download inside a mod. Source: https://docs.expo.dev/config-plugins/development-and-debugging/#best-practices-for-mods
- **Create, move or delete files only in dangerous mods**: "Generate, move, and delete new files in dangerous mods only." Why: introspection runs other mods expecting no file system writes. Smell: `fs.writeFileSync` inside `withInfoPlist` or at the top level of a plugin. Source: https://docs.expo.dev/config-plugins/development-and-debugging/#best-practices-for-mods
- **Import plugin helpers from the expo package**: "The `expo/config-plugins` and `expo/config` packages are re-exported from the `expo` package." - import `expo/config-plugins`, not the scoped package. Why: a directly installed copy can be an incompatible version, or unresolvable under pnpm and Yarn Berry. Smell: `require('@expo/config-plugins')` in a plugin file or as a direct dependency. Source: https://docs.expo.dev/config-plugins/development-and-debugging/#import-the-config-plugins-package

## Development builds and Expo Go

- **Do not plan a production app around Expo Go**: "It's limited and not useful for building production-grade projects, so most apps will convert to using development builds." Why: Expo Go ships a fixed set of native libraries and cannot take the project's native configuration. Smell: release documentation or QA steps that tell testers to open the app in Expo Go. Source: https://docs.expo.dev/develop/development-builds/faq/#why-use-a-development-build-aka-what-cant-you-do-in-expo-go-and-why
- **Move to a development build when adding a library with native code**: "There is no way to get the native code into the Expo Go app unless it was already included in the bundle that was uploaded to the app stores." Why: the JS loads, then fails at the first native call. Smell: a native dependency added while the `start` workflow still targets Expo Go. Source: https://docs.expo.dev/develop/development-builds/faq/#use-libraries-with-native-code-that-arent
- **Guard Updates API calls outside release builds**: "This method cannot be used in development mode, and the returned promise will be rejected if you try to do so." - check `__DEV__` or `Updates.isEnabled` and catch rejections. Why: `checkForUpdateAsync` and `fetchUpdateAsync` also reject in Expo Go and when `expo-updates` is not enabled. Smell: an unguarded `await Updates.checkForUpdateAsync()` in a startup effect. Source: https://docs.expo.dev/versions/v58.0.0/sdk/updates/#updatescheckforupdateasync

## Dependencies and autolinking

- **Install libraries with npx expo install**: "We recommend always using `npx expo install` instead of `npm install` or `yarn add` directly" Why: Expo CLI picks a version compatible with the SDK and warns about known incompatibilities. Smell: a version of an `expo-*` or core React Native library in package.json that differs from the SDK's expected range. Source: https://docs.expo.dev/workflow/using-libraries/#installing-a-third-party-library
- **Run npx expo install --check in CI**: "It exits with non-zero in Continuous Integration (CI)." - use `--check` in pipelines and `--fix` locally. Why: it turns version drift into a failing check. Smell: a pipeline with no dependency validation step after a dependency bump. Source: https://docs.expo.dev/more/expo-cli/#version-validation
- **Justify each expo.install.exclude entry**: "you can exclude it from the version checks" Why: an excluded package no longer triggers version warnings from `expo start`, `expo-doctor` or `expo install`. Smell: a growing `exclude` list with no comment in the PR on why each version was pinned. Source: https://docs.expo.dev/versions/v58.0.0/config/package-json/#installexclude
- **Deduplicate native modules**: "your JavaScript bundle may contain both versions of the native module, while autolinking and your native app will only contain one version" - `expo-doctor` lists the duplicates. Why: the mismatch can crash at runtime, and it is common in monorepos and with isolated dependencies. Smell: a lockfile change that introduces a second copy of a native library under a nested node_modules. Source: https://docs.expo.dev/modules/autolinking/

## Environment variables

- **Never put secrets in EXPO_PUBLIC_ variables**: "These variables will be visible in plain-text in your compiled application." Why: the value is inlined into the JavaScript bundle that every user downloads. Smell: `EXPO_PUBLIC_STRIPE_SECRET_KEY`, `EXPO_PUBLIC_DB_PASSWORD` or any private key behind the prefix. Source: https://docs.expo.dev/guides/environment-variables/#reading-environment-variables-from-env-files
- **Reference each variable as process.env.EXPO_PUBLIC_NAME**: "`process.env['EXPO_PUBLIC_KEY']` or `const {EXPO_PUBLIC_X} = process.env` is invalid and will not be inlined" Why: inlining only matches static dot notation. Smell: destructuring `process.env`, a computed key, or passing `process.env` into a helper. Source: https://docs.expo.dev/guides/environment-variables/#how-to-read-from-environment-variables
- **Use only the standard .env file names**: "In SDK 58 and later, Expo commands don't load other **.env** files, such as **.env.staging** or **.env.test**." - move those values into `.env`, `.env.development`, `.env.production` or their `.local` forms. Why: a non-standard file is ignored without an error. Smell: a new `.env.staging` file, or a script that depends on one. Source: https://docs.expo.dev/guides/environment-variables/#using-multiple-env-files-to-define-separate-environments
- **Do not set NODE_ENV to choose an environment**: "In SDK 58 and later, each command sets `NODE_ENV` to its mode and replaces any value you set." Why: the command decides between development and production, so the prefix has no effect on which .env files load. Smell: `NODE_ENV=staging npx expo start` or `NODE_ENV=test eas update` in scripts. Source: https://docs.expo.dev/guides/environment-variables/#environment-variables-and-node_env
- **Gitignore local env files**: "generally **.env.local** files should be added to your **.gitignore**" - the documented pattern is `.env*.local`. Why: they hold machine-specific values. Smell: `.env.local` or `.env.production.local` appearing in a diff. Source: https://docs.expo.dev/guides/environment-variables/#using-multiple-env-files-to-define-separate-environments
- **Do not rely on secret visibility for values that end up in the app**: "Secrets do not provide any additional security for values that you end up embedding in your application itself." Why: secret visibility protects job inputs such as an npm token, not bundle contents. Smell: a secret variable mapped into `extra` or renamed to an `EXPO_PUBLIC_` value during the build. Source: https://docs.expo.dev/eas/environment-variables/#visibility-settings-for-environment-variables
- **Do not give EXPO_PUBLIC_ variables secret visibility**: "Avoid setting excessive secret visibility to `EXPO_PUBLIC_` variables that are used in your app's JavaScript code or are used to resolve your app's configuration." Why: secret values cannot be read outside Expo servers, so local config resolution and `eas update` bundling cannot see them. Smell: `eas env:create --visibility secret` for a variable read by app.config.ts. Source: https://docs.expo.dev/eas/environment-variables/faq/#use-correct-visibility-settings
- **Keep passwords out of the eas.json env block**: "It should only be used for values that you would commit to your git repository" Why: eas.json is committed. Smell: `SENTRY_AUTH_TOKEN`, `NPM_TOKEN` or an API secret under `build.<profile>.env`. Source: https://docs.expo.dev/eas/json/#env
- **Do not expect build-profile env values during eas update**: "Environment variables set on the `env` field in build profiles are not available when you run `eas update`." Why: the update bundle would be built with different values from the binary it targets. Smell: an `EXPO_PUBLIC_API_URL` defined only under `build.production.env` in a project that publishes updates. Source: https://docs.expo.dev/build/updates/#environment-variables-and-eas-update
- **Pass --environment to eas update**: "the `--environment` flag is required when running `eas update`" - on SDK 55 and later. Why: only the named Expo Services environment is used and local .env files are ignored, which keeps updates and builds aligned. Smell: a CI step running `eas update --channel production` with no `--environment`. Source: https://docs.expo.dev/eas/environment-variables/usage/#using-environment-variables-with-expo-update
- **Set environment explicitly on every build profile**: "to ensure that the correct environment variables are always used for your build jobs" - set `environment` on each profile in eas.json. Why: otherwise it is inferred from `distribution` and `developmentClient`, which can surprise custom profiles. Smell: a `staging` profile with no `environment` that silently receives the preview variables. Source: https://docs.expo.dev/eas/environment-variables/faq/#explicitly-specify-the-environment-for-your-builds
- **Define build variables on Expo servers, not only in the CI provider**: "Environment variables must be defined on Expo servers to be made available to Expo Build builders." Why: variables set in the CI job exist only on the machine that calls `eas build`. Smell: a workflow that exports a variable before `eas build` and expects native build steps to read it. Source: https://docs.expo.dev/eas/environment-variables/faq/
- **Supply untracked secret files through file environment variables**: "instead of adding it to your project archive" - a file that contains secrets belongs in a file environment variable. Why: a `!`-prefixed entry in .easignore uploads the file with the project. Smell: `!google-services.json` or `!.env.production` in .easignore. Source: https://docs.expo.dev/build-reference/easignore/#adding-files-to-your-project-upload-with-easignore

## Splash screen and app icon

- **Use a .png splash icon**: "If you use another image format, making a production build of your app will fail." Why: only .png is supported for the splash icon. Smell: a .jpg, .webp or .svg path in the `expo-splash-screen` plugin options. Source: https://docs.expo.dev/develop/user-interface/splash-screen-and-app-icon/#export-the-splash-icon-as-a-png
- **Verify splash changes in a preview or production build**: "Development builds include `expo-dev-client`, which has its own splash screen and may cause conflicts." Why: Expo Go shows the app icon in place of the configured splash. Smell: a splash change approved from an Expo Go or development build screenshot. Source: https://docs.expo.dev/develop/user-interface/splash-screen-and-app-icon/#splash-screen
- **Supply an exactly square iOS icon**: "The icon must be exactly square. For example, a 1023x1024 icon is not valid." Why: icon generation and store validation reject other shapes. Smell: a replaced icon asset whose width and height differ. Source: https://docs.expo.dev/develop/user-interface/splash-screen-and-app-icon/#ios

## Permissions and privacy

- **Configure permissions at build time**: "require native build-time configuration before they can be requested using runtime JavaScript code" - this applies to standalone and development builds. Why: a runtime request with no manifest or Info.plist entry fails outside Expo Go. Smell: a new `requestPermissionsAsync()` call with no matching plugin option or `infoPlist` key. Source: https://docs.expo.dev/guides/permissions/
- **Write specific iOS usage descriptions**: "These default messages will most likely need to be tailored to your specific use case for your app to be accepted by the App Store." Why: boilerplate reasons are a documented rejection risk. Smell: a camera or location plugin added with no permission text option and no `NS...UsageDescription` override. Source: https://docs.expo.dev/guides/permissions/#ios
- **Remove unwanted Android permissions with blockedPermissions**: "To do this, specify the **full permission name**." - `android.blockedPermissions` is the only way to remove a permission that a package-level manifest adds. Why: omitting a permission from `android.permissions` does not remove what a library merges in. Smell: `RECORD_AUDIO` deleted from `permissions` in the belief that it is gone, or a short name such as `'CAMERA'` in the blocked list. Source: https://docs.expo.dev/guides/permissions/#android
- **Ship Info.plist changes in a new binary**: "Changes to the **Info.plist** cannot be updated over-the-air, they will only be deployed when you submit a new native binary." Why: usage strings live in native configuration. Smell: an OTA update that starts requesting a permission whose description is not in the installed build. Source: https://docs.expo.dev/guides/permissions/#ios
- **Declare required-reason APIs in ios.privacyManifests**: "You may need to include the required reasons for the APIs used by those dependencies" Why: Apple does not correctly parse the PrivacyInfo files of static CocoaPods dependencies; the guide notes its steps are still in development. Smell: a new native iOS dependency with a PrivacyInfo.xcprivacy file and no review of `privacyManifests`. Source: https://docs.expo.dev/guides/apple-privacy/#including-required-reasons-for-expo-sdk-packages-and-other-third-party-libraries

## App versions

- **Bump the user-facing version yourself for each release**: "the user-facing version should be explicitly set and updated by you" Why: it is the store-visible version and, under the appVersion policy, the runtime version too. Smell: a production release branch in which `version` is unchanged from the previous store release. Source: https://docs.expo.dev/build-reference/app-versions/#user-facing-version
- **Automate build numbers with the remote source and autoIncrement**: "One common cause for app store rejections is submitting a build with a duplicate version number." - set `cli.appVersionSource` to `remote` and `autoIncrement` on the production profile. Why: a forgotten manual bump is caught only at upload. Smell: hand-edited `versionCode` and `buildNumber` in every release commit. Source: https://docs.expo.dev/build-reference/app-versions/#developer-facing-build-version
- **Stop editing build numbers in app config once the source is remote**: "the build version values stored in app config are ignored and not updated when the version is incremented remotely" - remove them, or read the real value with `expo-application`. Why: the stale numbers mislead readers and any code that reads them. Smell: a PR that bumps `ios.buildNumber` in app.json while eas.json sets the remote source. Source: https://docs.expo.dev/build-reference/app-versions/#remote-version-source
- **Set cli.appVersionSource explicitly**: "If you omit this field, EAS CLI warns that it will be required in the future and uses local." Why: the implicit default is the manual workflow. Smell: an eas.json with `autoIncrement` and no `appVersionSource`. Source: https://docs.expo.dev/eas/json/#appversionsource
- **Do not combine remote versions with the nativeVersion runtime policy**: "It's not supported if you are using Expo Update and runtime policy set to" - the nativeVersion policy; the docs point to the appVersion policy for similar behaviour. Why: the runtime version would depend on numbers that are no longer in the project. Smell: the remote source in eas.json together with `policy: 'nativeVersion'` in app config. Source: https://docs.expo.dev/build-reference/app-versions/#limitations
- **Commit the bump when autoIncrement uses the local source**: "you need to commit your changes on every build if you want the version change to persist" Why: otherwise the next build reuses the same number. Smell: CI running `eas build` with local `autoIncrement` and no commit-back step. Source: https://docs.expo.dev/build-reference/app-versions/#limitations-1
- **Read the installed version with expo-application**: "instead of depending on values from app config" - the docs recommend `expo-application` for reading the version. Why: in projects with native directories the native values take precedence and can differ from the manifest. Smell: `Constants.expoConfig.version` shown on an about screen or sent with bug reports. Source: https://docs.expo.dev/build-reference/app-versions/#local-version-source

## EAS Build profiles and distribution

- **Never route a development profile to a store**: "These builds include developer tools, and they are never submitted to an app store." Why: a development client build is a debug binary. Smell: `--auto-submit` used with a profile that has `developmentClient: true`, or a submit profile that extends from it. Source: https://docs.expo.dev/build/eas-json/#development-builds
- **Do not set buildType apk on a store profile**: "but cannot be submitted to the Google Play Store" Why: Google Play requires app bundles for new apps. Smell: `android.buildType: 'apk'` under the production profile. Source: https://docs.expo.dev/submit/android/#build-a-production-app
- **Make internal distribution profiles produce an installable APK**: "or it won't be directly installable on an Android device" - a custom `gradleCommand` on an internal profile must produce an APK. Why: an AAB can only be distributed through the Play Store. Smell: an internal profile with `gradleCommand: ':app:bundleRelease'`. Source: https://docs.expo.dev/build/internal-distribution/#using-internal-distribution
- **Treat internal build URLs as public unless sign-in is required**: "By default, internal distribution build URLs are available to anybody with the URL" Why: anyone holding the link can install the build. Smell: internal build links posted to public issue trackers or stored in public CI logs. Source: https://docs.expo.dev/build/internal-distribution/#using-internal-distribution
- **Refresh the ad hoc profile in non-interactive iOS builds**: "The build can succeed, but the app may not install on registered devices added after the profile was last updated." - pass `--refresh-ad-hoc-provisioning-profile` with `--non-interactive` (EAS CLI 19.1.0 or later). Why: CI reuses the existing provisioning profile and its device list. Smell: a CI internal distribution build step with `--non-interactive` only. Source: https://docs.expo.dev/build/internal-distribution/#automation-on-ci-optional
- **Replace the deprecated releaseChannel field**: "which is only supported in SDK 49 and lower" - use `channel`. Why: `releaseChannel` (deprecated) belongs to the Classic Updates service. Smell: `releaseChannel` in a build profile of a current SDK project. Source: https://docs.expo.dev/eas/json/#releasechannel
- **Give each app variant its own identifier**: "the different Application IDs or Bundle Identifiers are set for each variant" - switch `android.package` and `ios.bundleIdentifier` on the variant variable. Why: two variants with the same identifier replace each other on a device. Smell: a new variant in app.config.js that changes only `name`. Source: https://docs.expo.dev/build-reference/variants/#convert-appjson-to-appconfigjs
- **Avoid applicationIdSuffix when EAS must detect the application ID**: "If you use `applicationIdSuffix` inside `productFlavors` or `buildTypes` sections then this value will not be detected correctly." - set a full `applicationId` per flavour. Why: EAS CLI currently supports only the `applicationId` field. Smell: `applicationIdSuffix '.dev'` in android/app/build.gradle of a project built with EAS. Source: https://docs.expo.dev/build-reference/variants/#android
- **Copy .gitignore into a new .easignore**: "If you create a **.easignore** file, EAS CLI uses it instead of all **.gitignore** files in your repository." Why: anything not listed again, including local env files and credentials, is uploaded. Smell: a short .easignore containing only the extra exclusions. Source: https://docs.expo.dev/build-reference/easignore/
- **Authenticate CI with EXPO_TOKEN from the secret store**: "This is possible by storing a personal access token in the `EXPO_TOKEN` environment variable in the CI settings." Why: the token grants access to the Expo account. Smell: a token literal in a workflow file, or `eas login` with a password in CI. Source: https://docs.expo.dev/build/building-on-ci/

## Credentials and signing

- **Never commit a release keystore**: "Under no circumstances should you check it into your repository." - debug keystores are the documented exception. Why: the keystore signs every store upload. Smell: a `.jks` or `.keystore` file other than the debug keystore in a diff. Source: https://docs.expo.dev/app-signing/app-credentials/#app-signing-by-google-play
- **Gitignore credentials.json and the files it references**: "Remember to add **credentials.json** and all of your credentials to **.gitignore**" Why: it holds keystore and certificate passwords in plain text. Smell: credentials.json, a `.p12` or a `.mobileprovision` file tracked by git. Source: https://docs.expo.dev/app-signing/local-credentials/#credentialsjson
- **Keep signing passwords out of the project's gradle.properties**: "Instead, create a **~/.gradle/gradle.properties** file on your computer and add the above variables to this file." Why: android/gradle.properties is committed when the android directory is. Smell: `MYAPP_UPLOAD_STORE_PASSWORD=` with a real value in android/gradle.properties. Source: https://docs.expo.dev/guides/local-app-production/#update-gradle-variables
- **Back up the Android keystore and its passwords**: "We recommend downloading and backing up your keystore and keystore password to a secure location." Why: without App signing by Google Play a lost keystore means the app can never be updated. Smell: a signing setup change with no record of where the backup lives. Source: https://docs.expo.dev/app-signing/security/
- **Do not revoke an APN key that other apps use**: "If you revoke an APN key, all apps that rely on that key will no longer be able to send or receive push notifications" Why: one key can serve any number of apps and revocation takes effect at once. Smell: a credentials clean-up task that revokes push keys without listing the dependent apps. Source: https://docs.expo.dev/app-signing/app-credentials/#push-notification-keys
- **Keep the update code signing private key outside the repository**: "The generated private key must be kept private and secure." - commit only the certificate. Why: whoever holds the key can sign updates that the app will accept. Smell: `private-key.pem` under the project root, or a `--key-output-directory` inside the repository. Source: https://docs.expo.dev/eas-update/code-signing/#generate-a-private-key-and-corresponding-certificate

## Store submission

- **Match the bundle identifier to the registered App ID**: "Check your Bundle Identifier and make sure it is exactly same as the one you have created in the Identifiers in Apple Developer Dashboard." Why: App Store Connect rejects an upload whose identifier matches no registered app. Smell: `ios.bundleIdentifier` changed in a release branch of an app that is already published. Source: https://reactnative.dev/docs/publishing-to-app-store#2-build-app-for-release
- **Build iOS store binaries with the Release configuration**: "Building an app for distribution in the App Store requires using the `Release` scheme in Xcode." Why: Release disables the in-app Dev Menu and bundles the JavaScript locally. Smell: a shared Xcode scheme whose Archive or Run action is set to Debug in a release change. Source: https://reactnative.dev/docs/publishing-to-app-store#1-configure-release-scheme
- **Do not commit a Google service account key**: "If you omit this field, Expo Submit uses the key that is assigned to your app on Expo servers." - leave `serviceAccountKeyPath` out, or point it at a path supplied through an environment variable. Why: the key can act on the Play Console on the project's behalf. Smell: `serviceAccountKeyPath: './play-key.json'` with that JSON file tracked by git. Source: https://docs.expo.dev/eas/json/#serviceaccountkeypath
- **Review any Android submit profile that sets a track**: "This also requires the `releaseStatus` to be set to `completed`" - and `completed` on the `production` track releases to all users as soon as the upload finishes. Why: a public release cannot be undone. Smell: `track: 'production'` with `releaseStatus: 'completed'` on a profile used by `--auto-submit`. Source: https://docs.expo.dev/build/automate-submissions/#android-submissions
- **Do not treat an iOS auto-submit as a store release**: "The release to Apple App Store review is a manual process." Why: `--auto-submit` uploads to TestFlight only. Smell: a release script that announces availability straight after the submit step. Source: https://docs.expo.dev/build/automate-submissions/#ios-submissions
- **Keep the app usable on iPad even when it targets phones**: "your app will still render at phone resolution on iPads and must be usable" Why: Apple may reject an app whose elements do not render properly on an iPad. Smell: `supportsTablet: false` taken as a reason to skip iPad testing before submission. Source: https://docs.expo.dev/distribution/app-stores/#responsive-design

## EAS Update

- **Ship native changes as a new binary, not an update**: "Change to native code or native dependencies" - listed with permission changes and SDK upgrades as cases that Expo Update cannot deliver. Why: an update replaces only JavaScript, styling and assets. Smell: an OTA release note that includes a new native library or a permission change. Source: https://docs.expo.dev/eas-update/introduction/#when-to-use-expo-update
- **Make a new build before publishing after native changes**: "any time native code is updated, we're required to make a new build before publishing an update" - and give that build a new runtime version. Why: an update that calls native code missing from the installed build fails on launch. Smell: a dependency with native code added while `runtimeVersion` and `version` stay unchanged. Source: https://docs.expo.dev/eas-update/runtime-versions/
- **Bump version with every native change under the appVersion policy**: "if you forget to bump the app version when changing the native runtime, then you'll have a runtime version mismatch" Why: the policy derives the runtime from `version` alone. Smell: a production build created from a branch with new native modules and the old `version`. Source: https://docs.expo.dev/eas-update/runtime-versions/#use-a-runtime-version-policy-that-automatically-updates-the-runtime-version-when-native-code-is-updated
- **Treat the fingerprint runtime policy as experimental**: "policy is experimental and not yet widely recommended" - the documented default recommendation is the appVersion policy. Why: fingerprint behaviour may still change. Smell: `policy: 'fingerprint'` adopted for production with no staged trial. Source: https://docs.expo.dev/eas-update/deployment/#runtime-version-configuration
- **Publish for the exact runtime version of the target builds**: "The runtime version of the build and the target runtime version of an update must match exactly." Why: a mismatched update is never offered to the build. Smell: a hotfix published from main after `version` was already bumped for the next release. Source: https://docs.expo.dev/eas-update/how-it-works/#matching-updates-and-builds
- **Fix the channel before creating a build**: "you cannot change the channel embedded in a build after you create it" Why: a wrong channel can only be corrected with a new build; runtime channel surfing exists on SDK 54 and later. Smell: a production profile whose `channel` still says `preview`. Source: https://docs.expo.dev/eas-update/deployment/
- **Set channel on custom-named build profiles**: "Set them manually if you use different profile names." Why: `eas update:configure` fills in only `preview` and `production`. Smell: a `staging` or `beta` build profile with no `channel`. Source: https://docs.expo.dev/eas-update/getting-started/#configure-the-update-channel
- **Promote the verified bundle, do not rebuild it**: "This will ensure the exact same bundle that you tested in staging is used in production." - use `eas update:republish --destination-channel production`. Why: a fresh `eas update` can pick up different code or variables. Smell: a production step that reruns `eas update` from a later commit than the one tested. Source: https://docs.expo.dev/eas-update/deployment/#deploying-to-production
- **Publish with the variant's variables**: "you should be cautious to set the correct environment variables for the app variant that you are publishing for" Why: app.config is re-evaluated at publish time and variant switches depend on those variables. Smell: `eas update` in CI with no `APP_VARIANT` while builds set one. Source: https://docs.expo.dev/build-reference/variants/#using-production-variant
- **Check persistent state before rolling back**: "your broken update may, for example, have modified persistent state" Why: older code may not read data that the broken update migrated. Smell: a rollback run straight after an update that changed a storage schema. Source: https://docs.expo.dev/eas-update/error-recovery/#help-i-published-a-broken-update-to-production-what-should-i-do
- **Check for updates soon after launch**: "we highly recommend that your app check for updates very shortly after launching" Why: errors thrown more than 10 seconds after first render do not trigger error recovery. Smell: `checkAutomatically: 'NEVER'` with a manual check that only runs deep inside the app. Source: https://docs.expo.dev/eas-update/error-recovery/#catching-an-error
- **Do not rely on built-in error recovery as a release safeguard**: "The behavior documented below is subject to change and should not be relied upon." Why: it is a last resort and users can still see a crash. Smell: untested updates sent straight to production on the assumption that recovery will catch failures. Source: https://docs.expo.dev/eas-update/error-recovery/
- **Do not block startup on downloading the latest update**: "We recommend against this strategy because the resulting user experience is extremely poor." Why: users on slow networks wait on the splash screen or give up. Smell: an awaited `fetchUpdateAsync()` then `reloadAsync()` in the root component before first render with no timeout. Source: https://docs.expo.dev/eas-update/download-updates/#what-if-i-want-to-always-block
- **Verify assets when assetPatternsToBeBundled is set**: "You have to be certain that assets not included in updates are built into the native build of the app." - run `npx expo-updates assets:verify`. Why: unmatched assets are not uploaded, so an update that references a new one shows nothing. Smell: a new image imported in an OTA change while the patterns exclude its folder. Source: https://docs.expo.dev/eas-update/asset-selection/#verifying-that-an-update-includes-all-required-app-assets
- **Keep updates within store rules**: "your updates need to follow the App Store and Play Store guidelines" Why: changes to app behaviour usually need review, and an update does not exempt them. Smell: a feature that changes the app's purpose released by update only. Source: https://docs.expo.dev/eas-update/introduction/#what-guidelines-must-i-follow-when-publishing
- **Register the root with registerRootComponent in apps that use updates**: "If you do not use `registerRootComponent`, your assets may not be available in release builds." Why: Expo configures asset loading for updates through it. Smell: `AppRegistry.registerComponent` in index.js of a project with `expo-updates` installed. Source: https://docs.expo.dev/eas-update/getting-started/

## Upgrading the Expo SDK and React Native

- **Upgrade one SDK version at a time**: "We recommend upgrading SDK versions incrementally, one at a time." Why: it isolates which release introduced a breakage. Smell: one PR that moves `expo` across two or more major versions. Source: https://docs.expo.dev/workflow/upgrading-expo-sdk-walkthrough/
- **Align dependencies and run the doctor after bumping expo**: "Upgrade all dependencies to match the installed SDK version." - then run `expo-doctor`. Why: libraries left on the previous SDK's versions cause native build and runtime errors. Smell: an upgrade PR that changes only the `expo` line in package.json. Source: https://docs.expo.dev/workflow/upgrading-expo-sdk-walkthrough/#upgrade-dependencies
- **Delete generated native directories after an SDK upgrade**: "Delete the **android** and **ios** directories if you generated them for a previous SDK version" - in a CNG project. Why: they were generated from the old template. Smell: an upgrade tested against a local ios/ folder that predates the bump. Source: https://docs.expo.dev/workflow/upgrading-expo-sdk-walkthrough/#update-native-projects
- **Move react-native, react and expo together**: "requires updating the `react-native`, `react`, and `expo` package versions in your `package.json` file" Why: each SDK targets one React Native and React pair (SDK 58 with React Native 0.88). Smell: `react-native` bumped alone in an Expo project. Source: https://reactnative.dev/docs/upgrading#expo-projects
- **Apply template changes by hand in projects without CNG**: "In case there are changes you need to manually apply them into your project." - use the Upgrade Helper diff between the two versions. Why: native project files are not regenerated. Smell: a React Native bump with no changes under ios/ or android/ when the helper lists some. Source: https://reactnative.dev/docs/upgrading#3-upgrade-your-project-files

## Local release builds, Metro and TypeScript

- **Test locally in the Release configuration before shipping**: "You can combine this with `--configuration Release` to create a production simulator build" - `npx expo run:ios --configuration Release`.
