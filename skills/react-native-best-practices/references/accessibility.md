# React Native code-review rules: accessibility

Extracted 2026-11-12 from the React Native 0.88 documentation (facebook/react-native-website, CC BY 4.0) and the Expo SDK 58 documentation (expo/expo, MIT). One rule per bullet, one source link each. Quotations are short excerpts; the rest is original.

## Accessible elements and labels

- **Mark a custom touch target as `accessible`**: "By default, all touchable elements are accessible." - [WCAG 4.1.2] that default covers `Pressable`, `Button` and the `Touchable*` family only; a plain `View` wired up with responder or gesture handlers needs `accessible={true}` itself. Why: without it the control is not exposed to VoiceOver or TalkBack as an element at all. Smell: a `View` with `onTouchEnd`, `onStartShouldSetResponder` or a gesture detector around it and no `accessible` prop. Source: https://reactnative.dev/docs/accessibility#accessible
- **Do not nest accessible elements and expect both to take focus**: "this does not necessarily mean that the view will be focused by VoiceOver or TalkBack" - the docs name the causes: "VoiceOver disallowing nested accessibility elements" and TalkBack choosing a parent instead. Keep one accessible element per focus stop. Why: the inner control becomes unreachable on one platform and reachable on the other. Smell: a `Pressable` row that contains a second `Pressable` (for example a delete icon), both left at the default. Source: https://reactnative.dev/docs/accessibility#accessible
- **Put `accessible` on the exact view that should take focus**: "accessibility focus is only available on the first child view with the `accessible` property, and not for the parent or sibling without `accessible`" - the prop is not inherited by siblings or parents, so decide per view which one is the focus stop. Why: a wrapper that was meant to read as one unit is skipped, or its parts are read one by one. Smell: a card whose title, price and badge are each focusable when the design calls for one summary, or a wrapper expected to group children with no `accessible` on it. Source: https://reactnative.dev/docs/accessibility#accessible
- **Label every accessible element that has no readable text**: "it is a good practice to set an `accessibilityLabel` on the view, so that people who use VoiceOver or TalkBack know what element they have selected" - [WCAG 4.1.2] icon-only buttons, image buttons and custom controls need a label. Why: "A screen reader will verbalize this string when the associated element is selected." Smell: a `Pressable` whose only child is an icon or `Image`, with no `accessibilityLabel` or `aria-label`. Source: https://reactnative.dev/docs/accessibility#accessibilitylabel
- **Check what the default label reads before adding one**: "The label is constructed by concatenating all Text node children separated by spaces." - a touchable with clear text children already has a label; add `accessibilityLabel` only when the concatenation reads badly. Why: a redundant label drifts from the visible text, and a bad concatenation reads fragments such as a currency symbol and digits as separate words. Smell: `accessibilityLabel` that repeats the child `Text` word for word, or a touchable with several small `Text` nodes that only make sense visually. Source: https://reactnative.dev/docs/accessibility#accessibilitylabel
- **Keep an overriding label in step with the visible content**: "Overrides the text that's read by the screen reader when the user interacts with the element." - once a label is set the child text is no longer read, so the label has to carry every changing value the children show. Why: the screen reader announces a stale or shorter message than the screen displays. Smell: a static `accessibilityLabel` string on a row whose children render a count, price, status or name from props. Source: https://reactnative.dev/docs/view#accessibilitylabel
- **Treat `accessibilityLabelledBy` as Android only**: "The value of `accessibilityLabelledBy` should match the `nativeID` of the related element" - [WCAG 1.3.1] the heading carries the Android label, so the field still needs its own `accessibilityLabel` for VoiceOver. Why: on iOS the association is not made and the input is announced without its visible label. Smell: a `TextInput` with `accessibilityLabelledBy` and no label of its own, or a value that matches no `nativeID` in the same screen. Source: https://reactnative.dev/docs/accessibility#accessibilitylabelledby-android
- **Add a hint when the label does not say what will happen**: "when it is not clear from the accessibility label alone" - use `accessibilityHint` to describe the result of the action, not to repeat the label. Why: the hint exists "to provide additional context to the user on the result of the action". Smell: a hint identical to the label, or an ambiguous control such as a bare chevron or a row that opens a different screen with no hint. Source: https://reactnative.dev/docs/accessibility#accessibilityhint
- **Never put essential information only in a hint**: "if the user has hints enabled in the device's VoiceOver settings" - on iOS the hint is read only when the user has hints switched on, so required information belongs in the label, value or state. Why: VoiceOver users with hints off never hear it. Smell: a destructive action, a price or a required-field notice that appears only in `accessibilityHint`. Source: https://reactnative.dev/docs/accessibility#accessibilityhint
- **Set `accessibilityLanguage` on foreign-language content, knowing it is iOS only**: "the screen reader will understand which language to use while reading the element's" - [WCAG 3.1.2] label, value and hint are then read in that language; the value is a BCP 47 tag such as `it-IT`. Why: VoiceOver otherwise reads the text with the device language's pronunciation; Android gets no effect from this prop. Smell: a language picker, a quoted phrase or user content in another language with no `accessibilityLanguage`, or a value like `italian`. Source: https://reactnative.dev/docs/accessibility#accessibilitylanguage-ios
- **Exempt photos and media from colour inversion on iOS**: "If there's a view you don't want to invert when this setting is on, possibly a photo, set this property to `true`." - apply `accessibilityIgnoresInvertColors` to photos, video and maps. iOS only. Why: with inversion on, images render as negatives. Smell: a full-bleed `Image`, avatar or video view with no `accessibilityIgnoresInvertColors`. Source: https://reactnative.dev/docs/accessibility#accessibilityignoresinvertcolors-ios
- **Pair the large content title with its switch**: "Requires `accessibilityShowsLargeContentViewer` to be set to `true`." - `accessibilityLargeContentTitle` does nothing alone. iOS only, and "Available in iOS 13.0 and later." Why: the long-press viewer for items that cannot grow with text size never appears. Smell: `accessibilityLargeContentTitle` on a tab bar item without `accessibilityShowsLargeContentViewer`. Source: https://reactnative.dev/docs/accessibility#accessibilitylargecontenttitle-ios
- **Give informative images `alt` text**: "Using this will automatically mark this element as accessible." - [WCAG 1.1.1] `alt` both names the image and exposes it; an `Image` is not an accessibility element by default. Why: without it the image is invisible to the screen reader and its information is lost. Smell: an `Image` that conveys content (a chart, a product photo, a status icon) with neither `alt` nor `accessible` plus `accessibilityLabel`. Source: https://reactnative.dev/docs/image#alt
- **Give a `Button` an `accessibilityLabel` when its title is not enough**: "Text to display for blindness accessibility features." - [WCAG 4.1.2] use it when the title is a symbol, an abbreviation or only meaningful next to other content. Why: the title alone is what gets read otherwise. Smell: `title` of `+`, `OK` or `x` on a `Button` with no `accessibilityLabel`. Source: https://reactnative.dev/docs/button#accessibilitylabel

## Roles

- **Give every custom control a role**: "communicates the purpose of a component to the user of assistive technology" - [WCAG 4.1.2] set `role` or `accessibilityRole` on any pressable that is not already a `Button`, `Switch` or `TextInput`. Why: without a role the screen reader reads the label with no indication that the element can be activated or what kind of control it is. Smell: a `Pressable` or `TouchableOpacity` with a label and no role. Source: https://reactnative.dev/docs/accessibility#accessibilityrole
- **Use `link` only for things that open a URL**: "For in-app screen navigation or actions, use `button` instead." - `link` is reserved for elements that open an external URL or web page in a browser. Why: users choose how to act on what the role announces, and a link that navigates in-app or submits a form misleads them. Smell: a role of `link` on a row that calls `navigation.navigate` or `router.push`. Source: https://reactnative.dev/docs/accessibility#accessibilityrole
- **Mark section titles as headings**: "Used when an element acts as a header for a content section (e.g. the title of a navigation bar)." - [WCAG 1.3.1] set `accessibilityRole` to `header`, or `role` to `heading`, on screen and section titles. Why: screen reader users move between headings to skim a screen; bold text alone gives them nothing to jump to. Smell: a large bold `Text` at the top of a section with no role. Source: https://reactnative.dev/docs/accessibility#accessibilityrole
- **Give a toggle button its checked state**: "Should be used with accessibilityState checked to indicate if the button is toggled on or off." - a role of `togglebutton` without `accessibilityState` of `checked` is incomplete. Why: the user hears that the control toggles but not which way it is set. Smell: `togglebutton` on a favourite, mute or filter control with the on/off state shown only by icon colour. Source: https://reactnative.dev/docs/accessibility#accessibilityrole
- **Do not set `role` and `accessibilityRole` to different things**: "`role` communicates the purpose of a component and has precedence over the" - `role` wins over `accessibilityRole`, and the two props use different vocabularies (`heading` and `header`, `img` and `image`, `slider` and `adjustable`, `searchbox` and `search`). Why: the losing prop is silently ignored, and a value from the wrong list is not a valid role. Smell: both props on one element, `role` of `header`, or `accessibilityRole` of `heading`. Source: https://reactnative.dev/docs/accessibility#role
- **Build custom tab bars from `tablist` and `tab`**: "Used to represent a list of tabs." - put `tablist` on the container, `tab` on each item, and the selected state on the active one. Why: without them a segmented control reads as a row of unrelated buttons with no selection. Smell: a hand-built tab bar or segmented control made of `Pressable` items with a role of `button` or none. Source: https://reactnative.dev/docs/accessibility#accessibilityrole

## State and value

- **Expose the disabled state, not only the disabled look**: "Indicates that the element is perceivable but disabled, so it is not editable or otherwise operable." - [WCAG 4.1.2] set `aria-disabled` or `accessibilityState` with `disabled` whenever a control is greyed out. Why: a control that only looks disabled is announced as an active button that then does nothing. Smell: reduced opacity plus an early return in `onPress`, with no disabled state on the element. Source: https://reactnative.dev/docs/accessibility#aria-disabled
- **Expose selection on selectable items**: "Indicates whether a selectable element is currently selected or not." - [WCAG 4.1.2] set `aria-selected` or `accessibilityState` with `selected` on tabs, chips and list rows that can be picked. Why: selection shown only by colour or a border is not announced. Smell: an `isActive` style on a tab or chip with no matching state prop. Source: https://reactnative.dev/docs/accessibility#aria-selected
- **Expose checked state on custom checkboxes, switches and radios**: "Indicates the state of a checkable element." - [WCAG 4.1.2] set `aria-checked` or `accessibilityState` with `checked`; the field takes a boolean or the string `mixed` for a partially selected parent. Why: the role says the control can be checked but never says whether it is. Smell: a custom checkbox that swaps an icon on press with no `checked` state, or a select-all box with no `mixed` case. Source: https://reactnative.dev/docs/accessibility#aria-checked
- **Expose expanded state on disclosure controls**: "Indicates whether an expandable element is currently expanded or collapsed." - [WCAG 4.1.2] set `aria-expanded` or `accessibilityState` with `expanded` on accordion headers, dropdown triggers and show-more buttons. Why: a rotating chevron is the only signal otherwise. Smell: a header that toggles a collapsible body with no `expanded` state. Source: https://reactnative.dev/docs/accessibility#aria-expanded
- **Mark regions that are loading as busy**: "assistive technologies may want to wait until the changes are complete before informing the user about the update" - set `aria-busy` or `accessibilityState` with `busy` while content is being replaced, and clear it afterwards. Why: partial updates are otherwise announced mid-change, or the busy flag stays on for ever. Smell: a button showing a spinner with no busy state, or `busy` set to `true` and never reset. Source: https://reactnative.dev/docs/accessibility#aria-busy
- **Give range controls a value**: "for range-based components, such as sliders and progress bars, it contains range information (minimum, current, and maximum)" - [WCAG 4.1.2] custom sliders, steppers and progress bars need `accessibilityValue` or the `aria-value*` props. Why: a role of `adjustable` or `progressbar` with no value announces a control with nothing to report. Smell: a custom progress bar drawn with an animated width and no value props. Source: https://reactnative.dev/docs/accessibility#accessibilityvalue
- **Supply `min` and `max` whenever `now` is set**: "Required if `now` is set." - all three go together, and the table types them as integers, so round fractions first. Why: a current value with no range cannot be turned into a percentage or position. Smell: `accessibilityValue={{now: progress}}` alone, or `now` holding a float between 0 and 1. Source: https://reactnative.dev/docs/accessibility#accessibilityvalue
- **Use the text value when numbers alone mislead**: "Will override `min`, `now`, and `max` if set." - `text` replaces the numeric range in the announcement, so use it for units, labels and named steps, and do not expect both to be read. Why: a bare number is meaningless for a rating, a size picker or a duration. Smell: a slider over named options exposing only an index, or `text` set alongside numbers the author expects to hear as well. Source: https://reactnative.dev/docs/accessibility#accessibilityvalue
- **Do not mix `aria-value*` props with `accessibilityValue` fields**: "Has precedence over the `now` value in the `accessibilityValue` prop." - each `aria-valuemin`, `aria-valuemax`, `aria-valuenow` and `aria-valuetext` prop wins over the matching object field; pick one style per component. Why: the overridden field is dead code that a later edit will update by mistake. Smell: `aria-valuenow` and `accessibilityValue` on the same element. Source: https://reactnative.dev/docs/view#aria-valuenow

## Hiding content and modal surfaces

- **Hide only what is truly decorative or covered**: "causes VoiceOver to ignore the `B` element and its children" - `aria-hidden` removes the whole subtree, so never apply it to a container that holds visible, operable content. Why: sighted users can press a control that screen reader users cannot reach. Smell: `aria-hidden` on a wrapper that contains a `Pressable` or `TextInput`, or left on after an overlay closes. Source: https://reactnative.dev/docs/accessibility#aria-hidden
- **Pair `accessibilityElementsHidden` with its Android counterpart**: "A boolean value indicating whether the given accessibility element, and any accessibility elements it contains, are hidden." - the prop is iOS only; Android needs `importantForAccessibility` set to `no-hide-descendants`, or use `aria-hidden` for both. Why: content hidden from VoiceOver stays reachable in TalkBack. Smell: `accessibilityElementsHidden` with no `importantForAccessibility` beside it. Source: https://reactnative.dev/docs/accessibility#accessibilityelementshidden-ios
- **Remember `importantForAccessibility` does nothing on iOS**: "the last value will force accessibility services to ignore the component and all of its children" - `no-hide-descendants` hides a subtree from TalkBack only. Why: content hidden on Android is still read by VoiceOver unless the iOS prop is set as well. Smell: `importantForAccessibility` used alone to hide a background screen or an off-screen carousel page. Source: https://reactnative.dev/docs/accessibility#importantforaccessibility-android
- **Resolve overlapping views explicitly on Android**: "In the case of two overlapping UI components with the same parent, default accessibility focus can have unpredictable behavior." - set `importantForAccessibility` on the covered layer when two siblings occupy the same area. Why: TalkBack may focus the layer underneath. Smell: an absolutely positioned overlay, skeleton or stacked card whose covered sibling keeps the default. Source: https://reactnative.dev/docs/accessibility#importantforaccessibility-android
- **Mark custom overlays as modal for VoiceOver**: "A boolean value that indicates whether VoiceOver should ignore the elements within views that are siblings of the receiver." - set `accessibilityViewIsModal` or `aria-modal` on hand-built sheets, drawers and dialogs. iOS only, so the background still has to be hidden from TalkBack separately. Why: focus otherwise wanders onto the screen behind the overlay. Smell: an absolutely positioned sheet with a backdrop and no modal prop, or the modal prop treated as covering Android. Source: https://reactnative.dev/docs/accessibility#accessibilityviewismodal-ios
- **Put the modal flag on the view whose siblings should be ignored**: "VoiceOver does not ignore the elements in view `A`" - that is the documented result when the flag sits on a child nested inside the overlay container instead of on the container that is a sibling of the background. Why: the prop is accepted, no error appears and the background stays reachable. Smell: `accessibilityViewIsModal` on the inner card of a sheet while the wrapper that sits beside the screen content has none. Source: https://reactnative.dev/docs/accessibility#accessibilityviewismodal-ios
- **Handle the escape gesture on dismissible surfaces**: "An escape function should move back hierarchically in the user interface." - give custom modals, sheets and pushed panels an `onAccessibilityEscape` that closes them or goes back. iOS only. Why: without a handler anywhere up the hierarchy the two-finger scrub does nothing. Smell: a custom overlay with a close button and no `onAccessibilityEscape`. Source: https://reactnative.dev/docs/accessibility#onaccessibilityescape-ios
- **Map magic tap to the main action of the screen**: "A magic tap function should perform the most relevant action a user could take on a component." - use `onMagicTap` for play or pause, answer or hang up, start or stop. iOS only. Why: it is a shortcut users expect to hit the primary action; binding it to something secondary or destructive surprises them. Smell: `onMagicTap` wired to navigation, deletion or an analytics call. Source: https://reactnative.dev/docs/accessibility#onmagictap-ios
- **Set `accessible` on views that carry gesture handlers**: "When `accessible` is `true`, the system will invoke this function when the user performs the escape gesture." - the same condition is documented for `onMagicTap` and `onAccessibilityTap`. Why: the handler is attached but never called. Smell: `onAccessibilityEscape` or `onMagicTap` on a layout `View` with no `accessible={true}`. Source: https://reactnative.dev/docs/view#onaccessibilityescape-ios

## Live regions and announcements

- **Announce dynamic changes, and cover iOS separately**: "When components dynamically change, we want TalkBack to alert the end user." - [WCAG 4.1.3] `accessibilityLiveRegion` does this on Android only; iOS needs an explicit announcement through `AccessibilityInfo`. Why: a validation error, toast or counter that updates silently is missed by screen reader users. Smell: status text that changes after an action with no live region, or a live region with no iOS path. Source: https://reactnative.dev/docs/accessibility#accessibilityliveregion-android
- **Default to `polite`; reserve `assertive` for urgent messages**: "Accessibility services should interrupt ongoing speech to immediately announce changes to this view." - that is what `assertive` does, so use it for errors and time-critical alerts only. Why: frequent interruptions cut off what the user was listening to. Smell: `assertive` on a counter, a progress label or a typing indicator. Source: https://reactnative.dev/docs/accessibility#accessibilityliveregion-android
- **Announce status changes that have no focusable element**: "Post a string to be announced by the screen reader." - [WCAG 4.1.3] call `AccessibilityInfo.announceForAccessibility` for results such as saved, sent, removed or failed. Why: it is the cross-platform route for messages when no live region applies. Smell: a success toast or snackbar shown with no announcement. Source: https://reactnative.dev/docs/accessibilityinfo#announceforaccessibility
- **Queue announcements that should not cut speech off**: "By default announcements will interrupt any existing speech, but on iOS they can be queued behind existing speech by setting `queue` to `true` in the options object." - use `announceForAccessibilityWithOptions` for non-urgent messages; the `queue` option is iOS only. Why: an announcement fired right after a press interrupts the reading of the element the user just reached. Smell: several `announceForAccessibility` calls in a row, or `queue` assumed to work on Android. Source: https://reactnative.dev/docs/accessibilityinfo#announceforaccessibilitywithoptions
- **Use high priority sparingly**: "High priority announcements will interrupt any ongoing speech and cannot be interrupted." - `priority` is iOS only; choose `low` for background updates and keep `high` for messages the user must not miss. Why: an uninterruptible announcement blocks the user until it finishes. Smell: `priority` of `high` on routine confirmations. Source: https://reactnative.dev/docs/accessibilityinfo#announceforaccessibilitywithoptions

## Accessibility actions

- **Declare actions and handle them**: "Implement an `onAccessibilityAction` function to handle action requests." - `accessibilityActions` and `onAccessibilityAction` are the two required halves. Why: actions listed without a handler are offered to the user and do nothing. Smell: `accessibilityActions` on an element with no `onAccessibilityAction`, or the reverse. Source: https://reactnative.dev/docs/accessibility#accessibility-actions
- **Offer gesture-only features as custom actions**: "custom actions specific to a given component such as deleting an email message" - swipe-to-delete, drag-to-reorder and long-press menus need an action with the same effect. Why: custom gestures are not available to screen reader users, who operate through the actions menu instead. Smell: a swipeable row or draggable item with no `accessibilityActions`. Source: https://reactnative.dev/docs/accessibility#accessibility-actions
- **Give custom actions a localised label**: "For custom actions, the `label` is a localized string containing a description of the action to be presented to the user." - pass the label through the translation function. Why: the label is what the user hears in the actions menu, in their own language. Smell: a custom action with no `label`, or a hard-coded English string in an app that ships translations. Source: https://reactnative.dev/docs/accessibility#accessibility-actions
- **Make `activate` do exactly what a tap does**: "This should perform the same action with, or without, assistive technology." - the handler for `activate` calls the same function as `onPress`; the same sentence applies to `longpress`. Why: it is what runs when a screen reader user double taps. Smell: an `activate` case that skips validation, confirmation or analytics that `onPress` performs. Source: https://reactnative.dev/docs/accessibility#accessibility-actions
- **Give adjustable controls `increment` and `decrement`**: "VoiceOver generates this action when the component has a role of `'adjustable'` and the user places focus on it and swipes upward" - a custom slider, stepper or rating needs the `adjustable` role plus both actions and an updated value. Why: with no role VoiceOver never sends the action, and with no handler the swipe does nothing. Smell: a custom slider driven only by a pan gesture. Source: https://reactnative.dev/docs/accessibility#accessibility-actions
- **Do not rely on single-platform standard actions**: "Android only - This action is generated when the user places accessibility focus on the component, then double-taps and holds one finger on the screen." - `longpress`, `expand` and `collapse` are Android only; `magicTap` and `escape` are iOS only. Why: a feature reachable only through one of them is missing on the other platform. Smell: a context menu exposed only through `longpress`, or dismissal only through `escape`, with no visible or custom-action alternative. Source: https://reactnative.dev/docs/accessibility#accessibility-actions

## Focus and order

- **Move focus with `sendAccessibilityEvent`, not `setAccessibilityFocus`**: "Prefer using `sendAccessibilityEvent` with eventType `focus` instead." - `AccessibilityInfo.setAccessibilityFocus` is marked deprecated; pass the component ref and `focus`. Why: the replacement takes a ref rather than a react tag. Smell: `AccessibilityInfo.setAccessibilityFocus(findNodeHandle(ref.current))` in new code. Source: https://reactnative.dev/docs/accessibilityinfo#sendaccessibilityevent
- **Make the focus target an accessible element**: "Make sure that any `View` you want to receive the accessibility focus has `accessible={true}`." - check the target of every programmatic focus call. Why: focus sent to a view that is not accessible has nowhere to land. Smell: a ref on a layout `View` or screen container passed to `sendAccessibilityEvent`. Source: https://reactnative.dev/docs/accessibilityinfo#sendaccessibilityevent
- **Use only `focus` in cross-platform event code**: "One of `'click'` (Android only), `'focus'`, `'viewHoverEnter'` (Android only), or `'windowStateChange'` (Android only)" - the other three event types need an Android branch. Why: logic built on them has no effect on iOS. Smell: `sendAccessibilityEvent(ref, 'windowStateChange')` used to announce a screen change with no iOS equivalent. Source: https://reactnative.dev/docs/accessibilityinfo#sendaccessibilityevent
- **Fix layout order before reaching for an order override**: "layout is excluded in the following examples even though it dictates the default focus order" - [WCAG 2.4.3] reading order follows layout, and `experimental_accessibilityOrder` is flagged experimental, so restructure first. Why: an override has to be maintained by hand every time the screen changes. Smell: `experimental_accessibilityOrder` on a screen whose order problem comes from absolute positioning or reversed flex direction. Source: https://reactnative.dev/docs/accessibility#experimental_accessibilityorder
- **List every focusable descendant in an order array**: "`D` will never get focused." - [WCAG 2.4.3] the array is exhaustive: an accessible descendant whose `nativeID` is missing from it is removed from focus. Why: adding a control later without updating the array makes it unreachable. Smell: a new accessible child added under a view with `experimental_accessibilityOrder` and no change to the array. Source: https://reactnative.dev/docs/accessibility#experimental_accessibilityorder
- **Do not make an ordered container accessible itself**: "A component cannot be both an accessibility container and an accessibility element" - a view that has both `accessible={true}` and its own order array is treated as one element. Why: its children drop out of the order and can no longer be focused. Smell: `accessible={true}` and `experimental_accessibilityOrder` on the same view. Source: https://reactnative.dev/docs/accessibility#experimental_accessibilityorder
- **Make custom controls reachable from a hardware keyboard on Android**: "Whether this `View` should be focusable with a non-touch input device, eg. receive focus with a hardware keyboard." - [WCAG 2.1.1] set `focusable` on interactive views built from `View`. Android only. Why: keyboard and switch users cannot reach a control that takes touch only. Smell: a `View` with responder handlers acting as a button and no `focusable`. Source: https://reactnative.dev/docs/view#focusable-android

## Touch targets and press feedback

- **Meet the minimum touch target**: "Typical interface guidelines recommend touch targets that are at least 30 - 40 points/density-independent pixels." - [WCAG 2.5.8] enlarge small controls with padding or `hitSlop`. Why: small targets cause missed and wrong presses, most of all for users with limited dexterity. Smell: a 16 or 20 point icon inside a `Pressable` with no padding and no `hitSlop`. Source: https://reactnative.dev/docs/view#hitslop
- **Do not count on `hitSlop` beyond the parent's bounds**: "The touch area never extends past the parent view bounds" - give the parent room, or use padding on the control itself. Why: the extra area is clipped and the target stays small. Smell: a large `hitSlop` on an icon whose parent is exactly the icon's size, such as a tight header row. Source: https://reactnative.dev/docs/view#hitslop
- **Show visible feedback on every press**: "All elements that respond to press should have a visual feedback when touched." - use the `pressed` state in `style` or `children`, or `android_ripple`. Why: without feedback users cannot tell whether the press registered. Smell: a `Pressable` with a static `style` object and no ripple. Source: https://reactnative.dev/docs/touchablewithoutfeedback
- **Avoid `TouchableWithoutFeedback`**: "Do not use unless you have a very good reason." - replace it with `Pressable` and a pressed style. Why: it gives no feedback by design, and the page itself points to `Pressable` as the future-proof option. Smell: a new `TouchableWithoutFeedback` import, most often used as a cheap tap handler around a card. Source: https://reactnative.dev/docs/touchablewithoutfeedback
- **Use a `PlatformColor` for the Android ripple in themed apps**: "the ripple is automatically updated when the system configuration changes" - a theme attribute keeps the press feedback visible in both light and dark mode. Android only. Why: a fixed ripple colour chosen for one scheme can vanish against the other. Smell: `android_ripple` with a hard-coded dark or light colour in an app that supports both schemes. Source: https://reactnative.dev/docs/pressable#android_ripple-android

## Text scaling

- **Leave font scaling on**: "Specifies whether fonts should scale to respect Text Size accessibility settings." - [WCAG 1.4.4] the default is `true`; fix the layout rather than switching scaling off. Why: users who set a larger text size get text that ignores it. Smell: `allowFontScaling={false}` on a `Text`, or set through a shared text component or default props. Source: https://reactnative.dev/docs/text#allowfontscaling
- **Do not cap text scaling tightly**: "Specifies the largest possible scale a font can reach when `allowFontScaling` is enabled." - [WCAG 1.4.4] a `maxFontSizeMultiplier` below 2 stops text from reaching double size; reserve caps for elements that truly cannot grow and give those another route such as the large content viewer. Why: a cap of 1 is the same as switching scaling off. Smell: `maxFontSizeMultiplier={1}` or `{1.2}` on body text or applied app-wide. Source: https://reactnative.dev/docs/text#maxfontsizemultiplier
- **Know that a multiplier cap is inherited**: "inherit from the parent node or the global default (0)" - a cap on a parent `Text` applies to nested `Text`; a value of `0` means "no max, ignore parent/global default". Why: one cap on a wrapper limits every nested string beneath it. Smell: `maxFontSizeMultiplier` on a wrapping `Text` that contains long-form content. Source: https://reactnative.dev/docs/text#maxfontsizemultiplier
- **Set the Dynamic Type ramp to match the text's purpose**: "ramp to apply to this element on iOS" - `dynamicTypeRamp` defaults to `body`; set `title1`, `headline`, `caption1` and so on for text styled as such. iOS only. Why: headings and captions otherwise scale along the body curve rather than their own. Smell: a large title or small caption style with no `dynamicTypeRamp`. Source: https://reactnative.dev/docs/text#dynamictyperamp-ios
- **Review line limits at large text sizes**: "Used to truncate the text with an ellipsis after computing the text layout" - `numberOfLines` cuts whatever does not fit, so check each limit with the largest text setting. Why: content that fits at default size is truncated for exactly the users who enlarged it. Smell: `numberOfLines={1}` on labels, prices, error messages or button text inside a fixed-height container. Source: https://reactnative.dev/docs/text#numberoflines
- **Do not shrink body text to fit**: "Specifies whether fonts should be scaled down automatically to fit given style constraints." - keep `adjustsFontSizeToFit` for short display strings; let other text wrap. Why: it scales text down, against the direction the user asked for. Smell: `adjustsFontSizeToFit` on paragraphs, form labels or list rows. Source: https://reactnative.dev/docs/text#adjustsfontsizetofit

## Text inputs

- **Declare what each field collects**: "Specifies autocomplete hints for the system, so it can provide autofill." - [WCAG 1.3.5] set `autoComplete` on name, email, address, phone, payment and credential fields. Why: autofill saves typing for users who find text entry slow or error-prone. Smell: a sign-up or checkout form whose `TextInput` elements have no `autoComplete`. Source: https://reactnative.dev/docs/textinput#autocomplete
- **Do not set both `autoComplete` and `textContentType`**: "Avoid using both `textContentType` and `autoComplete`." - choose one per field. Why: "For backwards compatibility, `textContentType` takes precedence when both properties are set", so the other value is ignored on iOS. Smell: both props on one `TextInput`, more so with values that disagree. Source: https://reactnative.dev/docs/textinput#textcontenttype-ios
- **Prefer `autoComplete` for cross-platform hints**: "provides the same functionality and is available for all platforms" - `textContentType` is iOS only, so a field that uses it alone has no hint on Android. Why: Android then falls back to guessing the field type. Smell: `textContentType` with no `autoComplete` in a form that ships to Android. Source: https://reactnative.dev/docs/textinput#textcontenttype-ios
- **Open the keyboard that matches the data**: "it determines which keyboard to open, e.g. `numeric` and has precedence over `keyboardType`" - set `inputMode` (or `keyboardType`) on numeric, email, URL and phone fields, and do not set the two to different values. Why: the wrong keyboard adds key presses and errors for every entry. Smell: an amount or phone field with the default keyboard, or `inputMode` and `keyboardType` that disagree. Source: https://reactnative.dev/docs/textinput#inputmode
- **Localise the input accessory button label**: "By default, the default button label is not localized." - pass a translated `inputAccessoryViewButtonLabel`. iOS only. Why: the control above the keyboard is shown and read in English in every locale. Smell: a translated app that uses an input accessory view with no `inputAccessoryViewButtonLabel`. Source: https://reactnative.dev/docs/textinput#inputaccessoryviewbuttonlabel-ios
- **Do not use the placeholder as the field's label**: "The string that will be rendered before text input has been entered." - [WCAG 3.3.2] the placeholder is gone once the user types, so give the field a visible label and an accessible name as well. Why: the user loses the prompt while reviewing or correcting an entry. Smell: a `TextInput` with `placeholder` and no adjacent `Text` label, `accessibilityLabel` or `aria-label`. Source: https://reactnative.dev/docs/textinput#placeholder

## Motion and system settings

- **Respect reduce motion**: "Query whether reduce motion is currently enabled." - [WCAG 2.3.3] check `AccessibilityInfo.isReduceMotionEnabled()` and shorten, replace or skip non-essential animation. Why: parallax, zoom and large transitions cause discomfort for users who switched the setting on. Smell: a screen with decorative or large-scale animation and no reduce motion check. Source: https://reactnative.dev/docs/accessibilityinfo#isreducemotionenabled
- **Subscribe to setting changes as well as reading them once**: "Fires when the state of the reduce motion toggle changes." - combine the initial query with `addEventListener('reduceMotionChanged', ...)`; on Android the value is also true when developer options turn animations off. Why: a value read once at start-up is stale after the user changes the setting. Smell: `isReduceMotionEnabled()` called once into module scope or a store with no listener. Source: https://reactnative.dev/docs/accessibilityinfo#addeventlistener
- **Remove accessibility listeners on clean-up**: "reduceMotionChangedSubscription.remove();" - `addEventListener` returns a subscription; call `remove()` in the effect's clean-up, as the example does. Why: a leaked listener keeps setting state on an unmounted component. Smell: `AccessibilityInfo.addEventListener` inside `useEffect` with no returned clean-up function. Source: https://reactnative.dev/docs/accessibilityinfo#example
- **Await the `AccessibilityInfo` queries**: "Returns a promise which resolves to a boolean." - every `is...Enabled()` method is asynchronous. Why: a promise is always truthy, so an un-awaited check takes the enabled branch for everyone. Smell: `if (AccessibilityInfo.isScreenReaderEnabled())` or the call used directly inside a JSX condition. Source: https://reactnative.dev/docs/accessibilityinfo#isscreenreaderenabled
- **Do not treat any accessibility service as a screen reader**: "This includes TalkBack but also any third-party accessibility app that may be installed." - `isAccessibilityServiceEnabled()` is Android only and broader; use `isScreenReaderEnabled()` for TalkBack alone. Why: password managers and automation tools register as accessibility services, so the broad check is true for many users with no screen reader. Smell: screen reader specific UI gated on `isAccessibilityServiceEnabled()`. Source: https://reactnative.dev/docs/accessibilityinfo#isaccessibilityserviceenabled-android
- **Take auto-dismiss timeouts from the user's setting**: "Gets the timeout in millisecond that the user needs." - [WCAG 2.2.1] pass the default duration to `getRecommendedTimeoutMillis` for toasts, snackbars and timed controls. Android only, so keep a generous default or a manual dismiss for iOS. Why: a fixed few seconds is too short for users who read or act slowly. Smell: `setTimeout(hide, 3000)` on a message or control with no call to the API. Source: https://reactnative.dev/docs/accessibilityinfo#getrecommendedtimeoutmillis-android
- **Replace blur and translucency when transparency is reduced**: "Query whether reduce transparency is currently enabled." - check `isReduceTransparencyEnabled()` and use an opaque background for blurred or translucent surfaces. iOS only. Why: text over a translucent layer is the case the setting exists to fix. Smell: a blur view or semi-transparent sheet behind text with no opaque fallback. Source: https://reactnative.dev/docs/accessibilityinfo#isreducetransparencyenabled-ios
- **Branch per platform for contrast settings**: "Query whether high text contrast is currently enabled." - `isHighTextContrastEnabled()` is Android only and `isDarkerSystemColorsEnabled()` is iOS only; use each on its own platform to switch to a higher-contrast palette. Why: one check alone covers half the users. Smell: a contrast toggle wired to one of the two methods with no platform branch. Source: https://reactnative.dev/docs/accessibilityinfo#ishightextcontrastenabled-android

## Colour scheme and system colours

- **Read the colour scheme on every render**: "Any rendering logic or styles that depend on the user preferred color scheme should try to call this function on every render, rather than caching the value." - use the `useColorScheme` hook, which the page recommends, not a value captured once. Why: the scheme can change while the app is open, for example on a sunset schedule. Smell: `Appearance.getColorScheme()` at module scope, or its result stored in a constant, a store or a `StyleSheet`. Source: https://reactnative.dev/docs/appearance#example
- **Handle a `null` colour scheme**: "May be returned if the native Appearance module is not available." - give theme selection a default branch. Why: indexing a theme map with `null` yields `undefined` colours. Smell: `themes[useColorScheme()]`, or a non-null assertion on the hook result. Source: https://reactnative.dev/docs/usecolorscheme#return-values
- **Do not force a scheme without a user-facing reason**: "Forces the application to always adopt a light or dark interface style." - call `Appearance.setColorScheme` only from an in-app theme setting, and never as a shortcut around unfinished dark styles. Why: it overrides a system preference that many users set for comfort or legibility. Smell: `Appearance.setColorScheme('light')` at start-up with no settings screen that controls it. Source: https://reactnative.dev/docs/appearance#setcolorscheme
- **Restore the system scheme with `auto`**: "Follow the system color scheme (removes any override)" - pass `'auto'` when the user picks the system option; `'unspecified'` does the same but is marked deprecated. Why: a leftover override pins the app to one scheme. Smell: `setColorScheme('unspecified')`, or a system option that maps to a fixed scheme. Source: https://reactnative.dev/docs/appearance#setcolorscheme
- **Wrap `PlatformColor` in a platform check**: "In order to avoid runtime errors, the function should be wrapped in a platform check" - native colour names differ per platform, so use `Platform.select` or `Platform.OS`. Why: a name that does not exist on the running platform fails at runtime. Smell: `PlatformColor('label')` or `PlatformColor('?attr/colorAccent')` in shared styles with no platform branch. Source: https://reactnative.dev/docs/platformcolor#example
- **Provide high-contrast variants of dynamic colours**: "two optional keys `highContrastLight` and `highContrastDark`" - fill them in for brand colours used as text or as a background behind text. Why: with only `light` and `dark` the colour does not change when the user turns on increased contrast. Smell: `DynamicColorIOS({light, dark})` for a text colour with no high-contrast keys. Source: https://reactnative.dev/docs/dynamiccolorios
- **Set `userInterfaceStyle` in the Expo app config**: "The app will default to the `light` style if this property is absent." - use `automatic` to follow the system on Android and iOS. Why: without it `useColorScheme` reports light for ever and dark styles never apply. Smell: dark theme code in a project whose `app.json` has no `userInterfaceStyle`, or has it set to `light`. Source: https://docs.expo.dev/develop/user-interface/color-themes/#configuration
- **Install `expo-system-ui` in development builds**: "Otherwise, the `userInterfaceStyle` property is ignored." - Android needs the package for the config value to take effect. Why: the app stays light on Android while iOS follows the system. Smell: `userInterfaceStyle` of `automatic` with no `expo-system-ui` in `package.json`. Source: https://docs.expo.dev/develop/user-interface/color-themes/#configuration
- **Keep `uiMode` in the Android manifest of an existing native project**: "Ensure that the `uiMode` flag is present on your `MainActivity`" - the flag belongs in `android:configChanges`, together with the `onConfigurationChanged` override the page shows. Why: without them scheme changes do not reach the JavaScript side while the app is running. Smell: an `AndroidManifest.xml` whose `configChanges` lacks `uiMode` in an app that claims to follow the system theme. Source: https://docs.expo.dev/develop/user-interface/color-themes/#android

## Right-to-left layout

- **Review absolute positioning for RTL**: "If you absolutely position elements to align with other flexbox elements, they may not align in RTL languages." - use `I18nManager.isRTL` to flip offsets and directional animations. Why: flex layout mirrors on its own and hand-placed elements do not. Smell: `position: 'absolute'` with `left` or `right` aligned to a flex row, or a `translateX` animation with a fixed sign. Source: https://reactnative.dev/docs/i18nmanager#change-positions-and-animations-based-on-rtl
- **Do not call `forceRTL` in production code**: "Avoid forcing RTL in production apps as it requires a full app restart to take effect" - the page limits it to development and testing. Why: users see the wrong direction until they restart, and the setting persists across restarts. Smell: `I18nManager.forceRTL(...)` outside a development-only branch. Source: https://reactnative.dev/docs/i18nmanager#forcertl
- **Check the native conditions for RTL when `isRTL` stays false**: "The user-preferred language on the device is an RTL language" - iOS also needs the language among the app's localisations, and Android needs `supportsRTL` set on the manifest's application element. Why: without them an Arabic or Hebrew device still gets a left-to-right layout. Smell: RTL translations added with no native localisation entry and no manifest flag. Source: https://reactnative.dev/docs/i18nmanager#isrtl
- **Use `start` and `end` in layout styles**: "You don't need to manually adjust `<View>` styling properties based on locale." - flex properties with `start` and `end` values change sides with the locale. Why: fewer hand-written direction branches to keep correct. Smell: `isRTL` conditionals around `justifyContent`, `alignItems` or margin styles. Source: https://docs.expo.dev/guides/localization/#layouts-and-views
- **Set `textAlign` explicitly on text**: "each `<Text>` tag should have the `textAlign: left` or `textAlign: right` style set if you want it to be aligned correctly" - `left` behaves as start and `right` as end, while an unset value means true left in both directions; put the style in the shared text component. Why: unstyled text stays left-aligned in an RTL layout. Smell: a base `Text` component with no `textAlign`. Source: https://docs.expo.dev/guides/localization/#text-alignment
- **Declare supported locales for RTL on iOS**: "On iOS, the device language must also be one of your app's supported locales" - list each RTL language under `supportedLocales` in the `expo-localization` plugin config. Why: the app otherwise renders left-to-right on a device set to that language. Smell: Arabic or Hebrew translation files with no matching `supportedLocales` entry. Source: https://docs.expo.dev/guides/localization/#rtl-support
- **Opt out of RTL explicitly when the app is not ready for it**: "To opt out of RTL layout, set the `supportsRTL` option to `false` on the `expo-localization` config plugin" - in SDK 58 "RTL support is enabled by default", so an untested app will mirror on RTL devices. Why: an unreviewed mirrored layout ships to users by default. Smell: an upgrade to SDK 58 with no RTL test pass and no `supportsRTL` decision in the app config. Source: https://docs.expo.dev/guides/localization/#disabling-rtl-support
- **Set content direction separately from the navigator's**: "Continue to set the layout direction for your app content separately." - `LocaleProvider` in Expo Router covers headers, transitions and gestures only. Why: navigation flips while the screens inside it stay in the old direction. Smell: a runtime language switch that updates `LocaleProvider` and nothing else. Source: https://docs.expo.dev/guides/localization/#changing-expo-router-direction-at-runtime

## Testing

- **Test TalkBack on an emulator image that has the Play Store**: "Android emulators don't have TalkBack installed by default." - install TalkBack from Google Play on such an image, or use a device. Why: an accessibility change that was never heard through a screen reader is unverified. Smell: a change to labels, roles or focus with test notes that mention no TalkBack pass. Source: https://reactnative.dev/docs/accessibility#testing-talkback-support-android
- **Verify VoiceOver behaviour on a physical device**: "VoiceOver isn't available via the simulator" - Accessibility Inspector helps during development, but the docs add "it's always best to test with a device". Why: the macOS VoiceOver used through the inspector can behave differently from iOS. Smell: iOS accessibility changes signed off from the simulator alone. Source: https://reactnative.dev/docs/accessibility#testing-voiceover-support-ios
