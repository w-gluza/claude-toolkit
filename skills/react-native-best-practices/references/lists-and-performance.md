# React Native code-review rules: lists and performance

Extracted 2026-11-12 from the React Native 0.88 documentation (facebook/react-native-website, CC BY 4.0) and the Expo SDK 58 documentation (expo/expo, MIT). One rule per bullet, one source link each. Quotations are short excerpts; the rest is original.

## Choosing a list component

- **Render long or growing collections with `FlatList`, not a mapped `ScrollView`**: "`ScrollView` renders all its react child components at once, but this has a performance downside." - `FlatList` mounts rows as they approach the viewport and unmounts those far away. Why: creating every row up front "will contribute to slow rendering and increased memory usage". Smell: `<ScrollView>{items.map(item => <Row ... />)}</ScrollView>` over server data or any array without a small fixed bound. Source: https://reactnative.dev/docs/scrollview
- **Keep `ScrollView` for short, bounded content**: "The ScrollView works best to present a small number of things of a limited size." - a settings screen or a form is fine in a `ScrollView`; a feed is not. Why: "All the elements and views of a `ScrollView` are rendered, even if they are not currently shown on the screen." Smell: a `FlatList` wrapping five static rows, or a `ScrollView` wrapping a paginated result. Source: https://reactnative.dev/docs/using-a-scrollview
- **Give every `ScrollView` and list a bounded height**: "ScrollViews must have a bounded height in order to work" - bound it through the parents rather than a fixed `height` on the scroll view, which the docs call discouraged. Why: "Forgetting to transfer `{flex: 1}` down the view stack can lead to errors here". Smell: a list inside a `View` with no `flex: 1`, or a vertical list nested in a vertical `ScrollView` so it never gets a finite height. Source: https://reactnative.dev/docs/scrollview

## FlatList and SectionList correctness

- **Pass `extraData` whenever rows read anything outside `data`**: "passing `extraData` is essential whenever `renderItem` has a stable reference" - a memoised or module-level `renderItem` that reads `selectedId`, a theme or a filter must list that value in `extraData`. Why: the list is a `PureComponent`, so without it the list has no signal "that an external dependency has updated". Smell: `renderItem` wrapped in `useCallback` reading state, with no `extraData` prop on the list. Source: https://reactnative.dev/docs/flatlist#example
- **Give `data` and `extraData` a new reference on every change**: "If any of your `renderItem`, Header, Footer, etc. functions depend on anything outside of the `data` prop, stick it here and treat it immutably." - replace arrays and objects rather than mutating them. Why: the list "will not re-render if `props` remain shallow-equal". Smell: `items.push(x); setItems(items)`, a `Set` mutated in place and passed as `extraData`, or `data={store.items}` with in-place sorting. Source: https://reactnative.dev/docs/flatlist#extradata
- **Keep row state in the item data or a store, not in the row component**: "Internal state is not preserved when content scrolls out of the render window." - an expanded flag, a checkbox or a draft input must live above the row. Why: virtualisation "fully unmounts react instances that are outside of the render window". Smell: `useState` inside a list row for anything the user would expect to survive scrolling away and back. Source: https://reactnative.dev/docs/flatlist
- **Provide `keyExtractor` when items have neither `key` nor `id`**: "The default extractor checks `item.key`, then `item.id`, and then falls back to using the index, like React does." - return a stable string from the data. Why: "Key is used for caching and as the react key to track item re-ordering", so index keys misattribute rows after insert, delete or sort. Smell: `keyExtractor={(_, index) => String(index)}`, or items keyed by `uuid` or `slug` with no `keyExtractor`. Source: https://reactnative.dev/docs/flatlist#keyextractor
- **Give each `SectionList` section its own `key` when sections can reorder**: "Note that this sets keys for each item, but each overall section still needs its own key." - `keyExtractor` covers items only. Why: without a section `key`, "the array index will be used by default". Smell: sections built from sorted or filtered groups with no `key` field on the section object. Source: https://reactnative.dev/docs/sectionlist#keyextractor
- **Build grids with `numColumns`, not `flexWrap`**: "Using this approach instead of a `flexWrap` layout can prevent conflicts with the item height logic." - set `numColumns` and style the rows with `columnWrapperStyle`. Why: the list measures rows; a wrapped content container hides the row structure from it. Smell: `contentContainerStyle={{flexDirection: 'row', flexWrap: 'wrap'}}` on a `FlatList`. Source: https://reactnative.dev/docs/flatlist#example
- **Use `numColumns` only for vertical grids of equal-height items**: "Items should all be the same height - masonry layouts are not supported." - a staggered grid needs a different component. Why: "Multiple columns can only be rendered with `horizontal={false}`". Smell: `numColumns` together with `horizontal`, or grid cells whose height depends on image aspect ratio or text length. Source: https://reactnative.dev/docs/flatlist#numcolumns
- **Include separators in the `getItemLayout` offset**: "Remember to include separator length (height or width) in your offset calculation if you specify `ItemSeparatorComponent`." - offset is `(ITEM + SEPARATOR) * index`. Why: a wrong offset makes `scrollToIndex` and the render window drift further out with every row. Smell: `getItemLayout` returning `offset: ITEM_HEIGHT * index` on a list that also sets `ItemSeparatorComponent` or a header. Source: https://reactnative.dev/docs/flatlist#getitemlayout
- **Implement `getItemLayout` before using `initialScrollIndex`**: "Requires `getItemLayout` to be implemented." - the list cannot start at an index whose offset it has not measured. Why: the prop also skips the optimisation that keeps the first batch mounted and "immediately renders the items starting at this initial index". Smell: `initialScrollIndex={n}` on a list with no `getItemLayout`. Source: https://reactnative.dev/docs/flatlist#initialscrollindex
- **Do not call `scrollToIndex` on unmeasured rows without `getItemLayout`**: "Cannot scroll to locations outside the render window without specifying the `getItemLayout` prop." - either supply layout or handle the failure. Why: the target offset is unknown until the row has rendered. Smell: `listRef.current.scrollToIndex({index: items.length - 1})` on a variable-height list with neither `getItemLayout` nor `onScrollToIndexFailed`. Source: https://reactnative.dev/docs/flatlist#scrolltoindex
- **Handle `onScrollToIndexFailed` on variable-height lists that scroll programmatically**: "Used to handle failures when scrolling to an index that has not been measured yet." - the documented recovery is to "compute your own offset and `scrollTo` it, or scroll as far as possible and then try again after more items have been rendered". Why: without the handler there is no recovery path when the target row is unmeasured. Smell: deep-link or jump-to-message code calling `scrollToIndex` with no failure handler. Source: https://reactnative.dev/docs/virtualizedlist#onscrolltoindexfailed
- **Give `SectionList.scrollToLocation` either `getItemLayout` or a failure handler**: "You cannot scroll to locations outside the render window without specifying the `getItemLayout` or `onScrollToIndexFailed` prop." - and pass `viewOffset` when sticky headers are on, as the target "may be covered by a sticky header". Why: sections far from the viewport have no measured offset. Smell: an alphabet index calling `scrollToLocation` on a `SectionList` with neither prop. Source: https://reactnative.dev/docs/sectionlist#scrolltolocation
- **Prefer `scrollToIndex` to `scrollToItem`**: "Requires linear scan through data - use `scrollToIndex` instead if possible." - keep the index you already have. Why: the scan runs on the JavaScript thread on every call and grows with the list. Smell: `scrollToItem({item})` in code that has the index in scope or could look it up in a map. Source: https://reactnative.dev/docs/flatlist#scrolltoitem
- **Pair `onRefresh` with a truthful `refreshing` value**: "Make sure to also set the `refreshing` prop correctly." - set it true when the refresh starts and false when it settles, including on error. Why: the built-in `RefreshControl` is driven only by that prop. Smell: `onRefresh={refetch}` with no `refreshing`, `refreshing={false}` hard-coded, or a flag that is never reset in a `catch` or `finally`. Source: https://reactnative.dev/docs/flatlist#onrefresh
- **Do not mix a custom `refreshControl` with `onRefresh` and `refreshing` on the list**: "The onRefresh and refreshing props are also ignored. Only works for vertical VirtualizedList." - put both props on the `RefreshControl` element instead. Why: the custom element "overrides the default `<RefreshControl>` component built internally". Smell: a list with `refreshControl={...}` and also list-level `onRefresh`, or a custom refresh control on a horizontal list. Source: https://reactnative.dev/docs/virtualizedlist#refreshcontrol
- **Set a threshold in every `viewabilityConfig`**: "At least one of the `viewAreaCoveragePercentThreshold` or `itemVisiblePercentThreshold` is required." - choose one and keep the config object stable across renders. Why: the callback has no definition of viewable without one. Smell: `viewabilityConfig={{minimumViewTime: 500}}` alone, or a config object literal created inline in render. Source: https://reactnative.dev/docs/flatlist#viewabilityconfig
- **Express `onEndReachedThreshold` in visible lengths, not pixels**: "How far from the end (in units of visible length of the list)" - `0.5` means half a screen from the end. Why: a pixel-sized number such as 200 asks for 200 screens, so `onEndReached` fires at once and pages are over-fetched. Smell: `onEndReachedThreshold={100}` or any value above single digits. Source: https://reactnative.dev/docs/virtualizedlist#onendreachedthreshold
- **Set `stickySectionHeadersEnabled` explicitly when both platforms must match**: "Only enabled by default on iOS because that is the platform standard there." - the default is `false` on Android and `true` on iOS. Why: a design reviewed on one platform behaves differently on the other. Smell: a `SectionList` with styled headers, no `stickySectionHeadersEnabled`, and a screenshot from one platform only. Source: https://reactnative.dev/docs/sectionlist#stickysectionheadersenabled
- **Never ship `disableVirtualization`** (deprecated): "You should only need to disable this for debugging purposes." - remove the prop and fix the underlying layout or key problem. Why: "Virtualization provides significant performance and memory optimizations". Smell: `disableVirtualization` or `disableVirtualization={true}` in committed code. Source: https://reactnative.dev/docs/virtualizedlist

## FlatList tuning

- **Implement `getItemLayout` when rows have a fixed size**: "`getItemLayout` is efficient if you have fixed size items" - return `{length, offset, index}` from constants. Why: it "removes the need for your `FlatList` to manage async layout calculations". Smell: a list of several hundred fixed-height rows with no `getItemLayout`, or one that computes layout by reading measured heights. Source: https://reactnative.dev/docs/flatlist#getitemlayout
- **Size `initialNumToRender` to one screen**: "This should be enough to fill the screen but not much more." - too low a value "may cause blank areas" on first paint, too high a value delays it. Why: "these items will never be unmounted as part of the windowed rendering". Smell: `initialNumToRender={50}` or `initialNumToRender={data.length}`, or a value of 2 on a list of short rows. Source: https://reactnative.dev/docs/flatlist#initialnumtorender
- **Lower `windowSize` only with the blank-area cost accepted**: "For a lower `windowSize`, you will have a bigger chance of seeing blank areas." - the default is 21, ten viewports either side. Why: a smaller window "will result in fewer items mounted simultaneously, saving memory". Smell: `windowSize={2}` or `windowSize={3}` on a fast-scrolling feed with no comment on the trade-off, or a raised value on a list of heavy rows. Source: https://reactnative.dev/docs/optimizing-flatlist-configuration#windowsize
- **Raise `maxToRenderPerBatch` with care**: "More items per batch means longer periods of JavaScript execution potentially blocking other event processing, like presses, hurting responsiveness." - the default is 10. Why: a bigger batch fills blank areas sooner at the price of slower touch response. Smell: `maxToRenderPerBatch={100}` on a list whose rows are pressable. Source: https://reactnative.dev/docs/optimizing-flatlist-configuration#maxtorenderperbatch
- **Treat `removeClippedSubviews` as a risk, not a free optimisation**: "Using this property may lead to bugs (missing content) in some circumstances - use at your own risk." - note the platform default: "On Android the default value is `true`." Why: "this does not save significant memory because the views are not deallocated, only detached". Smell: `removeClippedSubviews` or `removeClippedSubviews={true}` added to an iOS list in a commit that also reports missing rows. Source: https://reactnative.dev/docs/flatlist#removeclippedsubviews
- **Turn `removeClippedSubviews` off for rows that use transforms or absolute positioning**: "especially if you are doing complex things with transforms and/or absolute positioning" - the docs name this as where missing content shows up, mainly on iOS. Why: the same passage warns that this implementation "can have bugs, such as missing content (mainly observed on iOS)". Smell: swipeable, animated or overlapping rows inside a list with `removeClippedSubviews` enabled. Source: https://reactnative.dev/docs/optimizing-flatlist-configuration#removeclippedsubviews
- **Keep list rows shallow and logic-free**: "Try to avoid a lot of logic and nesting in your list items." - build a dedicated row component for long lists rather than reusing a full card. Why: "The more complex your components are, the slower they will render." Smell: a row that formats dates, filters arrays or renders a deep tree of wrappers on every render. Source: https://reactnative.dev/docs/optimizing-flatlist-configuration#use-basic-components
- **Use thumbnails, not full-size images, in rows**: "use a cropped version or thumbnail for list items, as small as possible" - request a sized variant from the image service. Why: "The heavier your components are, the slower they render." Smell: a row `Image` whose `uri` is the original upload or has no size parameter. Source: https://reactnative.dev/docs/optimizing-flatlist-configuration#use-light-components
- **Memoise row components**: "`React.memo()` creates a memoized component that will be re-rendered only when the props passed to the component change." - pass primitives or stable references so the comparison can succeed; with React Compiler enabled this is automatic. Why: without it every mounted row re-renders when the list parent does. Smell: a plain function row receiving a new inline object or closure per render. Source: https://reactnative.dev/docs/optimizing-flatlist-configuration#use-memo
- **Do not define `renderItem` inline in JSX** (without React Compiler): "move the `renderItem` function outside of the returned JSX" - then "ensure that it is wrapped in a `useCallback` hook to prevent it from being recreated each render". With React Compiler enabled the compiler memoises the function, so the manual `useCallback` is not needed. Why: a new function identity on each parent render defeats the list's `PureComponent` check. Smell: `renderItem={({item}) => <Row item={item} onPress={() => open(item.id)} />}` in a component that re-renders often. Source: https://reactnative.dev/docs/optimizing-flatlist-configuration#avoid-anonymous-function-on-renderitem

## ScrollView and RefreshControl

- **Set `refreshing` to true inside `onRefresh`**: "`refreshing` is a controlled prop, this is why it needs to be set to `true` in the `onRefresh` function otherwise the refresh indicator will stop immediately." - drive it from state or from the query's fetching flag. Why: the native control does not keep spinning by itself. Smell: `<RefreshControl refreshing={false} onRefresh={load} />`. Source: https://reactnative.dev/docs/refreshcontrol#example
- **Use `refreshControl` only on vertical scroll views**: "Only works for vertical ScrollViews (`horizontal` prop must be `false`)." - a horizontal carousel needs another refresh affordance. Why: the prop is ignored otherwise and the feature silently disappears. Smell: `horizontal` and `refreshControl` on the same `ScrollView`. Source: https://reactnative.dev/docs/scrollview#refreshcontrol
- **Throttle scroll handlers that do real work**: "This may be useful when expensive work is performed in response to scrolling." - set `scrollEventThrottle` to an interval in milliseconds, or move the work to a native-driven `Animated.event`. Why: `onScroll` "Fires at most once per frame during scrolling", so an expensive handler runs up to once per frame on the JavaScript thread. Smell: `onScroll={e => setOffset(e.nativeEvent.contentOffset.y)}` with no throttle. Source: https://reactnative.dev/docs/scrollview#scrolleventthrottle
- **Do not reorder content under `maintainVisibleContentPosition`**: "For now, don't re-order the content of any ScrollViews or Lists that use this feature." - append or prepend only. Why: reordering "will probably cause jumpiness and jank". Smell: a chat or feed list with `maintainVisibleContentPosition` whose data is re-sorted on update. Source: https://reactnative.dev/docs/scrollview#maintainvisiblecontentposition
- **Do not combine `stickyHeaderIndices` with `horizontal`**: "This property is not supported in conjunction with `horizontal={true}`." - sticky children exist for vertical scrolling only. Why: the prop has no effect and the header scrolls away. Smell: both props on one `ScrollView` or `FlatList`. Source: https://reactnative.dev/docs/scrollview#stickyheaderindices

## Animated

- **State `useNativeDriver` in every animation config**: "Animations without a `useNativeDriver` property will default to false for legacy reasons, but emit a warning (and typechecking error in TypeScript)." - the option is marked Required for `timing`, `spring`, `decay` and `event`. Why: an omitted option silently runs the animation on the JavaScript thread. Smell: `Animated.timing(value, {toValue: 1, duration: 300})` with no `useNativeDriver` key. Source: https://reactnative.dev/docs/animations#using-the-native-driver
- **Use the native driver for `transform` and `opacity` animations**: "Once the animation has started, the JS thread can be blocked without affecting the animation." - set `useNativeDriver: true` whenever only non-layout properties are animated. Why: without it `Animated` "calculates each keyframe on-demand on the JavaScript thread". Smell: `useNativeDriver: false` on a fade, slide, scale or rotation. Source: https://reactnative.dev/docs/animated#using-the-native-driver
- **Do not drive layout properties with the native driver**: "you can only animate non-layout properties: things like `transform` and `opacity` will work, but Flexbox and position properties will not" - animate `translateX` or `scale` instead of `left`, `width` or `height`, or use `LayoutAnimation`. Why: layout properties are outside what the native driver supports. Smell: `useNativeDriver: true` on a value bound to `height`, `width`, `top`, `margin*` or `flex`. Source: https://reactnative.dev/docs/animations#caveats
- **Keep one driver per animated value**: "Animated values are only compatible with one driver" - if any animation on a value uses the native driver, "make sure every animation on that value also uses the native driver". Why: a value started on one driver cannot be handed to the other, so the second animation fails. Smell: the same `Animated.Value` passed to one `timing` call with `useNativeDriver: true` and another with `false`. Source: https://reactnative.dev/docs/animations#using-the-native-driver
- **Bind scroll-linked animation through a native-driven `Animated.event`**: "without the native driver, the animation will always run a frame behind the gesture due to the async nature of React Native" - use `Animated.event([...], {useNativeDriver: true})` on an `Animated.ScrollView` or `Animated.FlatList`. Why: a JavaScript `onScroll` handler makes a collapsing header lag the finger. Smell: `onScroll` calling `value.setValue(...)` or `setState` to move a header. Source: https://reactnative.dev/docs/animations#using-the-native-driver
- **Do not pass `useNativeDriver: true` to an `Animated.event` used by `PanResponder`**: "This means it does not work with `PanResponder` but does work with things like `ScrollView#onScroll`." - keep the pan handler on the JavaScript driver or use a native gesture library. Why: with `Animated.event` the native driver "will only work with direct events and not bubbling events". Smell: `onPanResponderMove: Animated.event([null, {dx: pan.x}], {useNativeDriver: true})`. Source: https://reactnative.dev/docs/animations#caveats
- **Set `isInteraction: false` on long or looping animations near lists**: "When an animation is running, it can prevent `VirtualizedList` components from rendering more rows." - spinners, shimmer placeholders and pulsing badges should not count as interactions. Why: animations create an interaction handle by default, and the list renders distant rows only after interactions. Smell: `Animated.loop(...)` of a skeleton placeholder inside or beside a `FlatList` with no `isInteraction: false`. Source: https://reactnative.dev/docs/animations#caveats
- **Create each `Animated.Value` once per component instance**: "Typically initialized with `useAnimatedValue(0);` or `new Animated.Value(0);` in class components." - in function components use `useAnimatedValue` or hold the value in a ref. Why: a value constructed in the render body is replaced on every render and the running animation is lost. Smell: `const fade = new Animated.Value(0)` at the top level of a function component. Source: https://reactnative.dev/docs/animated#value
- **Render animated values only through animatable components**: "Only animatable components can be animated." - use `Animated.View`, `Animated.Text`, `Animated.Image`, `Animated.ScrollView`, `Animated.FlatList`, `Animated.SectionList` or `createAnimatedComponent`. Why: these components "do targeted native updates to avoid the cost of the React render and reconciliation process on every frame". Smell: an `Animated.Value` or interpolation inside the `style` of a plain `View`. Source: https://reactnative.dev/docs/animated#animatable-components
- **Check `finished` in the `start` callback**: "then it will receive `{finished: false}`" - follow-up work that assumes the end state must run only when `finished` is true. Why: the callback also fires when `stop()` interrupts the animation, for example by a gesture or a competing animation. Smell: `anim.start(() => setVisible(false))` or `start(() => navigation.goBack())` with no `finished` check. Source: https://reactnative.dev/docs/animated#working-with-animations
- **Do not read an animated value synchronously**: "there is no way to synchronously read the value because it might be driven natively" - use `stopAnimation(callback)` for the final value or `addListener` for recent ones. Why: the JavaScript copy is stale while the native driver runs. Smell: `value._value` or `value.__getValue()` in component code. Source: https://reactnative.dev/docs/animatedvalue#addlistener
- **Use `addListener` sparingly and never for per-frame UI**: "use it sparingly since it might have performance implications in the future" - reserve it for coarse state changes such as snapping to an option. Why: listener callbacks arrive asynchronously, so UI driven from them is "less sensitive to a few frames of lag" only when the change is coarse. Smell: `value.addListener(({value}) => setState(value))` feeding a style. Source: https://reactnative.dev/docs/animations#responding-to-the-current-animation-value
- **Drive each value from one mechanism at a time**: "can only be driven by one mechanism at a time" - starting a new animation or calling `setValue` stops the previous one. Why: a stray `setValue` in an effect or handler cancels the running animation with no error. Smell: `value.setValue(...)` in a handler that can fire while a `timing` or `spring` on the same value is running. Source: https://reactnative.dev/docs/animatedvalue
- **Clamp interpolations that must stay in range**: "The default value is `extend` but you can use `clamp` to prevent the output value from exceeding `outputRange`." - set `extrapolate: 'clamp'` for opacity, scale and header offsets. Why: over-scroll and spring overshoot push the input beyond `inputRange`, giving negative opacity or an inverted scale. Smell: `interpolate({inputRange: [0, 100], outputRange: [1, 0]})` on a scroll offset with no `extrapolate`. Source: https://reactnative.dev/docs/animations#interpolation
- **Configure a spring with one parameter family**: "you can only define one of bounciness/speed, tension/friction, or stiffness/damping/mass, but not more than one" - choose one set and delete the rest. Why: mixing families is invalid configuration. Smell: `Animated.spring(v, {tension: 40, bounciness: 8, ...})` or `stiffness` next to `friction`. Source: https://reactnative.dev/docs/animated#spring
- **Set `stopTogether: false` when parallel animations must finish independently**: "By default, if one of the animations is stopped, they will all be stopped." - the same default applies to every composed group. Why: interrupting one track otherwise freezes the others mid-way. Smell: `Animated.parallel([...])` where one child is stopped by a gesture and the rest are expected to complete. Source: https://reactnative.dev/docs/animated#parallel
- **Add `perspective` when animating `rotateX` or `rotateY`**: "At this time some animations may not render on Android without it." - put `{perspective: n}` in the same `transform` array. Why: the flip works on iOS and shows nothing on Android. Smell: `transform: [{rotateY: spin}]` with no `perspective` entry. Source: https://reactnative.dev/docs/animations#bear-in-mind
- **Animate image size with a scale transform, not `width` and `height`**: "Instead, use the `transform: [{scale}]` style property to animate the size." - this also keeps the animation eligible for the native driver. Why: on iOS each size change means the image "is re-cropped and scaled from the original image". Smell: an `Animated.Image` whose `width` or `height` is bound to an animated value. Source: https://reactnative.dev/docs/performance#animating-the-size-of-an-image-drops-ui-thread-fps
- **Do not hand-roll animation loops with `requestAnimationFrame`**: "In general, you shouldn't need to call this yourself - the animation APIs will manage frame updates for you." - express the motion with `Animated` or `LayoutAnimation`. Why: a manual loop calling `setState` re-renders React on every frame. Smell: a recursive `requestAnimationFrame` callback that calls `setState` with a position or opacity. Source: https://reactnative.dev/docs/animations#requestanimationframe
- **Type animated refs with `*Instance` types** (0.87+): "This also replaces the removed `Animated.LegacyRef` type." - use `ViewInstance`, `FlatListInstance` and their siblings for both plain and `Animated` variants. Why: under the Strict TypeScript API "component type names no longer work as ref types". Smell: `useRef<FlatList>(null)`, `useRef<Animated.View>(null)` or a cast through `Animated.LegacyRef`. Source: https://reactnative.dev/docs/strict-typescript-api

## LayoutAnimation

- **Call `LayoutAnimation` before the state update it should animate**: "A common way to use this API is to call it before updating the state hook in functional components" - `configureNext` applies to the next layout only. Why: the docs describe it as scheduling "an animation to happen on the next layout", so a call placed after the render has committed animates nothing or the wrong change. Smell: `setExpanded(!expanded); LayoutAnimation.easeInEaseOut();` in that order, or the call inside an effect. Source: https://reactnative.dev/docs/layoutanimation
- **Delete `setLayoutAnimationEnabledExperimental` calls on the New Architecture**: "calling `setLayoutAnimationEnabledExperimental` is unnecessary (it is a no-op)" - layout animations are enabled automatically; only the Legacy Architecture on Android needed the flag. Why: dead platform branching in the entry file. Smell: `UIManager.setLayoutAnimationEnabledExperimental?.(true)` guarded by `Platform.OS === 'android'` in a 0.88 or SDK 58 app. Source: https://reactnative.dev/docs/layoutanimation
- **Use `LayoutAnimation` only for animations that never need interrupting**: "`LayoutAnimation` only works for fire-and-forget animations" - if the motion must follow a finger or be cancelled, use `Animated`. Why: it "provides much less control than `Animated` and other animation libraries". Smell: `LayoutAnimation.configureNext` in a drag handler or for a sheet the user can swipe back. Source: https://reactnative.dev/docs/performance#dropping-js-thread-fps-because-of-doing-a-lot-of-work-on-the-javascript-thread-at-the-same-time

## Gestures

- **Reset gesture state in the terminate handler as well as release**: "or might be taken by the OS without asking" - handle `onResponderTerminate` or `onPanResponderTerminate` the same way as a cancelled gesture. Why: the responder can be taken by another view or by the system, and `onResponderRelease` then never fires. Smell: a drag that sets a pressed or dragging flag in grant and clears it only in release. Source: https://reactnative.dev/docs/gesture-responder-system#responder-lifecycle
- **Use capture handlers when a parent must win the touch**: "it should have a `onStartShouldSetResponderCapture` handler which returns true" - bubbling gives the deepest view priority, so a parent needs the capture phase. Why: with plain `*ShouldSetResponder` handlers "the deepest component will become responder". Smell: a parent swipe container whose child buttons swallow the gesture, patched with `pointerEvents='none'`. Source: https://reactnative.dev/docs/gesture-responder-system#capture-shouldset-handlers

## JavaScript thread and frames

- **Remove `console.*` calls from production bundles**: "When running a bundled app, these statements can cause a big bottleneck in the JavaScript thread." - strip them at build time with the documented Babel plugin, and remove logging middleware. Why: "A third party library could also call them." Smell: `console.log` in render paths or list rows, or a logger middleware with no development guard. Source: https://reactnative.dev/docs/performance#using-consolelog-statements
- **Measure performance in release builds only**: "JavaScript thread performance suffers greatly when running in dev mode." - a regression or an improvement claimed from a debug build is not evidence. Why: "a lot more work needs to be done at runtime to provide you with good warnings and error messages". Smell: a pull request quoting frame rates or timings taken from a development build or with the dev server attached. Source: https://reactnative.dev/docs/performance#running-in-development-mode-devtrue
- **Defer non-urgent work until the JavaScript thread is idle**: "Deferring work until the JS thread is idle (for example, with `requestIdleCallback`) can be a good approach" - schedule analytics, cache warming and similar tasks this way. Why: work done during a transition shows up as slow navigation, the most common manifestation the docs name. Smell: heavy synchronous work in a screen's mount effect or directly in an `onPress` that also navigates. Source: https://reactnative.dev/docs/performance#dropping-js-thread-fps-because-of-doing-a-lot-of-work-on-the-javascript-thread-at-the-same-time
- **Wrap heavy `onPress` work in `requestAnimationFrame`**: "wrap any action inside of your `onPress` handler in `requestAnimationFrame`" - let the press feedback paint first. Why: otherwise "we won't see that effect until after the `onPress` function has returned". Smell: an `onPress` that sets state causing a large re-render, with touch feedback visibly late. Source: https://reactnative.dev/docs/performance#my-touchablex-view-isnt-very-responsive
- **Do not use `setTimeout(fn, 0)` where a frame boundary is meant**: "`requestAnimationFrame(fn)` is not the same as `setTimeout(fn, 0)`" - the former "will fire after all the frames have flushed", the latter as soon as possible. Why: a zero timeout can run before the pending frame is drawn. Smell: `setTimeout(() => measureOrAnimate(), 0)` used to wait for a paint. Source: https://reactnative.dev/docs/timers
- **Prefer a native stack navigator for screen transitions**: "the transition animations are executed on the native main UI thread, so they are not interrupted by frame drops on the JavaScript thread" - the docs name `@react-navigation/native-stack` as the example. Why: a JavaScript-based stack animates on the thread that is also mounting the new screen. Smell: a JavaScript stack navigator chosen with no need for its custom transitions. Source: https://reactnative.dev/docs/performance#ui-frame-rate-main-thread
- **Turn `renderToHardwareTextureAndroid` off when the view stops moving** (Android): "If you don't plan to move a view anymore, turn this property off." - enable it for the duration of the animation only. Why: "Be careful not to overuse this or your memory usage could go through the roof." Smell: `renderToHardwareTextureAndroid` hard-coded to true on static content or on every list row. Source: https://reactnative.dev/docs/performance#moving-a-view-on-the-screen-scrolling-translating-rotating-drops-ui-thread-fps
- **Do not enable `needsOffscreenAlphaCompositing` without a measured need**: "it greatly increases the per-frame load on the GPU in most cases" - it is disabled by default. Why: the cost is paid on every frame the view is drawn. Smell: `needsOffscreenAlphaCompositing` on an animated container or a list row. Source: https://reactnative.dev/docs/profiling#too-much-gpu-work
- **Do not mount new UI in the middle of an animation or gesture**: "You're constructing new UI during the animation/interaction (e.g. loading in new content during a scroll)." - postpone the mount until the interaction ends or simplify what is mounted. Why: the docs state there is no quick mitigation "unless you're able to postpone creating new UI until after the interaction". Smell: a state update that mounts a large subtree fired from `onScroll` or at the start of a transition. Source: https://reactnative.dev/docs/profiling#creating-new-views-on-the-ui-thread
- **Reserve `setNativeProps` for continuous updates that state cannot keep up with**: "Direct manipulation will not be a tool that you reach for frequently." - try state and memoisation first. Why: it "stores state in the native layer (DOM, UIView, etc.) and not within your React components, which makes your code more difficult to reason about". Smell: `ref.current.setNativeProps({style: ...})` for a one-off change a state update would handle. Source: https://reactnative.dev/docs/the-new-architecture/direct-manipulation-new-architecture
- **Do not set the same prop from `setNativeProps` and from render**: "whatever value was previously set from `setNativeProps` will be completely ignored and overridden" - give each property one owner. Why: the next re-render silently reverts the imperative value. Smell: `setNativeProps({opacity})` on a view whose `style` also sets `opacity` from props or state. Source: https://reactnative.dev/docs/the-new-architecture/direct-manipulation-new-architecture#avoiding-conflicts-with-the-render-function
- **Measure views in `useLayoutEffect`**: "The best way to invoke those methods is in a `useLayoutEffect` hook" - call `measure` or `measureInWindow` there, not in `useEffect` or a timeout. Why: it gives "the most recent values for those measurements" and lets the change apply in the same frame. Smell: `setTimeout(() => ref.current.measure(...), 0)` or measuring in `useEffect` followed by a visible jump. Source: https://reactnative.dev/docs/the-new-architecture/layout-measurements
- **Call measure methods on native-backed refs only**: "composite components that aren't directly backed by a native view" - these do not expose the methods; forward the ref to the underlying `View`. Why: this "will generally include most components that you define in your own app". Smell: `cardRef.current.measure(...)` where `Card` is a custom component that does not forward its ref. Source: https://reactnative.dev/docs/the-new-architecture/layout-measurements
- **Do not use `performance.timeOrigin` as app start time**: "Provides the number of milliseconds from the UNIX epoch until system boot, instead of the number of milliseconds from the UNIX epoch until app startup." - the docs mark it as partial support; read `performance.rnStartupTiming` for startup marks, a React Native specific extension. Why: startup telemetry computed from `timeOrigin` is wrong by the device's uptime. Smell: `Date.now() - performance.timeOrigin` reported as time since launch. Source: https://reactnative.dev/docs/global-performance#timeorigin

## JavaScript loading and bundle size

- **Keep Hermes as the engine**: "Hermes is used by default by React Native and no additional configuration is required to enable it." - the same holds for Expo, where Hermes is the default engine; opting out needs a stated reason. Why: in release builds "JavaScript code is fully compiled to bytecode ahead of time". Smell: `jsEngine: 'jsc'` in app config, or the community JavaScriptCore package added without justification. Source: https://reactnative.dev/docs/hermes
- **Lazy-load screen-level components**: "you should consider lazy-loading screen-level components in your app, so that adding new screens to your app does not increase its startup time" - use React `lazy` with a `Suspense` boundary. Why: "Parsing and running JavaScript code requires memory and time." Smell: a root navigator that statically imports every screen, including rarely visited ones. Source: https://reactnative.dev/docs/optimizing-javascript-loading#recommended-lazy-load-large-components
- **Keep module scope free of side effects**: "Most modules in React apps should not have any side effects." - move subscriptions, global patches and registrations into explicit initialisers. Why: lazy loading and inlined requires "can change the behavior of your app" when modules act on import. Smell: `EventEmitter.addListener(...)`, `global.x = ...` or a registry call at the top level of a component module. Source: https://reactnative.dev/docs/optimizing-javascript-loading#tip-avoid-module-side-effects
- **Do not assume inline requires in Expo projects**: "in Expo projects, `require` calls are not inlined by default" - the React Native CLI inlines `require` calls automatically, Expo needs `inlineRequires: true` in the Metro config. Why: startup advice written for one toolchain does not hold on the other. Smell: a `metro.config.js` copied between a CLI project and an Expo project with the transform options left unchecked. Source: https://reactnative.dev/docs/optimizing-javascript-loading#advanced-automatically-inline-require-calls
- **Exclude side-effect modules from require inlining**: "you may want to exclude certain modules from this optimization, or disable it entirely" - list them in `inlineRequires.blockList` or `nonInlinedRequires`. Why: inlining "changes the order in which modules are evaluated, and can even cause some modules to _never_ be evaluated". Smell: a polyfill, logger set-up or global patch imported for its side effect in a project with `inlineRequires: true` and no block list. Source: https://reactnative.dev/docs/optimizing-javascript-loading#pitfalls-of-inline-requires
- **Do not configure RAM bundles with Hermes**: "Hermes bytecode is not compatible with the RAM bundle format" - remove the setting; Hermes covers the same use cases. Why: the docs mark the format as not supported when using Hermes. Smell: `bundleCommand: 'ram-bundle'` or `BUNDLE_COMMAND='ram-bundle'` in a Hermes project. Source: https://reactnative.dev/docs/optimizing-javascript-loading#advanced-use-random-access-module-bundles-non-hermes
- **Import `Platform` directly from `react-native` in each file** (Expo): "If you re-export `Platform.OS` from a different module, it will not be removed from the production bundle." - no `isIOS` helper modules. Why: platform shaking "runs on a per-file basis". Smell: `export const isAndroid = Platform.OS === 'android'` in a shared utils file, imported across the app to gate platform code. Source: https://docs.expo.dev/guides/tree-shaking/#platform-shaking
- **Guard development-only code with `__DEV__` or `process.env.NODE_ENV`** (Expo): "use the `process.env.NODE_ENV` environment variable or the non-standard `__DEV__` global boolean" - write the check inline so it can be folded. Why: after constant folding "The unreachable conditions are removed during" minification. Smell: debug menus or mock servers gated by a runtime config value or a helper function rather than `__DEV__`. Source: https://docs.expo.dev/guides/tree-shaking/#remove-development-only-code
- **Write `import` and `export`, not CommonJS, in application code** (Expo): "Files that use `module.exports` and `require` will not be tree-shaken." - this includes shared packages in a monorepo. Why: tree shaking "can only run on modules that use `import` and `export` syntax". Smell: `module.exports = {...}` in app source, or a workspace package compiled to CommonJS only. Source: https://docs.expo.dev/guides/tree-shaking/#remove-unused-imports-and-exports
- **Do not add `@babel/plugin-transform-modules-commonjs` to an Expo Babel config**: "This will break tree-shaking across your project." - Expo applies its own import support. Why: the plugin converts ESM to CommonJS before the optimiser sees it. Smell: the plugin listed in `babel.config.js`, often copied from a Jest set-up. Source: https://docs.expo.dev/guides/tree-shaking/#remove-unused-imports-and-exports
- **Enable `inlineRequires` in Expo only together with tree shaking**: "Avoid using this feature without Expo tree shaking as it will move modules around in ways that can change the execution order of side-effects." - enable both or neither. Why: with tree shaking on, side-effect modules are tracked and kept in order. Smell: `inlineRequires: true` in an Expo `metro.config.js` with no tree-shaking environment flags in the build. Source: https://docs.expo.dev/guides/tree-shaking/#side-effects
- **Strip console calls through the minifier in Expo**: "Use the `drop_console` option in the Terser minifier config." - pass an array to keep `warn` and `error`. Why: default minification leaves logs in the production bundle. Smell: a production Expo build with verbose `console.log` output and no `drop_console` or Babel removal plugin. Source: https://docs.expo.dev/guides/minify/#remove-console-logs
- **Never commit or share the Expo Atlas export casually**: "Treat it like your source code and only share it with people you trust." - keep `.expo/atlas.jsonl` out of version control and public artefacts. Why: it contains the source of every bundled module, "including the values of inlined" public environment variables. Smell: `.expo/atlas.jsonl` in a commit, a public CI artefact or an issue attachment. Source: https://docs.expo.dev/guides/analyzing-bundles/#using-expo-atlas-with-npx-expo-export
- **Do not publish source maps with a production web build**: "Avoid publishing source maps to production" - generate them for analysis and upload them to the error tracker only. Why: the docs cite both security issues and performance issues. Smell: `--source-maps` on the export step whose output directory is deployed as is. Source: https://docs.expo.dev/guides/analyzing-bundles/#analyzing-bundle-size-with-source-map-explorer

## React Compiler and New Architecture in Expo

- **Drop manual memoisation in compiled code**: "You can remove instances of `useCallback`, `useMemo`, and `React.memo` in favor of the automatic memoization." - new code in a compiler-enabled project should not add them by habit. Why: the compiler "automatically memoizes components and hooks". Smell: fresh `useCallback` and `useMemo` wrappers in a project with React Compiler on and no opt-out directive. Source: https://docs.expo.dev/guides/react-compiler/#usage
- **Migrate hot class components to functions**: "Class components will not be optimized." - convert the ones on frequently rendered paths such as list rows. Why: they keep re-rendering as before while the surrounding tree is memoised. Smell: a class component used as a list row or inside a frequently updating screen in a compiler-enabled app. Source: https://docs.expo.dev/guides/react-compiler/#usage
- **Remove the standalone compiler lint plugin on SDK 55 and later**: "React Compiler lint rules are included by default with `eslint-config-expo` in SDK 55 and later." - uninstall `eslint-plugin-react-compiler` and delete it from the ESLint config. Why: the docs state that a previously installed plugin can be uninstalled and removed from the ESLint configuration. Smell: `eslint-plugin-react-compiler` in `package.json` of an SDK 58 project. Source: https://docs.expo.dev/guides/react-compiler/#enabling-the-linter
- **Delete `newArchEnabled` from app config** (SDK 55+): "The New Architecture is always enabled and cannot be disabled." - the legacy architecture is available on SDK 54 or earlier only. Why: the flag has no effect and suggests a choice that no longer exists. Smell: `newArchEnabled: false` or `true` in `app.json` of an SDK 58 project, or a library pinned for legacy architecture support. Source: https://docs.expo.dev/guides/new-architecture/

## Images in lists and on screen

- **Give every network image explicit dimensions**: "you will need to manually specify the dimensions of your image" - set `width` and `height` or an aspect ratio in style. Why: React Native does not size remote images automatically, which avoids layout that would "jump all around as images load". Smell: `<Image source={{uri}} />` with no size in `style`, rendering nothing. Source: https://reactnative.dev/docs/images#network-images
- **Keep `require` paths for images static**: "the image name in `require` has to be known statically" - select between static `require` calls instead of building the path. Why: the bundler resolves and packages images at build time. Smell: `require('./icons/' + name + '.png')` or a template string inside `require`. Source: https://reactnative.dev/docs/images#static-image-resources
- **Do not rely on the `cache` source property outside iOS**: "The `cache` source property gives you control over how the network layer interacts with the cache." - the reference marks the cache enum as iOS; on Android use a component with a cross-platform cache policy. Why: `only-if-cached` or `reload` behaviour tested on iOS is absent on Android. Smell: `source={{uri, cache: 'force-cache'}}` presented as the offline strategy for both platforms. Source: https://reactnative.dev/docs/images#cache-control
- **Keep `data:` URI images very small**: "This is recommended for very small and dynamic images only, like icons in a list from a DB." - serve larger images from a URL. Why: the encoded bytes travel through JavaScript and props on every render. Smell: base64 photos or avatars from an API response passed as `uri`. Source: https://reactnative.dev/docs/images#uri-data-images
- **Set `resizeMethod='resize'` for images much larger than their view** (Android only): "This should be used instead of `scale` when the image is much larger than the view." - the default `auto` uses heuristics; state it for camera photos shown as thumbnails. Why: decoding a full-size bitmap for a small view wastes memory. Smell: gallery or camera-roll thumbnails on Android with no `resizeMethod` and out-of-memory reports. Source: https://reactnative.dev/docs/image#resizemethod-android
- **Preload with `Image.prefetch`, not `Image.getSize`**: "however it is not optimized for that purpose" - `prefetch` downloads to the disk cache and is the method meant for this. Why: `getSize` "may in future be implemented in a way that does not fully load/download the image data". Smell: `Image.getSize(url, noop)` called in a loop to warm the cache. Source: https://reactnative.dev/docs/image#getsize
- **Set `recyclingKey` on `expo-image` inside recycling lists** (Android and iOS): "to prevent showing the previous source before the new one fully loads" - use the item id. Why: a recycled view keeps its old bitmap until the new one arrives. Smell: an `expo-image` `Image` in a FlashList row with no `recyclingKey`, and wrong avatars flashing while scrolling. Source: https://docs.expo.dev/versions/v58.0.0/sdk/image/#recyclingkey
- **Do not expect response headers to expire the `expo-image` disk cache**: "the disk cache does not follow the `Cache-Control` or `Expires` headers of the image response" - on Android and iOS, change the URL with a version parameter or set a new `cacheKey` to show an updated image. Why: a replaced avatar at the same URL keeps showing the old file. Smell: an image updated in place on the server with a stable URL and no `cacheKey`. Source: https://docs.expo.dev/versions/v58.0.0/sdk/image/#caching-images
- **Cap the `expo-image` disk cache on iOS**: "The disk cache has no size limit by default." - pass `maxDiskSize` to `Image.configureCache()`. Why: on Android the cache is bounded at 250 MB, on iOS it is bounded only by a one-week age rule. Smell: an image-heavy app with no `Image.configureCache` call and storage complaints on iOS. Source: https://docs.expo.dev/versions/v58.0.0/sdk/image/#caching-images
- **Do not use the `memory` cache policy as persistence**: "Memory cache may be purged very quickly to prevent high memory usage and the risk of out of memory exceptions." - keep the default `disk` or use `memory-disk`. Why: a memory-only image is fetched again after every purge and every launch. Smell: `cachePolicy='memory'` on list images or `cachePolicy='none'` with no reason given. Source: https://docs.expo.dev/versions/v58.0.0/sdk/image/#cachepolicy
- **Leave `allowDownscaling` on for large assets**: "Turning off this functionality could negatively impact the application's performance, particularly when working with large assets." - the default is `true`. Why: without downscaling the full-resolution bitmap is held for a small view. Smell: `allowDownscaling={false}` on list or grid images. Source: https://docs.expo.dev/versions/v58.0.0/sdk/image/#allowdownscaling
- **Match `placeholderContentFit` to `contentFit`**: "Using a lower-resolution placeholder may cause flickering due to scaling differences between it and the final image." - the placeholder defaults to `scale-down`, the image does not. Why: the swap from placeholder to image visibly resizes. Smell: `placeholder` set, `contentFit='cover'` set, no `placeholderContentFit`. Source: https://docs.expo.dev/versions/v58.0.0/sdk/image/#placeholder

## Build speed

- **Keep single-ABI flags out of release builds** (Android only): "don't forget to remove those flags as you want to build an apk/app bundle that works for all the ABIs" - `--active-arch-only` and `reactNativeArchitectures` are for local development. Why: a release built for one architecture does not install on devices with another. Smell: `reactNativeArchitectures=arm64-v8a` committed in the shared `gradle.properties` or passed in the release pipeline. Source: https://reactnative.dev/docs/build-speed#build-only-one-abi-during-development-android-only
- **Enable Gradle configuration caching** (Android only, 0.79+): "Since React Native 0.79, you can also enable Gradle Configuration Caching." - add the flag to `android/gradle.properties`. Why: it lets later builds "skip the Configuration phase". Smell: a 0.88 project whose `gradle.properties` lacks `org.gradle.configuration-cache=true` while native build time is a stated problem. Source: https://reactnative.dev/docs/build-speed#enable-configuration-caching-android-only
- **Prefer clean native builds on CI over a restored compiler cache**: "On CI, we recommend to do a full clean build, to avoid poisoned cache problems." - if `ccache` is restored anyway, set `compiler_check content`. Why: "`ccache` relies on timestamps to compute a cache hit", which fails when files are downloaded again on every run. Smell: a CI job restoring the `ccache` folder with the default timestamp check. Source: https://reactnative.dev/docs/build-speed#using-this-approach-on-a-ci
