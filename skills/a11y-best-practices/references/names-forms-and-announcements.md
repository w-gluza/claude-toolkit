# Accessibility Names, Forms and Announcement Rules (WAI-ARIA APG, WCAG 2.2, MDN)
Extracted 2026-11-08 from the w3c/aria-practices and w3c/wcag repositories, the mdn/content repository and the eslint-plugin-jsx-a11y rule docs.

## Accessible name computation

- **Know which naming source wins**: "The aria-labelledby property is used if present. If the name is still empty, the aria-label property is used if present. If the name is still empty, then host-language-specific attributes or elements are used if present." (for HTML form controls that is "The associated label element(s)", for `fieldset` "The first child legend element"), then content for roles named from content, then fallback attributes. Why: "User agents construct an accessible name string for an element by walking through a list of potential naming methods and using the first that generates a name." Smell: an `aria-label` added to an `input` that already has a `label`, with the author expecting both strings to be announced; only the `aria-label` survives. Source: https://www.w3.org/WAI/ARIA/apg/practices/names-and-descriptions/#name_calculation
- **Never set `aria-label` and `aria-labelledby` on the same element**: "Don't use both on the same element because `aria-labelledby` will take precedence over `aria-label` if both are applied." Why: the APG puts it as "the aria-label attribute ought to be removed if it is not used". Smell: a component that spreads both `aria-label={label}` and `aria-labelledby={labelId}` onto one element, so the `aria-label` is dead code that misleads reviewers. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-label#description
- **Do not override visible content with `aria-label` or `aria-labelledby` on buttons, links, tabs, headings or options**: "If an element with one of the above roles that supports naming from child content is named by using aria-label or aria-labelledby, content contained in the element and its descendants is hidden from assistive technology users unless the descendant content is referenced by aria-labelledby." Why: "It is strongly recommended to avoid using either of these attributes to override content of one of the above elements except in rare circumstances where hiding content from assistive technology users is beneficial." Smell: `<button aria-label="Submit">Save changes</button>` or a `<a aria-label="Pricing page">Pricing</a>`, where the visible word is no longer part of what is announced. Source: https://www.w3.org/WAI/ARIA/apg/practices/names-and-descriptions/#naming_with_child_content
- **Check that every id in `aria-labelledby` resolves and still says the right thing**: "The `aria-labelledby` property value can include content from elements that aren't even visible. While you should provide assistive technology users with the same content as all other users, you can include content from elements with the HTML `hidden` attribute, CSS `display: none`, and CSS `visibility: hidden` in the calculated name string." Why: "Because calculating the name of an element with `aria-labelledby` can be complex and reference hidden content, testing with assistive technologies to ensure the expected name is presented to users is very important." Smell: `aria-labelledby={headingId}` where the heading is behind a conditional render and is not in the DOM at all (the name becomes empty), or points at a hidden element whose text was changed for another purpose. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-labelledby#benefits_and_drawbacks
- **Do not rely on `title` or `placeholder` as the name**: "For the HTML input and textarea elements, the placeholder attribute is used as a fallback labeling mechanism if nothing else (including the title attribute) results in a label. It is better to use a label element, since it does not disappear visually when the user focuses the form control." Why: "Because the attributes used in fallback name calculation are not intended for naming, they typically yield low quality accessible names that are not effective." Smell: `<input type="search" placeholder="Search">` or `<input title="Postcode">` with no `label`, `aria-label` or `aria-labelledby`. Source: https://www.w3.org/WAI/ARIA/apg/practices/names-and-descriptions/#naming_with_fallback

## Naming controls and links

- **Name from visible text whenever the design has some**: "When a user interface includes visible text that could be used to provide an appropriate accessible name, using the visible text for the accessible name simplifies maintenance, prevents bugs, and reduces language translation requirements." Why: "When names are generated from text that exists only in markup and is never displayed visually, there is a greater likelihood that accessible names will not be updated when the user interface design or content are changed." Smell: a button with visible text "Export" plus `aria-label="Download report"` that a later copy change leaves out of sync. Source: https://www.w3.org/WAI/ARIA/apg/practices/names-and-descriptions/#naming_rule_visible_text
- **Reach for `aria-labelledby` before `aria-label` when a visible label exists**: "`aria-label` can be used in cases where text that could label the element is _not_ visible. If there is visible text that labels an element, use `aria-labelledby` instead." Why: "It is strongly recommended to prioritize the use of `aria-labelledby` over `aria-label` if a visible label exists for the element to reference and receive its name from." Smell: a `section` with a visible `h2` and `aria-label="Recent orders"` repeating the heading text by hand. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-label#description
- **Give every icon-only control a text name**: "A common example of such an element is a button containing an SVG icon without any text." and "the `aria-label` attribute can be used to define a string that labels the interactive element on which it is set." Why: "Both the WAI-ARIA specification and WCAG require all focusable, interactive elements to have an accessible name." Smell: `<button onClick={close}><CloseIcon /></button>` with no `aria-label` and an `svg` that is not `aria-hidden`. Lint: jsx-a11y/control-has-associated-label. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-label#description
- **Keep the visible label inside the accessible name**: "the words which visually label a component are also the words associated with the component programmatically." Why: "When they don't match, speech-input users who attempt to use the visible text label as a means of navigation or selection (e.g., "move to Password") will be unsuccessful." and "when the accessible name is different from the visible label, it may function as a hidden command that can be accidentally activated by speech-input users." Smell: `<button aria-label="Send message">Submit</button>`, or an icon button whose `aria-label` is "Remove" while its tooltip reads "Delete item". Source: https://www.w3.org/WAI/WCAG22/Understanding/label-in-name.html#intent
- **Name by function, not appearance**: "Convey function or purpose, not form. For example, if an icon that looks like the letter X closes a dialog, name it Close, not X." Why: WCAG adds that for symbolic glyphs "the accessible name should be the function the button serves (e.g., "Spell check" or "Check spelling"), not the visible symbolic characters." Smell: `aria-label="X"`, `aria-label="Hamburger"`, `aria-label=">"`, or `aria-label="Left"` on a navigation region. Source: https://www.w3.org/WAI/ARIA/apg/practices/names-and-descriptions/#naming_effectively
- **Do not put the role word in the name**: "Do NOT include a WAI-ARIA role name in the accessible name. For example, do not include the word button in the name of a button, the word image in the name of an image, or the word navigation in the name of a navigation region." Why: "Doing so would create duplicate screen reader output since screen readers convey the role of an element in addition to its name." Smell: `aria-label="Close button"`, `<nav aria-label="Main navigation">`, `alt="Image of a chart"`. Source: https://www.w3.org/WAI/ARIA/apg/practices/names-and-descriptions/#naming_effectively
- **Write link text that states the destination**: "Whenever possible, provide link text that identifies the purpose of the link without needing additional context." Why: "Assistive technology has the ability to provide users with a list of links that are on the web page. Link text that is as meaningful as possible will aid users who want to choose from this list of links." Smell: `<a href>click here</a>`, `<a href>here</a>`, `<a href>learn more</a>` repeated down a page. Lint: jsx-a11y/anchor-ambiguous-text. Source: https://www.w3.org/WAI/WCAG22/Understanding/link-purpose-in-context.html#intent
- **Extend a "Read more" link with its heading via `aria-labelledby` on itself plus the heading**: "In some cases, the most effective name for an element is its own content combined with the content of another element. Because aria-labelledby has highest precedence in name calculation, in those situations, it is possible to use aria-labelledby to reference both the element itself and the other element." Why: the example yields "a name for the link of "Read more... 7 ways you can help save the bees"", keeping the visible words in the name. Smell: a card component with `<a href>Read more</a>` and no reference to the card title, or an `aria-label` that drops the words "Read more". Source: https://www.w3.org/WAI/ARIA/apg/practices/names-and-descriptions/#naming_with_aria-labelledby
- **Give links and headings perceivable content**: "When assistive technologies render an element that gets its accessible name from its content, such as a link or button, the accessible name is the only content the user can perceive for that element." Why: an `a` or `h2` whose only child is hidden from assistive technology has no name at all. Smell: `<a href="/"><img src="logo.svg" alt="" /></a>`, `<a href><Icon aria-hidden /></a>`, `<h2><Icon /></h2>`. Lint: jsx-a11y/anchor-has-content, jsx-a11y/heading-has-content. Source: https://www.w3.org/WAI/ARIA/apg/practices/names-and-descriptions/#naming_with_child_content
- **Give every `iframe` a unique `title`**: "The main use of the `title` attribute is to label `iframe` elements for assistive technology." Why: the frame is otherwise announced with no indication of what it contains. Smell: `<iframe src={embedUrl} />` with no `title`, or several frames all titled "embed". Lint: jsx-a11y/iframe-has-title. Source: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Global_attributes/title#description

## Descriptions

- **Attach hints and format rules with `aria-describedby`**: "Authors supply a description when there is a need to associate additional information with an element, such as instructions or format requirements for an input field." Why: "Because descriptions are optional strings that are usually significantly longer than names, they are presented last, sometimes after a slight delay." Smell: a `<p class="hint">Use the format YYYY-MM-DD</p>` under an `input` with no `aria-describedby` linking the two. Source: https://www.w3.org/WAI/ARIA/apg/practices/names-and-descriptions/#names_and_descriptions_definition
- **Put instructions in a description, not in `aria-label`**: "To provide additional instructions or to clarify the UI, use visible text with `aria-describedby` or `aria-description`, not `aria-label`." Why: "Instructions should be accessible to all users, not just to those with screen readers". Smell: `aria-label="Password, at least 12 characters including a number"` on an `input` that has a visible label "Password". Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-label#description
- **Keep described content plain text**: "The `aria-describedby` content should only be a text string. If there are important underlying semantics in the content, consider using `aria-details`." Why: "Descriptions are reduced to text strings." so lists, links and headings inside the referenced element are flattened. Smell: `aria-describedby` pointing at a `ul` of password rules or at a block that contains a link. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-describedby#description
- **Do not use `title` as the only description**: "A visible description together with aria-describedby is generally recommended." Why: "Note that the title attribute might not be accessible to some users, in particular sighted users not using a screen reader and not using a pointing device that supports hover (e.g., a mouse)." Smell: `<input pattern="..." title="Five digits">` as the sole explanation of the expected format. Source: https://www.w3.org/WAI/ARIA/apg/practices/names-and-descriptions/#describing_with_title

## Form labels and groups

- **Associate every input with a `label`**: "It does not suffice to have plain text adjacent to the `<input>` element. Rather, usability and accessibility requires the inclusion of either implicit or explicit `label`". Why: "The first example is inaccessible: no relationship exists between the prompt and the `<input>` element." Smell: `<span>Name</span><input />` or `<div class="label">Name</div>` next to an `input` with no `for`/`id` pair. Lint: jsx-a11y/label-has-associated-control. Source: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/input#associated_labels
- **Prefer explicit `for`/`id` association**: "Generally, we recommend using explicit association with the `for` attribute, to ensure compatibility with external tools and assistive technologies. In fact, you can simultaneously nest _and_ provide `id`/`for` for maximum compatibility." Why: "While common browser and screen reader combinations support implicit association, not all assistive technologies do." Smell: a wrapping `<label>Name <Input /></label>` in a design-system component with no `htmlFor`. Source: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/label#associating_a_label_with_a_form_control
- **Point `for` at the id of a labelable control, and only one**: "The first element in the document with an `id` attribute matching the value of the `for` attribute is the _labeled control_ for this `label` element - if the element with that `id` is actually a labelable element. If it is _not_ a labelable element, then the `for` attribute has no effect." Why: a `for` aimed at a wrapper does nothing and the control stays unnamed. Smell: `htmlFor={id}` where `id` lands on the wrapping `div`, or two inputs rendered with the same static `id="email"` on one page. Source: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/label#associating_a_label_with_a_form_control
- **Keep links and buttons out of `label`**: "Other than the implicitly associated form control, don't place additional interactive elements such as `a` or `button` inside a `<label>`." Why: "Doing so makes it difficult for people to activate the form input associated with the `label`." Smell: `<label><input type="checkbox" /> I accept the <a href="/terms">terms</a></label>`. Source: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/label#interactive_content
- **Group related controls in a `fieldset` with a `legend`**: "The HTML fieldset element can be used to group form controls, and the legend element can be used to give the group a name. For example, a group of radio buttons can be grouped together in a fieldset, where the legend element labels the group for the radio buttons." Why: "If a question is not programmatically associated with its answer options, assistive technology users may access the answers without being aware of the question." Smell: a radio group introduced by a `<p>` or `<h3>` question with the inputs in a bare `div`. Source: https://www.w3.org/WAI/ARIA/apg/practices/names-and-descriptions/#naming_with_legends
- **Make `legend` the first child of the `fieldset`, not a styled `div`**: "The caption for the fieldset is given by the first `legend` element nested inside it." Why: without it the APG notes the group falls back to the `title` attribute or nothing: "a fieldset element without a legend element child, but with a title attribute, gets its accessible name from the title attribute." Smell: `<fieldset><div className="legend">Delivery</div>...` or a `fieldset` with no `legend` at all. Source: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/fieldset#attributes
- **Placeholder is a hint, never the label**: "The placeholder should never be required to understand your forms. It is not a label, and should not be used as a substitute, because it isn't." Why: "once the user enters any text into the form control, or if the form control already has a value, the placeholder disappears." Smell: `<input placeholder="Email address" />` with no `label`; the same applies to `aria-placeholder` on a custom textbox, which "is used in addition to, not instead of, a label." Source: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/input#placeholders_are_not_accessible
- **Keep labels and instructions persistently available**: "When labels or instructions are provided, they need to be persistently available to users. In many cases, the best way to do this is to make them visually persistent as part of the UI." Why: "Providing labels and instructions (including examples of expected data formats) helps all users - but particularly those with cognitive, language, and learning disabilities - to enter information correctly." Smell: a floating label that disappears once the field has a value, or format instructions shown only in a tooltip on hover. Source: https://www.w3.org/WAI/WCAG22/Understanding/labels-or-instructions.html#intent
- **Build multipart labels with `aria-labelledby`, not by splitting the sentence**: "The solution is in an ARIA attribute called `aria-labelledby`. Its parameter is a string that consists of the IDs of the HTML elements you want to concatenate into a single accessible name." Why: for "Delete history after x days" the screen reader then says "Delete history after 21 days" instead of only the first half. Smell: `<label for="n">Delete history after</label><input id="n" /> days` where "days" is never part of the name. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Guides/Multipart_labels#problem

## Required, invalid and errors

- **Use `required` on native controls, `aria-required` only on custom ones**: "When a semantic HTML `input`, `select`, or `textarea` must have a value, it should have the `required` attribute applied to it." Why: "The `aria-required` attribute, like all ARIA states and properties, has no impact on element functionality." Smell: `<input aria-required="true" />` with validation done only in JavaScript, or a `div role="textbox"` with no `aria-required` while the design marks it mandatory. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-required#description
- **Show required state visibly and not by colour alone**: "If a form contains both required and optional form elements, the required elements should be indicated visually using a treatment that does not rely solely on color to convey meaning. Typically, descriptive text and/or an icon are used." Why: "Which elements are required should be apparent to all users." Smell: `required` set with no asterisk or "(required)" text, or a red label as the only cue. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-required#description
- **Set `aria-invalid="true"` when validation fails and tell the user**: "If a value is determined to be invalid or out-of-range, set `aria-invalid="true"` **and** tell the user there is an error." Why: "If you are creating your own form validation scripts, make sure to include `aria-invalid` on invalid form controls, along with styling (use the `[aria-invalid="true"]` attribute selector) and messaging". Smell: a `className={hasError ? 'input--error' : ''}` toggle with no `aria-invalid` attribute anywhere in the component. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-invalid#description
- **Do not flag empty required fields as invalid before the user submits**: "Do not set `aria-invalid="true"` on empty required elements until after the user attempts to submit the form. They may still be working on filling it out." Why: "When `aria-invalid` is used in conjunction with the `aria-required` attribute, `aria-invalid` should not be set to true before the form is submitted - only in response to validation." Smell: `aria-invalid={value === ''}` evaluated on first render. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-invalid#description
- **Identify errors in text and name the field**: "The error must be indicated in text." and "This SC requires that users be provided with information about the nature of the error, including the identity of the item in error." Why: "In the case of an unsuccessful form submission, it is not sufficient to only re-display the form without providing any hint that the submission failed." Smell: a red outline or an exclamation icon with no text, or a summary "Please fix the errors below" that does not say which fields. Source: https://www.w3.org/WAI/WCAG22/Understanding/error-identification.html#intent
- **Associate the message with the field and hide it when the field is valid**: "set `aria-invalid="true"` to define the object as being in an error state, then add the `aria-errormessage` attribute with the value being the `id` of the element (or elements) containing the error message text for that object." (`aria-describedby` is the other way to make the same programmatic connection). Why: "If the object is valid and you include the `aria-errormessage` attribute, make sure the element referenced is hidden, as the message it contains is not relevant." Smell: `<p className="error">{error}</p>` rendered after an `input` with neither `aria-describedby` nor `aria-errormessage`, or `aria-errormessage` pointing at an always-present empty element. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-errormessage#description
- **Let a live region carry errors that appear without a focus move**: "Often times, you will want the element with the error message to be an ARIA live region, such as when an error message is displayed to users after they have provided an invalid value." Why: "Adding the error message as an ARIA live region informs assistive technologies that the user may benefit from the error message content even if the error message wouldn't otherwise be conveyed to the user." Smell: a validation message inserted on `blur` into a plain `div` while focus has already moved to the next field. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-errormessage#description
- **Suggest the correction, not only the failure**: "ensure that users receive appropriate suggestions for correction of an input error if it is possible." Why: "For instance, "Email is not valid" would pass 3.3.1, but "Please provide a valid email address in the format name@domain.com" also conveys how it can be fixed and passes both." Smell: messages such as "Invalid input" or "Error" with no expected format or allowed values. Source: https://www.w3.org/WAI/WCAG22/Understanding/error-suggestion.html#intent
- **Add review, confirm or undo for legal, financial and data-destroying submissions**: "Provide ways for users to confirm, correct, or reverse important submissions." Why: "People with reading disabilities may transpose numbers and letters, and those with motor disabilities may hit keys by mistake. Providing the ability to reverse actions allows users to correct a mistake that could result in serious consequences." Smell: a one-click "Place order", "Transfer" or "Delete account" handler that submits immediately with no summary step, confirmation or undo. Source: https://www.w3.org/WAI/WCAG22/Understanding/error-prevention-legal-financial-data.html#brief

## Input purpose and re-entry

- **Add `autocomplete` tokens to fields that collect the user's own details**: "When these user input purposes are present, and if the technology supports doing so, the field purpose must be programmatically identifiable." Why: "assistive technologies may display familiar icons next to input fields to help users who have difficulties reading" and "The user is relieved of having to type the information and can instead confirm or, if needed, change the value of the field". Smell: `<input type="email" name="email" />` or a name, phone or address field with no `autocomplete`, an invented token such as `autocomplete="first-name"`, or `autocomplete="off"` on every input, since "What matters is whether or not the inputs programmatically expose their purpose." Lint: jsx-a11y/autocomplete-valid. Source: https://www.w3.org/WAI/WCAG22/Understanding/identify-input-purpose.html#intent
- **Do not ask for the same information twice in one process**: "Don't ask for the same information twice in the same activity." Why: "Requiring people to recall information previously entered can cause them to give up or re-enter the same information incorrectly. The autocomplete feature of browsers is not considered sufficient". Smell: a checkout that asks for the delivery address again on the billing step with no "same as delivery" option or pre-filled values. Source: https://www.w3.org/WAI/WCAG22/Understanding/redundant-entry.html#brief
- **Keep entered values when a submission fails**: "A user submits a checkout form with an incorrect credit card number in it. The page updates, showing an error message. Submitted information, such as credit card number, is not cleared from the form." Why: "Not having to repeatedly remember particular information reduces stress and the likelihood of mistakes." Smell: a submit handler that resets form state on a validation error, or a full navigation that re-renders empty fields. Source: https://www.w3.org/WAI/WCAG22/Understanding/redundant-entry.html#examples
- **Let password managers fill and users paste into login fields**: "if user agents and password managers are actively blocked from filling in the fields (for instance, by a script that prevents form fields from being automatically populated), or users are prevented from copy and paste operations (as they may rely on standalone/external third party password managers), then the page would fail this criterion unless an alternative is provided." Why: "A service that requires manual transcription of a verification code is not compliant." Smell: `onPaste={(e) => e.preventDefault()}` on a password or code field, `autocomplete="off"` on `type="password"`, or a one-time code split into six single-character inputs with no paste handling. Source: https://www.w3.org/WAI/WCAG22/Understanding/accessible-authentication-minimum.html#login-forms

## Page title and language

- **Give each page a descriptive `title`**: "help users find content and orient themselves within it by ensuring that each web page has a descriptive title." Why: "Titles identify the current location without requiring users to read or interpret page content." Smell: every route rendering the same `<title>App</title>`. Source: https://www.w3.org/WAI/WCAG22/Understanding/page-titled.html#intent
- **Update `document.title` on every client-side route change**: "In cases such as Single Page Applications (SPAs), where various distinct pages/views are all nominally served from the same URI and the content of the page is changed dynamically, the title of the page should also be changed dynamically to reflect the content or topic of the current view." Why: "a user agent may display the page title in the window title bar or as the name of the tab containing the page." Smell: a router that swaps the view with no title update, so the tab keeps the previous page's name. Source: https://www.w3.org/WAI/WCAG22/Understanding/page-titled.html#intent
- **Set `lang` on the `html` element**: "WCAG Success Criterion 3.1.1 **requires** that a page language is specified in a way which may be 'programmatically determined' (i.e., via the **`lang`** attribute)." Why: "Screen readers can load the correct pronunciation rules. Visual browsers can display characters and scripts correctly." Smell: `<html>` or `<Html>` in a document template with no `lang`. Lint: jsx-a11y/html-has-lang. Source: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Global_attributes/lang#accessibility_concerns
- **Use a valid BCP 47 tag that matches the real content language**: "If the attribute value is the _empty string_ (`lang=""`), the language is set to _unknown_; if the language tag is not valid according to BCP47, it is set to _invalid_." Why: WCAG defines the page language as "the language which is used most", so a wrong tag is as harmful as a missing one. Smell: `lang="english"`, `lang=""`, or a localised build that keeps `lang="en"` while serving Polish. Lint: jsx-a11y/lang. Source: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Global_attributes/lang#values
- **Mark passages in another language with their own `lang`**: "Indicate when words are in a different language." Why: "Speech synthesizers that support multiple languages will be able to speak the text in the appropriate accent with proper pronunciation. If changes are not marked, the synthesizer will try its best to speak the words in the default language it works in." Smell: a language switcher listing "Deutsch", "Français", "Polski" with no `lang` on each link, or a quoted foreign passage in a plain `blockquote`. Source: https://www.w3.org/WAI/WCAG22/Understanding/language-of-parts.html#brief
- **Put `lang` on the named element itself, not only on a child, when the name is in another language**: "Accessible names are "flat" strings, and don't contain any structure or information. Despite being correctly denoted in the underlying code or markup, changes in the natural language of content are not exposed to assistive technologies in these cases." Why: a workaround is "moving the lang language attribute to the element itself, rather than indicating a change of language on a child nodes inside the element". Smell: `<a href="/fr"><span lang="fr">Français</span></a>` where the link, read from a links list, is pronounced in the page language. Source: https://www.w3.org/WAI/WCAG22/Understanding/language-of-parts.html#intent

## Live regions

- **Default to `polite`; reserve `assertive` for time-critical messages**: "Normally, only `aria-live="polite"` is used." and "`aria-live="assertive"` should only be used for time-sensitive/critical notifications that absolutely require the user's immediate attention." Why: "a change to an assertive live region will interrupt any announcement a screen reader is currently making. As such, it can be extremely annoying and disruptive and should only be used sparingly." Smell: `aria-live="assertive"` or `role="alert"` on an autosave "Saved" indicator, a character counter or a "Copied to clipboard" toast. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Guides/Live_regions#live_regions
- **Render the live region first, then change its content**: "Establish the live region before updating its content. Start with an empty live region, then allow time for it to be exposed to assistive technologies before updating its content." Why: "Assistive technologies will generally only announce _dynamic_ changes in the content of a live region." and "The most reliable way to ensure that live regions are registered is to include them in the initial markup." Smell: `{message && <div role="status">{message}</div>}`, which mounts the region and its text in the same render, or a toast library that appends a new `role="alert"` node per toast. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Guides/Live_regions#live_regions
- **Use `role="alert"` for dynamically triggered errors only, into a primed container**: "The most important thing to know about the `alert` role is that it's for content that is dynamically displayed, not for content that appears on page load." and "Do not try to dynamically add/generate an element with `role="alert"` that is already populated with the alert message you want announced - this generally does _not_ lead to an announcement, as it is not a content change." Why: "if a page loads with multiple visible alerts scattered throughout, the alert role should not be used, as the messages were not dynamically triggered." Smell: server-rendered banners with `role="alert"`, or re-firing the same message without first clearing the container, since "it's usually best to briefly "clear" the contents of the alert container before then injecting the alert message." Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/alert_role#description
- **Hide a screen-reader-only live region visually, never with `display: none`**: "make sure that the container is not hidden using `display:none`, as this will hide it even from assistive technologies, meaning that they won't be notified of any changes. Instead, use something like the `.visually-hidden` styles". Why: "It's possible to visually hide the alert container itself, and use it to provide updates/notifications explicitly for screen readers." Smell: an announcer `div` toggled with `hidden` or `display: none` between messages. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/alert_role#example_3_visually_hidden_alert_container_for_screen_reader_notifications
- **Keep alerts to text, and never move focus to them**: "The `alert` role should only be used for text content, not interactive elements such as links or buttons." The APG adds: "it is crucial they do not affect keyboard focus." Why: "Live regions are typically announced as plain text, so links, buttons, and other semantics in the updated content may not be conveyed in the announcement itself." Smell: a toast with `role="alert"` whose only "Undo" or "Retry" lives inside the region, or `alertRef.current.focus()` after showing it. Source: https://www.w3.org/WAI/ARIA/apg/patterns/alert/#about
- **Do not auto-dismiss alerts**: "It is also important to avoid designing alerts that disappear automatically. An alert that disappears too quickly can lead to failure to meet WCAG 2.0 success criterion 2.2.3." Why: "Frequent interruptions inhibit usability for people with visual and cognitive disabilities". Smell: `setTimeout(dismiss, 3000)` on an error toast with no way to keep or reopen it. Source: https://www.w3.org/WAI/ARIA/apg/patterns/alert/#about
- **Set `aria-atomic="true"` when only part of the message changes**: "`aria-atomic="true"` ensures that each time the live region is updated, the entirety of the content is announced in full (e.g., "17:34")." Why: "when the clock changes from "17:33" to "17:34", assistive technologies will only announce "34", which won't be very useful to users." Smell: `<div aria-live="polite">Basket: <span>{count}</span> items</div>` where only the number node changes, announcing "3" on its own. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Guides/Live_regions#basic_examples_aria-atomic
- **Use `aria-busy` around multi-part updates and always reset it**: "When multiple parts of a live region need to be loaded before changes are announced to the user, set `aria-busy="true"` until loading is complete. Then set to `aria-busy="false"`." Why: "This prevents assistive technologies from announcing changes before updates are done." Smell: `aria-busy="true"` set at fetch start with no `false` on success or error, so the region never announces again. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-busy
- **Add a redundant `aria-live="polite"` to `status` and `log`, but not `aria-live` to `alert`**: for `status` and `log`, "To maximize compatibility, add a redundant `aria-live="polite"` when using this role." For `alert`: "adding both `aria-live` and `role="alert"` causes double speaking issues in VoiceOver on iOS." Why: `role="alert"` already means "`aria-live="assertive"` and `aria-atomic="true"`". Smell: `<div role="alert" aria-live="assertive">` in a toast component. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Guides/Live_regions#roles_with_implicit_live_region_attributes

## Announcing state in single-page apps

- **Expose every status message with a role or live property**: "Let assistive technology notify users about status changes that don't take focus." A status message is one where "the message provides information to the user on the success or results of an action, on the waiting state of an application, on the progress of a process, or on the existence of errors" and "is not delivered via a change in context." Why: "Most sighted users can observe text peripherally added to the viewport." Smell: "Saved", "5 results", "Added to basket" or "3 errors on page" text appended to the DOM in a plain `span` or `p`. Source: https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html#brief
- **Give loading states text and announce completion**: "After a user activates a process, an icon symbolizing 'busy' appears on the screen. The screen reader announces "application busy"." and "Where updating the visible message (e.g., to "system available") is not feasible, the use of a non-visible status message, such as "system available", ensures equivalent status information is provided." Why: "For a sighted user, when this text disappears, it is normally an indication that the state is now available. However non-sighted users would be unaware of this change". Smell: a `Spinner` component that renders only an animated `svg`, and a results list that appears with no "18 results returned" status. Source: https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html#examples
- **Pair a route change with a title update and an announcement**: "Presently, dynamically updating a page's title will not be automatically announced by screen readers. If you are going to update the page title to reflect significant changes to a page's state, then the use of ARIA Live Regions may be necessary, as well." Why: the view changes under the user with no page load event to signal it. Smell: a router that sets `document.title` (or does not) and renders the new view without a `role="status"` announcer or a focus move to the new content. Source: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/title#accessibility
- **Use `output` for calculated results instead of a live `span`**: "Many browsers implement this element as an `aria-live` region. Assistive technology will thereby announce the results of UI interactions posted inside it without requiring that focus is switched away from the controls that produce those results." Why: "Live-region updates are generally announced as plain text, so links, buttons, and other semantics nested inside `<output>` may not be conveyed in the announcement." Smell: a running total or converted value written into `<span id="total">` with no live semantics. Source: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/output#accessibility
