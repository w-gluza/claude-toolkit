# Accessibility Semantics and ARIA Rules (MDN, ARIA in HTML)

Extracted 2026-11-08 from the mdn/content repository, the w3c/html-aria source and the eslint-plugin-jsx-a11y rule docs.

## Native first

- **Use the native element before reaching for ARIA**: "If you can use a native HTML element or attribute with the semantics and behavior you require already built in, instead of re-purposing an element and adding an ARIA role, state or property to make it accessible, then do so." Why: "native elements have built-in keyboard accessibility, roles and states. However, if you choose to use ARIA, you are responsible for mimicking the equivalent browser behavior in script." Smell: `<div role="button" tabindex="0">` or `<span role="link">` where a `<button>` or `<a href>` would do. Lint: jsx-a11y/prefer-tag-over-role. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA#before_using_aria
- **Treat every ARIA attribute as a liability to justify**: "There is a saying \"No ARIA is better than bad ARIA.\"" Why: "they found that Home pages with ARIA present averaged 41% more detected errors than those without ARIA. While ARIA is designed to make web pages more accessible, if used incorrectly, it can do more harm than good." Smell: a component that sprinkles `role`, `aria-label` and `aria-live` onto plain `<div>` wrappers "for accessibility" with no test against a screen reader. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA#before_using_aria
- **Use `<select>`, checkboxes or radios instead of a `listbox`**: "It is highly recommended using the HTML select element, or a group of radio buttons if only one item can be selected, or a group of checkboxes if multiple items can be selected". Why: "there is a lot of keyboard interactivity to manage focus for all the descendants, and native HTML elements provide this functionality for you for free." Smell: `<ul role="listbox">` with `<li role="option">` children and a hand-rolled arrow-key handler for a plain single choice. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/listbox_role#description
- **Use `<input type="checkbox">` and `<input type="radio">` rather than the roles**: "The first rule of ARIA is: if a native HTML element or attribute has the semantics and behavior you require, use it instead of re-purposing an element and adding an ARIA role, state or property to make it accessible. As such, it is recommended to use the native HTML checkbox using form control instead of recreating a checkbox's functionality with JavaScript and ARIA." Why: "By using the `input` element with `type="checkbox"` instead of ARIA, there is no need for any JavaScript." Smell: `<span role="checkbox" aria-checked="false" tabindex="0">` or `<div role="radio">` inside a form. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/checkbox_role#best_practices
- **Use `<h1>` to `<h6>`, never `role="heading"`**: "The best way to use this role is to **not use it at all**, and instead use the native heading tags `h1` through `h6`". Why: "The `heading` role and `aria-level` attribute should only be used to retrofit accessibility on legacy code that you cannot make major changes to." Smell: `<div role="heading" aria-level="3">` in a component you own; or, per the heading elements page, "Do not use heading elements to resize text." Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/heading_role#best_practices
- **Use `<ul>`, `<ol>` and `<li>` instead of `list` and `listitem` roles**: "Only use `role="list"` and `role="listitem"` if you have to". Why: "Unlike the HTML `ol` and `ul`, the ARIA `list` roles doesn't distinguish between ordered and unordered lists." Smell: `<div role="list"><div role="listitem">` for ordinary content; or `<ul style="list-style: none">` where MDN notes "Styling a list with `list-style: none;` in CSS removes the list semantics. Adding `role="listitem"` returns the semantics." Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/list_role#best_practices
- **Use `<table>` for data tables, with `role="table"` only to repair CSS damage**: "Only use `table`, `tbody`, `thead`, `tr`, `th`, `td`, etc., for data table structure." Why: "A relevant use case for the ARIA table role is when CSS's display property overrides the native semantics of a table, such as by `display: grid`. In this case, you can use the ARIA table roles to re-add the semantics." Smell: `<div role="table">` with `role="row"` and `role="cell"` children built from scratch; `<table style="display: grid">` with no `role="table"` re-added; a `<table>` used purely for layout. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/table_role#best_practices
- **Build dialogs on `<dialog>` rather than `role="dialog"` on a `div`**: "While dialogs can be created using other elements, the native `<dialog>` element provides usability and accessibility features that must be replicated if you use other elements for a similar purpose." Why: "`<dialog>` elements invoked by the `showModal()` method implicitly have aria-modal="true"", and "When using `<dialog>` along with the `HTMLDialogElement.showModal()` method, this behavior is provided by the browser." Smell: `<div role="dialog" aria-modal="true">` with a hand-written focus trap and backdrop. Baseline: `<dialog>` Widely available since 2024-09-14. Source: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/dialog#accessibility
- **Mark the search area with `<search>` or `role="search"`**: "To mark the search area as a landmark, you can either wrap it with the `search` element or give it ARIA `role="search"`. As a general rule, use HTML semantics where possible and only use ARIA where there is no HTML equivalent." Why: "The search area is a really important landmark that people will want to find, but it is not listed in the landmarks menu or treated like a notable landmark beyond the actual input being called out as a search input". Smell: `<div class="search-controls"><input type="search">` with no landmark around it. Baseline: `<search>` Widely available since 2026-04-13. Source: https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/Accessibility/WAI-ARIA_basics#signpostslandmarks
- **Use `<details>`/`<summary>` for disclosures and do not re-ARIA them**: for `summary` the spec allows "No `role` if the `summary` element is a summary for its parent details element", and for `details` "No `role` other than group, which is NOT RECOMMENDED." Why: "The exposed role of a `summary` element can vary depending on the user agent and assistive technology", so an author role fights the browser's mapping. Smell: `<summary role="button" aria-expanded="false">`, `<details role="region">`, or a `div`-and-button disclosure where `<details>` would do. Baseline: `<details>` Widely available since 2022-07-15. Source: https://www.w3.org/TR/html-aria/#el-summary

## Interactive elements

- **Never build a button out of a `div` or `span`**: "you sometimes see buttons marked up using `div`s" and "using such code is not advised"; "In the rare to non-existent case when you need to use a non-button element for a button, use the `button` role and implement all the default button behaviors, including keyboard and mouse button support." Why: "you immediately lose the native keyboard accessibility you would have had if you'd just used `button` elements, plus you don't get any of the default CSS styling that buttons get." Smell: `<div className="btn" onClick={...}>`, with or without `role="button"` and `tabIndex`. Lint: jsx-a11y/no-static-element-interactions. Source: https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/Accessibility/HTML#use_semantic_ui_controls_where_possible
- **Do not use `<a href="#">` as a button**: "Anchor elements are often abused as fake buttons by setting their `href` to `#` or `javascript:void(0)` to prevent the page from refreshing, then listening for their `click` events." Why: "These bogus `href` values cause unexpected behavior when copying/dragging links, opening links in a new tab/window, bookmarking, or when JavaScript is loading, errors, or is disabled. They also convey incorrect semantics to assistive technologies, like screen readers." Smell: `<a href="#" onClick={toggle}>`, `<a href="javascript:void(0)">`, or an `<a>` with `preventDefault()` in its handler and no navigation. Source: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/a#onclick_events
- **Fix the design when a link behaves like a button instead of adding `role="button"`**: "If a link performs the action of a button, giving the element `role="button"` helps assistive technology users understand the function of the element. However, a better solution is to adjust the visual design so it matches the function and ARIA role." Why: "when links are used to behave like buttons, adding `role="button"` alone is not sufficient. It will also be necessary to add a key event handler that listens for the Space key in order to be consistent with native buttons." Smell: `<a href="/x" role="button">` that opens a menu or submits something and has no Space key handling. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/button_role#best_practices
- **Put a `<button>` inside an accordion heading, not a handler on the heading**: "Headers often double as expand/collapse controls for the content they headline. An accordion component is a common example of this pattern. Rather than assign the interaction handling code to the heading itself, put a button inside the heading instead. This pattern retains the role of the heading and the role of the button." Why: heading navigation keeps working and the control is a real button. Smell: `<h3 onClick={toggle} aria-expanded>` or `<h3 role="button">`. Lint: jsx-a11y/no-noninteractive-element-interactions. Source: https://github.com/jsx-eslint/eslint-plugin-jsx-a11y/blob/main/docs/rules/no-noninteractive-element-interactions.md
- **Put interactive content inside table cells, or make the table a `grid`**: "Table cells (and tables in general) are meant to contain data"; "move the button inside the cell" so that "This preserves the table cell semantics and the button semantics; the two are not conflated on the cell." Why: MDN's `table` role adds "If a table maintains a selection state, has two-dimensional navigation, or allows the user to rearrange cell order use `grid` or `treegrid` instead." Smell: `<td onClick>` or `<tr onClick>` as the only way to act on a row. Lint: jsx-a11y/no-noninteractive-element-interactions. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/table_role#description
- **Do not nest semantic elements inside a button, tab, option or other presentational-children role**: "browsers automatically apply role `presentation` to all descendant elements of any `button` element as it is a role that does not support semantic children." Why: "From the assistive technology user's perspective, the heading does not exist since the previous code snippets are equivalent" to plain text inside the button. Smell: `<button><h3>Title</h3><p>Body</p></button>`, `<div role="tab"><a href>`, a card where the whole thing is a `<button>` wrapping a heading and a link. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/button_role#all_descendants_are_presentational
- **Disable native controls with `disabled`, and reserve `aria-disabled` for custom or focus-kept controls**: "When needing to disable native HTML form controls, developers will need to specify the `disabled` attribute, as it provides all of the generally expected features of disabling a control by default." Why: "the `aria-disabled="true"` <strong>only</strong> semantically exposes these elements as being disabled. Web developers must manually ensure such elements have their functionality suppressed when exposed to the disabled state." Smell: `<button aria-disabled="true" onClick={submit}>` with no guard in the handler and no disabled styling. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-disabled#description
- **Never set `aria-disabled="true"` on a link with an `href`; remove the `href` instead**: "It is NOT RECOMMENDED to use `aria-disabled="true"` on an `a` element with an `href` attribute. If a link needs to be programmatically communicated as \"disabled\", remove the `href` attribute." Why: the `href` keeps the link focusable and activatable, so the announced state contradicts what happens on Enter. Smell: `<a href="/next" aria-disabled="true">` or `<Link aria-disabled>` on a pagination control. Source: https://www.w3.org/TR/html-aria/#el-a

## Roles

- **Give every role the states it requires**: "Elements containing `role="checkbox"` must also include the `aria-checked` attribute to expose the checkbox's state to assistive technology." Likewise for `switch` ("The `aria-checked` attribute is **required** when using the `switch` role"), `combobox` ("A WAI-ARIA combobox requires only one attribute: `aria-expanded`") and `heading` (`aria-level` "is required"). Why: without the state the role is announced without the information that makes it usable. Smell: `role="checkbox"` or `role="switch"` with no `aria-checked`; `role="combobox"` with no `aria-expanded`. Lint: jsx-a11y/role-has-required-aria-props. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/checkbox_role
- **Only use attributes the element's role supports**: "Many ARIA attributes (states and properties) can only be used on elements with particular roles. Some elements have implicit roles, such as `<a href="#" />`, which will resolve to `role="link"`." For example, on a tooltip "the `aria-expanded` role is not supported." Why: unsupported attributes are ignored or misreported, so the state the code tracks never reaches the user. Smell: `aria-checked` on a `<button>` without `role="checkbox"`, `aria-expanded` on `role="tooltip"`, `aria-selected` on a `<li>`. Lint: jsx-a11y/role-supports-aria-props. Source: https://github.com/jsx-eslint/eslint-plugin-jsx-a11y/blob/main/docs/rules/role-supports-aria-props.md
- **A `tab` lives in a `tablist`, points at its panel and carries `aria-selected`**: "Elements with the role `tab` _must_ either be a child of an element with the `tablist` role, or have their `id` as part of the `aria-owns` property of a `tablist`." Also "an element with the `tab` role _should_ contain the `aria-controls` property identifying a corresponding `tabpanel`", and "When elements with the `tab` role are selected or active they should have their `aria-selected` attribute set to `true`. Otherwise, their `aria-selected` attribute should be set to `false`." Why: "Some assistive technology will provide a count of the number of `tab` role elements inside a `tablist`, and inform users of which `tab` they currently have targeted." MDN also recommends "a `button` element with the role `tab`". Smell: `role="tab"` buttons sitting directly in a `<div>` or `<nav>` with no `role="tablist"`; `aria-selected` on the panel or on only the active tab; `<a href="#panel" role="tab">`. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/tab_role#description
- **Name each `tabpanel` from its tab and hide the inactive ones**: "Each `tab` in a `tablist` can serve as the label for its corresponding `tabpanel`. Include the `id` of each `tab` as the value for each `tabpanel`'s `aria-labelledby` attribute." Why: "All inactive `tabpanel` elements must be hidden to all users." Smell: a `tabpanel` with no `aria-labelledby`; inactive panels left in the tree without `hidden` or `display: none`. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/tabpanel_role#description
- **Do not use `role="menu"` for site navigation**: "When including a \"menu\" for site navigation, do not use the `menu` role. Rather, for the main site navigation use the native HTML `nav` element or simply a list of links. The `menu` role should be reserved for composite widgets requiring focus management." Why: "the `menu` role is for a list of actions or functions that require complex functionality, such as composite widget focus management and first-character navigation". Smell: `<ul role="menu">` with `<li role="menuitem"><a href>` links in a header or sidebar; `role="menuitem"` on rows whose parent has no `role="menu"`. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/menu_role#example_1_navigation_menu
- **Wire a `combobox` with `aria-expanded`, `aria-controls` and a matching `aria-haspopup`**: "When a combobox's popup is displayed, ensure the `aria-controls` attribute on the combobox element is set to the `id` of the popup `listbox`, `tree`, `grid`, or `dialog` element." and "The `aria-owns` in the code should be updated to `aria-controls`!" Why: "If the combobox popup element is a `tree`, `grid`, or `dialog` (anything other than a `listbox`), the `aria-haspopup` attribute is required." and "for this property, `true` means `menu`, so make sure that the value corresponds to the role of the popup, not a Boolean value." Smell: `role="combobox" aria-owns="list"`, `aria-haspopup="true"` on an input whose popup is a listbox, or a combobox whose popup toggle button is a descendant of the combobox element. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/combobox_role#description
- **Group `radio` roles in a `radiogroup` and put `aria-required` on the group**: "The radio role should always be nested with other associated radios in a `radiogroup`." and "To programmatically indicate that a radio button must be chosen from a radio group the `aria-required` attribute, with a value of `true`, must be specified on the `radiogroup` element. It is not expected to use the `aria-required` attribute on individual ARIA radio buttons." Why: "The radio buttons must be grouped together in a `radiogroup` to indicate which ones affect the same value." Smell: loose `role="radio"` elements with no `radiogroup` parent, or `aria-required` on each radio. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/radio_role#description
- **Choose `alertdialog` only when the alert needs a response, and make it modal**: "The `alertdialog` role should only be used for alert messages that have associated interactive controls. If an alert dialog only contains static content and has no interactive controls at all, use `alert` instead." Why: "Because of its urgent nature, interrupting the user's workflow, alert dialogs should be modal." Smell: `role="alertdialog"` on a non-modal toast, or `role="alert"` on a confirm dialog with Yes and No buttons. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/alertdialog_role#description
- **`role="dialog"` alone does not make a dialog; label it and manage focus**: "adding `role="dialog"` alone is not sufficient to make a dialog accessible." MDN lists two further requirements: labelling the dialog (strongly recommended) and managing keyboard focus. Why: "the dialog's label acts like a grouping label for the controls inside it (similar to how a `<legend>` element provides a grouping label for the controls inside a `<fieldset>` element)." Smell: `<div role="dialog">` with a visible `<h2>` title but no `aria-labelledby` pointing at it. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/dialog_role#description
- **Put `role="tooltip"` on the tip, keep it free of controls, and prefer visible text**: "The `role="tooltip"` is included on the element containing the tip content, not on the icon or control that triggers it." and "Because the tooltip itself never receives focus and is not in the tabbing order, a tooltip cannot contain interactive elements like links, inputs, or buttons." Why: "If the information is important enough to include as a tooltip or title, consider including it in visible text." Smell: `role="tooltip"` on the info icon, a tooltip with a "Learn more" link inside, or a `title` attribute standing in for a tooltip. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/tooltip_role#description
- **Put `role="img"` on inline `<svg>` and on composite imagery, and name it**: "If you are using embedded SVG images in your page, it is a good idea to set `role="img"` on the outer `svg` element and give it a label." Why: "This will cause screen readers to just consider it as a single entity and describe it using the label, rather than trying to read out all the child nodes". Smell: an inline `<svg>` icon with `<title>`-less paths and no `role`, or a group of emoji carrying meaning with no `role="img"` wrapper. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/img_role#svg_and_roleimg
- **Treat `role="application"` as a last resort and scope it tightly**: "This role should only be used to define very dynamic and desktop-like web applications. Most mobile and desktop web apps _are not_ considered applications for this purpose." Why: "Improperly using the `application` role can unintentionally take away access from information on a web page", and "If used, the application role should be added to the lowest common container possible, not on the `<body>` element". Smell: `<body role="application">` or `<div id="root" role="application">` on an ordinary SPA. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/application_role#accessibility_concerns
- **Use `role="document"` only inside an `application` or widget, never in a dialog**: "document role is only useful for focusable elements within a widget or application that should be read as static rich text." and "The `document` role is not needed inside a dialog. A dialog is a window, not a widget or application, so assistive technologies that have a reading mode already use it for the dialog's content." Why: "By default, web pages are treated as documents". Smell: `<div role="document" tabindex="0">` wrapping dialog body text or page content outside any `application`. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/document_role#description
- **Never write `role="generic"`**: "The `generic` role is intended for use as the implicit role of generic elements in host languages for use by user agents only; not for use by developers." Why: "Because the generic role is nameless, the `aria-labelledby` and `aria-label` attributes are prohibited." Alternatives: "use `presentation` or `none`, the `div` and `span` elements that have no semantic meaning, or semantic container roles such as `group`". Smell: `role="generic"` anywhere in authored markup. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/generic_role#description

## Landmark roles

- **Do not restate the implicit role of a landmark element**: "HTML landmark elements (`main`, `header`, `nav`, etc.) have built-in implicit ARIA roles, so there is no need to duplicate them." ARIA in HTML adds: "It is NOT RECOMMENDED for authors to set the ARIA `role` and `aria-*` attributes to values that match the implicit ARIA semantics defined in either table. Doing so is unnecessary and can potentially lead to unintended consequences." Smell: `<nav role="navigation">`, `<main role="main">`, `<button role="button">`, `<ul role="list">`. Lint: jsx-a11y/no-redundant-roles. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA#before_using_aria
- **Label every `nav` when there is more than one, and reuse the label for repeats**: "If there is more than one `navigation` landmark role or `nav` element in a document, provide a label for each landmark." and "If a `navigation` landmark role or `nav` element in a document is repeated in a document, and both landmarks have identical content, use the same label for each landmark." Why: "If labels were not provided, the person using screen reading software may have to investigate each `nav` element's contents to determine their purpose." Smell: a header `<nav>` and a footer `<nav>` with no `aria-label` or `aria-labelledby` on either. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/navigation_role#multiple_landmarks
- **Do not name a landmark after its own role**: "Screen readers will announce the type of role the landmark is. Because of this, you do not need to describe what the landmark is in its label. For example, a declaration of `role="navigation"` with an `aria-label="Primary navigation"` may be announced redundantly as, \"primary navigation navigation\"." Why: the role is spoken anyway, so the word is noise. Smell: `<nav aria-label="Main navigation">`, `<footer aria-label="Footer">`, `<aside aria-label="Sidebar">`, `<form aria-label="Contact form">`. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/navigation_role#redundant_descriptions
- **Keep one `main` per page and hide any inactive one**: "A document mustn't have more than one `<main>` element that doesn't have the `hidden` attribute specified." and "If a document contains two `main` roles, say updating page content when triggered by JavaScript, the inactive `main` role's presence should be removed from assistive technology via techniques such as toggling the `hidden` attribute." Why: "For those navigating via landmark roles, the main role is an alternative for \"skip to main content\" links." Smell: a layout `<main>` plus a `<main>` inside a routed page, or a `<main>` inside each `<article>`. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/main_role#use_only_one_main_role_per_document
- **Expect `header`, `footer` and `aside` to be landmarks only in the right context**: "When placed inside an `article`, `main`, `section`, `nav`, `aside`, or an element with the same ARIA role as these elements' implicit ARIA role, the `<header>` element has the `generic` role instead, and is no longer considered a landmark. In this case, it cannot be labeled with `aria-label` or `aria-labelledby`." Likewise "a `footer` element nested within an `article`, `aside`, `main`, `nav`, or `section` is not considered `contentinfo`", and `aside` is `complementary` "unless it has no accessible name and is nested in sectioning content". Why: "The `<header>` element defines a `banner` landmark when its context is the `body` element." Smell: `<article><header aria-label="Post header">`, or a site banner wrapped in `<main>` or `<section>` and expected to show up as `banner`. Source: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/header#accessibility
- **One `contentinfo` per page, with nothing nested in it**: "There should be only one `contentinfo` landmark per document, used as the immediate descendant of the `body` element." and "Do not nest additional `footer` elements or `contentinfo` landmarks inside the document's footer. Use other content sectioning elements instead." Why: landmarks exist to "quickly identify and navigate to large sections of the document", and nested footers make that list incoherent. Smell: `<footer>` inside `<footer>` for a mega-footer, or `<div role="contentinfo">` plus a body-level `<footer>`. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/contentinfo_role#one_contentinfo_landmark_per_page
- **A `section` is only a landmark when it has a name; otherwise use a `div`, and keep regions rare**: "Using the `section` element will automatically communicate a section has a role of `region` if it is given an accessible name." and, from the `section` element page, "If you are only using the element as a styling wrapper, use a `div` instead." Why: "Landmark roles are intended to be used sparingly, to identify larger overall sections of the document. Using too many landmark roles can create \"noise\" in screen readers, making it difficult to understand the overall layout of the page." Smell: `<section>` used as a generic wrapper everywhere, `role="region"` on small widgets, or `<section aria-label>` on every card so the landmarks list fills with regions. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/region_role#description
- **Name a `form` landmark, use `search` for search forms, and never put `role="form"` on fields**: "You do not need to declare `role="form"` on every form element (inputs, text areas, selects, etc.). It should be declared on the HTML element that wraps the form elements. Ideally, use the `form` element as the wrapping element and do not declare `role="form"`." Why: "The `<form>` element defines a `form` landmark when it has an accessible name" and "Use the `search` landmark instead of the `form` landmark when the form is used for search functionality." Smell: `<input role="form">`, `<div role="form">` around a `<form>`, or a site search `<form>` with no `role="search"` and no `<search>` wrapper. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/form_role#inputs_are_not_forms

## States and properties

- **Put `aria-expanded` on the control, not on the thing that expands**: "The `aria-expanded` attribute is applied to this focusable, interactive control that toggles the visibility of the object." and "The presence of the `aria-expanded` attribute indicates control. Avoid including it on elements that do not control the expanded state of other elements." Why: "A button that toggles a widget should have `aria-controls` set to the `id` of the toggled widget and `aria-expanded` set to the current state of the widget." Smell: `aria-expanded="true"` on the panel `div`, the `<ul>` submenu or the sidebar, while the trigger button has nothing. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-expanded#description
- **Point `aria-controls` from the controller to the controlled element**: "The `aria-controls` attribute identifies the element (or elements) whose contents or presence are controlled by the element on which the attribute is set, regardless of what type of interaction initiates the impacted behavior." Why: for tabs, "each element with `role="tab"` has an `aria-controls` attribute referencing its associated `tabpanel`", and for accordions "Each button may have an `aria-controls` specified, referencing the ID of the element containing the content associated with the invoking control." Smell: `aria-controls` on the panel pointing back at the button, or an `aria-controls` whose `id` does not exist in the DOM. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-controls#description
- **Use `aria-selected` only on `gridcell`, `option`, `row` and `tab`; use `aria-current` elsewhere**: "The `aria-selected` attribute indicates the current \"selected\" state for `gridcell`, `option`, `row` and `tab` roles." and "For other roles, the currently selected state is set with `aria-current`, or possibly `aria-checked` or `aria-pressed`, depending on the role." Why: `aria-selected` on an unsupported role is dropped, so the highlighted item is announced like all the others. Smell: `aria-selected="true"` on the active `<a>` in a nav, on a `<li>` in a plain list, or on a `<button>` in a toolbar. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-selected#description
- **Mark the current page or step with `aria-current`, once per set**: "In a breadcrumb list, when a link within a set of pagination links is styled to indicate the user is currently on that page, `aria-current="page"` should be set on that link." and "Only mark one element in a set of elements as current with `aria-current`." Why: "Don't use `aria-current` as a substitute for `aria-selected` in `gridcell`, `option`, `row` or `tab`." Smell: a nav link styled `.active` with no `aria-current`, several links with `aria-current="page"`, or `aria-current="true"` on the active tab. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-current#description
- **Use `aria-pressed` for toggle buttons and keep the label fixed**: "To describe the state of a button the correct ARIA attribute to use is `aria-pressed` and not `aria-checked` or `aria-selected`." and "Do not change the contents of the label on a toggle when the state changes. If a button label says \"pause\", do not change it to \"play\" when pressed." Why: "If you want the label to toggle between \"Paused\" and \"Play\", don't use `aria-pressed`." Smell: `<button aria-checked>` or `<button aria-selected>` for a filter chip; `<button aria-pressed={muted}>{muted ? "Unmute" : "Mute"}</button>`. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-pressed#description
- **Never add `aria-checked` to a native checkbox or radio**: "Authors MUST NOT use the `aria-checked` attribute on `input type=checkbox` elements." Why: "Authors MUST NOT use the `aria-checked` attribute on any element where the checkedness, or the indeterminate checked value of the element can be in opposition to the current value of the `aria-checked` attribute." Smell: `<input type="checkbox" checked aria-checked="true">`, or a controlled React checkbox that mirrors state into `aria-checked`. Source: https://www.w3.org/TR/html-aria/#el-input-checkbox
- **Do not double up native attributes with their `aria-*` twins, and never contradict them**: "authors SHOULD NOT specify both the native HTML attribute and the equivalent `aria-*` attribute on an element." For `required`: "Authors SHOULD NOT use the `aria-required="true"` on any element which also has a `required` attribute. Authors MUST NOT use `aria-required="false"` on any element which also has a `required` attribute." Why: "when HTML elements use both `aria-*` attributes and their host language (HTML) equivalents, user agents MUST ignore the WAI-ARIA attributes". Smell: `<input required aria-required="true">`, `<button disabled aria-disabled="false">`, `<input disabled aria-disabled="true">`. Source: https://www.w3.org/TR/html-aria/#docconformance-attr
- **Make `aria-haspopup` match the popup's role, and remember `true` means `menu`**: "Make sure the role of the element that serves as the container for the popup content is a `menu`, `listbox`, `tree`, `grid` or `dialog` and that the value of `aria-haspopup` matches the role of the popup container." Why: "The value `true` is the same as `menu`." and "A `tooltip` is not considered to be a popup in this context, as it is not interactive." Smell: `aria-haspopup="true"` on a button that opens a dialog or a listbox, `aria-haspopup` on a tooltip trigger, or `aria-haspopup="menu"` on a `<ul>` of links. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-haspopup#description
- **Use `aria-modal` only on `dialog` and `alertdialog`, and make the background inert**: "Relevant only on `dialog` and `alertdialog` containers, setting `aria-modal="true"` tells assistive technologies to let the user know the ability to interact with, or access other content on the page requires the modal dialog to be closed or otherwise lose focus." and "When a modal element is displayed, authors **should** mark all other contents as inert (such as \"inert subtrees\" in HTML)." Why: "`aria-modal="true"` on `dialog` and `alertdialog` role containers indicates the presence of a \"modal\" element to users of assistive technology, but does not actually make the element modal." Smell: `aria-modal="true"` on a `role="region"` drawer, or a custom modal with `aria-modal` but no `inert` on the rest of the page and no focus containment. Baseline: `inert` Widely available since 2025-10-11. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-modal#description

## Hiding and presentation

- **Never put `aria-hidden="true"` on a focusable element or any ancestor of one**: "`aria-hidden="true"` should not be used on elements that can receive focus. Additionally, since this attribute is inherited by an element's children, it should not be added onto the parent or ancestor of a focusable element." ARIA in HTML: "Authors MAY use the `aria-hidden` attribute on any HTML element that allows Global `aria-*` attributes to be specified, with the exception of focusable elements and the `body` element." Why: "A focusable element is any element which can be focused by use of keyboard or pointer device. Focusable elements are not always elements which can be tabbed to via a keyboard. For instance, an element with `tabindex="-1"` is focusable but is not a tabbable element." Smell: `<div aria-hidden="true">` wrapping a carousel slide that still contains a `<button>` or `<a>`, or `aria-hidden` on an off-screen menu whose links keep `tabindex`. Lint: jsx-a11y/no-aria-hidden-on-focusable. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-hidden#description
- **Do not add `aria-hidden` to content that is already hidden**: MDN says `aria-hidden="true"` should not be added when the `hidden` attribute is present or the element or an ancestor is hidden with `display: none` or `visibility: hidden`, because "In all three scenarios, the attribute is unnecessary to add because the element has already been removed from the accessibility tree." ARIA in HTML goes further: "authors MUST NOT use `aria-hidden="true"` on any element which also has the `hidden` attribute specified in the Hidden Until Found state." Why: with `until-found`, `aria-hidden` "will prevent this content from being discoverable to users of assistive technology when it is found via a browser's in-page find feature and visually rendered to users." Smell: `<div hidden aria-hidden="true">`, `<div hidden="until-found" aria-hidden="true">`, or `aria-hidden={!open}` alongside `display: none` toggling. Source: https://www.w3.org/TR/html-aria/#att-hidden
- **Choose `aria-hidden` to remove an element and `presentation` to remove only its semantics**: "`aria-hidden="true"` will remove the entire element from the accessibility API." while "`role="presentation"` and `role="none"` will remove the semantic meaning of an element while still exposing it and its content to assistive technology." Why: "Only when identical or equivalent meaning and functionality is exposed to assistive technologies can removing visible content from the accessibility API be considered." Smell: `role="presentation"` on a decorative icon that should vanish entirely, or `aria-hidden="true"` on a layout wrapper (or a visible price or status) whose text must still be read. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-hidden#description
- **Never put `role="presentation"` on a data table or a real list**: "If `presentation` or `none` is applied to a `table` element, the descendant `caption`, `thead`, `tbody`, `tfoot`, `tr`, `th`, and `td` elements inherit the role and are thus not exposed to assistive technologies." and "Because the `presentation` role was applied to the `ul` element, every child `li` element inherits the `presentation` role." Why: the row and column relationships that make a data table readable disappear with the role. Smell: `<table role="presentation">` that contains `<th>` or a `<caption>`; `<ul role="presentation">` on a list whose item count matters. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/presentation_role#description
- **Do not expect `presentation` to work on focusable elements or with other ARIA attributes, and never name it**: "Browsers ignore `role="presentation"` and `role="none"` on focusable elements, including link and inputs, or anything with a tabindex attribute set. Browsers also ignore the inclusion of the role if any of the element contains any global ARIA states and properties, such as `aria-describedby`." Why: "The element with `role="presentation"` is not part of the accessibility tree and should not have an accessible name. Do **not** use `aria-labelledby` or `aria-label`." Smell: `<a href role="presentation">`, `<div role="presentation" aria-label="...">`, `<img role="presentation" aria-describedby="...">`. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/presentation_role#description
- **Use `inert` for whole sections and `disabled` for single controls, and show which is which**: "While `inert` is a global attribute and can be applied to any element, it is generally used for sections of content. To make individual controls \"inert\", consider using the `disabled` attribute, along with CSS `:disabled` styles, instead." Why: "By default, there is no visual way to tell whether or not an element or its subtree is inert. As a web developer, it is your responsibility to clearly indicate the content parts that are active and those that are inert." Smell: `<button inert>` instead of `disabled`, or `inert` on the page behind a modal with no dimming or backdrop. Baseline: `inert` Widely available since 2025-10-11. Source: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Global_attributes/inert
- **Do not rely on `title` as a label or a tooltip**: "The `title` attribute is not an acceptable substitute for the `alt` attribute." and "While `title` can be used to provide a programmatically associated label for an `input` element, this is not good practice. Use a `label` instead." Why: "Use of the `title` attribute is highly problematic for" people on touch-only devices, keyboard users, screen reader and magnifier users, people with fine motor impairments and people with cognitive concerns, "due to inconsistent browser support, compounded by the additional assistive technology parsing of the browser-rendered page." Smell: `<img title="...">` with no `alt`, `<input title="Search">` with no `<label>`, `<button title="Delete">` as the only name, or `<abbr title>` where the expansion could be written in the text. Source: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Global_attributes/title#accessibility_concerns

## Allowed roles on HTML elements

- **An `<a>` without `href` is generic and cannot be named**: ARIA in HTML gives it the implicit role `generic` and allows "Any `role`, though generic SHOULD NOT be used. Naming Prohibited". Why: "Authors MUST NOT specify `aria-label` or `aria-labelledby` on elements with implicit WAI-ARIA roles which cannot be named." Smell: `<a aria-label="Open menu" onClick>` with no `href` and no `role`, or `<a>` placeholders in a nav that are expected to be announced as links. Source: https://www.w3.org/TR/html-aria/#el-a-no-href
- **A `div` or `span` with no role must not carry `aria-label` or `aria-labelledby`**: both are `generic` with "Naming Prohibited", and the spec's own do-not example is `<p aria-label>`, `<span aria-label>`, `<code aria-label>` and `<div aria-labelledby>`. Why: "Authors MAY use `aria-label` and `aria-labelledby` attributes to specify accessible names for elements which have an implicit or explicit ARIA role which allows naming from authors." A `generic` is not one of them, so the name is dropped. Smell: `<div aria-label="Toolbar">`, `<span aria-label="New">`, `<div aria-labelledby="h">` without a role such as `group`, `region` or `toolbar`. Source: https://www.w3.org/TR/html-aria/#docconformance-naming
- **A `button` may only take widget roles**: the allowed set is "`checkbox`, `combobox`, `gridcell`, `link`, `menuitem`, `menuitemcheckbox`, `menuitemradio`, `option`, `radio`, `separator`, `slider`, `switch`, `tab`, or `treeitem`" with "button is also allowed, but NOT RECOMMENDED." Why: a `<button>` keeps its focus and activation behaviour, so content roles would misreport it. Smell: `<button role="heading">`, `<button role="img">`, `<button role="presentation">`, `<button role="listitem">`. Source: https://www.w3.org/TR/html-aria/#el-button
- **Headings accept only `none`, `presentation` or `tab`**: for `h1` to `h6` the allowed roles are "`none`, `presentation` or `tab`" with "heading is also allowed, but NOT RECOMMENDED." Why: a heading that is also a button or link breaks heading navigation; put the control inside the heading instead. Smell: `<h2 role="button">`, `<h3 role="link">`, `<h1 role="banner">`, `<h2 role="heading" aria-level="2">`. Source: https://www.w3.org/TR/html-aria/#el-h1-h6
- **An `img` with empty `alt` takes no role but `none`/`presentation` and no ARIA but `aria-hidden`**: "No `role` other than the role=none or presentation roles, which are NOT RECOMMENDED. No `aria-*` attributes except `aria-hidden="true"`." Why: an image with empty `alt` is already presentational, so a widget role or a label contradicts it. Smell: `<img alt="" role="button">`, `<img alt="" aria-label="Logo">`, `<img alt="" aria-describedby="...">`. Source: https://www.w3.org/TR/html-aria/#el-img-empty-alt
- **A `nav` may only become `menu`, `menubar`, `tablist`, `none` or `presentation`**: the allowed roles are "`menu`, `menubar`, `none`, `presentation` or `tablist`" with "navigation is also allowed, but NOT RECOMMENDED." Why: `nav` already means a landmark of navigation links; other landmark or content roles conflict with that. Smell: `<nav role="navigation">`, `<nav role="list">`, `<nav role="region">`, `<nav role="toolbar">`. Source: https://www.w3.org/TR/html-aria/#el-nav
- **A `ul` may become a widget container, but its `li` children may only be `listitem` while it is a list**: for `ul` the allowed roles are "`group`, `listbox`, `menu`, `menubar`, `none`, `presentation`, `radiogroup`, `tablist`, `toolbar` or `tree`"; for `li`, "No `role` other than listitem, which is NOT RECOMMENDED, if the parent list element has an implicit or explicit `list` role. Otherwise, any `role` if the parent list element does not expose an implicit or explicit `list` role." Why: a `listitem` without a `list` parent, or a `tab` inside a `list`, gives assistive technology a structure that does not exist. Smell: `<ul><li role="button">` or `<ul><li role="tab">` with no role on the `<ul>`; `<ul role="navigation">`. Source: https://www.w3.org/TR/html-aria/#el-li
- **A `section` needs a name to be a region, and may not become `generic`**: the implicit role is "role=region if the `section` element has an accessible name" and otherwise `generic`; the allowances note "role=region is also allowed, but NOT RECOMMENDED. role=generic SHOULD NOT be used." Why: an unnamed `<section>` is announced as nothing, so code that expects a landmark from a bare `<section>` is mistaken. Smell: `<section role="region">` without a name, `<section role="generic">`, or a bare `<section>` expected to appear in the landmarks list. Source: https://www.w3.org/TR/html-aria/#el-section
