# Accessibility Testing and Tooling (Testing Library, axe-core, jsx-a11y, MDN)
Extracted 2026-11-08 from the testing-library-docs, axe-core and eslint-plugin-jsx-a11y repositories and the mdn/content repository.

## Query by role

- **Reach for `getByRole` first**: "`getByRole`: This can be used to query every element that is exposed in the accessibility tree. With the `name` option you can filter the returned elements by their accessible name. This should be your top preference for just about everything." Why: "There's not much you can't get with this (if you can't, it's possible your UI is inaccessible)." Smell: `screen.getByTestId('submit-button')` or `container.querySelector('button')` for a button that has visible text. Source: https://testing-library.com/docs/queries/about/#priority

- **Assert the role plus the accessible name, not the text alone**: "If you only query for a single element with `getByText('The name')` it's oftentimes better to use `getByRole(expectedRole, { name: 'The name' })`." Why: the accessible name "can be used to query a specific element if multiple elements with the same role are present on the rendered content", and a role query fails if the element has lost its semantics. Smell: `getByText('Save')` used to click a button, which also passes when "Save" is a `<div>` with an `onClick`. Source: https://testing-library.com/docs/queries/byrole/#api

- **Query the exact role; roles do not inherit**: "Roles are matched literally by string equality, without inheriting from the ARIA role hierarchy." Why: "querying a superclass role like `checkbox` will not include elements with a subclass role like `switch`." Smell: `getByRole('checkbox')` failing on an element the component renders with `role="switch"`, or a test widened to `getByRole('checkbox', { queryFallbacks: true })` for a `role="switch checkbox"` element. Source: https://testing-library.com/docs/queries/byrole/#api

- **Use `getByLabelText` for form fields and treat a placeholder-only query as a missing label**: "This method is really good for form fields. When navigating through a website form, users find elements using label text. This method emulates that behavior, so it should be your top preference." Placeholder comes next only because "A placeholder is not a substitute for a label. But if that's all you have, then it's better than alternatives." Why: a label query only passes when the field is programmatically labelled, which is what a screen reader announces. Smell: `getByPlaceholderText('Email')` or `getByTestId('email')` being the only way to reach an input, which means the input has no label or accessible name. Source: https://testing-library.com/docs/queries/about/#priority

- **Use `getByText` for non-interactive content and `getByDisplayValue` for filled fields**: "Outside of forms, text content is the main way users find elements. This method can be used to find non-interactive elements (like divs, spans, and paragraphs)." The display value query exists because "The current value of a form element can be useful when navigating a page with filled-in values." Smell: `getByText` used for buttons, links or headings that have roles, or `getByTestId` used to assert a prefilled value. Source: https://testing-library.com/docs/queries/about/#priority

- **Keep `getByAltText` and `getByTitle` below the role and text queries**: for the semantic queries "Note that the user experience of interacting with these attributes varies greatly across browsers and assistive technology", and for title "The title attribute is not consistently read by screenreaders, and is not visible by default for sighted users". Why: these attributes are real semantics but are not reliably exposed, so a test built on them does not prove the user can reach the element. Smell: `getByTitle('Close')` as the primary query for an icon button instead of `getByRole('button', { name: 'Close' })`. Source: https://testing-library.com/docs/queries/about/#priority

- **Use `getByTestId` last, never for anything with a role or text**: "`getByTestId`: The user cannot see (or hear) these, so this is only recommended for cases where you can't match by role or text or it doesn't make sense (e.g. the text is dynamic)." Why: a test id proves the element rendered, not that a user can find or operate it. Smell: `data-testid` attributes on buttons, links, inputs and headings, and a test file where most queries are `getByTestId`. Source: https://testing-library.com/docs/queries/about/#priority

- **Do not query by class or id**: "Note that using this as an escape hatch to query by class or id is not recommended because they are invisible to the user. Use a testid if you have to, to make your intention to fall back to non-semantic queries clear and establish a stable API contract in the HTML." Why: a selector on a class name breaks on styling changes and says nothing about accessibility. Smell: `container.querySelector('.btn-primary')` or `document.getElementById('submit')` in a test. Source: https://testing-library.com/docs/queries/about/#manual-queries

## Role query options

- **Filter by accessible name with `name`**: "With the `name` option you can filter the returned elements by their accessible name." and "Most often, this will be used with the `name` option like so: `getByRole('button', {name: /submit/i})`." Why: the name is what assistive technology announces, so the test fails when the name disappears or becomes generic. Smell: `getAllByRole('button')[2]` or `getByRole('button')` on a page with several buttons. Source: https://testing-library.com/docs/queries/about/#priority

- **Remember that an accessible name does not replace `alt`**: "The accessible name query does not replace other queries such as `*ByAlt` or `*ByTitle`. While the accessible name can be equal to these attributes, it does not replace the functionality of these attributes." Why: "`<img aria-label="fancy image" src="fancy.jpg" />` will be returned for `getByRole('img', { name: 'fancy image' })`. However, the image will not display its description if `fancy.jpg` could not be loaded." Smell: an `<img>` named with `aria-label` instead of `alt`, and a test that only checks `getByRole('img', { name })`. Source: https://testing-library.com/docs/queries/byrole/#api

- **Let the default `hidden: false` exclude what assistive technology cannot reach**: "If you set `hidden` to `true` elements that are normally excluded from the accessibility tree are considered for the query as well. The default behavior follows https://www.w3.org/TR/wai-aria-1.2/#tree_exclusion". In the dialog example "`getByRole('button')` would only return the `Close dialog`-button. To make assertions about the `Open dialog`-button you would need to use `getAllByRole('button', { hidden: true })`." Smell: `{ hidden: true }` added to a query to make it pass, which means the element is inside `aria-hidden`, `display: none` or `visibility: hidden` and a screen reader user cannot reach it either. Source: https://testing-library.com/docs/queries/byrole/#hidden

- **Do not switch `hidden` on globally for speed**: "`getByRole` performance can be improved by setting the option `hidden` to `true` and thereby avoid expensive visibility checks. Note that in doing so inaccessible elements will now be included in the result." Why: "`getByRole` is the most preferred query to use as it most closely resembles the user experience, however the calculations it must perform to provide this confidence can be expensive". Smell: `configure({ defaultHidden: true })` in test setup, or a suite that swapped role queries for `getByText` everywhere to save time. Source: https://testing-library.com/docs/queries/byrole/#performance

- **Assert widget state through role options, not class names**: "You can filter the returned elements by their checked state by setting `checked: true` or `checked: false`." The same pattern exists for `selected`, `pressed`, `expanded`, `current` and `busy`; for example "you can get the "Expandable Menu Item" link by calling `getByRole('link', { expanded: false })`." Why: these options read the `aria-*` state the screen reader announces, so the test fails when the visual state and the exposed state diverge. Smell: `expect(tab).toHaveClass('active')` or `expect(toggle).toHaveClass('open')` with no check of `aria-selected`, `aria-pressed` or `aria-expanded`. Source: https://testing-library.com/docs/queries/byrole/#checked

- **Query headings by `level`**: "An element with the `heading` role can be queried by any heading level `getByRole('heading')` or by a specific heading level using the `level` option `getByRole('heading', { level: 2 })`." Why: "While it is possible to explicitly set `role="heading"` and `aria-level` attribute on an element, it is **strongly encouraged** to use the semantic HTML headings `<h1>-<h6>`." Smell: `getByText('Settings')` for a section title, which passes when the title is a styled `<div>`. Source: https://testing-library.com/docs/queries/byrole/#level

## What automation covers

- **Run axe-core for the machine-checkable layer**: the WCAG 2.0 A and AA group is sixty rules of the shape "Ensure buttons have discernible text", "Ensure every form element has a label", "Ensure the contrast between foreground and background colors meets WCAG 2 AA minimum contrast ratio thresholds", "Ensure every HTML document has a lang attribute" and "Ensure elements with ARIA roles have all required ARIA attributes". Why: these checks compare markup against the specification and do not need a human to judge intent, so they belong in the test run or CI. Smell: no `axe` call in component tests or end-to-end tests, and missing alt or label bugs reaching review. Source: https://github.com/dequelabs/axe-core/blob/develop/doc/rule-descriptions.md

- **Keep best-practice rules on, even though they are not WCAG**: the best-practice group covers "Ensure the order of headings is semantically correct", "Ensure the document has a main landmark", "Ensure all page content is contained by landmarks", "Ensure tabindex attribute values are not greater than 0" and "Ensure that every form element has a visible label and is not solely labeled using hidden labels, or the title or aria-describedby attributes". Why: they are tagged `best-practice` rather than `wcag2a`, which means they are not conformance failures but still describe structure a screen reader user relies on. Smell: `heading-order` or `region` disabled in the axe config "because it is not WCAG". Source: https://dequeuniversity.com/rules/axe/4.14/heading-order?application=RuleDescription

- **Treat axe output as a starting list, not a verdict**: "Such tools aren't good enough to solve all your accessibility problems on their own. You'll need a combination of these, knowledge and experience, user testing, etc. to get a full picture." Why: an audit tool "checks pages and returns accessibility errors" for what can be computed from the DOM; it cannot judge whether an alt text is true or a focus order makes sense. Smell: a pull request described as "accessible, axe passes" with no keyboard or screen reader notes. Source: https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/Accessibility/Tooling#auditing_tools

- **Automate the programmatically detectable misses and reserve people for the rest**: "Test early and often, ideally running automated tests to pick up on programmatically detectable missing features (such as missing image alternative text or bad link text) and doing some testing with disabled user groups to see how well more complex site features work for them." Why: the open questions are of the kind "Is my date picker widget usable by people using screen readers?" and "If content updates dynamically, do visually impaired people know about it?", which no rule answers. Smell: a complex widget (date picker, combobox, drag and drop) shipped with only lint and axe coverage. Source: https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/Accessibility/What_is_accessibility#implementing_accessibility_into_your_project

- **Wire the checks into the build, not only the browser**: "Tools to integrate into your build process, programmatically adding accessibility tests, so you can catch errors as you develop your web application:" lists axe-core, jsx-a11y and Lighthouse audits, while the browser extensions are for when you "Use a tool to quickly check for common errors in your browser." Why: a lint rule or test fails on the diff that introduced the problem; an extension only finds it after it ships. Smell: eslint-plugin-jsx-a11y missing from the ESLint config of a React project, or axe only ever run by hand in DevTools. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/Guides/Information_for_Web_authors#automated_checking__repair

## Manual passes

- **Walk the feature with the keyboard only**: "Make sure your functionality is keyboard accessible (see Use semantic UI controls where possible for more details). Test using Tab, Return/Enter, etc." Why: "You should always test your site without a mouse and touch to test keyboard navigation." Smell: a control reachable only by `onClick` on a `<div>`, no visible focus ring, or focus lost to `<body>` after a dialog closes. Source: https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/Accessibility/Tooling#accessibility_testing_checklist

- **Test with a screen reader on the development machine**: "Make sure you have a screen reader or two installed on your development machine, and try using your favorite websites via a screen reader, as discussed below." Why: "If you mark up content using the wrong element, it can confuse screen reader users." Smell: a form whose inputs are announced as "blank" or "edit text" with no label, or a list of "clickable" items with no role. Source: https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/Accessibility/Tooling#screen_readers

- **Check links, headings, forms and tables out of context**: "Look at good-links.html, and note how they make sense when viewed out of context, for example in the VoiceOver Rotor. This is not the case with bad-links.html", where they are all just "click here". Why: screen reader users pull up lists of headings, links and form controls and navigate from there, so each name must stand alone. Smell: several links named "Read more" or "Learn more", or headings that read "Overview" in every section. Source: https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/Accessibility/Tooling#screen_reader_testing

- **Read the page with CSS turned off**: "To test source order, you can turn off a site's CSS and see how understandable it is without it." Why: "assistive technologies read website content based on the order of the source, and disabled people often modify or turn off parts of the CSS to make content more legible (common examples are increasing font size and applying high contrast color schemes)." Smell: `order`, `flex-direction: row-reverse` or absolute positioning used to move a control somewhere other than its source position. Source: https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/Accessibility/Tooling#testing_source_order

- **Zoom to 200 percent and check text still grows**: "Content satisfies the success criterion if it can be scaled up to 200% using at least one text scaling" method. Why: "Many people with visual impairments use screen magnifiers that are either physical magnifiers or software zoom capabilities." Smell: `maximum-scale=1` or `user-scalable=no` in the viewport meta, fixed pixel heights that clip text, or `font-size` locked in `px` on `html`. Source: https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html

- **Zoom to 400 percent, or a 320 CSS pixel viewport, and check for two-direction scrolling**: "This criterion requires non-excepted sections of content that are written in horizontal languages reflow when narrowed to a width equivalent to 320 CSS pixels." Why: "A common way for many article-driven web pages to meet the Reflow success criterion is to ensure that the presentation of a web page can adjust to a single column of content, fitting into a 320 CSS pixel wide viewport and only requiring a user scroll vertically to read the content of the web page." Smell: a horizontal scrollbar on the page at 320 px, fixed `width` on layout containers, or a sticky header that covers most of the zoomed screen. Source: https://www.w3.org/WAI/WCAG22/Understanding/reflow.html

- **Run the page with reduced motion on**: the fix list is "Avoid using unnecessary animation. Provide a control for users to turn off non-essential animations from user interaction. Take advantage of the reduce motion feature in the user agent or operating system." Why: "Some users experience distraction or nausea from animated content. For example, if scrolling a page causes elements to move (other than the essential movement associated with scrolling) it can trigger vestibular disorders." Smell: parallax, auto-playing carousels or entrance transitions with no `prefers-reduced-motion` branch. Source: https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html

- **Check contrast with a tool and never rely on colour alone**: "Use a tool like WebAIM's Color Contrast Checker to check whether your scheme is contrasting enough." and "avoid using only color for signposts or highlighting important information, as this might be missed by people with visual impairments like color blindness. Instead of marking required form fields in red, for example, mark them with an asterisk and in red." Why: automated contrast rules miss text on images and gradients, and cannot tell that an error is conveyed by a red border alone. Smell: a validation state that only changes `border-color`, or a link in body text distinguished only by hue. Source: https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/Accessibility/Tooling#color_contrast_checkers

- **Test in forced colours and other user overrides**: "disabled people often modify or turn off parts of the CSS to make content more legible (common examples are increasing font size and applying high contrast color schemes)." Why: in a high contrast scheme the author's colours are replaced, so anything conveyed by background colour or box shadow disappears. Smell: focus indicator drawn only with `box-shadow`, a custom checkbox whose checked state is a background colour, or `outline: none` with no replacement. Source: https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/Accessibility/Tooling#testing_source_order

- **Simulate impairments and then test with real users**: "While best to test your web applications with real users, you can simulate color blindness, low vision, low contrast, and zooming." and "You can't rely on automated tools alone for determining accessibility problems on your site. Every website project needs a user testing strategy, and it is highly recommended that you include some accessibility user groups". Smell: a release with no record of a keyboard-only, screen reader or low-vision pass on the primary flows. Source: https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/Accessibility/Tooling#user_testing

## Inspect the accessibility tree

- **Read the browser's accessibility tree, not the DOM, when checking semantics**: "Web browsers expose information about the page's content for screen readers (and other AT) to communicate to the user through a representation called the accessibility tree. This provides semantic information such as names and descriptions of elements, what their purpose or role is (is it a button, or an input field?), and whether they are in a particular state (for example, is a dialog box open or closed?)." Why: the tree is what `getByRole` and screen readers see; the DOM and the rendered pixels are not. Smell: a review that confirms a component "looks like a button" without checking its computed role and name in the Firefox Accessibility Inspector or Chrome's Accessibility pane. Source: https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/Accessibility/Tooling#screen_readers

- **Expect styling and script to be invisible to assistive technology**: "ATs mostly tend to make use of semantic information, so this information doesn't include things like styling information, or JavaScript. This information is structured in a tree of information called the accessibility tree." Why: "Where the native semantic information provided by the HTML elements in your web apps falls down, you can supplement it with features from the WAI-ARIA specification". Smell: state held only in a CSS class (`.is-open`, `.selected`, `.error`) with no matching element, attribute or `aria-*` state. Source: https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/Accessibility/What_is_accessibility#accessibility_apis

## Review order

- **Start with semantics**: "Make sure your HTML is as semantically correct as possible. Validating it is a good start, as is using an auditing tool." Why: "it's very important to use semantic HTML correctly" because the tree screen readers consume is built from it; names, keyboard behaviour and ARIA all sit on top. Smell: a diff full of `div` and `span` with handlers, or `role` attributes added to fix a lint error instead of changing the element. Source: https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/Accessibility/Tooling#accessibility_testing_checklist

- **Then check names and text alternatives**: "Make sure your non-text content has text alternatives. An auditing tool is good for catching such problems." Why: automation confirms the attribute exists; a person confirms the name is accurate, unique and useful out of context. Smell: `alt="image"`, icon buttons with no accessible name, `aria-label` text that differs from the visible label. Source: https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/Accessibility/Tooling#accessibility_testing_checklist

- **Then keyboard and hidden content**: "Make sure your functionality is keyboard accessible" and "Make sure hidden content is visible by screen readers." Why: focus order, focus management and what is hidden from whom can only be judged by operating the page. Smell: `tabIndex` greater than zero, `aria-hidden="true"` on a focusable element, or visually hidden content that is also `display: none` for screen readers. Source: https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/Accessibility/Tooling#accessibility_testing_checklist

- **Finish with the visual pass, then test early next time**: "Make sure your site's color contrast is acceptable, using a suitable checking tool." and "Run your site through an auditing tool." Why: "Consider accessibility from the start of a project, and test early and often. Just like any other bug, an accessibility problem becomes more expensive to fix the later it is discovered." Smell: an accessibility ticket raised after the design and markup are frozen, or contrast fixed by darkening one colour without re-checking zoom and forced colours. Source: https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/Accessibility/What_is_accessibility#implementing_accessibility_into_your_project
