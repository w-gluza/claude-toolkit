# Accessibility Keyboard and Focus Rules (WAI-ARIA APG, WCAG 2.2, MDN)

Extracted 2026-11-08 from the w3c/aria-practices and w3c/wcag repositories, the mdn/content repository and the eslint-plugin-jsx-a11y rule docs.

## Operable by keyboard

- **Give every pointer action a keyboard equivalent**: "Everything can be done with a keyboard except freehand movements." and "Ensure pointer actions have a keyboard equivalent." Why: "Many people rely on the keyboard interface, including blind and some mobility impaired people." Smell: a `<div onClick={...}>` or `<span onClick={...}>` with no `onKeyDown`, no `role` and no `tabIndex`. Lint: jsx-a11y/click-events-have-key-events. Source: https://www.w3.org/WAI/WCAG22/Understanding/keyboard.html#brief
- **Treat a role as a promise to implement its keys**: "Is a promise that the author of that `<div>` has also incorporated JavaScript that provides the keyboard interactions expected for a button." Why: "Unlike HTML input elements, ARIA roles do not cause browsers to provide keyboard behaviors or styling." Smell: `role="button"`, `role="tab"` or `role="menuitem"` on a `div` whose only handler is `onClick`. Source: https://www.w3.org/WAI/ARIA/apg/practices/read-me-first/#no_aria_better_bad_aria
- **Make interactive roles focusable**: "Elements with an interactive role and interaction handlers (mouse or key press) must be focusable." The APG puts it as "all interactive UI components need to be reachable via the keyboard" either by being in the tab sequence "or by making them accessible from a component that is in the tab sequence, e.g., as part of a composite component." Why: a control nobody can reach with Tab or arrow keys does not exist for keyboard users. Smell: `<div role="button" onClick={...}>` with no `tabIndex`. Lint: jsx-a11y/interactive-supports-focus. Source: https://www.w3.org/WAI/ARIA/apg/practices/keyboard-interface/#kbd_general_between
- **Prefer native interactive elements to `tabindex` on a `div`**: "Avoid using the `tabindex` attribute in conjunction with non-interactive content to make something intended to be interactive focusable by keyboard input. An example of this would be using a `div` element to describe a button, instead of the `button` element." Why: "Interactive components authored using non-interactive elements are not listed in the accessibility tree. This prevents assistive technology from being able to navigate to and manipulate those components." Smell: `<div tabIndex={0} onClick={...}>` where `<button type="button">` would do. Source: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Global_attributes/tabindex#accessibility_concerns
- **Bind the click action to a key handler that checks the key, not `keyCode`**: "any handlers bound to mouse events should also be bound to keyboard events. For example, to ensure that the Enter key will activate an element, if you have an `onclick="doSomething()"`, you should bind `doSomething()` to the key down event as well: `onkeydown="event.code === "Enter" && doSomething();"`." Why: "most browsers will activate `onclick` event handlers after Enter/Return is pressed on a link or form element that has focus" but "This doesn't work by default however when you allow a non-default-focusable event to have focus using tabindex". Smell: `onKeyDown={(e) => e.keyCode === 13 && ...}` or an `onKeyDown` that duplicates the click logic in a second function instead of calling the same one. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/Guides/Keyboard-navigable_JavaScript_widgets#ensure_that_the_keyboard_can_be_used_to_activate_element
- **Pair hover handlers with focus and blur**: "Functionality that runs in response to these events will not be accessible using other mechanisms, like keyboard controls." and "you should double up these events with similar events that can be activated by other means (so-called device-independent event handlers) - focus and blur would provide accessibility for keyboard users." Why: `mouseover`, `mouseout` and `dblclick` never fire for a keyboard user. Smell: `onMouseEnter={show} onMouseLeave={hide}` on a card, tooltip trigger or preview with no `onFocus`/`onBlur`. Lint: jsx-a11y/mouse-events-have-key-events. Source: https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/Accessibility/CSS_and_JavaScript#other_javascript_accessibility_concerns
- **Prevent the browser default only for keys you actually handle**: "If your widget handles a key event, prevent the browser from also handling it (for example, scrolling in response to the arrow keys) by using your event handler's return code." The APG adds for text inputs: "IMPORTANT: Ensure JavaScript does not interfere with browser-provided text editing functions by capturing key events for the keys used to perform them." Why: an unhandled arrow key that still scrolls the page confuses the user, and a blanket `preventDefault()` breaks typing, cursor movement and selection in editable comboboxes. Smell: `onKeyDown={(e) => { e.preventDefault(); ... }}` at the top of the handler before any key check, or a horizontal widget that swallows `ArrowUp`/`ArrowDown`. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/Guides/Keyboard-navigable_JavaScript_widgets#prevent_used_key_events_from_performing_browser_functions

## Tab order and tabindex

- **Let DOM order define the tab sequence**: "The default order of elements in the tab sequence is the order of elements in the DOM. The DOM order also determines screen reader reading order. It is important to keep the keyboard tab sequence and the screen reader reading order aligned, logical, and predictable" and "The most robust method of manipulating the order of the tab sequence while also maintaining alignment with the reading order that is currently available in all browsers is rearranging elements in the DOM." Why: "Usability of a keyboard interface is heavily influenced by how readily users can guess where focus will land after a navigation key is pressed." Smell: markup ordered for a visual effect with `order:` or `flex-direction: row-reverse` compensating in CSS, so Tab jumps backwards across the screen. Source: https://www.w3.org/WAI/ARIA/apg/practices/keyboard-interface/#kbd_general_between
- **Never use a positive `tabindex`**: "You are recommended to only use `0` and `-1` as `tabindex` values. Avoid using `tabindex` values greater than `0` and CSS properties that can change the order of focusable HTML elements (Ordering flex items)." Why: "Doing so makes it difficult for people who rely on using keyboard for navigation or assistive technology to navigate and operate page content. Instead, write the document with the elements in a logical sequence." Smell: `tabIndex={1}`, `tabindex="2"` or any value above zero. Lint: jsx-a11y/tabindex-no-positive. Source: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Global_attributes/tabindex
- **Reserve `tabindex="-1"` for programmatic focus targets**: "`tabindex="-1"` may be useful for elements that should not be navigated to directly using the Tab key, but need to have keyboard focus set to them. Examples include an off-screen modal window that should be focused when it comes into view, or a form submission error message that should be immediately focused when an errant form is submitted." Why: "A negative value (the exact negative value doesn't actually matter, usually `tabindex="-1"`) means that the element is not reachable via sequential keyboard navigation." Smell: a heading or error summary that code calls `.focus()` on but that has no `tabindex="-1"`, so the call silently does nothing. Source: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Global_attributes/tabindex
- **Do not add `tabindex="0"` to non-interactive elements**: "Tab key navigation should be limited to elements on the page that can be interacted with. Thus it is not necessary to add a tabindex to items in an unordered list, for example, to make them navigable through assistive technology." Why: "Generally, we should try to reduce the size of the page's tab ring rather than increasing it." and WCAG adds "authors should try to avoid having focusable elements which cannot be operated or actioned, as these are likely to make operation tedious for keyboard users." Smell: `<li tabIndex={0}>` on every list item, `tabIndex={0}` on a card wrapper, paragraph or heading that has no handler. Lint: jsx-a11y/no-noninteractive-tabindex. Source: https://www.w3.org/WAI/WCAG22/Understanding/focus-order.html#intent
- **Do not add `tabindex` to natively focusable elements or to `<dialog>`**: "Developers shouldn't add the `tabindex` attribute to these elements unless it changes the default behavior (for example, including a negative value will remove the element from the focus navigation order)." and "The tabindex attribute must not be used on the `dialog` element." Why: the browser already gives `a[href]`, `button`, `input`, `select`, `textarea` and `summary` a default `tabindex` of 0, and "Do not add the `tabindex` property to the `<dialog>` element as it is not interactive and does not receive focus." Smell: `<button tabIndex={0}>`, `<a href tabIndex={0}>`, `<dialog tabIndex={-1}>`. Source: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Global_attributes/tabindex
- **Do not nest focusable elements**: "it is a failure of Focus Order if items receive focus in an order that impedes the meaning or operation of content, or creates confusing or illogical focus orders - for example, a control appearing to receive focus multiple times due to the use of nested focusable elements." Why: the same control is announced twice and Tab appears to stall. Smell: `<div tabIndex={0} onClick={...}><button>...</button></div>`, or a clickable card with `tabIndex={0}` wrapping a link. Source: https://www.w3.org/WAI/WCAG22/Understanding/focus-order.html#intent
- **Make the focus order preserve meaning, not pixel layout**: "Focus order does not necessarily need to follow the visual layout of the web page, as long as the order in which elements receive focus is logical, and the hierarchy and relationship of content implied by the visual presentation is preserved." but "authors should generally still make sure that the focus order reinforces the reading order implied by the visual layout". Why: "People with disabilities that make reading difficult can become disoriented when tabbing takes focus someplace unexpected." Smell: a form where "the tab order for the form skips between fields in different sections of the form, so that focus moves from the name field to a checkbox, then to the street address, then to another checkbox." Source: https://www.w3.org/WAI/WCAG22/Understanding/focus-order.html#intent

## Focus management

- **Never let focus fall to `body`**: "It is essential that there is always a component within the user interface that is active (document.activeElement is not null or is not the body element) and that the active element has a visual focus indicator." and "if the user closes a dialog or performs a destructive operation like deleting an item from a list, the active element may be hidden or removed from the DOM. If such events are not managed to set focus on the button that triggered the dialog or on the list item following the deleted item, browsers move focus to the body element, effectively causing a loss of focus within the user interface." Why: after a loss of focus the next Tab press starts from the top of the page. Smell: a delete handler that removes the focused row, a "Remove" chip, a toast with a focused "Dismiss" button, or a conditional render that unmounts the focused element with no `.focus()` on a successor. Source: https://www.w3.org/WAI/ARIA/apg/practices/keyboard-interface/#kbd_focus_discernable_predictable
- **Move focus to the new view on a single-page route change**: the APG requires "there is always a component within the user interface that is active (document.activeElement is not null or is not the body element)" and MDN's `tabindex="-1"` guidance covers "an off-screen modal window that should be focused when it comes into view, or a form submission error message that should be immediately focused". Why: when a router swaps the page content, the previously focused link is removed and focus drops to `body`, so a screen reader user hears nothing and Tab restarts from the top. Smell: a router `navigate()` or `<Link>` handler with no focus call, and a page component whose `<h1>` has no `tabindex="-1"` to receive focus or a skip target. Source: https://www.w3.org/WAI/ARIA/apg/practices/keyboard-interface/#kbd_focus_discernable_predictable
- **Do not set initial focus or `autofocus` on page load, only inside a dialog or popover**: "Automatically focusing a form control can confuse visually-impaired people using screen-reading technology and people with cognitive impairments. When `autofocus` is assigned, screen-readers "teleport" their user to the form control without warning them beforehand." The APG allows an exception only where "The page offers a single, primary function that nearly all users employ immediately after page load." and "Any given user is likely to use the page often." Why: "Automatically focusing on a control can cause the page to scroll on load. The focus can also cause dynamic keyboards to display on some touch devices." Inside a `<dialog>` the attribute is the right tool, where MDN says it "should be added to the element the user is expected to interact with immediately upon opening a modal dialog". Smell: `<input autoFocus>` in a page-level form, or `useEffect(() => inputRef.current.focus(), [])` in a page component. Lint: jsx-a11y/no-autofocus. Source: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Global_attributes/autofocus#accessibility_concerns
- **Set focus with `element.focus()` and track it with `focus`/`blur` listeners**: "Do not dispatch the `focus` event to send focus to an element. DOM focus events are considered informational only: they are generated by the system after something is focused, but not actually used to set focus. Use `element.focus()` instead." and "Do listen for the `focus` and `blur` events to track focus changes. Don't assume that all focus changes will come via key and mouse events: assistive technologies such as screen readers can set the focus to any focusable element." Why: focus set by a screen reader bypasses key and mouse handlers, so state derived only from those handlers drifts out of sync. Smell: `el.dispatchEvent(new FocusEvent("focus"))`, or `activeIndex` state updated only in `onKeyDown` and `onClick`. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/Guides/Keyboard-navigable_JavaScript_widgets#usage_of_focus_events
- **Keep pointer and keyboard paths in the same state**: "When a component is clicked/tapped, authors should take the same steps to set the correct tabindex or aria-activedescendant for the element, in the same way that they would for keyboard navigation. Otherwise, this could lead to a confusing experience for users that switch between pointer and keyboard navigation, as it will lead to a mismatch." MDN agrees: "the code that updates the `tabindex` or the styling when users navigate using the arrow keys should also be used by mouse click handlers to produce the same changes." Why: a mouse user who clicks the third tab and then presses Right Arrow should move from the third tab, not the first. Smell: an `onClick` on a tab, option or cell that sets selection but never updates the roving `tabIndex` or `aria-activedescendant`. Source: https://www.w3.org/WAI/ARIA/apg/practices/keyboard-interface/#kbd_focus_activedescendant
- **Do not remove the focus outline; scope it with `:focus-visible` if needed**: "Ensure that focused elements have a focus ring. This can be done using the CSS `outline` property, which should not be unconditionally set to `none` - if you want to prevent unnecessary focus rings being displayed, use the `:focus-visible` pseudo-class." Why: an element reached with `tabindex="-1"` or `.focus()` is otherwise invisible to a sighted keyboard user. Appearance, size and contrast of the indicator belong to the visual-focus reference. Smell: `*:focus { outline: none; }`, `outline: 0` on `:focus`, or a reset stylesheet that strips `outline` with no `:focus-visible` rule. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/Guides/Keyboard-navigable_JavaScript_widgets#always_draw_the_focus_for_tabindex-1_items_and_elements_that_receive_focus_programmatically
- **Keep focus and selection distinct, and let selection follow focus only when it is instant**: "There is only one point of focus at any time and all operations take place at the point of focus." and "The selected state must be visually distinct from the focus indicator." On automatic selection: "if displaying a new panel causes a network request and possibly a page refresh, the effect of having selection automatically follow focus can be devastating to the experience for keyboard and screen reader users." Why: "From the developer's perspective, the difference is simple -- the focused element is the active element (document.activeElement). Selected elements are elements that have aria-selected="true"." Smell: `aria-selected` toggled in the same place as `.focus()` in a multi-select list, or a tab list whose arrow-key handler triggers a `fetch` for the new panel. Source: https://www.w3.org/WAI/ARIA/apg/practices/keyboard-interface/#kbd_selection_follows_focus
- **An overlay that can obscure focus must take focus or dismiss on blur**: "A dialog-like overlay that does not take focus on appearance and does not either constrain interaction to the overlay or dismiss itself on loss of focus (thus allowing focus to exit into the content behind it) will be at risk of failing this SC, where it is positioned such that it can obscure other focusable items." Why: "A properly constructed modal dialog will always pass this SC. Even if it appears directly on top of an item with focus, the dialog takes focus on appearance". Whether the indicator itself is visible enough belongs to the visual-focus reference. Smell: a fixed-position chat panel, cookie banner or toast rendered with `position: fixed` that neither receives focus nor closes on `blur`, while Tab continues through the page beneath it. Source: https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html#dialogs

## Composite widgets: roving tabindex and aria-activedescendant

- **Give a composite one stop in the Tab sequence**: "the tab sequence should include only one focusable element of a composite UI component. Once a composite contains focus, keys other than Tab and Shift + Tab enable the user to move focus among its focusable elements." Where focus lands on entry is "The element that had focus the last time the composite contained focus" for grids, "The selected element" for "radio groups, tabs, list boxes, and trees", and "The first element" for "menubars and toolbars". Why: "A radio group, for example, contains multiple radio buttons, each of which is focusable. However, only one of the radio buttons is included in the tab sequence." Smell: every `role="tab"`, `role="option"`, `role="menuitem"` or `role="gridcell"` rendered with `tabIndex={0}`. Source: https://www.w3.org/WAI/ARIA/apg/practices/keyboard-interface/#kbd_general_within
- **Implement roving tabindex fully**: "the element that is to be included in the tab sequence has tabindex="0" and all other focusable elements contained in the composite have tabindex="-1"." On each navigation key: "set tabindex="-1" on the element that has tabindex="0". Set tabindex="0" on the element that will become focused as a result of the key event. Set focus, element.focus(), on the element that has tabindex="0"." Why: "One benefit of using roving tabindex rather than aria-activedescendant to manage focus is that the user agent will scroll the newly focused element into view." Smell: an arrow-key handler that calls `.focus()` on the next item but leaves the previous item at `tabIndex={0}`, so Tab stops on two items. Source: https://www.w3.org/WAI/ARIA/apg/practices/keyboard-interface/#kbd_roving_tabindex
- **With `aria-activedescendant`, keep the container focusable and scroll the active item into view**: "only the container element needs to be included in the tab sequence. When the container has DOM focus, the value of aria-activedescendant on the container tells assistive technologies which element is active within the widget." and "When the container element receives DOM focus, draw a visual focus indicator on the active element and ensure the active element is scrolled into view." Why: "Because an element with `aria-activedescendant` must be tabbable, it must either have an inherent `tabIndex` of zero or declare a `tabIndex` attribute." Smell: `<ul role="listbox" aria-activedescendant={id}>` with no `tabIndex`, or options that change `aria-activedescendant` without `scrollIntoView` in a scrolling list. Lint: jsx-a11y/aria-activedescendant-has-tabindex. Source: https://www.w3.org/WAI/ARIA/apg/practices/keyboard-interface/#kbd_focus_activedescendant
- **Point `aria-activedescendant` only at an owned or controlled element**: "One of the following three conditions must be met. The element referenced as active is a DOM descendant of the focused referencing element. The focused referencing element has a value specified for the aria-owns property that includes the ID of the element referenced as active. The focused referencing element has role of combobox, textbox, or searchbox and has aria-controls property referring to an element with a role that supports aria-activedescendant". Why: "The attribute manages providing assistive technologies with information as to which element has focus, but doesn't actually create focus." Smell: an `<input aria-activedescendant="opt-3">` with no `aria-controls` pointing at the listbox that contains `opt-3`, or an ID that refers to an element rendered in a portal outside the container. Source: https://www.w3.org/WAI/ARIA/apg/practices/keyboard-interface/#kbd_focus_activedescendant
- **Keep disabled items inside composites focusable with `aria-disabled`**: "there are some contexts where it is useful for an element to convey a disabled state while remaining focusable, especially inside of composite widgets. This can be accomplished by applying the state aria-disabled="true"." Why: "screen reader users are far less likely to discover disabled elements that are not focusable because moving focus is one of their primary methods of discovery." MDN: "disabled items within a grouped widget (such as menu items in a menu) should remain navigable using arrow keys." Smell: `disabled` attribute or `tabIndex={-1}` skipping in the arrow-key handler for a `menuitem`, `option`, `tab` or `treeitem`. Source: https://www.w3.org/WAI/ARIA/apg/practices/keyboard-interface/#kbd_disabled_controls
- **Use the arrow keys that match the widget orientation and leave the others alone**: for tabs, "If the tab list is horizontal, it does not listen for `Down Arrow` or `Up Arrow` so those keys can provide their normal browser scrolling functions even when focus is inside the tab list." and "When a tab list has its aria-orientation set to `vertical`: `Down Arrow` performs as `Right Arrow` is described above. `Up Arrow` performs as `Left Arrow` is described above." Why: a horizontal widget that captures vertical arrows stops the page scrolling while it has focus. Smell: a `switch (e.key)` that handles all four arrows in a horizontal tab list, or a vertical listbox with `aria-orientation="vertical"` missing while it handles `ArrowLeft`. Source: https://www.w3.org/WAI/ARIA/apg/patterns/tabs/#keyboard_interaction

## Dialogs, popovers and tooltips

- **Move focus into the dialog when it opens**: "When a dialog opens, focus moves to an element inside the dialog." and "Generally, focus is initially set on the first focusable element. However, the most appropriate focus placement will depend on the nature and size of the content." For the alert dialog pattern: "See the keyboard interaction section for the modal dialog pattern." Why: without it, Tab continues through the page behind the dialog and a screen reader never announces the dialog. Smell: `setOpen(true)` with no `.focus()` call, or a `showModal()` replaced by toggling a `className`. Source: https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/#keyboard_interaction
- **Choose initial focus for long content and destructive actions**: "if the content would be difficult to understand when announced as a single unbroken string, then it is advisable to add `tabindex="-1"` to a static element at the start of the content and initially focus that element." and "If a dialog contains the final step in a process that is not easily reversible, such as deleting data or completing a financial transaction, it may be advisable to set focus on the least destructive action". Why: "If content is large enough that focusing the first interactive element could cause the beginning of content to scroll out of view" the user misses the start of the dialog. Smell: a confirmation dialog with `autoFocus` on the "Delete" button, or a terms dialog that focuses an "Accept" button below several paragraphs. Source: https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/#keyboard_interaction
- **Keep Tab and Shift+Tab inside a modal dialog, with a known way out**: "`Tab`: Moves focus to the next tabbable element inside the dialog. If focus is on the last tabbable element inside the dialog, moves focus to the first tabbable element inside the dialog." WCAG allows this: "There may be times when it's appropriate for a web page to restrict focus to a subsection of the content - for example, when the user is inside a modal dialog or popover. This does not fail the requirements of this criterion, as long as the user knows how to "untrap" the focus and leave that component." Why: "Keyboard users don't get stuck." Smell: a modal `div` where Tab reaches links behind the backdrop, or a trap with no `Escape` handler and no close button. Source: https://www.w3.org/WAI/WCAG22/Understanding/no-keyboard-trap.html#intent
- **Close the dialog on Escape, last-shown first**: "`Escape`: Closes the dialog." and "Keyboard users expect the Esc key to close modal dialogs; ensure that this behavior is implemented and maintained. If multiple modal dialogs are open, pressing the Esc key should close only the last shown dialog. When using `<dialog>`, this behavior is provided by the browser." Why: WCAG names `Esc` as "a commonly used "standard exit method"". Smell: a custom modal with `onKeyDown` handling only `Tab`, or a `cancel` event handler that calls `preventDefault()` on a `<dialog>` so Escape no longer closes it. Source: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/dialog#accessibility
- **Return focus to the invoking element when the dialog closes**: "When a dialog closes, focus returns to the element that invoked the dialog unless either: The invoking element no longer exists. Then, focus is set on another element that provides logical work flow." Why: "If activating the button closes a dialog, focus typically returns to the button that opened the dialog unless the function performed in the dialog context logically leads to a different element." Smell: a close handler that unmounts the dialog and nothing else, or one that stores the trigger in a ref on mount but never calls `triggerRef.current.focus()` on close. Source: https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/#keyboard_interaction
- **Give every dialog a visible close control in its tab sequence**: "It is strongly recommended that the tab sequence of all dialogs include a visible element with role `button` that closes the dialog, such as a close icon or cancel button." MDN: "It is important to provide a closing mechanism for every `<dialog>` element, and to ensure that this works on devices that might not have a physical keyboard." Why: Escape is unavailable on touch devices and to some switch users. Smell: a dialog closed only by clicking the backdrop or pressing Escape, or a close "X" rendered as a `span` with `onClick`. Source: https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/#keyboard_interaction
- **Use `<dialog>` with `showModal()` and `inert` rather than a hand-written focus trap**: "When implementing modal dialogs, everything other than the `<dialog>` and its contents should be rendered inert using the `inert` attribute. When using `<dialog>` along with the `HTMLDialogElement.showModal()` method, this behavior is provided by the browser." and "While dialogs can be created using other elements, the native `<dialog>` element provides usability and accessibility features that must be replicated if you use other elements for a similar purpose." Why: "Modal `dialog`s generated with `showModal()` escape inertness" while an inert subtree "gets removed from the tab order and accessibility tree." Apply `inert` to sections, not single controls, and remove it when the dialog closes; MDN warns "By default, there is no visual way to tell whether or not an element or its subtree is inert." Smell: a `focus-trap` loop over `querySelectorAll('a, button, [tabindex]')` inside a `<div role="dialog">`, `aria-hidden="true"` sprinkled on siblings instead of `inert`, or `inert` left on `<main>` after the dialog closes. Baseline: `dialog` Widely (since 2024-09); `inert` Widely (since 2025-10). Source: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/dialog#accessibility
- **Use `popover` with `popovertarget` for light-dismiss overlays so focus returns to the invoker**: "When the popover is shown, the keyboard focus navigation order is updated so that the popover is next in the sequence: for example, when a button is pressed to show a popover, any buttons inside the popover will be next in the tabbing order (will be focused by pressing the Tab key). Conversely, when closing the popover via the keyboard (usually via the Esc key), focus is shifted back to the invoker." Why: an `auto` popover "can also be closed, using browser-specific mechanisms such as pressing the Esc key" with no author code. Smell: a dropdown panel rendered in a portal at the end of `<body>` with a hand-written outside-click listener and no Escape handling or focus return. Baseline: `popover` Newly (since 2025-01). Source: https://developer.mozilla.org/en-US/docs/Web/API/Popover_API/Using#popover_accessibility_features
- **Keep tooltips unfocusable, dismissible with Escape, and tied to focus of the trigger**: "`Escape`: Dismisses the Tooltip." and "Focus stays on the triggering element while the tooltip is displayed. If the tooltip is invoked when the trigger element receives focus, then it is dismissed when it no longer has focus (onBlur)." Why: "Tooltip widgets do not receive focus." and "A hover that contains focusable elements can be made using a non-modal dialog." Smell: a tooltip shown only on `onMouseEnter`, a tooltip with `tabIndex={0}` or a link inside it, or no `keydown` listener for `Escape` while it is open. Source: https://www.w3.org/WAI/ARIA/apg/patterns/tooltip/#keyboard_interaction

## Menus and disclosure

- **Open a menu button with Enter, Space and Down Arrow, and focus the first item**: "`Enter`: opens the menu and places focus on the first menu item. `Space`: Opens the menu and places focus on the first menu item. (Optional) `Down Arrow`: opens the menu and moves focus to the first menu item. (Optional) `Up Arrow`: opens the menu and moves focus to the last menu item." Why: "Unlike a `menubar`, a `menu` is not visually persistent, and authors are responsible for ensuring focus moves to an item inside of a `menu` when the `menu` opens." Smell: a menu that opens on `onMouseEnter` only, or an `onClick` that sets `open` without moving focus into the menu. Source: https://www.w3.org/WAI/ARIA/apg/patterns/menu-button/#keyboard_interaction
- **Do not let Tab move through menu items**: "Because `menubar` and `menu` elements are composite widgets as described in the practice for Keyboard Navigation Inside Components, `Tab` and `Shift` + `Tab` do not move focus among the items in the menu." and "When focus is on a `menuitem` in a `menu` or `menubar`, move focus out of the `menu` or `menubar`, and close all menus and submenus." Why: the whole menu is one stop in the page tab sequence. Smell: `<li role="menuitem" tabIndex={0}>` for every item, or a menu that stays open after Tab leaves it. Source: https://www.w3.org/WAI/ARIA/apg/patterns/menubar/#keyboard_interaction
- **Use Down/Up in menus, Left/Right in menubars, and Right to open a submenu**: "`Down Arrow`: When focus is on a `menuitem` in a `menubar`, and that `menuitem` has a submenu, opens the submenu and places focus on the first item in the submenu. When focus is in a `menu`, moves focus to the next item, optionally wrapping from the last to the first." and "`Right Arrow`: When focus is in a `menubar`, moves focus to the next item, optionally wrapping from the last to the first. When focus is in a `menu` and on a `menuitem` that has a submenu, opens the submenu and places focus on its first item." Also "`Home`: If arrow key wrapping is not supported, moves focus to the first item in the current `menu` or `menubar`." Why: "Menu widgets behave like native operating system menus, such as the menus that pull down from the menubars commonly found at the top of many desktop application windows." Smell: a dropdown where only `Tab` moves between items, or a submenu that opens only on hover. Source: https://www.w3.org/WAI/ARIA/apg/patterns/menubar/#keyboard_interaction
- **Close the menu on Escape and return focus to its opener**: "`Escape`: Close the menu that contains focus and return focus to the element or context, e.g., menu button or parent `menuitem`, from which the menu was opened." Why: "If a menu is opened or a menubar receives focus as a result of a context action, `Escape` or `Enter` may return focus to the invoking context." Smell: an Escape handler that sets `open=false` and leaves `document.activeElement` on `body`, or a `menuitem` activation that closes the menu without focusing the menu button. Source: https://www.w3.org/WAI/ARIA/apg/patterns/menubar/#keyboard_interaction
- **Toggle a disclosure with both Enter and Space**: "`Enter`: activates the disclosure control and toggles the visibility of the disclosure content. `Space`: activates the disclosure control and toggles the visibility of the disclosure content." Why: "The element that shows and hides the content has role button." so it must behave like one. Smell: a "Show more" toggle built on `<a href="#">` (Space scrolls the page) or on a `div` with `onClick` only. Source: https://www.w3.org/WAI/ARIA/apg/patterns/disclosure/#keyboard_interaction
- **Keep every accordion header in the Tab sequence**: "`Tab`: Moves focus to the next focusable element; all focusable elements in the accordion are included in the page `Tab` sequence." and "`Enter` or `Space`: When focus is on the accordion header for a collapsed panel, expands the associated panel." Why: accordion headers are independent buttons, not a composite, so a roving tabindex here hides headers from Tab. Smell: `tabIndex={-1}` on all but one accordion header, or arrow-key handlers that wrap focus between headers while Tab skips them. Source: https://www.w3.org/WAI/ARIA/apg/patterns/accordion/#keyboard_interaction

## Tabs, lists, trees and comboboxes

- **Put only the active tab in the Tab sequence and move between tabs with arrows**: "`Tab`: When focus moves into the tab list, places focus on the active `tab` element. When the tab list contains the focus, moves focus to the next element in the page tab sequence outside the tablist, which is the tabpanel unless the first element containing meaningful content inside the tabpanel is focusable." and "`Left Arrow`: moves focus to the previous tab. If focus is on the first tab, moves focus to the last tab." Why: Tab should reach the panel content in one press, not after every tab, and "When the tabpanel does not contain any focusable elements or the first element with content is not focusable, the tabpanel should set `tabindex="0"` to include it in the tab sequence of the page." Smell: every `role="tab"` with `tabIndex={0}`, `ArrowLeft`/`ArrowRight` with no handler on the tab list, or a text-only `<div role="tabpanel">` with no `tabIndex`. Source: https://www.w3.org/WAI/ARIA/apg/patterns/tabs/#keyboard_interaction
- **Activate tabs automatically only when panels are preloaded; otherwise on Space or Enter**: "It is recommended that tabs activate automatically when they receive focus as long as their associated tab panels are displayed without noticeable latency. This typically requires tab panel content to be preloaded." and "`Space or Enter`: Activates the tab if it was not activated automatically on focus." Why: "Otherwise, automatic activation slows focus movement, which significantly hampers users' ability to navigate efficiently across the tab list." Smell: an arrow-key handler that calls `router.push` or `fetch` on each focus move, or a manual-activation tab list with no `Enter`/`Space` handler. Source: https://www.w3.org/WAI/ARIA/apg/patterns/tabs/#keyboard_interaction
- **Give a listbox arrow keys, Home/End, type-ahead and modifier-free multi-select**: "`Down Arrow`: Moves focus to the next option." "`Home` (Optional): Moves focus to first option. ... Supporting this key is strongly recommended for lists with more than five options." "Type-ahead is recommended for all listboxes, especially those with more than seven options" and for multi-select "`Space`: changes the selection state of the focused option." Why: "If none of the options are selected before the listbox receives focus, the first option receives focus." and "If an option is selected before the listbox receives focus, focus is set on the selected option." Smell: a custom select built from `div`s whose only handler is `onClick`, or a multi-select that requires `Ctrl`+click with no `Space` toggle. Source: https://www.w3.org/WAI/ARIA/apg/patterns/listbox/#keyboard_interaction
- **Give a tree Right/Left to open and close, Up/Down to move, Home/End and Enter**: "`Right arrow`: When focus is on a closed node, opens the node; focus does not move. When focus is on a open node, moves focus to the first child node." "`Left arrow`: When focus is on an open node, closes the node. When focus is on a child node that is also either an end node or a closed node, moves focus to its parent node." "`Home`: Moves focus to the first node in the tree without opening or closing a node. `End`: Moves focus to the last node in the tree that is focusable without opening a node." "`Enter`: activates a node, i.e., performs its default action." Why: "Type-ahead is recommended for all trees, especially for trees with more than 7 root nodes". Smell: a file tree where only clicking a chevron expands a node, or a `treeitem` handler covering `ArrowUp`/`ArrowDown` but not `Home`, `End`, `ArrowLeft` or `ArrowRight`. Source: https://www.w3.org/WAI/ARIA/apg/patterns/treeview/#keyboard_interaction
- **Keep DOM focus in the combobox input; Down Arrow opens, Escape dismisses, Enter accepts**: "`Tab`: The combobox is in the page `Tab` sequence. Note: The popup indicator icon or button (if present), the popup, and the popup descendants are excluded from the page `Tab` sequence." "`Down Arrow`: If the popup is available, moves focus into the popup" "`Escape`: Dismisses the popup if it is visible." "`Enter`: If the combobox is editable and an autocomplete suggestion is selected in the popup, accepts the suggestion". Why: "DOM Focus is maintained on the combobox and the assistive technology focus is moved within the listbox using `aria-activedescendant`". Smell: an autocomplete whose suggestion list items are `<li tabIndex={0}>` reached with Tab, an `onKeyDown` that calls `.focus()` on an option, or no `Escape` handler. Source: https://www.w3.org/WAI/ARIA/apg/patterns/combobox/#keyboard_interaction

## Grids, toolbars, radio groups, feeds and carousels

- **Make every grid cell focusable and navigable with arrows, Home/End, Page Up/Down and Ctrl+Home/End**: "In a grid, every cell contains a focusable element or is itself focusable, regardless of whether the cell content is editable or interactive." "`Right Arrow`: Moves focus one cell to the right. If focus is on the right-most cell in the row, focus does not move." "`Home`: moves focus to the first cell in the row that contains focus." "`Control` + `Home`: moves focus to the first cell in the first row." Why: "While in application mode, a screen reader user hears only focusable elements and content that labels focusable elements. So, screen reader users may unknowingly overlook elements contained in a grid that are either not focusable or not used to label a column or row." Arrow keys stop at the edges of a data grid; only a layout grid may wrap, because "While This type of focus movement wrapping can be very helpful in a layout grid, it would be disorienting if used in a data grid, especially for users of assistive technologies." Smell: `role="grid"` on a table where only the links inside cells are focusable and Tab visits each one, arrow keys that do nothing, or a spreadsheet-style grid whose Right Arrow jumps to the next row. Source: https://www.w3.org/WAI/ARIA/apg/patterns/grid/#dataGrid
- **Switch between grid navigation and in-cell editing with Enter, F2 and Escape**: "`Enter`: Disables grid navigation and: If the cell contains editable content, places focus in an input field, such as a textbox." "`F2`: If the cell contains editable content, places focus in an input field, such as a textbox. A subsequent press of `F2` restores grid navigation functions." "`Escape`: restores grid navigation. If content was being edited, it may also undo edits." Why: "While navigation keys, such as arrow keys, are moving focus from cell to cell, they are not available to perform actions like operate a combobox or move an editing caret inside of a cell." Smell: an editable cell `input` that is always focused so arrows move the caret and the grid cannot be navigated, or no way back to cell navigation once editing starts. Source: https://www.w3.org/WAI/ARIA/apg/patterns/grid/#gridNav_inside
- **Make a toolbar one tab stop with arrow navigation, and avoid controls that need the same arrows**: "`Tab` and `Shift` + `Tab`: Move focus into and out of the toolbar." "`Left Arrow`: Moves focus to the previous control." "`Right Arrow`: Moves focus to the next control." and "Avoid including controls whose operation requires the pair of arrow keys used for toolbar navigation. If unavoidable, include only one such control and make it the last element in the toolbar." Why: "Implement focus management so the keyboard tab sequence includes one stop for the toolbar and arrow keys move focus among the controls in the toolbar." Smell: `role="toolbar"` wrapping buttons that each have `tabIndex={0}`, or a horizontal toolbar with a horizontal slider in the middle. Source: https://www.w3.org/WAI/ARIA/apg/patterns/toolbar/#keyboard_interaction
- **Land on the checked radio and let arrows move and check, except inside a toolbar**: "When focus moves into a radio group: If a radio button is checked, focus is set on the checked button. If none of the radio buttons are checked, focus is set on the first radio button in the group." "`Right Arrow` and `Down Arrow`: move focus to the next radio button in the group, uncheck the previously focused button, and check the newly focused button." but in a toolbar "when navigating through a radio group in a toolbar with arrow keys, the button that is checked does not change." Why: "users need to be able to navigate among all toolbar elements, including the radio buttons, without changing which radio button is checked." Smell: a segmented control built from `div role="radio"` items that are all in the Tab sequence, or arrow keys that move focus without checking outside a toolbar. Source: https://www.w3.org/WAI/ARIA/apg/patterns/radio/#keyboard_interaction
- **Give a feed Page Down/Page Up and Ctrl+End/Ctrl+Home, and document them**: "`Page Down`: Move focus to next article. `Page Up`: Move focus to previous article. `Control` + `End`: Move focus to the first focusable element after the feed. `Control` + `Home`: Move focus to the first focusable element before the feed." Why: "Due to the lack of convention, providing easily discoverable keyboard interface documentation is especially important." Smell: an infinite-scroll list with `role="feed"` and no key handler, so a keyboard user can never get past content that keeps loading. Source: https://www.w3.org/WAI/ARIA/apg/patterns/feed/#keyboard_interaction
- **Stop carousel rotation on focus and put the rotation control first**: "If the carousel has an auto-rotate feature, automatic slide rotation stops when any element in the carousel receives keyboard focus. It does not resume unless the user activates the rotation control." "If present, the rotation control is the first element in the `Tab` sequence inside the carousel. It is essential that it precede the rotating content so it can be easily located." and "Activating the rotation control, next slide, and previous slide do not move focus, so users may easily repetitively activate them as many times as desired." Why: "if slides rotate automatically and a screen reader user is not aware of the rotation, the user may read an element on slide 1, execute the screen reader command for next element, and, instead of hearing the next element on slide 1, hear an element from slide 2". Smell: `setInterval` advancing slides with no pause button and no `onFocus` that clears it, or a pause button rendered after the slides. Source: https://www.w3.org/WAI/ARIA/apg/patterns/carousel/#keyboard_interaction

## Buttons, links, switches and range inputs

- **Activate buttons with both Space and Enter, toggles with Space, then place focus deliberately**: "`Space`: Activates the button. `Enter`: Activates the button." and "If activating the button opens a dialog, the focus moves inside the dialog." "If activating the button does not dismiss the current context, then focus typically remains on the button after activation, e.g., an Apply or Recalculate button." Why: MDN adds "Within a form, the Spacebar key should select or activate the control, while the Enter key should submit the form's default action." WCAG notes a control that "only reacts to `Enter`" still passes 2.1.1, so this is the convention users expect rather than the legal minimum. Checkboxes and switches toggle on Space: "`Space`: When focus is on the switch, changes the state of the switch. `Enter` (Optional): When focus is on the switch, changes the state of the switch." Smell: a `div role="button"` whose `onKeyDown` checks only `"Enter"`, an `<a href="#">` used as a button so Space scrolls the page, or `<div role="switch" aria-checked onClick={...}>` with no key handler. Source: https://www.w3.org/WAI/ARIA/apg/patterns/button/#keyboard_interaction
- **Use a real `<a href>` for links so Enter navigates**: "`Enter`: Executes the link and moves focus to the link target." and "Authors are strongly encouraged to use a native host language link element, such as an HTML `<A>` element with an `href` attribute." Why: "applying the link role to an element will not cause browsers to enhance the element with standard link behaviors, such as navigation to the link target or context menu actions. When using the `link` role, providing these features of the element is the author's responsibility." Smell: `<span role="link" onClick={() => navigate(...)}>`, or `<a>` without `href` carrying an `onClick`. Source: https://www.w3.org/WAI/ARIA/apg/patterns/link/#keyboard_interaction
- **Give a slider arrows for one step, Home/End for the range ends, and Page keys for large steps**: "`Right Arrow`: Increase the value of the slider by one step. `Up Arrow`: Increase the value of the slider by one step. `Left Arrow`: Decrease the value of the slider by one step. `Down Arrow`: Decrease the value of the slider by one step. `Home`: Set the slider to the first allowed value in its range. `End`: Set the slider to the last allowed value in its range. `Page Up` (Optional): Increase the slider value by an amount larger than the step change made by `Up Arrow`." Why: "Focus is placed on the slider (the visual object that the mouse user would move, also known as the thumb." Smell: a custom range control driven only by `onPointerMove`/drag, or a `div role="slider"` with no `tabIndex` and no `onKeyDown`. Source: https://www.w3.org/WAI/ARIA/apg/patterns/slider/#keyboard_interaction
- **Keep focus in the spin button text field and step with Up/Down, Home/End**: "`Up Arrow`: Increases the value. `Down Arrow`: Decreases the value. `Home`: If the spinbutton has a minimum value, sets the value to its minimum. `End`: If the spinbutton has a maximum value, sets the value to its maximum." and "Focus remains on the text field during operation." Why: "The text field is usually the only focusable component because the increase and decrease functions are keyboard accessible via arrow keys." Smell: a quantity picker where the plus and minus buttons are the only way to change the value, or where they are in the Tab sequence alongside the input. Source: https://www.w3.org/WAI/ARIA/apg/patterns/spinbutton/#keyboard_interaction

## Shortcuts and context changes

- **Do not change context when an element receives focus**: "Any component that is able to trigger an event when it receives focus must not change the context. Examples of changing context when a component receives focus include, but are not limited to: forms submitted automatically when a component receives focus; new windows launched when a component receives focus; focus is changed to another component when that component receives focus". Why: "Content that behaves predictably is especially important to people with disabilities." Smell: `onFocus={() => setOpenDialog(true)}`, `onFocus` that calls `window.open` or `router.push`, or an `onFocus` on a field that moves focus elsewhere. Source: https://www.w3.org/WAI/WCAG22/Understanding/on-focus.html#intent
- **Do not change context on input without warning the user first**: "Changes of context are appropriate only when it is clear that such a change will happen in response to the user's action." and "checking a checkbox, entering text into a text field, or changing the selected option in a list control changes its setting, but activating a link or a button does not." Why: "Unexpected changes of context can be so disorienting for users with visual disabilities or cognitive limitations, to the point where these users may be unable to use the content." Smell: `<select onChange={(e) => navigate(e.target.value)}>` with no "Go" button, a form that submits on the last radio's `onChange`, or auto-advancing focus between fields with no instruction. Source: https://www.w3.org/WAI/WCAG22/Understanding/on-input.html#intent
- **Make single-character shortcuts switchable off, remappable or focus-scoped**: "Ensure character-only shortcut keys can be turned off or modified." and "What matters is that a shortcut relies on a printable character (letters, punctuation, numbers, symbol characters), and not the number of physical keyboard keys that users need to press to trigger it." The exemption: "This success criterion doesn't affect components such as listboxes and drop-down menus. Although these components contain values (words) that may be selected by one or more character keys, the shortcuts are only active when the components have focus." Why: "Character-key shortcuts are easy to accidentally trigger, especially for keyboard and some speech input users." Smell: `document.addEventListener("keydown", (e) => e.key === "s" && focusSearch())` with no settings toggle and no modifier. Source: https://www.w3.org/WAI/WCAG22/Understanding/character-key-shortcuts.html#intent
- **Avoid `accesskey`**: "An `accesskey` value can conflict with a system or browser keyboard shortcut, or assistive technology functionality. What may work for one combination of operating system, assistive technology, and browser may not work with other combinations." and "Because of these issues, it is generally advised not to use `accesskey`s for most general-purpose websites and web apps." Why: "Certain `accesskey` values may not be present on certain keyboards, especially when internationalization is a concern." Smell: `accessKey="s"` on a search input or `accesskey` on navigation links. Lint: jsx-a11y/no-access-key. Source: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Global_attributes/accesskey#accessibility_concerns
- **Add shortcuts only on top of full keyboard navigation**: "Before assigning keyboard shortcuts, it is essential to ensure the features and functions to which shortcuts may be assigned are keyboard accessible without a keyboard shortcut." and "Do not use keyboard shortcuts as a substitute for access via navigation." Why: "If people who rely on the keyboard have to read documentation to learn which keys are required to use an interface, the interface may technically meet some accessibility standards but in practice is only accessible to the small subset of them who have the knowledge that such documentation exists". Smell: a command palette or `?` help overlay as the only route to a function whose button is `tabIndex={-1}` or missing. Source: https://www.w3.org/WAI/ARIA/apg/practices/keyboard-interface/#kbd_shortcuts_design_basic
- **Choose shortcut keys that do not collide with the OS, browser or assistive technology**: avoid "Any modifier keys + any of Tab, Enter, Space, or Escape." and "Meta key + any other single key" and "Alt + a function key." For assistive technology, steer clear of "Caps Lock + any other combination of keys. Insert + any combination of other keys. Scroll Lock + any combination of other keys. macOS only: Control + Option + any combination of other keys." Why: "Conflicts can block efficient access to functions that are essential to the user, and a perfect storm of conflicts can trap a user." Smell: a `keydown` handler for `e.metaKey && e.key === "k"`, `e.altKey && e.key === "F4"`, or `e.ctrlKey && e.key === "Tab"`. Source: https://www.w3.org/WAI/ARIA/apg/practices/keyboard-interface/#kbd_shortcuts_assignments_opsys_conflicts
