# Accessibility Structure and Media Rules (WCAG 2.2, WAI-ARIA APG, MDN)

Extracted 2026-11-08 from the w3c/wcag and w3c/aria-practices repositories, the mdn/content repository and the eslint-plugin-jsx-a11y rule docs.

## Headings

- **Mark up headings with heading elements, not styled text**: "People sometimes write headings, paragraphs, etc. using line breaks and adding HTML elements purely for styling"; with that markup "the screen reader hasn't got anything to use as signposts, so you can't retrieve a useful table of contents, and the whole page is seen as a single giant block". Why: "You can jump to the next/previous heading in many screen readers." and "You can also bring up a list of all headings in many screen readers, allowing you to use them as a handy table of contents to find specific content." Smell: `<span style="font-size: 3em">`, `<div className="card-title">` or `<p><strong>Results</strong></p>` doing the job of a heading. Source: https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/Accessibility/HTML#use_well-structured_text_content
- **Choose the heading level from the outline, never from the font size**: "Do not use heading elements to resize text. Instead, use the CSS `font-size` property." Why: "Heading information can be used by user agents to construct a table of contents for a document automatically." Smell: an `h4` directly under an `h2` because it looked the right size, or an `h1` inside a card because the design wanted large text; the fix is a class carrying `font-size`. Source: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/Heading_Elements#usage_notes
- **Do not skip heading levels on the way down**: "it is important to not skip one or more heading levels." Why: "Doing so may create confusion, as the person navigating this way may be left wondering where the missing heading is." Jumping back up when a subsection closes is fine: "When headings are nested, heading levels may be "skipped" when closing a subsection." Smell: `h1` followed by `h3`; a shared Card component that always renders `h4` wherever it is placed. Source: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/Heading_Elements#navigation
- **Use one `h1` per page**: "A page should generally have a single `<h1>` element that describes the content of the page (similar to the document's `<title>` element)." Why: nesting several `h1` elements inside sectioning elements "was never considered a best practice and is now non-conforming." Smell: an `h1` around the logo in the site header plus an `h1` in the article, or an `h1` inside every `<section>` relying on an outline algorithm that browsers never implemented. Source: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/Heading_Elements#avoid_using_multiple_h1_elements_on_one_page
- **Write headings that describe their section**: "When headings are clear and descriptive, users can find the information they seek more easily, and they can understand the relationships between different parts of the content more easily." Why: headings are read out of context in a heading list, and "Labels and headings do not need to be lengthy. A word, or even a single character, may suffice if it provides an appropriate cue to finding and navigating content." Smell: headings reading "Overview", "Details", "Section 1" or "Click here"; the same `h2` text ("Title") repeated on every card. Source: https://www.w3.org/WAI/WCAG22/Understanding/headings-and-labels.html#intent
- **Give headings exposed text content**: "Enforce that heading elements (`h1`, `h2`, etc.) have content and that the content is accessible to screen readers. Accessible means that it is not hidden using the `aria-hidden` prop." Why: an empty heading is announced with nothing to say and appears as a blank entry in the heading list. Smell: `<h2></h2>` filled by CSS `content`, `<h3><Icon aria-hidden="true" /></h3>`, a heading whose only content is a background image. Lint: jsx-a11y/heading-has-content. Source: https://github.com/jsx-eslint/eslint-plugin-jsx-a11y/blob/main/docs/rules/heading-has-content.md

## Landmarks

- **Put all content inside a landmark and keep the count low**: "Another best practice is to ensure that all content is contained within an appropriate landmark region." and "For optimum value, a general rule of thumb is that a page contains seven or fewer landmark regions." Why: "Since landmarks are intended to help assistive technology users perceive the high-level structure of a page, their value diminishes as their number grows." Smell: a cookie banner or `<div class="footer">` sitting outside `header`, `main` and `footer`; `role="region"` or `<section aria-label>` on every card in a grid. Source: https://www.w3.org/WAI/ARIA/apg/patterns/landmarks/#about
- **Prefer sectioning elements to landmark roles**: "Do not use an ARIA role or property if it is possible to use an HTML element that has equivalent semantics." Why: "When developing HTML, it is important to use native HTML elements where ever possible." The element carries the role without a chance of mistyping or forgetting it. Smell: `<div role="main">`, `<div role="navigation">`, `<div role="banner">`, `<div role="list">` with `role="listitem"` children where `ul` and `li` would do. Source: https://www.w3.org/WAI/ARIA/apg/practices/structural-roles/#when_to_use_structural_roles
- **Expose exactly one `main` landmark**: "Each page should have one `main` landmark." and "The `main` landmark should be a top-level landmark." Why: "A `main` landmark identifies the primary content of the page." and screen reader shortcuts and skip links need one unambiguous target; HTML allows extra `main` elements only when they carry the `hidden` attribute. Smell: a `<main>` plus a `<div role="main">`; a layout `<main>` wrapping a route component that renders its own `<main>`; several `<main>` elements hidden with CSS in a single-page app. Source: https://www.w3.org/WAI/ARIA/apg/practices/landmark-regions/#aria_lh_main
- **Label any landmark role that appears more than once, and keep the role out of the label**: "If a specific landmark role is used more than once on a page, provide each instance of that landmark with a unique label." Prefer the heading that opens the area: "If an area begins with a heading element (e.g. `h1-h6`) it can be used as the label for the area using the `aria-labelledby` attribute." Why: "Do not use the landmark role as part of the label. For example, a navigation landmark with a label "Site Navigation" will be announced by a screen reader as "Site Navigation Navigation". The label should simply be "Site"." Smell: two `<nav>` elements (site menu and breadcrumb) with no `aria-label` or `aria-labelledby`; `aria-label="Main navigation"`, `aria-label="Search form"` or `<section aria-label="Pricing section">`. Source: https://www.w3.org/WAI/ARIA/apg/practices/landmark-regions/#aria_lh_step3
- **Name every `region`**: "A `region` landmark must have a label." and "The HTML `section` element defines a `region` landmark when it has an accessible name (e.g. `aria-labelledby`, `aria-label` or `title`)." Why: "A `region` landmark is a perceivable section of the page containing content that is sufficiently important for users to be able to navigate to the section." Smell: `<div role="region">` with no name; a `<section>` meant to be navigable but left unnamed (it is then a plain generic container); `role="region" tabindex="0"` added to every scrollable `<pre>` only to make it focusable. Source: https://www.w3.org/WAI/ARIA/apg/practices/landmark-regions/#aria_lh_region
- **Keep `aside` out of other landmarks and related to the main content**: "`complementary` landmarks should be top level landmarks (e.g. not contained within any other landmarks)." and "If the complementary content is not related to the main content, a more general role should be assigned (e.g. `region`)." Why: "A `complementary` landmark is a supporting section of the document, designed to be complementary to the main content at a similar level in the DOM hierarchy, but remains meaningful when separated from the main content." Smell: `<aside>` nested inside `<main>` or `<article>`; `<aside>` wrapping an unrelated advert slot. Source: https://www.w3.org/WAI/ARIA/apg/practices/landmark-regions/#aria_lh_complementary
- **Use the `search` landmark for search and filter forms**: "Use the `search` landmark instead of the `form` landmark when the form is used for search functionality." and "Use the HTML `search` element to define a `search` landmark." Why: "A `search` landmark contains a collection of items and objects that, as a whole, combine to create search functionality." Smell: `<form class="search">` with no landmark at all; `<form role="search">` where a `<search>` wrapper would do; two search landmarks (site search and page filter) with no distinguishing labels. Source: https://www.w3.org/WAI/ARIA/apg/practices/landmark-regions/#aria_lh_search
- **Reserve `nav` for major navigation blocks**: "`<nav>` is intended only for a major block of navigation links; typically the `footer` element often has a list of links that don't need to be in a `<nav>` element." Why: "User agents, such as screen readers targeting disabled users, can use this element to determine whether to omit the initial rendering of navigation-only content." Smell: `<nav>` around a single Back link, around pagination, around social icons and around the footer link list, giving five navigation landmarks on one page. Source: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/nav#usage_notes
- **Only `header` and `footer` at body level are landmarks**: "The HTML `header` element is not considered a `banner` landmark when it is descendant of any of following elements (see HTML Accessibility Mappings): `article` `aside` `main` `nav` `section`". Why: "A `banner` landmark identifies site-oriented content at the beginning of each page within a website." and "Each page may have one `banner` landmark." Smell: the site header placed inside `<main>` or inside a wrapping `<section>` and expected to be announced as banner; `role="banner"` added to an article header. Source: https://www.w3.org/WAI/ARIA/apg/practices/landmark-regions/#aria_lh_banner
- **Keep repeated chrome out of `main`**: "The content of a `<main>` element should be unique to the document. Content that is repeated across a set of documents or document sections such as sidebars, navigation links, copyright information, site logos, and search forms shouldn't be included unless the search form is the main function of the page." Why: "Landmarks can be used by assistive technology to quickly identify and navigate to large sections of the document." Smell: `<main>` wrapping the `<nav>` and `<footer>` as a page container; the skip link target landing on the header. Source: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/main#usage_notes

## Lists and tables

- **Mark up lists as lists**: sighted users see that "list items are preceded by a bullet and perhaps indented"; "Having these structures and these relationships programmatically determined or available in text ensures that information important for comprehension will be perceivable to all." Why: "when technologies support programmatic relationships, it is strongly encouraged that information and relationships be programmatically determined rather than described in text." Smell: `<div>` rows prefixed with a typed bullet or hyphen, `<br>`-separated items, `<p>1. First step</p>`, a menu of links in bare `<a>` siblings. Source: https://www.w3.org/WAI/WCAG22/Understanding/info-and-relationships.html#intent
- **Pick `ol` when the order carries meaning**: "To determine which one to use, try changing the order of the list items; if the meaning is changed, the `ol` element should be used, otherwise you can use `<ul>`." Why: "Tables and ordered lists are meaningful sequences, but unordered lists are not." Smell: `<ul>` for step-by-step instructions or a ranking; `<ol>` for a tag cloud. Source: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/ul#usage_notes
- **Do not use `dl` or `ul` for indentation**: "Do not use this element (nor `ul` elements) to merely create indentation on a page. Although it works, this is a bad practice and obscures the meaning of description lists." Why: "To change the indentation of a description term, use the CSS `margin` property." Smell: `<dl><dd>` wrapping a quoted paragraph, a `<ul>` with a single `li` used to indent a note. Source: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/dl#notes
- **Use `th` for header cells**: "Table headers are defined using `th` elements"; with `td` everywhere "there is no way for a screen reader user to associate rows or columns together as groupings of data." Why: "This gives you complete groups of data that can be consumed by screen readers as single units." Smell: a first row of `<td><strong>Name</strong></td>`, a first column of bold `td` cells acting as row headers. Source: https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/Accessibility/HTML#accessible_data_tables
- **Caption every data table**: "By supplying a `caption` element whose value clearly and concisely describes the table's purpose, it helps the people decide if they need to check the rest of the table content or skip over it." Why: "This helps people navigating with the aid of assistive technology such as a screen reader, people experiencing low vision conditions, and people with cognitive concerns." Smell: a visual title in an `<h3>` or `<div>` above the table with no `<caption>`; a `<caption>` that is not the first child of `<table>`; a `<caption>` and a `<figcaption>` on a table that is the only content of a `<figure>`. Source: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/table#captions
- **Set `scope` on header cells**: "In simple contexts, using the `scope` attribute on header cells (`<th>` elements) is redundant because `scope` is inferred. However, certain assistive technologies may fail to infer correctly, so specifying header scope may improve user experiences." Why: a `th` in the first column is ambiguous between row and column header without it. Smell: `<th>` with no `scope`; `scope` on a `<td>` or `<div>`. Lint: jsx-a11y/scope. Source: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/th#usage_notes
- **Split complex tables or wire cells with `id` and `headers`**: "If the table cannot be broken apart, use a combination of the `id` and `headers` attributes to programmatically associate each table cell with the header(s) (`th` elements) the cell is associated with." Why: "screen readers may have difficulty parsing tables that are so complex that header cells can't be associated in a strictly horizontal or vertical way. This is typically indicated by the presence of the `colspan` and `rowspan` attributes." Smell: a two-row `<thead>` with `colspan` groups and data cells carrying no `headers`. Source: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/table#complicated_tables
- **Strip semantics from layout tables and never give them `th`**: role `presentation` is for "Suppressing table semantics of tables used for layout in circumstances where the table semantics do not convey meaningful relationships." Why: without it a screen reader announces a table with rows, columns and header relationships for a grid that only aligns a form. Smell: a layout `<table>` with `<th>` used for bold labels, or without `role="presentation"`; conversely `role="presentation"` on a real data table to quieten it. Source: https://www.w3.org/WAI/ARIA/apg/practices/hiding-semantics/#presentation_role_uses
- **Use a native `table` rather than `role="table"` and ARIA spans**: "authors are strongly encouraged to use a native HTML `table` element whenever possible." Why: "It is thus advisable to test implementations thoroughly with each browser and assistive technology combination that could be used by the target audience." and native `rowspan` and `colspan` already describe spans. Smell: `<div role="table">` built from flex rows for static data; `aria-colspan` or `aria-rowspan` on a `<td>`. Source: https://www.w3.org/WAI/ARIA/apg/patterns/table/#about
- **Set `aria-rowindex` on every row or on none**: "specifying an invalid value for `aria-rowindex` or setting it on some but not all rows in a table, could cause screen reader table reading functions to skip rows or simply stop functioning." Why: "When the number of rows represented by the DOM structure is not the total number of rows available for a table, grid, or treegrid, the `aria-rowcount` property is used to communicate the total number of rows available, and it is accompanied by the `aria-rowindex` property to identify the row indices of the rows that are present in the DOM." Smell: a virtualised table with `aria-rowcount` but no `aria-rowindex` on the header row, or indices restarting at 1 on every page. Source: https://www.w3.org/WAI/ARIA/apg/practices/grid-and-table-properties/#gridAndTableProperties_rows

## Reading order and markup

- **Write the DOM in reading order and position it with CSS afterwards**: "your content should make logical sense in its source order" and "you should get the source order right to start with, so what screen reader users get read out to them will make sense." Why: assistive technology and reader modes follow the DOM, not the rendered position. Smell: footer markup placed before `main` and pushed down with `order` or `grid-row`; a sidebar authored first because it sits on the left. Source: https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/Accessibility/HTML#structure_page_sections_logically
- **Do not let CSS placement contradict a meaningful sequence**: "It is important that it be possible to programmatically determine at least one sequence of the content that makes sense." The scope is narrow: "Providing a particular linear order is only required where it affects meaning." so swapping navigation and main content is fine, and in a multi-column document "the linear presentation of the content flows from the top of a column to the bottom of the column, then to the top of the next column." Why: "Content that does not meet this Success Criterion may confuse or disorient users when assistive technology reads the content in the wrong order, or when alternate style sheets or other formatting changes are applied." Smell: `order: -1` on a price shown before its label, `flex-direction: column-reverse` on a chat log or step list, `grid-area` placing step 3 before step 2, `grid-auto-flow: dense` reflowing numbered cards, alternating paragraphs between two columns. Source: https://www.w3.org/WAI/WCAG22/Understanding/meaningful-sequence.html#intent
- **Stop citing 4.1.1 Parsing and file markup faults under 1.3.1 or 4.1.2**: "This criterion has been removed from WCAG 2.2." Why: "Many issues that would have failed this criterion will fail Info and Relationships or Name, Role, Value." Smell: a duplicated `id` referenced by `aria-labelledby`, `headers` or `<label for>`; an `<li>` outside a list; a `<div>` inside a `<p>` or a `<button>` inside an `<a>`. Source: https://www.w3.org/WAI/WCAG22/Understanding/parsing.html#intent

## Navigation and consistency

- **Provide a way to bypass repeated blocks**: "Examples of repeated blocks of content include but are not limited to navigation links, header content, and advertising frames." Why: "Users who navigate sequentially through content will generally have to navigate through repeated content on each page." It is not needed where the browser already helps: "if a set of navigation links is provided at the bottom of a web page providing a "skip" link may be unnecessary." Smell: a header with thirty links and no skip link, no `main` landmark and no headings; fifty filter checkboxes before search results with nothing to jump past them. Source: https://www.w3.org/WAI/WCAG22/Understanding/bypass-blocks.html#intent
- **Make the skip link the first focusable element and point it at `main`**: "Adding an `id` attribute to the `<main>` element lets it be a target of a skip navigation link." Why: "This lets the user access the main content of the page faster." Smell: a skip link rendered after or inside the navigation; `href="#content"` with no matching `id`; the target `id` on a `<div>` that is removed on re-render. Source: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/main#skip_navigation
- **Keep the skip link usable by sighted keyboard users**: "People who use only the keyboard or a keyboard interface can reach content with fewer keystrokes." Why: "People who use screen magnifiers do not have to search through the same header content or other blocks of information to find where the main content begins each time they enter a new page." Both groups need to see the link when it receives focus. Smell: `.skip-link { position: absolute; left: -9999px; }` with no `:focus` rule bringing it on screen; `display: none` until hover; `visibility: hidden` so it cannot be focused at all. Source: https://www.w3.org/WAI/WCAG22/Understanding/bypass-blocks.html#benefits
- **Offer more than one way to reach a page**: "Even small sites should provide users some means of orientation. For a three or four page site, with all pages linked from the home page, it may be sufficient simply to provide links from and to the home page where the links on the home page can also serve as a site map." Why: "Users may find one technique easier or more comprehensible to use than another." Pages that are the result of a process, such as a search results or confirmation page, are exempt. Smell: content pages reachable only by paging through a sequence with Next; no site search, site map or navigation list. Source: https://www.w3.org/WAI/WCAG22/Understanding/multiple-ways.html#intent
- **Keep repeated navigation in the same order on every page**: "The intent of this success criterion is to encourage the use of consistent visual layout and source order for users who interact with repeated content within a set of web pages". Why: "Presenting repeated content in the same order is also important for visual users who use spatial memory or visual cues within the design to locate repeated content." Sub-navigation is allowed: the phrase same order "is not meant to imply that sub-navigation menus cannot be used". Smell: a per-page Header variant that reorders or drops items; the search box in the header on one template and in the footer on another. Source: https://www.w3.org/WAI/WCAG22/Understanding/consistent-navigation.html#intent
- **Identify the same function the same way everywhere**: "When components that perform the same functionality are identified differently, users may incorrectly assume that they perform different functions or spend additional time determining whether they are equivalent." Why: "Consistent identification allows users to apply knowledge gained from one page when interacting with another, reducing the effort required to locate and understand familiar functionality." Context-adapted labels such as "Page 4" becoming "Previous page" are allowed. Smell: the same icon button with `aria-label="Search"` on one page and `"Find"` on another; Save drawn as a floppy disk here and a tick there. Source: https://www.w3.org/WAI/WCAG22/Understanding/consistent-identification.html#intent
- **Put help in the same relative place on every page that has it**: "the mechanism must be located in the same relative order on each page within the set of pages." Why: "When the placement of the help mechanism is kept consistent across a set of pages, users looking for help will find it easier to identify." Omitting help on some pages is allowed: "the absence of a help mechanism on certain pages within a set does not constitute a violation." Smell: a Contact support link in the header on some templates and the footer on others; a chat widget mounted before the footer on one route and after it on another. Source: https://www.w3.org/WAI/WCAG22/Understanding/consistent-help.html#intent
- **Write instructions that name the control, not only its look or position**: "Some content relies on knowledge of the shape or position of objects that are not available from the structure of the content (for example, "round button" or "button to the right")." Why: "Some users with disabilities are not able to perceive shape or position due to the nature of the assistive technologies they use." Shape and position may still be mentioned "as long as the information is also provided in other ways." Smell: "Click the green button to continue", "use the menu on the right", "see the icons above", "fields marked in red" without the field names. Source: https://www.w3.org/WAI/WCAG22/Understanding/sensory-characteristics.html#intent

## Hiding content

- **Use `hidden` or `display: none` only for content that should vanish for everyone**: "The `hidden` attribute must not be used to hide content just from one presentation. If something is marked hidden, it is hidden from all presentations, including, for instance, screen readers." Why: "Hidden elements shouldn't be linked from visible elements unless using `hidden="until-found"`." and "If the content is not applicable or relevant, it shouldn't be linked." Smell: `hidden` or `display: none` on text meant only for screen readers (an sr-only label, a skip link, live region text); `href="#terms"` pointing at a `hidden` section. Source: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Global_attributes/hidden#usage_notes
- **Never set `display` on an element that carries `hidden`**: "changing the value of the CSS `display` property on a hidden element will override the hidden state. For instance, elements styled `display: block` will be displayed despite the `hidden` attribute's presence." Why: the element and its controls return to layout and to the tab order while the markup still claims it is hidden. Smell: `.panel { display: flex; }` on an element that is also toggled with `hidden`; a reset stylesheet with `[hidden] { display: block }`; the fix is `[hidden] { display: none !important }` or toggling a class instead. Source: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Global_attributes/hidden#the_hidden_state
- **Make inactive screens truly invisible**: "Content hiding techniques such as zero opacity, z-index order and off-screen placement must not be used exclusively to handle visibility." and "Use the `hidden` attribute or `visibility` or `display` style properties." Why: "Everything other than the currently visible screen must be _truly_ invisible (especially relevant for single page apps with multiple _cards_)". Smell: inactive carousel slides or an off-canvas menu hidden with `opacity: 0`, `transform: translateX(-100%)` or `height: 0; overflow: hidden` alone, leaving their links and buttons in the tab order; no `inert` or `visibility: hidden`. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/Guides/Mobile_accessibility_checklist#visibility
- **Use `aria-hidden="true"` only to drop content that is redundant for assistive technology**: "You should not be hiding visible content unless doing so improves the experience for users of assistive technologies by removing redundant or extraneous content." It changes nothing visually: "The presence of the `aria-hidden` attribute hides content from assistive technology but doesn't visually hide anything." and it is unnecessary when the `hidden` attribute, `display: none` or `visibility: hidden` already applies. Why: "Not all users of assistive technology are visually impaired. If visible content doesn't match text content in the accessibility API, the user experience will be negatively impacted for sighted users." Smell: `aria-hidden="true"` on a visible paragraph or table; `<div hidden aria-hidden="true">`; `aria-hidden` on a wrapper that contains a focusable control. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-hidden#description
- **Do not expect `role="presentation"` to work on focusable or labelled elements**: "Browsers ignore `role="presentation"`, and it therefore has no effect, if either of the following are true about the element to which it is applied: The element is focusable, e.g. it is natively focusable like an HTML link or input, or it has a `tabindex` attribute. The element has any global ARIA states and properties, e.g., `aria-label`." Why: the role removes semantics, not content, so it is never a hiding tool. Smell: `<img role="presentation" aria-label="Logo">`, `<a role="presentation">`, `<div role="presentation" tabindex="0">`, `role="none"` on a wrapper in the hope of silencing its text. Source: https://www.w3.org/WAI/ARIA/apg/practices/hiding-semantics/#presentation_role_ignored
- **Do not nest headings or other semantics inside `button`, `tab` or `img` roles**: "WAI-ARIA requires browsers to automatically apply role `presentation` to all descendant elements of any element with a role that cannot support semantic children." Why: "from the perspective of anyone using a technology that relies on an accessibility API, such as a screen reader, the heading does not exist." Smell: `<button><h3>Plan name</h3></button>`, `<li role="tab"><h2>`, `<div role="img"><h3>`, an accordion whose heading sits inside the trigger instead of wrapping it. Source: https://www.w3.org/WAI/ARIA/apg/practices/hiding-semantics/#children_presentational

## Images and icons

- **Give every `img` an `alt` attribute**: "The `alt` attribute holds a textual replacement for the image, which is mandatory and **incredibly useful** for accessibility"; "screen readers read the attribute value out to their users so they know what the image means." Why: "Alt text is also displayed on the page if the image can't be loaded for some reason: for example, network errors, content blocking, or link rot." Smell: `<img src={src} />`, `<img {...props} />` with no explicit `alt`, a wrapper component where `alt` is an optional prop. Lint: jsx-a11y/alt-text. Source: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/img#usage_notes
- **Describe what the image conveys, not that it is an image**: "An `alt` attribute's value should provide a clear and concise text replacement for the image's content. It should not describe the presence of the image itself or the file name of the image." Why: "the _Don't_ example could be read by a screen reader as "On my travels, I saw a cute little animal: image", which doesn't make sense." Smell: `alt="image"`, `alt="photo"`, `alt="hero-banner.jpg"`, `alt="Picture of the team"`. Lint: jsx-a11y/img-redundant-alt. Source: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/img#authoring_meaningful_alternate_descriptions
- **Write alt for the context and do not repeat nearby text**: "The alt should be brief and concise and include all the information conveyed in the image that is not duplicated in the surrounding text." Why: "The content of the `alt` attribute for a single image differs based on the context." and "Any personal knowledge or extra description shouldn't be included here, as it is not useful for people who have not seen the image before." Smell: `alt` identical to the `figcaption` or to the heading beside it; an avatar whose `alt` repeats the visible user name next to it; a product image `alt` padded with marketing copy. Source: https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/Accessibility/HTML#text_alternatives
- **Give decorative images an empty `alt` or move them to CSS**: "Putting alternative text on such items just distracts people using screen readers from the content on the page. Not marking the content in any way, though, leaves users guessing what the non-text content is and what information they may have missed". Why: "This type of non-text content, therefore, is marked or implemented in a way that assistive technologies (AT) will ignore it and not present anything to the user." Smell: `alt="decorative swirl"`, `alt="spacer"`, `alt="background"`, a divider image with `alt="line"`; conversely an informative image delivered as `background-image` with no text equivalent. Source: https://www.w3.org/WAI/WCAG22/Understanding/non-text-content.html#intent
- **Use an empty `alt` for an icon inside a control that already has text**: "For images that are being used as icons for a button or control, the `alt` prop should be set to an empty string (`alt=""`)." Why: "adding a label to an icon can produce a confusing or duplicated label on a control that already has appropriate text content." Smell: `<button><img src="save.svg" alt="save icon" /> Save</button>`; `<a href="/"><img alt="Home" /> Home</a>` announced as "Home Home". Source: https://github.com/jsx-eslint/eslint-plugin-jsx-a11y/blob/main/docs/rules/alt-text.md
- **Describe the action for functional images**: "For images used to trigger an action, for example, images nested inside an `a` or `button` element, consider describing the triggered action inside the `alt` attribute value. For example, you could write `alt="next page"` instead of `alt="arrow right"`." Why: the alt becomes the accessible name of the link or button, so it must say where it goes or what it does. Smell: `<a href="/"><img src="logo.svg" alt="logo" /></a>` instead of the site name; `<button><img alt="magnifying glass" /></button>`; an image-only link with `alt=""` and therefore no name. Source: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/img#authoring_meaningful_alternate_descriptions
- **Pair complex images with a long description and the data**: "The longer description identifies the type of chart, provides a high-level summary of the data, trends and implications comparable to those available from the chart. Where possible and practical, the actual data is provided in a table." Why: a short `alt` such as "Figure one - Sales in June, July and August" identifies the chart but cannot carry its content. Smell: `<img alt="Revenue chart">` with nothing else; a `<canvas>` chart with no text summary or table; an infographic with a one-line `alt`. Source: https://www.w3.org/WAI/WCAG22/Understanding/non-text-content.html#examples
- **Use real text instead of images of text**: "If authors can use text to achieve the same visual effect, they should present the information as text rather than using an image." Exceptions are "instances where a particular presentation of text is essential to the information being conveyed, such as type samples, logotypes, branding, etc." Why: people need "the text in a particular font size, foreground and background color, font family, line spacing or alignment." Smell: a PNG heading or promo banner with baked-in copy, `<img alt="50% off this weekend">`, screenshots of code or quotations used in place of the text. Source: https://www.w3.org/WAI/WCAG22/Understanding/images-of-text.html#intent
- **Caption with `figure` and `figcaption`, not `title`**: "The `title` attribute is not an acceptable substitute for the `alt` attribute. Additionally, avoid duplicating the `alt` attribute's value in a `title` attribute declared on the same image." and "If an image needs a caption, use the `figure` and `figcaption` elements." Why: "you should not assume that the user will ever see it: the user may only have keyboard or touchscreen." Smell: `<img title="...">` with no `alt`; `title` equal to `alt`; `<div class="figure"><img /><p class="caption">`. Source: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/img#the_title_attribute
- **Make an informative inline SVG a single labelled image**: "it is a good idea to set `role="img"` on the outer `svg` element and give it a label. This will cause screen readers to just consider it as a single entity and describe it using the label, rather than trying to read out all the child nodes". Why: "most screen readers will consider the element with `role="img"` set on it to be like a black box, and not access the individual elements inside it." Smell: an informative inline `<svg>` with neither `role="img"` plus `aria-label` or `aria-labelledby` nor `aria-hidden="true"`; a `<title>` child relied on alone. Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/img_role#svg_and_roleimg
- **Hide decorative SVG icons and icon fonts with `aria-hidden="true"`**: "Adding `aria-hidden="true"` to an element removes that element and all of its children from the accessibility tree. This can improve the experience for assistive technology users by hiding: Purely decorative content, such as icons or images". Why: otherwise the icon is announced as an unnamed graphic or its `<title>` duplicates the visible label. Smell: `<svg class="icon">` beside visible button text without `aria-hidden="true"`; `<i class="fa fa-trash"></i>` with no `aria-hidden` and no visible text (then it needs a name on the control instead). Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-hidden#description
- **Give meaningful emoji a role and a name**: "someone using a screen reader might get confused because the emojis might have either no text representation at all, or the alternative text might be confusing and not match the context it is being used in." Wrap them in `role="img"` with an `aria-label` that says what they mean. Why: "This seems to work OK across some browser/screen reader combinations, but some of them end up reading the label out twice. Use with caution and test thoroughly." Smell: `<span>✅</span>` as the only status indicator, emoji used as bullets or icons, `<i role="img">` instead of a `span`. Lint: jsx-a11y/accessible-emoji (deprecated in the plugin, still useful as a search). Source: https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/img_role#using_roleimg_to_confer_meaning_that_is_obscured_or_implied

## Audio, video and embedded content

- **Caption prerecorded video that has audio**: "Captions not only include dialogue, but identify who is speaking and include non-speech information conveyed through sound, including meaningful sound effects." Exception: "Captions are not needed when the synchronized media is, itself, an alternate presentation of information that is also presented via text on the web page." Why: "The intent of this success criterion is to enable people who are deaf or hard of hearing to watch synchronized media presentations." Smell: `<video>` with no `<track kind="captions">` and no captions in the player; auto-generated captions never reviewed; a captions file that transcribes speech only. Lint: jsx-a11y/media-has-caption. Source: https://www.w3.org/WAI/WCAG22/Understanding/captions-prerecorded.html#intent
- **Describe visual-only information in video**: "During existing pauses in dialogue, audio description provides information about actions, characters, scene changes, and on-screen text that are important and are not described or spoken in the main sound track." A full text alternative is the other route and "reads something like a screenplay or book." Why: "if all of the important information in the video track is already conveyed in the audio track, no additional audio description is necessary." so the check is whether the soundtrack alone tells the story. Smell: a product demo whose steps happen silently on screen with no `<track kind="descriptions">`, described version or full transcript. Source: https://www.w3.org/WAI/WCAG22/Understanding/audio-description-or-media-alternative-prerecorded.html#intent
- **Publish a transcript with audio-only and video-only media**: "Alternatives for time-based media that are text based make information accessible because text can be rendered through any sensory modality (for example, visual, auditory or tactile) to match the needs of the user." Why: "The purpose of the transcript is to provide an equivalent to what is presented visually." and ship it with the media rather than promising it later. Smell: a podcast `<audio>` with no transcript link beside it; a silent looping demo video or animated GIF with nothing but `alt="demo"`. Source: https://www.w3.org/WAI/WCAG22/Understanding/audio-only-and-video-only-prerecorded.html#intent
- **Render audio captions through a `video` element**: "The `<audio>` element doesn't directly support WebVTT. You will have to find a library or framework that provides the capability for you, or write the code to display captions yourself. One option is to play your audio using a `video` element, which does support WebVTT." Why: "Captions, which are specified using WebVTT, allow people who are hearing impaired to understand an audio recording's content as the recording is being played, while transcripts allow people who need additional time to be able to review the recording's content at a pace and format that is comfortable for them." Smell: `<audio><track kind="captions" /></audio>` with nothing rendering the cues (it satisfies the linter, not the listener). Source: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/audio#accessibility
- **Use the right `kind` on text tracks**: captions "provide transcription or translation of the dialog, sound effects, relevant musical cues, and other relevant audio information, such as the cue's source (e.g., character, environment). They are suitable for when sound is unavailable or not clearly audible"; subtitles "are suitable for when the sound is available but not understood". Why: "If omitted the default kind is `subtitles`." Smell: `<track src="captions.vtt">` with no `kind`; `kind="captions"` without `srclang` or `label`; two tracks sharing `kind`, `srclang` and `label`. Source: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/track#attributes
- **Do not autoplay sound, and give an independent pause and volume control if you must**: "we discourage the practice of automatically starting sounds (especially if they last more than 3 seconds), and encourage that the sound be started by an action initiated by the user after they reach the page". Why: "Individuals who use screen reading software can find it hard to hear the speech output if there is other audio playing at the same time." and "Muting the system volume is not "pausing or stopping" the autoplay audio." Smell: `<video autoplay>` without `muted`; `<audio autoplay>`; `autoplay="false"` (the attribute's presence is what counts); `media.play()` on mount; a background video whose only control is the device volume. Source: https://www.w3.org/WAI/WCAG22/Understanding/audio-control.html#intent
- **Title every `iframe`**: "People navigating with assistive technology such as a screen reader can use the `title` attribute on an `<iframe>` to label its content. The title's value should concisely describe the embedded content". Why: "Without this title, they have to navigate into the `<iframe>` to determine what its embedded content is. This context shift can be confusing and time-consuming, especially for pages with multiple `<iframe>`s and/or if embeds contain interactive content like video or audio." Smell: `<iframe src="https://www.youtube.com/embed/...">` with no `title`; `title="iframe"`; two embeds sharing one title. Lint: jsx-a11y/iframe-has-title. Source: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe#accessibility

## Moving content

- **Let users pause, stop or hide anything that moves for more than five seconds beside other content**: ""Moving, blinking and scrolling" refers to content in which the visible content conveys a sense of motion. Common examples include motion pictures, synchronized media presentations, animations, real-time games, and scrolling stock tickers." Why: "Content that moves or auto-updates can be a barrier to anyone who has trouble reading stationary text quickly as well as anyone who has trouble tracking moving objects. It can also cause problems for screen readers." A loader that is the only thing on screen is exempt, and one control for everything is preferred: "consider providing a single mechanism to pause, stop, hide, or (in the case of auto-updating content) control the update frequency that affects all these elements at the same time." Smell: an auto-advancing carousel with no pause button; `animation: spin 2s linear infinite` on a decoration beside content; `<marquee>`; a looping hero video with no control; a looping animation started by an IntersectionObserver when it scrolls into view. Lint: jsx-a11y/no-distracting-elements. Source: https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide.html#intent
- **Do not count hover or focus pausing as a pause mechanism**: "Having an animation stop only so long as a user has focus on it (where it restarts as soon as the user moves the focus away) would not be considered a "mechanism for the user to pause" because it makes the page unusable in the process and would not meet this SC." Why: "it must provide the user with a means to pause that does not tie up the user or the focus so that the page cannot be used." Smell: a carousel that pauses only on `:hover` or `:focus-within`; `pauseOnHover` as the only option offered. Source: https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide.html#intent
- **Give auto-updating content a pause or a frequency control, with no five-second grace**: "there is no five second exception for auto-updating since it makes little sense to auto-update for a few seconds and then stop" and "authors have the option of providing the user with a means to control the frequency of updates when content is auto-updating". Why: "Pausing and jumping to current display (when pause is released) is better for information that is real-time or "status" in nature." Smell: a `setInterval` news or price ticker, a live feed re-rendering every few seconds, with no pause or interval setting. Source: https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide.html#intent
