# TypeScript code-review rules: type safety

Extracted 2026-11-10 from the TypeScript handbook, reference, release notes and TSConfig reference (microsoft/TypeScript-Website, CC BY 4.0) and the TypeScript 7.0 announcement. Current stable at extraction: TypeScript 7.0.2. One rule per bullet, one source link each. Quotations are short excerpts; the rest is original.

## any and unknown

- **Type values of unknown shape as `unknown`, not `any`**: "no operations are permitted on an `unknown` without first asserting or narrowing to a more specific type" - `any` switches checking off for everything it touches and spreads through every assignment, while `unknown` forces a narrowing step before use. Why: an `any` lets a wrong property name, a missing null check or a bad call reach production without a single compiler error. Smell: `(data: any)`, `JSON.parse(text) as any`, `let result: any`, or a `Record<string, any>` for a shape that could be declared. Source: https://www.typescriptlang.org/docs/handbook/release-notes/typescript-3-0.html#new-unknown-top-type
- **Narrow `catch` variables from `unknown` instead of annotating them `any`** (4.4+): "This flag changes the default type of `catch` clause variables from `any` to `unknown`." - `useUnknownInCatchVariables` is part of `strict`; anything can be thrown, so test with `instanceof Error` or a shape check before reading `.message`. Why: a thrown string, `undefined` or a custom object has no `.message`, and the handler itself throws. Smell: `catch (err: any)`, `catch (e) { log(e.message) }` with strict off, or `(err as Error).message` with no `instanceof` check. Source: https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-4.html#defaulting-to-the-unknown-type-in-catch-variables---useunknownincatchvariables
- **Do not type a parameter or property as `Function`**: "values of type `Function` can always be called; these calls return `any`" - write the signature, such as `(input: string) => void`, or `() => void` for a callback that is stored but never called by this code. Why: a `Function` call is an untyped call, so argument count, argument types and the result are all unchecked. Smell: `callback: Function`, `handlers: Record<string, Function>`, or `fn: Function` in a props or options type. Source: https://www.typescriptlang.org/docs/handbook/2/functions.html#function

## Strict flags

- **Turn `strict` on and keep every member of the strict family on**: "When possible, a new codebase should always turn these strictness checks on." - `strict` switches on `noImplicitAny`, `strictNullChecks`, `strictFunctionTypes`, `strictPropertyInitialization` and `useUnknownInCatchVariables` together; opting one out should name the migration that needs it. Why: without `noImplicitAny` untyped parameters become `any`, and without `strictNullChecks` every `find`, `get` and optional property is assumed to hold a value. Smell: `"strict": false`, `"strictNullChecks": false` or `"noImplicitAny": false` in `tsconfig.json`, or a parameter like `function fn(s)` that compiles. Source: https://www.typescriptlang.org/docs/handbook/2/basic-types.html#strictness
- **Enable `noUncheckedIndexedAccess` and handle the `undefined` it adds** (4.1+): "every property access (like `foo.bar`) or indexed access (like `foo["bar"]`) is considered potentially undefined" - the flag is not part of `strict`; an index signature or array index then yields `T | undefined`, so check it or iterate with `for...of` instead of indexing. Why: a `string[]` lookup at a bad index and a `Record<string, T>` lookup for a missing key both return `undefined` at runtime, and without the flag the type says otherwise. Smell: `items[0].id`, `env["API_URL"].trim()`, `lookup[key].push(x)`, or `strs[i].toUpperCase()` in a counted loop. Source: https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-1.html#checked-indexed-accesses---nouncheckedindexedaccess

## Assertions and suppressions

- **Treat `as T` as an unchecked claim, and `as unknown as T` as a louder one**: "There won't be an exception or `null` generated if the type assertion is wrong." - an assertion is erased at compile time and only allowed between overlapping types; the double assertion through `unknown` or `any` exists to force a conversion the compiler rejected, so each one needs a reason the reviewer can verify. Why: the compiler now believes the claim and every later line is checked against a type the value may not have. Smell: `JSON.parse(body) as User`, `res.data as Order[]`, `event.target as HTMLInputElement` with no element check, or `value as unknown as Config`. Source: https://www.typescriptlang.org/docs/handbook/2/everyday-types.html#type-assertions
- **Replace `!` with a check or a type that admits the absence**: "Writing `!` after any expression is effectively a type assertion that the value isn't `null` or `undefined`" - the same applies to the definite assignment form `name!: string` on a class field, which silences `strictPropertyInitialization` without initialising anything. Why: when the claim is wrong the failure is a `TypeError` far from the line that made the claim. Smell: `map.get(id)!.name`, `document.querySelector("#root")!`, `users.find(u => u.id === id)!`, or `private client!: Client` with no constructor assignment. Source: https://www.typescriptlang.org/docs/handbook/2/everyday-types.html#non-null-assertion-operator-postfix-
- **Suppress with `// @ts-expect-error` and a reason, never `// @ts-ignore`**: "The difference is that `// @ts-ignore` will do nothing if the following line is error-free." - `@ts-expect-error` itself errors once the line is fixed, so the suppression cannot outlive the problem; `@ts-ignore` stays silent for ever, including over new errors on that line. Why: a stale suppression hides whatever error appears next on that line, which is how a refactor breaks a call without the compiler saying so. Smell: a bare `// @ts-ignore`, or `// @ts-expect-error` with no explanation of what is expected to fail. Source: https://www.typescriptlang.org/docs/handbook/release-notes/typescript-3-9.html#ts-ignore-or-ts-expect-error
- **Check a literal against a type with `satisfies`, not a cast or a wide annotation** (4.9+): "The new `satisfies` operator lets us validate that the type of an expression matches some type, without changing the resulting type of that expression." - the literal keeps its precise inferred type, so property access stays narrow, while typos and missing or extra keys are still errors. Why: `as Config` hides missing properties, and `const x: Record<K, A | B>` widens every property so the use sites need narrowing again. Smell: `const routes = { ... } as Routes`, `const palette: Record<Colour, string | RGB> = { ... }` followed by `palette.green.toUpperCase()` failing, or an `as const` plus a cast to get both. Source: https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-9.html#the-satisfies-operator

## Nullability

- **Use `?.` only where the type says the left side can be nullish**: "when `foo` is `null` or `undefined`, stop what we're doing and just return `undefined`" - the operator checks only the value on its left and turns an absent value into `undefined` that flows onwards, so on a value the type says is always present it adds nothing, and on one that must be present it hides a violated invariant. Why: a null that should have been an error becomes a silent `undefined` and surfaces later as a wrong total, an empty page or a skipped write. Smell: `user?.id` where `user: User`, `order?.items?.length ?? 0` inside a function whose contract requires an order, or `?.` added to make a red squiggle go away. Source: https://www.typescriptlang.org/docs/handbook/release-notes/typescript-3-7.html#optional-chaining

## Functions and narrowing

- **Declare callback types with function syntax so parameters are checked contravariantly**: "This is unsound because a caller might end up being given a function that takes a more specialized type, but invokes the function with a less specialized type." - under `strictFunctionTypes` a parameter written as a function-typed property or parameter is checked properly, but one written in method syntax keeps the bivariant check, so `onEvent: (e: Event) => void` catches a mismatch that `onEvent(e: Event): void` lets through. Why: a handler that accepts only `MouseEvent` gets called with a `KeyboardEvent` and reads a property that is not there. Smell: `interface Props { onChange(value: string | number): void }` for a callback type, or a `(e: SpecificEvent) => void` passed where `(e: Event) => void` is expected without an error. Source: https://www.typescriptlang.org/docs/handbook/type-compatibility.html#function-parameter-bivariance
- **Make a type predicate test every property it claims**: "A predicate takes the form `parameterName is Type`, where `parameterName` must be the name of a parameter from the current function signature." - the compiler trusts the predicate's return value completely, so a body that returns `true`, checks only `typeof x === "object"`, or checks one of five required fields narrows to a type the value does not have. Why: every caller then reads the unchecked properties without a guard, and the type guard is the one place the mistake could have been caught. Smell: `function isUser(x: unknown): x is User { return typeof x === "object" && x !== null }`, `x is Order` with `return true`, or a predicate that checks `"id" in x` and nothing else. Source: https://www.typescriptlang.org/docs/handbook/2/narrowing.html#using-type-predicates

## Objects and the runtime boundary

- **Spread only plain data, never class instances**: "Basically, that means you lose methods when you spread instances of an object" - spread copies own enumerable properties, so prototype methods are gone at runtime while the spread type still looks like the data part of the class. Why: the copy is passed where the original type is expected and the first method call throws. Smell: `const copy = { ...instance }` or `Object.assign({}, entity)` on a class instance, or `{ ...date }` and `{ ...map }` producing an empty object. Source: https://www.typescriptlang.org/docs/handbook/variable-declarations.html#spread
- **Validate data at every runtime boundary, because types check no runtime value**: "Type annotations never change the runtime behavior of your program." - types are erased before the code runs, and structural typing means an object with extra or wrong fields is accepted wherever its declared type is; a value from `fetch`, `JSON.parse`, a database row, `process.env` or a form is whatever arrived, and the annotation on it is a promise the compiler cannot keep. Why: a renamed field in another service, a null column or a missing environment variable passes the type check and fails somewhere downstream. Smell: `const user: User = await res.json()`, `JSON.parse(raw) as Settings`, `process.env.PORT as string`, or `rows as Account[]` with no parse or guard between the boundary and the typed use. Source: https://www.typescriptlang.org/docs/handbook/2/basic-types.html#erased-types
