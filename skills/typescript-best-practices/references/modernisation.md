# TypeScript code-review rules: modernisation

Extracted 2026-11-10 from the TypeScript handbook, reference, release notes and TSConfig reference (microsoft/TypeScript-Website, CC BY 4.0) and the TypeScript 7.0 announcement. Current stable at extraction: TypeScript 7.0.2. One rule per bullet, one source link each. Quotations are short excerpts; the rest is original.

## Literals and inference

- **Use `satisfies` instead of an annotation that widens or a cast that narrows back** (4.9+): "The new `satisfies` operator lets us validate that the type of an expression matches some type, without changing the resulting type of that expression." - the annotation checks the shape but throws away the literal and per-property types; `satisfies` checks the same shape and keeps them. Why: a widened annotation forces casts or guards at every use, and a cast hides the typo the annotation was meant to catch. Smell: `const palette: Record<Colors, string | RGB> = { ... }` followed by `(palette.green as string).toUpperCase()`, or an object literal with no check at all because the annotation got in the way. Source: https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-9.html#the-satisfies-operator
- **Use `as const` instead of hand-written literal types and `readonly` tuples** (3.4): "This feature means that types that would otherwise be used just to hint immutability to the compiler can often be omitted." - one suffix stops widening, makes properties `readonly` and turns array literals into `readonly` tuples. Why: a literal type spelled out by hand drifts from the value next to it, and the compiler already knows the value. Smell: `{ method: "GET" as "GET" }`, `const pair: readonly [number, number] = [10, 20]`, or a `type Colour = "red" | "blue"` maintained in parallel with an object that lists the same strings. Source: https://www.typescriptlang.org/docs/handbook/release-notes/typescript-3-4.html#const-assertions
- **Put `const` on the type parameter instead of `as const` at every call site** (5.0+): "you can now add a `const` modifier to a type parameter declaration to cause `const`-like inference to be the default" - the modifier only affects literals written inside the call, and the constraint must be `readonly` or inference falls back to the mutable constraint. Why: an `as const` that callers must remember is forgotten, and the function then sees `string[]` where it wanted a tuple. Smell: `getNames({ names: ["Alice", "Bob"] } as const)` repeated at each call of `function getNames<T extends HasNames>(arg: T)`, or `<const T extends string[]>` where the array is still inferred as `string[]`. Source: https://www.typescriptlang.org/docs/handbook/release-notes/typescript-5-0.html#const-type-parameters
- **Type a structured string with a template literal type instead of `string`** (4.1+): "When you use it with concrete literal types, it produces a new string literal type by concatenating the contents." - unions in substitution positions expand to every combination, and `infer` can pull the pieces back out of a caller's string. Why: `string` accepts `"frstNameChanged"` and `"top-middel"` as readily as the real names, so the typo surfaces at runtime. Smell: `on(eventName: string, callback: () => void)` where every caller passes `` `${key}Changed` ``, or `align: string` with a comment listing the nine allowed `"top-left"` style values. Source: https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-1.html#template-literal-types
- **Prefer a union or an `as const` object to an `enum` when the project wants erasable syntax** (`erasableSyntaxOnly` 5.8+): "In modern TypeScript, you may not need an enum when an object with `as const` could suffice" - `enum` emits runtime code, so type stripping and `erasableSyntaxOnly` reject it; enums remain fully supported otherwise and keeping them is a project choice, not a defect. Why: a new `enum` in a codebase that runs TypeScript files directly fails at run time rather than in the editor. Smell: `enum Direction { Up, Down }` added to a project with `"erasableSyntaxOnly": true`, or a mixed codebase where the same concept is an `enum` in one file and a string union in the next. Source: https://www.typescriptlang.org/docs/handbook/enums.html#objects-vs-enums

## Expressions and utility types

- **Use `?.` for nullish chains and `??` for defaults instead of `&&` chains and `||`** (3.7): "`??` avoids some unintended behavior from `0`, `NaN` and `""` being treated as falsy values." - `?.` stops at the first `null` or `undefined` on its left and returns `undefined`; both operators treat `0`, `""` and `false` as present. Why: `||` replaces a saved `0` with the default and `&&` chains silently swallow falsy data the code meant to keep. Smell: `const volume = saved.volume || 0.5`, `if (foo && foo.bar && foo.bar.baz)`, `if (log) log(msg)` instead of `log?.(msg)`, or `arr && arr[0]`. Source: https://www.typescriptlang.org/docs/handbook/release-notes/typescript-3-7.html#nullish-coalescing
- **Use `Awaited<T>` instead of a hand-rolled promise unwrapping type** (4.5+): "This type is meant to model operations like `await` in `async` functions, or the `.then()` method on `Promise`s - specifically, the way that they recursively unwrap `Promise`s." - it handles nested promises, `PromiseLike` and unions, which a one-level conditional type does not. Why: a home-made `Unwrap` returns `Promise<number>` for a double-wrapped value and disagrees with what `await` actually produces. Smell: `type Unwrap<T> = T extends Promise<infer U> ? U : T`, or `ReturnType<typeof load> extends Promise<infer R> ? R : never` to name an async result. Source: https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-5.html#the-awaited-type-and-promise-improvements
- **Use `NoInfer<T>` instead of a second type parameter that only blocks inference** (5.4+): "Surrounding a type in `NoInfer<...>` gives a signal to TypeScript not to dig in and match against the inner types to find candidates for type inference." - the parameter wrapped in `NoInfer` is checked against the inferred `T` instead of widening it. Why: without it `createStreetLight(["red", "green"], "blue")` infers `C` as the union of all three and the bad default passes. Smell: `function f<C extends string, D extends C>(colors: C[], defaultColor?: D)` where `D` appears nowhere else in the signature. Source: https://www.typescriptlang.org/docs/handbook/release-notes/typescript-5-4.html#the-noinfer-utility-type
- **Drop hand-written type predicates that the compiler now infers** (5.5+): "It now infers signatures with type predicates like `x is number` or `x is NonNullable<T>`." - inference needs a single `return` of a boolean refinement with no explicit return type; a truthiness check on a number or string does not qualify, and an explicit `is` is never checked against the body. Why: an explicit predicate is as unchecked as an `as` cast, so the inferred one is the safer of the two. Smell: `.filter((bird): bird is Bird => bird !== undefined)`, `function isDefined<T>(x: T | undefined): x is T { return x !== undefined }`, or `.filter(score => !!score)` on `(number | undefined)[]` that then needs a cast. Source: https://www.typescriptlang.org/docs/handbook/release-notes/typescript-5-5.html#inferred-type-predicates

## Modules

- **Mark type-only imports and exports with `type` and turn on `verbatimModuleSyntax`** (3.8, inline `type` 4.5+, option 5.0+): "The rules are much simpler - any imports or exports without a `type` modifier are left around." - with the option on, what you write is what is emitted, and a type imported as a value becomes a compile error instead of a surprise elision; it replaces `importsNotUsedAsValues` and `preserveValueImports`. Why: import elision decides per compiler whether a side-effect import survives, and single-file transpilers cannot tell a type from a value. Smell: `import { Car } from "./car"` where `Car` is an interface, `export { Car } from "./car"` for a type alias, or `"importsNotUsedAsValues": "error"` still in tsconfig. Source: https://www.typescriptlang.org/tsconfig/#verbatimModuleSyntax
- **Organise new code with ES modules, not namespaces** (`module Foo {}` spelling deprecated in 6.0, removed in 7.0): "for Node.js applications, modules are the default and we recommended modules over namespaces in modern code" - a module file is already a grouping with a name chosen by the importer, so a namespace inside it is a second layer with nothing to separate. Why: namespaces are global objects that hide dependencies and are not erasable syntax. Smell: `export namespace Shapes { export class Triangle {} }` in a file consumers reach with `shapes.Shapes.Triangle`, or `module Foo { export const bar = 10 }` where `namespace` or a plain module was meant. Source: https://www.typescriptlang.org/docs/handbook/namespaces-and-modules.html#using-modules

## Classes and resources

- **Mark overriding members with `override` and enable `noImplicitOverride`** (4.3+): "When this option is turned on, it becomes an error to override any method from a superclass unless you explicitly use an `override` keyword." - the keyword also fails when the base member is renamed away, so the subclass cannot keep a dead `show()` around. Why: without it a rename in the base class leaves orphaned methods and a new helper can silently replace a base method. Smell: `class Derived extends Base { show() {} }` with no `override`, or a tsconfig with `strict` but no `noImplicitOverride`. Source: https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-3.html#override-and-the---noimplicitoverride-flag
- **Use `using` and `await using` instead of `try`/`finally` for disposable resources** (5.2+): "The key difference is that variables declared with `using` get their `Symbol.dispose` method called at the end of the scope!" - disposal runs on early `return` and on `throw`, in last-in-first-out order, and a failure in both body and disposal surfaces as `SuppressedError`; `await using` calls `Symbol.asyncDispose`. Why: duplicated clean-up before every return is the version that gets forgotten. Smell: `const file = new TempFile(path); try { ... } finally { file[Symbol.dispose]() }`, or `close()` calls repeated before each `return` of a function that opens a handle. Source: https://www.typescriptlang.org/docs/handbook/release-notes/typescript-5-2.html#using-declarations-and-explicit-resource-management
- **Write new decorators against the standard proposal, not `experimentalDecorators`** (5.0+): "however, without the flag, decorators will now be valid syntax for all new code." - standard decorators take `(value, context)` and may sit after `export`; they do not support `emitDecoratorMetadata` or parameter decorators, so a framework that needs those keeps the flag deliberately. Why: the two systems type-check and emit differently, and a decorator written for one rarely works under the other. Smell: `"experimentalDecorators": true` added to a fresh tsconfig, or a new decorator typed `(target: any, key: string, descriptor: PropertyDescriptor)` with no framework requiring it. Source: https://www.typescriptlang.org/docs/handbook/release-notes/typescript-5-0.html#differences-with-experimental-legacy-decorators
