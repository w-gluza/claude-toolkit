# TypeScript code-review rules: type modelling

Extracted 2026-11-10 from the TypeScript handbook, reference, release notes and TSConfig reference (microsoft/TypeScript-Website, CC BY 4.0) and the TypeScript 7.0 announcement. Current stable at extraction: TypeScript 7.0.2. One rule per bullet, one source link each. Quotations are short excerpts; the rest is original.

## State and value sets

- **Model each state as its own union member with a literal discriminant**: "The problem with this encoding of `Shape` is that the type-checker doesn't have any way to know whether or not `radius` or `sideLength` are present based on the `kind` property." - give every state a required `kind` literal and only the properties that state actually has, then narrow on `kind` with `if` or `switch`. Why: one object with optional flags lets contradictory combinations type-check and forces `!` assertions that break when code moves. Smell: `interface Shape { kind: "circle" | "square"; radius?: number; sideLength?: number }` or `{ loading: boolean; error?: Error; data?: User }`, and `shape.radius!` inside a `kind` check. Source: https://www.typescriptlang.org/docs/handbook/2/narrowing.html#discriminated-unions
- **Use a union of literals for a known set of values, not `string` or `number`**: "This is pretty nice because string literal types can basically spell-check our string values." - a parameter or property that only ever takes a handful of values should list them. Why: the compiler rejects misspelt and unknown values at the call site instead of letting them reach a runtime branch nobody handles. Smell: `alignment: string` checked against `"left"`, `"right"` and `"center"` inside the body, or `status: number` compared to magic numbers. Source: https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-1.html#template-literal-types
- **Use `as const` when an object or array must keep its literal types**: "The `as const` suffix acts like `const` but for the type system, ensuring that all properties are assigned the literal type instead of a more general version like `string` or `number`." - without it a property initialised with `"GET"` widens to `string` because it could be reassigned. Why: widened literals fail against literal-union parameters and push people towards per-call assertions. Smell: `const req = { url, method: "GET" }` passed to `method: "GET" | "POST"`, patched with `req.method as "GET"` or `"GET" as "GET"`. Source: https://www.typescriptlang.org/docs/handbook/2/everyday-types.html#literal-inference
- **Compose string shapes with template literal types instead of a hand-written union or `string` (4.1+)**: "When a union is used in the interpolated position, the type is the set of every possible string literal that could be represented by each union member" - write `` `${Vertical}-${Horizontal}` `` or `` `${string & keyof T}Changed` `` and let the compiler expand it; the handbook recommends ahead-of-time generation only for very large unions. Why: the parts stay single-sourced and a new member of one part updates every combination. Smell: `position: string` where only nine `"top-left"` style values are valid, or a union of twelve strings typed out by hand that share two prefixes and three suffixes. Source: https://www.typescriptlang.org/docs/handbook/2/template-literal-types.html

## Structural typing

- **Do not rely on a type alias or a same-shaped class to keep two values apart**: "When you use the alias, it's exactly as if you had written the aliased type." - `type UserId = string` and `type OrderId = string` are the same type, and two classes or interfaces with the same members are assignable to each other; the only nominal-style distinction the Type Compatibility reference describes is a private or protected class member, which must originate from the same class on both sides. Why: a reviewer who reads the alias as a guarantee will miss an id passed into the wrong parameter. Smell: `function cancel(orderId: OrderId)` called with a `UserId`, or `class Metres { value: number }` and `class Seconds { value: number }` used interchangeably without complaint. Source: https://www.typescriptlang.org/docs/handbook/2/everyday-types.html#type-aliases
- **Treat an excess property error as a bug, not an obstacle**: "but a majority of excess property errors are actually bugs." - the check only runs on a fresh object literal assigned or passed directly; if the extra key is legitimate, widen the type with an index signature or add the property, and if it is a typo, fix the literal. Why: assigning the literal to an intermediate variable or casting it skips the check and the misspelt key silently does nothing at runtime. Smell: `createSquare({ width: 100, opacity: 0.5 } as SquareConfig)` or `const opts = { colour: "red", width: 100 }; createSquare(opts)` introduced to make an error go away. Source: https://www.typescriptlang.org/docs/handbook/2/objects.html#excess-property-checks

## Readonly

- **Mark properties `readonly` to signal intent, and remember it is shallow and not enforced across assignment**: "TypeScript doesn't factor in whether properties on two types are `readonly` when checking whether those types are compatible, so `readonly` properties can also change via aliasing." - `readonly` stops reassignment of that property only; nested objects stay mutable and a mutable alias of the same object can still change the value. Why: code that treats a `readonly` field as proof of immutability will be surprised by mutation through another reference. Smell: `readonly resident: { name: string; age: number }` relied on as deep immutability while `home.resident.age++` compiles, or a comment claiming a `ReadonlyPerson` cannot change. Source: https://www.typescriptlang.org/docs/handbook/2/objects.html#readonly-properties
- **Type arrays and tuples that are never mutated as `readonly T[]` and `readonly [A, B]` (syntax from 3.4)**: "Tuples tend to be created and left un-modified in most code, so annotating types as `readonly` tuples when possible is a good default." - the same applies to array parameters that only read; assignability is one-way, so a mutable array fits a `readonly` parameter but a `readonly` array (including anything from `as const`) does not fit a mutable one. Why: a mutable parameter type both permits accidental `push` inside the function and rejects callers holding `as const` data. Smell: `function render(items: string[])` that only iterates, or `distanceFromOrigin([x, y]: [number, number])` failing on `[3, 4] as const`. Source: https://www.typescriptlang.org/docs/handbook/2/objects.html#readonly-tuple-types

## Optional properties

- **Distinguish a missing property from one set to `undefined`, and turn on `exactOptionalPropertyTypes` to enforce it (4.4+)**: "`colorThemeOverride: undefined` is not the same as `colorThemeOverride` not being defined." - with the flag, `prop?: T` means present with a `T` or absent; write `prop?: T | undefined` only when an explicit `undefined` is a real third state. The flag is not part of `strict` and needs `strictNullChecks`. Why: `in` checks, `Object.keys`, spreads and `for`-`in` behave differently for an own `undefined` property than for a missing one. Smell: `{ name, age: undefined }` assigned to `age?: number`, or `age?: number | undefined` added everywhere just to keep such assignments compiling. Source: https://www.typescriptlang.org/tsconfig/#exactOptionalPropertyTypes

## Tuples

- **Prefer an object with named properties over a tuple when positions are not self-evident**: "it may be worth reconsidering whether using objects with descriptive property names may be better for your API." - tuples suit convention-based pairs such as `[key, value]`; three or more positional values of mixed meaning belong in an object. Why: callers must remember what index 2 means, and swapping two same-typed positions compiles. Smell: `function parse(): [string, number, boolean, string]` or `const [a, b, c, d] = result` with no obvious ordering. Source: https://www.typescriptlang.org/docs/handbook/2/objects.html#tuple-types
- **Type concat, compose and partial-application helpers with variadic tuples instead of overload ladders (4.0+)**: "The first change is that spreads in tuple type syntax can now be generic." - `[...T, ...U]` with `T extends readonly unknown[]` covers every length and keeps element order; rest elements may also sit anywhere in a tuple, not only at the end. Why: a fixed set of overloads is wrong for the first length nobody wrote and has to be maintained forever. Smell: seven `concat` overloads for `[A]`, `[A, B]`, `[A, B, C]`, or a `(...args: any[]) => any` fallback at the bottom of the ladder. Source: https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-0.html#variadic-tuple-types

## Declarations

- **Pick `interface` for object shapes by default and `type` when you need unions, tuples or mapped types**: "If you would like a heuristic, use `interface` until you need to use features from `type`." - the handbook's stated distinction is that an interface can be reopened and extended (declaration merging) while a type alias cannot, so a second `interface` with the same name in scope silently merges rather than erroring. Why: a reviewer should see a merge as deliberate augmentation of an external type, not as two unrelated declarations that happened to collide. Smell: `type Shape = { ... }` and `interface Shape` mixed for the same kind of thing in one module, or two `interface Config` blocks in the same file that nobody meant to merge. Source: https://www.typescriptlang.org/docs/handbook/2/everyday-types.html#differences-between-type-aliases-and-interfaces
- **Prefer an `as const` object plus a derived union over `enum` (`erasableSyntaxOnly` 5.8+ rejects enums)**: "In modern TypeScript, you may not need an enum when an object with `as const` could suffice:" - `const Direction = { Up: 0, Down: 1 } as const; type Direction = typeof Direction[keyof typeof Direction]` gives the same names and values with plain JavaScript output; `enum` declarations are among the constructs `erasableSyntaxOnly` reports because they have runtime semantics. Why: enums emit runtime objects, numeric enums accept any number, and `const enum` has publishing pitfalls the reference documents. Smell: `enum Direction { Up, Down }` in new code, `const enum` in a published declaration file, or a mixed string and numeric enum. Source: https://www.typescriptlang.org/docs/handbook/enums.html#objects-vs-enums
- **Derive types from the runtime source of truth with `typeof`, `keyof` and indexed access instead of restating them**: "We can combine this with `typeof` to conveniently capture the element type of an array literal:" - `typeof ROLES[number]`, `keyof typeof config` and `Person["age"]` keep a type bound to the value or parent type it describes. Why: a hand-copied union or property type drifts from the value the moment someone edits one side. Smell: `const ROLES = ["admin", "editor"] as const; type Role = "admin" | "editor"`, or `type Age = number` next to `interface Person { age: number }` instead of `Person["age"]`. Source: https://www.typescriptlang.org/docs/handbook/2/indexed-access-types.html
