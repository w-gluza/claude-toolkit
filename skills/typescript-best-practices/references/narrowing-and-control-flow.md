# TypeScript code-review rules: narrowing and control flow

Extracted 2026-11-10 from the TypeScript handbook, reference, release notes and TSConfig reference (microsoft/TypeScript-Website, CC BY 4.0) and the TypeScript 7.0 announcement. Current stable at extraction: TypeScript 7.0.2. One rule per bullet, one source link each. Quotations are short excerpts; the rest is original.

## Built-in guards

- **Do not treat `typeof x === "object"` as proof of an object or array**: "in JavaScript, `typeof null` is actually `"object"`!" - the object branch keeps `null` in the union, so pair the check with `x !== null` or test `Array.isArray(x)` first. Why: iterating or dereferencing the narrowed value still throws at runtime when it is `null`. Smell: `if (typeof strs === "object") { for (const s of strs)` where `strs` is `string[] | null`, or `(strs as string[])` right after the check. Source: https://www.typescriptlang.org/docs/handbook/2/narrowing.html#typeof-type-guards
- **Compare against `null` or `undefined` instead of a bare truthiness check when `0` or `""` is valid input**: "truthiness checking on primitives can often be error prone." - `x != null` removes both `null` and `undefined` in one step and narrows just as well as the strict forms. Why: a truthy guard silently drops the empty string and zero together with the missing value. Smell: `if (name)` or `if (!count) return` where the type is `string | null` or `number | undefined` and the falsy primitive is a legitimate value. Source: https://www.typescriptlang.org/docs/handbook/2/narrowing.html#truthiness-narrowing
- **Remember that an `in` check keeps optional members on both sides**: "optional properties will exist in both sides for narrowing." - `"swim" in animal` narrows to the members where `swim` is required or optional, and the false branch keeps the members where it is optional or absent. Why: the true branch still has to handle `undefined` when any union member declares `swim?`, so a call there is not safe by itself. Smell: `if ("swim" in animal) { animal.swim() }` over a union containing `{ swim?: () => void }`, patched with `animal.swim!()`. Source: https://www.typescriptlang.org/docs/handbook/2/narrowing.html#the-in-operator-narrowing

## Discriminated unions and exhaustiveness

- **Model variants as a union of object types that share a literal discriminant**: "only the union encoding of `Shape` will cause an error regardless of how `strictNullChecks` is configured." - one interface with a `kind` field and optional data fields cannot be narrowed by `kind`, so every access needs a non-null assertion. Why: with the union, a check on `kind` makes the variant's own fields required in that branch and the compiler catches a missing field without help. Smell: `interface Shape { kind: "circle" | "square"; radius?: number; sideLength?: number }` followed by `shape.radius!` inside `if (shape.kind === "circle")`. Source: https://www.typescriptlang.org/docs/handbook/2/narrowing.html#discriminated-unions
- **End a `switch` over a discriminant with a `default` that assigns the value to `never`**: "you can use narrowing and rely on `never` turning up to do exhaustive checking in a `switch` statement." - when a new member joins the union the assignment stops compiling at the switch rather than at a caller. Why: without it a new variant falls through and the function quietly returns `undefined`. Smell: `switch (shape.kind) { case "circle": ... case "square": ... }` with no `default`, or `default: throw new Error("unknown shape")` that never types `shape` as `never`. Source: https://www.typescriptlang.org/docs/handbook/2/narrowing.html#exhaustiveness-checking
- **Hold a hoisted guard or a destructured discriminant in a `const`, never a `let`** (4.4+, destructuring 4.6+): "If that type guard operates on a `const`, a `readonly` property, or an un-modified parameter, then TypeScript is able to narrow that value appropriately." - `const isCircle = shape.kind === "circle"` and `const { kind, payload } = action` both narrow the original object, and the analysis follows chains of constants, but a `let` binding or a reassigned parameter discards the guard. Why: the compiler only trusts a stored condition when nothing between the test and the use can change it. Smell: `let isValid = typeof input === "string"` followed by `(input as string)`, or a destructured `kind` whose sibling `payload` is cast in the branch. Source: https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-4.html#control-flow-analysis-of-aliased-conditions-and-discriminants
- **Rely on narrowing inside `switch (true)` cases instead of re-checking or casting** (5.3+): "TypeScript 5.3 now can perform narrowing based on conditions in each `case` clause within a `switch (true)`." - each `case` expression acts as a guard for its clause, and a clause reached by fallthrough sees the union of every case that led to it. Why: a cast inside a case hides the fact that the guard already did the work, and a fallthrough that assumes the previous case's type is wrong for the other path. Smell: `case typeof x === "string": return (x as string).trim()`, or a missing `break` between `case typeof x === "string":` and `case Array.isArray(x):` where the second clause calls a string method. Source: https://www.typescriptlang.org/docs/handbook/release-notes/typescript-5-3.html#switch-true-narrowing

## Control flow analysis

- **Let an early `return` or `throw` narrow the rest of the function instead of asserting**: "TypeScript uses this flow analysis to narrow types as it encounters type guards and assignments." - after `if (typeof padding === "number") return ...` the compiler already knows `padding` is `string` for the remainder, so a cast there repeats the work and will not fail when the type changes. Why: an assertion that sits below a guard is the clearest sign that narrowing was available and ignored. Smell: `if (typeof padding === "number") { return ... } return (padding as string) + input`, or `value!` on the line after `if (value == null) throw`. Source: https://www.typescriptlang.org/docs/handbook/2/narrowing.html#control-flow-analysis
- **Narrow `obj[key]` only through a literal, `unique symbol` or never-reassigned key** (4.7+, constant `obj` and `key` 5.5+): "TypeScript 4.7 now narrows the types of element accesses when the indexed keys are literal types and unique symbols." - since 5.5 the key may be any variable as long as neither `obj` nor `key` is ever mutated; otherwise copy the element into a local `const` and narrow that. Why: with a key that can change, the guard and the use may address different elements, so the compiler keeps the wide type and reviewers see a cast appear. Smell: `let key = ...` then `if (typeof obj[key] === "string") obj[key].toUpperCase()`, or `(obj[key] as string)` after a `typeof` check on the same expression. Source: https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-7.html#control-flow-analysis-for-bracketed-element-access

## Type predicates and assertion functions

- **Make the body of an explicit `x is T` predicate actually prove `T`**: "Explicit type predicates ("is") are no safer than a type assertion ("as")." - the compiler never checks that the returned boolean matches the declared predicate, so the function is a cast that every caller inherits. Why: a predicate that only checks `typeof x === "object"` tells all callers the value is a `User` and the real failure surfaces far from the guard. Smell: `function isUser(x: unknown): x is User { return typeof x === "object" && x !== null }` with no check of the fields `User` requires. Source: https://www.typescriptlang.org/docs/handbook/release-notes/typescript-5-5.html#inferred-type-predicates
- **Filter with an explicit comparison such as `x !== undefined`, not `!!x` or `Boolean`, so the predicate is inferred** (5.5+): "TypeScript did not infer a type predicate for `score => !!score`, and rightly so" - a predicate is inferred only when the function has no return annotation, a single `return` of a boolean refinement and no mutation of its parameter, and a truthiness test on a primitive is not a refinement because `false` can still mean `0` or `""`. Why: the element type keeps `undefined`, and the usual fix of `as number[]` hides a real bug where zero is dropped from the data. Smell: `.filter(Boolean) as string[]`, `.filter(x => !!x)` on `(number | undefined)[]`, or a hand-written `(x): x is number => !!x`. Source: https://www.typescriptlang.org/docs/handbook/release-notes/typescript-5-5.html#inferred-type-predicates
- **Give a throw-on-failure helper an `asserts` signature, and a `never` return type when it always throws**: "`asserts condition` says that whatever gets passed into the `condition` parameter must be true if the `assert` returns" - `asserts val is T` narrows one argument for the rest of the scope, and a function declared `: never` ends the control flow path so the code after it is narrowed and no `return` is needed. Why: a `void` helper tells the compiler nothing about what it checked, so callers reach for `!` and `as` after the call. Smell: `function invariant(cond: unknown, msg: string): void`, `assert(typeof x === "string"); (x as string).trim()`, or `return fail("...")` written only to satisfy the return type. Source: https://www.typescriptlang.org/docs/handbook/release-notes/typescript-3-7.html#assertion-functions

## Overloads and compiler errors

- **Prefer a union parameter to overloads that share arity and return type**: "Always prefer parameters with union types instead of overloads when possible" - a call resolves to exactly one overload, so a `string | any[]` argument matches neither `len(s: string)` nor `len(arr: any[])`. Why: the union accepts the combined input and removes the need for a separate implementation signature. Smell: `function len(s: string): number; function len(arr: any[]): number;`, or a caller forced to branch `typeof v === "string" ? len(v) : len(v)`. Source: https://www.typescriptlang.org/docs/handbook/2/functions.html#writing-good-overloads
- **Read an error's sub-messages down to the last line and fix that, rather than silencing the first**: "You can think of each sub-message as answering a "why?" question about the message above it." - a `number[]` versus `string[]` mismatch arrives as a chain whose final line names the element type that is actually wrong. Why: an assertion or ignore comment removes the message, not the mismatch, and it returns at runtime or in the next refactor. Smell: `// @ts-ignore` or `as unknown as T` added in the same diff as the type change that produced the error. Source: https://www.typescriptlang.org/docs/handbook/2/understanding-errors.html#error-elaborations
