# TypeScript code-review rules: compiler configuration, modules and declaration files

Extracted 2026-11-10 from the TypeScript handbook, reference, release notes and TSConfig reference (microsoft/TypeScript-Website, CC BY 4.0) and the TypeScript 7.0 announcement. Current stable at extraction: TypeScript 7.0.2. One rule per bullet, one source link each. Quotations are short excerpts; the rest is original.

## Strict checking

- **Keep `strict` on and fix what it reveals instead of loosening the config** (default true since 6.0): "The `strict` flag enables a wide range of type checking behavior that results in stronger guarantees of program correctness." - `strict` is the whole strict family at once; a TypeScript upgrade can add checks under it, and the right response to new errors is to fix the code or disable the one named check with a reason, not to switch the family off. The same goes for `skipLibCheck`, which buys compile time at the cost of accuracy; two copies of a dependency's types are fixed by deduplicating the tree, not by skipping the check. Why: every option turned off to make a build green hides a class of defects for the whole project from then on. Smell: a diff that sets `"strict": false`, `"strictNullChecks": false` or adds `"skipLibCheck": true` alongside a dependency bump. Source: https://www.typescriptlang.org/tsconfig/#strict
- **Enable `noFallthroughCasesInSwitch` and end every non-empty `case` explicitly**: "Ensures that any non-empty case inside a switch statement includes either `break`, `return`, or `throw`." - an empty `case` that shares a body with the next one is still allowed; only a `case` with statements and no terminator is reported. Why: a missing `break` runs the next branch's code silently and reads like an intentional fallthrough. Smell: `case 0: console.log("even"); case 1: console.log("odd"); break;`. Source: https://www.typescriptlang.org/tsconfig/#noFallthroughCasesInSwitch
- **Enable `noImplicitOverride` and write `override` on every member that replaces a base member** (4.3+): "Using `noImplicitOverride` you can ensure that the sub-classes never go out of sync, by ensuring that functions which override include the keyword `override`." - with `override` the compiler errors when the base member is renamed or removed, and with the flag it also errors when a subclass accidentally shadows a base member it did not mean to. Why: a renamed base method leaves a dead override behind, and a new helper can silently replace base behaviour. Smell: `class SharedAlbum extends Album { download() {} }` where `Album` declares `download`, with no `override` keyword. Source: https://www.typescriptlang.org/tsconfig/#noImplicitOverride
- **Keep `noUncheckedSideEffectImports` on and declare wildcard modules for asset imports** (5.6+, default true since 6.0): "When `--noUncheckedSideEffectImports` is enabled, TypeScript will error if it can't find a source file for a side effect import." - without the flag an unresolved `import "x";` is ignored, so a typo in a polyfill or registration import ships silently; bundler-handled assets get an ambient declaration such as `declare module "*.css" {}` in a global `.d.ts`. Why: a side effect import that resolves to nothing does nothing, and the only signal is the missing behaviour at runtime. Smell: `"noUncheckedSideEffectImports": false` added to silence `import "./button.css"`, or `import "polyfil/fetch"` passing with the flag off. Source: https://www.typescriptlang.org/tsconfig/#noUncheckedSideEffectImports
- **Enable `noPropertyAccessFromIndexSignature` and use bracket access for keys that only an index signature declares**: "The goal of this flag is to signal intent in your calling syntax about how certain you are this property exists." - declared properties keep dot access; keys that exist only through `[key: string]: T` must be written `obj["key"]`, which shows the reader the property may be absent. Why: dot access on an index signature looks like a known field and hides the lookup that can come back undefined. Smell: `settings.username` where `GameSettings` declares `speed`, `quality` and `[key: string]: string` but no `username`. Source: https://www.typescriptlang.org/tsconfig/#noPropertyAccessFromIndexSignature

## Modules and imports

- **Mark type-only imports and exports with `type` so single-file transpilers can erase them** (3.8+, inline `type` 4.5+): "`import type` only imports declarations to be used for type annotations and declarations." - `import type { T }`, `export type { T }` and inline `import { f, type T }` are always erased from the output; a bare `export { SomeType }` re-export or an ambient `const enum` reference is an error under `isolatedModules`, which should be on whenever a tool other than `tsc` transpiles files one at a time, because that tool cannot know whether a name is a type or a value. Why: a transpiler that keeps a type-only re-export emits an export of a name that does not exist at runtime. Smell: `export { Props } from "./Props"` where `Props` is an interface, or `import { Car } from "./car"` used only in annotations in a project with `isolatedModules` off. Source: https://www.typescriptlang.org/docs/handbook/release-notes/typescript-3-8.html#type-only-imports-and-export
- **Turn on `verbatimModuleSyntax` so imports are emitted exactly as written** (5.0+): "The rules are much simpler - any imports or exports without a `type` modifier are left around." - everything marked `type` is dropped and everything else stays, so the file shows what the output does; it replaces the deprecated `importsNotUsedAsValues` and `preserveValueImports`, and it errors on ESM `import` syntax in a file that will be emitted as CommonJS, which exposes a forgotten `"type": "module"` under `nodenext`; such files use `import x = require("x")` instead. It suits Node.js projects that are mostly ESM with a few CJS files and is not recommended for a CJS project that plans to move to ESM later. Why: import elision decided across files is invisible in the source and differs between tools. Smell: `"importsNotUsedAsValues"` or `"preserveValueImports"` in tsconfig, or an unmarked `import { Car } from "./car"` for an interface. Source: https://www.typescriptlang.org/tsconfig/#verbatimModuleSyntax
- **Set `module` for the host: `nodenext` for Node.js, `preserve` or `esnext` with `moduleResolution: bundler` for bundled code** (bundler 5.0+, preserve 5.4+): "`node16`, `node18`, and `nodenext` are the only correct `module` options for all apps and libraries that are intended to run in Node.js v12 or later, whether they use ES modules or not." - `module` drives format detection, interop rules and module resolution even under `noEmit`, so `esnext` or `commonjs` for code that runs in Node.js type-checks against the wrong rules; `bundler` resolution never requires extensions, so a library that ships `tsc` output should compile with `node18` or `nodenext` or it can emit `export * from "./utils"` that bundlers accept and Node.js rejects. Why: the compiler can only catch imports that will crash at runtime when it knows which runtime. Smell: `"module": "esnext"` in a server project with no bundler, `"moduleResolution": "node"`, or a published library built with `"moduleResolution": "bundler"`. Source: https://www.typescriptlang.org/docs/handbook/modules/reference.html#node16-node18-node20-nodenext
- **Write relative import specifiers the host will resolve: output extensions under `nodenext`, `.ts` only with `allowImportingTsExtensions` or `rewriteRelativeImportExtensions`** (5.7+): "In Node.js, module specifiers in import statements and dynamic `import()` calls are not allowed to omit file extensions or `/index.js` suffixes, while module specifiers in `require` calls are." - specifiers are emitted as written, so an ESM file under `nodenext` imports `./math.js` even though the source is `math.ts`; `allowImportingTsExtensions` is only permitted with `noEmit` or `emitDeclarationOnly` because the runtime or bundler must handle `.ts` itself, and `rewriteRelativeImportExtensions` rewrites `./x.ts` to `./x.js` in output but never touches bare specifiers, `paths` aliases or package `imports` entries. Why: an extensionless or `.ts` import that type-checks still fails with `ERR_MODULE_NOT_FOUND` when Node.js loads the output. Smell: `import { add } from "./math"` in an `.mts` file, or `import "./foo.ts"` in a project that emits JavaScript without `rewriteRelativeImportExtensions`. Source: https://www.typescriptlang.org/docs/handbook/modules/theory.html#module-resolution-is-host-defined

## Declaration files and publishing

- **Use `number`, `string`, `boolean`, `symbol`, `object` and `unknown`, never the boxed types or `any`**: "These types refer to non-primitive boxed objects that are almost never used appropriately in JavaScript code." - `Number`, `String`, `Boolean`, `Symbol` and `Object` describe wrapper objects, not the primitives callers pass; `object` is the non-primitive type and `unknown` is the type for a value passed through without inspection, whereas `any` disables checking for everything it touches and belongs only in a migration from JavaScript. Why: a signature in a `.d.ts` file is copied into every consumer, so a boxed type or `any` there spreads to all of them. Smell: `function reverse(s: String): String;`, `options: Object`, or `data: any` in a public signature. Source: https://www.typescriptlang.org/docs/handbook/declaration-files/do-s-and-don-ts.html#number-string-boolean-symbol-and-object
- **Type callbacks with a `void` return and required parameters, and do not add overloads that differ only in callback arity**: "It's always legal for a callback to disregard a parameter, so there's no need for the shorter overload." - a callback whose result is ignored returns `void`, not `any`, so nothing can use the result by accident; an optional callback parameter means the caller may omit the argument, which is rarely what the author meant, since a callback accepting fewer parameters is always assignable. Why: a shorter overload listed first lets wrongly typed functions match it, and `any` returns hide misuse of the result. Smell: `done: (data: unknown, elapsedTime?: number) => void`, `fn(x: () => any)`, or two `beforeAll` overloads where only the callback's parameter count differs. Source: https://www.typescriptlang.org/docs/handbook/declaration-files/do-s-and-don-ts.html#overloads-and-callbacks
- **Order overloads from specific to general and collapse variants into optional parameters or unions**: "sort overloads by putting the more general signatures after more specific signatures" - the first matching overload wins, so a general signature listed first hides the ones after it; overloads that differ only in trailing parameters become one signature with optional parameters when the return type is shared, and overloads that differ in one argument's type become a union, which also lets callers pass a `string | number` straight through. Why: an unreachable overload is dead API, and separate overloads reject pass-through calls that a union accepts. Smell: `declare function fn(x: unknown): unknown;` above `fn(x: HTMLElement): number;`, or `utcOffset(b: number): Moment; utcOffset(b: string): Moment;`. Source: https://www.typescriptlang.org/docs/handbook/declaration-files/do-s-and-don-ts.html#ordering
- **Ship generated declarations with the package and point `types` at them, annotating exports explicitly where `isolatedDeclarations` is on** (isolatedDeclarations 5.5+): "Set the `types` property to point to your bundled declaration file." - `declaration` generates the `.d.ts` files and `declarationMap` makes go-to-definition land in the `.ts` source, which matters with project references; packages whose declarations expose another package's types list it in `dependencies`, not `devDependencies`; `isolatedDeclarations` requires `declaration` or `composite` and errors on exports whose type cannot be read without the checker, so exported functions get return annotations, which is worth it only where a separate tool emits declarations or parallel builds need it. Why: a package without declarations is `any` to its consumers, and a missing dependency breaks their build. Smell: `"main": "./lib/main.js"` with no `"types"`, `@types/x` in `devDependencies` while the public API references it, or `export function foo() { return x; }` under `isolatedDeclarations`. Source: https://www.typescriptlang.org/docs/handbook/declaration-files/publishing.html#including-declarations-in-your-npm-package

## TypeScript 6.0 deprecations and 7.0 removals

- **Set `types`, `rootDir`, `target` and `lib` explicitly rather than inheriting the 6.0 defaults** (6.0+): "Several compiler options now have updated default values that better reflect modern development practices." - `types` now defaults to `[]`, so global packages such as `node` or `jest` must be listed and `["*"]` restores the old enumeration at a build-time cost; `rootDir` defaults to the tsconfig directory, so a project with sources in `src` sets `"rootDir": "./src"` or its output lands in `dist/src`; `target` defaults to the current year's ECMAScript version, a floating value that like `esnext` changes meaning between TypeScript releases, so a library pins a concrete year; `lib` drops `dom` when the code does not run in a browser, and in 6.0 `dom` already includes `dom.iterable` and `dom.asynciterable`. Why: a floating default makes the next compiler upgrade change output and globals without a diff in the repo. Smell: `Cannot find name 'process'` fixed with `"types": ["*"]`, output appearing at `dist/src/index.js`, or `"target": "esnext"` in a published library. Source: https://www.typescriptlang.org/docs/handbook/release-notes/typescript-6-0.html#simple-default-changes
- **Replace every option 6.0 deprecated instead of hiding it with `ignoreDeprecations`** (deprecated in 6.0, removed in 7.0): "those options will be removed entirely in TypeScript 7.0 (the native TypeScript port)." - `target: es5` and `downlevelIteration` go to an external compiler for ES5 output; `moduleResolution: node`, `node10` and `classic` become `nodenext` or `bundler`, and `bundler` may now pair with `module: commonjs`; `module: amd`, `umd`, `system` and `none` become `esnext` or `preserve`; `baseUrl` is removed by prefixing each `paths` entry with the directory; `esModuleInterop` and `allowSyntheticDefaultImports` can no longer be `false`, so CommonJS modules are default-imported; `alwaysStrict` can no longer be `false`, so reserved words such as `await` or `static` used as identifiers get renamed; `outFile` is replaced by a bundler; `module Foo {}` becomes `namespace Foo {}`, `asserts` on imports becomes `with`, and `no-default-lib` directives become `noLib` or `libReplacement`. Why: `ignoreDeprecations: "6.0"` keeps the build green on 6.0 and guarantees it fails on 7.0. Smell: `"ignoreDeprecations": "6.0"` in tsconfig, `"baseUrl": "./src"` beside `paths`, or `import * as express from "express"` followed by `express()`. Source: https://www.typescriptlang.org/docs/handbook/release-notes/typescript-6-0.html#preparing-for-typescript-70
- **Prove the build on 6.0 with `--stableTypeOrdering` and no `ignoreDeprecations` before adopting 7.0** (7.0+): the native compiler is built to check exactly what 6.0 checks under those two conditions; it adopts every 6.0 default, turns every 6.0 deprecation into a hard error, and always sorts types deterministically, so union order in emitted declarations can differ from 6.0 and an inference that only worked because of declaration order needs an explicit type argument or annotation. It parallelises checking across a default of four `--checkers`, and varying that count can in rare cases change order-dependent results, so CI and local builds should pin the same number; `--builders` parallelises project references and `--singleThreaded` disables all of it. Running `tsc file.ts` in a directory with a tsconfig is an error unless `--ignoreConfig` is passed; 7.0 ships no programmatic API until 7.1, so tools that import `typescript` keep running 6.0 through the `@typescript/typescript6` package alongside 7.0's `tsc`; JavaScript files are analysed like TypeScript, so JSDoc `@enum`, `@class`, a bare `?` type, postfix `!` and Closure-style function types stop being recognised. Why: differences found after the switch are hard to tell apart from real regressions. Smell: `"ignoreDeprecations": "6.0"` still present, a CI step running `tsc src/index.ts` next to `tsconfig.json`, or a diff that only reorders union members in checked-in `.d.ts` files. Source: https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/
