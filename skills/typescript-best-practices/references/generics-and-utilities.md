# TypeScript code-review rules: generics and utility types

Extracted 2026-11-10 from the TypeScript handbook, reference, release notes and TSConfig reference (microsoft/TypeScript-Website, CC BY 4.0) and the TypeScript 7.0 announcement. Current stable at extraction: TypeScript 7.0.2. One rule per bullet, one source link each. Quotations are short excerpts; the rest is original.

## When a type parameter earns its place

- **Add a type parameter only when it relates two or more positions**: "If a type parameter is only used once in the function signature, it's not relating anything." - count the inferred return type as a position; a parameter that still appears once can be replaced by its constraint and the signature means the same to callers. Why: type parameters exist to link an input to another input or to the output, and an unlinked one is noise that still has to be inferred. Smell: `function greet<S extends string>(s: S): void` or `function log<T>(value: T): void` where `string` or `unknown` would do. Source: https://www.typescriptlang.org/docs/handbook/2/functions.html#type-parameters-should-appear-twice
- **Use as few type parameters as the relationship needs**: "That's always a red flag, because it means callers wanting to specify type arguments have to manually specify an extra type argument for no reason." - a second parameter that only constrains the first, such as a callback typed `Func extends (arg: T) => boolean`, relates nothing new. Why: every extra parameter is one more thing to infer, to read and to pass by hand when inference fails. Smell: `function filter<T, F extends (x: T) => boolean>(arr: T[], fn: F): T[]` instead of `fn: (x: T) => boolean`. Source: https://www.typescriptlang.org/docs/handbook/2/functions.html#use-fewer-type-parameters
- **Push the type parameter down to the element rather than constraining the container**: "When possible, use the type parameter itself rather than constraining it" - `arr: Type[]` lets the element type flow out, whereas `Type extends any[]` makes `arr[0]` resolve through the constraint. Why: an expression on a constrained parameter is typed against the constraint at declaration time, so the function returns `any` instead of the caller's element type. Smell: `function first<T extends any[]>(arr: T) { return arr[0] }` whose return type is `any`. Source: https://www.typescriptlang.org/docs/handbook/2/functions.html#push-type-parameters-down
- **Return the type parameter itself, not a value that merely matches its constraint**: "It might look like this function is OK - `Type` is constrained to `{ length: number }`, and the function either returns `Type` or a value matching that constraint." - the compiler rejects this because `Type` promises the caller the same kind of value they passed in, and a fresh object literal is not that. Why: if it compiled, `minimumLength([1, 2, 3], 6).slice(0)` would crash at runtime because the returned object is not an array. Smell: a function declared `(obj: Type, n: number): Type` containing `return { length: n }`, or `return fallback as Type` added to silence the error. Source: https://www.typescriptlang.org/docs/handbook/2/functions.html#working-with-constrained-values

## Constraints and inference

- **Tie a key parameter to its object with a keyof constraint**: "You can declare a type parameter that is constrained by another type parameter." - `function getProperty<Type, Key extends keyof Type>(obj: Type, key: Key)` rejects a key that does not exist and returns `Type[Key]` instead of `unknown`. Why: the constraint turns a typo in the key into a compile error and gives the result the real property type. Smell: `function get<T>(obj: T, key: string) { return (obj as any)[key] }` or `obj[key as keyof T]`. Source: https://www.typescriptlang.org/docs/handbook/2/generics.html#using-type-parameters-in-generic-constraints
- **Let inference choose type arguments and write them only when inference fails or a wider type is intended**: "TypeScript can usually infer the intended type arguments in a generic call, but not always." - the handbook's example is `combine<string | number>([1, 2, 3], ["hello"])`, where the explicit argument deliberately widens a call that inference would reject. Why: explicit arguments duplicate what the values already say, go stale when the values change, and bury the few calls where an explicit argument does real work. Smell: `map<string, number>(names, (n) => n.length)` where both parameters already fix the types. Source: https://www.typescriptlang.org/docs/handbook/2/functions.html#specifying-type-arguments
- **Give a const type parameter a readonly constraint** (5.0+): "Using a mutable type constraint might give surprising results." - `<const T extends string[]>` still infers `string[]` because the readonly tuple candidate is not assignable to a mutable array and inference falls back to the constraint; `<const T extends readonly string[]>` infers `readonly ["a", "b", "c"]`. Why: the `const` modifier only replaces `as const` at the call site when the inferred readonly literal satisfies the constraint, and it never affects a value declared outside the call. Smell: `function route<const T extends string[]>(paths: T)` whose callers still see `string[]`. Source: https://www.typescriptlang.org/docs/handbook/release-notes/typescript-5-0.html#const-type-parameters
- **Wrap a position in NoInfer when it must be checked against a type parameter rather than contribute to it** (5.4+): "Surrounding a type in `NoInfer<...>` gives a signal to TypeScript not to dig in and match against the inner types to find candidates for type inference." - with `colors: C[], defaultColor?: NoInfer<C>` the call `createStreetLight(["red", "yellow", "green"], "blue")` is rejected instead of widening `C` to include `"blue"`. Why: every argument is otherwise an inference candidate, so a value meant to be validated silently widens the union it was supposed to be checked against. Smell: `(colors: C[], defaultColor?: C)` that accepts a colour not in the list, or the older workaround `<C extends string, D extends C>(colors: C[], defaultColor?: D)`. Source: https://www.typescriptlang.org/docs/handbook/release-notes/typescript-5-4.html#the-noinfer-utility-type

## Conditional and mapped types

- **Name the part you need with infer instead of digging it out by hand**: "This frees us from having to think about how to dig through and probing apart the structure of the types we're interested in." - `Type extends Array<infer Item> ? Item : Type` reads as a pattern, and from 4.7 the variable can carry its own constraint, `infer S extends string`, which removes a second nested conditional. Why: indexed-access digging such as `T[0]` or `T[number]` has to be rewritten for every shape, while an `infer` pattern states the shape once. Smell: `T extends [infer S, ...unknown[]] ? S extends string ? S : never : never` or `T extends any[] ? T[number] : T`. Source: https://www.typescriptlang.org/docs/handbook/2/conditional-types.html#inferring-within-conditional-types
- **Do not derive a type from an overloaded function and expect a particular overload**: "It is not possible to perform overload resolution based on a list of argument types." - `ReturnType`, `Parameters` and a hand-written `infer` all read the last signature, which is usually the widest catch-all, so the result is the union, not the branch a given call would pick. Why: a type taken from the wrong signature compiles and quietly admits values the real call never returns. Smell: `type Label = ReturnType<typeof createLabel>` where `createLabel` has three overload signatures. Source: https://www.typescriptlang.org/docs/handbook/release-notes/typescript-2-8.html#type-inference-in-conditional-types
- **Wrap both sides in a tuple when a conditional type must not distribute over a union**: "To avoid that behavior, you can surround each side of the `extends` keyword with square brackets." - a conditional whose checked type is a naked type parameter is applied to each union member separately, so `ToArray<string | number>` is `string[] | number[]` and `IsString<string | number>` is `boolean`, not `false`. Why: distribution is usually what you want, but when it is not, the result is a union of per-member answers rather than one answer for the whole type. Smell: `type IsString<T> = T extends string ? true : false` where `[T] extends [string]` was meant. Source: https://www.typescriptlang.org/docs/handbook/2/conditional-types.html#distributive-conditional-types
- **Rename or drop keys inside the mapped type with an as clause instead of layering helpers around it** (4.1+): "That means you don't have to use an extra `Omit` helper type in some cases." - `[K in keyof T as Exclude<K, "kind">]: T[K]` filters, and a template literal key such as `get${Capitalize<string & K>}` derives new names from old ones. Why: one mapped type keeps the key relationship visible, where a hand-written list of derived keys or a chain of helpers drifts from the source type. Smell: `type LazyPerson = { getName: () => string; getAge: () => number }` written out beside `Person`, or `Omit<{ [K in keyof T]: Wrapped<T[K]> }, "kind">`. Source: https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-1.html#key-remapping-in-mapped-types

## Utility types and compile cost

- **Reach for the built-in utility type that names the transformation**: "This utility will return a type that represents all subsets of a given type." - `Partial`, `Required`, `Readonly`, `Pick`, `Omit`, `Record`, `Exclude`, `Extract`, `NonNullable`, `ReturnType`, `Parameters` and `Awaited` (4.5+) are global, and each name tells the reader what relationship to the source type is intended. Why: a hand-written mapped type or a copied property list says how, not why, and drifts when the source type changes. Smell: `type TodoPatch = { title?: string; description?: string }` duplicated from `Todo`, `{ [K in keyof T]?: T[K] }` inline, or `T extends Promise<infer U> ? U : T` instead of `Awaited<T>`. Source: https://www.typescriptlang.org/docs/handbook/utility-types.html#partialtype
- **Keep recursive conditional types shallow and tail-recursive**: "In general, it's better not to use these types at all than to write something that fails on more realistic examples." - the 4.1 notes say recursive types can increase type-checking time and can hit an internal recursion depth limit, which is a compile error; 4.5 adds that a conditional whose branch is simply another conditional is evaluated without intermediate instantiations, so an accumulator parameter turns `Char | GetChars<Rest>` into a tail call, and the handbook likewise recommends ahead-of-time generation for large template literal unions. Why: a type that errors as excessively deep on a realistic input breaks every consumer, and the failure surfaces in their build, not yours. Smell: ``type GetChars<S> = S extends `${infer Char}${infer Rest}` ? Char | GetChars<Rest> : never``, or a string-parsing type exported from a package's `.d.ts`. Source: https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-1.html#recursive-conditional-types
