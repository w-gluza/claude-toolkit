# Next.js 16 code-review rules: caching and revalidation

Extracted 2026-11-10 from the Next.js 16.4.5 App Router documentation (MIT, Vercel, Inc.). One rule per bullet, one source link each. Quotations are short excerpts; the rest is original.

## Enabling Cache Components and prefetching

- **Set `partialPrefetching` explicitly next to `cacheComponents`** (with `cacheComponents`): "Set `partialPrefetching` explicitly." - add `partialPrefetching: true` whenever `cacheComponents: true` is present, and set it to `false` only while migrating an app that adopted Cache Components before Partial Prefetching. Why: leaving it unset logs a warning because the first Cache Components release shipped without Partial Prefetching; both become default in the next major. Smell: `next.config.ts` with `cacheComponents: true` and no `partialPrefetching` key. Source: https://nextjs.org/docs/app/api-reference/config/next-config-js/cacheComponents#usage
- **Enable `cacheComponents` before `partialPrefetching`**: "Without it, `next dev` and `next build` throw at config validation." - `partialPrefetching` depends on `cacheComponents`. Why: Partial Prefetching builds on the static shell that Cache Components produces. Smell: `partialPrefetching: true` with no `cacheComponents` entry. Source: https://nextjs.org/docs/app/api-reference/config/next-config-js/partialPrefetching#usage
- **Delete every `runtime` segment export** (with `cacheComponents`): "Remove any `runtime` export, including `runtime = 'nodejs'` and the deprecated `runtime = 'edge'`." - Cache Components only supports the Node.js runtime and rejects the segment config. Why: other runtimes are not guaranteed to work; use Proxy for edge behaviour. Smell: `export const runtime = 'edge'` in a `page.tsx` under a config with `cacheComponents: true`. Source: https://nextjs.org/docs/app/api-reference/config/next-config-js/cacheComponents#usage
- **Remove `experimental.ppr` and `experimental_ppr`** (with `cacheComponents`): "This means the `experimental.ppr` configuration flag and the `experimental_ppr` route segment configuration are no longer necessary and have been removed." - PPR is the default under Cache Components. Why: the flags were removed in Next.js 16. Smell: `export const experimental_ppr = true` or `experimental: { ppr: true }` still in the diff. Source: https://nextjs.org/docs/app/api-reference/config/next-config-js/cacheComponents#usage

## Caching with Cache Components

- **Do not cache components that must be fresh on every request** (with `cacheComponents`): "For components that fetch data from an asynchronous source such as an API, a database, or any other async operation, and require fresh data on every request, do not use `"use cache"`." - stream them instead. Why: a cache directive gives the result a lifetime and serves it to later requests. Smell: `'use cache'` on a component rendering a live order status or unread count. Source: https://nextjs.org/docs/app/getting-started/caching#streaming-uncached-data
- **Wrap uncached async reads in `<Suspense>`** (with `cacheComponents`): "Instead, wrap the component in `<Suspense>` and provide a fallback UI." - the fallback ships in the static shell while the data streams. Why: an uncached read outside a boundary triggers the blocking-route insight and blocks the shell. Smell: an `async` server component awaiting an uncached `fetch` rendered directly by the page with no `<Suspense>` ancestor. Source: https://nextjs.org/docs/app/getting-started/caching#streaming-uncached-data
- **Do not use `<Suspense>` to force dynamic rendering** (with `cacheComponents`): "`<Suspense>` provides a fallback UI while async work completes, but it does not itself opt a component into dynamic rendering." - only runtime APIs, `connection()` or uncached async work defer a component. Why: synchronous work completes during prerendering regardless of the boundary. Smell: a synchronous component wrapped in `<Suspense>` with a comment claiming it now renders per request. Source: https://nextjs.org/docs/app/getting-started/caching#streaming-uncached-data
- **Read `cookies()` in a Suspense-wrapped leaf, not at the page top** (with `cacheComponents`): "Reading `cookies()` here doesn't opt-in the whole route into dynamic rendering, the way the previous rendering model did." - keep the read inside a small component under `<Suspense>` so static and cached siblings still ship in the shell. Why: the boundary isolates the runtime access; a top-level read blocks the whole route. Smell: `const theme = (await cookies()).get('theme')` as the first line of `page.tsx`. Source: https://nextjs.org/docs/app/getting-started/caching#static-cached-and-streaming
- **Handle random values and timestamps explicitly** (with `cacheComponents`): "Cache Components requires you to explicitly handle these." - either `await connection()` before `Math.random()`, `Date.now()` or `crypto.randomUUID()` inside `<Suspense>`, or put the call in a `use cache` scope so every user shares one value. Why: these produce a different value each render and break the prerender. Smell: `const id = crypto.randomUUID()` in a server component body with neither `connection()` nor `'use cache'`. Source: https://nextjs.org/docs/app/getting-started/caching#random-values-and-timestamps
- **Read request-independent local files at module scope** (with `cacheComponents`): "When those resources are expected to be the same for every request, read them once at module scope instead of during rendering" - config and font files that never vary belong outside the component. Why: an `await readFile()` inside a component is treated as uncached data that needs `use cache` or `<Suspense>`. Smell: `const content = await readFile('./config.json')` inside the component function. Source: https://nextjs.org/docs/app/getting-started/caching#predictable-values
- **Push `await params` as deep as possible** (with `cacheComponents`): "The deeper your async work sits in the tree, the more of the page can be prerendered." - pass the `params` promise down and await it inside a `<Suspense>` leaf. Why: awaiting a dynamic param at layout level makes the whole layout runtime data. Smell: `const { slug } = await params` at the top of a layout that renders a sidebar and `children` below it. Source: https://nextjs.org/docs/app/getting-started/caching#maximizing-the-static-shell
- **Use `cacheTag` with a long lifetime for CMS-style content** (with `cacheComponents`): "When content doesn't need time-based revalidation, for example data from a CMS, use `cacheTag` and a long `cacheLife` like `max` to keep it in the static shell." - invalidate from a webhook with `revalidateTag`. Why: it avoids pointless time-based revalidation of unchanged content. Smell: `cacheLife('minutes')` on editorial content that only changes when an editor publishes. Source: https://nextjs.org/docs/app/getting-started/revalidating#what-should-i-cache

## `use cache`

- **Make every cached function or component `async`** (with `cacheComponents`): "Functions and components that use `use cache` must be async." - the directive only applies to async functions. Why: the cache stores a serialised promise result. Smell: `function getData() { 'use cache' ... }` without `async`. Source: https://nextjs.org/docs/app/api-reference/directives/use-cache
- **Make all exports async in a file-level `'use cache'`** (with `cacheComponents`): "Every exported function it covers must be async." - the file directive turns each export into a cached function, including `generateMetadata` and `generateStaticParams`. Why: a synchronous export cannot be cached and fails. Smell: a `'use cache'` file that also exports a synchronous helper, or `export function generateMetadata()` without `async` in such a file. Source: https://nextjs.org/docs/app/api-reference/directives/use-cache#caching-a-modules-exports-with-use-cache
- **Account for captured variables in the cache key** (with `cacheComponents`): "When a cached function references variables from outer scopes, those variables are automatically captured and bound as arguments, making them part of the cache key." - closures over per-user values create per-user entries. Why: unexpected key cardinality destroys hit rate. Smell: an inline `'use cache'` closure inside a component that captures `userId` or `session`. Source: https://nextjs.org/docs/app/api-reference/directives/use-cache#cache-keys
- **Keep arguments and return values serialisable** (with `cacheComponents`): "Arguments to cached functions and their return values must be serializable." - class instances, functions, symbols, WeakMaps and `URL` instances are not allowed. Why: entries are stored as RSC payloads. Smell: a cached component typed `{ user: UserClass }` or a cached function taking a `URL` argument. Source: https://nextjs.org/docs/app/api-reference/directives/use-cache#serialization
- **Pass children and slots through untouched** (with `cacheComponents`): "As long as you don't directly reference any of the JSX slots inside the body of the cacheable function itself, their presence in the returned output won't affect the cache entry." - compose dynamic children into cached wrappers. Why: introspecting a slot would make it part of the key and break serialisation. Smell: a cached wrapper calling `React.Children.map(children, ...)`. Source: https://nextjs.org/docs/app/api-reference/directives/use-cache#interleaving
- **Do not invoke a pass-through Server Action inside the cached scope** (with `cacheComponents`): "You can also pass Server Actions through cached components to Client Components without invoking them inside the cacheable function." - hand it to `<form action>` or a client prop. Why: calling it would execute a mutation during cache fill. Smell: `await performUpdate()` inside a `'use cache'` component that receives `performUpdate` as a prop. Source: https://nextjs.org/docs/app/api-reference/directives/use-cache#interleaving
- **Never read `cookies()`, `headers()` or `searchParams` inside a cached scope** (with `cacheComponents`): "Read these values outside the cached scope and pass them as arguments." - the restriction follows the call stack into helpers. Why: it throws `next-request-in-use-cache`. Smell: a util called from a cached function that does `await headers()`. Source: https://nextjs.org/docs/app/api-reference/directives/use-cache#request-time-apis
- **Do not treat a green `next build` as proof the cached scope is clean** (with `cacheComponents`): "On a dynamically rendered route this surfaces when the route runs, so it can pass `next build` and fail under `next start`." - run the production server against dynamic routes. Why: the request-API check only fires when the route executes. Smell: a PR adding `'use cache'` to a request-gated helper with only a build log as evidence. Source: https://nextjs.org/docs/app/api-reference/directives/use-cache#request-time-apis
- **Do not pass data into `use cache` through `React.cache`** (with `cacheComponents`): "Values stored via `React.cache` outside a `use cache` function are not visible inside it." - use function arguments instead. Why: each cached scope has an isolated `React.cache`. Smell: a `cache(() => ({ current: null }))` store written by a parent and read inside a cached child. Source: https://nextjs.org/docs/app/api-reference/directives/use-cache#reactcache-isolation
- **Set `cacheLife` in every `use cache` scope** (with `cacheComponents`): "Set an explicit cache lifetime with `cacheLife` in every `use cache` scope." - do not rely on the implicit `default` profile. Why: the lifetime should be readable at the call site and not depend on surrounding caches. Smell: a `'use cache'` body with no `cacheLife(` call. Source: https://nextjs.org/docs/app/api-reference/directives/use-cache#time-based-revalidation
- **Do not pass runtime-data promises into cached scopes** (with `cacheComponents`): "If your build hangs, you're accessing Promises that resolve to uncached or runtime data, created outside a `use cache` boundary." - await the value outside and pass the plain result. Why: the cached function waits for data that cannot resolve during the build and times out after 50 seconds. Smell: `<Cached promise={cookies()} />` or a cached component awaiting a `params` promise prop. Source: https://nextjs.org/docs/app/api-reference/directives/use-cache#build-hangs-cache-timeout
- **Do not share a promise Map between cached and uncached code** (with `cacheComponents`): "Use Next.js's built-in `fetch()` deduplication or use separate Maps for cached and uncached contexts." - a module-level dedupe Map holding dynamic promises hangs the build when read from `use cache`. Why: the cached reader waits for a request-time promise. Smell: `const cache = new Map<string, Promise<...>>()` populated by a dynamic component and read inside a cached one. Source: https://nextjs.org/docs/app/api-reference/directives/use-cache#build-hangs-cache-timeout
- **Cache every segment file to prerender a whole route** (with `cacheComponents`): "To prerender a whole route, add `use cache` to the top of every segment file it renders: the `page`, the `layout`, and any parallel route slots." - each segment is cached independently. Why: a cached layout does not cache its `children`. Smell: `'use cache'` on `layout.tsx` only, with an uncached `page.tsx` expected to be static. Source: https://nextjs.org/docs/app/api-reference/directives/use-cache#caching-a-route-segments-output-with-use-cache

## `use cache: private`

- **Reach for `'use cache: private'` only as a last resort** (with `cacheComponents`): "Only use `'use cache: private'` if you have compliance requirements or can't refactor to pass runtime data as arguments." - prefer extracting the cookie or header value and passing it to a plain `use cache` function. Why: private results are never stored server-side and cannot reduce origin load across users. Smell: `'use cache: private'` on a function whose only runtime input is a cookie value that could be an argument. Source: https://nextjs.org/docs/app/api-reference/directives/use-cache-remote#caching-with-runtime-data
- **Give private caches a `stale` of at least 30 seconds, or 5 minutes for the App Shell** (with `cacheComponents`): "The `stale` time must be at least 30 seconds for per-link prefetching to work, and at least 5 minutes for the content to be included in the route's App Shell." - choose the threshold that matches where the content should live. Why: shorter values exclude the result from prefetches. Smell: `cacheLife({ stale: 10 })` on a private function the PR says should be prefetched. Source: https://nextjs.org/docs/app/api-reference/directives/use-cache-private#basic-example
- **Use `stale: Infinity` for request-scoped deduplication only** (with `cacheComponents`): "If a function only needs request-scoped deduplication, use `cacheLife({ stale: Infinity })` to keep it from lowering the route's stale time." - Next.js takes the shortest stale across the route. Why: a finite stale on a dedupe helper shortens the client cache for the whole route. Smell: `cacheLife({ stale: 60 })` on a private helper that exists only to dedupe calls within one request. Source: https://nextjs.org/docs/app/api-reference/directives/use-cache-private#configuring-the-client-stale-time
- **Never call `connection()` inside any cache directive** (with `cacheComponents`): "The `connection()` API is prohibited in both `use cache` and `'use cache: private'` as it provides connection-specific information that cannot be safely cached." - call it in the uncached parent. Why: connection data cannot be keyed. Smell: `await connection()` as the first line of a `'use cache: private'` function. Source: https://nextjs.org/docs/app/api-reference/directives/use-cache-private#request-apis-allowed-in-private-caches

## `use cache: remote`

- **Use remote caching for content deferred to request time** (with `cacheComponents`): "Remote caching provides the most value when content is deferred to request time (outside the static shell)." - static-shell content is already served by plain `use cache`. Why: outside the shell each request looks up the cache, and serverless memory rarely hits. Smell: `'use cache: remote'` on a function that only runs during prerendering. Source: https://nextjs.org/docs/app/api-reference/directives/use-cache-remote#when-remote-caching-makes-sense
- **Avoid remote caching when keys are unique per request** (with `cacheComponents`): "If cache keys have mostly unique values per request (search filters, price ranges, user-specific parameters), cache utilization will be near-zero" - key on a low-cardinality dimension instead. Why: every lookup pays a network round trip and still misses. Smell: `'use cache: remote'` on `search(query, minPrice, maxPrice, sort)`. Source: https://nextjs.org/docs/app/api-reference/directives/use-cache-remote#when-to-avoid-remote-caching
- **Cache on the dimension with few unique values and filter in memory** (with `cacheComponents`): "find the dimension with fewer unique values (category vs. price, language vs. user ID), cache on that dimension, and filter or select the rest in memory" - one entry per category or language, not per user or price. Why: larger shared entries beat thousands of per-user entries. Smell: `getUserProfile(sessionId)` wrapped in `'use cache: remote'`. Source: https://nextjs.org/docs/app/api-reference/directives/use-cache-remote#cache-key-considerations
- **Use private, not remote, for user-specific data** (with `cacheComponents`): "For user-specific data, use `'use cache: private'` instead of `'use cache: remote'`" - remote entries are shared across all users. Why: personal data in a shared store is a leak and a poor hit rate. Smell: a remote-cached function keyed on a session id returning recommendations. Source: https://nextjs.org/docs/app/api-reference/directives/use-cache-remote#mixed-caching-strategies
- **Never nest remote and private caches in either direction** (with `cacheComponents`): "Remote caches cannot be nested inside private caches (`'use cache: private'`)" - and private caches cannot be nested inside remote ones; remote inside remote or inside plain `use cache` is fine. Why: the private scope has request data that the shared remote store must not hold. Smell: a `'use cache: private'` function awaiting a `'use cache: remote'` helper. Source: https://nextjs.org/docs/app/api-reference/directives/use-cache-remote#nesting-rules

## `cacheLife`

- **Call `cacheLife` only inside a cache directive scope** (with `cacheComponents`): "`cacheLife` cannot be used at module scope." - it must sit inside the function or component body. Why: a module-level call throws. Smell: `cacheLife('hours')` at the top of a file beneath a file-level `'use cache'`. Source: https://nextjs.org/docs/app/api-reference/functions/cacheLife#basic-setup
- **Keep `cacheLife` in the function that caches, not a shared helper** (with `cacheComponents`): "Avoid abstracting it into shared utilities so the cache behavior remains explicit and easy to reason about." - the lifetime should be visible where the directive is. Why: indirection hides the lifetime from readers. Smell: `applyDefaultCaching()` helper that calls `cacheLife` on behalf of cached functions. Source: https://nextjs.org/docs/app/api-reference/functions/cacheLife#basic-setup
- **Let only one `cacheLife` call execute per invocation** (with `cacheComponents`): "If you call `cacheLife`, ensure only one call executes per function invocation." - branches may each call it, but only one path should run. Why: multiple calls make the effective lifetime ambiguous. Smell: `cacheLife('days')` at the top followed by an unconditional `cacheLife('minutes')` later in the same body. Source: https://nextjs.org/docs/app/api-reference/functions/cacheLife#basic-setup
- **Keep `expire` longer than `revalidate`** (with `cacheComponents`): "When you set both `revalidate` and `expire`, `expire` must be longer than `revalidate`." - Next.js validates and errors otherwise. Why: an entry cannot expire before it is due for background refresh. Smell: `cacheLife({ revalidate: 3600, expire: 600 })`. Source: https://nextjs.org/docs/app/api-reference/functions/cacheLife#expire
- **Remember omitted profile fields inherit from `default`** (with `cacheComponents`): "Any omitted properties in a custom profile inherit from the `default` profile." - this applies to inline objects too. Why: `cacheLife({ stale: 60 })` still revalidates every 15 minutes and never expires. Smell: an inline profile setting one field with a comment assuming the others are unbounded or zero. Source: https://nextjs.org/docs/app/api-reference/functions/cacheLife#custom-cache-profiles
- **Do not set `stale` below 30 seconds expecting the client to honour it** (with `cacheComponents`): "This 30-second minimum prevents prefetched data from expiring before users can click on links." - the router enforces a floor. Why: prefetched links must remain usable. Smell: `cacheLife({ stale: 5 })` with a comment about near-real-time client refresh. Source: https://nextjs.org/docs/app/api-reference/functions/cacheLife#client-cache-behavior
- **Expect any Server Action revalidation to flush the whole client cache** (with `cacheComponents`): "When you call revalidation functions from a Server Action (`revalidateTag`, `revalidatePath`, `updateTag`, or `refresh`), the entire client cache is immediately cleared, bypassing the stale time." - call them only after real mutations. Why: frequent calls throw away every prefetched route. Smell: `revalidatePath('/')` inside an autosave action that fires on every keystroke. Source: https://nextjs.org/docs/app/api-reference/functions/cacheLife#client-cache-behavior
- **Keep short-lived caches out of the static shell deliberately** (with `cacheComponents`): "Of the presets, only `seconds` falls under any of these thresholds: its `expire` of 1 minute excludes it from prerenders." - `revalidate: 0` or `expire` under 5 minutes becomes a dynamic hole. Why: a short lifetime cannot be stored safely in a prerender. Smell: `cacheLife('seconds')` on a hero component the PR describes as part of the static shell. Source: https://nextjs.org/docs/app/api-reference/functions/cacheLife#prerendering-behavior
- **Wrap short-lived caches in `<Suspense>`** (with `cacheComponents`): "Use a `<Suspense>` boundary around dynamic caches to provide a fallback while content loads." - short-lived entries resolve at request time. Why: they become dynamic holes and need a fallback. Smell: a `cacheLife('seconds')` component rendered directly in a page with no boundary. Source: https://nextjs.org/docs/app/api-reference/functions/cacheLife#prerendering-behavior
- **Give outer caches an explicit lifetime** (with `cacheComponents`): "Inner caches with shorter lifetimes can reduce the outer cache's `default` lifetime." - an explicit outer `cacheLife` always wins over inner ones. Why: without it the outer lifetime silently depends on nested caches. Smell: a `'use cache'` page without `cacheLife` composing cached widgets that each set their own. Source: https://nextjs.org/docs/app/api-reference/functions/cacheLife#without-explicit-outer-cachelife
- **Set an explicit `cacheLife` when nesting a short-lived cache** (with `cacheComponents`): "To prevent this accidental misconfiguration, Next.js throws an error during prerendering." - the nested cache may come from an imported module or a dependency. Why: the outer lifetime would otherwise silently become short. Smell: a `'use cache'` page without `cacheLife` rendering a `cacheLife('seconds')` component. Source: https://nextjs.org/docs/app/api-reference/functions/cacheLife#nested-short-lived-caches

## `cacheTag`

- **Tag cached data that will ever need on-demand invalidation** (with `cacheComponents`): "The `cacheTag` function allows you to tag cached data for on-demand invalidation." - without a tag the only exits are time or a path purge. Why: mutations cannot target untagged entries precisely. Smell: `'use cache'` with `cacheLife('max')` on product data and no `cacheTag`, with a product edit action nearby. Source: https://nextjs.org/docs/app/api-reference/functions/cacheTag
- **Stay within 128 tags per call and 256 characters per tag** (with `cacheComponents`): "A single `cacheTag()` call accepts up to 128 tags, each with a maximum length of 256 characters." - excess tags are dropped with only a console warning. Why: a dropped tag can never be revalidated. Smell: `cacheTag(JSON.stringify(filters))` or spreading a large id list into one call. Source: https://nextjs.org/docs/app/api-reference/functions/cacheTag#good-to-know
- **Pick `updateTag` for forms, `revalidateTag` for background refresh** (with `cacheComponents`): "Use `updateTag` for read-your-own-writes scenarios, such as forms and other user-triggered mutations, where a user makes a change and the next read should fetch fresh data immediately." - `revalidateTag` serves stale while it refreshes. Why: the user must see their own write. Smell: a form action calling `revalidateTag('cart', 'max')` then redirecting to the cart. Source: https://nextjs.org/docs/app/api-reference/functions/cacheTag#usage

## Revalidation strategy

- **Share one tag across every reader of the same data** (with `cacheComponents`): "You can reuse the same tag in multiple functions to revalidate them all at once." - a single `revalidateTag` then refreshes all of them. Why: divergent tags leave some readers stale after a mutation. Smell: one function tagged `posts` and another tagged `post-list`, with the action invalidating only `posts`. Source: https://nextjs.org/docs/app/getting-started/revalidating#revalidatetag
- **Reserve `revalidatePath` for when tags are unknown** (with `cacheComponents`): "Use it when you want to revalidate a route without knowing which tags are associated with it." - prefer tag-based revalidation because it is more precise. Why: path revalidation over-invalidates. Smell: `revalidatePath('/products')` after editing one product that already carries a `product-${id}` tag. Source: https://nextjs.org/docs/app/getting-started/revalidating#revalidatepath

## `revalidateTag`

- **Always pass the second argument** (deprecated single-argument form): "The single-argument form `revalidateTag(tag)` is deprecated." - migrate to `updateTag` in Server Actions or `revalidateTag(tag, 'max')`. Why: the old form behaves like `{ expire: 0 }` and may be removed. Smell: `revalidateTag('posts')`. Source: https://nextjs.org/docs/app/api-reference/functions/revalidateTag#parameters
- **Use `'max'` for stale-while-revalidate**: "With the recommended `max` profile, users receive stale content while fresh data loads in the background." - a one-year window means requests are never blocked. Why: it suits catalogues, posts and docs where a short delay is fine. Smell: `revalidateTag('posts', 'seconds')` in a webhook for a blog. Source: https://nextjs.org/docs/app/api-reference/functions/revalidateTag
- **Use `{ expire: 0 }` outside Server Actions when data must be gone now**: "Use it when the caller needs the data gone immediately and you cannot use `updateTag`." - webhooks and Route Handlers cannot call `updateTag`. Why: the next request then blocks on a fresh render instead of serving stale. Smell: `updateTag('orders')` in a Route Handler or a `'max'` profile for a deletion that must not be visible. Source: https://nextjs.org/docs/app/api-reference/functions/revalidateTag#revalidation-behavior
- **Do not call `revalidateTag` from Client Components or Proxy**: "`revalidateTag` cannot be called in Client Components or Proxy, as it only works in server environments." - route it through a Server Action or handler. Why: it needs the server cache. Smell: `revalidateTag` imported in a `'use client'` file or `proxy.ts`. Source: https://nextjs.org/docs/app/api-reference/functions/revalidateTag#usage
- **Do not expect eager regeneration from `revalidateTag`**: "A revalidation is triggered by a request, not by the `revalidateTag` call, so pages using the tag revalidate as they are visited rather than all at once." - the call only marks data stale. Why: regeneration happens on the next visit. Smell: a cron job calling `revalidateTag` to pre-warm pages. Source: https://nextjs.org/docs/app/api-reference/functions/revalidateTag#revalidation-behavior

## `updateTag`

- **Call `updateTag` only from Server Actions**: "`updateTag` can only be called from within Server Actions." - it throws anywhere else. Why: it expires data for the caller's own next read. Smell: `updateTag('posts')` inside a Route Handler `POST`. Source: https://nextjs.org/docs/app/api-reference/functions/updateTag#usage
- **Use `updateTag` after mutations the user must see immediately**: "This function is designed for read-your-own-writes scenarios, where a user makes a change (like creating a post), and the UI immediately shows the change, rather than stale data." - the next request waits for fresh data. Why: `revalidateTag` with a profile would serve the stale version first. Smell: a create action calling `revalidateTag('posts', 'max')` then `redirect` to the new post. Source: https://nextjs.org/docs/app/api-reference/functions/updateTag

## `revalidatePath`

- **Pass the destination path when rewrites are involved**: "When using rewrites, you must pass the destination path (the actual route file location), not the source path that appears in the browser's address bar." - the cache is keyed by route file. Why: the source path matches no entry. Smell: `revalidatePath('/blog')` where `/blog` rewrites to `/news`. Source: https://nextjs.org/docs/app/api-reference/functions/revalidatePath#using-revalidatepath-with-rewrites
- **Pass `type` with a dynamic route pattern**: "If `path` contains a dynamic segment, for example `/product/[slug]`, this parameter is required." - omit it for literal paths and never append `/page` or `/layout` to the path instead. Why: the pattern needs to know whether it targets a page or a layout. Smell: `revalidatePath('/product/[slug]')` with no second argument, or `revalidatePath('/blog/[slug]/page')`. Source: https://nextjs.org/docs/app/api-reference/functions/revalidatePath#parameters
- **Do not expect `revalidatePath` to refresh other pages sharing the data**: "When you call `revalidatePath`, only the specified path gets fresh data on the next visit." - combine it with `updateTag` or `revalidateTag` for shared data. Why: other pages keep serving cached entries until their tags are invalidated. Smell: an edit action calling `revalidatePath('/blog')` while `/dashboard` renders the same posts. ## How revalidation works

- **Use `cacheHandlers` for `use cache` and `cacheHandler` for ISR**: "The `cacheHandlers` option (plural) is for `'use cache'` directives." - the singular option serves ISR, route handler responses and images. Why: the two caches are separate systems with different APIs. Smell: a Redis `cacheHandler` added with the expectation that `'use cache: remote'` now uses it. Source: https://nextjs.org/docs/app/guides/how-revalidation-works#the-revalidation-model
- **Cache HTML and RSC with the same TTL and invalidation**: "The primary mitigation is to cache HTML and RSC responses together with the same TTL and invalidation policy, and to respect the `Vary` header that Next.js sets." - mismatched variants show stale content on client navigation. Why: both artifacts come from the same render. Smell: a CDN rule that caches `*.rsc` responses for a different duration than HTML. Source: https://nextjs.org/docs/app/guides/how-revalidation-works#what-happens-if-they-get-out-of-sync
- **Configure `deploymentId` for rolling deployments**: "`deploymentId` mitigates this: when the client detects a different deployment ID from the server, it triggers a hard navigation to fetch consistent content." - it prevents cross-deployment skew. Why: a client from deploy A can otherwise receive deploy B's payload. Smell: a multi-instance rolling deploy with no `deploymentId` in config. Source: https://nextjs.org/docs/app/guides/how-revalidation-works#what-happens-if-they-get-out-of-sync
- **Catch errors inside `refreshTags`**: "Your handler must catch errors in `refreshTags()`: if it throws, the exception propagates as a request failure." - degrade to the last known local tag state. Why: a shared-store outage should mean stale content, not failed requests. Smell: `await client.sMembers(...)` in `refreshTags` with no `try/catch`. Source: https://nextjs.org/docs/app/guides/how-revalidation-works#multi-instance-with-shared-cache
- **Return `undefined` from `get()` on failure, never throw**: "A thrown error is not treated as a cache miss; it propagates as a render error, so always return `undefined` to signal a miss." - the framework does not wrap `get()`. Why: a store outage must become a fresh render, not a 500. Smell: `get()` that calls `JSON.parse(await client.get(key))` with no error handling. Source: https://nextjs.org/docs/app/guides/how-revalidation-works#graceful-degradation

## `cacheHandlers` for `use cache`

- **Do not try to configure a handler for `'use cache: private'`** (with `cacheComponents`): "Note that `'use cache: private'` does not use cache handlers and cannot be customized." - only `default`, `remote` and custom names are configurable. - **Consume the entry stream once and never keep it** (with `cacheComponents`): "Do not keep it once `set()` resolves." - buffer or pipe the bytes and store those. - **Build a fresh stream on every `get()` hit** (with `cacheComponents`): "Wrap your stored data in a new stream on every hit, never the stream you received in `set()`." - a stream can be read only once. - **Signal tag invalidation with `undefined` or `revalidate: -1`** (with `cacheComponents`): "Next.js serves it and regenerates in the background, because a negative `revalidate` always lies in the past." - return `undefined` to force regeneration now, `-1` to serve stale and refresh. Why: these are the only two signals the framework understands. Smell: a handler that mutates `expire` to 0 to mark a stale entry. - **Record tag timestamps rather than deleting tagged entries** (with `cacheComponents`): "Soft tags are not stored in an entry's `tags`, so deleting the entries that carry a tag does not cover `revalidatePath()`." - `get()` and `getExpiration()` compare timestamps against each entry. Why: path revalidation uses soft tags that the entry does not carry. Smell: `updateTags` implemented as a delete-by-tag loop. Source: https://nextjs.org/docs/app/api-reference/config/next-config-js/cacheHandlers#updatetags
- **Branch on `durations` in `updateTags`** (with `cacheComponents`): "Your handler should record when each tag was invalidated." - absent `durations` means expire immediately; present means stale now and expired after `durations.expire` seconds. Why: `updateTag` and `revalidateTag(tag, 'max')` expect different serving behaviour. Smell: `updateTags(tags)` ignoring the second parameter and always expiring immediately. Source: https://nextjs.org/docs/app/api-reference/config/next-config-js/cacheHandlers#updatetags
- **Catch errors in `set()`** (with `cacheComponents`): "Catch your own errors even so: a rejected `set()` joins the request's pending revalidation work, where it surfaces as a failed background task instead of a render error." - the response is already flowing. Why: an unhandled rejection becomes a failed background task. Smell: `await client.set(...)` in `set()` with no `try/catch`. Source: https://nextjs.org/docs/app/api-reference/config/next-config-js/cacheHandlers#error-handling
- **Write entries atomically** (with `cacheComponents`): "Use atomic writes or a write-then-rename pattern to avoid serving partial entries." - a half-written entry read back is undefined behaviour. Why: partial entries render partial pages. Smell: a file-system handler streaming directly into the final path. Source: https://nextjs.org/docs/app/api-reference/config/next-config-js/cacheHandlers#error-handling

## `cacheHandler` for ISR and `cacheMaxMemorySize`

- **Do not expect `cacheHandler` to serve `use cache`**: "It is not used by `'use cache'` directives." - it stores ISR pages, route handler responses and optimised images. Why: the two systems have separate handler APIs. Smell: a PR adding `cacheHandler` as the fix for `'use cache: remote'` misses. Source: https://nextjs.org/docs/app/api-reference/config/next-config-js/incrementalCacheHandlerPath
- **Set `cacheMaxMemorySize: 0` when adopting a custom `cacheHandler`**: "Set this to `0` when adopting a custom `cacheHandler`, so reads go to your store rather than a per-instance copy." - otherwise each instance still keeps a local copy. Why: a per-instance copy defeats shared invalidation. Smell: `cacheHandler: require.resolve('./cache-handler.js')` with `cacheMaxMemorySize` left at its default. Source: https://nextjs.org/docs/app/api-reference/config/next-config-js/cacheMaxMemorySize
- **Treat cache keys as opaque in a custom `cacheHandler`**: "Preserve the entire key when reading and writing entries; a key is not a request pathname." - response keys include the kind and a hash of the source route. Why: handlers that parse keys as paths break route isolation. Smell: `key.split('/')` to derive a pathname inside `get()`. Source: https://nextjs.org/docs/app/api-reference/config/next-config-js/incrementalCacheHandlerPath#get

## CDN caching

- **Purge the CDN alongside on-demand revalidation**: "To propagate on-demand revalidation to the CDN, trigger CDN purges alongside your revalidation call." - purge both HTML and RSC variants. Why: `revalidateTag` and `revalidatePath` only invalidate the Next.js server cache. Smell: a webhook calling `revalidateTag` behind a CDN with no purge call. Source: https://nextjs.org/docs/app/guides/cdn-caching#cache-control-headers
- **Include `_rsc` in the CDN cache key**: "The `_rsc` search parameter must be included in the cache key." - it distinguishes HTML from RSC and prefetch variants, and the `rsc` request header must be forwarded to the origin as well. Why: some CDNs strip query parameters by default and then serve HTML to RSC requests, which breaks client-side navigation. Smell: a CDN rule that ignores query strings for all routes, or a header allowlist that omits `rsc`. Source: https://nextjs.org/docs/app/guides/cdn-caching#what-you-must-preserve
- **Run `proxy.js` in front of the CDN cache**: "`proxy.js` (previously Middleware) should run before the CDN cache so it remains the source of truth for auth, redirects, and rewrites." - or bypass caching for routes that depend on it. Why: a cached response skips the proxy decision. Smell: auth checks in `proxy.ts` on routes the CDN caches with `s-maxage`. Source: https://nextjs.org/docs/app/guides/cdn-caching#where-cdn-caching-is-challenging
- **Set `expireTime` when the CDN should stop serving stale sooner than a year**: "You can specify a custom `stale-while-revalidate` expire time for CDNs to consume in the `Cache-Control` header for ISR enabled pages." - the header becomes `s-maxage={revalidate}, stale-while-revalidate={expireTime - revalidate}`. Why: the default expire is one year of stale serving. Smell: ISR pages with a strict freshness requirement and no `expireTime` in config. Source: https://nextjs.org/docs/app/api-reference/config/next-config-js/expireTime

## Other cache-related config

- **Remember `staleTimes.static` rewrites the `default` profile's `stale`** (experimental, with `cacheComponents`): "Updating `staleTimes.static` also updates the `stale` value of the `default` cache profile." - the two settings are coupled. Why: a global tweak silently changes every `use cache` scope without an explicit `cacheLife`. Smell: `staleTimes: { static: 30 }` in a `cacheComponents` app relying on the default profile. Source: https://nextjs.org/docs/app/api-reference/functions/cacheLife#client-cache-behavior
- **Leave `prefetchInlining` at its default** (experimental): "For most applications, there is no need to change the default behavior." - change it only while debugging navigation or measuring request volume. Why: inlining is on by default and tuned. Smell: `experimental.prefetchInlining: false` committed after a debugging session. Source: https://nextjs.org/docs/app/api-reference/config/next-config-js/prefetchInlining
- **Do not set `supportsImmutableAssets` in application code**: "App developers should only set it when troubleshooting adapter-specific issues." - it is for adapter authors. Why: enabling it on an unsupported provider can break deployments. Smell: `supportsImmutableAssets: true` in an app's `next.config.js`. Source: https://nextjs.org/docs/app/api-reference/config/next-config-js/supportsImmutableAssets

## CI build caching

- **Persist `.next/cache` between CI builds**: "To take advantage of this cache in Continuous Integration (CI) environments, your CI workflow will need to be configured to correctly persist the cache between builds." - add it to the provider's cache paths. Why: without it every build starts cold and logs a No Cache Detected error. Smell: a CI config that caches `node_modules` but not `.next/cache`. Source: https://nextjs.org/docs/app/guides/ci-build-caching
