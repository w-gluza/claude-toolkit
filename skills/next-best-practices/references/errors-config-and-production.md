# Next.js 16 code-review rules: errors, configuration, build, deployment, upgrading

Extracted 2026-11-10 from the Next.js 16.4.5 App Router documentation (MIT, Vercel, Inc.). One rule per bullet, one source link each. Quotations are short excerpts; the rest is original.

## Error handling and error boundaries

- **Return expected Server Function errors instead of throwing them**: "For these errors, avoid using `try`/`catch` blocks and throw errors. Instead, model expected errors as return values." - validation and business failures come back as data that `useActionState` renders. Why: thrown errors are reserved for unexpected failures and would trip error boundaries for ordinary form mistakes. Smell: a Server Action doing `throw new Error('Email is required')` after a form check. Source: https://nextjs.org/docs/app/getting-started/error-handling#server-functions
- **Use notFound() with a not-found.js file for missing records**: "You can call the `notFound` function within a route segment and use the `not-found.js` file to show a 404 UI." - a missing entity is an expected state, not an exception for error.js. Why: it produces a real 404 with dedicated UI rather than a generic error fallback. Smell: `if (!post) throw new Error('Not found')` inside a page. Source: https://nextjs.org/docs/app/getting-started/error-handling#not-found
- **Catch errors inside event handlers yourself**: "Error boundaries don't catch errors inside event handlers." - wrap async work in `onClick` and friends in try/catch and keep the failure in `useState` or `useReducer`. Why: nothing above the handler sees the rejection, so the user gets no feedback at all. Smell: `onClick={async () => { await saveItem() }}` with no try/catch and no error state. Source: https://nextjs.org/docs/app/getting-started/error-handling#nested-error-boundaries
- **Handle failures inside startTransition or accept that error.js takes over**: "Note that unhandled errors inside `startTransition` from `useTransition`, will bubble up to the nearest error boundary." - a rejected action inside a transition replaces the whole segment with the boundary UI. Why: transitions do not isolate errors the way event handlers do. Smell: `startTransition(() => action(formData))` with no catch around a call that can reject. Source: https://nextjs.org/docs/app/getting-started/error-handling#nested-error-boundaries
- **Give global-error.js its own html and body tags**: "Global error UI must define its own `<html>` and `<body>` tags, since it is replacing the root layout or template when active." Why: the root layout is gone when this file renders, so the document would otherwise be empty. Smell: a `global-error.tsx` that returns only a `<div>` with a message. Source: https://nextjs.org/docs/app/getting-started/error-handling#global-errors
- **Do not expect error.js to catch its own segment's layout**: "It does **not** wrap the `layout.js` or `template.js` above it in the same segment." - put the boundary in the parent segment or move risky work out of the layout. Why: the boundary renders inside the layout, so layout errors escape upwards. Smell: a `layout.tsx` with an unguarded `await fetch()` and a sibling `error.tsx` as the only protection. Source: https://nextjs.org/docs/app/api-reference/file-conventions/error
- **Narrow the error prop before reading properties**: "Narrow it, for example with `instanceof Error`, before reading properties like `message` or `digest`." Why: non-Error values can be thrown and the prop is not guaranteed to be an Error. Smell: `error.message` used directly in `error.tsx` without a type check. Source: https://nextjs.org/docs/app/api-reference/file-conventions/error#error
- **Correlate server errors by digest, not by message text**: "Errors forwarded from Server Components show a generic message with an identifier." - log the `digest` and search for it server-side. Why: production sanitises server messages so that internals never reach the client. Smell: `if (error.message.includes('timeout'))` branching inside an error boundary. Source: https://nextjs.org/docs/app/api-reference/file-conventions/error#errormessage
- **Prefer retry() over reset() for recovery buttons**: "In most cases, you should use `retry()` instead." - `retry` (stable since 16.3.0) refetches data and re-renders, `reset` only re-renders. Why: a render-only reset repeats the same failing data and loops. Smell: `<button onClick={() => reset()}>Try again</button>` after a fetch failure. Source: https://nextjs.org/docs/app/api-reference/file-conventions/error#reset
- **Do not rely on global CSS or metadata inside global-error**: "`global-error` and the built-in 500 page render their own document and do **not** include your global styles" - inline what the fallback needs and do not export `metadata`. Why: the root layout and its imports are not rendered while the global boundary is active. Smell: `global-error.tsx` using utility classes from `globals.css` or exporting `metadata`. Source: https://nextjs.org/docs/app/api-reference/file-conventions/error#global-error

## Environment variables

- **Put .env files at the project root, never under /src**: "Next.js will load the .env files **only** from the parent folder and **not** from the `/src` folder." Why: files in `src/` are silently ignored and every variable reads as undefined. Smell: `src/.env` or `src/.env.local` added to the repo. Source: https://nextjs.org/docs/app/guides/environment-variables#loading-environment-variables
- **Escape literal dollar signs in env values**: "If you need to use variable with a `$` in the actual value, it needs to be escaped e.g. `\$`." Why: `$VAR` is expanded as a reference to another variable. Smell: a password or connection string containing an unescaped `$` in `.env`. Source: https://nextjs.org/docs/app/guides/environment-variables#referencing-other-variables
- **Treat NEXT_PUBLIC_ values as build-time constants**: "all `NEXT_PUBLIC_` variables will be frozen with the value evaluated at build time" Why: the value is inlined into the client bundle and cannot change at `next start`. Smell: a deploy script that sets `NEXT_PUBLIC_API_URL` at runtime and expects the browser to pick it up. Source: https://nextjs.org/docs/app/guides/environment-variables#bundling-environment-variables-for-the-browser
- **Reference NEXT_PUBLIC_ variables as literal process.env.NAME expressions**: "Note that dynamic lookups will _not_ be inlined" - no computed keys and no destructuring. Why: inlining is a textual replacement that only matches the literal form. Smell: `process.env[\`NEXT_PUBLIC_${key}\`]` or `const { NEXT_PUBLIC_URL } = process.env`. Source: https://nextjs.org/docs/app/guides/environment-variables#bundling-environment-variables-for-the-browser
- **Await connection() before reading runtime server env in a prerendered route**: read non-public variables inside dynamic rendering, after `await connection()`, so the value comes from the running server rather than the build. Why: reads during prerender are frozen into the static output. Smell: `process.env.FEATURE_FLAG` read at the top of a statically rendered page. Source: https://nextjs.org/docs/app/guides/environment-variables#runtime-environment-variables
- **Commit .env.test and keep .env.local out of test runs**: "`.env.local` won't be loaded, as you expect tests to produce the same results for everyone." - `.env.test` is checked in, `.env.test.local` is not. Why: tests must be reproducible across machines and CI. Smell: a test setup that depends on a value only present in `.env.local`, or `.env.test` listed in `.gitignore`. Source: https://nextjs.org/docs/app/guides/environment-variables#test-environment-variables
- **Only use production, development or test as NODE_ENV**: "The allowed values for `NODE_ENV` are `production`, `development` and `test`." Why: other values break env file resolution and framework behaviour. Smell: `NODE_ENV=staging` in a deploy script. Source: https://nextjs.org/docs/app/guides/environment-variables#environment-variable-load-order
- **Do not use the env config key for secrets or runtime values**: "environment variables specified in this way will **always** be included in the JavaScript bundle" - this is the legacy mechanism; prefer `.env` files and `NEXT_PUBLIC_`. Why: the value ships to the browser regardless of its name. Smell: `env: { DATABASE_URL: process.env.DATABASE_URL }` in `next.config`. Source: https://nextjs.org/docs/app/api-reference/config/next-config-js/env

## next.config basics and output

- **Do not name the config next.config.cjs or next.config.cts**: "`next.config` with the `.cjs` or `.cts` extensions are currently **not** supported." Why: Next.js never loads those files, so the config is silently ignored. Smell: a renamed `next.config.cjs` in a diff. Source: https://nextjs.org/docs/app/api-reference/config/next-config-js#ecmascript-modules
- **Copy public and .next/static yourself when using standalone output**: "This minimal server does not copy the `public` or `.next/static` folders by default" Why: the standalone server serves no assets without them. Smell: a Dockerfile that copies only `.next/standalone` and then 404s on every image and chunk. Source: https://nextjs.org/docs/app/api-reference/config/next-config-js/output#automatically-copying-traced-files
- **Set outputFileTracingRoot in monorepos and keep trace patterns narrow**: "Keep patterns as narrow as possible to avoid oversized traces (avoid `**/*` at the repo root)." - files outside the project folder are only included when the root is widened. Why: a missing root drops needed files and a broad include bloats the output. Smell: `outputFileTracingIncludes: { '/**': ['**/*'] }` or a workspace package missing from the standalone image. Source: https://nextjs.org/docs/app/api-reference/config/next-config-js/output#caveats
- **Point distDir at a directory only Next.js owns**: "Next.js takes ownership of `distDir` and will sometimes delete its contents. Point it at a directory used only by Next.js." Why: other tooling output in the same folder gets wiped. Smell: `distDir: 'build'` where `build/` also holds Storybook or docs output. Source: https://nextjs.org/docs/app/api-reference/config/next-config-js/distDir
- **Share one deploymentId across every instance of a deployment**: "all instances for the same deployment should use the same `deploymentId`." - and route requests by deployment, because "Next.js does not read the `?dpl=` query parameter on incoming requests." Why: per-instance values cause false skew detection and a per-deployment value only helps if the load balancer honours it. Smell: `deploymentId: crypto.randomUUID()` evaluated at process start. Source: https://nextjs.org/docs/app/api-reference/config/next-config-js/deploymentId#multi-server-environments
- **Generate a consistent build ID when each environment rebuilds**: "If you are rebuilding for each stage of your environment, you will need to generate a consistent build ID" - use `generateBuildId` with a git SHA or similar. Why: instances with different build IDs serve mismatched chunks. Smell: multiple containers each running their own `next build` with no `generateBuildId`. Source: https://nextjs.org/docs/app/guides/self-hosting#build-cache
- **Keep productionBrowserSourceMaps off unless you mean to publish source**: "During production builds, they are disabled to prevent you leaking your source on the client, unless you specifically opt-in" Why: source maps expose original code to anyone. Smell: `productionBrowserSourceMaps: true` with no upload step to an error tracker and no access restriction. Source: https://nextjs.org/docs/app/api-reference/config/next-config-js/productionBrowserSourceMaps
- **Never enable exposeTestingApiInProductionBuild for a real deployment (experimental)**: "Do not enable this option for a user-facing production deployment." - and set the condition at build time because "Setting the condition only for `next start` does not add the testing API to an existing build." Why: it exposes testing endpoints in the production bundle. Smell: `experimental: { exposeTestingApiInProductionBuild: true }` unconditionally in `next.config`. Source: https://nextjs.org/docs/app/api-reference/config/next-config-js/exposeTestingApiInProductionBuild#reference
- **Check for built-in support before adding a webpack function**: "changes to webpack config are not covered by semver so proceed at your own risk" - CSS, Sass, CSS Modules, MDX and bundle analysis are already covered. Why: custom webpack config breaks on upgrades, opts you out of Turbopack, and runs three times (nodejs server, edge server, client) so it needs `isServer` branching. Smell: a `webpack()` function adding a `css-loader` rule. Source: https://nextjs.org/docs/app/api-reference/config/next-config-js/webpack

## TypeScript

- **Gitignore next-env.d.ts, keep it in include, never edit it**: "Add it to `.gitignore`. If your project already tracks the file, remove it from Git. Do not edit this file manually." - the file still has to appear in `tsconfig.json` `include`. Why: it is regenerated on every dev and build run, so edits are lost and tracked copies churn. Smell: a diff touching `next-env.d.ts`, or a custom `declare module` added to it. Source: https://nextjs.org/docs/app/api-reference/config/typescript#next-envdts
- **Expect CommonJS-only resolution in next.config.ts**: "Module resolution in `next.config.ts` is currently limited to CommonJS." - use `next.config.mts` or the Node native TypeScript resolver for ESM-only dependencies. Why: ESM-only packages fail to load from the config. Smell: `import x from 'esm-only-package'` in `next.config.ts` in a CommonJS project. Source: https://nextjs.org/docs/app/api-reference/config/typescript#type-checking-nextjs-configuration-files
- **Cast non-literal hrefs with as Route under typedRoutes**: "Literal `href` strings are validated, while non-literal `href`s may require a cast with `as Route`." Why: computed strings cannot be checked and will fail the type check, and the generated types only apply when `.next/types/**/*.ts` is in the `include` array. Smell: `<Link href={\`/posts/${slug}\`}>` producing a type error that is fixed with `// @ts-ignore`. Source: https://nextjs.org/docs/app/api-reference/config/typescript#statically-typed-links
- **Use TypeScript 5.1.3+ and @types/react 18.2.8+ for async Server Components**: "ensure you are using TypeScript `5.1.3` or higher and `@types/react` `18.2.8` or higher" Why: older versions report a type error on async components used as JSX. Smell: `{/* @ts-expect-error Async Server Component */}` left in JSX. Source: https://nextjs.org/docs/app/api-reference/config/typescript#with-async-server-components
- **Never set ignoreBuildErrors without a separate type check**: "If disabled, be sure you are running type checks as part of your build or deploy process, otherwise this can be very dangerous." Why: type errors ship to production unnoticed. Smell: `typescript: { ignoreBuildErrors: true }` with no `tsc --noEmit` step in CI. Source: https://nextjs.org/docs/app/api-reference/config/typescript#disabling-typescript-errors-in-production
- **Run next typegen before tsc in CI**: "To ensure `next-env.d.ts` is present before type-checking run `next typegen`." - it loads the config in the production phase, so env vars must be available. Why: a bare `tsc` fails or misses route types when the generated files are absent. Smell: a CI step `tsc --noEmit` with no preceding `next typegen` or `next build`. Source: https://nextjs.org/docs/app/api-reference/cli/next#next-typegen-options

## ESLint and linting

- **Replace next lint with eslint or biome run directly**: "The `next lint` command has been removed. Use Biome or ESLint directly. `next build` no longer runs linting." - a Next 16 breaking change. Why: the script fails and builds no longer lint for you. Smell: `"lint": "next lint"` in `package.json` or a CI job relying on build-time lint. Source: https://nextjs.org/docs/app/guides/upgrading/version-16#next-lint-command
- **Remove the eslint option from next.config**: "the `eslint` option in your Next config file is no longer needed and can be safely removed." Why: removed in Next 16, it no longer has any effect. Smell: `eslint: { ignoreDuringBuilds: true }` in `next.config`. Source: https://nextjs.org/docs/app/api-reference/config/eslint#rules
- **Use @next/eslint-plugin-next directly when react, import or jsx-a11y are already configured**: "Use `@next/eslint-plugin-next` directly if you have any of the following already configured" Why: `eslint-config-next` registers those plugins too and ESLint refuses duplicates. Smell: a "Cannot redefine plugin" error after adding `eslint-config-next` to an existing flat config. Source: https://nextjs.org/docs/app/api-reference/config/eslint#using-the-plugin-directly
- **Upgrade ESLint to 9 or later for eslint-config-next@16**: "`eslint-config-next@16` requires ESLint 9 or later" Why: install fails on peer dependency resolution. Smell: `"eslint": "^8"` beside `"eslint-config-next": "^16"` in `package.json`. Source: https://nextjs.org/docs/app/guides/upgrading/version-16#installation-fails-after-upgrading-eslint

## Building and prerender validation

- **Keep request-time reads inside Suspense under Cache Components**: "With Cache Components, `next build` validates that each App Router page can produce a static shell." - `params`, `cookies()` and `headers()` outside `<Suspense>` fail the build. Why: a request-time read at the top of the page leaves no static shell to prerender. Smell: `const { id } = await params` in a page body with no `<Suspense>` ancestor. Source: https://nextjs.org/docs/app/guides/building#prerender-validation
- **Never deploy a build produced with --debug-prerender**: "Do not deploy builds produced with `--debug-prerender`." Why: it disables minification and keeps debugging source maps. Smell: `next build --debug-prerender` in the `build` script of `package.json`. Source: https://nextjs.org/docs/app/guides/building#debug-prerender-errors
- **Return at least one param from generateStaticParams under Cache Components**: "With Cache Components, it must return at least one param." Why: an empty array is a build error. Smell: `export async function generateStaticParams() { return [] }` as a placeholder. Source: https://nextjs.org/docs/app/guides/building#prerendered-product-pages
- **Keep Math.random, new Date and crypto.randomUUID out of prerendered render paths**: "Synchronous values such as `Math.random()`, `new Date()`, and `crypto.randomUUID()` still produce prerender errors." Why: they make the static shell non-deterministic. Smell: `const nonce = crypto.randomUUID()` in a cached component body. Source: https://nextjs.org/docs/app/guides/building#a-blocking-product-page
- **Treat instant = false as a validation opt-out, not a performance setting**: "It does not change the rendering model or prevent prerendering." - it only disables the instant-navigation and non-empty-shell checks. Why: reviewers mistake it for a fix when the route is still blocking. Smell: `export const instant = false` added to silence a build error without a follow-up ticket. Source: https://nextjs.org/docs/app/guides/building#a-blocking-product-page

## Production checklist

- **Make request-time API usage intentional and wrap it in Suspense**: "Ensure Request-time API usage is intentional and wrap them in `<Suspense>` boundaries where appropriate." Why: one call to `cookies()` turns a whole route dynamic. Smell: `headers()` called in a shared layout that every page inherits. Source: https://nextjs.org/docs/app/guides/production-checklist#routing-and-rendering
- **Do not call Route Handlers from Server Components**: "But do not call Route Handlers from Server Components to avoid an additional server request." - call the data function directly. Why: the component is already on the server, so the HTTP hop is pure overhead. Smell: `fetch('http://localhost:3000/api/posts')` inside a Server Component. Source: https://nextjs.org/docs/app/guides/production-checklist#data-fetching-and-caching
- **Authorise inside every Server Action**: "Verify authentication and authorization inside each action. Do not rely on Proxy or layout or page level checks alone." Why: actions are callable endpoints regardless of which page rendered the form. Smell: `'use server'` function that deletes a record with no session check because the page was already gated. Source: https://nextjs.org/docs/app/guides/production-checklist#security
- **Keep database access in a server-only Data Access Layer**: "Move database access to a `server-only` Data Access Layer" Why: `import 'server-only'` makes accidental client imports a build error. Smell: `db.ts` imported from a `'use client'` component with no `server-only` guard. Source: https://nextjs.org/docs/app/guides/production-checklist#security
- **Prefix only public values with NEXT_PUBLIC_ and gitignore .env files**: "Ensure your `.env.*` files are added to `.gitignore` and only public variables are prefixed with `NEXT_PUBLIC_`." Why: anything with the prefix is inlined into the browser bundle. Smell: `NEXT_PUBLIC_STRIPE_SECRET_KEY` in an env file. Source: https://nextjs.org/docs/app/guides/production-checklist#security
- **Add global-error.tsx for a consistent fallback**: "Add `app/global-error.tsx` to provide consistent, accessible fallback UI" - pair it with `global-not-found` where that (experimental) feature is enabled. Why: root layout failures otherwise show the bare built-in 500 page. Smell: an `app/` directory with `error.tsx` in segments but no `global-error.tsx`. Source: https://nextjs.org/docs/app/guides/production-checklist#ui-and-accessibility
- **Add a Content Security Policy before going live**: "Consider adding a Content Security Policy" Why: it limits the blast radius of injected scripts. Smell: a production app with no CSP header in `proxy.ts` or `headers()` config. Source: https://nextjs.org/docs/app/guides/production-checklist#security
- **Analyse bundles before shipping large dependencies**: "Use the `@next/bundle-analyzer` plugin to analyze the size of your JavaScript bundles and identify large modules and dependencies that might be impacting your application's performance." Why: Next 16 no longer prints size metrics in the build output. Smell: a new charting or date library added to a `'use client'` component with no size check. Source: https://nextjs.org/docs/app/guides/production-checklist#analyzing-bundles

## Deployment, self-hosting and custom server

- **Run a reverse proxy in front of the Node server**: "it's recommended to use a reverse proxy (like nginx) in front of your Next.js server rather than exposing it directly to the internet." Why: TLS, compression and connection handling belong in the proxy. Smell: `next start -p 80` exposed directly on a public host. Source: https://nextjs.org/docs/app/guides/self-hosting#reverse-proxy
- **Install sharp and expect runtime image optimisation**: "The only additional dependency is the `sharp` package, which is required for Image Optimization." - on glibc Linux it may need memory allocator tuning. Why: without sharp the image optimiser cannot run. Smell: a production Dockerfile whose install step prunes `sharp`. Source: https://nextjs.org/docs/app/guides/deploying-to-platforms#minimum-requirements
- **Disable proxy buffering so streaming and Suspense work**: "If you are using nginx or a similar proxy, you will need to configure it to disable buffering to enable streaming." - set `X-Accel-Buffering: no` or the equivalent. Why: a buffering proxy or load balancer holds the whole response until the slowest part resolves, so chunked transfer must pass end to end. Smell: Suspense fallbacks never appear in production though they do locally. Source: https://nextjs.org/docs/app/guides/self-hosting#streaming-and-suspense
- **Use a shared cache handler with cacheMaxMemorySize 0 across multiple instances**: "A store inside the process, such as a `Map`, gives each pod its own copy of the cache again." Why: in-memory caches diverge between pods and serve inconsistent content; the shared handler must also serialise entries, index them by tag, bound its size and handle storage errors. Smell: a custom `cacheHandler` backed by a module-level `Map`. Source: https://nextjs.org/docs/app/guides/self-hosting#configuring-caching
- **Set NEXT_SERVER_ACTIONS_ENCRYPTION_KEY on every instance**: "When running multiple server instances, all instances must use the same encryption key." Why: actions encrypted by one instance fail to decrypt on another. Smell: a horizontally scaled deployment with no shared encryption key in its env. Source: https://nextjs.org/docs/app/guides/self-hosting#server-functions-encryption-key
- **Propagate revalidateTag across instances**: "Other instances continue serving stale content until they independently discover the invalidation." - use a shared cache handler or `refreshTags()` on each instance. Why: by default a tag invalidation only touches the instance that received it. Smell: a multi-instance deployment where editors report stale pages after publishing. Source: https://nextjs.org/docs/app/guides/self-hosting#multi-instance-cache-coordination
- **Shut down with SIGTERM and wait so after() work completes**: "When stopping the server, ensure a graceful shutdown by sending `SIGINT` or `SIGTERM` signals and waiting." Why: `after()` callbacks and in-flight requests are dropped by a hard kill. Smell: a container stop with `kill -9` or a zero-second grace period. Source: https://nextjs.org/docs/app/guides/self-hosting#after
- **Set a keep-alive timeout larger than the downstream proxy's**: "it's important to configure Next's underlying HTTP server with keep-alive timeouts that are _larger_ than the downstream proxy's timeouts." Why: Node otherwise closes connections the proxy still thinks are open and the proxy reports errors. Smell: `next start` behind an ALB with no `--keepAliveTimeout`. Source: https://nextjs.org/docs/app/api-reference/cli/next#configuring-a-timeout-for-downstream-proxies
- **Do not combine a custom server with standalone output**: "it does not trace custom server files" - the two cannot be used together. Why: the standalone bundle will not include `server.js`. Smell: `output: 'standalone'` in a project that starts with `node server.js`. Source: https://nextjs.org/docs/app/guides/custom-server
- **Set response headers before calling handle in a custom server**: "any later `res.setHeader()` call is silently discarded." Why: Next.js has already begun writing the response. Smell: `await handle(req, res); res.setHeader('x-request-id', id)`. Source: https://nextjs.org/docs/app/guides/custom-server

## Static export

- **Mark route handlers force-static in a static export**: "you must explicitly mark the handler as static by adding `export const dynamic = 'force-static'`" Why: otherwise the handler is not prerendered and the export fails. Smell: a `route.ts` under `output: 'export'` with no `dynamic` export. Source: https://nextjs.org/docs/app/guides/static-exports#route-handlers
- **Do not read the incoming request in a static export**: "If you need to read dynamic values from the incoming request, you cannot use a static export." Why: there is no server at request time. Smell: `request.headers` or `searchParams` used in a route handler of an exported site. Source: https://nextjs.org/docs/app/guides/static-exports#route-handlers
- **Guard browser APIs so they run only in the browser**: "you need to safely access these APIs only when running in the browser." - inside `useEffect` or behind a `typeof window` check. Why: prerendering runs in Node where `window` is undefined. Smell: `window.localStorage.getItem()` at the top level of a Client Component. Source: https://nextjs.org/docs/app/guides/static-exports#browser-apis
- **Avoid server-only features under output export**: "Attempting to use any of these features with `next dev` will result in an error" - cookies, rewrites, redirects, headers, Proxy, ISR, Draft Mode, Server Actions, the default image loader and dynamic routes without `generateStaticParams` are all unsupported. Why: they need a running server. Smell: a `'use server'` action or `proxy.ts` added to a project with `output: 'export'`. Source: https://nextjs.org/docs/app/guides/static-exports#unsupported-features
- **Use a custom image loader with static export**: "Note that images are optimized at runtime, not during the build." - the default loader needs a server. Why: exported sites have no optimisation endpoint. Smell: `<Image>` in an exported site with no `images.loader` and no `unoptimized`. Source: https://nextjs.org/docs/app/guides/self-hosting#image-optimization

## Instrumentation and observability

- **Place instrumentation.ts at the project root, outside app**: "The `instrumentation` file should be in the root of your project and not inside the `app` or `pages` directory." - or in `src/`, and rename it if `pageExtensions` adds a suffix. Why: files elsewhere are never loaded. Smell: `app/instrumentation.ts`. Source: https://nextjs.org/docs/app/guides/instrumentation#convention
- **Import side-effect modules inside register, not at the top of the file**: "We recommend importing the file from within the `register` function, rather than at the top of the file." Why: it keeps side effects in one place and avoids unintended consequences from module-level imports. Smell: `import './tracing-setup'` at line one of `instrumentation.ts`. Source: https://nextjs.org/docs/app/guides/instrumentation#importing-files-with-side-effects
- **Branch on NEXT_RUNTIME before importing runtime-specific code**: "Next.js calls `register` in all environments, so it's important to conditionally import any code that doesn't support specific runtimes" Why: Node-only SDKs such as OpenTelemetry `NodeSDK` crash the edge runtime.
