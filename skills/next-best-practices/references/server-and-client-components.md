# Next.js 16 code-review rules: server and client components, rendering, bundling

Extracted 2026-11-10 from the Next.js 16.4.5 App Router documentation (MIT, Vercel, Inc.). One rule per bullet, one source link each. Quotations are short excerpts; the rest is original.

## Choosing between Server and Client Components

- **Default to Server Components and add `'use client'` only where interactivity or browser APIs are needed**: "By default, layouts and pages are Server Components, which lets you fetch data and render parts of your UI on the server, optionally cache the result, and stream it to the client." - keep layouts, pages and data-reading components on the server and layer Client Components in for state, events and browser APIs. Why: server rendering keeps data access close to its source and sends less JavaScript. Smell: `'use client'` at the top of a `page.tsx` or `layout.tsx` whose only job is to fetch data and render markup. Source: https://nextjs.org/docs/app/getting-started/server-and-client-components
- **Keep secrets and data access in Server Components**: "Use API keys, tokens, and other secrets without exposing them to the client." - read `process.env` secrets, databases and internal services from Server Components only. Why: anything a Client Component touches is shipped to the browser. Smell: `process.env.API_KEY` read inside a `'use client'` file. Source: https://nextjs.org/docs/app/getting-started/server-and-client-components#when-to-use-server-and-client-components
- **Put `'use client'` on the leaf interactive component, not on a whole layout**: "add `'use client'` at the top of the files that define your interactive components instead of marking large parts of your UI as Client Components." - a layout with one search box should stay a Server Component and import a client `Search`. Why: every module a client entry imports joins the client bundle. Smell: `'use client'` added to `layout.tsx` because the nav contains one interactive widget. Source: https://nextjs.org/docs/app/getting-started/server-and-client-components#reducing-js-bundle-size
- **Treat everything a `'use client'` file imports or renders as part of the client bundle**: "Once a file is marked with `"use client"`, all of its imports and the components it directly renders are included in the client bundle." - the directive marks a module graph boundary, not a single component. Why: the bundler follows imports from the entry, so one directive can pull in a large graph. Smell: a `'use client'` component importing `@/lib/db` or a Node-only helper. Source: https://nextjs.org/docs/app/getting-started/server-and-client-components#using-client-components
- **Pass only serialisable props to Client Components**: "Props passed to Client Components need to be serializable by React." - plain objects, arrays, strings, numbers, dates, promises and React elements cross; class instances and ordinary functions do not. Why: props are encoded into the RSC payload and sent over the network. Smell: a Server Component passing an ORM model instance with methods, or a callback, to a `'use client'` component. Source: https://nextjs.org/docs/app/getting-started/server-and-client-components#passing-data-from-server-to-client-components
- **Nest server-rendered UI inside a Client Component through `children` or props rather than imports**: "You can pass Server Components as a prop to a Client Component." - a client `Modal` receives `<Cart />` as a child; it never imports it. Why: passing rendered output keeps the Server Component's code and data access on the server. Smell: a `'use client'` wrapper importing an async data-fetching component directly. Source: https://nextjs.org/docs/app/getting-started/server-and-client-components#interleaving-server-and-client-components
- **Create context providers in a Client Component that accepts `children`**: "React context is not supported in Server Components." - put `createContext` and the provider in a `'use client'` file and render it from a layout. Why: context is a client-side mechanism. Smell: `createContext` or `<X.Provider>` in a file without `'use client'`. Source: https://nextjs.org/docs/app/getting-started/server-and-client-components#context-providers
- **Render providers as deep in the tree as possible**: "You should render providers as deep as possible in the tree" - wrap `{children}` inside `<body>`, not the whole `<html>` element. Why: narrower provider scope lets Next.js optimise the static parts of the Server Component tree. Smell: `<ThemeProvider>` wrapping `<html>` in the root layout. Source: https://nextjs.org/docs/app/getting-started/server-and-client-components#context-providers
- **Wrap third-party client-only components in your own `'use client'` file before using them from a Server Component**: "wrap third-party components that rely on client-only features in your own Client Components" - re-export the package component from a local file that declares the directive. Why: packages that use hooks without declaring `'use client'` error when imported straight into a Server Component. Smell: a page importing a `useState`-based npm component with no local wrapper. Source: https://nextjs.org/docs/app/getting-started/server-and-client-components#third-party-components
- **Mark server-only modules with `import 'server-only'`**: "To prevent accidental usage in Client Components, you can use the `server-only` package." - add the import to any module that reads secrets or server resources. Why: importing it from a Client Component becomes a build-time error instead of a silent runtime failure. Smell: `lib/data.ts` reading `process.env.API_KEY` with no `server-only` import, re-exported from a barrel that client files import. Source: https://nextjs.org/docs/app/getting-started/server-and-client-components#preventing-environment-poisoning
- **Never rely on an unprefixed environment variable in client code**: "If variables are not prefixed, Next.js replaces them with an empty string." - only `NEXT_PUBLIC_` variables reach the browser; everything else is blanked. Why: server-only functions imported into the client run but fail quietly. Smell: `process.env.STRIPE_SECRET` referenced in a `'use client'` component. Source: https://nextjs.org/docs/app/getting-started/server-and-client-components#preventing-environment-poisoning

## Directives: placement and requirements

- **Place `'use client'` on the first line of the file, before imports, never inline**: "The `'use client'` directive must appear at the top of a file, before any imports." - it applies to the whole module and cannot be scoped to a function. Why: the module is bundled and shipped to the browser as a unit. Smell: the directive after an import statement or inside a component body. Source: https://nextjs.org/docs/app/api-reference/directives#where-to-place-a-directive
- **Declare `'use server'` and `'use cache'` in server modules, not in a `'use client'` module**: "Declare `'use server'` and `'use cache'` in server modules, not in a `'use client'` module." - Client Components import a reference from a server file instead. Why: the directives must be compiled in the server graph. Smell: a `'use client'` file that also contains an inline `'use server'` function. Source: https://nextjs.org/docs/app/api-reference/directives#where-to-place-a-directive
- **Make every export covered by a file-level `'use server'` or `'use cache'` async**: "Every exported function covered by a file-level `'use server'` or `'use cache'` directive must be `async`." - synchronous helpers do not belong in those files. Why: each export becomes a Server Function or cache entry with a serialised async contract. Smell: `export function formatPrice()` in an `actions.ts` that starts with `'use server'`. Source: https://nextjs.org/docs/app/api-reference/directives#where-to-place-a-directive
- **Do not pass ordinary functions across the client boundary; pass Server Functions as references**: "Ordinary functions, such as event handlers, cannot cross, but Server Functions can cross as references." - handlers live in the Client Component; mutations arrive as `'use server'` references. Why: functions are not serialisable, Server Function references are. Smell: `<Button onClick={handleClick} />` rendered from a Server Component. Source: https://nextjs.org/docs/app/api-reference/directives#what-each-directive-requires
- **Keep `'use cache'` code free of request-time APIs (requires `cacheComponents`)**: "Cached code cannot read request-time APIs like `cookies()`, `headers()`, or `searchParams` directly." - read request values outside the cached scope and pass them in. Why: cache entries are keyed on inputs and cannot vary on hidden request state. Smell: `await cookies()` inside a function whose first line is `'use cache'`. Source: https://nextjs.org/docs/app/api-reference/directives#what-each-directive-requires
- **Make `generateMetadata` and `generateStaticParams` async when the page file has a top-level `'use cache'` (requires `cacheComponents`)**: "With `'use cache'` at the top of a page or layout file, exported functions such as `generateMetadata` and `generateStaticParams` must be `async`." - the file-level directive covers them too. Why: every covered export is cached as an async function. Smell: `export function generateMetadata()` in a page that begins with `'use cache'`. Source: https://nextjs.org/docs/app/api-reference/directives#what-each-directive-requires
- **Cache the expensive function, not the whole page, when one request does the work (requires `cacheComponents`)**: "When one data request performs the expensive work, cache that function instead of the page." - placement decides the scope of the cache entry. Why: a page-level directive caches everything it imports, including parts that should stay fresh. Smell: `'use cache'` at the top of `page.tsx` to speed up one slow query. Source: https://nextjs.org/docs/app/api-reference/directives#placement-decides-what-you-cache

## The `use client` directive

- **Add `'use client'` only to the files whose components Server Components render directly**: "You only need to add it to the files whose components you want to render directly within Server Components." - modules imported from that entry are already client modules. Why: the directive defines entry points, not a per-component flag. Smell: a diff adding the directive to a dozen leaf components that are only ever imported from an existing client entry. Source: https://nextjs.org/docs/app/api-reference/directives/use-client

## The `use server` directive and Server Functions

- **Put Server Functions called from Client Components in a dedicated `'use server'` file**: "To use Server Functions in Client Components you need to create your Server Functions in a dedicated file using the `use server` directive at the top of the file." - import them into the Client Component from there. Why: a Client Component cannot define a Server Function inline. Smell: an inline `'use server'` function declared inside a `'use client'` component. Source: https://nextjs.org/docs/app/api-reference/directives/use-server#using-server-functions-in-a-client-component
- **Authenticate and authorise inside every Server Function before sensitive work**: "Always authenticate and authorize users before performing sensitive server-side operations." - every exported Server Function is a public endpoint. Why: anyone can call it with crafted arguments regardless of UI. Smell: `export async function deleteUser(id)` going straight to the database with no session check. Source: https://nextjs.org/docs/app/api-reference/directives/use-server#authentication-and-authorization
- **Read identity from cookies or headers, never from Server Function parameters**: "Read authentication from cookies or headers rather than accepting tokens as function parameters." - call your `auth()` helper inside the function. Why: parameters come from the client and can be forged. Smell: `createPost(userId, data)` or `updateProfile(token, data)` signatures. Source: https://nextjs.org/docs/app/api-reference/directives/use-server#authentication-and-authorization
- **Return only the fields the UI needs from a Server Function**: "Only return data the UI needs, not raw database records." - map to a DTO before returning. Why: return values are serialised and sent to the browser. Smell: `return user` after `db.user.findUnique` with a password hash or internal fields on the row. Source: https://nextjs.org/docs/app/api-reference/directives/use-server#return-values
- **Validate inputs and constrain return types in a data access layer**: "Design your data access functions as secure primitives: validate inputs, check authentication and authorization, and constrain return types to only what the caller needs." - Server Functions delegate to these primitives. Why: guarantees live in one place and apply to every caller. Smell: a Server Function trusting `formData.get('id')` with no validation. Source: https://nextjs.org/docs/app/api-reference/directives/use-server#security-considerations

## The server and client boundary

- **Expect a Client Component to render on the server too, with matching output**: "Hydration made the initial HTML interactive and required the component to produce matching output on the server and in the browser." - `'use client'` means "also runs in the browser", not "only in the browser". Why: hydration compares server HTML with the client render. Smell: `Date.now()`, `Math.random()` or `window.innerWidth` read during render in a Client Component. Source: https://nextjs.org/docs/app/guides/server-and-client-boundary
- **Do not gate crawlable content behind interaction or events**: "Content gated behind user interaction or an event does not appear in the HTML available to a crawler that does not run JavaScript." - render indexable text in the initial HTML. Why: HTML-only crawlers never execute JavaScript. Smell: product description rendered only when `isExpanded` state is true. Source: https://nextjs.org/docs/app/guides/server-and-client-boundary#rendering-environments
- **Read server data during a Server Component's render instead of adding an API route for the client to fetch**: "The component reads these resources during its own render, without an API route that exposes the data to the client first." - the page awaits the database directly. Why: no extra endpoint, no client waterfall, no exposed data surface. Smell: a new `app/api/posts/route.ts` plus `useEffect(() => fetch('/api/posts'))` for data a page could read directly. Source: https://nextjs.org/docs/app/guides/server-and-client-boundary#how-data-enters-the-tree
- **Pass only what a Client Component needs, because props end up in the HTML**: "Props are serialized and sent to the browser." - pick fields rather than forwarding whole records. Why: Server Components can read secrets and private rows that must not leak. Smell: `<Avatar user={user} />` where `user` is the full database row including email and hashes. Source: https://nextjs.org/docs/app/guides/server-and-client-boundary#how-data-enters-the-tree
- **Stream server data to a Client Component by passing the pending promise and reading it with `use`**: "To stream server-fetched data into a Client Component, start the request in a Server Component and pass the pending promise as a prop." - the nearest Suspense boundary shows a fallback until it resolves. Why: the request starts before the client runs, so no mount-time refetch is needed. Smell: a `useEffect` fetch on mount for data the parent Server Component already had. Source: https://nextjs.org/docs/app/guides/server-and-client-boundary#how-data-enters-the-tree
- **Never mutate Server Component DOM nodes directly from client code**: "Mutating Server Component DOM nodes directly can put the DOM out of sync with React's component tree." - re-render on the server and let React reconcile the new payload. Why: React owns the tree and will overwrite or mismatch manual edits. Smell: `document.querySelector('#server-list').innerHTML = ...` in a client effect. Source: https://nextjs.org/docs/app/guides/server-and-client-boundary#state-and-interactivity
- **Use native HTML behaviour before adding a Client Component**: "A button or form does not require a Client Component when the browser provides all the required behavior." - `<details>`, `<form action={serverFn}>` and `<video controls>` work without JavaScript. Why: fewer client bundles and working UI before hydration. Smell: `'use client'` plus `useState` for a collapsible that `<details>` already handles. Source: https://nextjs.org/docs/app/guides/server-and-client-boundary#state-and-interactivity
- **Never pass a plain function from a Server Component to a Client Component**: "Passing a function as a prop from a Server Component to a Client Component throws." - only a `'use server'` function crosses, as a reference. Why: the boundary serialises props and functions cannot be serialised. Smell: `onClose={() => ...}` or a formatter function passed from `page.tsx` to a client component. Source: https://nextjs.org/docs/app/guides/server-and-client-boundary#crossing-the-boundary
- **Name Server Function props `action` or `*Action`**: "The TypeScript plugin allows a Client Component prop typed as a function when its name is `action` or ends in `Action`." - other function-typed props are flagged. Why: a Server Function is indistinguishable from a plain function by type alone. Smell: a client prop `onSubmit: (data) => Promise<void>` receiving a Server Function. Source: https://nextjs.org/docs/app/guides/server-and-client-boundary#crossing-the-boundary
- **Expose compound-component parts as named exports when they cross the boundary**: "To use its pieces from a Server Component, expose them as named exports instead of static properties." - `Menu.Item` on a client module is `undefined` on the server side. Why: a Server Component importing a client module receives a reference, not the function with its static members. Smell: `<Menu.Item>` rendered in a Server Component where `Menu` is a `'use client'` module. Source: https://nextjs.org/docs/app/guides/server-and-client-boundary#crossing-the-boundary
- **Wrap shared components in a client wrapper instead of editing them**: "To leave a shared component unchanged, create a Client Component wrapper that imports it and place the directive on the wrapper." - keep the boundary near application code. Why: avoids adding the directive to every shared hook-using component. Smell: a diff adding `'use client'` to a design-system package component to make one page work. Source: https://nextjs.org/docs/app/guides/server-and-client-boundary#crossing-the-boundary

## Rendering philosophy

- **Decide static versus dynamic per component, not per route**: "the boundary between static and dynamic is at the component level, not the route level." - a static shell plus streamed dynamic sections replaces an all-or-nothing route setting. Why: one dynamic element should not force a whole page to render per request. Smell: `export const dynamic = 'force-dynamic'` added to a page because one widget reads cookies. Source: https://nextjs.org/docs/app/guides/rendering-philosophy#static-and-dynamic-as-a-spectrum
- **Cache a function and revalidate a tag rather than caching a route and redeploying (requires `cacheComponents`)**: "Cache a function with `use cache`, not a route." - an expensive query is cached independently of the page around it. Why: granular caching lets content update on demand without a rebuild. Smell: a full-page `revalidate` export or rebuild-on-change workflow for a single slow query. Source: https://nextjs.org/docs/app/guides/rendering-philosophy#what-this-enables

## Streaming and Suspense

- **Wrap each independent async component in its own `<Suspense>` boundary**: "When multiple components perform async work (fetching data, reading from a database), wrap each one in its own `<Suspense>` boundary." - siblings stream in whatever order they resolve. Why: boundaries do not block each other; one shared boundary waits for the slowest. Smell: three awaited fetches at the top of a page followed by all the markup. Source: https://nextjs.org/docs/app/guides/streaming#parallel-streaming-with-sibling-boundaries
- **Push `params`, `searchParams`, `cookies()`, `headers()` and data fetches down to the component that needs them**: "If you `await` any of these at the top of a layout or page, everything below that point becomes dynamic and cannot be prerendered as part of the static shell." - pass the promise down and resolve it inside a boundary. Why: the await point decides where the static shell ends. Smell: `const { id } = await params` at the top of a page when only one child uses it. Source: https://nextjs.org/docs/app/guides/streaming#push-dynamic-access-down
- **Prefer explicit `<Suspense>` near the dynamic access over a high-level `loading.js`**: "Prefer explicit `<Suspense>` boundaries close to the dynamic access." - `loading.js` is a valid boundary but turns the whole page into a skeleton. Why: the prerenderer stops at the nearest boundary; a high one loses granular streaming. Smell: a route with only `loading.tsx` and no inner boundaries around slow sections. Source: https://nextjs.org/docs/app/guides/streaming#when-to-use-loadingjs-vs-suspense
- **Do not add a Suspense boundary you do not need**: "Adding a boundary means accepting that, so don't add one you don't need." - React may fall back to any boundary under load. Why: unnecessary boundaries can hide content and hurt LCP. Smell: `<Suspense>` around a synchronous, static component. Source: https://nextjs.org/docs/app/guides/streaming#lcp-largest-contentful-paint
- **Keep LCP elements outside or above Suspense boundaries**: "Keep LCP elements outside or above Suspense boundaries so they render as part of the static shell." - hero image, main heading and product photo belong in the shell. Why: content inside a boundary cannot paint until the swap script runs. Smell: the page `<h1>` or hero image inside the same boundary as a data fetch. Source: https://nextjs.org/docs/app/guides/streaming#lcp-largest-contentful-paint
- **Size skeleton fallbacks to match the content they replace**: "Design skeleton fallbacks that match the dimensions of the content they represent." - reserve space with fixed or min-height containers. Why: a size mismatch causes layout shift when content swaps in. Smell: `fallback={<p>Loading...</p>}` for a grid of cards. Source: https://nextjs.org/docs/app/guides/streaming#cls-cumulative-layout-shift
- **Call `notFound()` before any await or Suspense boundary when the 404 status matters**: "If a `notFound()` fires mid-stream, Next.js cannot go back and change the status to 404." - a mid-stream not-found becomes a `noindex` meta tag on a 200 response. Why: headers and status are sent with the first chunk. Smell: `notFound()` called inside a component rendered under `<Suspense>` or after a `loading.tsx` kicks in. Source: https://nextjs.org/docs/app/guides/streaming#status-codes
- **Redirect before streaming starts, or in `proxy`, when an HTTP redirect is required**: "a `redirect()` mid-stream becomes a client-side redirect rather than an HTTP redirect header." - `proxy` and `next.config.js` redirects run before rendering. Why: once the body streams the response cannot carry a 307. Smell: an auth `redirect('/login')` deep inside a suspended component where a real HTTP redirect was expected. Source: https://nextjs.org/docs/app/guides/streaming#status-codes
- **Make any data the prerendered shell needs available at request time too (requires `cacheComponents`)**: "Make sure any data the shell relies on is also available at request time." - HTML-limited bots re-render the shell dynamically. Why: a page that works for people can fail for a crawler. Smell: the shell reading a build-only environment variable or a file that is absent in the runtime image. Source: https://nextjs.org/docs/app/guides/streaming#cache-components

## Preventing flash before hydration

- **Do not format locale-dependent dates in a Client Component's render without a mismatch strategy**: "React detects the mismatch, throws a hydration error, and the user sees a flash." - the server formats with its own locale and time zone. Why: hydration compares server and client text. Smell: `'use client'` plus `new Date(date).toLocaleDateString()` directly in JSX. Source: https://nextjs.org/docs/app/guides/preventing-flash-before-hydration#the-problem
- **Correct client-only values with an inline script that runs during HTML parsing**: "Using an inline script that runs synchronously as the browser parses the HTML, you can update the DOM before the first paint." - the script sets `textContent` or a `data-theme` attribute before React loads. Why: both effects and client re-rendering happen after the first paint. Smell: a `mounted` state flag that renders a placeholder until `useEffect` runs. Source: https://nextjs.org/docs/app/guides/preventing-flash-before-hydration
- **Do not use `useEffect` to patch server-rendered values**: "The user sees the server value first, then the correction." - effects run after hydration and paint, and a state update can reactivate parent Suspense boundaries. Why: the flash is exactly what you are trying to avoid. Smell: `useEffect(() => setTheme(localStorage.getItem('theme')))` in a theme provider. Source: https://nextjs.org/docs/app/guides/preventing-flash-before-hydration#why-not-useeffect
- **Add `suppressHydrationWarning` to the element an inline script modifies**: "React keeps whatever is in the DOM and discards the client's output for that element." - without it React treats the change as a hydration error and client-renders the boundary. Why: recovery discards other inline-script corrections in the same boundary. Smell: a `<script dangerouslySetInnerHTML>` updating a `<p id="date">` that lacks the attribute. Source: https://nextjs.org/docs/app/guides/preventing-flash-before-hydration#understanding-suppresshydrationwarning
- **Make an inline-script date component a Client Component so soft navigations format correctly**: "Scripts inserted via DOM updates don't execute in the browser." - on `<Link>` navigation the script never runs, so the component itself must format in the browser. Why: the RSC payload inserts markup without executing scripts. Smell: an inline-script date in a Server Component that shows the server locale after client navigation. Source: https://nextjs.org/docs/app/guides/preventing-flash-before-hydration#extracting-a-reusable-component
- **Use `<time dateTime>` for dates whose visible text is rewritten on the client**: "Use a `<time>` element with a `dateTime` attribute so search engines and screen readers can parse the ISO string regardless of the displayed text." - keep the machine-readable value in the attribute. Why: assistive technology and crawlers need a stable value. Smell: a `<span>` holding a locale-formatted date with no ISO source. Source: https://nextjs.org/docs/app/guides/preventing-flash-before-hydration#extracting-a-reusable-component
- **Add a nonce when a strict CSP blocks inline scripts**: "Inline scripts with `dangerouslySetInnerHTML` are blocked by strict Content Security Policies that don't allow `'unsafe-inline'`." - the script must carry the request nonce. Why: otherwise the correction silently never runs. Smell: a new inline `<script>` in an app whose `proxy` sets a strict `Content-Security-Policy`. Source: https://nextjs.org/docs/app/guides/preventing-flash-before-hydration#extracting-a-reusable-component
- **Read a theme cookie in the inline script, not with `cookies()` in the root layout**: "But reading it in the root layout opts the entire app out of static prerendering" - under Cache Components it also blocks every segment under the layout. Why: the root layout wraps every route. Smell: `const theme = (await cookies()).get('theme')` in `app/layout.tsx`. Source: https://nextjs.org/docs/app/guides/preventing-flash-before-hydration#storing-the-theme-in-a-cookie
- **Initialise React state lazily from the same source the inline script reads**: "Use a lazy state initializer that reads from the same source as the script." - guard with `typeof window === 'undefined'` on the server. Why: React's initial state must match the DOM the script produced. Smell: `useState(DEFAULT)` followed by an effect that reads `localStorage`. Source: https://nextjs.org/docs/app/guides/preventing-flash-before-hydration#syncing-with-react-state

## Interactive apps: transitions, optimistic UI and pending state

- **Split awaited reads into separate components, each with its own promise and boundary**: "When both are awaited at the top of the page component, the whole page blocks until the slowest read resolves." - the page returns its shell synchronously. Why: sequential awaits delay everything, including unrelated UI. Smell: `const task = await getTask(id); const comments = await getComments(id)` at the top of a page. Source: https://nextjs.org/docs/app/guides/interactive-apps#step-1-stream-slow-data-with-suspense
- **Wrap a Server Function call in `useTransition` with `useOptimistic` instead of calling it bare from a handler**: "If you click the dot, the Server Function runs, but the button keeps rendering the old `priority` prop until the next server render arrives." - the optimistic value renders until the transition ends. Why: a bare call gives no feedback and reads stale props. Smell: `onClick={() => updatePriority(id)}` with no transition or optimistic state. Source: https://nextjs.org/docs/app/guides/interactive-apps#step-2-respond-instantly-to-a-toggle
- **Run `router.push()` inside a transition and show local pending state**: "With this version, `router.push()` starts the navigation, but there's no local pending state." - the chip stays on the old URL value with no feedback. Why: the server render for the new search params takes time. Smell: filter chips calling `router.push` with no `isPending` or optimistic selection. Source: https://nextjs.org/docs/app/guides/interactive-apps#step-3-filter-with-pending-feedback
- **Expose pending state through a `data-pending` attribute for ancestors to style**: "The `data-pending` attribute on the `ChipGroup` root element lets ancestor components react through CSS without any coordination." - the ancestor uses `:has()` to dim itself. Why: no lifting of state or threading callbacks. Smell: an `isPending` boolean threaded through three props so a parent can fade. Source: https://nextjs.org/docs/app/guides/interactive-apps#handle-pending-feedback-internally
- **Track only pending items in `useOptimistic([])` next to the server-rendered list**: "a client component tracks only the pending comments using `useOptimistic([])` with an empty initial array." - the pending list resets when the server render arrives. Why: copying the whole list into client state creates two sources of truth. Smell: `useState(initialComments)` mirroring the server list and appending locally. Source: https://nextjs.org/docs/app/guides/interactive-apps#step-4-add-comments-with-instant-feedback
- **Inside a transition, use `useOptimistic` setters or direct DOM calls for same-frame updates, not `useState`**: "Inside a transition, `useState` setters are deferred until the transition completes, but `useOptimistic` setters and direct DOM calls like `formRef.reset()` apply on the current frame." - clear the form with a ref reset. Why: a deferred state update makes the input look stuck. Smell: `setText('')` inside the form action expecting an instant clear. ## Request lifecycle functions: `after`, `connection`, `io`

- **Use `after` for side effects that should not block the response**: "This is useful for tasks and other side effects that should not block the response, such as logging and analytics." - schedule the callback and return. Why: the user waits for every awaited call before `return`. Smell: `await analytics.track()` placed before the `return` of a Server Function. Source: https://nextjs.org/docs/app/api-reference/functions/after
- **Expect `after` to run even when the response failed, redirected or returned not found**: "`after` will be executed even if the response didn't complete successfully." - check the outcome inside the callback if it matters. Why: the callback is tied to response completion, not success. Smell: an `after` callback sending an "order placed" email without checking the write succeeded. Source: https://nextjs.org/docs/app/api-reference/functions/after#good-to-know

- **Call `connection()` before synchronous drivers or `Math.random()` and `new Date()` that must be per request**: "call `connection()` before your query to exclude them from prerendering" - without a request-time API the prerenderer would capture the value at build. - **Replace `unstable_noStore` with `connection()`**: "`connection` replaces `unstable_noStore` to better align with the future of Next.js." - the old API is superseded. Why: aligns with the current rendering model. Smell: a new `unstable_noStore()` call in a diff. Source: https://nextjs.org/docs/app/api-reference/functions/connection#good-to-know
- **Prefer `io()` over `connection()` under Cache Components (requires `cacheComponents`, added in 16.3)**: "Prefer `io()` over `connection()`, and reach for `connection()` only when you need to wait for a real user request." - `io()` suspends like any async function and can be cached and prefetched. - **Import custom polyfills in `instrumentation-client.js`**: "To include polyfills, you can import them into the `instrumentation-client.js` file." - the App Router entry for client-side setup. Why: it runs before the app code on every page. Smell: a polyfill import in the root layout or in a component. Source: https://nextjs.org/docs/architecture/supported-browsers#in-app-router
- **Do not add `fetch`, `URL` or `Object.assign` polyfills yourself**: "If any of your dependencies include these polyfills, they’ll be eliminated automatically from the production build to avoid duplication." - Next.js injects them only for browsers that need them. Why: duplication adds bytes with no benefit. Smell: `import 'whatwg-fetch'` in application code. Source: https://nextjs.org/docs/architecture/supported-browsers#polyfills
- **Give every page a unique, descriptive title**: "For the most accessible user experience, ensure that each page in your application has a unique and descriptive title." - the route announcer reads `document.title`, then `<h1>`, then the pathname. Why: screen readers announce the title on client-side transitions. Smell: a new route with no `metadata.title` and no `<h1>`. Source: https://nextjs.org/docs/architecture/accessibility#route-announcements
- **Keep the `eslint-plugin-jsx-a11y` rules enabled**: "By default, Next.js includes `eslint-plugin-jsx-a11y` to help catch accessibility issues early" - it flags missing alt text, bad `aria-*` and wrong roles. Why: early detection of accessibility defects. Smell: an ESLint config that disables `jsx-a11y` rules to clear warnings. Source: https://nextjs.org/docs/architecture/accessibility#linting

## Glossary rules

- **Use React `cache()` for non-`fetch` work that is called more than once per render**: "For non-`fetch` operations, use the React `cache` function." - `fetch` GET requests are memoised automatically across layouts, pages and `generateMetadata`, but not in Route Handlers. Why: duplicate database calls in a single render waste time. Smell: the same ORM query called in `layout.tsx` and `page.tsx` without `cache()`. Source: https://nextjs.org/docs/app/glossary#memoization
- **Write `proxy.js`, not `middleware.js` (renamed in 16)**: "Formerly known as Middleware." - the file runs on the server before the request completes. Why: the convention has a new name. Smell: a new `middleware.ts` added to the project root. Source: https://nextjs.org/docs/app/glossary#proxy
