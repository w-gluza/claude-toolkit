# Next.js 16 code-review rules: metadata, images, fonts, scripts, styling

Extracted 2026-11-10 from the Next.js 16.4.5 App Router documentation (MIT, Vercel, Inc.). One rule per bullet, one source link each. Quotations are short excerpts; the rest is original.

## CSS and styling

- **Keep global stylesheets for truly global CSS and import them once in the root layout**: "this currently does not remove stylesheets as you navigate between routes which can lead to conflicts" - a global stylesheet imported from a nested page or component stays loaded after navigation, so only base styles belong in global CSS and they belong at the root. Why: Next.js uses React's built-in stylesheet support with Suspense, which never unloads a stylesheet. Smell: `import './dashboard.css'` (not a `.module.css`) inside `app/dashboard/page.tsx`. Source: https://nextjs.org/docs/app/getting-started/css#global-css
- **Use Tailwind for most styling and CSS Modules for the rest**: "Use CSS Modules for component-specific styles when Tailwind utilities aren't sufficient." - reach for a scoped module when utilities run out, not for a second global stylesheet. Why: modules generate unique class names, so the same class name in two files cannot collide. Smell: a component-specific stylesheet with plain `.card` selectors imported as a global file. Source: https://nextjs.org/docs/app/getting-started/css#recommendations
- **Use the Tailwind v4 PostCSS setup unless very old browsers are a requirement**: "If you need broader browser support for very old browsers, see the Tailwind CSS v3 setup instructions" - new projects use `@tailwindcss/postcss` and `@import 'tailwindcss'` in the global stylesheet. Why: v3 exists in the docs only as a compatibility path. Smell: a new `tailwind.config.js` with `content` globs and `@tailwind base;` directives in a fresh project. Source: https://nextjs.org/docs/app/getting-started/css#tailwind-css
- **Contain CSS imports in one entry file where possible**: "Try to contain CSS imports to a single JavaScript or TypeScript entry file" - stylesheet order follows import order, so scattered imports make the final cascade unpredictable. Why: production chunking merges stylesheets based on where they are imported. Smell: the same global stylesheet imported from several layouts and components. Source: https://nextjs.org/docs/app/getting-started/css#recommendations
- **Do not let a linter auto-sort imports in files that import CSS**: "Turn off linters or formatters that auto-sort imports" - an import sorter can silently reorder stylesheets and change which rule wins. Why: CSS order depends on import order in the source. Smell: `sort-imports` or `simple-import-sort` enabled on files that import `.css` or `.module.css`. Source: https://nextjs.org/docs/app/getting-started/css#recommendations
- **Verify CSS order against a production build, not the dev server**: "CSS ordering can behave differently in development, always ensure to check the build (`next build`) to verify the final CSS order." - a cascade that looks right in `next dev` may not survive chunking. Why: production concatenates and splits stylesheets differently from development. Smell: a PR that fixes an override by reordering imports with no note that `next build` was checked. Source: https://nextjs.org/docs/app/getting-started/css#development-vs-production

## CSS-in-JS

- **Use CSS-in-JS only inside Client Components with a style registry**: "Configuring CSS-in-JS is a three-step opt-in process that involves:" - a registry collects rules, `useServerInsertedHTML` flushes them, and a Client Component wraps the tree during server rendering. Why: Server Components and streaming need the library to emit styles before the content that uses them. Smell: `styled.div` or `css` template literals used in a file without `'use client'`, or no registry component in the root layout. Source: https://nextjs.org/docs/app/guides/css-in-js#configuring-css-in-js-in-app
- **Put the style registry in a Client Component at the top of the tree**: "We specifically use a Client Component at the top level of the tree for the style registry because it's more efficient to extract CSS rules this way." - the registry should wrap `children` in the root layout, not sit deeper or in a Server Component. Why: this avoids regenerating styles on later server renders and keeps them out of the Server Component payload. Smell: `StyledComponentsRegistry` wrapped around a single page instead of the root layout `children`. Source: https://nextjs.org/docs/app/guides/css-in-js#styled-components
- **Enable the styled-components compiler option before using styled-components**: "First, enable styled-components in `next.config.js`." - `compiler.styledComponents: true` must be set alongside the registry. Why: without the compiler option server and client class names differ and hydration breaks. Smell: `styled-components` added to `package.json` with no `compiler` change in `next.config`. Source: https://nextjs.org/docs/app/guides/css-in-js#styled-components

## Sass

- **Use `.module.scss` for component-level Sass**: "You can use component-level Sass via CSS Modules and the `.module.scss` or `.module.sass` extension." - Sass follows the same global versus module split as plain CSS. Why: a non-module `.scss` file imported into a component is global and leaks across routes. Smell: `import './card.scss'` inside a component instead of `card.module.scss`. Source: https://nextjs.org/docs/app/guides/sass
- **Do not rely on custom Sass functions under Turbopack**: "The `functions` property for defining custom Sass functions is only supported with webpack." - `sassOptions.functions` is ignored when Turbopack builds the project. Why: Turbopack cannot execute JavaScript functions passed through config. Smell: `sassOptions: { functions: { ... } }` in a project that runs `next dev` or `next build` with Turbopack. Source: https://nextjs.org/docs/app/api-reference/config/next-config-js/sassOptions

## CSS build options

- **Leave `cssChunking` at its default unless there is a measured reason (experimental)**: "For most applications, the default (`true`) is the right choice in either bundler" - merging CSS reduces requests and is correct for almost every project. Why: the alternatives trade more requests for ordering guarantees or finer sharing. Smell: `experimental.cssChunking: false` added with no linked ordering bug or performance report. Source: https://nextjs.org/docs/app/api-reference/config/next-config-js/cssChunking#choosing-a-strategy
- **Use `cssChunking: 'strict'` on webpack when one stylesheet depends on another (experimental)**: "if `b.css` depends on `a.css`, `'strict'` prevents the merge and loads them in import order, at the cost of more chunks and requests." - the default merges files in any order and assumes no dependency between them. Why: an override that relies on load order can flip under merging. Smell: two stylesheets imported in different orders in different files, with a cascade bug blamed on "random" ordering. Source: https://nextjs.org/docs/app/api-reference/config/next-config-js/cssChunking#choosing-a-strategy
- **Use `cssChunking: 'graph'` only on Turbopack and only to tune sharing (experimental)**: "Switch to `graph` to tune how CSS is shared across routes, cutting the unused CSS a route downloads at the cost of more requests" - `'graph'` is Turbopack-only, while `false` and `'strict'` are webpack-only. Why: each strategy is implemented for one bundler. Smell: `cssChunking: 'graph'` in a project built with webpack, or `'strict'` under Turbopack. Source: https://nextjs.org/docs/app/api-reference/config/next-config-js/cssChunking#options
- **Fix unused CSS at the source before tuning chunking**: "which you fix in your source by removing the unused rules or moving them into a stylesheet only the routes that use them import" - dead rules in an imported stylesheet are a code problem, not a bundler problem. Why: chunking only governs how stylesheets are grouped, not what is in them. Smell: a Lighthouse unused-CSS finding answered with a `cssChunking` change instead of moving rules into a module. Source: https://nextjs.org/docs/app/api-reference/config/next-config-js/cssChunking#debugging-what-a-route-actually-uses
- **Enable `inlineCss` only for small atomic CSS bundles and first-visit heavy traffic (experimental)**: "Inlined styles cannot be cached separately from HTML." - inlining helps first-time visitors on Tailwind-sized CSS and hurts returning visitors and large bundles. Why: every HTML response re-sends the CSS and TTFB grows with bundle size. Smell: `experimental.inlineCss: true` in a project shipping Bootstrap or Material UI stylesheets. Source: https://nextjs.org/docs/app/api-reference/config/next-config-js/inlineCss#when-external-css-is-better
- **Do not set `useLightningcss` expecting it to change Turbopack (experimental)**: "Turbopack uses Lightning CSS by default since Next 14.2. This configuration option has no effect on Turbopack." - the flag only switches webpack away from PostCSS. Why: Turbopack always uses Lightning CSS. Smell: `experimental.useLightningcss: true` added to a Turbopack project as a "speed-up". Source: https://nextjs.org/docs/app/api-reference/config/next-config-js/useLightningcss

## Images: component usage

- **Use `next/image` for content images instead of a bare `<img>`**: "The Next.js Image component extends the HTML `<img>` element for automatic image optimization." - it sizes, formats, lazy-loads and reserves space automatically. Why: a plain `<img>` gets none of the size optimisation or layout-shift protection. Smell: `<img src="/hero.jpg">` in a page or layout. Source: https://nextjs.org/docs/app/api-reference/components/image
- **Statically import local images so width, height and blur data are inferred**: "If the image is statically imported, Next.js will automatically determine the intrinsic `width` and `height`." - `import hero from './hero.png'` is preferred over a string path for files in the repo. Why: inferred dimensions prevent Cumulative Layout Shift and give a free blur placeholder. Smell: `<Image src="/profile.png" width={500} height={500}>` for a file that lives under `public` and could be imported. Source: https://nextjs.org/docs/app/getting-started/images#local-images
- **Give dynamic image imports a static prefix and keep it narrow**: "The path must include a static prefix (like `../content/blog/images/`)." - a dynamic `import()` whose path starts with a literal `../content/blog/images/` prefix bundles every file under that prefix, and nothing outside it. Why: a vague prefix bloats the bundle, and the prefix is what stops external input escaping the directory. Smell: a dynamic `import()` whose path is built from `userPath` alone, or a prefix pointing at the project root. Source: https://nextjs.org/docs/app/getting-started/images#images-without-static-imports
- **Provide `width` and `height` for remote images, or use `fill`**: "Since Next.js does not have access to remote files during the build process" - a URL `src` needs explicit dimensions so the aspect ratio can be reserved. Why: without them the browser cannot reserve space and the page shifts as the image loads. Smell: `<Image src="https://cdn.example.com/a.jpg" alt="..." />` with no `width`, `height` or `fill`. Source: https://nextjs.org/docs/app/getting-started/images#remote-images
- **Use `fill` when the intrinsic size is unknown**: "If the height and width are unknown, we recommend using the `fill` property." - guessing dimensions produces a wrong aspect ratio and a distorted or shifted image. Why: `width` and `height` describe intrinsic size, not rendered size, and are used only for the ratio. Smell: `width={100} height={100}` on an image whose real ratio is unknown, with CSS forcing the rendered size. Source: https://nextjs.org/docs/app/api-reference/components/image#width-and-height
- **Position the parent of a `fill` image**: "When using `fill`, the parent element must be positioned, with `position: relative`, `fixed`, or `absolute`." - the image is absolutely positioned, so it sizes against the nearest positioned ancestor. Why: an unpositioned parent lets the image escape to some ancestor further up. Smell: `<div><Image fill ... /></div>` where the `div` has no `position` style or class. Source: https://nextjs.org/docs/app/api-reference/components/image#styling-images
- **Set `sizes` on every `fill` or CSS-responsive image**: "If `sizes` is missing, the browser assumes the image will be as wide as the viewport (`100vw`)." - a thumbnail without `sizes` downloads a viewport-wide file. Why: `sizes` drives both the browser's `srcset` choice and the `srcset` Next.js generates. Smell: `<Image fill ... />` inside a grid card with no `sizes` prop. Source: https://nextjs.org/docs/app/api-reference/components/image#sizes
- **Write `alt` text that could replace the image, or an empty string for decoration**: "It is not meant to supplement the image and should not repeat information that is already provided in the captions above or below the image." - describe what the image conveys, and use `alt=""` when it is purely decorative. Why: `alt` is read by screen readers and search engines and shown when the image fails. Smell: `alt="image"`, `alt` duplicating a caption, or a decorative background image with descriptive `alt`. Source: https://nextjs.org/docs/app/api-reference/components/image#alt
- **Replace `priority` with `preload` on Next.js 16**: "Starting with Next.js 16, the `priority` property has been deprecated" - `preload` is the renamed prop with the same intent. Why: the rename makes the behaviour explicit: a `<link rel="preload">` in the head. Smell: `<Image priority ... />` in code written against Next 16. Source: https://nextjs.org/docs/app/api-reference/components/image#priority
- **Reach for `loading="eager"` or `fetchPriority="high"` before `preload`**: "In most cases, you should use `loading=\"eager\"` or `fetchPriority=\"high\"` instead of `preload`." - reserve `preload` for a single above-the-fold LCP image and do not combine it with `loading` or `fetchPriority`. Why: preloading multiple candidates or a non-LCP image wastes bandwidth and competes with critical resources. Smell: `preload` on several images in a carousel, or `preload` together with `loading="lazy"`. Source: https://nextjs.org/docs/app/api-reference/components/image#preload
- **Keep the default lazy loading unless the image must load immediately**: "Use `eager` only when you want to ensure the image is loaded immediately." - below-the-fold images should stay lazy. Why: eager loading pulls every image into the initial load. Smell: `loading="eager"` on list or footer images. Source: https://nextjs.org/docs/app/api-reference/components/image#loading
- **Supply `blurDataURL` when using `placeholder="blur"` on a remote or dynamic image**: "If the image is dynamic or remote, you must provide `blurDataURL` yourself." - only static imports of `jpg`, `png`, `webp` and `avif` get one automatically. Why: without it the blur placeholder has nothing to show. Smell: `placeholder="blur"` on a URL `src` with no `blurDataURL`. Source: https://nextjs.org/docs/app/api-reference/components/image#blurdataurl
- **Set `height: 'auto'` when overriding width in `style`**: "If you’re using the `style` prop to set a custom width, be sure to also set `height: 'auto'` to preserve the image’s aspect ratio." - a width override alone stretches the image to the intrinsic height. Why: the component sets explicit width and height attributes. Smell: `style={{ width: '100%' }}` with no `height: 'auto'`. Source: https://nextjs.org/docs/app/api-reference/components/image#style
- **Use `onLoad` and `onError` only from Client Components**: "Using props like `onLoad`, which accept a function, requires using Client Components to serialize the provided function." - a Server Component cannot pass a function prop to `<Image>`. Why: functions are not serialisable across the server-client boundary. Smell: `onLoad={...}` on `<Image>` in a file without `'use client'`. Source: https://nextjs.org/docs/app/api-reference/components/image#onload
- **Replace `onLoadingComplete` with `onLoad`**: "Deprecated in Next.js 14, use `onLoad` instead." - the new callback receives an event whose `target` is the `<img>`. Why: the prop is deprecated and will be removed. Smell: `onLoadingComplete={(img) => ...}` in new code. Source: https://nextjs.org/docs/app/api-reference/components/image#onloadingcomplete
- **Mark SVGs, GIFs and tiny images `unoptimized`**: "This is useful for images that do not benefit from optimization such as small images (less than 1KB), vector images (SVG), or animated images (GIF)." - these pass through the optimiser for no gain. Why: vectors resize losslessly and animations are not transcoded. Smell: an animated GIF routed through `/_next/image` with a `quality` prop. Source: https://nextjs.org/docs/app/api-reference/components/image#unoptimized
- **Use `unoptimized` for images that need authentication headers**: "If the `src` image requires authentication, consider using the unoptimized property to disable Image Optimization." - the default loader never forwards request headers to the origin. Why: the optimiser fetches the source without cookies or auth, so protected images 401. Smell: an `<Image>` pointing at a signed or cookie-protected URL without `unoptimized`. Source: https://nextjs.org/docs/app/api-reference/components/image#src
- **Do not eager-load both images in a light/dark theme pair**: "You cannot use `preload` or `loading=\"eager\"` because that would cause both images to load." - keep lazy loading and use `fetchPriority="high"` if the pair is the LCP. Why: the CSS media query hides one image, but preloading fetches both. Smell: two `<Image preload>` elements toggled by `prefers-color-scheme`. Source: https://nextjs.org/docs/app/api-reference/components/image#theme-detection

## Images: configuration and security

- **Allow remote images with the narrowest `remotePatterns` possible**: "Be as specific as possible to prevent malicious usage." - set `protocol`, `hostname`, `port`, `pathname` and `search` for each origin. Why: the optimisation endpoint fetches and serves any URL the patterns admit. Smell: `remotePatterns: [{ hostname: '**' }]` or a bare `hostname` with every other field omitted. Source: https://nextjs.org/docs/app/getting-started/images#remote-images
- **Do not omit `protocol`, `port`, `pathname` or `search` in a remote pattern**: "When omitting `protocol`, `port`, `pathname`, or `search` then the wildcard `**` is implied. This is not recommended because it may allow malicious actors to optimize urls you did not intend." - every omitted field is a wildcard. Why: a shared image host serves many tenants, and a wildcard pathname admits all of them. Smell: `{ protocol: 'https', hostname: 'res.cloudinary.com' }` with no `pathname`. Source: https://nextjs.org/docs/app/api-reference/components/image#remotepatterns
- **Replace `images.domains` with `remotePatterns`**: "Deprecated since Next.js 14 in favor of strict `remotePatterns` in order to protect your application from malicious users." - `domains` cannot restrict protocol, port or pathname. Why: most remote image servers are multi-tenant, so a hostname alone is too broad. Smell: `images: { domains: ['s3.amazonaws.com'] }` in `next.config`. Source: https://nextjs.org/docs/app/api-reference/components/image#domains
- **Set `maximumRedirects` low when remote hosts may redirect**: "any allowed `remotePatterns` that respond with a redirect will follow the redirect from the remote image server without validating `remotePatterns` again on the redirect location." - the default follows up to three redirects unchecked. Why: an allowed host that redirects elsewhere turns the optimiser into an open fetcher. Smell: a user-controlled image host in `remotePatterns` with the default `maximumRedirects`. Source: https://nextjs.org/docs/app/api-reference/components/image#remotepatterns
- **Set `search` on `localPatterns` entries**: "Omitting the `search` property allows all search parameters which could allow malicious actors to optimize URLs you did not intend." - pin an exact query string or an empty one. Why: unrestricted query strings let callers vary the request freely. Smell: `localPatterns: [{ pathname: '/assets/images/**' }]` with no `search`. Source: https://nextjs.org/docs/app/api-reference/components/image#localpatterns
- **Keep every `quality` prop inside the configured `qualities` allowlist**: "This field is required starting with Next.js 16 because unrestricted access could allow malicious actors to optimize more qualities than you intended." - the default allowlist is `[75]`, and a prop outside it is coerced to the nearest value with a dev warning. Why: each extra quality is another cached variant an attacker can request. Smell: `quality={90}` on an image while `qualities` is unset or does not include 90. Source: https://nextjs.org/docs/app/api-reference/components/image#qualities
- **Stick to WebP unless AVIF's trade-offs are understood, and forward `Accept` through any proxy**: "If you self-host with a Proxy/CDN in front of Next.js, you must configure the Proxy to forward the `Accept` header." - formats are chosen from `Accept`, AVIF encodes about 50% slower, and each format is cached separately. Why: a proxy that strips `Accept` serves the original format to everyone. Smell: `formats: ['image/avif', 'image/webp']` added on a self-hosted deployment with no CDN header configuration. Source: https://nextjs.org/docs/app/api-reference/components/image#formats
- **Keep `minimumCacheTTL` low because optimised images cannot be invalidated**: "There is no mechanism to invalidate the cache at this time, so its best to keep `minimumCacheTTL` low." - prefer static imports, which hash the file and cache it immutably. Why: a long TTL means a replaced image keeps serving the old bytes until the cache file is deleted. Smell: `minimumCacheTTL: 31536000` on remote images that editors replace in place. Source: https://nextjs.org/docs/app/api-reference/components/image#minimumcachettl
- **Pair `dangerouslyAllowSVG` with a CSP and attachment disposition**: "it is strongly recommended to also set `contentDispositionType` to force the browser to download the image, as well as `contentSecurityPolicy` to prevent scripts embedded in the image from executing." - prefer `unoptimized` for SVGs instead. Why: SVG can carry scripts, and the optimiser serves arbitrary remote files. Smell: `dangerouslyAllowSVG: true` with `contentDispositionType: 'inline'` and no `contentSecurityPolicy`. Source: https://nextjs.org/docs/app/api-reference/components/image#dangerouslyallowsvg
- **Leave `dangerouslyAllowLocalIP` off unless the SSRF risk is accepted**: "Only enable once you understand the SSRF risk." - it lets the optimiser fetch from private network addresses. Why: an attacker can use it to read content on the internal network. Smell: `dangerouslyAllowLocalIP: true` added to fix a 400 in a VPC without a security note. Source: https://nextjs.org/docs/app/api-reference/components/image#dangerouslyallowlocalip

## Fonts

- **Load fonts through `next/font` instead of external stylesheet links**: "No requests are sent to Google by the browser." - fonts are downloaded at build time and self-hosted with the static assets. Why: self-hosting removes an external request and the layout shift it causes. Smell: `<link href="https://fonts.googleapis.com/css2?family=...">` in a layout or `@import url(...)` in global CSS. Source: https://nextjs.org/docs/app/api-reference/components/font
- **Apply a site-wide font in the root layout**: "Fonts are scoped to the component they're used in. To apply a font to your entire application, add it to the Root Layout." - the `className` or `variable` goes on `<html>` or `<body>` in `app/layout.tsx`. Why: a font applied in a page covers only that route. Smell: the same `Geist({ ... })` call repeated in several pages to get a global font. Source: https://nextjs.org/docs/app/getting-started/fonts
- **Prefer variable fonts, and specify `weight` for any font that is not variable**: "if you can't use a variable font, you will need to specify a weight" - a static Google font with no `weight` fails to load correctly. Why: variable fonts cover all weights in one file; static ones need each weight named. Smell: `Roboto({ subsets: ['latin'] })` with no `weight`. Source: https://nextjs.org/docs/app/getting-started/fonts#google-fonts
- **Declare `subsets` on every Google font**: "Failing to specify any subsets while `preload` is `true` will result in a warning." - name the subsets to preload, usually `['latin']`. Why: subsetting shrinks the file, and the preload link needs to know which subset to point at. Smell: `Inter({})` with no `subsets` array. Source: https://nextjs.org/docs/app/api-reference/components/font#specifying-a-subset
- **Add fonts sparingly**: "Use multiple fonts conservatively since each new font is an additional resource the client has to download." - every font call ships another file set. Why: each font is a network resource on first load. Smell: four or five different `next/font` calls across a small app. Source: https://nextjs.org/docs/app/api-reference/components/font#using-multiple-fonts
- **Define each font once in a definitions file and import the object**: "if you need to use the same font in multiple places, you should load it in one place and import the related font object where you need it." - every call to a font loader hosts a separate instance. Why: repeated calls duplicate the font files in the build. Smell: `Inter({ subsets: ['latin'] })` called in both `layout.tsx` and `Header.tsx`. Source: https://nextjs.org/docs/app/api-reference/components/font#using-a-font-definitions-file
- **Declare a font in the narrowest layout or page that needs it**: "If it's the root layout, it is preloaded on all routes." - a font used on one route should be called from that page so it is preloaded only there. Why: preloading follows the file where the font function is called. Smell: a display font for the marketing landing page loaded from the root layout. Source: https://nextjs.org/docs/app/api-reference/components/font#preloading
- **Split fonts into separate calls when only some files should preload**: "Every font file a call loads shares this setting, because they become a single group of `@font-face` rules with one `font-family`." - `preload` is per call, not per `src` entry. Why: an array `src` cannot preload the regular weight and skip the italic. Smell: `preload: false` set on one object inside a `src` array. Source: https://nextjs.org/docs/app/api-reference/components/font#preload
- **Keep a `declarations` `font-family` equal to the exported constant**: "Keep the value the same as the exported constant, so `className` and the CSS variable reference the same family." - overriding the generated family name must stay in sync with how it is referenced. Why: a mismatch leaves `className` and `variable` pointing at different families. Smell: `declarations: [{ prop: 'font-family', value: 'Brand' }]` with the font exported as `brandSans`. Source: https://nextjs.org/docs/app/api-reference/components/font#declarations

## Scripts

- **Load third-party scripts with `next/script` so they run once**: "Next.js will ensure the script will only load once, even if a user navigates between multiple pages." - a raw `<script>` tag re-executes on each render that includes it. Why: the component deduplicates and schedules loading. Smell: `<script src="https://widget.example.com/x.js">` written as plain JSX. Source: https://nextjs.org/docs/app/guides/scripts#application-scripts
- **Put third-party scripts only in the pages or layouts that need them**: "We recommend only including third-party scripts in specific pages or layouts in order to minimize any unnecessary impact to performance." - a script in the root layout loads on every route. Why: each script is main-thread work on routes that never use it. Smell: a chat widget `<Script>` in `app/layout.tsx` for a feature that lives under `/support`. Source: https://nextjs.org/docs/app/guides/scripts#application-scripts
- **Reserve `beforeInteractive` for critical scripts in the root layout**: "This strategy should only be used for critical scripts that need to be fetched as soon as possible." - it must live in a root layout and is meant for bot detectors and consent managers. Why: it is injected into `<head>` and fetched before any first-party code. Smell: `strategy="beforeInteractive"` on analytics or in a nested page. Source: https://nextjs.org/docs/app/api-reference/components/script#beforeinteractive
- **Do not expect `beforeInteractive` scripts to re-run on client navigation**: "These scripts run once per document load. A client-side navigation does not run them again" - that includes a change of root param such as `/en` to `/fi`. Why: the root layout stays mounted across those navigations. Smell: a locale-dependent script with `beforeInteractive` expected to re-initialise per locale. Source: https://nextjs.org/docs/app/api-reference/components/script#beforeinteractive
- **Keep tag managers and analytics on the default `afterInteractive`**: "should be used for any script that needs to load as soon as possible but not before any first-party Next.js code." - the default loads after some hydration and only on routes that render it. Why: it balances early availability against first-party priority. Smell: Google Tag Manager forced to `beforeInteractive`. Source: https://nextjs.org/docs/app/api-reference/components/script#afterinteractive
- **Use `lazyOnload` for chat widgets and social embeds**: "This strategy should be used for any background or low priority scripts that do not need to load early." - idle-time loading keeps them off the critical path. Why: they only need to exist after the page is fully loaded. Smell: a chat support plugin on the default strategy. Source: https://nextjs.org/docs/app/api-reference/components/script#lazyonload
- **Do not use `strategy="worker"` in the App Router (experimental, requires `nextScriptWorkers`)**: "The `worker` strategy is not yet stable and does not yet work with the App Router." - it is Pages Router only and needs Partytown. ## Metadata object and generateMetadata

- **Export `metadata` and `generateMetadata` only from Server Components**: "The `metadata` object and `generateMetadata` function exports are only supported in Server Components." - metadata must resolve on the server before the page renders. - **Keep `page.tsx` a Server Component and move client logic to a child file**: "keep your `page.tsx` as a Server Component and move the Client Component logic to a separate file" - a page needing `useState` should import a client child rather than become a client file itself. - **Use the static `metadata` object when nothing depends on the request**: "If metadata doesn't depend on request information, it should be defined using the static `metadata` object rather than `generateMetadata`." - a function returning constants is unnecessary. - **Export either `metadata` or `generateMetadata` from a segment, never both**: "You cannot export both the `metadata` object and `generateMetadata` function from the same route segment." - pick one per file. - **Call `notFound()` or `redirect()` from `generateMetadata` when the data is missing**: "The `redirect()` and `notFound()` Next.js methods can also be used inside `generateMetadata`." - do not return placeholder metadata for an entity that does not exist. - **Pair `title.template` with `title.default`**: "`title.default` is required when you add a `title.template`." - the template applies to children, and the default is what the segment itself shows. - **Do not put `title.template` in a `page.js`**: "`title.template` defined in `page.js` has no effect because a page is always the terminating segment" - templates belong in layouts and apply to child segments only. ## Asset prefix

- **Use `basePath`, not `assetPrefix`, to host under a sub-path**: "We do not suggest you use a custom Asset Prefix for this use case." - `assetPrefix` is for a CDN origin only. Why: only `_next/static` requests are rewritten. Smell: `<Image src="/logo.png">` expected to load from the CDN because `assetPrefix` is set.
