# Next.js 16 code-review rules: data fetching, mutations, route handlers, proxy, security

Extracted 2026-11-10 from the Next.js 16.4.5 App Router documentation (MIT, Vercel, Inc.). One rule per bullet, one source link each. Quotations are short excerpts; the rest is original.

## Fetching data in Server Components

- **Fetch where the data is used instead of drilling props**: "Identical `fetch` requests in a React component tree are memoized by default, so you can fetch data in the component that needs it instead of drilling props." - call the same `fetch` in each component that needs the result rather than fetching once at the top and threading it down. Why: identical GET requests are deduplicated within one render pass, so the extra calls cost nothing. Smell: a page fetching `user` and passing it through three layers of props to the one leaf that renders it. Source: https://nextjs.org/docs/app/getting-started/fetching-data#with-the-fetch-api
- **Do not assume a server-side `fetch` is cached or non-blocking**: "`fetch` requests are not cached by default and will block the page from rendering until the request is complete." - either add `use cache` or wrap the fetching component in `<Suspense>` to stream it. Why: an uncached fetch at the top of a page delays the whole route until it resolves. Smell: `const data = await fetch(url)` directly in `page.tsx` with no `use cache`, no Suspense and a comment assuming it is cached. Source: https://nextjs.org/docs/app/getting-started/fetching-data#with-the-fetch-api
- **Do not rely on `loading.js` to cover uncached reads in a layout**: "a layout that accesses uncached or runtime data (e.g. `cookies()`, `headers()`, or uncached fetches) does not fall back to a same route segment `loading.js`." - a layout that awaits request data blocks navigation until it finishes. Why: `loading.js` only wraps `page.js` and its children, not the layout above it. Smell: `const session = await cookies()` at the top of `layout.tsx` with a sibling `loading.tsx` expected to show a skeleton. Source: https://nextjs.org/docs/app/getting-started/fetching-data#with-loadingjs
- **Place Suspense boundaries next to the uncached access**: "using `<Suspense>` closer to the runtime or uncached data access is recommended." - wrap the specific component that reads uncached or runtime data rather than relying on a route-level fallback. Why: everything outside the boundary can be sent immediately and only the slow part streams. Smell: one `loading.tsx` for a whole dashboard where a single widget does the slow query. Source: https://nextjs.org/docs/app/getting-started/fetching-data#with-loadingjs
- **Pass promises to Client Components and unwrap with `use`**: "Start by fetching data in your Server component, and pass the promise to your Client Component as prop" - start the request on the server without awaiting it, then read it in the client with `use()` inside a Suspense boundary. Why: the client can render while the data streams, instead of waiting for the server to finish the await. Smell: a `'use client'` component calling `fetch` in `useEffect` for data the parent Server Component already had access to. Source: https://nextjs.org/docs/app/getting-started/fetching-data#streaming-data-with-the-use-api
- **Start independent requests before awaiting any of them**: "Start multiple requests by calling `fetch`, then await them with `Promise.all`." - sequential `await` calls serialise requests that do not depend on each other. Why: requests begin when `fetch` is called, so eager calls run in parallel and avoid a waterfall. Smell: `const artist = await getArtist(id); const albums = await getAlbums(id)` where `getAlbums` needs only `id`. Source: https://nextjs.org/docs/app/getting-started/fetching-data#parallel-data-fetching
- **Wrap non-`fetch` data access in `React.cache`**: "For data access that does not use `fetch`, such as an ORM or database query, wrap the function in `React.cache`." - ORM and database helpers get no automatic memoisation. Why: multiple components calling the same query in one request would otherwise run it repeatedly. Smell: `export async function getUser(id) { return db.query.users.findFirst(...) }` called from a layout and a page in the same route. Source: https://nextjs.org/docs/app/getting-started/fetching-data#reusing-data-with-reactcache
- **Use `'use cache: private'` for preloaded functions that read request APIs (requires `cacheComponents`)**: "If the function reads request APIs such as `cookies()` or `headers()`, use `'use cache: private'`." - a plain `'use cache'` cannot read request data, so preload helpers that touch cookies need the private variant. Why: private cache functions deduplicate within one request without storing the result in a server cache across users. Smell: `async function getCart() { 'use cache'; const c = await cookies(); ... }`. Source: https://nextjs.org/docs/app/getting-started/fetching-data#preloading-data

## Fetching data in Client Components

- **Roll back optimistic values when the write fails**: "An optimistic update should restore the previous browser value if the write fails." - keep the previous value and restore it in the error path. Why: otherwise the UI shows a state the server never accepted. Smell: `setQueryData(key, newValue)` in `onMutate` with no `onError` that restores the previous snapshot. Source: https://nextjs.org/docs/app/guides/client-side-data-fetching#coordinate-mutations
- **Invalidate the cached server read that seeded the client cache**: "After a mutation, invalidate any cached server read that provided the initial data" - a browser-side cache update alone leaves the next server render stale. Why: the Server Component that provided the fallback data reads from its own cache layer. Smell: a mutation that calls SWR `mutate` or `setQueryData` but never calls `updateTag` or `revalidateTag` for the tagged server read. Source: https://nextjs.org/docs/app/guides/client-side-data-fetching#coordinate-mutations
- **Keep the interactive shell outside the Suspense boundary**: "Keep the interactive shell outside the boundary so it remains available while the results load" - only the results list should suspend, not the input that drives it. Why: suspending the whole component hides the control the user is typing into. Smell: `useSWR(key, fetcher, { suspense: true })` in the same component that renders the search `<input>`. Source: https://nextjs.org/docs/app/guides/client-side-data-fetching/swr#use-suspense-for-client-data
- **Put independent Suspense reads in sibling components**: "Multiple Suspense reads in one component run sequentially." - split independent queries into separate components so they start together. Why: each suspending read in one component blocks the next from starting. Smell: two `useSWR(..., { suspense: true })` calls, or two `useSuspenseQuery` calls, in one component body. Source: https://nextjs.org/docs/app/guides/client-side-data-fetching/swr#use-suspense-for-client-data
- **Define the SWR key once and share it**: "The `fallback` key and the `useSWR` key must match exactly. If they drift, SWR ignores the fallback value and fetches on the client." - export the key from one module and import it in both the provider and the hook. Why: a mismatched key silently discards the server-provided data and refetches. Smell: `fallback: { ['/api/products/' + id]: ... }` in the page and `useSWR(\`/api/product/${id}\`)` in the client. Source: https://nextjs.org/docs/app/guides/client-side-data-fetching/swr#provide-initial-data-from-a-server-component
- **Create a fresh `QueryClient` per server render and one per browser**: "Create a new query client for each server render and reuse one query client in the browser" - branch on `typeof window` so the server never shares a client across requests. Why: a module-level client on the server leaks data between users and requests. Smell: `const queryClient = new QueryClient()` at module scope in a provider file that also renders on the server. Source: https://nextjs.org/docs/app/guides/client-side-data-fetching/tanstack-query#set-up-the-provider
- **Override `queryFn` when prefetching on the server**: "Override `queryFn` on the server because the Route Handler's relative URL only resolves in the browser" - call the data function directly on the server and leave the relative URL for the client. Why: a relative `fetch('/api/...')` has no origin to resolve against during server rendering. Smell: `queryClient.prefetchQuery(productCache.options(id))` in a Server Component where `options` fetches `/api/products/${id}`. Source: https://nextjs.org/docs/app/guides/client-side-data-fetching/tanstack-query#provide-initial-data-from-a-server-component
- **Do not call TanStack `dehydrate()` during Cache Components prerendering (requires `cacheComponents`)**: "With Cache Components, `dehydrate()` reads the current time (`Date.now()`) while prerendering and causes a current-time prerender error." - build the dehydrated state by hand with a cached timestamp tagged like the data. Why: a current-time read inside the static shell is not prerenderable. Smell: `<HydrationBoundary state={dehydrate(queryClient)}>` in a page under `cacheComponents: true`. Source: https://nextjs.org/docs/app/guides/client-side-data-fetching/tanstack-query#build-a-prerenderable-hydration-state

## Mutating data with Server Functions

- **Verify authentication and authorisation inside every Server Function**: "Server Functions are reachable via direct POST requests, not just through your application's UI. Always verify authentication and authorization inside every Server Function." - each exported action is a public endpoint and must check the caller itself. Why: the UI that renders a form is not a security boundary; anyone can POST to the action ID. Smell: `'use server'` file where `deletePost(id)` goes straight to `db.post.delete` with no session read. Source: https://nextjs.org/docs/app/getting-started/mutating-data#what-are-server-functions
- **Do not expect `refresh()` to revalidate cached tags**: "The `refresh()` function does not revalidate tagged data." - use `updateTag` or `revalidateTag` when cached data changed; `refresh()` only refetches the current route's RSC payload. Why: tagged cache entries stay stale after `refresh()`. Smell: an action that writes to the database then calls `refresh()` while the page reads via a `'use cache'` function tagged with `cacheTag`. Source: https://nextjs.org/docs/app/getting-started/mutating-data#refresh-data
- **Put revalidation before `redirect`**: "Calling `redirect` throws a framework handled control-flow exception. Any code after it won't execute." - any `revalidatePath`, `revalidateTag` or cleanup after `redirect()` is dead code. Why: `redirect` throws, so execution stops at that line. Smell: `redirect('/posts'); revalidatePath('/posts')` in that order. Source: https://nextjs.org/docs/app/getting-started/mutating-data#redirect-after-a-mutation

## Server Actions: dispatch, revalidation and security

- **Never parallelise Server Actions from the client with `Promise.all`**: "do not rely on `Promise.all` to parallelize Server Actions from the client." - the client dispatches actions one at a time; do parallel work inside one action, in a Server Component or in a Route Handler. Why: Next.js queues actions per client so the re-rendered tree stays consistent with its result. Smell: `await Promise.all([saveTitle(t), saveBody(b)])` in a client event handler where both are actions. Source: https://nextjs.org/docs/app/guides/server-actions#sequential-dispatch-on-the-client
- **Use `updateTag` when the user must see their own write immediately**: "immediate expiration of a tag. The next read (including the route re-render that ships with the action's response) waits for fresh data." - `revalidateTag` with a profile serves stale data while refreshing in the background, and `updateTag` is Server Actions only. Why: the action's own re-render only waits for fresh data under `updateTag`. Smell: `revalidateTag(tag, 'max')` in an action followed by UI that expects the new value in the same round trip. Source: https://nextjs.org/docs/app/guides/server-actions#choosing-a-cache-update
- **Treat every action as an untrusted entry point**: "The implementation stays on the server, but the route is reachable to anyone who can send the same POST. Treat every action as an untrusted entry point." - framework protections (CSRF origin check, body limit, encrypted IDs) are not application-level checks. Why: the action ID in the client bundle is enough to invoke it without going through the UI. Smell: an action that assumes its caller already passed a page-level `redirect('/login')`. Source: https://nextjs.org/docs/app/guides/server-actions#security
- **Validate every input an action receives**: "Treat `FormData`, query parameters, and headers as untrusted." - parse and validate before use. Why: all of these are controlled by the client. Smell: `const amount = Number(formData.get('amount'))` used in a charge with no range check or schema. Source: https://nextjs.org/docs/app/guides/server-actions#security
- **Send an identifier plus the change, not the whole record**: "Send a reference (typically an ID) plus the user's change, and re-read the rest from a trusted source using the session." - look the row up by ID and owner on the server. Why: a client-supplied object can carry any ID, ownership or field value. Smell: `export async function completeItem(item: Item) { await db.item.update({ where: { id: item.id }, data: { completed: true } }) }`. Source: https://nextjs.org/docs/app/guides/server-actions#security
- **Do not mistake schema validation for authorisation**: "A well-formed `Item` object can still refer to a row the caller does not own." - after `zod.parse`, still scope the query to the session user. Why: schemas check shape, not ownership. Smell: `const data = schema.parse(input); await db.item.update({ where: { id: data.id } })` with no `ownerId` condition. Source: https://nextjs.org/docs/app/guides/server-actions#security
- **Configure `allowedOrigins` when a proxy or CDN changes the host**: "Configure `serverActions.allowedOrigins` for proxy or CDN domains." - the CSRF check compares `Origin` with `Host` or `X-Forwarded-Host` and rejects mismatches. Why: behind a reverse proxy the browser's origin differs from the host the server reports. Smell: actions failing in production behind a proxy and the fix being a disabled CSRF check instead of `allowedOrigins`. Source: https://nextjs.org/docs/app/guides/server-actions#security
- **Set a stable encryption key for multi-instance deployments**: "For multi-instance and self-hosted deployments, set `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY` to a stable key shared across instances." - closure variables are encrypted per build and must decrypt on every instance. Why: instances with different keys cannot read each other's action references. Smell: a self-hosted multi-replica deployment with no `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY` in its environment. Source: https://nextjs.org/docs/app/guides/server-actions#security

## Forms with Server Actions

- **Strip `$ACTION_` fields before using `Object.fromEntries(formData)`**: "Note that this object will contain extra properties prefixed with `$ACTION_`." - filter or pick known fields rather than spreading the whole object into a write. Why: React adds internal action metadata to the submitted form data. Smell: `await db.insert(users).values(Object.fromEntries(formData))`. Source: https://nextjs.org/docs/app/guides/forms#how-it-works
- **Pass extra arguments with `bind`, not trusted hidden inputs**: "However, the value will be part of the rendered HTML and will not be encoded." - hidden inputs are visible and editable in the HTML; `bind` keeps the argument server-encoded and still supports progressive enhancement. Why: a hidden `userId` can be changed before submit. Smell: `<input type="hidden" name="userId" value={userId} />` whose value the action treats as the caller's identity. Source: https://nextjs.org/docs/app/guides/forms#passing-additional-arguments
- **Validate form fields on the server with a schema**: "you can use a schema validation library like Zod or Valibot to validate the form fields." - HTML attributes like `required` are a client convenience only. Why: server-side validation is the only check that cannot be bypassed. Smell: an action that reads `formData.get('email')` and writes it to the database with no `safeParse`. Source: https://nextjs.org/docs/app/guides/forms#form-validation
- **Add the `prevState` parameter when an action is used with `useActionState`**: "When using `useActionState`, the Server function signature will change to receive a new `prevState` or `initialState` parameter as its first argument." - the form data becomes the second argument. Why: with the old signature the action reads the previous state as if it were the `FormData`. Smell: `useActionState(createUser, initialState)` while `createUser(formData: FormData)` calls `formData.get(...)` on its first parameter. Source: https://nextjs.org/docs/app/guides/forms#validation-errors
- **Call `useFormStatus` from a child of the form, not the form's own component**: "When using this hook, you'll need to create a separate component to render the loading indicator." - the hook reads the status of the nearest parent `<form>`. Why: called in the component that renders the form, it has no parent form and `pending` is never true. Smell: `const { pending } = useFormStatus()` in the same component that returns `<form action={...}>`. Source: https://nextjs.org/docs/app/guides/forms#pending-states

## The Form component

- **Do not pass `method`, `encType` or `target` to `<Form>`**: "Are not supported as they override `<Form>` behavior." - use a plain `<form>` when those attributes are needed. Why: they fall back to native browser submission and lose client-side navigation and prefetching. Smell: `<Form action="/search" method="post">`. Source: https://nextjs.org/docs/app/api-reference/components/form#caveats
- **Do not call `preventDefault` in a `<Form>` `onSubmit`**: "calling `event.preventDefault()` will override `<Form>` behavior such as navigating to the specified URL." - keep `onSubmit` for side effects only. Why: the default action is what performs the navigation. Smell: `<Form action="/search" onSubmit={(e) => { e.preventDefault(); track() }}>`. Source: https://nextjs.org/docs/app/api-reference/components/form#caveats

## Route Handlers

- **Never place `route.js` and `page.js` in the same segment**: "Each `route.js` or `page.js` file takes over all HTTP verbs for that route." - move the handler under a sub-path such as `app/api/`. Why: both claim every HTTP method for the route and conflict. Smell: `app/posts/page.tsx` alongside `app/posts/route.ts`. Source: https://nextjs.org/docs/app/getting-started/route-handlers#route-resolution
- **Opt into caching only for `GET` handlers**: "Route Handlers are not cached by default. You can, however, opt into caching for `GET` methods." - other methods are never cached, even next to a cached `GET` in the same file. Why: the default changed to dynamic in v15, and only `GET` can be made static. Smell: `export const dynamic = 'force-static'` in a file whose `POST` is expected to be cached, or a `GET` assumed cached with no config. Source: https://nextjs.org/docs/app/getting-started/route-handlers#caching
- **Keep `use cache` out of the handler body (requires `cacheComponents`)**: "`use cache` cannot be used directly inside a Route Handler body; extract it to a helper function." - put the directive in a separate async function the handler awaits. Why: the directive is not valid at the top of a `GET`/`POST` export. Smell: `export async function GET() { 'use cache'; ... }`. Source: https://nextjs.org/docs/app/getting-started/route-handlers#with-cache-components
- **Await `params` in a handler's context**: "a promise that resolves to an object containing the dynamic route parameters for the current route." - `params` has been a promise since v15. Why: destructuring a promise synchronously yields `undefined` fields. Smell: `export async function GET(req, { params }) { const { id } = params }` with no `await`. Source: https://nextjs.org/docs/app/api-reference/file-conventions/route#context-optional
- **Set response headers on a new `Response`, not on `headers()`**: "This `headers` instance is read-only. To set headers, you need to return a new `Response` with new `headers`." - `headers()` reads the incoming request only. Why: the returned object is read-only and silently or loudly rejects writes. Smell: `(await headers()).set('x-trace', id)` inside a route handler. Source: https://nextjs.org/docs/app/api-reference/file-conventions/route#headers
- **Coerce and validate `formData` values, which are all strings**: "Since `formData` data are all strings, you may want to use `zod-form-data` to validate the request and retrieve data in the format you prefer (e.g. `number`)." - parse numbers and booleans explicitly. Why: `formData.get` never returns a number, so arithmetic on it is a bug. Smell: `const qty = formData.get('qty') * price`. Source: https://nextjs.org/docs/app/api-reference/file-conventions/route#request-body-formdata
- **Centralise CORS headers for many handlers**: "To add CORS headers to multiple Route Handlers, you can use Proxy or the `next.config.js` file." - per-handler headers are for one-off endpoints. Why: duplicated CORS blocks drift and miss new routes. Smell: the same three `Access-Control-*` headers pasted into every `route.ts` under `app/api/`. Source: https://nextjs.org/docs/app/api-reference/file-conventions/route#cors

## Backend for Frontend

- **Treat every Route Handler as a public endpoint**: "Route Handlers are public HTTP endpoints. Any client can access them." - add authentication and authorisation inside the handler. Why: nothing restricts who can call a `route.ts`. Smell: `app/api/admin/users/route.ts` returning all users with no session check. Source: https://nextjs.org/docs/app/guides/backend-for-frontend#public-endpoints
- **Do not leak internals in error responses**: "Avoid exposing sensitive information in error messages sent to the client." - return a generic message and log the detail server-side. Why: stack traces and database errors reveal implementation and data. Smell: `return new Response(error.stack, { status: 500 })` or echoing a raw ORM error message. Source: https://nextjs.org/docs/app/guides/backend-for-frontend#public-endpoints
- **Sanitise anything interpolated into generated markup**: "Sanitize any input used to generate markup." - escape user content before building XML, RSS or HTML strings. Why: unescaped values break the document or inject content. Smell: a template literal RSS feed with `<title>${item.title}</title>` from user-authored data. Source: https://nextjs.org/docs/app/guides/backend-for-frontend#content-types
- **Remember a rewrite target is still reachable directly**: "The `/docs/md/...` route is still directly accessible without the rewrite." - block direct access in Proxy if the route must only serve the rewritten form. Why: rewrites add a path, they do not hide the destination. Smell: an internal-only `app/internal/[...slug]/route.ts` protected solely by a `rewrites()` entry. Source: https://nextjs.org/docs/app/guides/backend-for-frontend#content-negotiation
- **Clone the request before reading the body twice**: "You can only read the request body once. Clone the request if you need to read it again" - call `request.clone()` for the second reader. Why: the body stream is consumed on first read and throws afterwards. Smell: `await request.json()` for validation followed by `await request.json()` again for processing. Source: https://nextjs.org/docs/app/guides/backend-for-frontend#consuming-request-payloads
- **Reject off-origin redirect targets on callback URLs**: "Use a Route Handler to verify the response and decide where to redirect the user." - compare the resolved destination origin with the request origin before redirecting. Why: a `redirect_url` query parameter taken as-is is an open redirect. Smell: `NextResponse.redirect(searchParams.get('redirect_url'))` with no origin comparison. Source: https://nextjs.org/docs/app/guides/backend-for-frontend#webhooks-and-callback-urls
- **Rate limit expensive endpoints**: "In addition to code-based checks, enable any rate limiting features provided by your host." - add a check that returns 429 before doing the work. Why: email sends, database writes and third-party calls are abuse targets. Smell: a `POST` handler that sends an email with no rate limiting at all. Source: https://nextjs.org/docs/app/guides/backend-for-frontend#rate-limiting
- **Validate content type and size before processing a payload**: "Never trust incoming request data. Validate content type and size, and sanitize against XSS before use." - check `Content-Type`, enforce a size limit and sanitise strings. Why: unchecked bodies allow malformed input and resource exhaustion. Smell: `const body = await request.json()` passed straight to a database write. Source: https://nextjs.org/docs/app/guides/backend-for-frontend#verify-payloads
- **Do not rely on Proxy alone for authentication**: "Always verify credentials before granting access. Do not rely on proxy alone for authentication and authorization." - check again in the handler or data layer. Why: a matcher change can silently remove coverage. Smell: `app/api/orders/route.ts` with no auth because `proxy.ts` matches `/api/:path*`. Source: https://nextjs.org/docs/app/guides/backend-for-frontend#access-to-protected-resources
- **Strip sensitive data from responses and logs**: "Remove sensitive or unnecessary data from responses and backend logs." - return minimal objects and never log whole requests. Why: logs and responses are retained and read by more people than intended. Smell: `console.log(request.headers)` or `console.log(body)` in a login handler. Source: https://nextjs.org/docs/app/guides/backend-for-frontend#access-to-protected-resources
- **Fetch from the source in Server Components, not from your own Route Handlers**: "Fetch data in Server Components directly from its source, not via Route Handlers." - import the data function instead of calling your own API over HTTP. Why: there is no server listening at build time, and at runtime it adds a round trip. Smell: `await fetch('http://localhost:3000/api/items')` or `fetch(process.env.BASE_URL + '/api/items')` in `page.tsx`. Source: https://nextjs.org/docs/app/guides/backend-for-frontend#server-components
- **Do not use Server Actions for data fetching**: "Server Actions are queued. Using them for data fetching introduces sequential execution." - read data in Server Components or through a Route Handler. Why: actions are dispatched one at a time per client. Smell: a `'use client'` list calling a `getItems()` action in `useEffect` on mount. Source: https://nextjs.org/docs/app/guides/backend-for-frontend#server-actions
- **Do not keep state in module scope across requests**: "Route Handlers cannot share data between requests." - use a database or external store. Why: on serverless hosts each invocation may be a fresh instance and the file system may be read-only. Smell: `const rateLimits = new Map()` at the top of `route.ts` used as a rate limiter or cache. Source: https://nextjs.org/docs/app/guides/backend-for-frontend#deployment-environment

## Proxy

- **Use `proxy.ts`, not `middleware.ts`, from Next.js 16**: "Starting with Next.js 16, Middleware is now called Proxy to better reflect its purpose." - the file and export are now `proxy`. Why: `middleware` is the deprecated name. Smell: a new `middleware.ts` with `export function middleware(request)`. Source: https://nextjs.org/docs/app/getting-started/proxy#proxy
- **Migrate existing middleware with the codemod**: "The `middleware.js` file convention has been deprecated in Next.js 16 and renamed to `proxy.js`." - run `npx @next/codemod@canary middleware-to-proxy .` to rename the file and the export. Why: the deprecated convention will not be the documented path forward. Smell: an upgrade PR to Next 16 that leaves `middleware.ts` untouched. Source: https://nextjs.org/docs/app/api-reference/file-conventions/middleware
- **Prefer `redirects` config for simple redirects**: "For simple redirects, consider using the `redirects` configuration in `next.config.ts` first." - reserve Proxy for logic that needs request data. Why: config redirects run earlier and without executing code. Smell: a `proxy.ts` whose only job is `if (pathname === '/old') return NextResponse.redirect('/new')`. Source: https://nextjs.org/docs/app/getting-started/proxy#use-cases
- **Do not make Proxy the session or authorisation system**: "it should not be used as a full session management or authorization solution." - use it for optimistic redirects and keep real checks near the data. Why: Proxy runs on every request, including prefetches, and is not meant for slow data access. Smell: `proxy.ts` querying the database to load permissions for every request. Source: https://nextjs.org/docs/app/getting-started/proxy#use-cases
- **Do not expect fetch cache options to work in Proxy**: "Using fetch with `options.cache`, `options.next.revalidate`, or `options.next.tags`, has no effect in Proxy." - cache outside Proxy or accept an uncached call. Why: the Next.js data cache is not available in the Proxy layer. Smell: `fetch(url, { next: { revalidate: 60 } })` inside `proxy.ts`. Source: https://nextjs.org/docs/app/getting-started/proxy#use-cases
- **Export exactly one proxy function**: "The file must export a single function, either as a default export or named `proxy`." - compose helpers into that one function. Why: multiple proxy exports from one file are not supported. Smell: `export function proxy()` and `export default function()` in the same `proxy.ts`. Source: https://nextjs.org/docs/app/api-reference/file-conventions/proxy#proxy-function
- **Exclude static assets with a negative matcher**: "Consider using a negative match pattern to exclude these paths, otherwise auth logic or redirects can unintentionally block CSS, JS, or images from loading." - match `/((?!api|_next/static|_next/image|favicon.ico).*)` or similar. Why: without a matcher Proxy runs on `_next/static`, `_next/image` and `public/` files. Smell: an auth redirect in `proxy.ts` with no `config.matcher`. Source: https://nextjs.org/docs/app/api-reference/file-conventions/proxy#matcher
- **Keep `matcher` values static**: "The `matcher` values need to be constants so they can be statically analyzed at build-time. Dynamic values such as variables will be ignored." - write the pattern inline. Why: matchers are resolved at build time, so a computed value is dropped. Smell: `export const config = { matcher: protectedRoutes.map((r) => r + '/:path*') }`. Source: https://nextjs.org/docs/app/api-reference/file-conventions/proxy#matcher
- **Do not assume Proxy covers Server Functions on excluded paths**: "a Proxy matcher that excludes a path will also skip Server Function calls on that path." - actions are POSTs to the page that uses them, so they follow the page's match. Why: a matcher change or moving an action to another route can silently drop coverage. Smell: an action on a public landing page excluded from the matcher that relies on Proxy for auth. Source: https://nextjs.org/docs/app/api-reference/file-conventions/proxy#execution-order
- **Do not set `runtime` in Proxy**: "Setting the `runtime` config option in Proxy will throw an error." - Proxy uses Node.js by default in Next 16 and the option is not available. Why: the segment config does not apply to the proxy file. Smell: `export const runtime = 'edge'` in `proxy.ts`. Source: https://nextjs.org/docs/app/api-reference/file-conventions/proxy#runtime
- **Use `event.waitUntil` for background work in Proxy**: "The `waitUntil()` method takes a promise as an argument, and extends the lifetime of the Proxy until the promise settles." - pass logging or analytics promises to `waitUntil`. Why: a fire-and-forget promise may be cut off when the response is sent. Smell: `fetch('https://analytics.example/log', { method: 'POST' })` in `proxy.ts` with no `await` and no `waitUntil`. Source: https://nextjs.org/docs/app/api-reference/file-conventions/proxy#waituntil-and-nextfetchevent

## Request and response APIs

- **Do not `force-cache` requests that carry user credentials**: "Caching is opt-in. Set `cache: 'force-cache'` to cache any request, including `POST` and requests that send `authorization` or `cookie` headers." - cached entries are keyed by URL, method, headers and body, so a per-user request can be cached and served to others only if the headers differ; still, treat caching of authenticated responses as a deliberate choice. Why: forcing the cache on a request that depends on the caller can expose one user's data to another when the key collides. Smell: `fetch(url, { cache: 'force-cache', headers: { cookie } })` for a profile endpoint. Source: https://nextjs.org/docs/app/api-reference/functions/fetch#optionscache
- **Do not expect `fetch` memoisation in Route Handlers**: "Memoization does not apply in Route Handlers, since they are not part of the React component tree." - deduplicate manually if a handler needs the same resource twice. Why: memoisation is a render-pass feature. Smell: two identical `fetch` calls in one `GET` handler assumed to hit the network once. Source: https://nextjs.org/docs/app/api-reference/functions/fetch#memoization
- **Await `cookies()`**: "You must use `async/await` or React's `use` function to access cookies." - the synchronous form is a compatibility shim that will be removed. Why: `cookies` returns a promise since v15. Smell: `cookies().get('session')`. Source: https://nextjs.org/docs/app/api-reference/functions/cookies#good-to-know
- **Read cookies inside a Suspense boundary under Cache Components (requires `cacheComponents`)**: "calling `cookies()` outside of a `<Suspense>` boundary prevents the route from being prerendered." - move the read into a component wrapped in `<Suspense>`. Why: request data cannot be part of the static shell. Smell: `const store = await cookies()` at the top of `page.tsx` with `cacheComponents: true`. Source: https://nextjs.org/docs/app/api-reference/functions/cookies#good-to-know
- **Only set or delete cookies in a Server Function or Route Handler**: "HTTP does not allow setting cookies after streaming starts, so you must use `.set` in a Server Function or Route Handler." - Server Components may read cookies but never write them. Why: once streaming begins the response headers are already sent. Smell: `cookieStore.set('theme', value)` inside a page or layout render. Source: https://nextjs.org/docs/app/api-reference/functions/cookies#good-to-know
- **Set cookie security options explicitly**: "The only option with a default value is `path`." - pass `httpOnly`, `secure`, `sameSite` and an expiry for every session cookie. Why: nothing else is defaulted, so an unprotected cookie is the default outcome. Smell: `cookieStore.set('session', token)` with no options object. Source: https://nextjs.org/docs/app/api-reference/functions/cookies#options
- **Do not try to write through `headers()`**: "Since `headers` is read-only, you cannot `set` or `delete` the outgoing request headers." - return a `Response` with headers, or set them in Proxy. Why: the object exposes the incoming request only. Smell: `(await headers()).set('cache-control', 'no-store')`. Source: https://nextjs.org/docs/app/api-reference/functions/headers#good-to-know
- **Do not read `request.ip` or `request.geo`**: "`ip` and `geo` removed." - read the platform's forwarded headers instead. Why: both properties were removed from `NextRequest` in v15. Smell: `const ip = request.ip ?? request.headers.get('x-forwarded-for')`. Source: https://nextjs.org/docs/app/api-reference/functions/next-request#version-history
- **Forward request headers with `NextResponse.next({ request: { headers } })`, never `NextResponse.next({ headers })`**: "In contrast, `NextResponse.next({ headers })` is a shorthand for sending headers from proxy to the client." - the `request` form passes headers upstream to the route; the bare form sends them to the browser. Why: sending headers like `Content-Type` to the client can break Server Action submissions and streaming, and exposes values meant for the server. Smell: `return NextResponse.next({ headers: requestHeaders })` after injecting auth or nonce headers. Source: https://nextjs.org/docs/app/api-reference/functions/next-response#next
- **Allow-list forwarded headers instead of copying them all**: "In general, avoid copying all incoming request headers because doing so can leak sensitive data to clients or upstream services." - build a new `Headers` with known-safe names and drop `authorization`, `cookie` and custom `x-*`. Why: forwarded headers may reach external services. Smell: `new Headers(request.headers)` passed wholesale to an upstream `fetch` or to `NextResponse.next`. Source: https://nextjs.org/docs/app/api-reference/functions/next-response#next
- **Build redirect targets from `request.url` or `request.nextUrl`**: "The URL can be created and modified before being used in the `NextResponse.redirect()` method." - use `new URL('/login', request.url)` and set search params on it. Why: an absolute URL resolved against the current request keeps host and base path correct. Smell: `NextResponse.redirect('/login')` with a bare path string in `proxy.ts`. Source: https://nextjs.org/docs/app/api-reference/functions/next-response#redirect

## Data security and taint

- **Read `process.env` only in the Data Access Layer**: "Secret keys should be stored in environment variables, but only the Data Access Layer should access `process.env`." - components and actions call DAL functions rather than reading secrets. Why: keeping secrets in one module makes exposure easy to audit. Smell: `process.env.STRIPE_SECRET_KEY` referenced in `page.tsx` or a `'use client'` file. Source: https://nextjs.org/docs/app/guides/data-security#data-access-layer
- **Do not pass whole database rows to Client Components**: "This approach, however, makes it easier to accidentally expose private data to the client" - map to the fields the component renders and narrow the prop type. Why: every field of a prop object is serialised into the RSC payload. Smell: `<Profile user={rows[0]} />` where `Profile` is `'use client'` and typed as `{ user: User }`. Source: https://nextjs.org/docs/app/guides/data-security#component-level-data-access
- **Treat tainting as an extra layer, not the filter (experimental, requires `experimental.taint`)**: "However, it's an additional layer of protection, you should still filter and sanitize the data in your DAL before passing it to React's render context." - keep DTO filtering even with taint enabled. Why: taint only catches the cases it can track by reference. Smell: a DAL that returns full rows because `experimental_taintObjectReference` is applied. Source: https://nextjs.org/docs/app/guides/data-security#tainting
- **Never put secrets in `NEXT_PUBLIC_` variables**: "Next.js exposes any environment variable prefixed with `NEXT_PUBLIC_` to the client." - keep secrets unprefixed and server-only. Why: prefixed variables are inlined into the browser bundle. Smell: `NEXT_PUBLIC_API_SECRET` or `NEXT_PUBLIC_DATABASE_URL` in `.env`. Source: https://nextjs.org/docs/app/guides/data-security#tainting
- **Mark server-only modules with `import 'server-only'`**: "This ensures that proprietary code or internal business logic stays on the server by causing a build error if the module is imported in the client environment." - add it at the top of DAL, database and secret-reading modules. Why: without it a client import silently ships server code and secrets. Smell: `lib/db.ts` or `lib/session.ts` without `import 'server-only'`. Source: https://nextjs.org/docs/app/guides/data-security#preventing-client-side-execution-of-server-only-code
- **Never derive privileges from `searchParams`, params or headers**: "You should always validate input from client, as they can be easily modified." - re-verify from the session on every request. Why: all of these are set by the caller. Smell: `if ((await searchParams).isAdmin === 'true') return <AdminPanel />`. Source: https://nextjs.org/docs/app/guides/data-security#validating-client-input
- **Re-verify the caller inside actions defined on protected pages**: "A page-level authentication check does not extend to the Server Actions defined within it. Always re-verify inside the action" - an inline action is a separate entry point. Why: the page redirect controls rendering, not who can POST to the action. Smell: `redirect('/login')` at the top of the page and an inline `'use server'` action below it that runs `db.record.deleteMany()` with no check. Source: https://nextjs.org/docs/app/guides/data-security#authentication-and-authorization
- **Check ownership of the resource, not just the session**: "This prevents Insecure Direct Object Reference (IDOR) vulnerabilities" - compare the row's owner with the session user before mutating. Why: authentication proves identity, authorisation proves the right to touch this row. Smell: `if (!session) throw ...; await db.post.delete({ where: { id: postId } })` with no `authorId` check. Source: https://nextjs.org/docs/app/guides/data-security#authentication-and-authorization
- **Return only what the UI needs from an action**: "Server Action return values are serialized and sent to the client. Only return what the UI needs, not raw database records." - return `{ success: true }` or a narrow object. Why: the whole return value, including internal fields, goes to the browser. Smell: `return db.user.update({ ... })` as the action's result. Source: https://nextjs.org/docs/app/guides/data-security#controlling-return-values
- **Do not close over secrets in inline actions**: "We don't recommend relying on encryption alone to prevent sensitive values from being exposed on the client." - read secrets inside the action from the DAL instead of capturing them. Why: closed-over variables are sent to the client, encrypted but still transmitted. Smell: `const apiKey = process.env.KEY; async function send() { 'use server'; await call(apiKey) }` inside a component. Source: https://nextjs.org/docs/app/guides/data-security#closures-and-encryption
- **Never perform mutations during render**: "Mutations (e.g. logging out users, updating databases, invalidating caches) should never be a side-effect, either in Server or Client Components." - move writes into a Server Action triggered by a form or event. Why: renders can be repeated, prefetched and cached, and GET requests must stay safe. Smell: `if ((await searchParams).logout) cookieStore.delete('AUTH_TOKEN')` in a page body. Source: https://nextjs.org/docs/app/guides/data-security#avoiding-side-effects-during-rendering
- **Taint the copy if you copy a tainted object (experimental, requires `experimental.taint`)**: "Copying an object creates an untainted version, which loses all guarantees given by the API." - spread, `structuredClone` and `JSON.parse(JSON.stringify())` all drop the taint. Why: taint tracks references only. Smell: `<Client user={{ ...taintedUser }} />`. Source: https://nextjs.org/docs/app/api-reference/config/next-config-js/taint#caveats
- **Taint derived values too, or better, drop the secret from the data (experimental, requires `experimental.taint`)**: "Tainting cannot keep track of data derived from a tainted value. You also need to taint the derived value." - a string built from a tainted value passes to the client untouched. Why: only the exact tainted value or reference is blocked. Smell: `` const v = `version::${config.SERVICE_API_KEY}` `` passed as a prop to a Client Component. Source: https://nextjs.org/docs/app/api-reference/config/next-config-js/taint#caveats

## Authentication and authorisation

- **Keep the session payload minimal and free of PII**: "It should not contain personally identifiable information like phone number, email address, credit card information, etc, or sensitive data like passwords." - store the user ID and role, look up the rest per request. Why: the payload lives in the browser cookie. Smell: `encrypt({ userId, email, phone, passwordHash })`. Source: https://nextjs.org/docs/app/guides/authentication#2-encrypting-and-decrypting-sessions
- **Set the session cookie on the server with the recommended options**: "The cookie should be set on the server, and include the recommended options" - `httpOnly`, `secure`, `sameSite`, an expiry and `path`. Why: client-set cookies can be tampered with and unprotected cookies are readable by scripts. Smell: `document.cookie = 'session=' + token` in client code, or a server `set` call missing `httpOnly` and `secure`. Source: https://nextjs.org/docs/app/guides/authentication#3-setting-cookies-recommended-options
- **Read only the cookie in Proxy auth checks**: "it's important to only read the session from the cookie (optimistic checks), and avoid database checks to prevent performance issues." - decrypt the cookie, decide, and leave database verification to the DAL. Why: Proxy runs on every route, including prefetched ones. Smell: `await db.session.findUnique(...)` inside `proxy.ts`. Source: https://nextjs.org/docs/app/guides/authentication#optimistic-checks-with-proxy-optional
- **Check that auth libraries support the Node.js runtime used by Proxy**: "Proxy uses the Node.js runtime, check if your Auth library and session management library are compatible." - verify imports before using them in `proxy.ts`. Why: Proxy defaults to Node.js in Next 16 and the runtime cannot be changed there. Smell: an edge-only session helper imported into `proxy.ts`. Source: https://nextjs.org/docs/app/guides/authentication#optimistic-checks-with-proxy-optional
- **Run auth Proxy on all routes, excluding only assets**: "Although, for auth, it's recommended Proxy runs on all routes." - use a negative matcher rather than an allow-list of protected paths. Why: an allow-list misses every new protected route. Smell: `matcher: ['/dashboard']` as the only coverage for a growing app. Source: https://nextjs.org/docs/app/guides/authentication#optimistic-checks-with-proxy-optional
- **Do not expect `React.cache` to deduplicate in actions or handlers**: "Server Actions and Route Handlers are not part of a render pass, so the wrapper does nothing and every call runs the function." - call `verifySession()` once and pass the result. Why: cache is scoped to a React render pass. Smell: `verifySession()` called three times in one action on the assumption it runs once. Source: https://nextjs.org/docs/app/guides/authentication#creating-a-data-access-layer-dal
- **Do not make a layout the only auth check**: "be cautious when doing checks in Layouts as these don't re-render on navigation, meaning the user session won't be checked on every route change." - check near the data or in the component being gated. Why: partial rendering skips the layout on client navigation. Smell: `if (!session) redirect('/login')` in `app/(app)/layout.tsx` with no checks in pages or the DAL. Source: https://nextjs.org/docs/app/guides/authentication#layouts-and-auth-checks
- **Do not use `return null` in a layout as a guard**: "A layout also does not control whether the rest of the route renders." - segments and parallel slots still render and appear in the RSC payload. Why: the router renders children independently of what the layout returns. Smell: `if (!authorized) return null` in a layout wrapping sensitive pages. Source: https://nextjs.org/docs/app/guides/authentication#layouts-and-auth-checks
- **Push session reads into a nested Suspense boundary**: "move the `await` into a nested Server Component and wrap it in `<Suspense>` so the rest of the page streams first." - only the user menu should wait on the session. Why: a top-level await in a layout holds `{children}` behind it. Smell: `const user = await getUser()` at the top of the root layout to render an avatar. Source: https://nextjs.org/docs/app/guides/authentication#auth-and-streaming
- **Do not import the DAL from Client Components**: "Client Components can't import the DAL." - run `verifySession()` in a parent Server Component and pass data down or through context. Why: DAL modules are server-only and would either fail the build or leak. Smell: `import { verifySession } from '@/app/lib/dal'` in a file starting with `'use client'`. Source: https://nextjs.org/docs/app/guides/authentication#auth-and-streaming
- **Return 401 for no session and 403 for insufficient role in Route Handlers**: "Treat Route Handlers with the same security considerations as public-facing API endpoints, and verify if the user is allowed to access the Route Handler." - check authentication first, then authorisation. Why: both checks are needed and the status codes mean different things. Smell: a handler that returns 401 for a role failure, or returns data before any session check. Source: https://nextjs.org/docs/app/guides/authentication#route-handlers

## Authentication with Cache Components

- **Put every session read behind Suspense (requires `cacheComponents`)**: "A component that reads the session must sit behind a `<Suspense>` boundary. With Cache Components, reading `cookies()` outside a boundary is a build error." - render the authenticated part inside a boundary and leave the shell static. Why: request reads cannot be prerendered into the static shell. Smell: `await getCurrentUser()` directly in a page body with no `<Suspense>` ancestor. Source: https://nextjs.org/docs/app/guides/authentication-with-cache-components#step-2-show-the-user-without-blocking-the-page
- **Use `use cache: private` for session helpers (requires `cacheComponents`)**: "it reads `cookies()` and `headers()` directly, keeping the result in the browser only, never on the server." - a session helper that validates a cookie cannot use a plain `use cache`. Why: the read is request- and time-dependent and must not be shared across users. Smell: `async function getCurrentUser() { 'use cache'; const { userId } = await getSession() ... }`. Source: https://nextjs.org/docs/app/guides/authentication-with-cache-components#step-1-read-the-current-user
- **Never read `cookies()` or `headers()` inside a plain `use cache` function (requires `cacheComponents`)**: "Reading `cookies()` or `headers()` inside a plain `use cache` function. This throws." - read outside and pass the value in, or use the private variant. Why: a shared cache entry cannot depend on the request. Smell: `'use cache'` followed by `(await cookies()).get(...)`. Source: https://nextjs.org/docs/app/guides/authentication-with-cache-components#common-pitfalls
- **Create the user promise inside the Suspense boundary, not at the top of a layout (requires `cacheComponents`)**: "Because `getCurrentUser` reads the request, create its promise inside the Suspense boundary, not at the top of a layout." - start it in the component that sits inside the boundary and hand it to the provider. Why: a promise created at layout level ties the whole segment to the request. Smell: `const userPromise = getCurrentUser()` in `layout.tsx` outside any boundary. Source: https://nextjs.org/docs/app/guides/authentication-with-cache-components#step-3-share-the-user-across-components
- **Keep ID-keyed cached getters unexported (requires `cacheComponents`)**: "Keep `getNotesByUserId` unexported so a caller can't request another user's notes by passing a different id." - export a wrapper that resolves the user from the session and passes the ID down. Why: a cached function keyed by an argument will serve whatever ID it is given. Smell: `export async function getNotesByUserId(userId) { 'use cache'; ... }` with no auth. Source: https://nextjs.org/docs/app/guides/authentication-with-cache-components#step-4-cache-session-derived-data
- **Keep secrets out of cache arguments and tags (requires `cacheComponents`)**: "Key and tag on a stable identifier like the user id, and keep secrets and sensitive personal data (tokens, passwords, raw emails) out of arguments and tags." - cache keys and tags are stored as plain text. Why: a remote cache receives arguments and tag values unhashed. Smell: `cacheTag(\`session:${token}\`)` or a cached function taking the raw session cookie as an argument. Source: https://nextjs.org/docs/app/guides/authentication-with-cache-components#step-4-cache-session-derived-data
- **Re-read the session inside the action that calls `updateTag` (requires `cacheComponents`)**: "Re-read the session inside the action so it authorizes itself rather than trusting the client." - derive `userId` from the cookie, not from an argument. Why: the action is a public POST and the tag it expires belongs to a user. Smell: `export async function addNote(userId: string, formData)` with `updateTag(\`notes:${userId}\`)`. Source: https://nextjs.org/docs/app/guides/authentication-with-cache-components#step-5-update-session-derived-data

## Auth interrupts: forbidden and unauthorized

- **Enable `authInterrupts` before using `forbidden()` or `unauthorized()` (canary, experimental)**: "While these functions are experimental, you must enable the `authInterrupts` option in your `next.config.js` file to use them" - add `experimental.authInterrupts: true`. Why: the functions are gated behind the flag. Smell: `import { forbidden } from 'next/navigation'` in a project whose config has no `authInterrupts`. Source: https://nextjs.org/docs/app/api-reference/config/next-config-js/authInterrupts
- **Await any function that may call `forbidden()` (requires `authInterrupts`)**: "Always `await` the function that may call it." - the interrupt works by throwing in the render path. Why: an un-awaited promise rejects where nothing catches it and no forbidden UI renders. Smell: `void checkAccess()` or `checkAccess().then(...)` where `checkAccess` calls `forbidden()`. Source: https://nextjs.org/docs/app/api-reference/functions/forbidden#good-to-know
- **Do not wrap `forbidden()` in `try/catch` (requires `authInterrupts`)**: "A `try/catch` around the call suppresses the interrupt and no forbidden UI renders." - rethrow with `unstable_rethrow` if you must catch. Why: the thrown error is the mechanism Next.js uses to render `forbidden.tsx`. Smell: `try { if (!admin) forbidden() } catch (e) { log(e) }`. Source: https://nextjs.org/docs/app/api-reference/functions/forbidden#good-to-know
- **Do not call `unauthorized()` in the root layout (requires `authInterrupts`)**: "The `unauthorized` function cannot be called in the root layout." - call it in pages, nested layouts, actions or handlers. Why: there is no boundary above the root layout to render the UI. Smell: `if (!session) unauthorized()` inside `app/layout.tsx`. Source: https://nextjs.org/docs/app/api-reference/functions/unauthorized#good-to-know
- **Do not expect a 403 status after streaming has started (requires `authInterrupts`)**: "The response starts streaming from the `<Suspense>` boundary before `forbidden()` runs, so it keeps its `200` status." - check in Proxy or before streaming when a real status code matters. Why: once the shell is sent the status cannot change, only a `noindex` tag is added. Smell: a test or API client asserting `403` from a page whose check lives inside a Suspense boundary. Source: https://nextjs.org/docs/app/api-reference/functions/forbidden#calling-forbidden-after-streaming-has-started
- **Use `forbidden()` for authenticated users without permission and `unauthorized()` for unauthenticated ones (requires `authInterrupts`)**: "This ensures that users who are authenticated but lack the required permissions cannot access the route." - the two map to 403 and 401 respectively. Why: the wrong interrupt renders the wrong UI, for example a login form to a signed-in user. Smell: `if (session.role !== 'admin') unauthorized()`. Source: https://nextjs.org/docs/app/api-reference/functions/forbidden#role-based-route-protection

## Content Security Policy

- **Generate a fresh nonce per request in Proxy**: "Every time a page is viewed, a fresh nonce should be generated." - create it inside the proxy function, not at module scope. Why: a predictable or reused nonce defeats the CSP. Smell: `const nonce = crypto.randomUUID()` at the top of `proxy.ts` outside the function, or a nonce read from an environment variable. Source: https://nextjs.org/docs/app/guides/content-security-policy#adding-a-nonce-with-proxy
- **Allow `'unsafe-eval'` in development only**: "`unsafe-eval` is not required for production. Neither React nor Next.js use `eval` in production by default." - branch on `NODE_ENV`. Why: `unsafe-eval` in production weakens the policy for a debugging feature that is off. Smell: `script-src 'self' 'unsafe-eval'` with no environment check. Source: https://nextjs.org/docs/app/guides/content-security-policy#adding-a-nonce-with-proxy
- **Skip prefetches and static assets in the CSP matcher**: "We recommend ignoring matching prefetches (from `next/link`) and static assets that don't need the CSP header." - add `missing` entries for `next-router-prefetch` and `purpose: prefetch` and exclude `_next/static`. Why: those requests do not render a document and the extra work is wasted. Smell: a CSP `proxy.ts` with `matcher: '/:path*'` and no `missing` conditions. Source: https://nextjs.org/docs/app/guides/content-security-policy#adding-a-nonce-with-proxy
- **Set the CSP header on the forwarded request headers, not only the response**: "During rendering, Next.js parses the `Content-Security-Policy` header and extracts the nonce using the `'nonce-{value}'` pattern." - pass it via `NextResponse.next({ request: { headers } })` and also on the response. Why: Next.js reads the nonce from the request header during server rendering. Smell: `response.headers.set('Content-Security-Policy', csp)` with no matching `requestHeaders.set(...)`. Source: https://nextjs.org/docs/app/guides/content-security-policy#how-nonces-work-in-nextjs
- **Accept that nonce CSP forces dynamic rendering everywhere**: "Static optimization and Incremental Static Regeneration (ISR) are disabled" - and Partial Prerendering is incompatible because the static shell cannot carry a per-request nonce. Why: nonces are injected during server-side rendering, which needs a request. Smell: a nonce-based CSP added to an app that relies on ISR or `cacheComponents` static shells. Source: https://nextjs.org/docs/app/guides/content-security-policy#dynamic-rendering-requirement

## Draft Mode

- **Use `POST` for operations that change future requests**: "`GET` is meant to be a safe, read-only method. Operations that affect future requests, like enabling Draft Mode via a cookie, should use `POST`." - the `GET` entry handler is only tolerated because a CMS opens it in a tab; exit via a Server Action or `POST`. Why: `GET` requests can be prefetched, cached and logged. Smell: a `GET` route that toggles state for any visitor without a CMS contract. Source: https://nextjs.org/docs/app/guides/draft-mode#what-this-guide-covers
- **Never ship a draft-enable handler without a secret**: "As written, the handler is public: anyone who hits `/api/draft` enables Draft Mode for themselves." - require a shared secret and fail with 401 otherwise. Why: Draft Mode bypasses every cache and exposes unpublished content. Smell: `draft.enable()` with no token comparison. Source: https://nextjs.org/docs/app/guides/draft-mode#step-1-create-a-route-handler
- **Validate the secret and slug, then redirect to the fetched path**: "check that the secret matches and that the `slug` parameter exists (if not, the request should fail)" - look the slug up in the CMS and redirect to the returned path, not the query value. Why: redirecting to the raw `slug` parameter is an open redirect. Smell: `redirect(searchParams.get('slug'))` straight after `draft.enable()`. Source: https://nextjs.org/docs/app/guides/draft-mode#step-2-access-the-route-handler-from-your-headless-cms
- **Toggle Draft Mode outside caching directive scopes**: "`draftMode().enable()` and `draftMode().disable()` cannot be called inside a caching directive scope" - call them from a Route Handler or Server Action; only `isEnabled` is readable inside `use cache`. Why: enabling sets a cookie, which is a request-time side effect. Smell: `draft.enable()` inside a `'use cache'` function. Source: https://nextjs.org/docs/app/guides/draft-mode#draft-mode-with-cache-components
- **Disable prefetching on links to a Draft Mode exit route**: "If calling the route using the `<Link>` component, you must pass `prefetch={false}` to prevent accidentally deleting the cookie on prefetch." - or use a form submission instead of a link. Why: `<Link>` prefetches by default, which would clear the cookie before the click. Smell: `<Link href="/api/disable-draft">Exit preview</Link>`. Source: https://nextjs.org/docs/app/api-reference/functions/draft-mode#disabling-draft-mode

## Server Actions and proxy body configuration

- **Write `allowedOrigins` entries as host, including the port**: "Only the `host` of the request's `Origin` header is matched against your entries, which is the hostname plus the port when the URL carries one." - no scheme, no path; include `:8443` when the browser URL has it. Why: an entry with a scheme never matches and the action is rejected. Smell: `allowedOrigins: ['https://my-proxy.com']`. Source: https://nextjs.org/docs/app/api-reference/config/next-config-js/serverActions#allowedorigins
- **Use `*` for one label and `**` for several in `allowedOrigins`**: "a `*` stands in for exactly one label of the host, and `**` for one or more." - list the bare host separately; partial labels and wildcard ports are unsupported. Why: `*.example.com` does not match `example.com` or `a.b.example.com`. Smell: `allowedOrigins: ['*.my-proxy.com']` alone when actions are also submitted from `my-proxy.com`. Source: https://nextjs.org/docs/app/api-reference/config/next-config-js/serverActions#allowedorigins
- **Leave headroom in `bodySizeLimit` for multipart overhead**: "If you expect uploads close to the configured value, leave some room for this overhead." - the limit counts boundaries and part headers, not just the file. Why: a 1 MB file in a `multipart/form-data` body exceeds a 1 MB limit. Smell: `bodySizeLimit: '1mb'` paired with a UI that allows 1 MB uploads. Source: https://nextjs.org/docs/app/api-reference/config/next-config-js/serverActions#bodysizelimit
- **Raise `proxyClientMaxBodySize` when Proxy must see large bodies (experimental)**: "The request will continue processing normally, but only the partial body will be available" - the default 10 MB buffer truncates silently with only a console warning. Why: a handler that parses the truncated body gets corrupt input and no error. Smell: an upload route behind `proxy.ts` accepting 20 MB files with the default limit. Source: https://nextjs.org/docs/app/api-reference/config/next-config-js/proxyClientMaxBodySize#behavior

## Config headers, redirects and rewrites

- **Order `headers()` entries so the intended value comes last**: "If two headers match the same path and set the same header key, the last header key will override the first." - put the specific override after the general rule. Why: later entries win for the same key. Smell: a `/admin` `Cache-Control` entry listed before a `/:path*` entry that sets the same key. Source: https://nextjs.org/docs/app/api-reference/config/next-config-js/headers#header-overriding-behavior
- **Escape regex characters used literally in `source`**: "so when used in the `source` as non-special values they must be escaped by adding `\\` before them" - `(`, `)`, `{`, `}`, `:`, `*`, `+`, `?` are pattern syntax. Why: an unescaped character changes the match or fails to compile. Smell: `source: '/docs(v2)/:slug'`. Source: https://nextjs.org/docs/app/api-reference/config/next-config-js/headers#regex-path-matching
- **Do not try to override `Cache-Control` for hashed static assets**: "Next.js sets the `Cache-Control` header of `public, max-age=31536000, immutable` for truly immutable assets. It cannot be overridden." - target other responses instead. Why: files with a content hash are safe to cache forever and the header is fixed. Smell: a `headers()` entry for `/_next/static/:path*` setting `Cache-Control`. Source: https://nextjs.org/docs/app/api-reference/config/next-config-js/headers#cache-control
- **Scope `Access-Control-Allow-Origin` to real origins**: "Cross-Origin Resource Sharing (CORS) is a security feature that allows you to control which sites can access your resources." - replace the placeholder `*` with the specific origins that need access. Why: a wildcard on an authenticated API opens it to every site. Smell: `{ key: 'Access-Control-Allow-Origin', value: '*' }` on `/api/:path*` that reads cookies. Source: https://nextjs.org/docs/app/api-reference/config/next-config-js/headers#cors
- **Use `permanent: true` only for redirects that will never change**: "if `true` will use the 308 status code which instructs clients/search engines to cache the redirect forever" - temporary moves use `permanent: false` (307). Why: a cached 308 cannot be undone in browsers that already saw it. Smell: `permanent: true` on an experiment or seasonal redirect. Source: https://nextjs.org/docs/app/api-reference/config/next-config-js/redirects
- **Put a slash before every path parameter**: "Remember to include the forward slash `/` before the colon `:` in path parameters of the `source` and `destination` paths" - `/old:path*` is a literal, not a parameter. Why: a literal source can match its own destination and loop. Smell: `source: '/old-blog:path*'`. Source: https://nextjs.org/docs/app/api-reference/config/next-config-js/redirects
- **Do not redirect a path that a real route also serves**: "Redirects are checked before the filesystem which includes pages and `/public` files." - the redirect wins and the page becomes unreachable. Why: config redirects run before file-system routing. Smell: `source: '/about'` in `redirects()` while `app/about/page.tsx` exists. Source: https://nextjs.org/docs/app/api-reference/config/next-config-js/redirects
- **Pass unused rewrite parameters explicitly when another is used**: "If a parameter is used in the destination none of the parameters will be automatically passed in the query." - add `?second=:second` to the destination. Why: automatic query forwarding stops as soon as any parameter appears in the destination. Smell: `source: '/:first/:second', destination: '/:first'` with code reading `second` from the query. Source: https://nextjs.org/docs/app/api-reference/config/next-config-js/rewrites#rewrite-parameters
- **Use `fallback` rewrites for incremental adoption, not a catch-all in `afterFiles`**: "You can also have Next.js fall back to proxying to an existing website after checking all Next.js routes." - `fallback` runs after dynamic routes, so it never shadows them. Why: a `/:path*` rewrite earlier in the chain hides dynamic routes. Smell: `afterFiles: [{ source: '/:path*', destination: 'https://old-site.com/:path*' }]`. Source: https://nextjs.org/docs/app/api-reference/config/next-config-js/rewrites#incremental-adoption-of-nextjs

## Proxy flags and dev origins

- **Leave `skipProxyUrlNormalize` off unless you rewrite with a custom `fetch`**: "Most projects don't need this option." - it exposes internal `_rsc` params and navigation headers; the `matcher` still matches the destination URL without it. Why: the flag changes what Proxy sees and returns, not which routes it runs on. Smell: `skipProxyUrlNormalize: true` added to restrict Proxy to certain paths. Source: https://nextjs.org/docs/app/api-reference/config/next-config-js/skipProxyUrlNormalize
- **Rename `skipMiddlewareUrlNormalize` and never set both**: "It still works and logs a deprecation warning. Setting both at once throws" - the v16 codemod renames it. Why: the old alias is deprecated and the pair is a hard error. Smell: both `skipMiddlewareUrlNormalize` and `skipProxyUrlNormalize` in `next.config.ts`. Source: https://nextjs.org/docs/app/api-reference/config/next-config-js/skipProxyUrlNormalize#deprecated-alias
- **Set a canonical URL when `skipTrailingSlashRedirect` is on**: "Serving one page at both `/about` and `/about/` gives search engines two URLs for it." - add `alternates.canonical` in metadata or redirect in Proxy. Why: both forms return 200 once the automatic redirect is disabled. Smell: `skipTrailingSlashRedirect: true` with no canonical metadata and no trailing-slash handling in `proxy.ts`. Source: https://nextjs.org/docs/app/api-reference/config/next-config-js/skipTrailingSlashRedirect#good-to-know
- **Write `allowedDevOrigins` entries as bare hostnames**: "Write your entries that way too, without `https://` and without a port." - `*` matches one label and `**` one or more, so list the bare host and the wildcard separately. Why: scheme, port and path are ignored in matching, so an entry with them never matches. Smell: `allowedDevOrigins: ['https://dev.example.com:3000']`. Source: https://nextjs.org/docs/app/api-reference/config/next-config-js/allowedDevOrigins
