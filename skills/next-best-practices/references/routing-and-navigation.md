# Next.js 16 code-review rules: routing and navigation

Extracted 2026-11-10 from the Next.js 16.4.5 App Router documentation (MIT, Vercel, Inc.). One rule per bullet, one source link each. Quotations are short excerpts; the rest is original.

## Project structure and file conventions

- **Expose a route only with a `page` or `route` file**: "A route becomes public when a `page` or `route` file exists." - a folder on its own defines a segment but serves nothing, so helper files can live beside routes. Why: only the content returned by `page.js` or `route.js` is sent to the client. Smell: `app/admin/layout.tsx` with no `page.tsx`, and a test or link that expects `/admin` to render. Source: https://nextjs.org/docs/app/getting-started/project-structure#nested-routes
- **Use `_folder` to opt helper folders out of routing**: "This indicates the folder is a private implementation detail and should not be considered by the routing system" - prefix a folder with an underscore when it holds components or utilities, and the folder and all its subfolders stop being route segments. Why: it avoids naming conflicts with future Next.js file conventions and separates UI logic from routing logic. Smell: `app/dashboard/components/page.tsx` added for a demo and silently served at `/dashboard/components`. Source: https://nextjs.org/docs/app/getting-started/project-structure#private-folders
- **Use route groups to share a layout without changing the URL**: "The folders in parenthesis will be omitted from the URL" - wrap a folder in `(name)` to group routes by section or team and give the group its own `layout.js`. Why: it lets you opt a subset of routes into a layout while keeping the URL hierarchy flat. Smell: a `shop/` folder added purely to share a layout, forcing every cart route to live under `/shop/`. Source: https://nextjs.org/docs/app/getting-started/project-structure#organize-routes-without-affecting-the-url-path
- **Never let two route groups resolve to the same path**: "Routes in different groups should not resolve to the same URL path." - a page may exist under only one group for a given URL. Why: `(marketing)/about/page.js` and `(shop)/about/page.js` both resolve to `/about` and the build errors. Smell: a diff adding `app/(shop)/about/page.tsx` while `app/(marketing)/about/page.tsx` already exists. Source: https://nextjs.org/docs/app/api-reference/file-conventions/route-groups#caveats
- **Expect a full page load when crossing root layouts**: "If you navigate between routes that use different root layouts, it'll trigger a full page reload." - a `<Link>` between two route groups that each own a root layout is not a client-side transition. Why: the `<html>` and `<body>` elements are replaced, so client state is lost. Smell: a `<Link>` from `(shop)/cart` to `(marketing)/blog` paired with context state the author expects to survive. Source: https://nextjs.org/docs/app/api-reference/file-conventions/route-groups#caveats
- **Define the home route inside a group when there is no top-level layout**: "make sure your home route (/) is defined within one of the route groups" - with multiple root layouts and no `app/layout.js`, `/` must come from `app/(group)/page.js`. Why: otherwise no root layout wraps `/` and the route fails. Smell: a diff that deletes `app/layout.tsx` to create per-group root layouts but leaves `app/page.tsx` in place. Source: https://nextjs.org/docs/app/api-reference/file-conventions/route-groups#caveats
- **Give every root layout its own `<html>` and `<body>`**: "The `<html>` and `<body>` tags need to be added to each root layout." - any layout with no `layout.js` above it is a root layout and must produce the document shell. Why: Next.js does not inject those elements for you. Smell: `app/(shop)/layout.tsx` returning a `<main>` fragment after `app/layout.tsx` was removed. Source: https://nextjs.org/docs/app/getting-started/project-structure#creating-multiple-root-layouts
- **Keep `public` at the project root when using `src`**: "The `/public` directory should remain in the root of your project." - only application code moves under `src`; config files, `.env.*` and `public` stay at the root. Why: static files are served from the root `public` folder only. Smell: `src/public/logo.png` referenced as `/logo.png`. Source: https://nextjs.org/docs/app/api-reference/file-conventions/src-folder
- **Put `proxy.ts` inside `src` when the app lives there**: "If you're using Proxy, ensure it is placed inside the `src` folder." - the proxy file follows the `app` folder, not the config files. Why: a root-level `proxy.ts` is not picked up for a `src/app` project. Smell: `src/app/` alongside a root `proxy.ts` whose redirects never fire. Source: https://nextjs.org/docs/app/api-reference/file-conventions/src-folder
- **Use metadata file conventions, not `public`, for robots and favicons**: "For static metadata files, such as `robots.txt`, `favicon.ico`, etc, you should use special metadata files inside the `app` folder." - place `app/robots.txt`, `app/icon.png` or `app/sitemap.ts` rather than dropping them in `public`. Why: the metadata conventions integrate with the Metadata API and route generation. Smell: `public/robots.txt` or `public/favicon.ico` added in a diff. Source: https://nextjs.org/docs/app/api-reference/file-conventions/public-folder#robots-favicons-and-others

## Layouts and pages

- **Accept and render `children` in every layout**: "Layout components should accept and use a `children` prop." - the prop carries the nested layout, page or special file for the segment. Why: a layout that drops `children` renders nothing below it. Smell: `export default function Layout() { return <Nav /> }` with no `{children}` in the output. Source: https://nextjs.org/docs/app/api-reference/file-conventions/layout#children-required
- **Use the Metadata API instead of hand-written `<head>` tags**: "Instead, use the Metadata APIs which automatically handles advanced requirements such as streaming and de-duplicating `<head>` elements." - export `metadata` or `generateMetadata` rather than placing `<title>` or `<meta>` in a root layout. Why: manual head tags are not de-duplicated or streamed correctly. Smell: `<head><title>My App</title></head>` inside `app/layout.tsx`. Source: https://nextjs.org/docs/app/api-reference/file-conventions/layout#metadata
- **Await `params` and `searchParams`; they are promises**: "Since the `params` prop is a promise, you must use `async/await` or React's `use` function to access the values." - in Client Components, which cannot be `async`, unwrap with `use(params)`. Why: synchronous access still works in Next.js 15 for backwards compatibility but is deprecated and will be removed. Smell: `const { slug } = params` with no `await`, or an `async` component marked `'use client'`. Source: https://nextjs.org/docs/app/api-reference/file-conventions/page#params-optional
- **Treat `searchParams` as a plain object, not `URLSearchParams`**: "`searchParams` is a plain JavaScript object, not a `URLSearchParams` instance." - read keys by property and expect `string | string[] | undefined`. Why: repeated keys arrive as arrays and there is no `.get()` method. Smell: `(await searchParams).get('q')` or `searchParams.has('page')` in a page. Source: https://nextjs.org/docs/app/api-reference/file-conventions/page#searchparams-optional
- **Know that reading `searchParams` makes the page dynamic**: "Using `searchParams` opts your page into dynamic rendering because it requires an incoming request to read the search parameters from." - use the prop when the query drives data loading; use `useSearchParams` in a Client Component when the query is only used on the client. Why: a page the author expected to be static becomes request-rendered. Smell: `await searchParams` added to a page that was previously prerendered, only to toggle a client-side filter. Source: https://nextjs.org/docs/app/getting-started/layouts-and-pages#rendering-with-search-params
- **Do not read search params or pathname in a layout**: "Layouts do not rerender on navigation, so they cannot access search params which would otherwise become stale." - read the `searchParams` prop in the page, or `useSearchParams` and `usePathname` in a Client Component. Why: a layout keeps its first render across navigations, so any URL-derived value in it goes stale. Smell: a layout signature destructuring `searchParams`, or a layout computing active links from `params`. Source: https://nextjs.org/docs/app/api-reference/file-conventions/layout#query-params
- **Wrap runtime data in a layout in `<Suspense>` or move it to the page**: "Move uncached data fetching from `layout.js` into `page.js` where `loading.js` can show a fallback." - `loading.js` sits below the layout, so `cookies()`, `headers()` or uncached fetches in the layout are not covered by it. Why: without Cache Components the navigation blocks until the layout renders; with Cache Components (requires `cacheComponents`) the build errors unless the access is in its own boundary. Smell: `const store = await cookies()` at the top of `layout.tsx` beside a `loading.tsx`. Source: https://nextjs.org/docs/app/api-reference/file-conventions/layout#interaction-with-loadingjs
- **Fetch the same data in layout and page instead of passing it down**: "Layouts cannot pass data to their `children`." - call the same fetch in both places and rely on React `cache` or automatic `fetch` deduplication. Why: there is no channel from layout to page, and duplicate requests are deduped within a render. Smell: `React.cloneElement(children, { user })` or a context created only to push layout data into a page. Source: https://nextjs.org/docs/app/api-reference/file-conventions/layout#fetching-data
- **Extract client hooks into a Client Component imported by the layout**: "Since `usePathname` is a client hook, you need to extract the nav links into a Client Component, which can be imported into your layout" - keep the layout a Server Component and import a small `'use client'` nav. Why: marking the whole layout as a Client Component ships it to the browser and loses server rendering of its children. Smell: `'use client'` added at the top of `layout.tsx` only so `usePathname` compiles. Source: https://nextjs.org/docs/app/api-reference/file-conventions/layout#active-nav-links
- **Type route files with `PageProps` and `LayoutProps`**: "Using a literal route (e.g. `'/blog/[slug]'`) enables autocomplete and strict keys for `params`." - the helpers are global after `next dev`, `next build` or `next typegen` and infer `params`, `searchParams` and named slots. Why: hand-written prop types drift from folder names and miss slots. Smell: `{ params: Promise<{ id: string }> }` written by hand in `app/posts/[slug]/page.tsx`. Source: https://nextjs.org/docs/app/api-reference/file-conventions/page#page-props-helper
- **Validate params against a known set and narrow the type**: "Route `params` values are typed as `string`, `string[]`, or `undefined` (for optional catch-all segments), because their values aren't known until runtime." - check the value with a type guard and call `notFound()` for anything outside the set. Why: users can type any URL, so an unchecked cast lets invalid values reach data access. Smell: `const locale = (await params).locale as Locale`. Source: https://nextjs.org/docs/app/api-reference/file-conventions/dynamic-routes#typescript

## Templates

- **Reach for `template.js` only when children must remount on navigation**: "Unlike layouts that persist across routes and maintain state, templates are given a unique key, meaning children Client Components reset their state on navigation." - use it to resynchronise effects, reset inputs or show Suspense fallbacks on every navigation; otherwise use a layout. Why: a template remounts its subtree whenever its segment changes, which discards state a layout would keep, and search param changes do not remount it. Smell: a `template.tsx` wrapping a sidebar whose open or closed state is expected to persist across pages. Source: https://nextjs.org/docs/app/api-reference/file-conventions/template

## Loading UI and streaming

- **Add `loading.tsx` to dynamic routes**: "We recommend adding `loading.tsx` to dynamic routes to enable partial prefetching, trigger immediate navigation, and display a loading UI while the route renders." - a dynamic route with no loading file is not prefetched and blocks until the server responds. Why: the fallback is prefetched with the layout, so navigation is immediate and interruptible. Smell: `app/blog/[slug]/page.tsx` with an uncached fetch and no `loading.tsx` in the segment. Source: https://nextjs.org/docs/app/getting-started/linking-and-navigating#dynamic-routes-without-loadingtsx
- **Run `notFound()`, `redirect()` and auth checks before streaming starts when the status code matters**: "Run the corresponding check before the response body streams to return a `404`, `403`, or `401` status for compliance or analytics." - once a Suspense fallback renders the response is already `200`, and a later `notFound()` only adds a `noindex` tag. Why: the first bytes fix the status code. Smell: an existence check placed inside a Suspense child while monitoring or SEO relies on a real `404`. Source: https://nextjs.org/docs/app/api-reference/file-conventions/loading#status-codes
- **Keep Proxy 404 checks cheap**: "Keep Proxy checks fast, and avoid fetching full content there." - check a slug or key in Proxy and rewrite to a not-found route, but do not load the whole entity. Why: Proxy runs on every matching request, so heavy fetches slow the whole site. Smell: `proxy.ts` calling the CMS for the full article body to decide whether to 404. Source: https://nextjs.org/docs/app/api-reference/file-conventions/loading#status-codes

## Not found

- **Call `notFound()` in the render path, never in a floating promise**: "A call left in an un-awaited promise throws where nothing catches it, and no not-found UI renders" - call it from a component, or from a function the component awaits. Why: it works by throwing, and an unhandled rejection never reaches the not-found boundary. Smell: `fetchUser(id).then((u) => { if (!u) notFound() })` without `await`. Source: https://nextjs.org/docs/app/api-reference/functions/not-found
- **Do not wrap `notFound()` in `try/catch`**: "If you need to catch errors near the call, use `unstable_rethrow` to let the interrupt through first." - a catch block swallows the thrown interrupt and the 404 UI never renders. Why: the function signals by throwing a `NEXT_HTTP_ERROR_FALLBACK;404` error. Smell: `try { const post = await getPost(slug); if (!post) notFound() } catch (e) { log(e) }`. Source: https://nextjs.org/docs/app/api-reference/functions/not-found#good-to-know
- **Do the existence check inside a Suspense-wrapped component when the shell should stay visible**: "do the existence check inside a component wrapped in `<Suspense>` instead of blocking the whole route." - put the check in the data-access function awaited by the child, and add a `not-found.tsx` beside the route so the nearest boundary is your own. Why: the shell and loading UI stay on screen and the not-found UI replaces only the streamed content. Smell: a page that awaits the entity at the top solely to call `notFound()`, delaying everything else. Source: https://nextjs.org/docs/app/api-reference/functions/not-found#calling-notfound-after-streaming-has-started
- **Return a full document from `global-not-found.js` (experimental, requires `experimental.globalNotFound`)**: "Unlike `not-found.js`, this file must return a full HTML document, including `<html>` and `<body>` tags." - import global styles, fonts and theme attributes in the file itself because it bypasses the root layout. Why: the file is served at the routing level with no layout around it. Smell: `app/global-not-found.tsx` returning a bare `<div>` and relying on `globals.css` imported in the root layout. Source: https://nextjs.org/docs/app/api-reference/file-conventions/not-found#global-not-foundjs-experimental

## Dynamic routes and generateStaticParams

- **Add `generateStaticParams` to dynamic segments that could be prerendered**: "If a dynamic segment could be prerendered but isn't because it's missing `generateStaticParams`, the route will fallback to dynamic rendering at request time." - return the known param objects so the pages are built ahead of time. Why: a route that could be static is rendered on every request and loses full prefetching. Smell: `app/blog/[slug]/page.tsx` whose data source is a finite list but exports no `generateStaticParams`. Source: https://nextjs.org/docs/app/getting-started/linking-and-navigating#dynamic-segments-without-generatestaticparams
- **Always return an array from `generateStaticParams`**: "You must always return an array from `generateStaticParams`, even if it's empty." - an empty array means all paths render on first visit; anything else makes the route dynamic. Why: the return type decides whether the route is prerenderable at all. Smell: an early `return` in a conditional branch of `generateStaticParams`, or `return null` when the API fails. Source: https://nextjs.org/docs/app/api-reference/functions/generate-static-params#all-paths-at-runtime
- **Return at least one param under Cache Components (requires `cacheComponents`)**: "Empty arrays cause a build error." - Cache Components uses the sample params to validate that the route handles `cookies()`, `headers()` and `searchParams` correctly, and a placeholder param defeats that validation. Why: with no sample there is nothing to validate against at build time. Smell: `export async function generateStaticParams() { return [] }` in an app with `cacheComponents: true`. Source: https://nextjs.org/docs/app/api-reference/functions/generate-static-params#with-cache-components
- **Generate params only for the segment's own level and above**: "A child route segment's `generateStaticParams` function is executed once for each segment a parent `generateStaticParams` generates." - a layout in `[category]` can emit `category` only; the `[product]` page emits `product`, optionally using the parent's `params` argument. Why: a parent cannot know its children's values and the child runs once per parent result. Smell: `app/products/[category]/layout.tsx` returning `{ category, product }` pairs. Source: https://nextjs.org/docs/app/api-reference/functions/generate-static-params#generate-params-from-the-top-down
- **Use `dynamicParams = false` to 404 paths not returned by `generateStaticParams`**: "When this config option is used, only paths provided by `generateStaticParams` will be served, and unspecified routes will 404 or match" - export it when unknown slugs must never render on demand (not available with `cacheComponents`, see below). Why: the default lets any slug render at request time. Smell: a route documented as serving only a fixed list but with no `dynamicParams` export, so `/blog/anything` renders. Source: https://nextjs.org/docs/app/api-reference/functions/generate-static-params#disable-rendering-for-unspecified-paths
- **Remove `dynamic`, `dynamicParams`, `revalidate` and `fetchCache` when enabling Cache Components (Next 16)**: "`dynamic`, `dynamicParams`, `revalidate`, and `fetchCache` removed when Cache Components is enabled." - those segment configs belong to the previous caching model and are replaced by `use cache`, `cacheLife` and Suspense. Why: Next.js 16 removes them under `cacheComponents`. Smell: `export const revalidate = 60` or `export const dynamic = 'force-dynamic'` in a project with `cacheComponents: true`. Source: https://nextjs.org/docs/app/api-reference/file-conventions/route-segment-config#version-history
- **Wrap param access in Suspense when there is no `generateStaticParams` (requires `cacheComponents`)**: "Param access must be wrapped by Suspense fallback UI." - pass the `params` promise into a child rendered inside `<Suspense>` or use `loading.tsx`. Why: the static shell cannot include values that are only known at request time. Smell: `const { slug } = await params` at the top of a page body with no boundary and no `generateStaticParams`. Source: https://nextjs.org/docs/app/api-reference/file-conventions/dynamic-routes#without-generatestaticparams
- **Pass the `params` promise down from layouts instead of awaiting it at the top (requires `cacheComponents`)**: "In layouts, avoid awaiting `params` at the top level." - await inside the component that needs the value. Why: a top-level await prevents the layout from being prerendered. Smell: `const { team } = await params` in `layout.tsx` when only a heading needs it. Source: https://nextjs.org/docs/app/api-reference/file-conventions/dynamic-routes#without-generatestaticparams
- **Wrap conditional runtime access in Suspense even when sample params pass the build (requires `cacheComponents`)**: "Build-time validation only covers code paths that execute with the sample params." - a branch that reads `cookies()` for slugs not in the samples is validated on first request and fails there. Why: only executed branches are checked at build. Smell: `if (slug.startsWith('private-')) return <PrivatePost />` where `PrivatePost` reads `cookies()` without a boundary. Source: https://nextjs.org/docs/app/api-reference/file-conventions/dynamic-routes#with-generatestaticparams

## Parallel and intercepting routes

- **Add a `default.js` for every slot, including the implicit `children` slot**: "If `default.js` doesn't exist, an error is returned for named slots (`@team`, `@analytics`, etc) and requires you to define a `default.js` in order to continue." - on a hard navigation Next.js cannot recover a slot's active subpage and renders `default.js` instead. Why: refreshes and deep links otherwise error or 404. Smell: a new `@analytics` folder with `page.tsx` but no `default.tsx`. Source: https://nextjs.org/docs/app/api-reference/file-conventions/default
- **Authorise inside each slot, not in the layout's conditional**: "Both slots render on the server, regardless of which one the layout returns." - the conditional chooses what is displayed, not what runs, so `@admin/page.js` still fetches and its output is in the response. Why: a role check in the layout is not an access control. Smell: `return role === 'admin' ? admin : user` while `@admin/page.tsx` calls `getAdminStats()` with no check. Source: https://nextjs.org/docs/app/api-reference/file-conventions/parallel-routes#conditional-routes
- **Keep all slots at one level either static or dynamic**: "If one slot is dynamic, all slots at that level must be dynamic." - slots are combined with the page into one route, so they cannot be prerendered separately. Why: slots are not route segments and share the segment's rendering mode. Smell: `@feed/page.tsx` reading `cookies()` while the author expects `@sidebar` to stay prerendered. Source: https://nextjs.org/docs/app/api-reference/file-conventions/parallel-routes#slots
- **Return `null` from a modal slot's `default.js`**: "This ensures that the modal is not rendered when it's not active." - the default for `@auth` or `@modal` must render nothing. Why: otherwise the modal appears on every page load that does not match the intercepted route. Smell: `app/@modal/default.tsx` rendering the `<Modal>` shell. Source: https://nextjs.org/docs/app/api-reference/file-conventions/parallel-routes#modals
- **Add a `null` catch-all page to a modal slot so links close it**: "Since client-side navigations to a route that no longer match the slot will remain visible, we need to match the slot to a route that returns `null` to close the modal." - add `@modal/[...catchAll]/page.tsx` returning `null`, or a matching `page.tsx` per destination. Why: a slot keeps its last active state on soft navigation. Smell: `<Link href="/">Close</Link>` inside a modal with no catch-all in the slot, so the modal persists on `/`. Source: https://nextjs.org/docs/app/api-reference/file-conventions/parallel-routes#closing-the-modal
- **Count interception levels in route segments, not folders**: "The `(..)` convention is based on _route segments_, not the file-system." - `@slot` folders and route groups do not count as levels. Why: `app/feed/@modal/(..)photo` intercepts `app/photo` because `@modal` is not a segment. Smell: `@modal/(..)(..)photo` used because the folder is two directories deep. Source: https://nextjs.org/docs/app/api-reference/file-conventions/intercepting-routes#convention

## Link component

- **Use `<Link>` for in-app navigation**: "`<Link>` is the primary way to navigate between routes in Next.js." - it extends `<a>` with prefetching and client-side transitions. Why: a plain anchor triggers a full page load that resets state and scroll. Smell: `<a href="/dashboard">` for an internal route. Source: https://nextjs.org/docs/app/getting-started/layouts-and-pages#linking-between-pages
- **Prefer `<Link>` over `useRouter` for navigation**: "Use the `<Link>` component for navigation unless you have a specific requirement for using `useRouter`." - reserve `router.push` for navigation triggered inside event handlers after some other work. Why: only `<Link>` prefetches on viewport entry and renders a real anchor. Smell: `<button onClick={() => router.push('/about')}>About</button>` with no other logic in the handler. Source: https://nextjs.org/docs/app/api-reference/functions/use-router
- **Use `onNavigate`, not `onClick`, to intercept or block client navigation**: "`onClick` executes for all click events, while `onNavigate` only runs during client-side navigation." - `onNavigate` receives `preventDefault()` and skips modifier-key clicks, external URLs and downloads. Why: an `onClick` guard also breaks opening in a new tab. Smell: `onClick={(e) => { if (dirty && !confirm()) e.preventDefault() }}` on a `<Link>`. Source: https://nextjs.org/docs/app/api-reference/components/link#onnavigate
- **Offset sticky headers with `scroll-padding-top`**: "Because Next.js skips sticky and fixed positioned elements when finding the scroll target, content may end up behind a sticky header after navigation." - set `scroll-padding-top` on `html` or `scroll-margin-top` on targets. Why: the router scrolls with native `scrollIntoView`, which honours those properties. Smell: a `useEffect` that calls `window.scrollBy(0, -64)` after each pathname change. Source: https://nextjs.org/docs/app/api-reference/components/link#scroll-offset-with-sticky-headers
- **Give `<Link>` both `as` and `href` when Proxy rewrites the destination**: "In order for the `<Link />` component to properly prefetch links with rewrites via Proxy, you need to tell Next.js both the URL to display and the URL to prefetch." - `as` is the visible URL and `href` the rewritten route. Why: otherwise the prefetch goes through Proxy or targets the wrong route. Smell: `<Link href="/dashboard">` where `proxy.ts` rewrites `/dashboard` to `/auth/dashboard`. Source: https://nextjs.org/docs/app/api-reference/components/link#prefetching-links-in-proxy
- **Use `replace` or `history.replaceState` for URL state the user should not back into**: "The user is not able to navigate back to the previous state." - locale switches or sort toggles that would otherwise fill the history stack belong in `replaceState` or `<Link replace>`. Why: `pushState` and `router.push` add an entry per change. Smell: `router.push` called on every keystroke of a search box. Source: https://nextjs.org/docs/app/getting-started/linking-and-navigating#windowhistoryreplacestate

## Prefetching

- **Judge prefetching in production, not `next dev`**: "Automatic prefetching runs only in production." - test prefetch and instant navigation on `next build && next start`, and run baseline `instant()` tests against a production build. Why: dev never prefetches, so missing skeletons and slow transitions in dev are not evidence. Smell: a PR note saying prefetch does not work, verified only on the dev server. Source: https://nextjs.org/docs/app/guides/prefetching#automatic-prefetch
- **Disable or defer prefetching for large link lists**: "This is useful to avoid unnecessary usage of resources when rendering large lists of links (e.g. an infinite scroll table)." - set `prefetch={false}`, or prefetch on hover. Why: every link entering the viewport otherwise schedules a prefetch. Smell: a 500-row table of default `<Link>`s. Source: https://nextjs.org/docs/app/getting-started/linking-and-navigating#disabling-prefetching
- **Restore the default with `null` or `'auto'`, never `true` versus `false`**: "`prefetch={null}` restores default prefetching once the user shows intent." - under Partial Prefetching use `prefetch={active ? true : 'auto'}` (requires `partialPrefetching`). Why: `false` before intent disables the App Shell prefetch, and `true` by default forces a server render per link. Smell: `prefetch={isFeatured ? true : false}` or `prefetch={hovered ? true : false}`. Source: https://nextjs.org/docs/app/guides/prefetching#hover-triggered-prefetch
- **Keep layouts and pages pure; side effects run during prefetch**: "If your layouts or pages are not pure and have side-effects (e.g. tracking analytics), Next.js might run them when the route is prefetched, not when the user visits the page." - move tracking into a `useEffect` in a Client Component or a Server Action. Why: prefetch renders the route before any visit. Smell: `trackPageView()` called in a layout or page body. Source: https://nextjs.org/docs/app/guides/prefetching#triggering-unwanted-side-effects-during-prefetching
- **Prevent default before `router.push` on a hand-rolled anchor**: "Use `onClick` to prevent it, then call `router.push` to navigate on the client." - ejecting from `<Link>` makes you responsible for prefetching, cache invalidation and accessibility. Why: without `preventDefault` the browser reloads the page before the client navigation. Smell: `<a href={href} onClick={() => router.push(href)}>`. Source: https://nextjs.org/docs/app/guides/prefetching#extending-or-ejecting-link
- **Do not opt links into `prefetch={true}` by default**: "Each visible `<Link prefetch={true}>` can wake a server, and that cost only pays off if more of the page is ready before the click" - use it only where URL data (`params`, `searchParams`) drives cached content and traffic justifies it. Why: a grid of cards makes one server request per card. Smell: `prefetch` added to every item in a product grid. Source: https://nextjs.org/docs/app/guides/optimizing-prefetching#trade-offs

## Partial Prefetching and navigation stages (requires `cacheComponents`)

- **Set `partialPrefetching` explicitly once `cacheComponents` is on**: "When `cacheComponents` is enabled without a `partialPrefetching` value, Next.js logs a warning asking you to set it to `true` or `false`." - both will be enabled by default in the next major and the options removed. Why: the default `<Link>` behaviour changes with the flag. Smell: `next.config.ts` with `cacheComponents: true` and no `partialPrefetching` key. Source: https://nextjs.org/docs/app/guides/adopting-partial-prefetching#enable-partial-prefetching
- **Audit existing `prefetch={true}` links before enabling Partial Prefetching**: "In an existing app, review the UI delivered by `<Link prefetch={true}>` before enabling Partial Prefetching." - legacy full prefetches include uncached dynamic content; after the flag only cached URL-specific content is resolved. Why: content users saw instantly before may start streaming in after the click. Smell: a diff that flips `partialPrefetching: true` with no changes to existing `prefetch` links. Source: https://nextjs.org/docs/app/guides/adopting-partial-prefetching#enable-partial-prefetching
- **Remove `prefetch={true}` from static, cached or real-time destinations**: "A prefetch of real-time content would be stale by the click, so there is nothing to preserve." - keep it only for destinations that read URL data with cached content behind it (requires `partialPrefetching`). Why: static output is already in the App Shell and live data cannot usefully be prefetched. Smell: `<Link href="/about" prefetch={true}>`, or `prefetch` on a link to a live dashboard. Source: https://nextjs.org/docs/app/guides/adopting-partial-prefetching#real-time-content
- **Move `params` and `searchParams` reads behind Suspense (requires `partialPrefetching`)**: "Reading `params` or `searchParams` outside a `<Suspense>` boundary ties the shell to the link's URL" - pass the promise to a child inside the boundary and await there. Why: the App Shell is shared by every link to the route and cannot hold per-URL data. Smell: `const { slug } = await params` as the first line of a page component. Source: https://nextjs.org/docs/app/guides/adopting-partial-prefetching#move-url-data-behind-suspense
- **Cache the data behind a URL read so `prefetch={true}` can resolve it**: "To make the content resolvable at prefetch time, cache it behind the read with `use cache`." - without a cache directive the per-link prefetch stops at the Suspense fallback. Why: uncached work is never run during a prefetch. Smell: `<Link prefetch={true}>` to a search page whose `getResults` has no `use cache`. Source: https://nextjs.org/docs/app/guides/adopting-partial-prefetching#prefetching-url-data
- **Read cookies outside `use cache` and pass the value in**: "`"use cache"` cannot call `cookies()` inside the cached function" - extract the session value at the call site, or use `use cache: private` when the lookup is tied to one session. Why: the cached function needs a deterministic signature so sessions sharing a value share the entry. Smell: `await cookies()` inside a function whose first statement is `'use cache'`. Source: https://nextjs.org/docs/app/guides/optimizing-prefetching#include-session-data-in-the-shell
- **Give navigation-critical caches a `stale` time of at least five minutes**: "The App Shell carries cached content whose `stale` time is at least 5 minutes" - shorter-lived content streams in after navigation instead. Why: the client router only reuses entries above that threshold. Smell: `cacheLife('seconds')` on the function that renders the navigation. Source: https://nextjs.org/docs/app/guides/adopting-partial-prefetching#uncached-content
- **Never await `prefetch()` or `navigation()` in a cached scope, Client Component or `generateStaticParams`**: "Calling it inside `use cache`, `use cache: private`, `unstable_cache()`, `after()`, `generateStaticParams`, or a Client Component throws." - put the directive on a function called below the await. Why: the stage boundary must sit above the cached work. Smell: `await prefetch()` as the second line of a `'use cache'` function. Source: https://nextjs.org/docs/app/api-reference/functions/prefetch#good-to-know
- **Wrap the component that awaits `navigation()` or `prefetch()` in `<Suspense>`**: "A call outside a `<Suspense>` boundary surfaces an Instant Insight in development." - the fallback is what the prefetched output shows in place of the deferred subtree. Why: without a boundary the deferral has nothing to render. Smell: `await navigation()` in a page component rendered directly by the layout. Source: https://nextjs.org/docs/app/api-reference/functions/navigation#good-to-know
- **Choose `navigation()` for reusable work and `connection()` for per-request work**: "Use `navigation()` when the work is reusable but should wait until the user navigates." - `navigation()` keeps the subtree cacheable; `connection()` marks it request-dependent. Why: `connection()` throws away the cache lifetime of everything below it. Smell: `await connection()` placed above a `use cache` call just to keep it out of prefetches. Source: https://nextjs.org/docs/app/api-reference/functions/navigation#how-navigation-differs-from-connection
- **Alias the `prefetch` import in files that export the `prefetch` segment config**: "A `page` or `layout` that also calls the `prefetch()` function needs to import it under another name" - for example `import { prefetch as prefetchStage } from 'next/cache'`. Why: the export and the import share a name. Smell: `export const prefetch = 'partial'` and `import { prefetch } from 'next/cache'` in one file. Source: https://nextjs.org/docs/app/api-reference/file-conventions/route-segment-config/prefetch
- **Omit `prefetch = 'auto'` and set `'partial'` on the destination**: "`'auto'` is the default and is equivalent to omitting the export; don't write `prefetch = 'auto'` explicitly." - the only meaningful values are `'partial'` and `'force-disabled'`, exported from the page or layout being linked to, never from a Client Component. Why: the segment caps what any link into it may prefetch. Smell: `export const prefetch = 'auto'`, or `<Link prefetch="partial">`. Source: https://nextjs.org/docs/app/api-reference/file-conventions/route-segment-config/prefetch
- **Strip per-route `prefetch = 'partial'` once the global flag is on**: "The per-route `prefetch = 'partial'` exports are now redundant." - run the `remove-partial-prefetch` codemod on the correct app folder and check the file count. Why: the codemod reports `0 ok` for a wrong path instead of failing. Smell: `partialPrefetching: true` in config beside leftover `export const prefetch = 'partial'` lines. Source: https://nextjs.org/docs/app/guides/adopting-partial-prefetching#adopting-incrementally

## Instant navigation and ensureStatic (requires `cacheComponents`)

- **Fix blocking navigations by caching or pushing work into Suspense**: "When a caching decision is unclear, keep the data fresh behind `<Suspense>` rather than guessing a cache lifetime." - extract slug-dependent or uncached fetches into a child component with a fallback, and add `use cache` only where the lifetime is known. Why: top-level awaits in a page block the whole navigation. Smell: two `await fetch()` calls at the top of a page component with no boundary. Source: https://nextjs.org/docs/app/guides/instant-navigation#ai-workflow
- **Push Suspense boundaries down instead of wrapping the whole page**: "A `<Suspense>` boundary placed high in the tree (say, wrapping the whole page) might satisfy validation, but it replaces most of the page with a single fallback on every navigation." - keep header, image and description visible and put only the in-flight data behind fallbacks. Why: a full-page skeleton feels slower than partial content at the same load time. Smell: one `<Suspense>` around the entire page body. Source: https://nextjs.org/docs/app/guides/instant-navigation#iterate-on-loading-states
- **Use `instant = false` only to exempt a blocking ancestor of an instant page**: "Reach for `false` only when you've configured a deeper page as instant and need to exempt navigations that pass through a blocking ancestor." - place it as low as possible; on the root layout it disables static shell validation for the whole app. Why: unconfigured ancestors are already fine and a high `false` hides real problems. Smell: `export const instant = false` added to `app/layout.tsx` to silence the dev overlay. Source: https://nextjs.org/docs/app/api-reference/file-conventions/route-segment-config/instant#disabling-instant
- **Wait for the destination URL inside `instant()` before asserting**: "For client navigations, wait for the destination URL before asserting on its UI." - otherwise a shared selector matches the source page before the destination commits. Why: a passing assertion on the wrong page hides a broken prefetch. Smell: `await link.click(); await expect(page.locator('h1')).toContainText(...)` with no `waitForURL`. Source: https://nextjs.org/docs/app/guides/instant-navigation#prevent-regressions-with-e2e-tests
- **Set `EXPOSE_TESTING_API=1` at build time for production `instant()` tests**: "Setting it only for `next start` does not add the testing API to an existing build." - gate `experimental.exposeTestingApiInProductionBuild` on the variable and set it when running `next build`. Why: the API is compiled into the build, not read at start. Smell: a CI job exporting the variable only for the `start` step. Source: https://nextjs.org/docs/app/guides/instant-navigation#prevent-regressions-with-e2e-tests
- **Never weaken a parent's `ensureStatic` in a child**: "A descendant can set a stricter static level, but not a weaker one" - `'auto'` or an omitted export is compatible with any level; `false` conflicts with every static level; parallel slots must agree. Why: the build fails on a less-constrained or incompatible child. Smell: `ensureStatic = 'navigation'` in a layout with `ensureStatic = 'shell'` in a page below it. Source: https://nextjs.org/docs/app/api-reference/file-conventions/route-segment-config/ensureStatic#combining-levels-across-layouts-and-pages
- **Export complete `generateStaticParams` sets under `ensureStatic = 'navigation'`**: "a dynamic route must export `generateStaticParams()` and return at least one complete parameter set." - every object must include every dynamic parameter in the route, even ones only read on the client. Why: the complete route must be produced at prerender time. Smell: `ensureStatic = 'navigation'` on `[locale]/[slug]/page.tsx` with `generateStaticParams` returning only `{ locale }`. Source: https://nextjs.org/docs/app/api-reference/file-conventions/route-segment-config/ensureStatic#dynamic-route-parameters
- **Keep runtime data out of `ensureStatic = 'navigation'` routes even inside Suspense**: "the following server content fails validation, even when it is wrapped in `<Suspense>` or the segment sets `instant = false`" - uncached fetches, `cookies()`, `headers()`, server `searchParams`, short cache lifetimes and request-dependent promises passed to Client Components all fail. Why: `'navigation'` is the final stage, so nothing can be deferred past it. Smell: `cookies()` in a Suspense child of a route whose layout exports `ensureStatic = 'navigation'`. Source: https://nextjs.org/docs/app/api-reference/file-conventions/route-segment-config/ensureStatic#validation

## Navigation hooks

- **Import `useRouter` from `next/navigation`**: "The `useRouter` hook should be imported from `next/navigation` and not `next/router` when using the App Router" - `pathname` and `query` are gone; use `usePathname` and `useSearchParams`. - **Never pass untrusted URLs to `router.push` or `router.replace`**: "You must not send untrusted or unsanitized URLs to `router.push` or `router.replace`, as this can open your site to cross-site scripting (XSS) vulnerabilities." - validate or allow-list any redirect target that comes from the URL or user input. - **Do not expect `router.refresh()` to invalidate server caches**: "Use `revalidatePath` or `revalidateTag` to invalidate server-side cached data." - `refresh()` re-requests the route and clears the client cache only. - **Use `redirect()` during render and `useRouter` in event handlers**: "`redirect` can be called in Client Components during the rendering process but not in event handlers." - swap to `router.push` inside `onClick` and friends. - **Reserve `bfcacheId` for migrations (requires `cacheComponents`)**: "Use `bfcacheId` only as a last resort, like when migrating an existing codebase." - reset state in the event handler or key on data instead. - **Wrap `useSearchParams` in `<Suspense>` on prerendered routes**: "During production builds, a static page that calls `useSearchParams` from a Client Component must be wrapped in a `Suspense` boundary, otherwise the build fails" - in development the hook does not suspend, so the problem only appears at build. - **Prefer `connection()` over `dynamic = 'force-dynamic'` to force dynamic rendering**: "Prefer using `connection()` instead, as it semantically ties dynamic rendering to the incoming request." - await it in a Server Component above the client tree. Why: `dynamic` is removed under Cache Components and hides the reason for dynamic rendering. Smell: `export const dynamic = 'force-dynamic'` added so `useSearchParams` works without Suspense. Source: https://nextjs.org/docs/app/api-reference/functions/use-search-params#dynamic-rendering
- **Wrap `usePathname` and segment hooks in Suspense when params are not covered by `generateStaticParams` (requires `cacheComponents`)**: "Wrap the component (or a parent) in a `Suspense` boundary so its fallback can be rendered during prerendering; otherwise, the build fails." - `useParams`, `useSelectedLayoutSegment` and `useSelectedLayoutSegments` behave the same. Why: a static sidebar in a layout suspends on any page below it with an unknown param. Source: https://nextjs.org/docs/app/api-reference/functions/use-pathname#cache-components
- **Isolate pathname-dependent UI when Proxy or rewrites change the URL**: "design the UI so that only a small, isolated part depends on the client pathname." - render a stable fallback on the server and update after mount. Why: prerendered HTML carries the source pathname and the browser shows the rewritten one, causing hydration mismatches. Smell: a prerendered page under a rewrite that prints `usePathname()` into markup. Source: https://nextjs.org/docs/app/api-reference/functions/use-pathname#avoid-hydration-mismatch-with-rewrites
- **Filter route groups out of `useSelectedLayoutSegments`**: "The returned segments include Route Groups, which you might not want to be included in your UI." - drop entries that start with a bracket, and remember catch-all segments arrive as one joined string. Source: https://nextjs.org/docs/app/api-reference/functions/use-selected-layout-segments
- **Prefer `loading.js` and prefetching over `useLinkStatus`**: "Prefer route-level fallbacks with `loading.js`, and prefetching for instant transitions." - use the hook as a quick patch inside a `<Link>` descendant when prefetch is disabled or the route is dynamic without a loading file. Why: a prefetched destination skips the pending state entirely. Smell: a spinner driven by `useLinkStatus` on every nav link instead of a `loading.tsx`. - **Render link hints at a fixed size and toggle opacity**: "Inline indicators can easily introduce layout shifts." - keep a fixed-size, always-rendered hint element and add an animation delay so it only appears when navigation is slow. ## Redirects

- **Call `redirect()` outside `try/catch`**: "Invoking the `redirect()` function throws a `NEXT_REDIRECT` error and terminates rendering of the route segment in which it was thrown." - in Server Actions and Route Handlers do the work inside `try`, then redirect after the block. - **Redirect before render with `next.config.js` or Proxy, not a page**: "If you'd like to redirect before the render process, use `next.config.js` or Proxy." - known path changes belong in `redirects()`; conditional ones in `proxy.ts`. - **Use `permanentRedirect` when the canonical URL changes**: "`permanentRedirect` is often used after a mutation or event that changes an entity's canonical URL" - it returns 308 so crawlers update; `redirect` returns 307. - **Keep config redirects under platform limits; move large sets to Proxy**: "For example, on Vercel, there's a limit of 1,024 redirects." - store a redirect map in a key-value store and look it up in Proxy, with a Bloom filter in front. - **Do not import a large redirect map into Proxy**: "This avoids importing a large redirects file into Proxy, which can slow down every incoming request." - check a Bloom filter in Proxy and forward hits to a Route Handler that holds the full map. - **Validate requests to a redirect lookup Route Handler**: "You should validate requests made to your Route Handler to prevent malicious requests." - reject missing or malformed `pathname` input and only return entries from your own map. Why: the handler is a public endpoint. Smell: a `GET` handler that echoes any `destination` derived from the query. Source: https://nextjs.org/docs/app/guides/redirecting#2-optimizing-data-lookup-performance
- **Call `refresh()` only from Server Actions**: "It cannot be used in Route Handlers, Client Components, or any other context." - use `router.refresh()` on the client and `revalidatePath` in handlers. Why: it refreshes the client router of the action's caller. Smell: `import { refresh } from 'next/cache'` in `route.ts`. Source: https://nextjs.org/docs/app/api-reference/functions/refresh#usage

- **Put route-level `<ViewTransition>` wrappers in each `page.tsx`, not the layout**: "Put the wrapper in each `page.tsx`, not the layout." - every participating page needs the same wrapper. Why: layouts persist across navigations, so enter and exit never fire there. Smell: `<ViewTransition enter=... exit=...>` around `{children}` in `layout.tsx`. Source: https://nextjs.org/docs/app/guides/view-transitions#step-3-add-directional-motion-for-navigation
- **Keep `share` when adding `default="none"` to a named pair**: "With `default="none"` and no `share` prop, the pair silently stops morphing." - use `share="morph"` with `default="none"` on both ends. Why: `default="none"` suppresses every animation including the shared element one. Smell: `<ViewTransition name="photo-1" default="none">` with no `share`. Source: https://nextjs.org/docs/app/guides/view-transitions#customizing-the-morph-animation
- **Let clicks pass through the transition overlay**: "While a transition runs, the `::view-transition` overlay captures pointer events, so clicks during the animation are lost." - add `::view-transition { pointer-events: none; }` and keep transitions short. Why: users clicking during a slide get nothing. Smell: 400ms route slides with no `pointer-events` rule. Source: https://nextjs.org/docs/app/guides/view-transitions#keeping-the-page-interactive
- **Honour `prefers-reduced-motion` for directional slides**: "Directional slides simulate physical movement across the viewport." - zero the durations under the media query, or keep crossfades and remove movement; the docs call slides the most common trigger for motion sensitivity. Why: positional animation is the main accessibility risk. Smell: `::view-transition-new(.nav-forward)` keyframes with no reduced-motion override. Source: https://nextjs.org/docs/app/guides/view-transitions#respecting-reduced-motion

## Internationalisation

- **Nest every special file under `app/[lang]`**: "ensure all special files inside `app/` are nested under `app/[lang]`." - the root layout moves to `app/[lang]/layout.js` so the locale reaches every layout and page. Why: a sibling `app/page.tsx` escapes locale routing. Smell: `app/page.tsx` left beside `app/[lang]/page.tsx`. Source: https://nextjs.org/docs/app/guides/internationalization#routing-overview
- **Narrow the locale with a type guard and `notFound()`**: "using `hasLocale` narrows the type to your supported locales." - `lang` arrives as `string`, and the guard returns a 404 for a missing translation instead of a runtime error. Why: an unsupported locale would otherwise crash the dictionary lookup. Smell: `dictionaries[lang]()` with no membership check. Source: https://nextjs.org/docs/app/guides/internationalization#localization
- **Load dictionaries in Server Components with `server-only`**: "we do not need to worry about the size of the translation files affecting our client-side JavaScript bundle size." - keep `getDictionary` behind `import 'server-only'` and pass strings down. Why: dictionaries imported into a Client Component ship to the browser. Smell: `import en from './dictionaries/en.json'` in a `'use client'` file. Source: https://nextjs.org/docs/app/guides/internationalization#localization
- **Export `generateStaticParams` for the locale set**: "To generate static routes for a given set of locales, we can use `generateStaticParams` with any page or layout." - return one object per supported locale from the root layout. Why: without it every localised route renders on demand. Smell: `app/[lang]/layout.tsx` with no `generateStaticParams`. Source: https://nextjs.org/docs/app/guides/internationalization#static-rendering

## Multi-zones

- **Keep pages that are visited together in one zone**: "Pages that are frequently visited together should live in the same zone to avoid hard navigations." - cross-zone navigation unloads the page. Why: only same-zone navigations are soft. Smell: a checkout flow split across two zones. Source: https://nextjs.org/docs/app/guides/multi-zones
- **Give each non-default zone a unique `assetPrefix` and unique paths**: "A zone is a normal Next.js application where you also configure an assetPrefix to avoid conflicts with pages and static files in other zones." - the default zone needs none; two zones must not serve the same path. Why: `_next` assets and routes otherwise collide. Smell: a second zone with no `assetPrefix`, or two zones both serving `/blog`. Source: https://nextjs.org/docs/app/guides/multi-zones#how-to-define-a-zone
- **Route between zones with `rewrites`, using Proxy only for dynamic decisions**: "Routing requests through `rewrites` is recommended to minimize latency overhead for the requests, but proxy can also be used when there is a need for a dynamic decision" - reserve `proxy.ts` for feature-flagged migrations. Why: rewrites avoid running code per request. Smell: `proxy.ts` rewriting fixed `/blog/*` paths to another zone. Source: https://nextjs.org/docs/app/guides/multi-zones#routing-requests-using-proxy
- **Use `<a>` for links into another zone**: "Links to paths in a different zone should use an `a` tag instead of the Next.js `<Link>` component." - `<Link>` tries to prefetch and soft navigate any relative path. Why: the destination is served by a different application. Smell: `<Link href="/dashboard">` in the marketing zone when `/dashboard` is another zone. Source: https://nextjs.org/docs/app/guides/multi-zones#linking-between-zones
- **Allow the user-facing origin for Server Actions across zones**: "you must explicitly allow the user-facing origin since your user facing domain may serve multiple applications." - set `experimental.serverActions.allowedOrigins` to the production domain. Why: the action origin differs from the zone's own host. Smell: form actions in a zone failing with an origin mismatch and no `allowedOrigins`. Source: https://nextjs.org/docs/app/guides/multi-zones#server-actions

## next.config routing options

- **Use `typedRoutes` at the top level, not under `experimental`**: "This option has been marked as stable, so you should use `typedRoutes` instead of `experimental.typedRoutes`." - the option requires TypeScript. Why: the experimental key is obsolete. Smell: `experimental: { typedRoutes: true }`. Source: https://nextjs.org/docs/app/api-reference/config/next-config-js/typedRoutes
- **Do not prefix `<Link>` hrefs with `basePath`**: "When linking to other pages using `next/link` and `next/router` the `basePath` will be automatically applied." - write `/about` and let Next.js produce `/docs/about`. Why: a manual prefix doubles up. Smell: `<Link href="/docs/about">` with `basePath: '/docs'`. Source: https://nextjs.org/docs/app/api-reference/config/next-config-js/basePath#links
- **Prefix `next/image` `src` with `basePath`**: "When using the `next/image` component, you will need to add the `basePath` in front of `src`." - unlike `<Link>`, images are not rewritten automatically. Why: the image would 404 under the sub-path. Smell: `<Image src="/me.png">` with `basePath: '/docs'`. Source: https://nextjs.org/docs/app/api-reference/config/next-config-js/basePath#images
