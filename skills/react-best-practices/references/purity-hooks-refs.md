## Keeping Components Pure

- **Components are pure functions**: Write every component so that it "minds its own business" and gives "same inputs, same output" - it must always return the same JSX given the same props, state and context. Why: "React assumes that every component you write is a pure function" and relies on this for server rendering, memoization and interruptible rendering. Smell: component output depends on anything other than props/state/context (globals, time, randomness, call order). Source: https://react.dev/learn/keeping-components-pure#purity-components-as-formulas
- **Do not change preexisting variables during render**: Components "should only return their JSX, and not change any objects or variables that existed before rendering". Why: "calling this component multiple times will produce different JSX" and other components reading the variable become unpredictable too. Smell: module-level `let` variable read and reassigned inside a component body (`guest = guest + 1`). Source: https://react.dev/learn/keeping-components-pure#side-effects-unintended-consequences
- **Pass shared data via props, not shared variables**: Replace a mutated outer variable with a prop passed explicitly to each component. Why: "All communication must happen through props" because React "does not guarantee that component functions will execute in any particular order". Smell: parent writes `currentPerson = person` and sibling/child components read that module variable instead of receiving a prop. Source: https://react.dev/learn/keeping-components-pure#fix-a-broken-profile
- **Never depend on render order**: Each component should "think for itself" and "not attempt to coordinate with or depend upon others during rendering". Why: "you should not expect your components to be rendered in any particular order". Smell: component behavior relies on another component having rendered first (flags, counters, caches set during a sibling's render). Source: https://react.dev/learn/keeping-components-pure#side-effects-unintended-consequences
- **Treat props, state and context as read-only**: "You should always treat these inputs as read-only" and "never change preexisting variables or objects while your component is rendering". Why: mutating inputs makes the component impure and its output unpredictable across renders. Smell: `props.items.push(...)`, `state.foo = ...`, or assigning into a context value during render. Source: https://react.dev/learn/keeping-components-pure#detecting-impure-calculations-with-strict-mode
- **Set state instead of writing to variables**: "When you want to change something in response to user input, you should set state instead of writing to a variable". Why: only state updates tell React to re-render; variable writes are invisible to React. Smell: event handler assigns to a local or module variable and expects the UI to reflect it. Source: https://react.dev/learn/keeping-components-pure#detecting-impure-calculations-with-strict-mode
- **Use StrictMode to surface impurity**: Wrap the root in `<React.StrictMode>` so React "calls each component's function twice during development". Why: "Pure functions only calculate, so calling them twice won't change anything" - impure ones break visibly (e.g. Guest #2, #4, #6). Smell: app root rendered without StrictMode; duplicated side effects appearing in dev being "fixed" by removing StrictMode. Source: https://react.dev/learn/keeping-components-pure#detecting-impure-calculations-with-strict-mode
- **Local mutation is fine**: "It's completely fine to change variables and objects that you've just created while rendering." Why: objects created during the same render are unknown to code outside the component, so mutating them is the component's "little secret". Smell (non-issue): `const cups = []; for (...) cups.push(<Cup />)` inside the component body. Source: https://react.dev/learn/keeping-components-pure#local-mutation-your-components-little-secret
- **Copy before mutating a prop array**: Do not `push` onto a prop array; either render the extra item separately or "create a new array (by copying the existing one) before you push an item into it". Why: `push` on a prop mutates "an object that was created before StoryTray started rendering", producing duplicates under StrictMode. Smell: `stories.push({...})` in render; use `stories.slice()`/spread or render the extra `<li>` directly. Source: https://react.dev/learn/keeping-components-pure#fix-a-broken-story-tray
- **Know mutating vs non-mutating array methods**: Remember that "push, pop, reverse, and sort will mutate the original array, but slice, filter, and map will create a new one". Why: using a mutating method on props/state during render breaks purity. Smell: `.sort()` or `.reverse()` called directly on a prop or state array in render. Source: https://react.dev/learn/keeping-components-pure#fix-a-broken-story-tray
- **Side effects belong in event handlers**: "In React, side effects usually belong inside event handlers" because "event handlers don't need to be pure". Why: event handlers run in response to user actions, not during rendering. Smell: DOM writes, network calls, logging, or storage writes placed directly in the component body. Source: https://react.dev/learn/keeping-components-pure#where-you-can-cause-side-effects
- **useEffect is a last resort for side effects**: Use `useEffect` for a side effect only "if you've exhausted all other options and can't find the right event handler" - "this approach should be your last resort". Why: "When possible, try to express your logic with rendering alone." Smell: `useEffect` used for something an event handler or plain render calculation could express. Source: https://react.dev/learn/keeping-components-pure#where-you-can-cause-side-effects
- **Express DOM outcomes in JSX, not imperative writes**: Compute values like `className` and include them in the render output instead of setting them via `document.getElementById(...)` during render. Why: "Rendering is a calculation, it shouldn't try to 'do' things" - "the side effect (modifying the DOM) was not necessary at all". Smell: `document.getElementById('x').className = ...` inside a component body. Source: https://react.dev/learn/keeping-components-pure#fix-a-broken-clock

## Rules of React

- **Follow the Rules of React as rules, not guidelines**: Treat the Rules of React as hard rules because "if they are broken, your app likely has bugs". Why: breaking them also makes code "unidiomatic and harder to understand and reason about". Smell: code that "works" only by relying on undocumented render ordering or on effects running once. Source: https://react.dev/reference/rules
- **Use StrictMode plus eslint-plugin-react-hooks**: "We strongly recommend using Strict Mode alongside React's ESLint plugin to help your codebase follow the Rules of React." Why: they find and surface rule violations early so the app stays maintainable. Smell: project without `eslint-plugin-react-hooks` configured or with the rules disabled. Source: https://react.dev/reference/rules
- **Components must be idempotent**: "React components are assumed to always return the same output with respect to their inputs - props, state, and context." Why: purity "makes your app predictable, easy to debug, and allows React to automatically optimize your code". Smell: `new Date()`, `Math.random()` or global reads in the component body determining output. Source: https://react.dev/reference/rules#components-and-hooks-must-be-pure
- **Side effects must run outside of render**: "Side effects should not run in render, as React can render components multiple times to create the best possible user experience." Why: repeated renders would repeat the side effect. Smell: mutation of external state, DOM writes, or I/O in the component body. Source: https://react.dev/reference/rules#components-and-hooks-must-be-pure
- **Props and state are immutable**: "A component's props and state are immutable snapshots with respect to a single render. Never mutate them directly." Why: mutation produces inconsistent output and skips re-rendering. Smell: `props.x = ...` or `state.items.push(...)`. Source: https://react.dev/reference/rules#components-and-hooks-must-be-pure
- **Hook arguments and return values are immutable**: "Once values are passed to a Hook, you should not modify them. Like props in JSX, values become immutable when passed to a Hook." Why: hooks may memoize on their arguments and return values. Smell: mutating an object after passing it to a custom hook, or mutating what a hook returned. Source: https://react.dev/reference/rules#components-and-hooks-must-be-pure
- **Values are immutable after being passed to JSX**: "Don't mutate values after they've been used in JSX. Move the mutation before the JSX is created." Why: React may eagerly evaluate JSX, so later mutation yields outdated UI. Smell: object passed as a prop in a JSX expression, then modified further down the same function. Source: https://react.dev/reference/rules#components-and-hooks-must-be-pure
- **Never call component functions directly**: "Components should only be used in JSX. Don't call them as regular functions." Why: React must decide when components render to attach state, reconcile and optimize. Smell: `{Article()}` instead of `<Article />`. Source: https://react.dev/reference/rules#react-calls-components-and-hooks
- **Never pass around hooks as regular values**: "Hooks should only be called inside of components. Never pass it around as a regular value." Why: hooks must be static so React and developers can reason about a component locally. Smell: a hook passed as a prop or argument, or a hook created dynamically at runtime. Source: https://react.dev/reference/rules#react-calls-components-and-hooks
- **Only call Hooks at the top level**: "Don't call Hooks inside loops, conditions, or nested functions. Instead, always use Hooks at the top level of your React function, before any early returns." Why: React relies on a stable call order between renders. Smell: `useX()` inside `if`, `for`, `.map`, or after a `return`. Source: https://react.dev/reference/rules#rules-of-hooks
- **Only call Hooks from React functions**: "Don't call Hooks from regular JavaScript functions." Why: hooks work only while React renders a function component or custom hook. Smell: a plain helper without a `use` prefix that calls `useState`/`useEffect`. Source: https://react.dev/reference/rules#rules-of-hooks

## Components and Hooks must be pure

- **Be idempotent for the same inputs**: A pure component or hook is "Idempotent - You always get the same result every time you run it with the same inputs - props, state, context for component inputs; and arguments for hook inputs." Why: this lets React pause, re-run and prioritize rendering safely. Smell: hook or component output varies between two calls with identical inputs. Source: https://react.dev/reference/rules/components-and-hooks-must-be-pure#why-does-purity-matter
- **No side effects in render**: "Code with side effects should run separately from rendering. For example as an event handler ... or as an Effect - which runs after render." Why: React "can pause rendering components that aren't as important to update, and only come back to them later". Smell: effects (logging, mutation, I/O) executed in the component body rather than in a handler or `useEffect`. Source: https://react.dev/reference/rules/components-and-hooks-must-be-pure#why-does-purity-matter
- **Do not mutate non-local values**: "Components and Hooks should never modify values that aren't created locally in render." Why: re-running render would re-trigger the mutation "in a way that won't match what you want". Smell: writing to a module variable, a shared Set/Map, or a global object in the component body. Source: https://react.dev/reference/rules/components-and-hooks-must-be-pure#why-does-purity-matter
- **Top-level component code runs in render**: Treat code written "at the top level" of a component as running during render; only event handlers and Effects run outside it. Why: "One quick heuristic to tell if code runs during render is to examine where it is." Smell: expensive or effectful statements placed at component top level that should be in `onSelect`/`useEffect`. Source: https://react.dev/reference/rules/components-and-hooks-must-be-pure#how-to-tell-if-code-runs-in-render
- **Avoid non-idempotent calls like `new Date()` and `Math.random()` in render**: "you should just avoid using them during render"; synchronize such values via an Effect or an event handler instead. Why: "`new Date()` is not idempotent as it always returns the current date and changes its result every time it's called." Smell: `const time = new Date();` or `Math.random()` inside the component body driving JSX. Source: https://react.dev/reference/rules/components-and-hooks-must-be-pure#components-and-hooks-must-be-idempotent
- **Move non-idempotent work into an Effect or handler**: Use `useState(() => new Date())` plus a `useEffect` with `setInterval` and cleanup to synchronize the value. Why: "By wrapping the non-idempotent `new Date()` call in an Effect, it moves that calculation outside of rendering." Smell: clock/time/random value recomputed in render each time. Source: https://react.dev/reference/rules/components-and-hooks-must-be-pure#components-and-hooks-must-be-idempotent
- **Prefer event handlers over Effects for side effects**: "In most cases, you'll use event handlers to handle side effects"; "only as a last resort - you can also handle side effects using `useEffect`." Why: "Using an event handler explicitly tells React that this code doesn't need to run during render, keeping render pure." Smell: `useEffect` reacting to a state flag set by a click in order to run the side effect. Source: https://react.dev/reference/rules/components-and-hooks-must-be-pure#side-effects-must-run-outside-of-render
- **Local mutation is allowed**: Creating a local array and pushing into it during render is fine - "There is no need to contort your code to avoid local mutation." Why: "`items` is always recreated every time `<FriendList />` is rendered, the component will always return the same result." Smell (non-issue): `const items = []; ... items.push(<Friend />)` inside the component. Source: https://react.dev/reference/rules/components-and-hooks-must-be-pure#local-mutation
- **Never mutate values created outside the component during render**: Do not push into or modify an array/object declared outside the component. Why: "we will continue appending `friends` to `items` every time that component is run, leading to multiple duplicated results." Smell: `const items = [];` at module scope mutated by `FriendList` render. Source: https://react.dev/reference/rules/components-and-hooks-must-be-pure#local-mutation
- **Lazy initialization is acceptable**: A one-time `initializeIfNotReady()` call in render is fine "if it doesn't affect other components". Why: "As long as calling a component multiple times is safe and doesn't affect the rendering of other components, React doesn't care if it's 100% pure." Smell (non-issue): idempotent `Lib.initializeIfNotReady()` at top of a component. Source: https://react.dev/reference/rules/components-and-hooks-must-be-pure#lazy-initialization
- **Do not change the DOM in render**: "Side effects that are directly visible to the user are not allowed in the render logic of React components"; synchronize with `document` in an Effect instead. Why: "merely calling a component function shouldn't by itself produce a change on the screen." Smell: `document.title = product.title;` in the component body. Source: https://react.dev/reference/rules/components-and-hooks-must-be-pure#changing-the-dom
- **Don't mutate props**: "never mutate props directly" - "make a copy instead" (`const url = new Url(item.url, base)`). Why: "if you mutate them, the application will produce inconsistent output, which can be hard to debug". Smell: `item.url = ...` where `item` is a prop. Source: https://react.dev/reference/rules/components-and-hooks-must-be-pure#dont-mutate-props
- **Don't mutate state**: Update state "using the setter function that is returned by `useState`" rather than in place. Why: "Changing values on the state variable doesn't cause the component to update, leaving your users with an outdated UI." Smell: `count = count + 1` or `state.list.push(x)` instead of `setCount`/`setList`. Source: https://react.dev/reference/rules/components-and-hooks-must-be-pure#dont-mutate-state
- **Don't mutate hook arguments**: "never mutate hook arguments directly" - copy (`const newIcon = { ...icon }`) and modify the copy. Why: "If you were to mutate the Hook's arguments, the custom hook's memoization will become incorrect." Smell: custom hook assigns onto a parameter object (`icon.className = ...`); caller mutates an object after passing it to a hook (`icon.enabled = false`). Source: https://react.dev/reference/rules/components-and-hooks-must-be-pure#return-values-and-arguments-to-hooks-are-immutable
- **Don't mutate hook return values**: "it's important to not modify the return values of Hooks, as they may have been memoized." Why: hooks are "black boxes" and local reasoning depends on their outputs staying intact. Smell: `const style = useIconStyle(icon); style.color = 'red';`. Source: https://react.dev/reference/rules/components-and-hooks-must-be-pure#return-values-and-arguments-to-hooks-are-immutable
- **Don't mutate values after passing them to JSX**: "Don't mutate values after they've been used in JSX. Move the mutation to before the JSX is created", or create a new value per element. Why: "React may eagerly evaluate the JSX before the component finishes rendering", so later mutations "lead to outdated UIs". Smell: `const header = <Header styles={styles} />; styles.size = "small"; const footer = <Footer styles={styles} />`. Source: https://react.dev/reference/rules/components-and-hooks-must-be-pure#values-are-immutable-after-being-passed-to-jsx

## React calls Components and Hooks

- **Never call component functions directly**: "Components should only be used in JSX. Don't call them as regular functions. React should call it." Why: "React must decide when your component function is called during rendering." Smell: `<Layout>{Article()}</Layout>` instead of `<Layout><Article /></Layout>`. Source: https://react.dev/reference/rules/react-calls-components-and-hooks#never-call-component-functions-directly
- **Let React orchestrate so hooks stay valid**: Avoid calling components directly in loops or conditionally because "If a component contains Hooks, it's easy to violate the Rules of Hooks". Why: direct calls tie the callee's hooks to the caller's hook order. Smell: `items.map((item) => Row(item))` where `Row` uses hooks. Source: https://react.dev/reference/rules/react-calls-components-and-hooks#never-call-component-functions-directly
- **Use JSX so components get identity, reconciliation and devtools**: Render via JSX so "Components become more than functions", "Component types participate in reconciliation", and React can do "More efficient reconciliation". Why: React "can decide exactly which components in the tree need re-rendering and skip over the ones that don't". Smell: helper "render functions" invoked directly in place of component elements. Source: https://react.dev/reference/rules/react-calls-components-and-hooks#never-call-component-functions-directly
- **Never pass around Hooks as regular values**: "Hooks should only be called inside of components or Hooks. Never pass it around as a regular value." Why: "This enables local reasoning" and "Breaking this rule will cause React to not automatically optimize your component." Smell: a hook stored in a variable, object, or prop to be invoked elsewhere. Source: https://react.dev/reference/rules/react-calls-components-and-hooks#never-pass-around-hooks-as-regular-values
- **Don't write higher-order Hooks**: "you shouldn't write higher order Hooks" like `withLogging(useData)`; "create a static version of the Hook with the desired functionality" instead. Why: "Hooks should be as 'static' as possible" and "immutable and not be mutated". Smell: `const useDataWithLogging = withLogging(useData);` inside a component. Source: https://react.dev/reference/rules/react-calls-components-and-hooks#dont-dynamically-mutate-a-hook
- **Don't pass Hooks as props (no hook dependency injection)**: "don't pass Hooks as props"; "always inline the call of the Hook into that component and handle any logic in there." Why: dynamic hook use "increases the complexity of your app greatly and inhibits local reasoning" and makes conditional hook calls likely. Smell: `<Button useData={useDataWithLogging} />`. Source: https://react.dev/reference/rules/react-calls-components-and-hooks#dont-dynamically-use-hooks
- **Put conditional hook behavior inside the Hook**: "If there's any conditional logic to change the Hook's behavior, it should be inlined into the Hook." Why: keeps the calling component "much easier to understand and debug". Smell: caller choosing between two hooks at runtime based on a flag. Source: https://react.dev/reference/rules/react-calls-components-and-hooks#dont-dynamically-use-hooks
- **Mock the server, not components, for tests**: "If you find yourself needing to mock components for tests, it's better to mock the server instead to respond with canned data"; end-to-end tests are "usually more effective". Why: mocking via injected hooks pushes toward dynamic hook usage. Smell: test-only props that swap in a different hook implementation. Source: https://react.dev/reference/rules/react-calls-components-and-hooks#dont-dynamically-use-hooks

## Rules of Hooks

- **Only call Hooks at the top level**: "Don't call Hooks inside loops, conditions, nested functions, or try/catch/finally blocks. Instead, always use Hooks at the top level of your React function, before any early returns." Why: React can "only call Hooks while React is rendering a function component" and depends on consistent call order. Smell: any `useX()` not at the top of a component or custom hook body. Source: https://react.dev/reference/rules/rules-of-hooks#only-call-hooks-at-the-top-level
- **No Hooks inside conditions or loops**: "Do not call Hooks inside conditions or loops." Why: hook order would differ between renders. Smell: `if (cond) { const theme = useContext(ThemeContext); }` or `useContext` inside a `for` loop. Source: https://react.dev/reference/rules/rules-of-hooks#only-call-hooks-at-the-top-level
- **No Hooks after a conditional return**: "Do not call Hooks after a conditional return statement" - "move it before the return!" Why: an early return skips later hooks on some renders. Smell: `if (cond) return null;` followed by `useState`/`useEffect`. Source: https://react.dev/reference/rules/rules-of-hooks#only-call-hooks-at-the-top-level
- **No Hooks in event handlers**: "Do not call Hooks in event handlers" - "move it outside!" Why: handlers run outside render. Smell: `function handleClick() { const theme = useContext(ThemeContext); }`. Source: https://react.dev/reference/rules/rules-of-hooks#only-call-hooks-at-the-top-level
- **No Hooks in class components**: "Do not call Hooks in class components" - "write a function component instead of a class!" Why: hooks only work in function components. Smell: `useEffect` inside a class `render()`. Source: https://react.dev/reference/rules/rules-of-hooks#only-call-hooks-at-the-top-level
- **No Hooks inside functions passed to useMemo/useReducer/useEffect**: "Do not call Hooks inside functions passed to `useMemo`, `useReducer`, or `useEffect`." Why: those callbacks are nested functions, not the component's top level. Smell: `useMemo(() => { const theme = useContext(ThemeContext); ... })`. Source: https://react.dev/reference/rules/rules-of-hooks#only-call-hooks-at-the-top-level
- **No Hooks inside try/catch/finally**: "Do not call Hooks inside try/catch/finally blocks." Why: a throw would change which hooks get called. Smell: `try { const [x, setX] = useState(0); } catch { const [x, setX] = useState(1); }`. Source: https://react.dev/reference/rules/rules-of-hooks#only-call-hooks-at-the-top-level
- **Use eslint-plugin-react-hooks**: "You can use the `eslint-plugin-react-hooks` plugin to catch these mistakes." Why: it statically enforces hook placement. Smell: hook-order violations that lint would have flagged. Source: https://react.dev/reference/rules/rules-of-hooks#only-call-hooks-at-the-top-level
- **Custom Hooks may call other Hooks**: "Custom Hooks may call other Hooks (that's their whole purpose)" because they "are also supposed to only be called while a function component is rendering." Why: the top-level rule extends into custom hook bodies. Smell (non-issue): `useState` at the top level of `useWindowWidth`. Source: https://react.dev/reference/rules/rules-of-hooks#only-call-hooks-at-the-top-level
- **Only call Hooks from React functions**: "Don't call Hooks from regular JavaScript functions"; call them only "from React function components" or "from custom Hooks". Why: "you ensure that all stateful logic in a component is clearly visible from its source code." Smell: `function setOnlineStatus() { const [s, setS] = useOnlineStatus(); }` - a non-`use` function calling a hook. Source: https://react.dev/reference/rules/rules-of-hooks#only-call-hooks-from-react-functions

## Reusing Logic with Custom Hooks

- **Extract duplicated stateful logic into a custom Hook**: When two components share the same state + Effect logic, "Declare a function called `useOnlineStatus` and move all the duplicated code into it." Why: components then "describe what they want to do ... rather than how to do it". Smell: identical `useState` + `useEffect` subscription blocks copy-pasted across components. Source: https://react.dev/learn/reusing-logic-with-custom-hooks#extracting-your-own-custom-hook-from-a-component
- **Component names start with a capital letter**: "React component names must start with a capital letter, like `StatusBar` and `SaveButton`." Why: the convention lets React and readers distinguish components from functions. Smell: lowercase-named function returning JSX used as a component. Source: https://react.dev/learn/reusing-logic-with-custom-hooks#hook-names-always-start-with-use
- **Hook names start with `use` + capital letter**: "Hook names must start with `use` followed by a capital letter, like `useState` (built-in) or `useOnlineStatus` (custom)." Why: "you can always look at a component and know where its state, Effects, and other React features might 'hide'." Smell: `getOnlineStatus()` that internally calls `useState`/`useEffect`. Source: https://react.dev/learn/reusing-logic-with-custom-hooks#hook-names-always-start-with-use
- **Only Hooks and components call Hooks**: "Only Hooks and components can call other Hooks!" and the React-configured linter enforces this. Why: a non-`use` function cannot legally contain hook calls. Smell: linter error when renaming `useX` to `getX`. Source: https://react.dev/learn/reusing-logic-with-custom-hooks#hook-names-always-start-with-use
- **No `use` prefix for functions that don't call Hooks**: "If your function doesn't call any Hooks, avoid the `use` prefix. Instead, write it as a regular function" (e.g. `getSorted` not `useSorted`). Why: "This ensures that your code can call this regular function anywhere, including conditions." Smell: `useSorted(items)` containing only pure array logic. Source: https://react.dev/learn/reusing-logic-with-custom-hooks#should-all-functions-called-during-rendering-start-with-the-use-prefix
- **Use the `use` prefix when at least one Hook is called inside**: "You should give `use` prefix to a function (and thus make it a Hook) if it uses at least one Hook inside of it"; "If you don't plan to use Hooks inside it (now or later), don't make it a Hook." Why: a hook without hooks "is often confusing and limiting". Smell: `use`-prefixed helper with no hook calls and no plan to add them. Source: https://react.dev/learn/reusing-logic-with-custom-hooks#should-all-functions-called-during-rendering-start-with-the-use-prefix
- **Custom Hooks share stateful logic, not state**: "Custom Hooks let you share stateful logic but not state itself. Each call to a Hook is completely independent from every other call to the same Hook." Why: each call declares its own independent state variables and Effects. Smell: expecting two components calling `useFormInput()` to see the same value. Source: https://react.dev/learn/reusing-logic-with-custom-hooks#custom-hooks-let-you-share-stateful-logic-not-state-itself
- **Lift state up to actually share it**: "When you need to share the state itself between multiple components, lift it up and pass it down instead." Why: a custom hook cannot share state across callers. Smell: custom hook used as a substitute for lifted state or context. Source: https://react.dev/learn/reusing-logic-with-custom-hooks#custom-hooks-let-you-share-stateful-logic-not-state-itself
- **Custom Hooks must be pure**: "like components, custom Hooks need to be pure. Think of custom Hooks' code as part of your component's body!" Why: "The code inside your custom Hooks will re-run during every re-render of your component." Smell: side effects or external mutation at the top level of a custom hook. Source: https://react.dev/learn/reusing-logic-with-custom-hooks#passing-reactive-values-between-hooks
- **Pass reactive values between Hooks**: Feed the return value of one hook (e.g. `roomId` from `useState`) as input to another (`useChatRoom({ roomId, serverUrl })`) so the logic "still responds to prop and state changes". Why: "Every time your `ChatRoom` component re-renders, it passes the latest `roomId` and `serverUrl` to your Hook." Smell: custom hook reading stale values captured once instead of receiving them as arguments. Source: https://react.dev/learn/reusing-logic-with-custom-hooks#passing-reactive-values-between-hooks
- **Accept event handlers as named options**: To let callers customize behavior, "change your custom Hook to take `onReceiveMessage` as one of its named options". Why: moves per-component logic back into the component while the hook stays reusable. Smell: hardcoded callback behavior (e.g. `showNotification`) inside a shared hook. Source: https://react.dev/learn/reusing-logic-with-custom-hooks#passing-event-handlers-to-custom-hooks
- **Wrap received event handlers in Effect Events**: "Wrap this event handler into an Effect Event to remove it from the dependencies" (`useEffectEvent(onReceiveMessage)`). Why: "Adding a dependency on `onReceiveMessage` is not ideal because it will cause the chat to re-connect every time the component re-renders." Smell: callback prop listed in a custom hook's `useEffect` dependency array. Source: https://react.dev/learn/reusing-logic-with-custom-hooks#passing-event-handlers-to-custom-hooks
- **Don't extract a Hook for every duplication**: "You don't need to extract a custom Hook for every little duplicated bit of code. Some duplication is fine" - e.g. wrapping "a single `useState` call ... is probably unnecessary." Why: over-abstraction adds indirection without clarity. Smell: `useFormInput` that only wraps one `useState`. Source: https://react.dev/learn/reusing-logic-with-custom-hooks#when-to-use-custom-hooks
- **Consider wrapping every Effect in a custom Hook**: "whenever you write an Effect, consider whether it would be clearer to also wrap it in a custom Hook." Why: "Wrapping it into a custom Hook lets you precisely communicate your intent and how the data flows through it" and prevents others adding "unnecessary dependencies". Smell: raw `useEffect` fetching/subscribing directly in a component. Source: https://react.dev/learn/reusing-logic-with-custom-hooks#when-to-use-custom-hooks
- **Keep unrelated Effects separate**: "it's correct to keep these Effects separate from each other. They synchronize two different things, so you shouldn't merge them into one Effect." Why: each Effect should synchronize one thing. Smell: one `useEffect` fetching cities and areas together. Source: https://react.dev/learn/reusing-logic-with-custom-hooks#when-to-use-custom-hooks
- **Name Hooks so intent is obvious**: A custom hook's name "should be clear enough that even a person who doesn't write code often could have a good guess about what your custom Hook does, what it takes, and what it returns" (`useData(url)`, `useChatRoom(options)`, `useMediaQuery(query)`). Why: "If you struggle to pick a clear name, it might mean that your Effect is too coupled to the rest of your component's logic." Smell: vague names like `useStuff`, `useLogic`, `useHelper`. Source: https://react.dev/learn/reusing-logic-with-custom-hooks#keep-your-custom-hooks-focused-on-concrete-high-level-use-cases
- **No custom "lifecycle" Hooks**: "Avoid creating and using custom 'lifecycle' Hooks that act as alternatives and convenience wrappers for the `useEffect` API itself" - `useMount(fn)`, `useEffectOnce(fn)`, `useUpdateEffect(fn)`. Why: they "don't fit well into the React paradigm" and "the linter won't warn you" about missing reactive dependencies. Smell: `useMount(() => { connect(roomId) })` that ignores `roomId` changes. Source: https://react.dev/learn/reusing-logic-with-custom-hooks#keep-your-custom-hooks-focused-on-concrete-high-level-use-cases
- **Start with the React API directly, then extract**: "If you're writing an Effect, start by using the React API directly" and "Then, you can (but don't have to) extract custom Hooks for different high-level use cases." Why: keeps abstractions grounded in concrete needs. Smell: generic hook abstraction written before any concrete Effect exists. Source: https://react.dev/learn/reusing-logic-with-custom-hooks#keep-your-custom-hooks-focused-on-concrete-high-level-use-cases
- **Constrain what a custom Hook can do**: "A good custom Hook makes the calling code more declarative by constraining what it does." Why: "If your custom Hook API doesn't constrain the use cases and is very abstract, in the long run it's likely to introduce more problems than it solves." Smell: highly generic hook taking arbitrary callbacks and flags. Source: https://react.dev/learn/reusing-logic-with-custom-hooks#keep-your-custom-hooks-focused-on-concrete-high-level-use-cases
- **Wrap Effects in Hooks to ease migration**: "Wrapping your Effects in custom Hooks makes it easier to upgrade your code when these solutions become available" (e.g. moving `useOnlineStatus` to `useSyncExternalStore` without touching components). Why: "When React adds new features, you can remove those Effects without changing any of your components." Smell: raw Effects duplicated across many components that would all need editing to adopt a new API. Source: https://react.dev/learn/reusing-logic-with-custom-hooks#custom-hooks-help-you-migrate-to-better-patterns
- **Prefer useSyncExternalStore for external subscriptions**: For subscribing to browser/external state like `navigator.onLine`, use "a dedicated API called `useSyncExternalStore` which takes care of all of these problems for you." Why: the `useState` + `useEffect` version "assumes that when the component mounts, `isOnline` is already `true`" and breaks on the server. Smell: manual `useState` + `addEventListener` Effect mirroring an external store. Source: https://react.dev/learn/reusing-logic-with-custom-hooks#custom-hooks-help-you-migrate-to-better-patterns
- **Move heavily coordinated imperative logic out of Effects entirely**: "The more coordination between Effects is needed ... the more it makes sense to extract that logic out of Effects and Hooks completely" into a class or plain module that "becomes the 'external system'". Why: "This lets your Effects stay simple because they only need to send messages to the system you've moved outside React." Smell: multiple chained Effects orchestrating animation frames or complex state machines. Source: https://react.dev/learn/reusing-logic-with-custom-hooks#there-is-more-than-one-way-to-do-it
- **Sometimes you don't need a Hook at all**: Prefer a plain CSS animation when it is "both simpler and much more efficient" than a JS Effect - "Sometimes, you don't even need a Hook!" Why: platform features can replace imperative React code. Smell: `requestAnimationFrame` fade-in hook where a CSS `@keyframes` would do. Source: https://react.dev/learn/reusing-logic-with-custom-hooks#there-is-more-than-one-way-to-do-it
- **Wrap tick/listener callbacks in Effect Events inside interval Hooks**: "Inside `useInterval`, wrap the tick callback into an Effect Event" so you can "omit `onTick` from dependencies of your Effect." Why: otherwise "The Effect won't re-synchronize on every re-render" is violated and the interval resets each render. Smell: `useEffect(..., [onTick, delay])` in a `useInterval` hook. Source: https://react.dev/learn/reusing-logic-with-custom-hooks#fix-a-resetting-interval

## Referencing Values with Refs

- **Use a ref for information that should not trigger re-renders**: "When you want a component to 'remember' some information, but you don't want that information to trigger new renders, you can use a ref." Why: "setting state re-renders a component. Changing a ref does not!" Smell: `useState` holding a value never used in JSX (timer id, subscription handle). Source: https://react.dev/learn/referencing-values-with-refs#adding-a-ref-to-your-component
- **Keep rendering data in state, not refs**: "When a piece of information is used for rendering, keep it in state." Why: refs don't re-render, so the screen would not update. Smell: `useRef` value interpolated into JSX. Source: https://react.dev/learn/referencing-values-with-refs#example-building-a-stopwatch
- **Keep handler-only data in a ref**: "When a piece of information is only needed by event handlers and changing it doesn't require a re-render, using a ref may be more efficient" (e.g. "Since the interval ID is not used for rendering, you can keep it in a ref"). Why: avoids unnecessary re-renders. Smell: `const [intervalId, setIntervalId] = useState(null)` used only to `clearInterval`. Source: https://react.dev/learn/referencing-values-with-refs#example-building-a-stopwatch
- **Prefer state; refs are rare**: "in most cases, you'll want to use state. Refs are an 'escape hatch' you won't need often." Why: refs bypass React's tracking and one-way data flow. Smell: components whose logic is built mostly on `ref.current` mutation. Source: https://react.dev/learn/referencing-values-with-refs#differences-between-refs-and-state
- **Don't read or write `ref.current` during rendering**: "Don't read or write `ref.current` during rendering. If some information is needed during rendering, use state instead." Why: "Since React doesn't know when `ref.current` changes, even reading it while rendering makes your component's behavior difficult to predict." Smell: `{countRef.current}` or `if (ref.current) ...` in the component body driving JSX. Source: https://react.dev/learn/referencing-values-with-refs#best-practices-for-refs
- **Lazy one-time ref initialization is the exception**: The only render-time ref access allowed is "code like `if (!ref.current) ref.current = new Thing()` which only sets the ref once during the first render." Why: it is idempotent after the first run. Smell (non-issue): guarded first-render initialization of a ref. Source: https://react.dev/learn/referencing-values-with-refs#best-practices-for-refs
- **Treat refs as an escape hatch for external systems**: "Refs are useful when you work with external systems or browser APIs. If much of your application logic and data flow relies on refs, you might want to rethink your approach." Why: refs step outside React's one-way data flow. Smell: business logic or derived UI values stored and read via refs. Source: https://react.dev/learn/referencing-values-with-refs#best-practices-for-refs
- **Use refs for timeout IDs, DOM elements, and non-render objects**: Typical ref uses are "Storing timeout IDs", "Storing and manipulating DOM elements", "Storing other objects that aren't necessary to calculate the JSX." Why: "If your component needs to store some value, but it doesn't impact the rendering logic, choose refs." Smell: such values kept in state or module variables. Source: https://react.dev/learn/referencing-values-with-refs#when-to-use-refs
- **Don't keep per-render data in plain local variables across events**: Store a timeout ID "in a ref, which React will preserve between renders" rather than `let timeoutID = null` in the component body. Why: "all local variables get initialized from scratch" on each re-render, so another handler cannot "see" the value. Smell: `let timeoutID` declared in component body and assigned in a handler. Source: https://react.dev/learn/referencing-values-with-refs#fix-a-broken-chat-input
- **Ref-driven toggles that render must become state**: If "the current value of a ref is used to calculate the rendering output ... this information should not be in a ref, and should have instead been put in state." Why: mutating the ref never re-renders, so the button "always shows 'Off'". Smell: `{isOnRef.current ? 'On' : 'Off'}`. Source: https://react.dev/learn/referencing-values-with-refs#fix-a-component-failing-to-re-render
- **Don't share module-level mutable variables between component instances**: Keep a per-instance timeout "in a ref. Each button will get its own ref, so they won't conflict with each other." Why: "A variable like `timeoutID` is shared between all components", so one instance resets another's timer. Smell: `let timeoutID;` at module scope used by a reusable component. Source: https://react.dev/learn/referencing-values-with-refs#fix-debouncing
- **Mirror state into a ref when async code needs the latest value**: To read the latest text in a timeout, "keep the latest input text in a ref" alongside state and "update the current ref value manually" in the change handler. Why: "State works like a snapshot, so you can't read the latest state from an asynchronous operation like a timeout." Smell: `setTimeout(() => alert(text))` expecting post-click edits to be reflected. Source: https://react.dev/learn/referencing-values-with-refs#read-the-latest-state

## Manipulating the DOM with Refs

- **Use a ref to reach DOM nodes React manages**: To "focus a node, scroll to it, or measure its size and position", declare `const myRef = useRef(null)` and pass `<div ref={myRef}>`. Why: "There is no built-in way to do those things in React". Smell: `document.querySelector`/`getElementById` used inside a component to find its own elements. Source: https://react.dev/learn/manipulating-the-dom-with-refs#getting-a-ref-to-the-node
- **Access DOM refs from event handlers**: "You can then access this DOM node from your event handlers and use the built-in browser APIs defined on it." Why: refs are populated during commit, so handlers see a valid node. Smell: `inputRef.current.focus()` executed in the component body. Source: https://react.dev/learn/manipulating-the-dom-with-refs#getting-a-ref-to-the-node
- **Don't call useRef inside map/loops/conditions**: `items.map(() => { const ref = useRef(null); ... })` "Doesn't work!" because "Hooks must only be called at the top-level of your component." Why: hook count would vary with list length. Smell: `useRef` inside `.map()` callback. Source: https://react.dev/learn/manipulating-the-dom-with-refs#how-to-manage-a-list-of-refs-using-a-ref-callback
- **Avoid querySelectorAll on a parent ref for list items**: Using a parent ref plus `querySelectorAll` "is brittle and can break if your DOM structure changes." Why: it couples logic to DOM shape. Smell: `listRef.current.querySelectorAll('li')[index]`. Source: https://react.dev/learn/manipulating-the-dom-with-refs#how-to-manage-a-list-of-refs-using-a-ref-callback
- **Use a ref callback with cleanup for lists of refs**: "pass a function to the `ref` attribute" that stores the node in a Map and returns a cleanup that deletes it. Why: React "will call your ref callback with the DOM node when it's time to set the ref, and call the cleanup function returned from the callback when it's time to clear it." Smell: array of refs created ad hoc, or ref callback without cleanup leaking removed nodes. Source: https://react.dev/learn/manipulating-the-dom-with-refs#how-to-manage-a-list-of-refs-using-a-ref-callback
- **Expect ref callbacks to run twice under StrictMode**: "When Strict Mode is enabled, ref callbacks will run twice in development." Why: helps find non-idempotent ref callbacks. Smell: ref callback that appends or counts without being idempotent/cleaned up. Source: https://react.dev/learn/manipulating-the-dom-with-refs#how-to-manage-a-list-of-refs-using-a-ref-callback
- **Be cautious touching another component's DOM**: "Refs are an escape hatch. Manually manipulating another component's DOM nodes can make your code fragile." Why: the child owns its DOM structure. Smell: parent reaching into a child's internals via a forwarded ref for styling or structure changes. Source: https://react.dev/learn/manipulating-the-dom-with-refs#accessing-another-components-dom-nodes
- **Pass `ref` as a prop to expose a child's DOM node**: "You can pass refs from parent component to child components just like any other prop" (`function MyInput({ ref }) { return <input ref={ref} /> }`). Why: "A component doesn't expose its DOM nodes by default. You can opt into exposing a DOM node by using the `ref` prop." Smell: `forwardRef` wrappers or hacks where a plain `ref` prop suffices in React 19. Source: https://react.dev/learn/manipulating-the-dom-with-refs#accessing-another-components-dom-nodes
- **Restrict exposed API with useImperativeHandle when needed**: "In uncommon cases, you may want to restrict the exposed functionality. You can do that with `useImperativeHandle`" exposing "Only ... focus and nothing else". Why: forwarding the raw node "lets the parent component do something else - for example, change its CSS styles." Smell: raw DOM node forwarded when the parent should only be able to focus. Source: https://react.dev/learn/manipulating-the-dom-with-refs#exposing-a-subset-of-the-api-with-an-imperative-handle
- **Don't access DOM refs during render**: "you don't want to access refs during rendering. That goes for refs holding DOM nodes as well." Why: "During the first render, the DOM nodes have not yet been created, so `ref.current` will be `null`. And during the rendering of updates, the DOM nodes haven't been updated yet." Smell: `ref.current.getBoundingClientRect()` in the component body. Source: https://react.dev/learn/manipulating-the-dom-with-refs#when-react-attaches-the-refs
- **Access refs from event handlers, else an Effect**: "Usually, you will access refs from event handlers. If you want to do something with a ref, but there is no particular event to do it in, you might need an Effect." Why: React "sets `ref.current` during the commit". Smell: DOM measurement or focus logic outside handlers/Effects. Source: https://react.dev/learn/manipulating-the-dom-with-refs#when-react-attaches-the-refs
- **Use flushSync when the DOM must update before a ref read**: "wrap the state update into a `flushSync` call" from `react-dom` before `listRef.current.lastChild.scrollIntoView()`. Why: "state updates are queued", so "`setTodos` does not immediately update the DOM" and the scroll "lags behind by one item". Smell: `setState(...)` immediately followed by a DOM read/scroll on a ref in the same handler. Source: https://react.dev/learn/manipulating-the-dom-with-refs#flushing-state-updates-synchronously-with-flush-sync
- **Only use DOM refs to step outside React**: "You should only use them when you have to 'step outside React'. Common examples of this include managing focus, scroll position, or calling browser APIs that React does not expose." Why: React already "automatically updates the DOM to match your render output". Smell: refs used to set text, classes or children that JSX could express. Source: https://react.dev/learn/manipulating-the-dom-with-refs#best-practices-for-dom-manipulation-with-refs
- **Stick to non-destructive actions**: "If you stick to non-destructive actions like focusing and scrolling, you shouldn't encounter any problems." Why: modifying the DOM manually risks "conflicting with the changes React is making". Smell: `ref.current.remove()`, `appendChild`, `innerHTML =` on React-managed nodes. Source: https://react.dev/learn/manipulating-the-dom-with-refs#best-practices-for-dom-manipulation-with-refs
- **Avoid changing DOM nodes managed by React**: "Avoid changing DOM nodes managed by React. Modifying, adding children to, or removing children from elements that are managed by React can lead to inconsistent visual results or crashes." Why: "you've changed the DOM, and React doesn't know how to continue managing it correctly." Smell: conditional-rendered element also removed imperatively via a ref. Source: https://react.dev/learn/manipulating-the-dom-with-refs#best-practices-for-dom-manipulation-with-refs
- **Only modify DOM parts React has no reason to update**: "You can safely modify parts of the DOM that React has no reason to update. For example, if some `<div>` is always empty in the JSX, React won't have a reason to touch its children list." Why: React never reconciles children it doesn't render. Smell: third-party widget mounted into a div that also has JSX children. Source: https://react.dev/learn/manipulating-the-dom-with-refs#best-practices-for-dom-manipulation-with-refs
- **Sync state with DOM events when the DOM can change on its own**: Add `onPlay`/`onPause` handlers that call `setIsPlaying` "so if the user plays the video using the browser controls, the state will adjust accordingly." Why: imperative `play()`/`pause()` alone leaves state out of sync with native controls. Smell: `isPlaying` state toggled only by the app button while a `<video>` has native controls. Source: https://react.dev/learn/manipulating-the-dom-with-refs#play-and-pause-the-video
- **Attach a ref conditionally to track the active item**: Pass `ref={index === i ? selectedRef : null}` so "React will make sure that `selectedRef.current` always points at the correct DOM node", combined with `flushSync` before scrolling. Why: avoids one ref per item and "the `flushSync` call is necessary to force React to update the DOM before the scroll." Smell: array of refs for every item just to scroll the selected one. Source: https://react.dev/learn/manipulating-the-dom-with-refs#scrolling-an-image-carousel

## Passing Data Deeply with Context

- **Create and export the context with a default value**: "Create and export it with `export const MyContext = createContext(defaultValue)`." Why: the argument is "the default value" React uses "If you don't provide the context". Smell: `createContext()` with no meaningful default, or context created inside a component. Source: https://react.dev/learn/passing-data-deeply-with-context#step-1-create-the-context
- **Read context with useContext at the top level**: "you can only call a Hook immediately inside a React component (not inside loops or conditions). `useContext` tells React that the `Heading` component wants to read the `LevelContext`." Why: `useContext` is a Hook and follows the Rules of Hooks. Smell: `useContext` inside a condition, loop, or callback. Source: https://react.dev/learn/passing-data-deeply-with-context#step-2-use-the-context
- **Provide context or the default is used**: "even though you're using the context, you have not provided it yet. React doesn't know where to get it!" - wrap consumers in a provider. Why: without a provider "React will use the default value you've specified". Smell: `useContext` consumer with no `<MyContext value>` ancestor, silently receiving the default. Source: https://react.dev/learn/passing-data-deeply-with-context#step-2-use-the-context
- **Provide with `<MyContext value={...}>` wrapping children**: "Wrap children into `<MyContext value={...}>` to provide it from a parent." Why: "The component will use the value of the nearest `<MyContext>` in the UI tree above it." Smell: legacy `<MyContext.Provider>` where React 19's `<MyContext value>` is available; provider placed as a sibling rather than an ancestor. Source: https://react.dev/learn/passing-data-deeply-with-context#step-3-provide-the-context
- **A component may read context and provide a modified value below**: Let `Section` do `const level = useContext(LevelContext)` and render `<LevelContext value={level + 1}>`. Why: "each `Section` could read the `level` from the `Section` above, and pass `level + 1` down automatically" so no manual prop is needed. Smell: nesting depth or theme passed manually as a prop at every level. Source: https://react.dev/learn/passing-data-deeply-with-context#using-and-providing-context-from-the-same-component
- **Override context only by wrapping in another provider**: "the only way to override some context coming from above is to wrap children into a context provider with a different value." Why: context "might remind you of CSS property inheritance" - the nearest provider wins. Smell: attempting to mutate the received context value to change it for children. Source: https://react.dev/learn/passing-data-deeply-with-context#context-passes-through-intermediate-components
- **Keep unrelated concerns in separate contexts**: "different React contexts don't override each other. Each context that you make with `createContext()` is completely separate from other ones." Why: "One component may use or provide many different contexts without a problem." Smell: one giant context object bundling theme, user, and routing state. Source: https://react.dev/learn/passing-data-deeply-with-context#context-passes-through-intermediate-components
- **Don't reach for context just because props go several levels deep**: "Just because you need to pass some props several levels deep doesn't mean you should put that information into context." Why: "Context is very tempting to use! However, this also means it's too easy to overuse it." Smell: context introduced to avoid passing a prop through two or three components. Source: https://react.dev/learn/passing-data-deeply-with-context#before-you-use-context
- **Start by passing props**: "Start by passing props. If your components are not trivial, it's not unusual to pass a dozen props down through a dozen components." Why: "it makes it very clear which components use which data" and "made the data flow explicit". Smell: context as first resort for any shared value. Source: https://react.dev/learn/passing-data-deeply-with-context#before-you-use-context
- **Extract components and pass JSX as `children`**: When intermediate components only forward data, "make `Layout` take `children` as a prop, and render `<Layout><Posts posts={posts} /></Layout>`." Why: "this often means that you forgot to extract some components along the way" and it "reduces the number of layers". Smell: `<Layout posts={posts} />` where `Layout` never uses `posts`. Source: https://react.dev/learn/passing-data-deeply-with-context#before-you-use-context
- **Use context only when props and composition fail**: "If neither of these approaches works well for you, consider context." Why: context should be the fallback after explicit alternatives. Smell: context added without first trying props or `children` composition. Source: https://react.dev/learn/passing-data-deeply-with-context#before-you-use-context
- **Reserve context for tree-wide concerns**: Good use cases are "Theming", "Current account", "Routing", and "Managing state" with a reducer; "if some information is needed by distant components in different parts of the tree, it's a good indication that context will help you." Why: these values are needed by many distant components. Smell: context for data used by a single subtree branch or only one consumer. Source: https://react.dev/learn/passing-data-deeply-with-context#use-cases-for-context
- **Combine context with state for dynamic values**: "Context is not limited to static values. If you pass a different value on the next render, React will update all the components reading it below!" Why: "This is why context is often used in combination with state." Smell: context value derived from a mutable module variable instead of state. Source: https://react.dev/learn/passing-data-deeply-with-context#use-cases-for-context

## Scaling Up with Reducer and Context

- **Combine a reducer with context for complex shared state**: "You can combine reducers and context together to manage state of a complex screen" so "any component below `TaskApp` in the tree can read the tasks and dispatch actions without the repetitive 'prop drilling'." Why: passing "all state and functions" through "tens or hundreds of components in the middle ... can be quite frustrating". Smell: `tasks`, `onChangeTask`, `onDeleteTask` threaded through several layers that don't use them. Source: https://react.dev/learn/scaling-up-with-reducer-and-context#combining-a-reducer-with-context
- **Create two separate contexts for state and dispatch**: "you will create two separate contexts: `TasksContext` provides the current list of tasks. `TasksDispatchContext` provides the function that lets components dispatch actions." Why: consumers can subscribe to state or dispatch independently. Smell: single context carrying `{ tasks, dispatch }` together. Source: https://react.dev/learn/scaling-up-with-reducer-and-context#step-1-create-the-context
- **Export contexts from a separate file**: "Export them from a separate file so that you can later import them from other files." Why: consumers across the tree need to import the same context object. Smell: `createContext` defined inline in the component file that also renders the app. Source: https://react.dev/learn/scaling-up-with-reducer-and-context#step-1-create-the-context
- **Provide both state and dispatch from the reducer's component**: "Take the `tasks` and `dispatch` returned by `useReducer()` and provide them to the entire tree below" via nested `<TasksContext value={tasks}><TasksDispatchContext value={dispatch}>`. Why: "Provide both contexts from the component that uses the reducer." Smell: provider placed in a component that does not own the `useReducer` call. Source: https://react.dev/learn/scaling-up-with-reducer-and-context#step-2-put-state-and-dispatch-into-context
- **Remove prop passing once context is provided**: "Now you don't need to pass the list of tasks or the event handlers down the tree"; each component "reads the context that it needs". Why: keeping both props and context is redundant wiring. Smell: `<TaskList tasks={tasks} onChangeTask={...} />` still passed while the same values are in context. Source: https://react.dev/learn/scaling-up-with-reducer-and-context#step-3-use-context-anywhere-in-the-tree
- **Dispatch actions from consumers via the dispatch context**: "To update the task list, any component can read the `dispatch` function from context and call it." Why: avoids passing handler callbacks through intermediaries. Smell: leaf components receiving `onChange`/`onDelete` callbacks that merely wrap `dispatch`. Source: https://react.dev/learn/scaling-up-with-reducer-and-context#step-3-use-context-anywhere-in-the-tree
- **Move reducer and contexts into one file with a Provider component**: "declare a new `TasksProvider` component in the same file" that manages state with the reducer, provides both contexts, and takes `children` as a prop. Why: "This removes all the complexity and wiring from your `TaskApp` component." Smell: app component cluttered with `useReducer` plus two nested providers. Source: https://react.dev/learn/scaling-up-with-reducer-and-context#moving-all-wiring-into-a-single-file
