# React 19.2 code-review rules: rendering, props, hooks, React 19 APIs, compiler

## Rendering Lists

- **Keys on mapped JSX**: Give every JSX element "directly inside a `map()` call" a `key`. Why: keys let React "keep track of each of them even if their position or data changes". Smell: `items.map((item) => <Row item={item} />)` with no `key` prop. Source: https://react.dev/learn/rendering-lists#keeping-list-items-in-order-with-key
- **Keys from data, not on the fly**: "Rather than generating keys on the fly, you should include them in your data" (database IDs, or `crypto.randomUUID()`/`uuid` assigned once when the item is created). Why: keys must be stable across renders to identify the same item. Smell: `key={\`${item.name}-${Date.now()}\`}` or ids computed inside the render body. Source: https://react.dev/learn/rendering-lists#where-to-get-your-key
- **Keys unique among siblings**: "Keys must be unique among siblings", though "it's okay to use the same keys for JSX nodes in different arrays". Why: React matches siblings by key; duplicates make matching ambiguous. Smell: `key={item.type}` where several items share a type. Source: https://react.dev/learn/rendering-lists#rules-of-keys
- **Keys must not change**: "Keys must not change or that defeats their purpose! Don't generate them while rendering." Why: a changing key tells React the item is a different one. Smell: `key={Math.random()}`, `key={index + offset}` where offset changes. Source: https://react.dev/learn/rendering-lists#rules-of-keys
- **No index keys on dynamic lists**: Do not use the array index as key when items can be "inserted, deleted, or if the array gets reordered"; "Index as a key often leads to subtle and confusing bugs." Why: index identifies position, not the item, so state and DOM get attached to the wrong item. Smell: `key={index}` on a list that can reorder, filter, or grow at the front. Source: https://react.dev/learn/rendering-lists#why-does-react-need-keys
- **No random keys**: "do not generate keys on the fly, e.g. with `key={Math.random()}`"; "use a stable ID based on the data". Why: "keys never match up between renders, leading to all your components and DOM being recreated every time", which is slow and "will also lose any user input inside the list items". Smell: `key={Math.random()}`, `key={crypto.randomUUID()}` inside render. Source: https://react.dev/learn/rendering-lists#why-does-react-need-keys
- **Key is not a prop**: "your components won't receive `key` as a prop"; "If your component needs an ID, you have to pass it as a separate prop: `<Profile key={id} userId={id} />`." Why: `key` is "only used as a hint by React itself". Smell: a component reading `props.key` or destructuring `{ key }`. Source: https://react.dev/learn/rendering-lists#why-does-react-need-keys
- **Fragment key for multiple nodes per item**: When each item needs to render several DOM nodes, wrap them in "the `<Fragment>` syntax" (the explicit `<Fragment key={...}>`, since "the short `<>...</>` syntax won't let you pass a key"). Why: keys must be on the element directly returned from `map()`. Smell: `<><h1 /><p /></>` returned from `map()` with the key placed on an inner child. Source: https://react.dev/learn/rendering-lists#displaying-several-dom-nodes-for-each-list-item
- **Explicit return in block-body arrows**: "you must write `return` explicitly if your `=>` is followed by a `{` curly brace!" Why: with a block body, "If you forget it, nothing gets returned!" Smell: `items.map((item) => { <li>{item}</li> })` rendering nothing. Source: https://react.dev/learn/rendering-lists#filtering-arrays-of-items
- **Move list data out of components**: "move data out of components and into data structures like arrays and objects" and render them with `map()`/`filter()`. Why: avoids duplicating near-identical JSX by hand. Smell: five copy-pasted `<li>` siblings differing only in text. Source: https://react.dev/learn/rendering-lists#recap

## Conditional Rendering

- **Prefer parent-side exclusion over returning null**: "returning `null` from a component isn't common because it might surprise a developer trying to render it. More often, you would conditionally include or exclude the component in the parent component's JSX." Why: keeps a component's rendering contract predictable. Smell: a leaf component whose first line is `if (!isVisible) return null` while the parent always renders it. Source: https://react.dev/learn/conditional-rendering#conditionally-returning-nothing-with-null
- **Ternaries in moderation**: The ternary "works well for simple conditions, but use it in moderation"; "If your components get messy with too much nested conditional markup, consider extracting child components to clean things up." Why: nested ternaries make markup hard to read. Smell: `a ? <X/> : b ? <Y/> : <Z/>` inside JSX. Source: https://react.dev/learn/conditional-rendering#conditional-ternary-operator--
- **No numbers on the left of &&**: "Don't put numbers on the left side of `&&`." Why: "if the left side is `0`, then the whole expression gets that value (`0`), and React will happily render `0` rather than nothing." Smell: `messageCount && <p>New messages</p>`; fix is `messageCount > 0 && ...`. Source: https://react.dev/learn/conditional-rendering#logical-and-operator-
- **Use variables and if for complex branches**: "you can use tools like variables and functions to tidy up complex expressions"; assigning JSX to a `let` and using `if` "is the most verbose, but it's also the most flexible." Why: markup is code, so branching logic can live outside the JSX tree. Smell: a long inline conditional chain where a `let itemContent` plus `if` would read better. Source: https://react.dev/learn/conditional-rendering#conditionally-assigning-jsx-to-a-variable
- **Avoid duplicated branches**: When two `return` branches differ only slightly, do not duplicate the markup; "you can conditionally include a little JSX" inside a single return. Why: duplicated JSX is "harder to maintain" when the shared parts change. Smell: two `return <li className="item">...</li>` statements differing in one string. Source: https://react.dev/learn/conditional-rendering#conditionally-including-jsx
- **Shortcuts are optional**: "The shortcuts are common, but you don't have to use them if you prefer plain `if`." Why: readability beats terseness. Smell: contorted `&&`/`??` chains to avoid an `if` statement. Source: https://react.dev/learn/conditional-rendering#recap

## Passing Props to a Component

- **Destructure props in the signature**: "To read props, use the `function Avatar({ person, size })` destructuring syntax." Why: it is the conventional, readable equivalent of `props.person`. Smell: `function Avatar(props)` followed by repeated `props.x` reads. Source: https://react.dev/learn/passing-props-to-a-component#step-2-read-props-inside-the-child-component
- **Curlies inside parens when destructuring**: "Don't miss the pair of `{` and `}` curlies inside of `(` and `)` when declaring props." Why: without them you are declaring a positional parameter, not destructuring. Smell: `function Avatar(person, size)`. Source: https://react.dev/learn/passing-props-to-a-component#step-2-read-props-inside-the-child-component
- **Default values via destructuring**: Give fallbacks "by putting `=` and the default value right after the parameter" (`size = 100`). Why: "used for missing and `undefined` props". Smell: `const size = props.size || 100` or `defaultProps` on a function component. Source: https://react.dev/learn/passing-props-to-a-component#specifying-a-default-value-for-a-prop
- **Defaults do not cover null or 0**: "if you pass `size={null}` or `size={0}`, the default value will not be used." Why: destructuring defaults only apply to `undefined`. Smell: passing `null` to a prop and expecting the default. Source: https://react.dev/learn/passing-props-to-a-component#specifying-a-default-value-for-a-prop
- **Spread with restraint**: "Use spread syntax with restraint. If you're using it in every other component, something is wrong. Often, it indicates that you should split your components and pass children as JSX." Why: blanket forwarding hides what a component actually needs. Smell: `<Avatar {...props} />` in most components of a feature. Source: https://react.dev/learn/passing-props-to-a-component#forwarding-props-with-the-jsx-spread-syntax
- **Pass JSX as children for wrappers**: For components that wrap arbitrary content, nest JSX so it "will appear as `Card` component's `children` prop". Why: the wrapper "doesn't need to 'know' what's being rendered inside of it". Smell: `<Card content={<Avatar />} />` or wrapper components with many render-slot props. Source: https://react.dev/learn/passing-props-to-a-component#passing-jsx-as-children
- **Props are read-only**: "Don't try to 'change props'." "When you need to respond to the user input... you will need to 'set state'." Why: "Props are read-only snapshots in time: every render receives a new version of props." Smell: `props.person.name = 'X'` or `person.count++` inside a component. Source: https://react.dev/learn/passing-props-to-a-component#how-props-change-over-time
- **Ask the parent for new props**: To change a prop, "ask its parent component to pass it different props" rather than mutating. Why: one-way data flow keeps rendering predictable. Smell: a child mutating an object it received to "update" the parent. Source: https://react.dev/learn/passing-props-to-a-component#how-props-change-over-time

## Thinking in React

- **Single responsibility per component**: "a component should ideally only be concerned with one thing. If it ends up growing, it should be decomposed into smaller subcomponents." Why: the same principle that makes functions readable applies to components. Smell: one component rendering a search bar, filters, table rows, and empty state. Source: https://react.dev/learn/thinking-in-react#step-1-break-the-ui-into-a-component-hierarchy
- **Match components to the data model**: "Separate your UI into components, where each component matches one piece of your data model." Why: "If your JSON is well-structured, you'll often find that it naturally maps to the component structure". Smell: a component that receives half the fields of three different entities. Source: https://react.dev/learn/thinking-in-react#step-1-break-the-ui-into-a-component-hierarchy
- **Static version first, no state**: "don't use state at all to build this static version. State is reserved only for interactivity, that is, data that changes over time." Why: separates the typing-heavy layout work from the thinking-heavy interactivity work. Smell: `useState` added to a component that never changes the value. Source: https://react.dev/learn/thinking-in-react#step-2-build-a-static-version-in-react
- **Minimal state, compute the rest**: "Figure out the absolute minimal representation of the state your application needs and compute everything else on-demand." Why: "The most important principle for structuring state is to keep it DRY". Smell: `const [items, setItems]` alongside `const [itemCount, setItemCount]`. Source: https://react.dev/learn/thinking-in-react#step-3-find-the-minimal-but-complete-representation-of-ui-state
- **Unchanging values are not state**: "Does it remain unchanged over time? If so, it isn't state." Why: state exists only for data that changes. Smell: `useState(PRODUCTS)` with no setter ever called. Source: https://react.dev/learn/thinking-in-react#step-3-find-the-minimal-but-complete-representation-of-ui-state
- **Props are not state**: "Is it passed in from a parent via props? If so, it isn't state." Why: copying a prop into state creates two sources of truth. Smell: `const [value, setValue] = useState(props.value)` plus an effect to re-sync it. Source: https://react.dev/learn/thinking-in-react#step-3-find-the-minimal-but-complete-representation-of-ui-state
- **Computable values are not state**: "Can you compute it based on existing state or props in your component? If so, it definitely isn't state!" Why: derived state gets out of sync and is redundant. Smell: `const [filteredProducts, setFilteredProducts]` updated whenever `filterText` changes. Source: https://react.dev/learn/thinking-in-react#step-3-find-the-minimal-but-complete-representation-of-ui-state
- **State lives in the closest common parent**: For each piece of state "Identify every component that renders something based on that state", "Find their closest common parent", and "Often, you can put the state directly into their common parent." Why: "React uses one-way data flow, passing data down the component hierarchy". Smell: two siblings each owning a copy of the same filter value. Source: https://react.dev/learn/thinking-in-react#step-4-identify-where-your-state-should-live
- **Create a holder component when needed**: "If you can't find a component where it makes sense to own the state, create a new component solely for holding the state and add it somewhere in the hierarchy above the common parent component." Why: avoids forcing state into an unrelated component. Smell: state lifted into a layout/root component that has nothing to do with it. Source: https://react.dev/learn/thinking-in-react#step-4-identify-where-your-state-should-live
- **Inverse data flow via passed setters**: "The state is owned by `FilterableProductTable`, so only it can call `setFilterText`"; to let children update it, "pass these functions down" and call them from the child's "`onChange` event handlers". Why: makes data flow explicit. Smell: child components mutating shared objects or reaching into refs to change parent state. Source: https://react.dev/learn/thinking-in-react#step-5-add-inverse-data-flow

## useMemo

- **Top level only**: "you can only call it at the top level of your component or your own Hooks. You can't call it inside loops or conditions. If you need that, extract a new component and move the state into it." Why: hook call order must be stable. Smell: `useMemo` inside `items.map(...)` or after an early `return`. Source: https://react.dev/reference/react/useMemo#caveats
- **Performance only, not correctness**: "You should only rely on `useMemo` as a performance optimization. If your code doesn't work without it, find the underlying problem and fix it first." Why: "React may throw away the cache if there is a specific reason to do that." Smell: logic that breaks (loops, double-fires) when `useMemo` is removed. Source: https://react.dev/reference/react/useMemo#caveats
- **Only three valid reasons**: Wrap a calculation only when it "is noticeably slow, and its dependencies rarely change", it is passed "as a prop to a component wrapped in `memo`", or it "is later used as a dependency of some Hook". Why: "There is no benefit to wrapping a calculation in `useMemo` in other cases" and "code becomes less readable". Smell: `useMemo(() => a + b, [a, b])` or memoizing a string concat passed to a plain DOM element. Source: https://react.dev/reference/react/useMemo#should-you-add-usememo-everywhere
- **Accept children instead of memoizing**: "When a component visually wraps other components, let it accept JSX as children." Why: "when the wrapper component updates its own state, React knows that its children don't need to re-render." Smell: memoizing a heavy subtree that could have been passed as `children`. Source: https://react.dev/reference/react/useMemo#should-you-add-usememo-everywhere
- **Keep state local**: "Prefer local state and don't lift state up any further than necessary... don't keep transient state like forms and whether an item is hovered at the top of your tree or in a global state library." Why: high-up state re-renders large subtrees, inviting memoization. Smell: `isHovered` or form draft values stored in a global store. Source: https://react.dev/reference/react/useMemo#should-you-add-usememo-everywhere
- **Fix impurity, don't memoize over it**: "If re-rendering a component causes a problem or produces some noticeable visual artifact, it's a bug in your component! Fix the bug instead of adding memoization." Why: memoization only hides the impurity. Smell: `useMemo` added to stop a side effect from running twice. Source: https://react.dev/reference/react/useMemo#should-you-add-usememo-everywhere
- **Avoid Effects that set state**: "Avoid unnecessary Effects that update state. Most performance problems in React apps are caused by chains of updates originating from Effects." Why: effect chains render components "over and over". Smell: `useEffect(() => setX(compute(y)), [y])`. Source: https://react.dev/reference/react/useMemo#should-you-add-usememo-everywhere
- **Move objects inside the calculation**: "An even better fix is to move the `searchOptions` object declaration inside of the `useMemo` calculation function" so the dependency is a primitive. Why: "Depending on an object like this defeats the point of memoization" because it is "different every time". Smell: `useMemo(..., [allItems, searchOptions])` where `searchOptions` is an object literal in the component body. Source: https://react.dev/reference/react/useMemo#memoizing-a-dependency-of-another-hook
- **useCallback for functions**: "Wrap your functions into `useCallback` instead of `useMemo`" when memoizing a function. Why: `useMemo(() => () => ...)` "looks clunky" and is otherwise equivalent. Smell: `useMemo(() => (arg) => doThing(arg), deps)`. Source: https://react.dev/reference/react/useMemo#memoizing-a-function
- **Never mutate inputs in the calculation**: "Your calculation shouldn't change any existing objects, but it's okay to change any new objects you created during the calculation." Why: Strict Mode calls it twice and impurity shows as duplicated data. Smell: `todos.push(...)` inside `useMemo`. Source: https://react.dev/reference/react/useMemo#my-calculation-runs-twice-on-every-re-render
- **Explicit return for object results**: "write a `return` statement explicitly" instead of relying on `() => ({ ... })`. Why: `() => {` starts a block body, so the object is silently not returned, and the parens fix is "too easy for someone to break". Smell: `useMemo(() => ({ a, b }), [a, b])`. Source: https://react.dev/reference/react/useMemo#my-usememo-call-is-supposed-to-return-an-object-but-returns-undefined
- **Always pass the dependency array**: "Make sure you've specified the dependency array as a second argument!" Why: without it "`useMemo` will re-run the calculation every time". Smell: `useMemo(() => filterTodos(todos, tab))`. Source: https://react.dev/reference/react/useMemo#every-time-my-component-renders-the-calculation-in-usememo-re-runs
- **Extract a per-item component for lists**: When you need `useMemo` per list item, "Extract a component for each item and memoize data for individual items", or "remove `useMemo` and instead wrap `Report` itself in `memo`". Why: hooks cannot be called in loops. Smell: `useMemo` inside `.map()`. Source: https://react.dev/reference/react/useMemo#i-need-to-call-usememo-for-each-list-item-in-a-loop-but-its-not-allowed

## useCallback

- **Top level only**: `useCallback` is a Hook, "so you can only call it at the top level of your component or your own Hooks. You can't call it inside loops or conditions." Why: hook order must be stable. Smell: `useCallback` inside `.map()` or an `if`. Source: https://react.dev/reference/react/useCallback#caveats
- **Performance only**: "You should only rely on `useCallback` as a performance optimization. If your code doesn't work without it, find the underlying problem and fix it first." Why: the cache is not a semantic guarantee. Smell: behavior that changes when `useCallback` is deleted. Source: https://react.dev/reference/react/useCallback#skipping-re-rendering-of-components
- **Only two valid reasons**: Cache a function only when "You pass it as a prop to a component wrapped in `memo`" or "The function you're passing is later used as a dependency of some Hook". Why: "There is no benefit to wrapping a function in `useCallback` in other cases" and "code becomes less readable". Smell: `useCallback` on a handler passed straight to `<button onClick>`. Source: https://react.dev/reference/react/useCallback#should-you-add-usecallback-everywhere
- **useCallback does not avoid creating the function**: "`useCallback` does not prevent creating the function. You're always creating a function (and that's fine!)". Why: the only effect is a stable identity, not saved allocation. Smell: justifying `useCallback` as "avoids re-creating the function". Source: https://react.dev/reference/react/useCallback#should-you-add-usecallback-everywhere
- **Follow the five memo-avoidance principles**: accept JSX as children, "Prefer local state", "Keep your rendering logic pure", "Avoid unnecessary Effects that update state", "remove unnecessary dependencies from your Effects". Why: "you can make a lot of memoization unnecessary by following a few principles". Smell: `useCallback` sprinkled everywhere instead of restructuring. Source: https://react.dev/reference/react/useCallback#should-you-add-usecallback-everywhere
- **Profile before memoizing**: "If a specific interaction still feels laggy, use the React Developer Tools profiler to see which components benefit the most from memoization, and add memoization where needed." Why: targeted memoization beats blanket memoization. Smell: PR adding `useCallback` with no measured lag. Source: https://react.dev/reference/react/useCallback#should-you-add-usecallback-everywhere
- **Updater functions instead of state deps**: "When you read some state only to calculate the next state, you can remove that dependency by passing an updater function instead." Why: "You'll usually want memoized functions to have as few dependencies as possible." Smell: `useCallback(() => setTodos([...todos, x]), [todos])`. Source: https://react.dev/reference/react/useCallback#updating-state-from-a-memoized-callback
- **Move functions inside Effects**: "it's even better to remove the need for a function dependency. Move your function inside the Effect." Why: "your code is simpler and doesn't need `useCallback`". Smell: `useCallback(createOptions, [roomId])` used only inside one `useEffect`. Source: https://react.dev/reference/react/useCallback#preventing-an-effect-from-firing-too-often
- **Wrap custom Hook return functions**: "If you're writing a custom Hook, it's recommended to wrap any functions that it returns into `useCallback`." Why: "This ensures that the consumers of your Hook can optimize their own code when needed." Smell: a shared hook returning `navigate = (url) => dispatch(...)` unmemoized. Source: https://react.dev/reference/react/useCallback#optimizing-a-custom-hook
- **Always pass the dependency array**: "Make sure you've specified the dependency array as a second argument!" Why: without it "`useCallback` will return a new function every time". Smell: `useCallback((x) => ...)` with one argument. Source: https://react.dev/reference/react/useCallback#every-time-my-component-renders-usecallback-returns-a-different-function
- **Extract item component or memo it for lists**: "extract a component for an individual item, and put `useCallback` there" or "remove `useCallback`... and instead wrap `Report` itself in `memo`". Why: hooks cannot run in loops. Smell: `useCallback` in `.map()`. Source: https://react.dev/reference/react/useCallback#i-need-to-call-usecallback-for-each-list-item-in-a-loop-but-its-not-allowed

## useEffect

- **Top level only**: "you can only call it at the top level of your component or your own Hooks. You can't call it inside loops or conditions." Why: hook order must be stable. Smell: `useEffect` after an early return or inside a branch. Source: https://react.dev/reference/react/useEffect#caveats
- **Effects are for external systems**: "If you're not trying to synchronize with some external system, you probably don't need an Effect." Why: Effects exist to sync with code "not controlled by React" (timers, subscriptions, third-party widgets). Smell: `useEffect` that only calls a setter from props/state. Source: https://react.dev/reference/react/useEffect#caveats
- **Cleanup mirrors setup**: "implement the cleanup function" so it "stops or undoes whatever the setup is doing"; "the user shouldn't be able to distinguish between the setup being called once... and a setup → cleanup → setup sequence". Why: Strict Mode runs "one extra development-only setup+cleanup cycle". Smell: `connection.connect()` with no returned `disconnect`. Source: https://react.dev/reference/react/useEffect#my-effect-runs-twice-when-the-component-mounts
- **No cleanup without setup**: "Avoid: Cleanup logic without corresponding setup logic"; "Your cleanup logic should be 'symmetrical' to the setup logic". Why: cleanup runs "before every re-render with changed dependencies", not just on unmount. Smell: `useEffect(() => () => doSomething(), [])`. Source: https://react.dev/reference/react/useEffect#my-cleanup-logic-runs-even-though-my-component-didnt-unmount
- **Never suppress the deps linter**: "Avoid suppressing the linter like this: `// eslint-ignore-next-line react-hooks/exhaustive-deps`"; "Instead, prove they're unnecessary." Why: "When dependencies don't match the code, there is a high risk of introducing bugs." Smell: `eslint-disable-next-line react-hooks/exhaustive-deps` above a `useEffect`. Source: https://react.dev/reference/react/useEffect#specifying-reactive-dependencies
- **Deps are not a choice**: "you can't 'choose' the dependencies of your Effect. Every reactive value used by your Effect's code must be declared as a dependency." Why: "Reactive values include props and all variables and functions declared directly inside of your component." Smell: an Effect reading `roomId` with `[]` deps. Source: https://react.dev/reference/react/useEffect#specifying-reactive-dependencies
- **No render-created objects as deps**: "Avoid using an object created during rendering as a dependency. Instead, create the object inside the Effect." Why: the object "is different every time", so the Effect re-runs on every render. Smell: `const options = { serverUrl, roomId }` in the body and `[options]` deps. Source: https://react.dev/reference/react/useEffect#removing-unnecessary-object-dependencies
- **No render-created functions as deps**: "Avoid using a function created during rendering as a dependency. Instead, declare it inside the Effect." Why: same identity problem as objects. Smell: `function createOptions()` in the body listed in deps. Source: https://react.dev/reference/react/useEffect#removing-unnecessary-function-dependencies
- **Always pass the dependency array**: Check "that you haven't forgotten to specify the dependency array"; without it the Effect "re-runs after every commit!" Why: missing deps means "run after every render". Smell: `useEffect(() => {...})` with one argument. Source: https://react.dev/reference/react/useEffect#my-effect-runs-after-every-re-render
- **Memoize deps only as last resort**: "As a last resort (if these methods didn't help), wrap its creation with `useMemo` or `useCallback`." Why: removing the dependency (updater function, move inside Effect, Effect Event) is simpler. Smell: `useMemo` added solely to stabilize an Effect dep before trying to move the value inside. Source: https://react.dev/reference/react/useEffect#my-effect-runs-after-every-re-render
- **Question Effects that set state in a loop**: "ask yourself whether your Effect is connecting to some external system... If there is no external system, consider whether removing the Effect altogether would simplify your logic"; for data "not used by rendering, a ref... might be more appropriate". Why: an infinite cycle means the Effect "is updating some state" that changes its own deps. Smell: `useEffect(() => setItems([...items, x]), [items])`. Source: https://react.dev/reference/react/useEffect#my-effect-keeps-re-running-in-an-infinite-cycle
- **useLayoutEffect only for paint-blocking visuals**: "replace `useEffect` with `useLayoutEffect`" only if the Effect "must block the browser from painting the screen"; "this shouldn't be needed for the vast majority of Effects." Why: layout effects block paint. Smell: `useLayoutEffect` for data fetching or subscriptions. Source: https://react.dev/reference/react/useEffect#my-effect-does-something-visual-and-i-see-a-flicker-before-it-runs
- **Sparingly branch on client vs server**: "Use this pattern sparingly"; "In many cases, you can avoid the need for this by conditionally showing different things with CSS." Why: slow-connection users see the initial content for seconds, so "you don't want to make jarring changes". Smell: `const [isClient, setIsClient] = useState(false)` + mount Effect just to swap layout. Source: https://react.dev/reference/react/useEffect#displaying-different-content-on-the-server-and-the-client
- **One process per Effect**: "write every Effect as an independent process and think about a single setup/cleanup cycle at a time." Why: React may run setup/cleanup "multiple times" as deps change. Smell: a single Effect that subscribes, fetches, and logs analytics together. Source: https://react.dev/reference/react/useEffect#connecting-to-an-external-system

## useState

- **Top level only**: "you can only call it at the top level of your component or your own Hooks. You can't call it inside loops or conditions. If you need that, extract a new component and move the state into it." Why: hook order must be stable. Smell: `useState` inside an `if`. Source: https://react.dev/reference/react/useState#caveats
- **Pure initializer and updater**: "If your initializer function is pure (as it should be)" and "If your updater function is pure (as it should be)" the Strict Mode double call is harmless. Why: "React will call your initializer function twice" and "call your updater function twice" in development to surface impurities. Smell: `setTodos(prev => { prev.push(x) })`. Source: https://react.dev/reference/react/useState#my-initializer-or-updater-function-runs-twice
- **Setters do not update the running code**: "The `set` function only updates the state variable for the next render. If you read the state variable after calling the `set` function, you will still get the old value." Why: "state behaves like a snapshot". Smell: `setName('Robin'); console.log(name)` expecting the new value. Source: https://react.dev/reference/react/useState#ive-updated-the-state-but-logging-gives-me-the-old-value
- **Replace, never mutate**: "state is considered read-only, so you should replace it rather than mutate your existing objects"; "Don't mutate an object in state like this: `form.firstName = 'Taylor'`." Why: React "will ignore your update if the next state is equal to the previous state, as determined by an `Object.is` comparison". Smell: `obj.x = 10; setObj(obj)`. Source: https://react.dev/reference/react/useState#updating-objects-and-arrays-in-state
- **Updater for multiple updates in one event**: "if you do multiple updates within the same event, updaters can be helpful"; using `setAge(a => a + 1)` always is "reasonable" but "not always necessary". Why: several `setAge(age + 1)` calls in one handler all read the same snapshot. Smell: three `setCount(count + 1)` calls in one handler expecting +3. Source: https://react.dev/reference/react/useState#updating-state-based-on-the-previous-state
- **Consider a reducer for cross-state derivations**: "If it's calculated from the previous state of some other state variable, you might want to combine them into one object and use a reducer." Why: updaters only see their own state. Smell: updater for state A that closes over stale state B. Source: https://react.dev/reference/react/useState#is-using-an-updater-always-preferred
- **Pass initializer, don't call it**: To avoid recreating expensive initial state, pass "an initializer function" (`useState(createInitialTodos)`), not `useState(createInitialTodos())`. Why: the call result "is only used during the initial render" but the call itself "will run on every render". Smell: `useState(computeExpensive())`. Source: https://react.dev/reference/react/useState#avoiding-recreating-the-initial-state
- **Reset with key, not effects**: "If you want to reset the entire component tree's state, pass a different `key` to your component." Why: a key change tells React to recreate the component "from scratch". Smell: `useEffect(() => { setValue(''); }, [userId])` to reset a form. Source: https://react.dev/reference/react/useState#resetting-state-with-a-key
- **Remove redundant state**: "If the value you need can be computed entirely from the current props or other state, remove that redundant state altogether." Why: derived state is a second source of truth. Smell: `useState` mirroring a prop with an Effect to sync. Source: https://react.dev/reference/react/useState#storing-information-from-previous-renders
- **Prefer event handlers over render-time setState**: "If you can, update all the relevant state in the event handlers"; the render-phase set pattern "is usually best avoided. However, it's better than updating state in an effect." Why: a render-time set must "be inside a condition" or "your component would re-render in a loop until it crashes". Smell: unconditional `setX()` in the body, or `useEffect(() => setPrev(count), [count])`. Source: https://react.dev/reference/react/useState#storing-information-from-previous-renders
- **Pass handlers, don't call them**: "Wrong: calls the handler during render `onClick={handleClick()}`"; "Correct: passes down the event handler `onClick={handleClick}`". Why: calling during render sets state during render and triggers "Too many re-renders". Smell: `onClick={handleClick()}`. Source: https://react.dev/reference/react/useState#im-getting-an-error-too-many-re-renders
- **Wrap functions stored in state**: "To actually store a function, you have to put `() =>` before them in both cases." Why: React treats a bare function as an initializer/updater and "tries to call them and store the result". Smell: `useState(someFunction)` or `setFn(someOtherFunction)`. Source: https://react.dev/reference/react/useState#im-trying-to-set-state-to-a-function-but-it-gets-called-instead
- **Setter identity is stable**: "The `set` function has a stable identity, so you will often see it omitted from Effect dependencies... If the linter lets you omit a dependency without errors, it is safe to do." Why: avoids needless deps and needless `useCallback`. Smell: `useCallback(..., [setValue])` added only to satisfy a perceived dep. Source: https://react.dev/reference/react/useState#setstate-caveats

## useRef

- **No ref.current reads or writes during render**: "Do not write or read `ref.current` during rendering, except for initialization. This makes your component's behavior unpredictable." Why: the component body should behave "like a pure function". Smell: `myRef.current = 123` in the body or `<h1>{myRef.current}</h1>`. Source: https://react.dev/reference/react/useRef#caveats
- **Access refs in handlers and effects**: "You can read or write refs from event handlers or effects instead." Why: those run outside the pure render phase. Smell: ref logic in the component body instead of `useEffect`/`onClick`. Source: https://react.dev/reference/react/useRef#referencing-a-value-with-a-ref
- **Rendered data belongs in state**: "refs are not appropriate for storing information you want to display on the screen. Use state for that instead"; "Information that's used for rendering should be state instead." Why: "Changing a ref does not trigger a re-render." Smell: `{countRef.current}` in JSX expecting it to update on click. Source: https://react.dev/reference/react/useRef#referencing-a-value-with-a-ref
- **Non-rendered data belongs in a ref**: "Since the interval ID is not used for rendering, it's appropriate to keep it in a ref"; refs are "perfect for storing information that doesn't affect the visual output". Why: avoids re-renders for bookkeeping values like timeout ids. Smell: `const [intervalId, setIntervalId] = useState(null)`. Source: https://react.dev/reference/react/useRef#a-stopwatch
- **Don't mutate rendered objects through a ref**: "if it holds an object that is used for rendering (for example, a piece of your state), then you shouldn't mutate that object." Why: mutating rendered data bypasses React's change detection. Smell: `stateRef.current.items.push(x)` where `items` is rendered. Source: https://react.dev/reference/react/useRef#caveats
- **Guard expensive ref initialization**: Initialize expensive ref contents with `if (playerRef.current === null) { playerRef.current = new VideoPlayer(); }` instead of `useRef(new VideoPlayer())`. Why: the initial value "is only used during the initial render" but the argument expression runs on every render. Smell: `useRef(new Expensive())`. Source: https://react.dev/reference/react/useRef#avoiding-recreating-the-ref-contents
- **Prefer built-in React mechanisms over DOM refs**: Use refs "as an escape hatch" for "focusing a node, scrolling to it, or measuring its dimensions"; if you use them for something expressible with props/state, "you should rethink your approach". Why: React should own the DOM it renders. Smell: `ref.current.textContent = value` instead of rendering `{value}`. Source: https://react.dev/reference/react/useRef#manipulating-the-dom-with-a-ref
- **Accept ref as a prop to expose a DOM node**: "By default, your own components don't expose refs to the DOM nodes inside them"; "add `ref` to the list of props your component accepts and pass `ref` as a prop to the relevant child built-in component". Why: otherwise the parent gets `TypeError: Cannot read properties of null`. Smell: `<MyInput ref={inputRef} />` where `MyInput` ignores `ref`. Source: https://react.dev/reference/react/useRef#i-cant-get-a-ref-to-a-custom-component

## React v19

- **ref as a plain prop**: Accept `ref` in function component props (`function MyInput({placeholder, ref})`); "New function components will no longer need `forwardRef`", and "In future versions we will deprecate and remove `forwardRef`." Why: `ref` is passed as a regular prop in React 19. Smell: `forwardRef((props, ref) => ...)` in new code. Source: https://react.dev/blog/2024/12/05/react-19#ref-as-a-prop
- **Render Context directly as provider**: "you can render `<Context>` as a provider instead of `<Context.Provider>`"; "In future versions we will deprecate `<Context.Provider>`." Why: the shorter form is the forward-compatible one. Smell: `<ThemeContext.Provider value={...}>` in new code. Source: https://react.dev/blog/2024/12/05/react-19#context-as-a-provider
- **Use Actions for mutations**: "In React 19, we're adding support for using async functions in transitions to handle pending states, errors, forms, and optimistic updates automatically"; use `startTransition(async () => ...)` rather than manual `isPending` state. Why: Actions manage "Pending state", "Optimistic updates", "Error handling", and "Forms" for you. Smell: `setIsPending(true); await ...; setIsPending(false)` in a submit handler. Source: https://react.dev/blog/2024/12/05/react-19#actions
- **useActionState for common Action cases**: `useActionState` "accepts a function (the 'Action'), and returns a wrapped Action to call", exposing "the last result of the Action as `data`, and the pending state of the Action as `pending`". Why: replaces hand-rolled error/pending/result state; "we've renamed it and deprecated `useFormState`." Smell: `ReactDOM.useFormState` or three `useState`s for error/pending/result around one submit. Source: https://react.dev/blog/2024/12/05/react-19#new-hook-useactionstate
- **useOptimistic for optimistic UI**: Use `useOptimistic(currentName)` and call `setOptimisticName(newName)` inside the Action; "When the update finishes or errors, React will automatically switch back to the `currentName` value." Why: removes manual rollback logic. Smell: manual `setState(optimistic)` + `catch { setState(previous) }`. Source: https://react.dev/blog/2024/12/05/react-19#new-hook-optimistic-updates
- **Pass functions to form action**: `<form action={actionFunction}>` (also `formAction` on `<input>`/`<button>`); "When a `<form>` Action succeeds, React will automatically reset the form for uncontrolled components"; call `requestFormReset` to reset manually. Why: forms "use Actions by default and reset the form automatically after submission". Smell: `onSubmit={(e) => { e.preventDefault(); ... }}` for a simple mutation form. Source: https://react.dev/blog/2024/12/05/react-19#form-actions
- **useFormStatus in design-system buttons**: "`useFormStatus` reads the status of the parent `<form>` as if the form was a Context provider" (`const {pending} = useFormStatus()`). Why: avoids "drilling props down to the component". Smell: threading an `isPending` prop through generic button components. Source: https://react.dev/blog/2024/12/05/react-19#new-hook-useformstatus
- **use for promises and conditional context**: "`use` can be called conditionally" ("such as after early returns") but "can only be called in render, similar to hooks". Why: `useContext` cannot follow an early return; `use` can. Smell: hoisting `useContext` above an early return just to satisfy hook rules when `use(ThemeContext)` fits. Source: https://react.dev/blog/2024/12/05/react-19#new-feature-use
- **No render-created promises in use**: "`use` does not support promises created in render"; pass "a promise from a Suspense powered library or framework that supports caching for promises". Why: React warns "A component was suspended by an uncached promise." Smell: `use(fetch(url))` or `use(fetchData())` inside the component body. Source: https://react.dev/blog/2024/12/05/react-19#new-feature-use
- **Ref callbacks may return cleanup**: "We now support returning a cleanup function from `ref` callbacks"; "When the component unmounts, React will call the cleanup function". Why: "If your `ref` returns a cleanup function, React will now skip" calling it with `null`, and "we will deprecate calling refs with `null` when unmounting". Smell: `ref={(node) => { if (node === null) teardown(); else setup(node); }}`. Source: https://react.dev/blog/2024/12/05/react-19#cleanup-functions-for-refs
- **No implicit returns in ref callbacks**: "returning anything else from a `ref` callback will now be rejected by TypeScript. The fix is usually to stop using implicit returns": `ref={current => {instance = current}}`. Why: an implicit return is indistinguishable from a cleanup function. Smell: `ref={current => (instance = current)}`. Source: https://react.dev/blog/2024/12/05/react-19#cleanup-functions-for-refs
- **useDeferredValue initialValue**: Pass an `initialValue` (`useDeferredValue(deferredValue, '')`) when the first render should show a placeholder value. Why: React "will return it as `value` for the initial render... and schedules a re-render in the background with the `deferredValue`". Smell: extra `useState`/Effect to seed a deferred value on mount. Source: https://react.dev/blog/2024/12/05/react-19#use-deferred-value-initial-value
- **Render metadata tags in place**: Render `<title>`, `<meta>`, `<link>` inside components; React "automatically hoist them to the `<head>` section of document". Why: no need for effects or `react-helmet` for simple cases. Smell: `useEffect(() => { document.title = post.title }, [post.title])`. Source: https://react.dev/blog/2024/12/05/react-19#support-for-metadata-tags
- **Root-level error hooks**: Use `onCaughtError`, `onUncaughtError`, and `onRecoverableError` on `createRoot`/`hydrateRoot` for error reporting. Why: React 19 logs "a single error with all the error information included" and routes caught vs uncaught errors separately. Smell: `window.onerror` or duplicated `console.error` wrappers around Error Boundaries. Source: https://react.dev/blog/2024/12/05/react-19#error-handling
- **Follow the upgrade guide for removed APIs**: For "a full list of breaking and notable changes" (removed `propTypes`, function-component `defaultProps`, string refs, legacy context, `findDOMNode`, `ReactDOM.render`, etc.) "See the React 19 Upgrade Guide". Why: the blog defers the removed-API list to https://react.dev/blog/2024/04/25/react-19-upgrade-guide. Smell: `Component.propTypes = ...`, `Component.defaultProps = ...`, `ref="input"`, `ReactDOM.render(...)`. Source: https://react.dev/blog/2024/12/05/react-19#how-to-upgrade

## React Compiler Introduction

- **Follow the Rules of React**: Rolling out the compiler "will depend on the health of your codebase and how well you've followed the Rules of React"; the compiler "understands the Rules of React". Why: the compiler relies on components and hooks being pure and idempotent. Smell: mutating props/state, side effects during render, hooks called conditionally. Source: https://react.dev/learn/react-compiler/introduction#is-it-safe-to-use
- **Rely on the compiler for new code**: "For new code, we recommend relying on the compiler for memoization and using `useMemo`/`useCallback` where needed to achieve precise control." Why: "In most cases, this memoization will be as precise, or moreso, than what you may have written." Smell: new components wrapped in `memo` with `useMemo`/`useCallback` on every value. Source: https://react.dev/learn/react-compiler/introduction#what-should-i-do-about-usememo-usecallback-and-reactmemo
- **Keep manual memo as escape hatch for effect deps**: Use `useMemo`/`useCallback` "as an escape hatch to provide control over which values are memoized", commonly "if a memoized value is used as an effect dependency". Why: "to ensure that an effect does not fire repeatedly even when its dependencies do not meaningfully change". Smell: removing a `useMemo` that stabilizes an Effect dependency. Source: https://react.dev/learn/react-compiler/introduction#what-should-i-do-about-usememo-usecallback-and-reactmemo
- **Don't strip existing memoization blindly**: "For existing code, we recommend either leaving existing memoization in place (removing it can change compilation output) or carefully testing before removing the memoization." Why: removal changes what the compiler emits. Smell: a mass "remove all useMemo/useCallback" refactor PR. Source: https://react.dev/learn/react-compiler/introduction#what-should-i-do-about-usememo-usecallback-and-reactmemo
- **Only components and hooks get memoized**: "React Compiler only memoizes React components and hooks, not every function" and "React Compiler's memoization is not shared across multiple components or hooks." Why: an expensive helper called from many components still runs in each. Smell: `expensivelyProcess(items)` called in many components with the expectation it is cached globally. Source: https://react.dev/learn/react-compiler/introduction#expensive-calculations-also-get-memoized
- **Profile before hand-caching**: "We recommend profiling first to see if it really is that expensive before making code more complicated." Why: a truly expensive shared function may need "its own memoization outside of React", but only if measured. Smell: custom caches added around helpers with no profiling evidence. Source: https://react.dev/learn/react-compiler/introduction#expensive-calculations-also-get-memoized
- **Inline arrows break manual memo, not compiler memo**: The manual example "has a subtle bug that breaks memoization": `onClick={() => handleClick(item)}` "creates a new function every time" so "`Item` will always receive a new `onClick` prop"; "React Compiler is able to optimize this correctly with or without the arrow function." Why: hand-written `memo` + `useCallback` is easy to defeat. Smell: `useCallback`ed handler wrapped in an inline arrow passed to a `memo` child. Source: https://react.dev/learn/react-compiler/introduction#before-react-compiler
