## You Might Not Need an Effect

- **No Effects for data transformation**: "You don't need Effects to transform data for rendering" - transform all the data at the top level of your component instead. Why: an Effect that sets state after render restarts the whole render-commit-effect process from scratch, causing an extra render pass. Smell: `useEffect` that computes a derived value (filter/map/concat) from props or state and stores it via `setState`. Source: https://react.dev/learn/you-might-not-need-an-effect#how-to-remove-unnecessary-effects
- **No Effects for user events**: "You don't need Effects to handle user events" - handle user interactions in the corresponding event handlers. Why: by the time an Effect runs, you don't know what the user did (for example, which button was clicked). Smell: `useEffect` watching a boolean/state flag like `submitted` or `isClicked` to fire a POST request or notification. Source: https://react.dev/learn/you-might-not-need-an-effect#how-to-remove-unnecessary-effects
- **Calculate derived values during render**: "When something can be calculated from the existing props or state, don't put it in state. Instead, calculate it during rendering." Why: faster (no cascading updates), simpler (less code), and less error-prone (no state variables getting out of sync). Smell: `const [fullName, setFullName] = useState(); useEffect(() => setFullName(firstName + ' ' + lastName), [firstName, lastName])`. Source: https://react.dev/learn/you-might-not-need-an-effect#updating-state-based-on-props-or-state
- **useMemo instead of Effect for expensive calculations**: "To cache expensive calculations, add `useMemo` instead of `useEffect`." Why: `useMemo` skips re-running the pure calculation on updates without an extra state variable and render pass. Smell: `useState` + `useEffect` pair that stores the result of `getFilteredTodos(todos, filter)` in state. Source: https://react.dev/learn/you-might-not-need-an-effect#caching-expensive-calculations
- **Only memoize pure calculations**: "The function you wrap in `useMemo` runs during rendering, so this only works for pure calculations." Why: rendering must stay pure; side effects inside `useMemo` break React's rendering model. Smell: `useMemo` body that fetches, logs, mutates a ref, or touches the DOM. Source: https://react.dev/learn/you-might-not-need-an-effect#caching-expensive-calculations
- **Measure before memoizing**: "unless you're creating or looping over thousands of objects, it's probably not expensive" - measure with `console.time` in a production build before adding `useMemo`. Why: `useMemo` won't make the first render faster; it only helps skip unnecessary work on updates. Smell: `useMemo` wrapping a trivial expression like `a + b` or a small array `.find`. Source: https://react.dev/learn/you-might-not-need-an-effect#how-to-tell-if-a-calculation-is-expensive
- **Reset state with key, not Effect**: "To reset the state of an entire component tree, pass a different `key` to it." Why: resetting in an Effect renders with the stale value first, then again, and must be repeated in every component that holds state. Smell: `useEffect(() => { setComment(''); }, [userId])`. Source: https://react.dev/learn/you-might-not-need-an-effect#resetting-all-state-when-a-prop-changes
- **Adjust partial state during render, not in Effect**: "To reset a particular bit of state in response to a prop change, set it during rendering" using a `prevItems` comparison guarded by a condition. Why: React re-renders immediately after the render exits, so children skip rendering the stale value; an Effect causes an extra committed render. Smell: `useEffect(() => { setSelection(null); }, [items])`. Source: https://react.dev/learn/you-might-not-need-an-effect#adjusting-some-state-when-a-prop-changes
- **Prefer computing over adjusting state**: "Although this pattern is more efficient than an Effect, most components shouldn't need it either" - "Always check whether you can reset all state with a key or calculate everything during rendering instead" (store `selectedId`, derive `selection`). Why: adjusting state based on props or other state makes data flow more difficult to understand and debug. Smell: `if (items !== prevItems) { setPrevItems(items); setSelection(null); }` where storing an ID and deriving via `items.find` would work. Source: https://react.dev/learn/you-might-not-need-an-effect#adjusting-some-state-when-a-prop-changes
- **Only render-triggered side effects belong in Effects**: "Use Effects only for code that should run *because* the component was displayed to the user"; share event logic via a plain function called from each handler. Why: event-specific logic in an Effect re-fires on reload/remount (e.g. notification shows again because `product.isInCart` is already true). Smell: `useEffect(() => { if (product.isInCart) showNotification(...) }, [product])`. Source: https://react.dev/learn/you-might-not-need-an-effect#sharing-logic-between-event-handlers
- **Interaction-caused POSTs go in handlers, display-caused in Effects**: "If this logic is caused by a particular interaction, keep it in the event handler. If it's caused by the user *seeing* the component on the screen, keep it in the Effect." Why: a register/submit request should happen only on that particular interaction, whereas analytics on mount is legitimately caused by display. Smell: `useEffect(() => { if (jsonToSubmit !== null) post('/api/register', jsonToSubmit) }, [jsonToSubmit])`. Source: https://react.dev/learn/you-might-not-need-an-effect#sending-a-post-request
- **No chains of Effects adjusting state**: "Avoid: Chains of Effects that adjust the state solely to trigger each other" - "calculate what you can during rendering, and adjust the state in the event handler". Why: the tree re-renders between each `set` call and the chain becomes rigid and fragile when requirements change (e.g. history replay re-triggers the chain). Smell: several `useEffect`s each with `if (x) setY(...)` where `y` is a dependency of the next Effect. Source: https://react.dev/learn/you-might-not-need-an-effect#chains-of-computations
- **Effect chains are OK only for network synchronization**: "a chain of Effects is appropriate because you are synchronizing with network" (e.g. dependent dropdown options fetched from the server). Why: the next state cannot be calculated directly in the event handler when it depends on async external data. Smell: not a smell - the acceptable exception when each link fetches data rather than adjusting local state. Source: https://react.dev/learn/you-might-not-need-an-effect#chains-of-computations
- **Use snapshot-safe next values in handlers**: "If you need to use the next value for calculations, define it manually like `const nextRound = round + 1`." Why: inside event handlers state behaves like a snapshot; `round` still reflects the click-time value after `setRound(round + 1)`. Smell: handler reads `round` after `setRound(round + 1)` expecting the incremented value. Source: https://react.dev/learn/you-might-not-need-an-effect#chains-of-computations
- **App-init logic runs once per app load, outside mount Effects**: "Avoid: Effects with logic that should only ever run once" - use a module-level `didInit` flag or run at module initialization in root modules like `App.js`. Why: components must be resilient to remounting (dev double-invocation can e.g. invalidate an auth token). Smell: `useEffect(() => { loadDataFromLocalStorage(); checkAuthToken(); }, [])` in `App`. Source: https://react.dev/learn/you-might-not-need-an-effect#initializing-the-application
- **Don't overuse module-level init**: "don't overuse this pattern. Keep app-wide initialization logic to root component modules like `App.js` or in your application's entry point." Why: top-level code runs once when a component is imported even if never rendered, causing slowdown or surprising behavior. Smell: side-effecting statements at module scope in a leaf component file. Source: https://react.dev/learn/you-might-not-need-an-effect#initializing-the-application
- **Notify parent in the event handler, not an Effect**: "Perform all updates during the event that caused them" - call `onChange(nextIsOn)` alongside `setIsOn(nextIsOn)` in the handler. Why: the Effect-based `onChange` runs too late and starts another render pass; React batches updates in one event into a single render. Smell: `useEffect(() => { onChange(isOn); }, [isOn, onChange])`. Source: https://react.dev/learn/you-might-not-need-an-effect#notifying-parent-components-about-state-changes
- **Lift state up instead of syncing state**: "Whenever you try to keep two different state variables synchronized, try lifting state up instead!" Why: a fully controlled component means less state overall to worry about. Smell: child `useState` mirrored to parent via `onChange` plus parent prop mirrored back into child state. Source: https://react.dev/learn/you-might-not-need-an-effect#notifying-parent-components-about-state-changes
- **Don't pass data up to the parent in an Effect**: "Avoid: Passing data to the parent in an Effect" - let the parent fetch the data and pass it down. Why: data flows from parents to children; child-to-parent updates in Effects make data flow very difficult to trace. Smell: `useEffect(() => { if (data) onFetched(data); }, [onFetched, data])` in a child. Source: https://react.dev/learn/you-might-not-need-an-effect#passing-data-to-the-parent
- **Use useSyncExternalStore for external stores**: "React has a purpose-built Hook for subscribing to an external store that is preferred instead" of an Effect with `addEventListener` + `setState`. Why: less error-prone than manually syncing mutable data to React state with an Effect. Smell: `useEffect` that adds `online`/`offline` (or similar) listeners and calls `setIsOnline`. Source: https://react.dev/learn/you-might-not-need-an-effect#subscribing-to-an-external-store
- **Fetch in Effects with cleanup to avoid races**: "To fix the race condition, you need to add a cleanup function to ignore stale responses" (an `ignore` flag set in cleanup). Why: responses may arrive out of order, so the last `setResults` call could show results for a stale query. Smell: `useEffect(() => { fetchResults(query, page).then(setResults); }, [query, page])` with no cleanup return. Source: https://react.dev/learn/you-might-not-need-an-effect#fetching-data
- **Prefer framework/custom-hook data fetching**: "modern frameworks provide more efficient built-in data fetching mechanisms than fetching data in Effects"; otherwise "extract your fetching logic into a custom Hook" like `useData(url)`. Why: moving fetching into a hook makes it easier to adopt an efficient strategy later and handles caching, SSR and waterfalls. Smell: raw `fetch` inside `useEffect` in a component body rather than a query hook. Source: https://react.dev/learn/you-might-not-need-an-effect#fetching-data
- **Minimize raw useEffect calls**: "whenever you have to resort to writing Effects, keep an eye out for when you can extract a piece of functionality into a custom Hook with a more declarative and purpose-built API". Why: "The fewer raw `useEffect` calls you have in your components, the easier you will find to maintain your application." Smell: multiple bespoke `useEffect`s in a component where an existing hook (`useData`, `useOnlineStatus`) would cover the case. Source: https://react.dev/learn/you-might-not-need-an-effect#fetching-data

## Synchronizing with Effects

- **Rendering code must be pure**: "Rendering code ... must be pure" and "only calculate results without side effects". Why: React may call the component function many times; side effects there run unpredictably. Smell: `fetch`, `addEventListener`, DOM mutation, or `ref.current.play()` directly in the component body. Source: https://react.dev/learn/synchronizing-with-effects#what-are-effects-and-how-are-they-different-from-events
- **Effects are for side effects caused by rendering, not by events**: "Effects let you specify side effects that are caused by rendering itself, rather than by a particular event." Why: Effects run at the end of a commit after the screen updates, making them the right time to synchronize with external systems. Smell: user-action logic (send message, buy) placed in `useEffect`. Source: https://react.dev/learn/synchronizing-with-effects#what-are-effects-and-how-are-they-different-from-events
- **Don't rush to add Effects**: "Don't rush to add Effects to your components" - "If your Effect only adjusts some state based on other state, you might not need an Effect." Why: Effects are for stepping out of React to external systems (browser APIs, widgets, network). Smell: `useEffect` whose body is only `setX(...)` derived from props/state. Source: https://react.dev/learn/synchronizing-with-effects#you-might-not-need-an-effect
- **Don't call imperative APIs during render**: "Don't call `play()` or `pause()` during rendering" - wrap the DOM/widget call in `useEffect`. Why: rendering must be pure, and the DOM node doesn't exist yet during the first render. Smell: `ref.current.play()` in the component body outside an Effect. Source: https://react.dev/learn/synchronizing-with-effects#step-1-declare-an-effect
- **No unconditional setState in an Effect without deps**: Setting state in an Effect that runs after every render "causes an infinite loop" - "Effects should synchronize with external systems, not adjust state based on other state." Why: setting state triggers rendering, which runs the Effect again. Smell: `useEffect(() => { setCount(count + 1); });` with no dependency array. Source: https://react.dev/learn/synchronizing-with-effects#step-1-declare-an-effect
- **Specify dependencies so Effects don't run every render**: "Specify an array of dependencies as the second argument to `useEffect`" so React skips the Effect when dependencies are unchanged. Why: synchronizing with external systems is not instant (reconnecting on every keystroke is slow) and some effects (fade-in) should run once. Smell: `useEffect(() => { connect(); })` with no dependency array. Source: https://react.dev/learn/synchronizing-with-effects#step-2-specify-the-effect-dependencies
- **Declare every value the Effect uses**: "You must declare all values from your component that the Effect uses" - "You can't 'choose' your dependencies. They are determined by the code inside the Effect." Why: React compares dependencies with `Object.is`; a missing one leaves the Effect stale. Smell: dependency array shorter than the set of props/state read in the Effect body, with a lint warning. Source: https://react.dev/learn/synchronizing-with-effects#step-2-specify-the-effect-dependencies
- **Refs and setState functions may be omitted from deps**: "the `ref` object has a stable identity" and "the `set` functions returned by `useState` also have stable identity" so they can be omitted. Why: React guarantees the same object from the same `useRef`/`useState` call on every render, so they never cause a re-run. Smell: not a smell - but a ref passed from a parent is not guaranteed stable and must be declared. Source: https://react.dev/learn/synchronizing-with-effects#step-2-specify-the-effect-dependencies
- **Return a cleanup that stops/undoes the Effect**: "Add cleanup if needed" - "return a cleanup function from your Effect" that disconnects, unsubscribes, or resets. Why: React calls cleanup before the Effect re-runs and on unmount, preventing leaked connections/listeners. Smell: `connection.connect()` or `addEventListener` in an Effect with no `return () => ...`. Source: https://react.dev/learn/synchronizing-with-effects#step-3-add-cleanup-if-needed
- **Don't use refs to guard against double-firing**: "Don't use refs to prevent Effects from firing" - "implement cleanup" instead. Why: a ref guard makes dev look right but leaves the connection open when the component unmounts and remounts. Smell: `if (!connectionRef.current) { connectionRef.current = createConnection(); ... }` inside `useEffect(..., [])`. Source: https://react.dev/learn/synchronizing-with-effects#step-3-add-cleanup-if-needed
- **Make Effects resilient to dev remounting via cleanup**: "React remounts components in development to find bugs. The correct approach is to implement cleanup so Effects work correctly after remounting." Why: Effects must work whether run once (production) or in a setup -> cleanup -> setup sequence (development). Smell: logic that breaks or duplicates when Strict Mode runs the Effect twice, "fixed" by disabling Strict Mode. Source: https://react.dev/learn/synchronizing-with-effects#how-to-handle-the-effect-firing-twice-in-development
- **Widget cleanup when calls are not idempotent**: For non-React widgets, no cleanup is needed "if calling the method multiple times with the same value has no side effects", but APIs like `showModal()` require a matching `close()` in cleanup. Why: calling `showModal` twice throws; cleanup keeps the widget consistent with remounts. Smell: `dialog.showModal()` in an Effect with no `return () => dialog.close()`. Source: https://react.dev/learn/synchronizing-with-effects#controlling-non-react-widgets
- **Unsubscribe in cleanup**: "If your Effect subscribes to something, the cleanup function should unsubscribe." Why: otherwise every remount adds another listener. Smell: `window.addEventListener('scroll', handleScroll)` without `removeEventListener` in the cleanup. Source: https://react.dev/learn/synchronizing-with-effects#subscribing-to-events
- **Reset animations in cleanup**: "If your Effect animates something in, the cleanup function should reset the animation to the initial values." Why: keeps the animation correct across remounts and re-synchronizations. Smell: `node.style.opacity = 1` in an Effect with no reset in the returned cleanup. Source: https://react.dev/learn/synchronizing-with-effects#triggering-animations
- **Fetch cleanup ignores stale results**: "If your Effect fetches something, the cleanup function should either abort the fetch or ignore its result" via an `ignore` flag. Why: you can't undo a completed request, but you must ensure a stale response doesn't overwrite newer state. Smell: `async` fetch in `useEffect` calling `setTodos(json)` without an `ignore` check or `AbortController`. Source: https://react.dev/learn/synchronizing-with-effects#fetching-data
- **Prefer a data-fetching library over raw Effects**: Effect-based fetching has downsides (no SSR data, network waterfalls, no cache, race-condition boilerplate); "use or build a client-side cache" such as TanStack Query, useSWR, or React Router 6.4+ or a framework mechanism. Why: these solve caching, dedup and waterfalls that raw Effects don't. Smell: hand-rolled `useEffect` + `fetch` + loading/error state where a query library exists in the project. Source: https://react.dev/learn/synchronizing-with-effects#fetching-data
- **Analytics on display may stay in an Effect**: "Log events on component appearance" with `logVisit(url)` in an Effect keyed on `url`; the dev double-fire is acceptable. Why: the reason to send the event is that the component was displayed, and dev-machine analytics shouldn't skew production metrics. Smell: not a smell - analytics on mount is a legitimate Effect. Source: https://react.dev/learn/synchronizing-with-effects#sending-analytics
- **App initialization is not an Effect**: "Not an Effect: Initializing the application" - run once-per-app logic at module scope (guarded by `typeof window !== 'undefined'`) outside components. Why: guarantees the logic runs once after the page loads regardless of remounts. Smell: `checkAuthToken()` / `loadDataFromLocalStorage()` in `useEffect(..., [])` of `App`. Source: https://react.dev/learn/synchronizing-with-effects#not-an-effect-initializing-the-application
- **Purchases and business-critical actions are not Effects**: "Not an Effect: Buying a product" - the `/api/buy` POST belongs in the click handler. Why: remounting would execute the purchase twice; "If remounting breaks the logic of your application, this usually uncovers existing bugs." Smell: `useEffect(() => { fetch('/api/buy', { method: 'POST' }); }, [])`. Source: https://react.dev/learn/synchronizing-with-effects#not-an-effect-buying-a-product
- **Reason about each render's own Effect**: "Each render has its own Effects" - React runs the previous render's cleanup, then the new render's Effect when dependencies differ. Why: an Effect captures the props/state of its render, so cleanup must undo that specific render's setup. Smell: cleanup that reads a mutable outer variable instead of the value captured in the same Effect closure. Source: https://react.dev/learn/synchronizing-with-effects#putting-it-all-together

## Removing Effect Dependencies

- **Dependencies should match the code**: "Dependencies should match the code" - every reactive value the Effect reads must appear in the dependency list. Why: this is what keeps the Effect synchronized to the latest props and state. Smell: Effect body reads `roomId` but dependency array is `[]`. Source: https://react.dev/learn/removing-effect-dependencies#dependencies-should-match-the-code
- **Prove a value is not a dependency before removing it**: "To remove a dependency, prove that it's not a dependency" - e.g. move it outside the component so it is no longer reactive. Why: you can't arbitrarily choose dependencies; only non-reactive values may be left out. Smell: a prop or state removed from the deps array while still read inside the Effect. Source: https://react.dev/learn/removing-effect-dependencies#to-remove-a-dependency-prove-that-its-not-a-dependency
- **Change the code, then adjust dependencies**: "To change the dependencies, change the code" - edit the Effect or how reactive values are declared, then let the deps follow. Why: "The dependency list describes your code" rather than being something you pick. Smell: editing only the deps array to silence the linter without touching the Effect body. Source: https://react.dev/learn/removing-effect-dependencies#to-change-the-dependencies-change-the-code
- **Never suppress the dependency linter**: "Treat the dependency lint error as a compilation error" - do not use `eslint-ignore-next-line react-hooks/exhaustive-deps`. Why: suppressing "lies" to React about what the Effect depends on and leads to unintuitive stale-value bugs. Smell: `// eslint-disable-next-line react-hooks/exhaustive-deps` above a `useEffect` deps array. Source: https://react.dev/learn/removing-effect-dependencies#to-change-the-dependencies-change-the-code
- **Move event-specific code to an event handler**: "Should this code move to an event handler?" - if the Effect exists only because a state flag like `submitted` flipped after a user action, put the logic in `handleSubmit`. Why: an Effect keyed on such a flag re-runs on unrelated changes (e.g. `theme`) and repeats the action. Smell: `useEffect(() => { if (submitted) { post(...); showNotification(...) } }, [submitted, theme])`. Source: https://react.dev/learn/removing-effect-dependencies#should-this-code-move-to-an-event-handler
- **Split unrelated synchronization into separate Effects**: "Is your Effect doing several unrelated things?" - "Each Effect in your code should represent a separate and independent synchronization process." Why: with one combined Effect, changing one dependency (e.g. `city`) needlessly re-runs the other work (refetching countries). Smell: one `useEffect` fetching cities and areas with deps `[country, city]`. Source: https://react.dev/learn/removing-effect-dependencies#is-your-effect-doing-several-unrelated-things
- **Use updater functions instead of reading state for the next state**: "Are you reading some state to calculate the next state?" - use `setMessages(msgs => [...msgs, receivedMessage])`. Why: reading `messages` inside the Effect would force it as a dependency and re-connect on every message. Smell: `setMessages([...messages, newMessage])` inside an Effect with `messages` in deps. Source: https://react.dev/learn/removing-effect-dependencies#are-you-reading-some-state-to-calculate-the-next-state
- **Use an Effect Event to read a value without reacting to it**: "Do you want to read a value without 'reacting' to its changes?" - wrap the non-reactive part in `useEffectEvent`. Why: it lets the Effect stay reactive to `roomId` while reading the latest `isMuted` without re-connecting. Smell: `isMuted` in an Effect's deps only because it's read inside a message callback. Source: https://react.dev/learn/removing-effect-dependencies#do-you-want-to-read-a-value-without-reacting-to-its-changes
- **Wrap event handler props in Effect Events**: "Wrapping an event handler from the props" - wrap `onReceiveMessage` in `useEffectEvent` so it need not be a dependency. Why: a parent passing a new inline function on every render would otherwise re-connect the chat every time. Smell: `onReceiveMessage` prop listed in Effect deps, causing re-synchronization on parent re-render. Source: https://react.dev/learn/removing-effect-dependencies#wrapping-an-event-handler-from-the-props
- **Separate reactive and non-reactive code**: "Separating reactive and non-reactive code" - keep the reactive part (e.g. log on `roomId` change) in the Effect and pass the reactive value into an Effect Event that reads non-reactive values like `notificationCount`. Why: only the values you want the Effect to react to remain as dependencies. Smell: `logVisit(roomId, notificationCount)` directly inside the Effect with both in deps. Source: https://react.dev/learn/removing-effect-dependencies#separating-reactive-and-non-reactive-code
- **Avoid object and function dependencies**: "Does some reactive value change unintentionally?" - "Avoid relying on objects and functions as dependencies." Why: each render creates a new object/function that `Object.is` treats as different, so the Effect re-runs on every render. Smell: `const options = { serverUrl, roomId }` in the component body with `[options]` in deps. Source: https://react.dev/learn/removing-effect-dependencies#does-some-reactive-value-change-unintentionally
- **Move static objects and functions outside the component**: "Move static objects and functions outside your component" so they are no longer reactive. Why: values that don't depend on props/state never change and don't need to be dependencies. Smell: a constant config object or helper function declared inside the component and listed in Effect deps. Source: https://react.dev/learn/removing-effect-dependencies#move-static-objects-and-functions-outside-your-component
- **Move dynamic objects and functions inside the Effect**: "Move dynamic objects and functions inside your Effect" so only primitives like `roomId` remain dependencies. Why: values created inside the Effect are not reactive values of the component. Smell: `createOptions()` or an options object built in the component body from props and passed into the Effect. Source: https://react.dev/learn/removing-effect-dependencies#move-dynamic-objects-and-functions-inside-your-effect
- **Read primitive values from objects**: "Read primitive values from objects" - destructure `const { roomId, serverUrl } = options` outside the Effect and depend on the primitives. Why: a parent may re-create the object on every render, but primitive contents rarely change. Smell: `[options]` in deps where `options` is a prop object. Source: https://react.dev/learn/removing-effect-dependencies#read-primitive-values-from-objects
- **Calculate primitive values from functions**: "Calculate primitive values from functions" - call the passed function outside the Effect (`const { roomId, serverUrl } = getOptions()`) and depend on the results. Why: works only for pure functions safe to call during render; avoids function identity as a dependency. Smell: `[getOptions]` in deps where `getOptions` is a prop callback. Source: https://react.dev/learn/removing-effect-dependencies#calculate-primitive-values-from-functions

## Separating Events from Effects

- **Ask why the code needs to run**: "Every time you need to answer this question, consider why the code needs to run" - interaction-caused code goes in a handler, synchronization-caused code in an Effect. Why: the reason for running determines whether logic should be reactive. Smell: logic placed in `useEffect` "because it needs to happen after X" without a synchronization target. Source: https://react.dev/learn/separating-events-from-effects#choosing-between-event-handlers-and-effects
- **Event handlers for specific interactions**: "sending a message should be an event handler" - user-triggered actions run only when the user performs that interaction. Why: "The user will get rather upset if you send their message at any other time or for any other reason." Smell: `sendMessage(message)` inside a `useEffect`. Source: https://react.dev/learn/separating-events-from-effects#event-handlers-run-in-response-to-specific-interactions
- **Effects for staying synchronized**: "Effects run whenever synchronization is needed" - connecting to the selected chat room belongs in an Effect regardless of how the user got there. Why: the component must remain synchronized with the currently selected room even with no interactions. Smell: `connection.connect()` placed in a click handler and never re-run when `roomId` changes. Source: https://react.dev/learn/separating-events-from-effects#effects-run-whenever-synchronization-is-needed
- **Handler logic is not reactive**: "Logic inside event handlers is not reactive" - "Event handlers can read reactive values without 'reacting' to their changes." Why: "a change to the `message` does not mean that they want to send a message." Smell: an Effect with `[message]` deps that calls `sendMessage(message)`. Source: https://react.dev/learn/separating-events-from-effects#logic-inside-event-handlers-is-not-reactive
- **Effect logic is reactive - declare what it reads**: "Logic inside Effects is reactive" - "If your Effect reads a reactive value, you have to specify it as a dependency." Why: a change to `roomId` means the user wants a different room, so the Effect must re-run. Smell: Effect reads `roomId` with deps `[]`. Source: https://react.dev/learn/separating-events-from-effects#logic-inside-effects-is-reactive
- **Extract non-reactive logic with useEffectEvent**: "Use a special Hook called `useEffectEvent` to extract this non-reactive logic out of your Effect." Why: adding `theme` as a dependency would make the chat re-connect every time you switch theme. Smell: `showNotification('Connected!', theme)` inside an Effect with `theme` in deps. Source: https://react.dev/learn/separating-events-from-effects#declaring-an-effect-event
- **Omit Effect Events from dependencies**: "Effect Events are not reactive and must be omitted from dependencies." Why: they always see the latest props and state, so listing them is unnecessary. Smell: `[roomId, onConnected]` where `onConnected` comes from `useEffectEvent`. Source: https://react.dev/learn/separating-events-from-effects#declaring-an-effect-event
- **Follow the linter when the value should be reactive**: For `logVisit(url)`, "it makes sense to follow the dependency linter, and add `url` as a dependency." Why: each URL represents a different page, so the visit log should react to `url`. Smell: `logVisit(url)` with deps `[]`. Source: https://react.dev/learn/separating-events-from-effects#reading-latest-props-and-state-with-effect-events
- **Split reactive and non-reactive parts with an Effect Event**: When reading `numberOfItems` in a visit log, "Split the code in two parts" - an Effect reactive to `url` calling `onVisit(url)`, an Effect Event reading `numberOfItems`. Why: a change in cart count does not mean the user visited the page again. Smell: `logVisit(url, numberOfItems)` with only `[url]` in deps and a lint warning. Source: https://react.dev/learn/separating-events-from-effects#reading-latest-props-and-state-with-effect-events
- **Pass reactive values into Effect Events as arguments**: "it's better to pass this `url` to the Effect Event explicitly" as `visitedUrl`. Why: it declares that a different URL is a separate event and prevents accidentally dropping `url` from deps, especially with async logic in the Effect. Smell: `useEffectEvent(() => logVisit(url, numberOfItems))` called as `onVisit()` with no arguments. Source: https://react.dev/learn/separating-events-from-effects#reading-latest-props-and-state-with-effect-events
- **Never suppress the dependency linter**: "We recommend never suppressing the linter" - "If you never suppress the linter, you will never see problems with stale values." Why: React stops warning about new reactive dependencies and closures capture stale values (e.g. `canMove` forever `true`). Smell: `// eslint-disable-next-line react-hooks/exhaustive-deps` on an Effect with `[]` that uses a function declared in the component. Source: https://react.dev/learn/separating-events-from-effects#is-it-okay-to-suppress-the-dependency-linter-instead
- **Apply useEffectEvent only to lines that shouldn't be reactive**: "This doesn't mean that `useEffectEvent` is always the correct solution. You should only apply it to the lines of code that you don't want to be reactive." Why: wrapping reactive logic in an Effect Event would stop it from re-synchronizing when it should. Smell: the whole Effect body moved into a `useEffectEvent`, leaving the Effect with `[]`. Source: https://react.dev/learn/separating-events-from-effects#is-it-okay-to-suppress-the-dependency-linter-instead
- **Only call Effect Events from inside Effects**: "Only call them from inside Effects." Why: Effect Events are non-reactive pieces of Effect code, not general-purpose callbacks. Smell: an `useEffectEvent` result invoked from a click handler or during render. Source: https://react.dev/learn/separating-events-from-effects#limitations-of-effect-events
- **Never pass Effect Events to other components or Hooks**: "Never pass them to other components or Hooks" - "always declare Effect Events directly next to the Effects that use them". Why: the receiving hook would need the callback in its deps, defeating the purpose. Smell: `useTimer(onTick, 1000)` where `onTick` was created with `useEffectEvent`. Source: https://react.dev/learn/separating-events-from-effects#limitations-of-effect-events

## Lifecycle of Reactive Effects

- **Think in start/stop synchronization, not mount/update/unmount**: "Think about Effects independently from your component's lifecycle" - "Always focus on a single start/stop cycle at a time." Why: an Effect may start and stop synchronizing many times while the component stays mounted. Smell: comments or logic like "componentDidMount" / "runs once on mount" that ignore re-synchronization on dependency change. Source: https://react.dev/learn/lifecycle-of-reactive-effects#the-lifecycle-of-an-effect
- **Describe how to start and how to stop**: An Effect "describes how to synchronize an external system to the current props and state" - the body starts and the cleanup stops. Why: "Describe how to start and stop synchronization well, and your Effect will be resilient." Smell: Effect that starts a connection/subscription with no cleanup to stop it. Source: https://react.dev/learn/lifecycle-of-reactive-effects#the-lifecycle-of-an-effect
- **Expect re-synchronization on prop changes**: "Synchronization may need to happen multiple times" - when `roomId` changes React runs cleanup with the old value, then the Effect with the new value. Why: the external system must follow the current props and state. Smell: Effect depending on `roomId` whose cleanup doesn't undo the previous room's connection. Source: https://react.dev/learn/lifecycle-of-reactive-effects#why-synchronization-may-need-to-happen-more-than-once
- **Cleanup must fully undo setup**: "How React verifies that your Effect can re-synchronize" - in development React starts and stops the Effect one extra time to check cleanup. Why: seeing connect -> disconnect -> connect proves the Effect can re-synchronize correctly. Smell: setup that leaves listeners/timers/connections behind, visible as duplicate logs after the dev double-run. Source: https://react.dev/learn/lifecycle-of-reactive-effects#how-react-verifies-that-your-effect-can-re-synchronize
- **Declare all reactive values as dependencies**: "Props, state, and values declared inside the component are reactive" - "include reactive values as Effect dependencies". Why: any reactive value can change on a re-render, and the Effect must re-synchronize with it. Smell: `serverUrl` converted from a module constant to `useState` but missing from deps. Source: https://react.dev/learn/lifecycle-of-reactive-effects#effects-react-to-reactive-values
- **Empty deps means the Effect uses no reactive values**: "What an Effect with empty dependencies means" - `[]` is valid only when the Effect reads nothing from props/state (connect on mount, disconnect on unmount). Why: the dependency array describes the code; `[]` with reactive reads is a lie. Smell: `useEffect(..., [])` whose body references a prop. Source: https://react.dev/learn/lifecycle-of-reactive-effects#what-an-effect-with-empty-dependencies-means
- **All component-body variables are reactive**: "All variables declared in the component body are reactive" - including values computed from props like `const serverUrl = settings.serverUrl`. Why: they are recalculated on every render and participate in the data flow. Smell: a locally derived variable used in an Effect but omitted from deps because "it's not state". Source: https://react.dev/learn/lifecycle-of-reactive-effects#all-variables-declared-in-the-component-body-are-reactive
- **Mutable values cannot be dependencies**: "Mutable values (including global variables) aren't reactive" - `location.pathname` and `ref.current` can't be dependencies. Why: changing them doesn't trigger a re-render and reading mutable data during rendering breaks purity. Smell: `ref.current` or `window.location.pathname` listed in an Effect's deps array. Source: https://react.dev/learn/lifecycle-of-reactive-effects#all-variables-declared-in-the-component-body-are-reactive
- **Use useSyncExternalStore for external mutable values**: "read and subscribe to an external mutable value with `useSyncExternalStore`" instead of an Effect depending on it. Why: it subscribes React to changes outside the rendering data flow. Smell: Effect reading `location.pathname` or another global mutable and calling `setState`. Source: https://react.dev/learn/lifecycle-of-reactive-effects#all-variables-declared-in-the-component-body-are-reactive
- **Let the linter verify dependencies**: "React verifies that you specified every reactive value as a dependency" - the linter error indicates a real missing dependency. Why: it keeps the Effect synchronized to the latest props and state. Smell: unresolved `react-hooks/exhaustive-deps` warnings in the diff. Source: https://react.dev/learn/lifecycle-of-reactive-effects#how-react-knows-that-it-needs-to-re-synchronize-the-effect
- **Make values non-reactive instead of omitting them**: "What to do when you don't want to re-synchronize" - move a value outside the component or inside the Effect to prove it's not reactive, rather than dropping it from deps. Why: "you can't 'choose' your dependencies"; the array must describe what the code reads. Smell: a constant-like value declared in the component body and then omitted from deps. Source: https://react.dev/learn/lifecycle-of-reactive-effects#what-to-do-when-you-dont-want-to-re-synchronize
- **Suppress the linter only as a last resort**: "Suppress linter errors like `// eslint-disable-next-line react-hooks/exhaustive-deps` only as a last resort" - "There's always a way to fix the code without breaking the rules." Why: these suppressions "usually indicate bugs" with stale values. Smell: any `eslint-disable` for `exhaustive-deps`. Source: https://react.dev/learn/lifecycle-of-reactive-effects#what-to-do-when-you-dont-want-to-re-synchronize
- **Stable values may be omitted**: "`setState` from `useState`" and the "`ref` object from `useRef`" are stable and "can be omitted from dependencies, though including them is harmless." Why: React guarantees their identity never changes between renders. Smell: not a smell - but a ref or setter received via props is not guaranteed stable. Source: https://react.dev/learn/lifecycle-of-reactive-effects#what-to-do-when-you-dont-want-to-re-synchronize
- **One synchronization process per Effect**: "Each Effect represents a separate synchronization process" - "Don't add unrelated logic to your Effect only because this logic needs to run at the same time." Why: changing dependencies for one concern shouldn't trigger the other (e.g. logging a visit shouldn't re-connect). Smell: `logVisit(roomId)` and `createConnection(...)` in the same `useEffect`. Source: https://react.dev/learn/lifecycle-of-reactive-effects#each-effect-represents-a-separate-synchronization-process
