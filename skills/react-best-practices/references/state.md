# React State Rules (react.dev, React 19.2)

## Choosing the State Structure

- **Group related state**: "If you always update two or more state variables at the same time, consider merging them into a single state variable." Why: "Then you won't forget to always keep them in sync." Smell: two `useState` values that are always set together in the same handler (e.g. `setX(...); setY(...)`). Source: https://react.dev/learn/choosing-the-state-structure#group-related-state
- **Group state of unknown count into an object or array**: Group data into an object or array "when you don't know how many pieces of state you'll need" (e.g. a form with user-added custom fields). Why: a fixed set of `useState` calls cannot represent a dynamic number of fields. Smell: hooks called conditionally or a growing list of `useState` calls for dynamic fields. Source: https://react.dev/learn/choosing-the-state-structure#group-related-state
- **Copy all fields when setting an object state**: When state is an object, "you can't update only one field in it without explicitly copying the other fields"; use `setPosition({ ...position, x: 100 })` or split into separate state variables. Why: `setPosition({ x: 100 })` "would not have the `y` property at all". Smell: setter called with a partial object literal lacking the other fields. Source: https://react.dev/learn/choosing-the-state-structure#group-related-state
- **Avoid contradictions in state**: Replace booleans that "should never be `true` at the same time" (e.g. `isSending`, `isSent`) with "one `status` state variable that may take one of three valid states". Why: several pieces of state that "may contradict and 'disagree' with each other" leave "room for mistakes". Smell: multiple `is*` boolean state variables describing one lifecycle (`isLoading`, `isSuccess`, `isError`). Source: https://react.dev/learn/choosing-the-state-structure#avoid-contradictions-in-state
- **Derive readability constants, not state**: "You can still declare some constants for readability" like `const isSending = status === 'sending'`, "but they're not state variables". Why: derived constants "don't need to worry about them getting out of sync with each other". Smell: a boolean stored in state that equals `status === 'x'`. Source: https://react.dev/learn/choosing-the-state-structure#avoid-contradictions-in-state
- **Avoid redundant state**: "If you can calculate some information from the component's props or its existing state variables during rendering, you should not put that information into that component's state." Why: change handlers "don't need to do anything special to update it"; the value is recalculated from fresh data on every render. Smell: `fullName` state alongside `firstName`/`lastName` state, or a `useEffect` that sets state from other state. Source: https://react.dev/learn/choosing-the-state-structure#avoid-redundant-state
- **Don't mirror props in state**: Do not write `const [color, setColor] = useState(messageColor)`; "use the `messageColor` prop directly in your code" or alias it with a constant. Why: "if the parent component passes a different value of `messageColor` later ... the `color` state variable would not be updated!" because "the state is only initialized during the first render". Smell: `useState(someProp)` where the prop is later expected to change. Source: https://react.dev/learn/choosing-the-state-structure#don-t-mirror-props-in-state
- **Name ignored props `initial*` or `default*`**: Mirroring a prop into state "only makes sense when you *want* to ignore all updates for a specific prop"; "start the prop name with `initial` or `default` to clarify that its new values are ignored". Why: makes the intentional one-time initialization explicit to callers. Smell: `useState(props.value)` where `value` is not prefixed with `initial`/`default`. Source: https://react.dev/learn/choosing-the-state-structure#don-t-mirror-props-in-state
- **Avoid duplication in state**: "When the same data is duplicated between multiple state variables, or within nested objects, it is difficult to keep them in sync. Reduce duplication when you can." Why: editing one copy leaves the other stale. Smell: `selectedItem` object state that is "the same object as one of the items inside the `items` list". Source: https://react.dev/learn/choosing-the-state-structure#avoid-duplication-in-state
- **Keep ID or index in state for selection**: "Hold the `selectedId` in state, and then get the `selectedItem` by searching the `items` array for an item with that ID." Why: "only the selected ID is essential. The rest could be calculated during render." Smell: `useState<Item>()` for a selected/active/hovered entity instead of `useState<Item['id']>()`. Source: https://react.dev/learn/choosing-the-state-structure#avoid-duplication-in-state
- **Avoid deeply nested state**: "If the state is too nested to update easily, consider making it 'flat'"; "when possible, prefer to structure state in a flat way." Why: "Deeply hierarchical state is not very convenient to update" and flattening "helps ensure you don't have duplication in different parts of a nested object". Smell: state where updates require spreading three or more levels (`{...a, b: {...a.b, c: {...a.b.c, d}}}`). Source: https://react.dev/learn/choosing-the-state-structure#avoid-deeply-nested-state
- **Normalize trees into ID maps**: Instead of "a tree-like structure where each `place` has an array of its child places", "have each place hold an array of its child place IDs" and "store a mapping from each place ID to the corresponding place". Why: removing an item then requires updating "only ... two levels of state". Smell: recursive `children: Node[]` arrays stored in state. Source: https://react.dev/learn/choosing-the-state-structure#avoid-deeply-nested-state
- **Clean up removed items from normalized tables**: "Ideally, you would also remove the deleted items (and their children!) from the 'table' object to improve memory usage." Why: orphaned entries linger in memory after their parent drops the ID. Smell: a delete handler that removes an ID from `childIds` but never deletes the entry from the map. Source: https://react.dev/learn/choosing-the-state-structure#improving-memory-usage
- **Make state as simple as it can be, but no simpler**: Aim to "make state easy to update without introducing mistakes" and "choose your state variables carefully to avoid creating 'impossible' states". Why: "Removing redundant and duplicate data from state helps ensure that all its pieces stay in sync." Smell: state shape that permits combinations the UI never renders. Source: https://react.dev/learn/choosing-the-state-structure#principles-for-structuring-state

## Sharing State Between Components

- **Lift state up to coordinate components**: When "you want the state of two components to always change together ... remove state from both of them, move it to their closest common parent, and then pass it down to them via props". Why: siblings cannot read each other's local state, so coordination requires a shared owner. Smell: two siblings each holding `useState` for something that must stay in sync (e.g. only one panel open). Source: https://react.dev/learn/sharing-state-between-components#lifting-state-up-by-example
- **Remove state from the children first**: "Start by removing this line from the `Panel` component: `const [isActive, setIsActive] = useState(false);`" and "add `isActive` to the `Panel`'s list of props". Why: the parent "can *control* `isActive` by passing it down as a prop" only if the child no longer owns it. Smell: a child keeps both a local `useState` and a same-named prop. Source: https://react.dev/learn/sharing-state-between-components#step-1-remove-state-from-the-child-components
- **Locate the closest common parent**: "To lift state up, you must locate the closest common parent component of *both* of the child components that you want to coordinate"; it "will become the 'source of truth'". Why: lifting higher than necessary spreads state farther than it needs to travel. Smell: shared state placed at app root when only two nearby siblings use it. Source: https://react.dev/learn/sharing-state-between-components#step-2-pass-hardcoded-data-from-the-common-parent
- **Reshape state when lifting it**: "Lifting state up often changes the nature of what you're storing as state"; instead of a boolean per panel, use "the index of the active `Panel`". Why: "Using the active index instead of two 'is shown' flags ensured that only one panel is active at a given time." Smell: parent holding `isOpenA`, `isOpenB` booleans instead of a single `activeIndex`/`activeId`. Source: https://react.dev/learn/sharing-state-between-components#step-3-add-state-to-the-common-parent
- **Pass event handlers down so children can change parent state**: "A `Panel` can't set the `activeIndex` state directly"; the parent "needs to *explicitly allow* the `Panel` component to change its state by passing an event handler down as a prop" (e.g. `onShow={() => setActiveIndex(0)}`). Why: keeps the parent as the single owner while letting children trigger changes. Smell: passing the raw setter (`setActiveIndex`) down instead of a purpose-named handler, or child mutating shared state. Source: https://react.dev/learn/sharing-state-between-components#step-3-add-state-to-the-common-parent
- **Decide what is controlled vs uncontrolled**: "When writing a component, consider which information in it should be controlled (via props), and which information should be uncontrolled (via state)." Why: "Uncontrolled components are easier to use ... but they're less flexible when you want to coordinate them"; "Controlled components are maximally flexible, but they require the parent components to fully configure them with props." Smell: a component with internal state that parents repeatedly work around with keys or effects to influence. Source: https://react.dev/learn/sharing-state-between-components#controlled-and-uncontrolled-components
- **Single source of truth for each piece of state**: "For each unique piece of state, you will choose the component that 'owns' it"; "Instead of duplicating shared state between components, *lift it up* to their common shared parent, and *pass it down* to the children that need it." Why: "It doesn't mean that all state lives in one place--but that for *each* piece of state, there is a *specific* component that holds that piece of information." Smell: the same value held in `useState` in two components and synced via props plus effects. Source: https://react.dev/learn/sharing-state-between-components#a-single-source-of-truth-for-each-state
- **Move state up or down freely as the app evolves**: "It is common that you will move state down or back up while you're still figuring out where each piece of the state 'lives'"; "you can always change your mind and refactor later." Why: state ownership is a design decision, not a fixed commitment. Smell: state kept high in the tree "just in case" with no second consumer. Source: https://react.dev/learn/sharing-state-between-components#a-single-source-of-truth-for-each-state

## Preserving and Resetting State

- **State is tied to tree position, not the component**: "React associates each piece of state it's holding with the correct component by where that component sits in the render tree." Why: "the state is actually held inside React", not in the function or JSX. Smell: assuming two `<Counter />` instances share state, or that state follows a component when it moves. Source: https://react.dev/learn/preserving-and-resetting-state#state-is-tied-to-a-position-in-the-tree
- **Removing a component destroys its state**: "React preserves a component's state for as long as it's being rendered at its position in the UI tree. If it gets removed, or a different component gets rendered at the same position, React discards its state." Why: "when React removes a component, it destroys its state." Smell: conditionally unmounting a component and expecting its inputs or counters to survive. Source: https://react.dev/learn/preserving-and-resetting-state#state-is-tied-to-a-position-in-the-tree
- **Same component at same position preserves state even with different props**: Switching between `<Counter isFancy={true} />` and `<Counter isFancy={false} />` at the same position "will not reset the counter's state". Why: React sees "the same component in the same position". Smell: expecting a prop change alone to reset a child's internal state. Source: https://react.dev/learn/preserving-and-resetting-state#same-component-at-the-same-position-preserves-state
- **Position in the UI tree matters, not JSX markup**: "It's the position in the UI tree--not in the JSX markup--that matters to React!" Two `return` branches each rendering `<div><Counter /></div>` share "the same 'address'". Why: "This is how React matches them up between the previous and next renders, regardless of how you structure your logic." Smell: two `if` branches returning structurally identical JSX, expecting separate state. Source: https://react.dev/learn/preserving-and-resetting-state#same-component-at-the-same-position-preserves-state
- **Different component at same position resets the entire subtree**: "When you render a different component in the same position, it resets the state of its entire subtree." Why: React removes the first component and "destroys its state". Smell: toggling between `<section><Counter/></section>` and `<div><Counter/></div>` and losing the counter. Source: https://react.dev/learn/preserving-and-resetting-state#different-components-at-the-same-position-reset-state
- **Match up tree structure to preserve state**: "If you want to preserve the state between re-renders, the structure of your tree needs to 'match up' from one render to another." Why: "If the structure is different, the state gets destroyed." Smell: wrapping/unwrapping a child in a conditional wrapper element between renders. Source: https://react.dev/learn/preserving-and-resetting-state#different-components-at-the-same-position-reset-state
- **Never nest component definitions**: "Always declare component functions at the top level, and don't nest their definitions." Why: "a *different* `MyTextField` function is created for every render ... so React resets all state below. This leads to bugs and performance problems." Smell: `function Inner() {...}` or `const Inner = () => ...` declared inside another component body. Source: https://react.dev/learn/preserving-and-resetting-state#different-components-at-the-same-position-reset-state
- **Reset state by rendering in different positions**: To reset, you can render the alternatives in different positions, e.g. `{isPlayerA && <Counter person="Taylor" />}{!isPlayerA && <Counter person="Sarah" />}`. Why: "each `Counter` appears in a different position and their states reset independently." Smell: a single conditional `isPlayerA ? <Counter .../> : <Counter .../>` that unexpectedly carries state across players. Source: https://react.dev/learn/preserving-and-resetting-state#option-1-rendering-a-component-in-different-positions
- **Use `key` to reset state at the same position**: "Specifying a `key` tells React to use the `key` itself as part of the position, instead of their order within the parent"; "Keys aren't just for lists! You can use keys to make React distinguish between any components." Why: with different keys "React sees them as two different counters, and so they will never share state." Smell: a `useEffect` that resets local state when an id prop changes, instead of `key={id}` on the component. Source: https://react.dev/learn/preserving-and-resetting-state#option-2-resetting-state-with-a-key
- **Keys are scoped to the parent**: "Remember that keys are not globally unique. They only specify the position *within the parent*." Why: the same key in different parents refers to different positions. Smell: relying on a key to match components across different parents. Source: https://react.dev/learn/preserving-and-resetting-state#option-2-resetting-state-with-a-key
- **Reset forms with a key on the entity id**: Use `<Chat key={to.id} contact={to} />` so that "switching the recipient always clears the text field." Why: the key makes each contact's form a distinct component instance. Smell: form/editor component receiving a changing `entity` prop while keeping stale draft input. Source: https://react.dev/learn/preserving-and-resetting-state#resetting-a-form-with-a-key
- **Prefer lifting state to preserve drafts of removed components**: To keep state for components no longer rendered, "you could lift the state up and hold the pending message for each recipient in the parent component. This is the most common solution." Why: hiding with CSS "can get very slow if the hidden trees are large" and `localStorage` is a persistence workaround. Smell: rendering all tabs/chats hidden via CSS solely to keep their local state alive. Source: https://react.dev/learn/preserving-and-resetting-state#preserving-state-for-removed-components

## State as a Snapshot

- **Update state to make the UI react**: "For an interface to react to the event, you need to *update the state*"; setting state "queues a new render". Why: React re-renders "according to the new" state value rather than mutating the DOM directly. Smell: event handlers touching DOM nodes or local variables instead of calling a setter. Source: https://react.dev/learn/state-as-a-snapshot#setting-state-triggers-renders
- **Treat each render as a snapshot**: The JSX returned is "a snapshot of the UI in time. Its props, event handlers, and local variables were all calculated using its state at the time of the render." Why: "When React calls your component, it gives you a snapshot of the state for that particular render." Smell: code assuming a variable read during render reflects a later state change. Source: https://react.dev/learn/state-as-a-snapshot#rendering-takes-a-snapshot-in-time
- **Setting state only changes it for the next render**: "Setting state only changes it for the *next* render"; after `setNumber(number + 1)` the value of `number` in the same handler "is still `0`". Why: state "lives" in React "outside of your function" and the current render's value is fixed. Smell: calling `setX(x + 1)` several times in one handler expecting cumulative increments. Source: https://react.dev/learn/state-as-a-snapshot#rendering-takes-a-snapshot-in-time
- **Don't read state right after setting it**: After `setNumber(number + 5); alert(number);` the alert shows the old value (`0`). Why: the setter does not change "the state variable you already have, but instead triggers a re-render". Smell: `setValue(next); doSomething(value)` expecting `value` to be `next`. Source: https://react.dev/learn/state-as-a-snapshot#state-over-time
- **A state variable's value never changes within a render**: "A state variable's value never changes within a render, even if its event handler's code is asynchronous." Why: "Its value was 'fixed' when React 'took the snapshot' of the UI by calling your component." Smell: a `setTimeout`/promise callback inside a handler that expects to see state updated after scheduling. Source: https://react.dev/learn/state-as-a-snapshot#state-over-time
- **Rely on fixed values in async handlers**: "React keeps the state values 'fixed' within one render's event handlers. You don't need to worry whether the state has changed while the code is running." Why: this makes "event handlers less prone to timing mistakes" (the delayed message goes to the recipient chosen at submit time). Smell: copying state into refs or module variables to "protect" a handler from later changes. Source: https://react.dev/learn/state-as-a-snapshot#state-over-time
- **Use an updater function to read the latest state before a re-render**: "If you wanted to read the latest state before a re-render? You'll want to use a state updater function." Why: the closed-over state variable is a stale snapshot; only the updater receives the pending value. Smell: multiple sequential `setX(x + n)` calls or handlers that need the queued value. Source: https://react.dev/learn/state-as-a-snapshot#state-over-time
- **Use the substitution method to reason about handlers**: "You can mentally substitute state in event handlers, similarly to how you think about the rendered JSX." Why: "Every render (and functions inside it) will always 'see' the snapshot of the state that React gave to *that* render." Smell: handler logic like `alert(walk ? 'Stop is next' : 'Walk is next')` misread as inverted. Source: https://react.dev/learn/state-as-a-snapshot#recap
- **Don't expect variables or handlers to survive re-renders**: "Variables and event handlers don't 'survive' re-renders. Every render has its own event handlers"; "Event handlers created in the past have the state values from the render in which they were created." Why: each render produces a fresh closure over that render's state. Smell: storing a handler created in one render and calling it later expecting current state. Source: https://react.dev/learn/state-as-a-snapshot#recap

## Queueing a Series of State Updates

- **Expect batching within an event handler**: "React waits until *all* code in the event handlers has run before processing your state updates"; the re-render "only happens *after* all `setNumber()` calls". Why: batching "lets you update multiple state variables--even from multiple components--without triggering too many re-renders" and avoids "half-finished" renders. Smell: code that expects a re-render (or DOM update) between two setter calls in the same handler. Source: https://react.dev/learn/queueing-a-series-of-state-updates#react-batches-state-updates
- **Don't rely on batching across separate events**: "React does not batch across *multiple* intentional events like clicks--each click is handled separately." Why: React "only batches when it's generally safe to do", so "if the first button click disables a form, the second click would not submit it again." Smell: logic assuming two rapid clicks are coalesced into one update. Source: https://react.dev/learn/queueing-a-series-of-state-updates#react-batches-state-updates
- **Use an updater function to update the same state multiple times**: "To update the same state variable multiple times before the next render, pass an *updater function*" like `setNumber(n => n + 1)` instead of `setNumber(number + 1)`. Why: React "queues this function to be processed" and "goes through the queue" giving each updater the previous result. Smell: `setCount(count + 1)` repeated in one handler or in a loop. Source: https://react.dev/learn/queueing-a-series-of-state-updates#updating-the-same-state-multiple-times-before-the-next-render
- **Know that a plain value replaces the queue result**: "Any other value (e.g. number `5`) adds 'replace with `5`' to the queue, ignoring what's already queued." Why: `setState(5)` "works like `setState(n => 5)`" and discards prior queued updater results. Smell: mixing `setX(value)` after `setX(updater)` and expecting the updater's contribution to survive. Source: https://react.dev/learn/queueing-a-series-of-state-updates#what-happens-if-you-replace-state-after-updating-it
- **Updater functions must be pure**: "Updater functions must be pure and only *return* the result. Don't try to set state from inside of them or run other side effects." Why: "In Strict Mode, React will run each updater function twice (but discard the second result) to help you find mistakes." Smell: `setX(prev => { fetch(...); setY(...); return prev + 1; })`. Source: https://react.dev/learn/queueing-a-series-of-state-updates#what-happens-if-you-replace-state-after-updating-it
- **Name the updater argument after the state variable**: "It's common to name the updater function argument by the first letters of the corresponding state variable" (`setEnabled(e => !e)`), or "repeat the full state variable name or use a prefix" (`setEnabled(prevEnabled => !prevEnabled)`). Why: signals the argument is the previous value of that same state. Smell: `setItems(x => ...)` or `setItems(data => ...)` with unrelated names. Source: https://react.dev/learn/queueing-a-series-of-state-updates#naming-conventions
- **Setting state does not change the current render's variable**: "Setting state does not change the variable in the existing render, but it requests a new render." Why: "React processes state updates after event handlers have finished running." Smell: reading a state variable after its setter in the same handler and expecting the new value. Source: https://react.dev/learn/queueing-a-series-of-state-updates#recap

## Updating Objects in State

- **Treat objects in state as immutable**: "Although objects in React state are technically mutable, you should treat them as if they were immutable--like numbers, booleans, and strings. Instead of mutating them, you should always replace them." Why: "when you mutate state directly without using the state setting function, React has no idea that the object has changed." Smell: `position.x = e.clientX` on an object obtained from `useState`. Source: https://react.dev/learn/updating-objects-in-state#treat-state-as-read-only
- **Create a new object and pass it to the setter**: "To actually trigger a re-render, create a *new* object and pass it to the state setting function." Why: `setPosition` tells React to "replace `position` with this new object and render this component again". Smell: mutation followed by `setState(sameObject)` or no setter call at all. Source: https://react.dev/learn/updating-objects-in-state#treat-state-as-read-only
- **Local mutation of freshly created objects is fine**: "Mutation is only a problem when you change *existing* objects that are already in state. Mutating an object you've just created is okay because *no other code references it yet*." Why: "Changing it isn't going to accidentally impact something that depends on it"; you can even do this "while rendering". Smell: none; this is the allowed pattern (`const next = {}; next.x = 1; setPosition(next)`). Source: https://react.dev/learn/updating-objects-in-state#local-mutation-is-fine
- **Use spread to copy and override fields**: "When you want to update *only one* field in an object but keep the previous values for all other fields", use `setPerson({ ...person, firstName: e.target.value })`. Why: preserves untouched fields without mutating the original. Smell: setter called with only the changed field, dropping the rest. Source: https://react.dev/learn/updating-objects-in-state#copying-objects-with-the-spread-syntax
- **Remember spread is shallow**: "The `...` spread syntax is 'shallow'--it only copies things one level deep." Why: "if you want to update a nested property, you'll have to use it more than once." Smell: `{ ...person }` followed by `copy.artwork.city = 'x'`. Source: https://react.dev/learn/updating-objects-in-state#copying-objects-with-the-spread-syntax
- **Use computed property names for multi-field handlers**: "You can use the `[` and `]` braces inside your object definition to specify a property with a dynamic name" (`[e.target.name]: e.target.value`). Why: lets one handler serve several inputs without duplicating copy logic. Smell: three near-identical `handleFirstNameChange`/`handleLastNameChange`/`handleEmailChange` handlers. Source: https://react.dev/learn/updating-objects-in-state#using-a-single-event-handler-for-multiple-fields
- **Copy every level up to the changed nested field**: "To update a nested object, you need to create copies all the way up from the place you're updating" (`{ ...person, artwork: { ...person.artwork, city: 'New Delhi' } }`). Why: objects are not really nested; "multiple objects can 'point' at the same object", so mutating a shared inner object affects every holder. Smell: `person.artwork.city = 'x'; setPerson({ ...person })`. Source: https://react.dev/learn/updating-objects-in-state#updating-a-nested-object
- **Flatten deeply nested state or use Immer**: "If your state is deeply nested, you might want to consider flattening it"; otherwise "you might prefer a shortcut to nested spreads" via Immer's `useImmer`. Why: Immer "lets you write using the convenient but mutating syntax and takes care of producing the copies for you" while it "doesn't overwrite the past state". Smell: repetitive multi-level spreads in many handlers. Source: https://react.dev/learn/updating-objects-in-state#write-concise-update-logic-with-immer
- **Mix `useState` and `useImmer` as needed**: "You can mix and match `useState` and `useImmer` in a single component as much as you like." Why: Immer is "a great way to keep the update handlers concise, especially if there's nesting in your state". Smell: none; a permitted pattern. Source: https://react.dev/learn/updating-objects-in-state#write-concise-update-logic-with-immer
- **Never mutate state even when you can "get away" with it**: "In practice, you can often 'get away' with mutating state in React, but we strongly advise you not to do that." Why: mutation breaks debugging (past logs "clobbered"), memo optimizations (`prevObj === obj` checks), snapshot-based new features, undo/redo, and simpler implementation. Smell: `state.items.push(x); setState(state)` that "works" but bypasses equality checks. Source: https://react.dev/learn/updating-objects-in-state#why-is-mutating-state-not-recommended-in-react

## Updating Arrays in State

- **Treat arrays in state as read-only**: "You should treat arrays in React state as read-only. This means that you shouldn't reassign items inside an array like `arr[0] = 'bird'`, and you also shouldn't use methods that mutate the array, such as `push()` and `pop()`." Why: arrays "are just another kind of object" and mutation does not trigger renders. Smell: `items.push(x)`, `items[i] = y`, `items.splice(...)` on state arrays. Source: https://react.dev/learn/updating-arrays-in-state#updating-arrays-without-mutation
- **Use non-mutating methods and set a new array**: "Every time you want to update an array, you'll want to pass a *new* array to your state setting function" created with "non-mutating methods like `filter()` and `map()`". Why: React detects the new reference and re-renders. Smell: mutating then calling `setItems(items)` with the same reference. Source: https://react.dev/learn/updating-arrays-in-state#updating-arrays-without-mutation
- **Adding: prefer `concat`/spread over `push`/`unshift`**: Avoid `push`, `unshift`; prefer `concat`, `[...arr]` spread syntax. Why: spread "can do the job of both `push()` by adding to the end of an array and `unshift()` by adding to the beginning" without mutation. Smell: `list.push(item)` in a handler. Source: https://react.dev/learn/updating-arrays-in-state#adding-to-an-array
- **Removing: prefer `filter`/`slice` over `pop`/`shift`/`splice`**: Avoid `pop`, `shift`, `splice`; prefer `filter`, `slice`, e.g. `artists.filter(a => a.id !== artist.id)`. Why: "`filter` does not modify the original array." Smell: `splice(index, 1)` on a state array. Source: https://react.dev/learn/updating-arrays-in-state#removing-from-an-array
- **Replacing: prefer `map` over index assignment or `splice`**: Avoid `splice`, `arr[i] = ...` assignment; prefer `map`, using the index as the second argument "to decide whether to return the original item ... or something else". Why: "Assignments like `arr[0] = 'bird'` are mutating the original array." Smell: `counters[index] += 1; setCounters(counters)`. Source: https://react.dev/learn/updating-arrays-in-state#replacing-items-in-an-array
- **Transforming: use `map` to create a new array**: "If you want to change some or all items of the array, you can use `map()` to create a **new** array." Why: the map callback decides per item "based on its data or its index" without touching the original. Smell: `forEach` that assigns into the existing array. Source: https://react.dev/learn/updating-arrays-in-state#transforming-an-array
- **Inserting: combine spread with `slice`**: To insert at a position, spread `slice(0, insertAt)`, the new item, then `slice(insertAt)`. Why: `slice` "lets you cut a 'slice' of the array" without mutating it. Smell: `splice(insertAt, 0, item)` on state. Source: https://react.dev/learn/updating-arrays-in-state#inserting-into-an-array
- **Use `slice`, not `splice`**: "`slice` lets you copy an array or a part of it. `splice` **mutates** the array (to insert or delete items). In React, you will be using `slice` (no `p`!) a lot more often." Why: the two are "named similarly but are very different". Smell: any `.splice(` call on a state array. Source: https://react.dev/learn/updating-arrays-in-state#updating-arrays-without-mutation
- **Sorting/reversing: copy the array first**: "The JavaScript `reverse()` and `sort()` methods are mutating the original array, so you can't use them directly"; "you can copy the array first, and then make changes to it" (`const nextList = [...list]; nextList.reverse();`). Why: sorting the state array in place mutates the snapshot. Smell: `items.sort(...)` directly on state, including inside render. Source: https://react.dev/learn/updating-arrays-in-state#making-other-changes-to-an-array
- **Don't mutate items inside a copied array**: "Even if you copy an array, you can't mutate existing items *inside* of it directly"; "`nextList[0]` and `list[0]` point to the same object." Why: "copying is shallow--the new array will contain the same items as the original one." Smell: `const next = [...list]; next[0].seen = true; setList(next)`. Source: https://react.dev/learn/updating-arrays-in-state#making-other-changes-to-an-array
- **Update objects in arrays with `map` and object spread**: "You can use `map` to substitute an old item with its updated version without mutation" returning `{ ...artwork, seen: nextSeen }` for the matching id. Why: "When updating nested state, you need to create copies from the point where you want to update, and all the way up to the top level." Smell: `list.find(a => a.id === id).seen = true`. Source: https://react.dev/learn/updating-arrays-in-state#updating-objects-inside-arrays
- **Only mutate objects you have just created**: "In general, you should only mutate objects that you have just created. If you were inserting a *new* artwork, you could mutate it, but if you're dealing with something that's already in state, you need to make a copy." Why: existing items may be referenced by other state ("Another person's artwork list may point to the same element"). Smell: mutating an element found via `find` on a state array. Source: https://react.dev/learn/updating-arrays-in-state#updating-objects-inside-arrays
- **Keep state shallow or use Immer**: "You shouldn't need to update state more than a couple of levels deep. If your state objects are very deep, you might want to restructure them differently so that they are flat"; otherwise use Immer, where "mutation like `artwork.seen = nextSeen` is now okay" on the `draft`. Why: Immer "always constructs the next state from scratch according to the changes that you've done to the `draft`". Smell: nested `map` inside `map` with spreads in many handlers. Source: https://react.dev/learn/updating-arrays-in-state#write-concise-update-logic-with-immer

## Reacting to Input with State

- **Declare what to show instead of manipulating the UI**: "You don't directly manipulate the UI--meaning you don't enable, disable, show, or hide components directly. Instead, you declare what you want to show, and React figures out how to update the UI." Why: imperative manipulation "gets exponentially more difficult to manage in more complex systems". Smell: `ref.current.disabled = true`, `element.style.display = 'none'`, `classList.add` inside handlers. Source: https://react.dev/learn/reacting-to-input-with-state#how-declarative-ui-compares-to-imperative
- **Identify all visual states first**: "First, you need to visualize all the different 'states' of the UI the user might see" (Empty, Typing, Submitting, Success, Error) and "mock up" them "before you add logic". Why: React "stands at the intersection of design and computer science" and each visual state must be representable. Smell: component whose JSX cannot render an obvious state (e.g. no error rendering path). Source: https://react.dev/learn/reacting-to-input-with-state#step-1-identify-your-components-different-visual-states
- **Determine human and computer triggers**: State updates respond to "Human inputs, like clicking a button, typing in a field" and "Computer inputs, like a network response arriving, a timeout completing"; "in both cases, you must set state variables to update the UI." Why: "human inputs often require event handlers"; drawing states and transitions "can sort out bugs long before implementation". Smell: transitions handled outside of state (e.g. network success toggling DOM directly). Source: https://react.dev/learn/reacting-to-input-with-state#step-2-determine-what-triggers-those-state-changes
- **Keep as few moving pieces as possible**: "Each piece of state is a 'moving piece', and you want as few 'moving pieces' as possible. More complexity leads to more bugs!" Why: every additional state variable must be kept in sync. Smell: a component with many `useState` calls covering overlapping concerns. Source: https://react.dev/learn/reacting-to-input-with-state#step-3-represent-the-state-in-memory-with-usestate
- **Start with state that absolutely must be there**: "Start with the state that *absolutely must* be there" (e.g. `answer`, `error`), then add a variable "representing which one of the visual states that you want to display". Why: "There's usually more than a single way to represent that in memory, so you'll need to experiment with it." Smell: adding a state variable per visual state before checking what is essential. Source: https://react.dev/learn/reacting-to-input-with-state#step-3-represent-the-state-in-memory-with-usestate
- **Prevent state that represents no valid UI**: "Your goal is to prevent the cases where the state in memory doesn't represent any valid UI that you'd want a user to see." Why: e.g. "you never want to show an error message and disable the input at the same time, or the user won't be able to correct the error!" Smell: combinations of state values with no corresponding design mock. Source: https://react.dev/learn/reacting-to-input-with-state#step-4-remove-any-non-essential-state-variables
- **Remove paradoxes by combining booleans into a `status`**: "Does this state cause a paradox? For example, `isTyping` and `isSubmitting` can't both be `true`"; "combine these into a `status` that must be one of three values: `'typing'`, `'submitting'`, or `'success'`." Why: "There are four possible combinations of two booleans, but only three correspond to valid states." Smell: `isTyping`, `isSubmitting`, `isSuccess` as separate `useState` booleans. Source: https://react.dev/learn/reacting-to-input-with-state#step-4-remove-any-non-essential-state-variables
- **Remove state available from another state variable**: "Is the same information available in another state variable already?" e.g. "remove `isEmpty` and instead check `answer.length === 0`." Why: "By making them separate state variables, you risk them going out of sync and causing bugs." Smell: `isEmpty` state kept alongside the string it describes. Source: https://react.dev/learn/reacting-to-input-with-state#step-4-remove-any-non-essential-state-variables
- **Remove state derivable from the inverse of another**: "Can you get the same information from the inverse of another state variable? `isError` is not needed because you can check `error !== null` instead." Why: the boolean duplicates information already present. Smell: `hasError`/`isError` boolean stored next to an `error` value. Source: https://react.dev/learn/reacting-to-input-with-state#step-4-remove-any-non-essential-state-variables
- **Keep only essential state**: After cleanup, "you know they are essential, because you can't remove any of them without breaking the functionality." Why: refactoring state "will make your components easier to understand, reduce duplication, and avoid unintended meanings." Smell: a state variable that can be deleted with the component still working. Source: https://react.dev/learn/reacting-to-input-with-state#step-4-remove-any-non-essential-state-variables
- **Use a reducer to eliminate remaining impossible states**: When "a non-null `error` doesn't make sense when `status` is `'success'`", "to model the state more precisely, you can extract it into a reducer." Why: "Reducers let you unify multiple state variables into a single object and consolidate all the related logic!" Smell: `status` and `error` as separate variables with implicit invariants between them. Source: https://react.dev/learn/reacting-to-input-with-state#step-4-remove-any-non-essential-state-variables
- **Express all interactions as state changes in event handlers**: "Lastly, create event handlers that update the state." Why: "Expressing all interactions as state changes lets you later introduce new visual states without breaking existing ones" and "change what should be displayed in each state without changing the logic of the interaction itself." Smell: handlers that both set state and imperatively toggle UI. Source: https://react.dev/learn/reacting-to-input-with-state#step-5-connect-the-event-handlers-to-set-state

## Extracting State Logic into a Reducer

- **Consolidate scattered update logic into a reducer**: When "components with many state updates spread across many event handlers can get overwhelming", "consolidate all the state update logic outside your component in a single function, called a reducer". Why: keeps the component focused on what happened rather than how state changes. Smell: several handlers each spreading/mapping the same array state with slightly different logic. Source: https://react.dev/learn/extracting-state-logic-into-a-reducer#consolidate-state-logic-with-a-reducer
- **Dispatch actions describing what happened, not what to do**: "Instead of telling React 'what to do' by setting state, you specify 'what the user just did' by dispatching 'actions' from your event handlers." Why: "Cleanly separates the *how* of update logic from the *what happened* of event handlers." Smell: `dispatch({ type: 'set_tasks', tasks: [...] })` that carries precomputed next state. Source: https://react.dev/learn/extracting-state-logic-into-a-reducer#step-1-move-from-setting-state-to-dispatching-actions
- **Give actions a descriptive string `type`**: "By convention, give it a string `type` that describes what happened, and pass any additional information in other fields." Why: the type is "specific to component" and makes logs readable. Smell: actions keyed by numbers, or with a `type` like `'update'` that says nothing about the interaction. Source: https://react.dev/learn/extracting-state-logic-into-a-reducer#step-1-move-from-setting-state-to-dispatching-actions
- **Reducer signature: `(state, action) => nextState`**: "A reducer function is where you will put your state logic. It takes two arguments, the current state and the action object, and it returns the next state." Why: React sets the returned value as the next state. Smell: a reducer that returns `undefined` for some branch. Source: https://react.dev/learn/extracting-state-logic-into-a-reducer#step-2-write-a-reducer-function
- **Wrap each `case` in braces and end with `return`**: "We recommend wrapping each `case` block into the `{` and `}` curly braces so that variables declared inside of different `case`s don't clash with each other. Also, a `case` should usually end with a `return`." Why: "If you forget to `return`, the code will 'fall through' to the next `case`, which can lead to mistakes!" Smell: `case 'x':` without braces, or a case ending in `break` in a plain (non-Immer) reducer. Source: https://react.dev/learn/extracting-state-logic-into-a-reducer#step-2-write-a-reducer-function
- **Throw on unknown actions**: The default branch should `throw Error('Unknown action: ' + action.type)`. Why: silently returning state hides typos in action types. Smell: `default: return state`. Source: https://react.dev/learn/extracting-state-logic-into-a-reducer#step-2-write-a-reducer-function
- **Replace `useState` with `useReducer(reducer, initialState)`**: `const [tasks, dispatch] = useReducer(tasksReducer, initialTasks);` returns "a stateful value" and "a dispatch function". Why: the reducer "can be exported and tested separately in isolation" and can live in its own file. Smell: reducer-like logic duplicated inside handlers while still using `useState`. Source: https://react.dev/learn/extracting-state-logic-into-a-reducer#step-3-use-the-reducer-from-your-component
- **Use a reducer when state bugs recur, not for everything**: "We recommend using a reducer if you often encounter bugs due to incorrect state updates in some component, and want to introduce more structure to its code. You don't have to use reducers for everything: feel free to mix and match!" Why: `useState` means "less code upfront" and is "very easy" for simple updates; reducers "help when many event handlers modify state in a similar way". Smell: `useReducer` for a single boolean toggle, or `useState` with ten interdependent handlers. Source: https://react.dev/learn/extracting-state-logic-into-a-reducer#comparing-usestate-and-usereducer
- **Reducers must be pure**: "Reducers must be pure--same inputs always result in the same output. They should not send requests, schedule timeouts, or perform any side effects ... They should update objects and arrays without mutations." Why: "reducers run during rendering! (Actions are queued until the next render.)" Smell: `fetch`, `setTimeout`, `state.items.push(...)`, or `Date.now()` inside a reducer. Source: https://react.dev/learn/extracting-state-logic-into-a-reducer#writing-reducers-well
- **One action per user interaction**: "Each action describes a single user interaction, even if that leads to multiple changes in the data"; dispatch "one `reset_form` action rather than five separate `set_field` actions." Why: "If you log every action in a reducer, that log should be clear enough for you to reconstruct what interactions or responses happened in what order." Smell: a handler dispatching several actions in a row for one click. Source: https://react.dev/learn/extracting-state-logic-into-a-reducer#writing-reducers-well
- **Use Immer to write reducers in a mutating style**: With `useImmerReducer`, "Immer provides you with a special `draft` object which is safe to mutate ... reducers managed by `useImmerReducer` can mutate their first argument and don't need to return state." Why: keeps reducers concise when updates are nested. Smell: mutating `state` directly in a plain `useReducer` reducer while assuming Immer semantics. Source: https://react.dev/learn/extracting-state-logic-into-a-reducer#writing-concise-reducers-with-immer
